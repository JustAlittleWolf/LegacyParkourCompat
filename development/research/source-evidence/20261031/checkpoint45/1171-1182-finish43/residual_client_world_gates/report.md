## 1. Chunk readiness and block/collision providers — no-diff

`ClientChunkCache.getChunk(x,z,status,create)` in 1.17.1 (`ClientChunkCache.java:67–76`) and 1.18.2 (`:69–78`) has the same operation order and outcomes: check storage range; read the indexed slot; require a non-null chunk whose stored coordinates match the requested coordinates; return it; otherwise return the singleton empty chunk only when `create` is true, else null. The 1.18 and 1.18.1 selected file hashes are identical, as are the client-cache implementation bodies. `ChunkStatus` is accepted but not consulted in any version. Storage range/index/replace are also unchanged in the compared source; equal readiness includes equal cache contents, center/radius, and query arguments.

The client level inherits the `Level` providers. `Level.getBlockState` (1.17.1 `Level.java:377–383`; 1.18.2 `:369–375`) returns void air outside build height, otherwise resolves the horizontal chunk through `getChunk(sectionX,sectionZ)` and reads that chunk's state. `Level.getChunkForCollisions` (`:572–574` in 1.17.1; `:570–572` in 1.18.2) delegates to `getChunk(x,z,ChunkStatus.FULL,false)`, returning null when unavailable; this delegates to the client cache above. The intermediate `Level.java` provider bodies match these behaviors. The collision iterator consumes that provider and skips absent chunks under the same semantics.

**Disposition:** no-diff under equal chunk readiness, cache bounds/slots, and block-state inputs. This closes the open route group without claiming packet producer equality or packet/tick interleaving.

## 2. Block-entity update to piston collision — accepted conditional difference

The receiver changed its acceptance gate. In 1.17.1 `ClientPacketListener.handleBlockEntityData` (`ClientPacketListener.java:1090–1116`) resolves a block entity at the packet position, then calls `load(tag)` only for a hard-coded set of numeric type IDs and matching classes (spawner, command block, beacon, skull, banner, structure, end gateway, sign, bed, conduit, jigsaw, campfire, beehive). `PistonMovingBlockEntity` is absent from that allowlist, so an equal piston type/tag packet is not loaded by this path. In 1.18 and 1.18.1 (`ClientPacketListener.java:1055–1074`) and 1.18.2 (`:1059–1078`), the receiver resolves `getBlockEntity(pos, packetType)` and, if present, calls `load(tag)` for a non-null tag. Thus a matching typed piston block entity with a non-null raw tag reaches `PistonMovingBlockEntity.load` in the newer path, while the 1.17.1 allowlist skips it. Equal raw NBT does not establish equal post-receiver BE state here.

For directly equal loaded piston fields, `PistonMovingBlockEntity.load` is otherwise behaviorally the same: read `blockState` via `NbtUtils.readBlockState`, `facing`, `progress`, copy progress to `progressO`, then read `extending` and `source` (`1.17.1 PistonMovingBlockEntity.java:316–324`; 1.18+ `:312–320`). Its player-relevant collision provider changed in 1.18.2 (`getCollisionShape`, 1.17.1 `:337–367`; 1.18+ `:332–360`): for `!extending && isSourcePiston`, 1.17.1 unconditionally calls `movedState.setValue(PistonBaseBlock.EXTENDED,true)` for the extra base shape; 1.18.2 adds `movedState.getBlock() instanceof PistonBaseBlock` to that condition. The later source-piston head construction, movement-direction/no-clip early return, progress transform, and shape union are otherwise the same. Therefore with equal loaded fields where `extending=false`, `source=true`, and `movedState` is not a piston base, 1.17.1 attempts an invalid property write (and can fail the collision query), while 1.18.2 leaves that preliminary shape empty and continues to its translated piston-head shape. This changes the local player's collision query when the moving BE is encountered; it is conditional on inconsistent/non-standard state fields, not an unconditional standard-piston movement claim. For valid non-source, extending, or piston-base cases the added check does not change this branch's result.

Factual producer gate (not used to narrow the source claim): ordinary `PistonBaseBlock.moveBlocks` in both 1.17.1 (`PistonBaseBlock.java:275–337`) and 1.18.2 (`:269–329`) creates the source moving BE only in the `bl`/`extending` branch and passes a piston-head state as its `movedState`, with `extending=true` and `source=true` (`MovingPistonBlock.newMovingBlockEntity(..., headState, direction, true, true)`). The ordinary source producer therefore does not satisfy the changed `!extending && source && non-PistonBase` guard. This producer fact is only an applicability fact for standard source creation; it does not erase the equal-raw-NBT receiver/collision difference above.

**Disposition:** accepted conditional difference for a received/loaded typed moving-piston BE whose raw NBT encodes non-extending + source + non-piston moved state; receiver acceptance also differs. Keep valid standard source-piston creation as a factual gating condition. Do not generalize this to ordinary piston-source trajectories.

## Additional requested gate: nonempty in-memory update tags — accepted conditional receiver difference remains

`ClientPacketListener.handleUpdateTags` differs even for equal packet payloads on an in-memory connection. 1.17.1 (`ClientPacketListener.java:1408–1421`) deserializes the packet into a `TagContainer`, checks missing tags, assigns the local `tags` field, and calls `tagContainer.bindToGlobal()` only when `!connection.isMemoryConnection()`. 1.18 and 1.18.1 (`:1341–1353`) share this method. In 1.18.2 (`:1345–1360`), the handler iterates packet registries and `updateTagsForRegistry` skips empty payloads but deserializes and invokes `registry.bindTags(...)` for each nonempty payload without a memory-connection guard; only `Blocks.rebuildCache()` remains guarded. Thus for an in-memory connection carrying a valid nonempty tag payload, receiver-side registry binding differs. Because the receiver itself changes the resulting memberships, this is not closed by assuming equal post-receiver tag membership; downstream tag predicates can observe the differing application. Empty payloads and non-memory connections do not meet this gate.

**Disposition:** retain as an accepted conditional receiver difference for valid nonempty update-tag payloads on in-memory connections; do not treat it as a default movement difference or assume equal output memberships.
