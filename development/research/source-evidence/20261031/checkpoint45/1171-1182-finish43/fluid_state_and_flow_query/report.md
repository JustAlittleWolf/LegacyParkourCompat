## Reachable player routes

- `Entity.tick` reaches `updateInWaterStateAndDoFluidPushing`, which clears stored per-tag heights, checks/pushes WATER at epsilon `0.014`, then checks LAVA at the dimension-selected epsilon (`0.007` ultra-warm, otherwise `0.0023333333333333335`). The bounded tag audit traces `updateFluidHeightAndDoFluidPushing` through the shrunken entity box, the `touchingUnloadedChunk` early return, tag membership, surface-height test, flow averaging/normalization, velocity threshold and horizontal/vertical velocity write. `LivingEntity.travel` consumes the resulting water/lava occupancy and flow-related state through its existing branch order. The exact blocks, chunk availability, fluid memberships and neighboring inputs remain dependencies; this report assumes them equal as assigned.
- `Entity.updateFluidOnEyes` reads `FluidState.getHeight` at `getEyeY() - 0.11111111F` and populates the eye tag state. The tag audit establishes equal WATER eye membership results under equal tags despite the 1.18.2 storage/API migration. The local-player movement callers query WATER.
- `LivingEntity.travel` reads the fluid at `blockPosition()` and calls `canStandOnFluid` in its water and lava branches. The local player inherits `LivingEntity.canStandOnFluid`, which returns `false` on all four releases.
- Ordinary collision reaches `LiquidBlock.getCollisionShape` with `CollisionContext.of(entity)`. When all guards pass, the fluid-standing predicate can supply `LiquidBlock.STABLE_SHAPE`; the local-player context's `canStandOnFluid` test is false on every endpoint, so that guard prevents this fluid-specific support shape for a player. Non-player cases such as Strider standing are outside this player audit.
- `ClipContext.getFluidShape` selects either `FluidState.getShape` or an empty shape according to its fluid selector. In 1.18.2, `Entity.move` adds the previously audited fall-distance-reset ray using the WATER selector. This adds a movement query route in 1.18.2, but is part of the existing 1.18.1→1.18.2 fall-reset change; it is not a new fluid-query delta proposed here.

## Compared terminal query results

- `FluidState.getType`, `isSource`, `isEmpty`, `getHeight`, `getOwnHeight`, `getAmount`, `getFlow`, and `getShape` remain delegations to the same owning fluid operation. `getShape` also delegates without changing arguments or order. The additional 1.18.2 `is(Fluid)` remains a type-identity query and is not a local-player movement selector in the traced routes.
- `FluidState.is(Tag)` / `Fluid.is(Tag)` use `tag.contains(fluid)` in 1.17.1, 1.18 and 1.18.1. In 1.18.2 the movement-facing `FluidState.is(TagKey)` and `Fluid.is(TagKey)` use the fluid's built-in registry holder membership. Given equal tag membership for the same fluid, each returns the same boolean. This covers WATER/LAVA occupancy, eye-water membership, and the 1.18.2 ClipContext WATER selector. The new APIs do not by themselves change query results under that condition.
- `FluidState.isSource` and `isEmpty` continue to delegate to the same fluid predicates. `EmptyFluid` retains `isEmpty=true`, source=false, amount/own-height/height zero, flow `Vec3.ZERO`, and empty shape. Flowing WATER/LAVA states continue to return their LEVEL amount and false source status; source states return amount `8` and true source status.
- `FlowingFluid.getFlow` is semantically identical across all four releases: iterate `Direction.Plane.HORIZONTAL` in the same order; sample each neighbor state; accept empty or same-type fluid; use own-height differences (including the same `0.8888889F` lower-neighbor correction); accumulate step-X/Z times the float difference into doubles; normalize; for FALLING, inspect the same side and above-side solid faces and add `(0,-6,0)` after normalizing; normalize again. With equal center/neighbor fluid states, block states, `Material.blocksMotion` answers and sturdy-face answers, the returned `Vec3` is equal. The player fluid-push loop consumes this result under its pre-existing equal-input gates.
- `FlowingFluid.getHeight` still returns `1.0F` when the above fluid type is same, otherwise own height. `getOwnHeight` remains `amount / 9.0F`; the amount/source implementations and the shape calculation retain the same arithmetic (`amount == 9 && same-above` selects a full block, else a box whose height is the fluid state's height). Under equal state/neighbor inputs, height and shape results are equal. The shape only enters a player movement clip through the newly added 1.18.2 reset ray; the earlier releases have no corresponding reset-ray operation.
- `WaterFluid`/`LavaFluid` preserve source-vs-flowing amounts, source predicates, type-family `isSame`, and inherited flow/height paths. `canBeReplacedWith` and fluid spread/source-conversion methods are fluid-state producers/updates, not direct player query results, so their remaining implementations are excluded from this movement-response closure.

## Collision-context migration and player result

In 1.17.1, 1.18 and 1.18.1, `CollisionContext.canStandOnFluid(FluidState, FlowingFluid)` is implemented by `EntityCollisionContext` as `predicate.test(flowingFluid) && !fluidState.getType().isSame(flowingFluid)`. `LiquidBlock.getCollisionShape` passes the fluid state above and its own `FlowingFluid`. In 1.18.2, the signature and stored predicate use `FluidState`; `EntityCollisionContext` returns `predicate.test(candidateState) && !fluidState.getType().isSame(candidateState.getType())`, and `LiquidBlock` passes the above and current block fluid states. The call shape and type comparison were migrated together. For `LocalPlayer`, the predicate is the inherited `LivingEntity.canStandOnFluid`, always false, so both the predicate result and `LiquidBlock` collision-shape result remain false/empty. The `LivingEntity.travel` can-stand gates likewise stay false. Thus this signature/argument migration has no conditional local-player result delta under equal valid states. A result may differ for other entity subclasses that override the predicate; those are outside this scope.

## Material and adjacent selector results

`Material.isLiquid`, `isSolid`, `blocksMotion`, `isReplaceable` and `isSolidBlocking` retain their field-return bodies. The 1.17.1→1.18.2 `Material.java` source difference is constructor/builder parameter renaming; relevant material constants and getter behavior are unchanged. The movement-facing material read in `FlowingFluid.getFlow` is `getMaterial().blocksMotion()` when considering a lower neighbor, and `isSolidFace` preserves the `Material.ICE` exception before `BlockState.isFaceSturdy`. Under equal block state inputs these material results are equal. `Entity.playStepSound` also reads `Material.isLiquid`, but that is only a sound-selection path. Other flow spread uses of `Material.isSolid` / `blocksMotion` mutate fluid/block state and are excluded producer routes.

`ClipContext.Fluid` keeps NONE, SOURCE_ONLY and ANY selectors; equal `isSource`/`isEmpty` answers yield equal selections. 1.18.2 adds WATER, whose membership answer is equal under equal tag membership. `CollisionContext`/`EntityCollisionContext` were checked only for the fluid-standing response described above. Other collision-context changes and block-shape providers are outside this fluid query slice.

## Coverage conclusion and limits

No new independent terminal fluid/material query difference is proposed. Under equal valid fluid/block states, equal neighboring states and equal tag membership, the audited type/source/empty/amount/height/flow/tag/material answers are equal. The one conditional player-movement query route in the newer endpoint is the already reported 1.18.2 fall-distance-reset ray, which can use equal fluid shapes and the newly added WATER selector but has no old counterpart operation. This audit does not establish world/chunk/tag-resource input equality, active-state producer parity, collision-provider parity, a trajectory witness or full-pair freeze. No claim is made about fluid ticking/spread, fluid state production, rendering, sounds or non-player movement.
