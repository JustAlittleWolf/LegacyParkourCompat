# B6 dynamic movement inputs and dependency closure: 1.20.6 → 1.21.1

## Bounded result

This inventory checks the dynamic state read by the client player tick and its movement calls, across both cutovers 1.20.6 → 1.21 and 1.21 → 1.21.1. Vanilla fluid state, ordinary fluid tags, player movement predicates, effect consumers and the receiving handlers checked are source-equal between 1.21 and 1.21.1. At 1.20.6 → 1.21 the consumer graph remains, but three inputs change from old direct/static sources to attribute-backed values: Swift Sneak → `SNEAKING_SPEED`, Depth Strider → `WATER_MOVEMENT_EFFICIENCY`, and Soul Speed block-factor response → `MOVEMENT_EFFICIENCY` plus movement-speed modifiers. The exact vanilla Soul Speed and armor tag declarations are source-equal at 1.20.6, 1.21 and 1.21.1. Prior authorized packaged-resource evidence closes these default tag payloads and the 1.21.1 enchantment definitions.

The movement meaning of equal-state comparison is concrete: when the LocalPlayer has the same valid effective fluid/tag state and same-tick received attribute/effect state, the client movement consumer can be compared without reconstructing the server's enchantment/effect production or packet trajectory. This assignment does not establish the producer's transition timing or parity, nor arbitrary pack overlays. No new candidate finding is drafted here.

## Paired dynamic-input inventory

### Current fluid state, tags, predicates and flow

- **Checked equal at both cutovers:** `LivingEntity.travel(Vec3)` in 1.20.6 lines 2104–2167 and in 1.21/1.21.1 lines 2091–2150 reads the current `FluidState` at `level().getFluidState(blockPosition())`, gates on `isInWater()` / `isInLava()`, `isAffectedByFluids()` and `canStandOnFluid`, then uses water/lava tag heights, current velocity, sprinting, ground/collision/climbable state and gravity. The surrounding two branches preserve their order and non-Depth-Strider math. The water branch's dynamic Depth Strider term changes from an enchantment helper (old) to `WATER_MOVEMENT_EFFICIENCY` (new); this is detailed below.
- **Checked equal:** `FluidState.java` is byte-identical across endpoints. `FluidTagsProvider` is byte-identical and declares WATER = still + flowing water and LAVA = still + flowing lava. `FluidTags.java` definitions are byte-different at 1.20.6→1.21 as package/registry internals changed, but the `WATER`, `LAVA`, `WATER_FLOWING` and `LAVA_FLOWING` keys used by movement and the provider's effective members are the same. Therefore the source-declared default fluid category memberships are equal. World contents, per-position levels/flow, current height and neighboring-block-dependent current pushing remain dynamic world state; this assignment assumes same-tick equal valid received/world state and did not compare world generation or trajectory production.
- `LivingEntity.travel` lava, jumping-in-fluid (`LivingEntity.java:2643+ old; 2638+ new`), and the current-state movement gates use the same current fluid predicates. Entity water-state refresh/source mechanics are below.
- **Partial, not a change verdict:** all player tick consumers in `LocalPlayer.aiStep` call shared `isInWater`, `isUnderWater`, `isSwimming`, `isEyeInFluid(FluidTags.WATER)` and shift/fluid gates. Underwater sprint/input threshold and swimming flags remain state predicates; full caller graph into all neighboring block flow-update machinery was not exhaustively compared. Rendering-only `waterVisionTime` use is excluded. `Entity.java` current fluid lookup/height/flow implementation and block/fluid update producers were not fully audited as a pair.

### Potion/effect state

- **Checked equal at both cutovers:** movement gates and values in `LivingEntity.travel`, `jumpFromGround`, and `getJumpBoostPower` consume active `SLOW_FALLING`, `DOLPHINS_GRACE`, `JUMP`, and fluid/levitation state with the same tests/math in 1.20.6 and 1.21. At 1.21→1.21.1 the whole `LivingEntity.java` is byte-identical. `LocalPlayer`'s jump-effect input use in its item-use/horse path is also unchanged between 1.20.6 and 1.21; its entire 1.21.1 source is byte-identical to 1.21.
- **Same-valid-received-state route checked:** `ClientPacketListener.handleUpdateMobEffect` constructs an instance from the packet effect holder, duration, amplifier, ambient/visible/icon bits and calls `forceAddEffect`; `handleRemoveMobEffect` calls `removeEffectNoUpdate`. The handlers are textually equivalent at 1.20.6 and 1.21 (method line shifts only), and the client-side application is a consumer of the authoritative packet value for this comparison. Player-effect tick/production, duration decrement timing relative to the player's movement tick, and server application timing were not proven equivalent.
- The effect objects are registry-backed runtime values. This inventory compares movement branches on the same valid effect identity/amplifier/duration-state, not effect-registry resource data or how a server produces/applies effects.

### Equipment, enchantments and attributes

- **Dynamic input refactor at 1.20.6→1.21:** `LocalPlayer.aiStep` sets input slow speed from `clamp(0.3F + EnchantmentHelper.getSneakingSpeedBonus(this), 0, 1)` in 1.20.6:666; 1.21 reads `(float)getAttributeValue(Attributes.SNEAKING_SPEED)` at 663. Vanilla defaults are 0.3 in 1.21 and `Player.createAttributes()` adds it; old code has no `SNEAKING_SPEED` attribute. Built-in Swift Sneak adds per level 0.15 to this attribute in 1.21.1 source registration (`Enchantments.java:559–582`), matching prior default-resource audit. The consuming attribute is syncable. Equal valid `SNEAKING_SPEED` is the relevant client state; old direct helper's equipped enchantment is its old route.
- In `LivingEntity.travel`, 1.20.6 water movement uses `EnchantmentHelper.getDepthStrider(this)`, clamped to 3 and halved off-ground; 1.21 reads `WATER_MOVEMENT_EFFICIENCY`, halves it off-ground and uses that as the interpolation factor. The built-in 1.21.1 Depth Strider attribute effect adds 0.33333334 per level to syncable water efficiency (registration `Enchantments.java:344–368`), with player armor eligibility/tag path source-backed below. Thus the old consumer dynamically reads equipped Depth Strider; the new consumer dynamically reads received water-efficiency value. Other branch predicates, `getSpeed`, fluid state and Dolphin's Grace are independent same-state inputs.
- Soul Speed: old `LivingEntity.getBlockSpeedFactor()` checks that the movement-support block belongs to `SOUL_SPEED_BLOCKS` and that equipped Soul Speed level is positive, returning 1.0; new client `getBlockSpeedFactor()` interpolates the base block factor toward 1 using `MOVEMENT_EFFICIENCY`. The 1.21.1 built-in Soul Speed effects supply `MOVEMENT_EFFICIENCY = 1.0` on a qualifying location change and movement-speed effect; exact effect registration and default definition match (`Enchantments.java:439–522`, resource audit). The producer is server/location-change driven; for this task, only the client consumer under equal valid movement-efficiency/movement-speed state and equal active support-tag result is compared. Do not infer same-tick attribute refresh or transition parity from this consumer closure.
- `Attributes.java` changes at 1.21 to register syncable `MOVEMENT_EFFICIENCY` (default 0), `SNEAKING_SPEED` (0.3, range 0–1) and `WATER_MOVEMENT_EFFICIENCY` (0, range 0–1). `Player.createAttributes()` adds `SNEAKING_SPEED`; `LivingEntity.createLivingAttributes()` supplies the movement-efficiency attributes. Existing `MOVEMENT_SPEED` and jump strength remain, with old player movement-speed base 0.1F retained. At 1.20.6 there are no analogous sneak/water/movement-efficiency attributes; helper enchantment direct reads are used instead.
- **Same-valid-received-state route checked:** `ClientPacketListener.handleUpdateAttributes` resolves the entity, obtains its `AttributeMap`, finds each snapshot's instance, applies base value and modifiers; the handler's control flow is unchanged between 1.20.6 and 1.21 and 1.21.1. This supports comparing the already-received attribute state as consumed by LocalPlayer. It does not prove server-side computation, packet completeness, or same tick arrival. Attribute defaults/registration are source facts, not proof of runtime server state.
- Equipment packet handler `handleSetEquipment` applies each slot by calling `LivingEntity.setItemSlot` on the client entity; old/new branches are the same. Old direct enchantment reads therefore consume equipped stack data as received. In 1.21, equipment alone is not a substitute for the separate attribute snapshot for these movement consumers; compare equal received effective attributes, not inferred attributes from packet arrival. Full equipment modifier recalculation and server packet order are outside this equal-state assumption.

## Explicit residual dependencies and limits

1. Effective same-tick server-sent `MOVEMENT_SPEED`, `MOVEMENT_EFFICIENCY`, `SNEAKING_SPEED`, and `WATER_MOVEMENT_EFFICIENCY` values are assumed equal for their paired consumers. Server effect production, attribute calculation, equipment-to-modifier processing and packet ordering/arrival timing remain unverified and are not claimed.
2. Effective per-position current `FluidState`, fluid height, water/lava membership, and neighbor-dependent current/flow inputs are assumed equal. `Entity.java` fluid refresh, full world/block fluid production, and trajectory equality are unexamined.
3. Active potion/effect identity and amplifier are assumed equal and valid at the consumer tick. Effect production, duration update order around packet receipt, and equal-tick synchronization remain unexamined.
4. Vanilla default Soul Speed/armor tag and 1.21.1 enchantment resource closure is supported by the allowed resource audit; arbitrary data/resource pack overlays and dynamically redefined enchantments/tags are not covered.
5. This inventory does not close every LocalPlayer-tick terminal input (e.g. all entity/world state writers, block support/jump factors, gravity, collision shapes, vehicle branches, or every direct external response); separate lanes own the remaining movement graph. In this bounded dynamic-input assignment, no broad full-pair completeness claim is made.
