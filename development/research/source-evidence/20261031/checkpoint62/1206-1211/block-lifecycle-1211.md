## Source differences and lifecycle route

`Level.setBlock` writes the new state through `LevelChunk.setBlockState` before invoking lifecycle callbacks. In both endpoints, `LevelChunk.setBlockState` calls the old state's `onRemove` only on the logical server; on the client it removes the old block entity when the block changes. After the old callback, it calls the new state's `onPlace` on the server and creates or updates the new block entity. See `net/minecraft/world/level/Level.java:211-251` and `net/minecraft/world/level/chunk/LevelChunk.java:238-302` in either endpoint.

`BlockBehaviour.onRemove` is unchanged: if the old state has a block entity and the replacement is a different block, it removes the old entity. The four callback changes move their neighbor notifications across this cleanup call, with their existing branch conditions retained:

- `ChiseledBookShelfBlock.onRemove`: 1.21 notifies comparators after dropping and clearing a nonempty shelf but before `super.onRemove`; 1.21.1 calls `super.onRemove` first and then notifies only when that shelf was nonempty. The `!oldState.is(newBlock)` gate is unchanged. In `Level.updateNeighbourForOutputSignal`, this directly schedules adjacent comparator reevaluation; item dropping and inventory clearing are outside movement scope.
- `LecternBlock.onRemove`: book popping remains before `super.onRemove`; the powered-state notification for the block below moves from before to after entity removal. The `!oldState.is(newBlock)` and old `POWERED` gates are unchanged. Book/item entity effects are excluded.
- `SculkSensorBlock.onRemove`: `super.onRemove` now precedes the neighbor notifications, still only when the removed state was `ACTIVE` and the replacement is a different block. Its redstone output is read from the old block state (`POWER`/`PHASE`), not its block entity.
- `ShulkerBoxBlock.onRemove`: it still caches whether a ShulkerBoxBlockEntity existed, but now removes it through `super.onRemove` before notifying comparators. The different-block gate is unchanged.

The LevelChunk replacement change is at `LevelChunk.java:289-301` in 1.21.1. Before reusing a fetched block entity for a new block-entity state, it now tests `isValidBlockState`; a rejected entity is removed and a new entity is constructed. `BlockEntity.java:41-55, 247-250` also validates constructor and setter states. `isValidBlockState` delegates to `BlockEntityType.isValid`, which checks membership of the state's block in that entity type's registered valid-block set (`BlockEntityType.java:300`); it does not change block-state collision math.

Paired callback locations are: chiseled bookshelf 1.21 `ChiseledBookShelfBlock.java:188-202`, 1.21.1 `:188-211`; lectern 1.21 `LecternBlock.java:208-219`, 1.21.1 `:208-220`; sculk sensor 1.21 `SculkSensorBlock.java:121-127`, 1.21.1 `:121-128`; shulker box 1.21 `ShulkerBoxBlock.java:177-183`, 1.21.1 `:177-185`. The block-entity addition is paired against 1.21 `BlockEntity.java:39-42, 234-236` and `LevelChunk.java:284-300`. The relevant client update, collision, comparator, base block behavior, and entity type sources listed above have identical source hashes at both endpoints.

## Movement-path closure for this bounded area

The client receives authoritative block updates through `ClientPacketListener.handleBlockUpdate` → `ClientLevel.setServerVerifiedBlockState` → `ClientLevel.setBlock` → `Level.setBlock` → `LevelChunk.setBlockState` (`ClientPacketListener.java:781-783`, `ClientLevel.java:145-155`). The client branch does not invoke these four `onRemove` callbacks. It removes an old entity on a different-block replacement before movement queries use the new state.

Player collision uses `Entity.move`/`Entity.collide` and `CollisionGetter.getBlockCollisions`, which obtains `BlockState` collision shapes (`Entity.java:618, 875-944`; `CollisionGetter.java:83-90`; `BlockBehaviour.java:308, 633-634`). Among these four blocks, `ShulkerBoxBlock.getShape` is the relevant entity-dependent collision provider: it uses `ShulkerBoxBlockEntity.getBoundingBox`; the chiseled bookshelf has no entity-dependent shape override, the lectern's shape/collision shapes are fixed shapes, and the sculk sensor shape is its fixed `SHAPE` (`ShulkerBoxBlock.java:211-219`, `LecternBlock.java:120-127`, `SculkSensorBlock.java:167-169`). Under ordinary valid replacements, a different old block's entity is removed in both endpoints before the new state is exposed to the next client collision query, and the new block entity is then created for the replacement. Same-block state changes keep an entity whose registered type accepts that block. Thus the new validity check does not change any of these blocks' collision providers for the same valid state/world data.

The callback notifications can reach redstone neighbors, and a resulting piston can eventually push a player. For the comparator route changed by the shelf/shulker callbacks, `ComparatorBlock.checkTickOnNeighbor` schedules reevaluation for two ticks later when its sampled output/powered state differs (`ComparatorBlock.java:133-143`); by then LevelChunk has completed entity replacement. `Level.setBlock` also emits a new-state analog-output notification after `LevelChunk.setBlockState` returns when the replacement has analog output (`Level.java:239-243`). Lectern and sensor notifications sample the already-installed replacement state; their relevant powered output is stored in state, not the entity. These sources show no changed final movement input for a valid transition. A malformed/stale entity whose type rejects the current state can have its lifecycle and, for a shulker entity, queried shape repaired in 1.21.1; that is not evidence for a historical movement change on a valid block/world state.

No source-confirmed player movement difference was found in this bounded lifecycle slice. Rendering/animation, comparator inventories, book/item drops and other inventory consequences are excluded. This conclusion does not close unrelated 1.21→1.21.1 movement slices or establish pair freeze.
