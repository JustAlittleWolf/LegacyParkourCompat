## Residual packet and callback routes

I enumerated `ClientPacketListener` handlers with a resolved-entity or current-player reference and searched for direct position, velocity, on-ground, pose, rotation, abilities, rider/camera, attribute, effect and equipment writes. Exact `ClientPacketListener.java`, `LocalPlayer.java`, `Entity.java`, `LivingEntity.java`, `Player.java`, `AttributeMap.java`, and `MultiPlayerGameMode.java` source hashes for 1.21 and 1.21.1 are identical. Thus the second boundary has no change in these slices.

### Current local player and entity position/velocity receivers

- `handleMovePlayer(ClientboundPlayerPositionPacket)` writes local player position, previous-position fields, velocity and relative/absolute rotations, then acknowledges and responds to the packet (`ClientPacketListener.java:618-686` in 1.20.6; `:620-688` in 1.21/1.21.1). The relative-axis selection, preserved-versus-zeroed velocity, update order, rotation math, teleport acknowledgement and response are unchanged.
- `handleSetEntityMotion` resolves by entity ID and applies `lerpMotion`; old handler divides each raw integer component by `8000.0`, while 1.21 passes the packet getters' already-divided values. For equal valid raw short values, the double operands are identical. `Entity.lerpMotion` delegates to `setDeltaMovement` in all three endpoints. This is an equivalent location/refactor, not a movement difference.
- `handleExplosion` adds all three packet knockback floats to the current local player's velocity after finalizing the explosion; the player velocity write and order are unchanged. Explosion block/visual effects were not analyzed here.
- `handleMoveEntity` applies relative position/rotation interpolation and on-ground only when `!entity.isControlledByLocalInstance()`. `handleTeleportEntity` always updates the packet-position codec, then has the same false-local-control gate for interpolation and on-ground. `LocalPlayer.isEffectiveAi()` returns `true` in a client level in all compared versions, overriding `Entity.isEffectiveAi()`'s logical-server default; consequently the interpolation/on-ground mutation is skipped for the current LocalPlayer. Other entities are outside this player-response disposition.
- `handleRotateMob` changes interpolated head yaw only. It does not write local player position, velocity, body yaw or pitch; the remaining head interpolation is not used by the ordinary LocalPlayer travel direction path. `handleRemoveEntities` removes the resolved entity and does not write player movement state.
- `handleSetEntityPassengersPacket` can attach the local player to a vehicle and, for a newly boarded boat, sets the player's yaw/head yaw to the boat yaw. The listener route is unchanged. Movement while riding is excluded vehicle physics; no boundary difference is accepted from this route. `handleMoveVehicle` writes vehicle state, also excluded. `handleEntityLinkPacket` changes leash-holder state only; in 1.21 the receiver generalizes Mob to Leashable and still does not target the LocalPlayer movement path.
- `handleSetEntityData` assigns synchronized values to the entity. The pose/dimensions callback path is the same: `Entity.onSyncedDataUpdated` refreshes dimensions for pose metadata; `LocalPlayer.onSyncedDataUpdated` adds its hand-use state handling. No changed current-player position/velocity/pose write was found in these callbacks. Full block collision/provider effects are outside this X1 packet slice.

### Movement-driving client state and other responses

- `handlePlayerAbilities` writes flying, build/invulnerability permissions and flying/walking speeds through the same handler in both pairs. `handlePlayerInfoUpdate` and `handleGameEvent(CHANGE_GAME_MODE)` call the same local mode update route. `LocalPlayer.onGameModeChanged` clears vertical velocity for spectator mode under the same condition. `handleSetCamera` is unchanged; camera state also gates copying input into local impulses in `LocalPlayer.serverAiStep`, whose camera comparison and call path are unchanged.
- `handleUpdateAttributes`, `handleSetEquipment`, `handleUpdateMobEffect` and `handleRemoveMobEffect` have unchanged receiver/application flow for equal valid packet attributes, stacks and effects. Attribute/effect/enchantment input producers and default memberships are not re-audited in this residual X1 slice; dynamic movement-input closure remains a separate dependency area.
- `handleEntityEvent` forwards events to the entity except for client effects (guardian/sniffer sounds, totem particles/activation). `LocalPlayer.handleEntityEvent` only handles permission-level IDs 24–28; inherited `LivingEntity`/`Player` event branches are sounds, particles, item/effect visuals or death/damage state. No changed event branch writes local player position, velocity, on-ground or movement ability. Damage/death resolution is excluded.
- `handleBlockEvent` reaches `ClientLevel.blockEvent` and inherited `Level.blockEvent`, which invokes the current block state's callback; the dispatch path is unchanged. Piston motion invoked by that callback reaches `Entity.move(MoverType.PISTON, ...)`; block callback/shape closure is owned by the bounded collision/event slice. `handleLevelEvent` forwards client effects to `ClientLevel.levelEvent`/renderer and contains no player movement call. Chunk/block update packets change world state, not player fields directly; resulting collision dependencies are out of this residual receiver slice.
- `handleBundlePacket` dispatches bundled packets through the ordinary packet handler paths without a new player movement write. `handleTickingState` and `handleTickingStep` alter simulation tick rate/frozen tick count, not the movement operation for an individual fixed tick. Inventory selection, camera/presentation, experience, spawn-location, health/food, and damage-event handlers contain no eligible changed direct movement write in this scan; their non-movement state or excluded producers are not promoted to findings.

## Unreviewed candidate: respawn preserves base movement attributes

**Source candidate only; no independent verdict attached.** In `ClientPacketListener.handleRespawn`, both sides create a replacement `LocalPlayer`. In 1.20.6 (`ClientPacketListener.java:1131-1133`) prior attributes are copied only under `packet.shouldKeep((byte)1)` by `AttributeMap.assignValues`. When that bit is false, the new player keeps its constructed defaults. In 1.21 and 1.21.1 (`ClientPacketListener.java:1134-1138`), the true branch calls `assignAllValues`, but the false branch newly calls `assignBaseValues(oldPlayer.getAttributes())`; `AttributeMap.java:111-117` copies each matching old base value into the replacement and does not copy modifiers.

Concrete equal-state input witness: before the same valid respawn packet with keep-attributes false, the local player's syncable `JUMP_STRENGTH` base value is `0.6` in both clients. `Attributes.JUMP_STRENGTH` is syncable and range `[0,32]` with default `0.42F` (1.20.6 `Attributes.java:45-47`; 1.21/1.21.1 `:53-55`); `LivingEntity.createLivingAttributes()` includes the attribute (1.20.6 `LivingEntity.java:292-305`; 1.21/1.21.1 `:304-317`). `handleUpdateAttributes` accepts its packet snapshot by `AttributeInstance.setBaseValue` (1.20.6 `ClientPacketListener.java:2059-2083`; 1.21/1.21.1 `:2062-2086`). Both old/new `LivingEntity.getJumpPower()` read that effective value. With keep-attributes false, old reconstruction uses new default `0.42F`, whereas 1.21 reconstruction copies base `0.6`; the later common `resetPos`, `adjustPlayer` and `setLocalMode` do not overwrite `JUMP_STRENGTH` (the game-mode methods only update `Abilities`).

On the next ordinary locally controlled grounded jump with the same input, block jump factor, and active effect state, `LivingEntity.jumpFromGround()` writes `getJumpPower()` into Y delta movement (1.20.6 `LivingEntity.java:2057-2079`; 1.21/1.21.1 `:2043-2067`). Since the attribute base is the only changed input in this witness, the direct jump velocity differs (`0.42F` vs `0.6F` on a unit block-jump factor and no jump effect). LocalPlayer reaches this inherited route: its `isEffectiveAi()` returns true on client; the living AI branch processes jump input; the game-mode used is Survival, not a vehicle. No producer, packet-order timeline, runtime or trajectory claim is made; comparison assumes only the same valid pre-respawn attribute state and same valid respawn packet as requested.

The client source verifies a movement-affecting state-copy delta. The candidate needs independent blind review and a separate applicability decision before acceptance. Its interval is bounded to 1.20.6→1.21; all selected receiver/attribute/jump source hashes are identical from 1.21→1.21.1.
