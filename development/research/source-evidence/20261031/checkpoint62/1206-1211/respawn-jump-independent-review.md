## Trace and finding

- **Respawn construction and gate.** In 1.20.6 `ClientPacketListener.handleRespawn` constructs a replacement `LocalPlayer` at lines 1109–1114 and installs it at 1116–1118. The only attribute-copy operation is guarded by `shouldKeep((byte)1)` at lines 1131–1133; when false, no attributes are copied. In 1.21 / 1.21.1 the new player is likewise constructed (1110–1115) and installed (1117–1119), but the same gate now has an `else` at lines 1134–1138: true calls `assignAllValues`, false calls `assignBaseValues`.
- **What survives the 1.21 false branch.** `AttributeMap.assignBaseValues` (1.21 / 1.21.1 `AttributeMap.java:111–117`) walks instantiated entries in the old map, obtains the corresponding entry from the new map, then sets its base to the old base. It intentionally does not copy modifiers. The 1.20.6 `AttributeMap` has no `assignBaseValues` method. `handleUpdateAttributes` at 1.20.6 `ClientPacketListener.java:2067–2080` and 1.21 / 1.21.1 `:2070–2082` obtains each attribute instance and writes the packet snapshot’s base with `setBaseValue`; thus a prior valid syncable attribute update establishes the old map entry and base assumed in this finding.
- **Jump strength default and applicability.** `Attributes.JUMP_STRENGTH` is registered in all compared versions with default `0.42F`, range `[0.0, 32.0]`, and `setSyncable(true)` (1.20.6 `Attributes.java:45–47`; 1.21 / 1.21.1 `:53–55`). `LivingEntity.createLivingAttributes` includes it in each version (1.20.6 `LivingEntity.java:294–305`; 1.21 / 1.21.1 `:304–318`), so the replacement player's newly created attribute map has the 0.42 default. A base value of 0.6 is inside the registered range and is syncable. Given the same raw attribute snapshot and old-player state before respawn, 1.20.6 leaves the replacement at 0.42; 1.21 / 1.21.1 copies the instantiated 0.6 base into the replacement despite the respawn packet's `shouldKeep((byte)1)` being false.
- **Reachable movement consequence.** `LocalPlayer.serverAiStep` copies `input.jumping` into the player `jumping` state while controlling the camera (1.20.6 `LocalPlayer.java:612–618`; 1.21 / 1.21.1 `:608–614`). The inherited `LivingEntity.aiStep` grounded-jump gate calls `jumpFromGround` when on ground and `noJumpDelay == 0` (1.20.6 `LivingEntity.java:2651–2657`; 1.21 / 1.21.1 `:2646–2652`). `getJumpPower(float)` multiplies `getAttributeValue(JUMP_STRENGTH)` by the supplied scale and block jump factor, then adds jump-boost power (1.20.6 `LivingEntity.java:2061–2063`; 1.21 / 1.21.1 `:2047–2049`). In the ordinary grounded, non-boosted example with block jump factor 1, `jumpFromGround` writes that result as the Y component of delta movement (1.20.6 `LivingEntity.java:2070–2074`; 1.21 / 1.21.1 `:2056–2060`). Thus this state difference directly changes the local jump's Y-velocity write from 0.42 to 0.6 under those stated conditions.

## Scope boundary

The finding requires only a prior valid client attribute state with the syncable `JUMP_STRENGTH` base instantiated (for example, a snapshot base of 0.6) and the same respawn packet with `shouldKeep((byte)1) == false`. No assertion is made that a particular server emits that snapshot, that a specific ordering occurs, or what subsequent tick trajectory results. The intermediate 1.21 → 1.21.1 comparison is unchanged for these source slices.
