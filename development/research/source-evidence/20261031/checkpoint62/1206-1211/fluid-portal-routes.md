## Fluid-current and eye-state route

### Route and dependencies

`Entity.tick` calls `baseTick`; `baseTick` performs portal bookkeeping, then calls fluid pushing, eye-fluid refresh and swimming refresh in that order. The fluid route is inherited by `Player`/`LocalPlayer`; `LocalPlayer.tick` calls `super.tick` before its position packet send (`LocalPlayer.java:190-203` in 1.20.6; `:191-204` in 1.21/1.21.1). On the client, `LivingEntity`/`Player` movement uses the refreshed state in `Player.travel` and inherited `LivingEntity.travel`, which writes velocity and invokes `move`.

The paired tick and fluid-height routines are structurally unchanged:

- `1.20.6 net/minecraft/world/entity/Entity.java:418-441`: base-tick call order; `updateInWaterStateAndDoFluidPushing` at `:1203-1225`; `updateFluidOnEyes` at `:1227-1239`; `isEyeInFluid` at `:1303-1305`; `updateFluidHeightAndDoFluidPushing` at `:3052-3117`.
- `1.21/1.21.1 net/minecraft/world/entity/Entity.java:419-442`: same call order; water/lava update at `:1242-1264`; eye-fluid refresh at `:1266-1278`; `isEyeInFluid` at `:1342-1344`; fluid-height update at `:3091-3156`.

The fluid update itself has no client/server guard: `baseTick` invokes it for any entity on either logical side. In the LocalPlayer route it runs in the client tick and is an inherited entity calculation. The height/current routine first returns `false` if `touchingUnloadedChunk`; otherwise it deflates the entity AABB by `0.001`, floors minima and ceils maxima, scans x/y/z cells in the same nested order, reads each `FluidState`, tests the requested fluid tag and requires the cell fluid surface to reach the deflated box bottom. It records maximum depth. If `isPushedByFluid` is true it sums each cell's `getFlow`; flow is depth-scaled below 0.4. A nonzero aggregate is averaged by contributing-cell count, normalized only for non-Player entities, scaled by the passed coefficient, raised to minimum length `0.0045000000000000005` only when both existing horizontal velocity components are below `0.003` and the scaled push is shorter, then added to velocity. The player receives this current without the non-player normalization.

The inputs and neighbor reads are unchanged across the three trees: WATER current coefficient `0.014`; LAVA coefficient `0.007` in ultra-warm dimensions, otherwise `0.0023333333333333335`; boat-above-water suppression clears `wasTouchingWater`; water contact sets `wasTouchingWater`, resets fall distance and clears fire (splash is first-contact-only and non-first-tick). The eye query uses `getEyeY`, `BlockPos.containing(x, eyeY, z)`, the fluid at that one cell, its `getHeight`, strict `fluidTop > eyeY`, and all registry tags attached to that fluid state. It skips eye sampling while a non-submerged boat's bounding box spans the eye. `wasEyeInWater` is assigned from the prior `isEyeInFluid(WATER)` value before the set is cleared and refilled, preserving this operation order.

`FluidState.getFlow` and `getHeight` delegate to the registered `Fluid`; `getTags` streams its holder tags (`FluidState.java:49-59,91-93,104-105,132-134`). `FlowingFluid.getFlow` reads the four horizontal fluid neighbors; for empty-height neighbors it checks that neighbor block's `blocksMotion`, then the fluid one block below; falling fluid also tests solid faces at each horizontal neighbor and the block above it. It uses same-fluid identity/empty checks, fluid own heights, FALLING state, sturdy faces and the IceBlock exception, then normalizes (`FlowingFluid.java:54-115`). Height reads the fluid directly above for same-fluid identity and otherwise uses own height; own height is amount / `9.0F` (`:425-436`). These methods are byte-identical across 1.20.6, 1.21 and 1.21.1.

`FluidTags.java:8-9` exposes WATER and LAVA. The 1.21 `ResourceLocation.withDefaultNamespace` change at `FluidTags.java:14-15` is only construction of the same default-namespace keys. Eye membership remains the full tag set on the fluid holder, while current/depth membership uses only the WATER/LAVA keys.

### Player consumers and compared outcomes

- `Player.travel` adds the same swimming vertical-look correction in all three releases: it uses look-vector y, `0.085` if below `-0.2` else `0.06`, gated by look y `<= 0`, jumping, or a nonempty fluid state at `(x, y + 0.9, z)`. The same movement is added to y velocity. In 1.20.6 the method begins at `Player.java:1473`; in 1.21.1 it begins at `:1456` and the exact block reads fluid at `:1460-1464`.
- `LivingEntity.travel` retains the water/lava branch gates, inputs and order: locally controlled instance, gravity/slow-falling, fluid state at block position, water branch if `isInWater && isAffectedByFluids && !canStandOnFluid`, otherwise lava branch if `isInLava && isAffectedByFluids && !canStandOnFluid`. It executes `moveRelative`, movement, velocity damping/falling adjustment and collision jump write. 1.20.6 lines `2104-2167`; 1.21.1 lines `2091-2149`.
- One fluid-movement consumer changed between 1.20.6 and 1.21: the water travel branch replaces the Depth Strider enchantment level and its cap / off-ground half / division by 3 (`LivingEntity.java:2117-2129`) with `Attributes.WATER_MOVEMENT_EFFICIENCY`, off-ground half and direct interpolation (`1.21.1 LivingEntity.java:2104-2112`). This is a movement-affecting change, but its attribute/equipment provenance and assignment are owned by the separate attribute/effect/equipment lane; retained here as an open interface dependency, not as a finding. The LAVA movement branch and `Player.travel` fluid gates are otherwise unchanged in the paired slices.
- `LivingEntity` fluid-jump consumption remains based on `isAffectedByFluids`, LAVA versus WATER height, `isInWater`, fluid jump threshold, ground state and no-jump delay; the jump dispatch reads `getFluidHeight(WATER/LAVA)` and calls `jumpInLiquid` or ground jump (`1.20.6 LivingEntity.java:2643-2667`; `1.21.1 :2638-2662`). Related underwater breathing/drowning logic is outside the requested movement response; only its `isEyeInFluid(WATER)` input interface was observed.

**Verdict:** current generation, surface/depth sampling, eye-fluid sampling, tags, flow-neighbor dependencies and direct velocity addition are unchanged at these endpoints. Fluid-dependent player travel is partially changed due to WATER_MOVEMENT_EFFICIENCY and awaits the separate attribute/equipment input audit. The existence of attribute inputs in water-travel is confirmed; their broader production/consumer coverage is unexamined here.

## Nether and End portal route

### 1.20.6 route

`NetherPortalBlock.entityInside` at `net/minecraft/world/level/block/NetherPortalBlock.java:84-87` calls `Entity.handleInsidePortal` when `canChangeDimensions()`. `handleInsidePortal` (`Entity.java:2049-2059`) refreshes portal cooldown if active; otherwise only the server records immutable entrance position and both logical sides set `isInsidePortal=true`. On the next `baseTick`, `handleNetherPortal` (`Entity.java:2061-2089`) is gated by `level instanceof ServerLevel`; it increments `portalTime`, checks destination availability, nether enabled and no passenger, sets cooldown, calls `changeDimension`, then clears the inside flag. When entry ends, timer decays by 4 to zero. Thus timer-driven dimension change is server-owned.

`EndPortalBlock.entityInside` (`EndPortalBlock.java:48-55`) is also server-only, requires `canChangeDimensions` and AABB/shape intersection, then calls `changeDimension` to END or OVERWORLD. Client never runs that direct End portal response.

`LocalPlayer.aiStep` calls `handleNetherPortalClient` outside `ReceivingLevelScreen` (`LocalPlayer.java:647-655`). Its helper only clears the portal flag, closes eligible screens, plays trigger sound, changes spinner intensity, or decays cooldown (`:822-850`); it does not call position, delta movement, pose, or dimensions writers.

### 1.21 / 1.21.1 route and changed gates

`NetherPortalBlock.entityInside` (`NetherPortalBlock.java:97-101`) calls `setAsInsidePortal` when `canUsePortal(false)`. The inherited check is `alive && !passenger` (`Entity.java:2591-2593`). `setAsInsidePortal` (`Entity.java:2121-2131`) refreshes cooldown when active; otherwise it updates or creates `PortalProcessor`, which stores portal object, entry position, timer and inside-this-tick flag. `Entity.baseTick` calls `handlePortal` (`Entity.java:419-442`); the handler at `:2134-2155` is gated on `ServerLevel`, processes portal timer/cooldown, asks the portal for a destination and calls `changeDimension` only when server conditions pass. `PortalProcessor.processPortalTeleportation` (`PortalProcessor.java:21-29`) advances only for continuously-inside ticks with `canUsePortal(false)` true; decay subtracts four and expiration clears processor (`:40-46`).

`EndPortalBlock.entityInside` now checks `canUsePortal(false)` plus shape intersection on client and server (`EndPortalBlock.java:53-61`). In the server End-to-Overworld first-credits branch it calls `showEndCredits`; otherwise it enters the portal processor. This is a source-visible client entry-state change relative to 1.20.6's server-only End block. In examined client code, it creates portal-local state and transition visuals, not position/velocity/pose writes.

`LocalPlayer.aiStep` calls `getActivePortalLocalTransition() == Portal.Transition.CONFUSION` and updates cooldown outside `ReceivingLevelScreen` (`LocalPlayer.java:643-652`). `getActivePortalLocalTransition` merely reads the processor's local transition (`:811-813`); `handleConfusionTransitionEffect` changes screen, plays sound, updates spinner intensity and clears the per-tick inside flag (`:823-853`). These are UI/visual state only. Nether transition time is server rule-dependent in `NetherPortalBlock.java:103-115`; `PortalProcessor` uses server portal policy and contains no player position, velocity, pose or movement write.

### Authority and packet boundary

The portal's actual dimensional movement remains server-authoritative in both slices. 1.20.6 reaches `ServerPlayer.changeDimension(ServerLevel)` from server portal processing; it sends `ClientboundRespawnPacket`, then calls `connection.teleport` with the server-selected `PortalInfo.pos` (`ServerPlayer.java:788-824`). 1.21.1 calls `ServerPlayer.changeDimension(DimensionTransition)` after `Entity.handlePortal` server gates; for different dimensions it sends `ClientboundRespawnPacket` then teleports to transition `pos` (`ServerPlayer.java:840-878`).

The narrow receiving path was checked: `ClientPacketListener.handleRespawn` swaps dimension-level/local player and calls `resetPos` (`1.20.6 ClientPacketListener.java:1073-1144`; `1.21.1 :1076-1150`); the accompanying `handleMovePlayer(ClientboundPlayerPositionPacket)` writes local position and delta movement from the authoritative correction (`1.20.6 :618-668`; `1.21.1 :620-670`). That is a server-driven direct position/velocity response boundary, not client replay of portal physics. This note does not audit the general position-packet response sweep beyond these portal dispatches.

**Verdict:** the portal entry/timer machinery changes substantially at 1.21, and the End portal gains client entry state, but the examined LocalPlayer portal path still changes only UI/visual/cooldown state. Portal destination movement is server-side and reaches the client through authoritative respawn/position packets. No new client-local portal write to position, velocity or pose was found. The 1.21 and 1.21.1 files for `Entity`, `LocalPlayer`, portal blocks, and `PortalProcessor` have identical SHA-256; no difference was found between those two releases in the assigned slices.
