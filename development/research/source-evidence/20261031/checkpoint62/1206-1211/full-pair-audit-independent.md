## Authority and reachable tick path

Compared `Minecraft.tick` → `ClientLevel.tickEntities` → `tickNonPassenger` → `LocalPlayer.tick` → inherited `LivingEntity`/`Player` tick and AI movement path in 1.20.6 and 1.21. Both client levels tick the local player as a normal non-passenger entity. `LocalPlayer.tick` enters `super.tick()` only when its current block is in a loaded chunk. `LocalPlayer.isEffectiveAi()` is `true`; `Player.isLocalPlayer()` defaults to `false`, and `LocalPlayer.isLocalPlayer()` is `true`. Thus `Entity.isControlledByLocalInstance()` selects client-local authority for the local player and for a vehicle controlled by that local player, while remote players on the client do not obtain local authority from the predicate. Vehicle physics itself is excluded. These predicate bodies and the ClientLevel/Minecraft tick entry code have no source-hash change from 1.21 to 1.21.1.

This traces the normal local simulation gate, not every packet-originated position/velocity response. `ClientPacketListener` changes across 1.20.6→1.21 and its player-position/velocity response writers were not fully audited.

## Supplementary source audit: world-border margins and knockback scope (2026-10-31)

### WorldBorder lower-margin candidate — accepted movement output

I checked `WorldBorder.isWithinBounds(double,double,double)`, `isInsideCloseToBorder`, `getCollisionShape`, `Entity.collide`, and `Entity.collideBoundingBox` directly in all three canonical sources. At 1.20.6, the lower X/Z checks are strict (`>`); at 1.21 and 1.21.1 they are inclusive (`>=`). The close-to-border margin and `< 2 * margin` distance test are unchanged. The old and new collision methods both conditionally add the border shape before block shapes; the 1.21 helper refactor preserves that route while reading the changed predicate.

The reviewed witness is valid as a source-level equal-input movement comparison: empty collision area; player AABB width `0.6`, center `(-0.1, 0.5)`; border min `(0.9, 0.5)` from size `1000` and center `(500.9, 500.5)`; airborne; requested vector `(0,0,-0.39)`. The swept AABB has size `0.6 × 0.99` in X/Z, so margin is `1.0`. Its X center equals `minX - margin`, and distance-to-border is `-1.0`, passing the unchanged near-border gate. Old strict bounds reject adding the border shape; new inclusive bounds accept it. The border collision interior uses `floor(minZ)=0`; the exterior shape clips the negative-Z request at `0 - AABB.minZ = -0.2`. With no other colliders, the source-resolved vector changes from `(0,0,-0.39)` to `(0,0,-0.2)`. `Entity.move` reaches this `Entity.collideBoundingBox` path. The same method/predicate files are byte-identical at 1.21 and 1.21.1. No trajectory or producer claim is needed.

### Separate `WorldBorder.isWithinBounds(AABB)` change — no eligible local movement callsite found

The AABB overload changes from strict rectangle overlap to testing the minimum corner and an inset maximum corner. I searched all canonical 1.21 callsites and traced the position-producing consumers. `CollisionGetter.findFreePosition` filters block shapes with this overload; its `Entity` caller is `fudgePositionAfterSizeChange`, which `refreshDimensions` invokes only off-client and only for non-`Player` entities. The other `findFreePosition` caller is `PortalShape.findCollisionFreePosition(ServerLevel, ...)`, a server portal-placement route. `LivingEntity.baseTick` also uses the AABB overload only inside `!level.isClientSide` for out-of-border player damage, which is excluded. Remaining callsites are spawn/AI/presentation or block placement checks. Thus this overload is a changed source terminal, but the inspected callers do not establish an eligible local-player movement output; it is closed as out of scope for this audit. This is distinct from, and does not weaken, the accepted lower-margin `Entity.collide` witness above.

### `LivingEntity.knockback` — source change verified, excluded producer; receiver remains closed

I verified the source difference in `LivingEntity.knockback`: 1.21 adds random near-zero horizontal perturbation at squared-length threshold `1.0E-5`, while 1.20.6 performed caller-side perturbation in `hurt` at `1.0E-4`. The supplied close-range attack witness exercises a `ServerPlayer` victim and can yield a different server-produced velocity. However, `LivingEntity.hurt` returns on `level.isClientSide` before its damage/knockback route, and the changed method is in server attack/damage production. Under the assigned exclusions for attack/damage calculation and server physics, this is **not accepted as an eligible LocalPlayer movement delta**.

The direct client motion receiver remains closed: 1.20.6's `handleSetEntityMotion` divides the raw packet integer components by `8000.0` at the callsite; 1.21/1.21.1 packet getters perform that same double division before the unchanged `lerpMotion` write. For equal raw packet components, the received vector is identical. This matches the earlier packet-response disposition; it does not claim equality of the excluded server-generated packet contents.

The AABB-overload change and server knockback change add no eligible local movement finding under the stated callsite/scope constraints. ## Follow-up correction: collision helper classification and step-up witness (2026-10-31)

The preceding core cross-check listed `Entity.collideWithShapes` among methods whose candidate behavior was still open. That wording was too broad: the helper's axis clipping body is shared/equal across the endpoints, as are `Shapes.collide` and `VoxelShape.collide`. It is a closed numerical terminal. The remaining step-up delta is the 1.21 candidate-height selection and its integration in `Entity.collide`/`collideBoundingBox` (`collectColliders`, `collectCandidateStepUpHeights`), not a changed `collideWithShapes` implementation.

A direct source-level shared-block witness confirms a separate output change for that candidate selection. Set a regular player box to `[0.2,1,0.2]..[0.8,2.8,0.8]`, grounded with `maxUpStep=0.6`, on a full-block floor at top Y=1; place a bottom oak slab at X `[1,2]`, top Y=1.5, spanning the player Z interval; request `Vec3(2,0,0)`. `Attributes.STEP_HEIGHT` defaults to `0.6`; `SlabBlock`'s bottom shape is `Block.box(0,0,0,16,8,16)`, yielding local Y `[0,0.5]`.

On the base horizontal collision, movement clips to X `0.2`. In 1.20.6 the full-step candidate rises `0.6`, moves the full X `2.0`, then the downward correction returns `-0.6` at the final X box, whose interval no longer overlaps the slab; the net returned movement is `(2.0,0,0)`. In 1.21 the step-region shape coordinates include the slab-top offset `0.5`; the ascending candidate path clears the slab at bottom Y `1.5`, moves the full X `2.0`, and returns `(2.0,0.5,0)` (the equal initial/current box has zero `$$1.minY - $$8.minY` correction). This is an equal raw position/state/request source comparison, not a runtime trajectory. It confirms a second reachable `Entity.collide` output change independent of the WorldBorder witness. The 1.21.1 `Entity`, `SlabBlock`, `Attributes`, and shape collision sources match 1.21.

Also, `Entity.updateFluidHeightAndDoFluidPushing` is reached by `Entity.baseTick` on the LocalPlayer path; it is not outside the ordinary local tick. Its exact `* 1.0` removal and output disposition are corrected above. This method's scan and output are now explicitly included as a closed no-change terminal.
