# Independent source review: respawn jump-strength base

**Verdict: ACCEPT for 1.20.5/1.20.6 → 1.21; confirmed unchanged in 1.21.1.** The checked source establishes the client-side state transition for a replacement player when the respawn packet has `shouldKeep((byte)1) == false`. Given a pre-respawn local-player `JUMP_STRENGTH` base of `0.6`, 1.20.5 and 1.20.6 leave the replacement at the default represented by `0.42F`; 1.21 and 1.21.1 copy the prior base `0.6`. This verifies applicability, not packet-production history or packet ordering.

Versions 1.20.4, 1.20.5, 1.20.6 and 1.21.1 have published `mojmap.provenance.json` manifests identifying the version and namespace; 1.20.5 identifies the mapping family as official Mojang client mappings. For 1.21 the tree has embedded `mojmap/.decompile-provenance.json` (SHA-256 recorded in `source-hashes.txt`), which identifies the `lpc-decompile-v1` pipeline and toolchain but contains no top-level version/mapping fields. The directory identity and matching source hashes bind the inspected 1.21 slices; the corresponding 1.21.1 manifest identifies that release and namespace. Relevant source-file hashes are in `source-hashes.txt`.

## Respawn and attribute-map behavior

- **1.20.5 and 1.20.6:** `ClientPacketListener.handleRespawn` constructs a replacement `LocalPlayer`, then calls `assignValues(oldAttributes)` only inside `if (shouldKeep((byte)1))` (both versions `ClientPacketListener.java:1073–1151`, attribute gate `:1131–1133`). With the flag false, there is no attribute copy. The replacement's jump-strength base therefore remains its default. This is a fresh default map: `Player` passes `EntityType.PLAYER` to its superclass (`Player.java:194–196`), `LivingEntity` constructs an `AttributeMap` from `DefaultAttributes.getSupplier` (`LivingEntity.java:246–250`), and `DefaultAttributes` registers `Player.createAttributes()` for `EntityType.PLAYER` (`DefaultAttributes.java:137`). The same constructor chain applies in 1.21 (`Player.java:195–197`, `LivingEntity.java:258–262`, `DefaultAttributes.java:137`).
- **1.21 and 1.21.1:** the corresponding gate has an `else`: true uses `assignAllValues`, false uses `assignBaseValues` (`ClientPacketListener.java:1076–1156`, gate `:1134–1138`). `AttributeMap.assignBaseValues` iterates the old map's instantiated attributes and sets the matching new instance's base from the old base (`AttributeMap.java:111–118`). It does not transfer modifiers. `assignAllValues` uses `replaceFrom`, which also replaces modifiers (`:102–109`; `AttributeInstance.replaceFrom`).

## Player attribute availability and exact default

The 1.20.4 source has a legacy `Attributes.JUMP_STRENGTH` named `horse.jump_strength`, default `0.7`, range `[0, 2]` (`Attributes.java:24–26`); `LivingEntity.createLivingAttributes` does not add it (`:280–288`), and `Player.createAttributes` only extends that living-attribute builder (`Player.java:204–209`). It is not the player jump attribute in the finding. In 1.20.5, `Attributes.JUMP_STRENGTH` is the new `generic.jump_strength`, registered with `new RangedAttribute(..., 0.42F, 0.0, 32.0).setSyncable(true)` (`Attributes.java:45–47`), and `LivingEntity.createLivingAttributes` adds it (`:292–306`). `Player.createAttributes` extends that builder (`Player.java:221–230`). These registration and supplier lines are identical in 1.20.6. In 1.21 / 1.21.1 the registration is at `Attributes.java:53–55`, the living-attribute addition at `LivingEntity.java:304–318`, and the player builder extends it at `Player.java:222–235`. Thus 1.20.5 is the first inspected release with the generic living/player jump-strength attribute; do not describe the older horse-specific attribute as its introduction.

The `F` suffix matters: `RangedAttribute` accepts a `double` (`RangedAttribute.java:9`) and its `Attribute` superclass stores a `double` default (`Attribute.java:9–16`). Java widens the already-rounded float literal `0.42F` to double, yielding exactly `0.41999998688697815`. `AttributeInstance` initializes its base from that default (`AttributeInstance.java:29–33` in 1.20.5/1.20.6; `:34–38` in 1.21). The ordinary visible value is 0.42, but the stored base is that widened float value.

## Reachable effect and bounds

For a valid prior player attribute state with base `0.6`, `handleUpdateAttributes` writes the received snapshot base directly to the old player's matching instance in both eras (1.20.6 `ClientPacketListener.java:2059–2075`; 1.21 `:2062–2078`). No server-side producer claim is needed. A 0.6 base is within the registered `[0, 32]` range. On a normal grounded jump with no jump boost and block jump factor 1, `LivingEntity.getJumpPower(float)` multiplies the attribute value and `jumpFromGround` writes that result to delta movement Y (1.20.6 `LivingEntity.java:2061–2073`; 1.21 `:2047–2060`). The jump-power method casts the attribute value to `float`; this yields the ordinary jump-power values `0.42F` versus `0.6F` under those stated conditions.

The verified 1.20.4 → 1.20.5 boundary concerns introduction of the generic player/living jump-strength attribute, not the respawn-copy change. The respawn-copy difference is bounded here by the inspected 1.20.6 and 1.21 endpoints; no exact earlier 1.21 cutover is asserted. All compared relevant 1.21 and 1.21.1 source files have identical hashes, so these slices are unchanged in 1.21.1.
