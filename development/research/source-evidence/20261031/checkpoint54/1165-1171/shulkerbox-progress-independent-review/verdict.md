## Source calculation

`ShulkerBoxBlock.getShape` in all three releases gets the block entity at the queried position and returns `Shapes.create(blockEntity.getBoundingBox(blockState))` when it is a shulker box; otherwise it returns `Shapes.block()` (1.16.5 `ShulkerBoxBlock.java:218-220`; 1.17/1.17.1 `:223-225`). The collision context is unused. The block-entity progress fields start at zero and are not read from or written to NBT (`ShulkerBoxBlockEntity` constructors, `load`, and `save`). Its client tick copies `progress` to `progressOld`, then adds `0.1F` while opening or subtracts `0.1F` while closing, clamping at 1 or 0. `getProgress(1.0F)` is `Mth.lerp(1.0F, progressOld, progress)`; `Mth.lerp(f,g,h)` is `g + f * (h - g)`. For the reachable adjacent-tick values, that binary32 expression returns the current `progress` exactly.

Under the local tick transition relation from initial zero, with open/close status changes permitted between ticks, exact binary32 arithmetic reaches 23 current-progress values, all bounded by `[0,1]`:

`0`, `1.4901161193847656e-8`, `0.09999992698431015`, `0.10000000149011612`, `0.10000001639127731`, `0.19999992847442627`, `0.20000000298023224`, `0.20000001788139343`, `0.2999999225139618`, `0.30000001192092896`, `0.3999999165534973`, `0.4000000059604645`, `0.49999991059303284`, `0.5`, `0.5999999046325684`, `0.6000000238418579`, `0.6999999284744263`, `0.7000000476837158`, `0.7999999523162842`, `0.8000000715255737`, `0.8999999761581421`, `0.9000000953674316`, `1`.

The tiny positive value is ordinarily reachable: starting at zero, three opening ticks produce `0.1`, `0.2`, `0.30000001192092896`; switching to closing and ticking three times produces `0.20000001788139343`, `0.10000001639127731`, `1.4901161193847656e-8`. This establishes a concrete producer path, independent of server-side event/state production. A fixed query may also be reasoned about for any supplied finite progress value, but such a value is not thereby claimed producer-reachable.

For equal direction, block position, state, and progress `p`, the AABB geometry is algebraically identical over reachable `[0,1]`. 1.16.5 uses `Shapes.block().bounds().expandTowards(0.5F * p * step)` (`ShulkerBoxBlockEntity.java:93-100`). 1.17 and 1.17.1 use `Shulker.getProgressAabb(direction, 0.5F * p)` (`ShulkerBoxBlockEntity.java:100-101`), whose helper uses `new AABB(BlockPos.ZERO).expandTowards(step * max(-1,p))` and `.contract(-step * (1 + min(-1,p)))` (`Shulker.java:244-253`). Since `p` is in `[0,1]`, the min is exactly `-1`, contraction is exactly zero, and the float expansion term is exactly the same `0.5F * p * step`. For positive facings the extra endpoint is `1 + e`; for negative facings it is `-e`, where `e = float(0.5F * p)`. The other axes remain `[0,1]`.

The difference is in `Shapes.create(AABB)` encoding. 1.16.5 `Shapes.findBits` measures scaled endpoints against `floor` with absolute tolerance `1e-7` (`Shapes.java:55-105`). 1.17/1.17.1 use `round` and tolerance `1e-7 * scale` (`Shapes.java:61-117`), then return `block()` when all three encodings are zero. For every reachable `p >= 0.09999992698431015`, `e >= 0.04999996`: the expanded endpoint is outside the allowed unit interval, both versions fall back to an `ArrayVoxelShape`, and the same exact AABB bounds are preserved. At `p=0`, all releases return the full block.

At the reachable tiny value `p=1.4901161193847656e-8`, `e=7.450580596923828e-9`. For WEST, DOWN, or NORTH, the old AABB has respectively `minX`, `minY`, or `minZ = -e` and opposite endpoint 1. Old `findBits(-e,1)` rejects all scales because `floor(-e * scale)=-1` and the distance to that integer is near one; it therefore keeps the exact protruding AABB in an `ArrayVoxelShape`. New `findBits(-e,1)` rounds `-e` to zero, returns zero bits on every axis, and `Shapes.create` returns `Shapes.block()`, losing the tiny outward lid sliver. For EAST, UP, or SOUTH the expanded max is `1+e`; both algorithms encode zero bits and return the full block, so this case does not differ.

## Collision replay and verdict

Take block position `(0,0,0)`, facing WEST, and the reachable tiny progress above. Let a LocalPlayer query AABB be `[-0.65, 0.2, 0.2]..[-0.05, 2.0, 0.8]` and requested X movement be `0.05 - 1e-9`. Its swept query ends at approximately `x=-1e-9`, overlapping the old shulker sliver `[-7.450580596923828e-9,0)` while staying wholly west of the ordinary block `[0,1]`. `CollisionSpliterator` constructs `entityShape=Shapes.create(queryBox)` and, for non-full shapes, emits a block provider only when `Shapes.joinIsNotEmpty(provider.move(pos), entityShape, BooleanOp.AND)` is true (`CollisionSpliterator.java:37-45, 71-85`). The old `ArrayVoxelShape` AND is nonempty; the new `Shapes.block()` special case checks intersection with the unit cube, which is false for this swept box. Thus the old stream includes the shulker and the new stream does not.

For X-axis clipping against the same provider (`Entity.collideBoundingBox`/`Shapes.collide`), the old WEST boundary clips positive movement to `-e - (-0.05) = 0.0499999925494194`; the new provider leaves the requested `0.049999999` unchanged. The `CollisionSpliterator` gates and axis-clipping order are unchanged in these source versions; the divergence is the vanished shape emitted to the collision stream.

Verdict: accept a player-relevant dynamic collision-shape difference introduced between 1.16.5 and 1.17, still present in 1.17.1. It is narrowly gated to an ordinarily reachable tiny residual progress and the three negative-facing directions; the older version preserves a sliver and the newer versions quantize it away before LocalPlayer collision collection/clipping. This is source-derived, not runtime parity evidence.
