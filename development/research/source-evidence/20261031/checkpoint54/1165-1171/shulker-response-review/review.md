# Independent source review: Shulker opening response

## Verdict: ACCEPT, bounded to this candidate

The exact Mojmap sources support an eligible direct LocalPlayer movement-response difference introduced between 1.16.5 and 1.17 and retained in 1.17.1. Under the same replicated Shulker state, attachment, player state, and open movement space, the first opening step computes and sends a different `MoverType.SHULKER` displacement to an on-foot LocalPlayer. This is a source-level static witness, not a runtime trajectory or parity result.

## Independent route and adjacent-version comparison

- `ClientPacketListener.handleSetEntityData` resolves the entity ID and calls `entity.getEntityData().assignValues(...)` when metadata exists (1.16.5 `ClientPacketListener.java:576–581`; 1.17 `:458–463`; 1.17.1 same handler body). `Shulker` declares `DATA_PEEK_ID` as a synchronized byte. Its goal code uses `setRawPeekAmount(100)` on opening in each release; synchronized attachment position/face give the client the same geometry input.
- `ClientLevel.tickNonPassenger` invokes `entity.tick()` for a Shulker in a ticking client chunk (1.16.5 `ClientLevel.java:181–194`; 1.17/1.17.1 `:173–181`). The Shulker tick's peek calculation and player response are not server-gated.
- In 1.16.5 `Shulker.tick()` lines 213–245 copies the previous `currentPeekAmount`, increments the current value by `0.05F` toward `rawPeek * 0.01F`, computes the previous/current physical peek as `double`, expands the full body AABB toward the opening face, queries non-spectators, and calls `entity.move(MoverType.SHULKER, new Vec3(h * stepX, ...))` for non-Shulkers with `noPhysics == false`.
- In 1.17 and 1.17.1, `Shulker.tick()` lines 174–175 calls `onPeekAmountChange()` when `updatePeekAmount()` changes the current value. `getPhysicalPeek(float)` lines 204–206 returns a `float`; `onPeekAmountChange()` lines 224–241 computes `float h = f - g`, queries a directional swept/front-face AABB using `NO_SPECTATORS` plus a same-root-vehicle exclusion, then makes the same `MoverType.SHULKER` call. The 1.17 and 1.17.1 bodies match.
- The LocalPlayer is inserted into the queried client-level entity store: 1.16.5 `ClientLevel.addPlayer` calls `addEntity`, which adds the player to its `LevelChunk` (`ClientLevel.java:273–285`); `Level.getEntities` delegates to `LevelChunk.getEntities` (`Level.java:690–705`), whose loop tests `entity2.getBoundingBox().intersects(aABB)` (`LevelChunk.java:476–492`). In 1.17/1.17.1 `ClientLevel.addPlayer` similarly calls `entityStorage.addEntity`, `getEntities()` returns that storage's getter, and `EntitySectionStorage` builds the same bounding-box intersection predicate before `EntitySection` delivers passing entities (`ClientLevel.java:223–233, 741–742`; `EntitySectionStorage.java:111–120`; `EntitySection.java:29–38`). The LocalPlayer passes these query filters when it is on foot, not a spectator and not `noPhysics`. For a +X opening from a Shulker centered at `(0.5, 0, 0.5)`, the old expanded query spans X `[0, 1+d]`; the new swept query spans X `[1, 1+d]`. A standing player centered at `(1.25, 0, 0.5)` has an X interval approximately `[0.95, 1.55]`, so it intersects both query regions. Its body also overlaps the Shulker entity box, but `Entity.move` clips against block shapes, not another entity; choose an otherwise open movement corridor. With a non-passenger player, the new same-vehicle predicate passes.

## Reproduced arithmetic and movement witness

Use the same synchronized raw peek target `100`, previous/current animation values `0.0F` and the first opening update to `0.05F`, Shulker attachment direction `WEST` (opening direction `+X`), and the same standing LocalPlayer at `x=1.25`, `y=0`, `z=0.5`. The numeric operations below were reproduced from the source's float and double evaluation order and `Mth.SIN` lookup-table formula (`Mth.java:26–44`):

1. For current peek `0.05F`, the float argument path reaches sine-table index `18022` and the table entry rounds to `0.9876943F`. Previous peek `0.0F` reaches the `1.0F` sine entry.
2. The old expression `0.5 - Mth.sin((0.5F + current) * (float)Math.PI) * 0.5` uses a double `0.5` after the float-returning sine, yielding `d = 0.00615283846855164`; prior `e = 0`, so old `h` is that double.
3. The new `getPhysicalPeek(float)` expression uses `0.5F` throughout and returns a float physical peek. Subtracting the two float peek values gives `h = 0.006152838F`, widened to binary64 as `0.0061528380028903484` in the `Vec3` constructor.
4. Both query regions include this player. `h²` is approximately `3.7857E-5`, above `Entity.move`'s `lengthSqr() > 1.0E-7` resolved-write threshold (`Entity.java:506` old; `:555` new). `MoverType.SHULKER` does not enter the piston restriction, and the Player edge-backoff override only acts for `SELF` or `PLAYER`, so the equal unblocked +X input is retained.
5. With standing width `0.6F` and no block obstruction, the old translated-box writer gives player X `1.2561528384685516`; the 1.17 position writer gives X `1.2561528380028903`. These are computed source expressions for one fixed input pair. `Entity.move` itself also has a 1.16.5→1.17 position-reconstruction change, so this final-position illustration is the composition of two paired source operations; the isolated Shulker difference is already established at the distinct `h` values passed to `Entity.move`.

## Assumptions and exclusions

The witness holds fixed the synchronized peek byte/animation values, Shulker attachment position and face, LocalPlayer position/dimensions/flags, client entity collection, and block-collision state. It assumes the Shulker is ticked in a client ticking chunk, the player is on foot (not a passenger of the same root vehicle), non-spectating and has `noPhysics == false`, and the small +X motion corridor is unobstructed. The ordinary Shulker attack-goal source sets the raw open target to `100`; server production of that synchronized state is not part of this response review. There is no runtime launch, trajectory replay, or claim about frequency. This verdict accepts only the Shulker response candidate; it does not certify complete source-pair coverage or pair freeze.
