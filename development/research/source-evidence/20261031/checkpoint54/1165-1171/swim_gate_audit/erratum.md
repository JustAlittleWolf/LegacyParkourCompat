# Erratum: built-in water tag and waterlogged-sign witness

**Scope:** supplements the immutable `report.md`; does not replace or edit it. Original report SHA-256 remains `e542799891232a2ef200251f94f8ed65b5f1320be47d61e2e0c7d46ebbd2d076`, and the existing `SHA256SUMS.txt` is unchanged. This erratum supersedes only the original report's open built-in `FluidTags.WATER` membership gate. It does not establish a runtime trajectory or runtime parity.

## Built-in tag membership is closed

In both exact Mojmap roots, `net/minecraft/data/tags/FluidTagsProvider.java:addTags()`, lines 16–20, declares `FluidTags.WATER` with `Fluids.WATER` and `Fluids.FLOWING_WATER` (line 18). This is the built-in tag provider source for both 1.17 and 1.17.1; the two files are byte-identical by SHA-256. `SignBlock.getFluidState(BlockState)`, lines 119–122, returns `Fluids.WATER.getSource(false)` when `WATERLOGGED` is true. Therefore the source fixture below passes the vanilla built-in `FluidTags.WATER` membership check. This closes the tag-membership uncertainty for this built-in fluid; it makes no claim about later datapack or mod changes to tags.

## Constructed static source witness

The following concrete block/entity state satisfies the relevant 1.17 and 1.17.1 source queries. It is a static source witness; no game was launched and no full player trajectory was recorded.

1. Place a dry `Blocks.STONE_SLAB` at `(0,0,0)` with `TYPE=BOTTOM` and `WATERLOGGED=false`. `Blocks.java`, lines 1887–1889, registers it as a `SlabBlock`. `SlabBlock.java`, lines 26–35, defines `BOTTOM_AABB` as `(0,0,0)` to `(16,8,16)` and the default state as bottom/dry; lines 48–57 select that shape for `BOTTOM`. `Block.box`, lines 146–148, divides coordinates by 16, so the slab top is exactly Y `0.5`. Its ordinary collision shape uses this shape because default `hasCollision` is true (`BlockBehaviour.java`, lines 287–289 and 821).
2. Put a solid support block at `(-1,2,0)`. At `(0,2,0)`, place an `OAK_WALL_SIGN` in source water with `FACING=EAST` and `WATERLOGGED=true`. `WallSignBlock.canSurvive`, lines 56–59, requires the block at `blockPos.relative(FACING.getOpposite())` to have solid material; EAST therefore uses the support at X `-1`. `WallSignBlock.getStateForPlacement`, lines 63–76, reads the fluid at the clicked position, selects a horizontal facing with a surviving support, and sets `WATERLOGGED` when that fluid type is `Fluids.WATER`. Independently, `SignBlock` implements `SimpleWaterloggedBlock` (lines 33–34); `SimpleWaterloggedBlock` accepts `Fluids.WATER` and changes the state to waterlogged when water is placed (lines 18–28).
3. The `OAK_WALL_SIGN` registration uses `.noCollission()` (`Blocks.java`, lines 589–592). `Properties.noCollission()`, lines 891–895, sets `hasCollision=false`; `BlockBehaviour.getCollisionShape`, lines 287–289, consequently returns `Shapes.empty()` for it. The sign outline shape does not obstruct the player. The waterlogged sign's `getFluidState` is still the WATER source, as above.
4. Put a standing survival LocalPlayer at `(0.5,0.5,0.5)`, sprinting, not flying/spectating/passenger, with shared swimming initially false and with loaded surrounding cells. Standing player dimensions are `0.6 × 1.8`; standing eye height is `1.62` (`Player.java`, lines 120–133 and 1837–1848). `EntityDimensions.makeBoundingBox`, lines 17–25, centers width on X/Z and extends height upward from position Y. The bounding box is therefore X/Z `[0.2,0.8]`, Y `[0.5,2.3]`; after `deflate(0.001)`, its Y range is `[0.501,2.299]`.

In 1.17.1 `Entity.updateFluidHeightAndDoFluidPushing`, lines 2773–2811, scans X/Y/Z from `floor(min)` inclusive to `ceil(max)` exclusive. For this box the sampled X and Z cells are each `0` (`floor(0.201)=0`, `ceil(0.799)=1`); Y cells are `0,1,2` (`floor(0.501)=0`, `ceil(2.299)=3`). Thus `(0,2,0)` is included. Its waterlogged sign fluid state is a WATER source. `FlowingFluid.getHeight`, lines 464–475, returns source own height when the cell above is not the same fluid; `WaterFluid.Source.getAmount`, lines 146–155, is 8, so the surface is `2 + 8/9`, above the scan's minimum Y. The body-fluid contact query therefore reports water.

The eye sample is `getEyeY() - 0.11111111F`: `0.5 + 1.62 - 0.11111111F`, approximately Y `2.0089`. `Entity.updateFluidOnEyes`, lines 1090–1108, samples `(getX(), sampleY, getZ())`, floors it to `(0,2,0)`, and accepts the WATER tag when the fluid surface is above that height. The waterlogged source surface `2 + 8/9` exceeds the sample. After that eye sample is stored, the next base tick has `wasEyeInWater=true`; `Entity.isUnderWater()`, lines 1052–1054, combines that with refreshed body contact.

Conversely, `Entity.setPosRaw`, lines 2956–2964, sets the cached `blockPosition` to `(floor(x), floor(y), floor(z))`, here `(0,0,0)`. The slab's `getFluidState`, lines 94–97, returns the superclass fluid state when dry; `BlockBehaviour.getFluidState`, lines 176–179, returns `Fluids.EMPTY`. So the feet-cell WATER predicate is false while body contact and the preceding eye-water sample are true.

## Update and player movement route

- `Entity.baseTick()`, 1.17.1 `Entity.java`, lines 395–417, updates fluid contact, then eye fluid, then swimming. `updateSwimming()`, 1.17 lines 1056–1062, has the sprint/underwater/non-passenger entry condition; 1.17.1 `Entity.java`, lines 1056–1064, adds the feet-cell WATER query on the initially-not-swimming branch. With the stated state, old 1.17 sets swimming true and 1.17.1 keeps it false.
- `Player.updateSwimming()` overrides in both releases delegate to `super.updateSwimming()` when the player is not flying (1.17 `Player.java`, lines 1451–1457; 1.17.1, lines 1442–1448), so the Entity gate is actually reached for this survival player. `Player.isSwimming()`, 1.17.1 `Player.java`, lines 1801–1804, gates the shared bit for non-flying, non-spectator players; those are the witness assumptions. `LocalPlayer.tick()`, lines 190–203, enters `super.tick()`. `LivingEntity.tick()`, lines 2218–2222 and 2257, reaches virtual `aiStep()` after `super.tick()`; `LocalPlayer.aiStep()` calls its superclass path, and `LivingEntity.aiStep()` invokes virtual travel (1.17.1 lines 2540–2547). `Player.tick()` calls `updatePlayerPose()` only after `super.tick()` (lines 247–248 and 288–290), so this travel call uses the standing dimensions assumed by the witness. Thus the base-tick flag reaches the local player's travel call before the pose update.
- `Player.travel(Vec3)`, 1.17 lines 1418–1430 and 1.17.1 lines 1409–1421, contains the same swimming-specific branch: when swimming and not passenger, it may add `(lookY - velocityY) * h` to Y velocity before `super.travel`. With a horizontal look (`lookY=0`) the branch condition is true. This establishes the downstream branch divergence for the witness.
- A concrete source path to a differing pre-travel velocity is also available: `LocalPlayer.isEffectiveAi()` returns true (1.17.1 `LocalPlayer.java`, lines 498–501), and while it controls the camera `serverAiStep` copies jump input to `this.jumping` (lines 612–619). `Player.isAffectedByFluids()` returns true when not flying (1.17.1 `Player.java`, lines 1012–1014), and `LivingEntity.aiStep()` handles the jump before virtual travel (lines 2513–2535). At this witness, water height is `2 + 8/9 - 0.501`, above `Entity.getFluidJumpThreshold()==0.4` (`Entity.java`, lines 2849–2855), so grounded jump input selects `jumpInLiquid`; that method adds `0.04F` Y (`LivingEntity.java`, lines 1991–1993). With horizontal look and no flight, 1.17 scales that positive increment by `1-0.06` in `Player.travel`; 1.17.1 skips the swimming-only adjustment. This is source arithmetic, not a simulation of the final trajectory.
