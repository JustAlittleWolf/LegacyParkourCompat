# Erratum 1 — expanded AABB reaches Shapes.create

This immutable erratum corrects the source-graph statement in `result.md`; that original file is retained unchanged. The original claim that block collision collection does not encode the movement-expanded AABB was false. `CollisionGetter.getBlockCollisions(entity, aABB)` constructs `CollisionSpliterator`, and both the 1.16.5 and 1.17 constructors set `entityShape = Shapes.create(aABB)`. In `Entity.collide`, that `aABB` is the movement-expanded box passed to `getEntityCollisions` and, through the collision helper, the block collision query. Therefore the expanded query must be included in this audit.

## Corrected bounded conclusion

Three-axis short-pose movement can make `CollisionSpliterator`'s expanded query pass `findBits`; and 1.17 can grid-encode some near-grid query endpoints that 1.16.5 leaves as an `ArrayVoxelShape`. For example, a 0.6F pose box with minima `(0.12500006, 0.125, 0.125)` and a positive 3-axis request ending at maxima `(0.87500006, 0.75, 0.75)` has an X interval rejected at every 1.16.5 denominator but accepted at denominator 8 in 1.17 (the rounded 1.17 X bounds are `[0.125, 0.875]`); Y and Z can be exact denominator-8 intervals. These are source-reachable dimensions because `Entity.move` accepts a Vec3 and `expandTowards` adds the positive components to the maxima. One- and two-axis requests retain at least one unexpanded 0.6F or 0.2F extent, so their expanded query cannot pass all-axis grid encoding in either version.

Despite that representation divergence, no provider-selection difference is admitted by the bounded `CollisionSpliterator` path. Full-block shapes bypass `entityShape` and use the same raw `this.box.intersects(...)` check in both versions. Partial shapes are admitted by `Shapes.joinIsNotEmpty(providerShape, entityShape, AND)`. For non-cube coordinate lists, `IndirectMerger` in both versions suppresses merged coordinate intervals of width at most `1.0E-7`; the endpoints moved by successful 1.17 rounding are strictly less than `1.0E-7` in world coordinates, so a newly gained or lost intersection exists only in a sliver that does not form a merged interval. When both operands have `CubePointRange` coordinates, 1.17 may use `DiscreteCubeMerger`; its boundaries are exact shared dyadic grid coordinates, so a rounded query endpoint on a provider grid face creates no positive-volume cell intersection on the far side. A cube provider that already occupies the adjacent filled cell also intersects the unrounded 1.16.5 continuous query, so the admission result remains true there as well. Thus this bounded Boolean admission result is equal for equal provider shapes. The ensuing axis clip receives the same admitted block shapes. This is a static source conclusion, not a runtime trajectory proof.

`CollisionSpliterator` also uses a separate current-box border check. That call still receives `source.getBoundingBox()` rather than the expanded query and does not change the original report's deflated-current-box analysis. Entity collision candidates and all other collision/query consumers are outside this erratum's conclusion. This is not a full collision-provider or pair-wide audit.
