## Source-confirmed movement deltas and boundaries

### Jump Boost sum precision (introduced in the inspected interval by 1.17)

1.16.5 `LivingEntity.jumpFromGround()` stores `getJumpPower()` in `float f`, conditionally performs `f += 0.1F * (amplifier + 1)`, then writes that float to Y delta movement. In 1.17 and 1.17.1, `getJumpBoostPower()` returns the same float-derived boost product as a double; `jumpFromGround()` adds it to float `getJumpPower()` in `double d` and writes `d`. Therefore the boosted sum no longer rounds to float before the velocity write. Player `jumpFromGround()` calls `super`, and `LivingEntity.aiStep()` reaches it under its ordinary grounded / shallow-fluid gates. With base `0.42F`, amplifier 0, the prior source-only arithmetic witness is old `0.5199999809265137` (float-rounded) vs new `0.5199999883770943` (double sum). This is source arithmetic, not runtime trajectory parity. It is already present in 1.17, not an additional 1.17.1 change.

### Position / box reconstruction in `Entity.move()` (introduced in 1.17)

The ordinary local-player ground/water/fall-flying paths call `LivingEntity.travel()`, which calls `Entity.move(MoverType.SELF, ...)`; `Player.travel()` delegates to that inherited route. In 1.16.5 both `noPhysics` movement and collision-resolved movement translate the existing AABB and derive position from the translated box center/minY. 1.17 changes both sites to `setPos(x + dx, y + dy, z + dz)`. The collision-resolved site retains `vec32.lengthSqr() > 1.0E-7`; post-move collision and velocity-response gates remain in order. The 1.17 implementation persists in 1.17.1.

This is the bounded position/box writer delta. Prior collision39 reconciliation reviewed endpoint `Entity.move` and the paired shape/query dependencies. That source work does not establish all displacement outcomes or full-pair closure; see unresolved coverage below.

### Swimming entry predicate (introduced in 1.17.1)

1.17 `Entity.updateSwimming()` turns swimming on when sprinting, underwater, and not a passenger. 1.17.1 adds `level.getFluidState(blockPosition).is(FluidTags.WATER)` to only that not-already-swimming branch. `Player.updateSwimming()` reaches the base implementation for a non-flying player; `Entity.baseTick()` invokes it after the fluid state updates; `Player.travel()` has a swimming-specific movement branch. Thus the predicate is on the ordinary player graph. Prior source-only review leaves the concrete non-WATER-feet fluid/tag precondition unresolved, and fluid/tag/provider work is outside this inventory. Keep this as a source delta candidate; no concrete altered player state or movement result is claimed here.
