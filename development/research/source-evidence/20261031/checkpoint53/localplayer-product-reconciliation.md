## Per-operation reconciliation

### 1. Shift clears `sprintTriggerTime` — covered

- Hook and change: `SprintTriggerHook` (`player.sprint.trigger`) and `change/v1_15_2/SprintTrigger`, annotated `V1_15_2`. It returns only `itemUseReset`, so saved shift input alone does not authorize the intercepted timer write, matching the 1.15.2 form.
- Current route: `LocalPlayerMixin.legacyparkourcompat$sprintTriggerReset` redirects the `sprintTriggerTime` PUTFIELD at `aiStep` ordinal 1, supplies the pre-poll `wasShiftKeyDown` local and the no-passenger item-use reset cause, then writes only when the resolved hook says to reset. `LocalPlayerAccessor` performs the field write. The mixin comment identifies this as the shift-specific reset site.
- Later route: `change/v1_21_4/SprintTrigger` returns `priorShift || itemUseReset`, restoring the added shift cause for profiles that resolve to it. No additional catalog entry is needed; discovery registers each annotated hook interface from the change class.
- Resolution/fallback: for target 1.15.2, the 1.15.2 change is selected. For target 1.16, the resolver can select the later 1.21.4 change, whose behavior includes the shift reset. Native/latest profiles resolve no historical changes. With no hook, the redirect defaults to allowing the native write.
- Disposition: no movement-code gap found for the accepted 1.15.2 and 1.16 forms. The supplied boundary evidence validates the operation through 1.16.5. The 1.21.4 change comment asserts the same shift-reset behavior at 1.16 and 1.21.4; this supplied source-only trio does not independently certify every release from 1.17 through 1.21.3. Treat that broader interval as reliant on the existing implementation evidence, not on the attached boundary report.

## Architecture and remaining evidence boundary

The three routes are all client mixins in `src/client/resources/legacyparkourcompat.client.mixins.json`. `MovementRuntime.appliesTo` rejects non-player entities, logical-server entities, and disabled/native profiles; `MovementRuntime.find` then returns no change, and each redirect/wrapper falls back to vanilla. `ChangeResolver` selects the earliest `emulates` version newer than or equal to the selected profile independently per hook, and client `MovementChangeDiscovery` scans version packages and registers the implemented `@MechanicType` interfaces. No explicit registration changes are needed.

No product implementation extension is identified for the accepted 1.15.2→1.16 deltas. The precise open boundary is release coverage beyond what the provided source audit checked: all three forms were source-checked only from 1.16.0 through 1.16.5; the sprint hook's existing `V1_21_4` sentinel is relied on by resolver for profiles beginning at 1.16, but this assignment's boundary artifacts do not certify each intermediate release.
