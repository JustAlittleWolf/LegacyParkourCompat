# Independent audit — residual legacy block providers, 1.15.2 → 1.16.5 Mojmap

## Verdicts

- **Moving source-piston head collision shape — ACCEPT (fixed-state source claim).** In `PistonMovingBlockEntity.getCollisionShape`, both endpoints build a piston-head state only on the `isSourcePiston()` route, then set facing and `SHORT` before querying the head collision shape. Older source line 351 uses `this.extending != 1.0F - this.progress < 4.0F`; newer line 353 uses `< 0.25F`. With ordinary normalized progress `p ∈ [0,1]`, the former inner comparison is always true; the latter is true exactly when `p > 0.75F`. For an extending piston, the selected booleans are old `false`, new `true` when `p ≤ 0.75`; for a retracting piston they are old `true`, new `false` in that interval. They agree for `p > 0.75`. `PistonHeadBlock.getShape` selects the same corresponding short/long arm boxes in both versions; the newer state cache preserves this per-facing selection. This establishes a real shape difference for the same supplied moving-piston state and progress.
- **Retracting source-piston push volume — ACCEPT (fixed-state source claim).** `getCollisionRelatedBlockState` requires retraction, a source piston, and a moved `PistonBaseBlock`. Older source lines 89–96 leave `SHORT` at its default `false`; newer lines 92–99 set it to `this.progress > 0.25F`. The result is used immediately by `moveCollidedEntities` to obtain the collision shape, find intersecting entities, compute the component-box movement, and call `moveEntityByPiston` → `Entity.move(MoverType.PISTON, ...)`. For `p > 0.25F`, the newer selected head arm is short while the old one remains long; the candidate can differ for an entity intersecting only the removed arm segment. The client level entity query accepts `Entity` instances, and the newer slime-specific `ServerPlayer` exception does not match `LocalPlayer`.
- **Other 80 classes — ACCEPT with the coverage's fixed-state scope.** The 80 listed names match the other 80 paired candidate rows (81 total including `PistonMovingBlockEntity`); every candidate path is marked `modified` in corrected `path-status-ordinal-v2.tsv`. The sidecar comparison contains 107 movement-provider/contact method rows; the seven marked changed are BaseRail outline, Campfire contact, EndPortal contact, Fire outline, inherited Kelp outline, piston collision shape and RedStoneWire outline. The non-piston changed rows do not establish another in-scope fixed-state player collision/contact delta: rails, fire and redstone wire are registered `noCollission`; Kelp and its body remain `noCollission`; campfire difference changes the damage parameter (damage calculation is excluded); end-portal transfer is server-only. The remaining listed movement provider/contact bodies are recorded equal. State generation, neighboring-state maintenance and excluded effects remain outside this slice.

## Tag and update-order dependencies

Neither piston claim depends on tag membership. The shape route uses the moving block entity fields plus `PistonHeadBlock` properties; the push route uses `isSourcePiston`, the moved block's `PistonBaseBlock` type, its sticky-piston identity, progress and facing. No `BlockTags`/`FluidTags` predicate participates in either route. Tag payloads are absent from the permitted exact source roots, so this audit does **not** close tag-dependent block-state evolution elsewhere (notably mushroom support/growth, sand eligibility, campfire utility predicates, and fluid tags). Those are not inputs to either accepted fixed-state piston claim.

Exact live-state gate remains open: in 1.16.5, `PistonMovingBlockEntity.tick` retains a completed client BE for up to five `deathTicks` (lines 278–300; especially 281–286), while the server removes it at completion; `MovingPistonBlock.onRemove` calls `finalTick`, whose client-side condition forces cleanup when a moving-piston state is replaced (BE lines 257–273). Whether client block-state update arrival/order leaves a moving-piston state and its BE available to a later local-player collision query is unverified. This gate limits a claim about unconditional live-world occurrence, and particularly whether a completed stale state affects clipping. It does **not** block either fixed-state predicate/shape claim. The push method runs during the active `progress < 1` tick branch (newer BE lines 302–310), but world update ordering for the presence of that active BE also has not been established.
