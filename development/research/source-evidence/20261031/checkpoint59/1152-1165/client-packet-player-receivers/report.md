# Clientbound packet receiver residual — 1.15.2 → 1.16.5 (Mojmap)

## Scope and source identity

This bounded source-only closure examines the changed `ClientGamePacketListener` interface, `ClientboundPlayerAbilitiesPacket`, `ClientboundMoveEntityPacket`, `ClientboundTeleportEntityPacket`, and `ClientboundLoginPacket`, following their `ClientPacketListener` consumers only for local-player position, velocity, abilities, `onGround`, and movement-mode state. It assumes equal decoded logical fields for the compared packets. It does not assess server packet production, world/block-state production, or whether any particular live connection emits a movement/teleport entity packet naming the local player.

The corrected endpoint inventories report zero missing, unlisted, or mismatched source paths. ## Receiver reachability and candidates

`ClientPacketListener.handleMoveEntity` resolves the packet ID with `ClientboundMoveEntityPacket.getEntity(level)`, which calls `level.getEntity(entityId)`. `ClientPacketListener.handleLogin` registers the local player under the packet player ID with `level.addPlayer(id, player)` (1.15.2 `ClientPacketListener.java:339–387`, especially 367–375; 1.16.5 `:350–409`, especially 390–398). `handleTeleportEntity` resolves the same ID through `level.getEntity` directly.

Both movement handlers then test `!entity.isControlledByLocalInstance()`. This test is true for a `LocalPlayer` in a client level: `LocalPlayer.isLocalPlayer()` returns true (1.15.2 `LocalPlayer.java:328–330`, 1.16.5 `:343–345`), but the inherited `Entity.isControlledByLocalInstance()` uses `getControllingPassenger()` (null for LocalPlayer: 1.15.2 `Entity.java:2428–2430`, 1.16.5 `:2470–2472`) and falls back to `!level.isClientSide` (1.15.2 `Entity.java:2521–2524`, 1.16.5 `:2557–2560`). Thus it returns false in `ClientLevel`, and the local player is reachable by these receiver branches. The old audit's treatment of these as remote-only interpolation is not applicable to the LocalPlayer ID.

### Candidate: teleport receiver changes the local-player position response

- 1.15.2 `ClientPacketListener.handleTeleportEntity`, `:593–613`: after `setPacketCoordinates(d,e,f)`, for an entity entering the `!isControlledByLocalInstance()` branch, the handler chooses the current position when all three absolute coordinate deltas are below `0.03125`, `0.015625`, and `0.03125`; otherwise it chooses the packet coordinates. It then calls `lerpTo` and copies packet `onGround`.
- 1.16.5 `ClientPacketListener.handleTeleportEntity`, `:602–617`: the same branch always calls `lerpTo(d,e,f,...)` and then `setOnGround(packet.isOnGround())`; the small-distance choice is gone.
- `Entity.lerpTo` directly calls `setPos` and `setRot` in both versions (1.15.2 `Entity.java:1648–1651`; 1.16.5 `:1687–1690`). For a packet naming the registered local player and with all three nonzero coordinate differences below the old thresholds, 1.15.2 preserves current position while 1.16.5 immediately writes the packet position. This is an eligible client receiver difference under equal decoded packet coordinates. The packet's only class-source edit is in its constructor (`entity.onGround` → `entity.isOnGround()`), a producer-side expression excluded by this assignment; decoded packet fields are unchanged.

### Conditional candidate: move receiver retains raw zero-delta coordinates

- 1.15.2 `ClientPacketListener.handleMoveEntity`, `:624–646`, accumulates each short delta into integer `xp/yp/zp`, converts the three integers through `ClientboundMoveEntityPacket.packetToEntity`, then calls `lerpTo`. `Entity.setPacketCoordinates` initializes those integer accumulators with `Mth.lfloor(coordinate * 4096.0)` (`Entity.java:236–238`).
- 1.16.5 `ClientPacketListener.handleMoveEntity`, `:628–648`, calls `ClientboundMoveEntityPacket.updateEntityPosition(entity.getPacketCoordinates())`, stores that result with `setPacketCoordinates`, then calls `lerpTo`. For an axis whose packet delta is zero, `updateEntityPosition` returns the input double unchanged; for nonzero deltas it floors to packet coordinates, adds the short, and divides by `4096.0` (`ClientboundMoveEntityPacket.java:28–35`). In this release `Entity.setPacketCoordinates(Vec3)` stores the double vector unchanged (`Entity.java:239–249`); 1.15.2's setter floors each component into packet units.
- Therefore a zero-delta axis can preserve a fractional raw packet coordinate in 1.16.5 where 1.15.2 snaps it to the 1/4096 packet grid, and `lerpTo` writes that coordinate to a local player when its ID resolves. This state is reachable in the receiver graph after a fractional-coordinate teleport packet, which stores raw coordinates in 1.16.5 and quantizes them in 1.15.2. Treat this as a conditional, dependent receiver candidate; do not infer that a server producer emits such a packet sequence for the local player. For packet-coordinate states already on the 1/4096 grid, this zero-delta distinction collapses. `onGround` also changed from direct field assignment to `setOnGround`, but the newer setter is exactly `this.onGround = value` (`Entity.java:477–479`), so that write has no delta.

## No-delta and excluded paths

- **`ClientGamePacketListener`: no direct receiver behavior.** It is an interface. The paired edits remove/rename four unrelated packet callback declarations; the declarations for `handleLogin`, `handleMoveEntity`, and `handlePlayerAbilities` retain their same argument types, and declaration-only changes do not alter the concrete receiver operations compared above.
- **Player abilities: no delta.** `ClientPacketListener.handlePlayerAbilities` writes the same six decoded fields in the same order to local player abilities in both versions (1.15.2 `:1690–1698`; 1.16.5 `:1709–1717`). `ClientboundPlayerAbilitiesPacket` retains the same decoded fields and getters. Its changes remove packet setters and use direct field assignment when reading/constructing/writing; the boolean masks and float reads/writes remain equivalent. The receiver remains the same direct ability-state sink.
- **Login: no direct movement-state delta under equal common fields.** Both `handleLogin` bodies reset position, register the same local player, install keyboard input, call `gameMode.adjustPlayer(player)`, and call `gameMode.setLocalMode(packet.getGameType())` (1.15.2 `:339–387`; 1.16.5 `:350–409`). The new `previousGameType` is stored by `setPreviousLocalMode`; it is previous-mode metadata for later mode-toggle behavior, not the current player movement mode/abilities applied by this receiver. The new dimension/registry/world metadata and flat/debug settings affect level setup and are outside this direct player-response slice. The current game type still updates abilities through the same `GameType.updatePlayerAbilities` path.
- **Other fields:** Move/teleport handlers set packet `onGround` identically in effect; the new setter is a direct assignment. The movement handlers' packet-thread gate, entity lookup, rotation conversion, and no-position/rotation-only branches show no additional direct local-player change. The supplied older direct-response audit already covers received entity motion and ordinary player-position correction; they are not reopened here.

## Remaining synchronization gate and limits

The position writes above are synchronous in the receiver through `Entity.lerpTo`; packet arrival relative to a particular local tick is not established. The tick residual's broader packet/state interleaving gate therefore remains open where a claim depends on the *next* movement tick, but it does not undo these direct receiver writes. Ability reception has no changed interpretation here. Server packet production/authority, movement-packet sequencing, world/block-state production, and runtime parity remain outside this closure. No product finding, canonical backlog edit, build, test, decompilation, or runtime launch was performed.
