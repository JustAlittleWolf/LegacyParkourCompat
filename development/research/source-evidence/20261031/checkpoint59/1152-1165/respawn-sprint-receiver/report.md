# Respawn receiver keeps sprint state without copying its speed modifier

## Pair and exact boundary

Pair: Minecraft 1.15.2 Mojmap → 1.16 Mojmap; the receiver change is first present in release ID `1.16` and remains through `1.16.5`.

In 1.15.2 `ClientPacketListener.handleRespawn` constructs a replacement `LocalPlayer`, copies the old player's synchronized entity data, then unconditionally runs `localPlayer2.getAttributes().assignValues(localPlayer.getAttributes())` (`ClientPacketListener.java:1042, 1078–1079`). Starting in 1.16, the handler still copies synchronized entity data, but copies attributes only when `clientboundRespawnPacket.shouldKeepAllPlayerData()` is true (`:1082, 1126–1129`). The new branch and its behavior remain in .1–.5. This evidence is about the direct client receiver and an input packet with that decoded field false; it does not claim which server event produces the field or packet sequence.

The new-player path does not itself restore the sprint attribute. `MultiPlayerGameMode.createPlayer` invokes `new LocalPlayer(...)`; its new constructor stores the old sprint value in `wasSprinting` but does not call `setSprinting`. `handleRespawn` assigns the prior entity-data list afterwards, copying `Entity`'s shared sprint flag to the replacement. `adjustPlayer` updates abilities and does not set sprinting. Consequently, for `shouldKeepAllPlayerData=false`, the sprint flag survives the handler while the old attribute map is omitted.

## Concrete same-input movement consequence

Choose a prior local player with the ordinary player movement-speed base `0.1` and an active sprint-speed modifier (the value installed by `LivingEntity.setSprinting(true)`: `+0.3` multiply-total), with the sprint bit true. Use a `ClientboundRespawnPacket` input whose `shouldKeepAllPlayerData` field is false. At the completed receiver boundary, the old path copied both sprint bit and the active modifier; the new path copies the bit but the replacement player has only the ordinary base movement-speed attribute. Under these stated equal inputs the old `Player.getSpeed()` is `0.13` and the new read is `0.1`.

For the concrete movement sequence, use unchanged forward input with `forwardImpulse >= 0.8`, food above six, no water/swimming, horizontal collision, item use, or blindness, and a flat block directly below the reset spawn position. `resetPos` clears velocity but does not set `onGround`; the newly constructed entity begins with the same false on-ground flag on both sides. The first airborne `Player.aiStep` computes equal `flyingSpeed` from the copied true sprint bit (`0.026` on both sides), and the airborne branch uses that same value; the local sprint-stop gate also leaves the sprint bit true. The downward movement then collides with the shared floor and `Entity.move` sets `onGround=true` for both endpoints. On the next local tick, the same forward conditions still preserve the sprint bit, and the grounded branch of `LivingEntity.travel` reaches `getFrictionInfluencedSpeed`: it reads `Player.getSpeed()` and supplies it to `moveRelative`. The horizontal movement input therefore uses `0.13 * 0.21600002/(friction^3)` versus `0.1 * 0.21600002/(friction^3)` before clipping. This source sequence establishes a reachable movement input difference; it does not predict the later tick position.
The receiver may be followed by a `handleUpdateAttributes` packet before movement; that is simply a different raw client input stream. This candidate is conditional on no intervening movement-speed attribute update that overwrites the replacement map before the eligible travel read. It does not require proof of server authority, default-attribute dirtying, or packet production frequency. A subsequent client position response may provide the stated `onGround` input; its producer is not claimed.

## Source boundary scan and integrity

I checked the `ClientPacketListener.java` and `LocalPlayer.java` bodies in 1.15.2, 1.16, 1.16.1, 1.16.2, 1.16.3, 1.16.4 and 1.16.5. The `shouldKeepAllPlayerData` gate is absent in 1.15.2 and present at 1.16, persisting through 1.16.5. The replacement LocalPlayer constructor's `wasSprinting` parameter is also introduced in 1.16 and persists. The release roots are exact Mojmap source trees. `source-hashes.tsv` records **36/36** inspected Java-source hashes matching their own release source manifest: `mojmap.sources.sha256` for sidecar-published releases and the release-local `.decompile-provenance.json` source map for 1.16.3/.4. The table's SHA-256 is `252a251077103f526a57e7a60799723b436fb79fd6cbfbc50e2771908064108e`.
