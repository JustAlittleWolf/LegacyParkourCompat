## Remaining equal-state registration delta: suffocation responses

The complete 1.16.5 registration census in this route has nine `.isSuffocating(...)` sites: leaves, moving piston, farmland, soul sand, grass path, stained glass, stained-glass panes, ShulkerBoxes, and piston bases (`Blocks.java`, 222, 349, 502, 740, 1968, 3206, 3219, 3235, 3246). Existing reports close leaves, liquids, soul sand's collision/speed provider, glass, moving-piston and piston-base provider gates, and the ShulkerBox opened-block-entity witness. The farmland and grass-path registrations were left unclassified by the suffocation witness census; they, together with the previously identified soul-sand registration, use the new unconditional predicate and need to remain explicit in the movement inventory.

A targeted comparison of movement-facing builder properties in all 680 same-name direct `Blocks` registrations found no other changed `.friction`, `.speedFactor`, `.jumpFactor`, or `.noCollission` call. The changed property calls outside suffocation are `isValidSpawn` additions on trapdoors, barrier, bedrock, carved pumpkins, jack-o'-lantern, and redstone lamp; `isRedstoneConductor` additions on beacon, observer, redstone block, and redstone lamp; `hasPostProcess` additions on mushrooms and magma; and `emissiveRendering` on magma. These govern spawn checks, redstone propagation, light/render processing, and do not add a direct LocalPlayer position/velocity/collision response in this route. Shulker `dynamicShape` is assigned in the shared `Blocks.shulkerBox` helper rather than the per-color registration statements and is part of the already checked Shulker provider route. New block registrations are outside this existing-block pair.

The three same-state registrations are:

These are source-confirmed predicate deltas for equal supplied states, not changed collision formulas. Their player consumer is concrete on both endpoints: old `LocalPlayer.aiStep` calls four `checkInBlock` probes under `!noPhysics`; `checkInBlock` calls `blocked`, whose vertical-cell loop reaches `Player.freeAt` and `BlockState.isSuffocating` (`LocalPlayer.java:385–388, 651–655; `Player.java:1489–1491`). New `LocalPlayer.aiStep` calls the four corresponding `moveTowardsClosestSpace` probes, and `suffocatesAt` calls `noBlockCollision` using `BlockState.isSuffocating` as a filter (`LocalPlayer.java:414–446, 656–661`). A player box overlapping the partial collision shape can therefore have the old provider say “not blocked” while the new provider admits the block through the suffocation filter; if a sampled escape direction is available, the new code can write horizontal velocity where the old code does not. This is conditional on the sampled player box/state and escape candidates; no trajectory was simulated.

The earlier soul-sand fixed-state report established equal collision and speed providers, but its note that the old default does not classify these partial shapes as suffocating is the premise for this separate `LocalPlayer` predicate delta. The farmland and grass-path registrations likewise require this exact consumer trace; a registration census by itself is not a movement finding.

## Wall and Iron Bars: fixed providers versus neighbor-derived states

For an already supplied wall state, the collision provider is closed: corresponding connected directions and `UP` produce the same collision arms/post. The LOW/TALL distinction in `WallSide` changes outline height, while the collision table uses 24 for both arm tops. This is the fixed-state result in `wall-block-variants/report.md` and `block-state-properties-audit/report.md`.

The remaining movement-relevant producer members are precise:

1. `WallBlock.connectsTo` gains `block instanceof IronBarsBlock` in 1.16.5 (`WallBlock.java:130–134`; old `:60–64`). `getStateForPlacement`, `sideUpdate`, and `updateShape` feed that result into the four directional wall properties (`:137–218`). On 1.15.2 an iron-bar neighbor is not a sturdy full face and is not a wall/fence gate, so it does not connect; in 1.16.5 it connects unconditionally. This is the already documented wall-to-bars path: when the adjacent supplied neighbor is iron bars, the new side state can select an extra collision arm returned by `getCollisionShape`, which `Entity.move` consumes through block-collision collection. It is a conditional state-generation delta; do not reopen the fixed-state LOW/TALL provider math.
2. `IronBarsBlock.attachsTo` gains `block.is(BlockTags.WALLS)` in 1.16.5 (old/new `IronBarsBlock.java`, source hashes below). Its placement and horizontal `updateShape` call `attachsTo` for each neighbor. When the neighbor belongs to effective `BlockTags.WALLS` and the old `attachsTo` result is false, the new bars state can add that direction while the old state does not. `CrossCollisionBlock.makeShapes`, `getAABBIndex`, and `getCollisionShape` preserve the fixed-state direction-arm math; `Entity.move` reads the state collision shape. This is a distinct bars-to-wall state producer from the existing wall-to-bars connection. The exact conditional domain is effective `BlockTags.WALLS` membership plus the old attachment result; Java sources alone do not establish arbitrary datapack tag contents.
3. `WallBlock.updateShape` additionally derives side `LOW`/`TALL` from the collision face of the block above and derives `UP` through `shouldRaisePost` (`WallBlock.java:160–257`). The legacy method uses its previous boolean-side/post rule (`:94–123`). The supplied fixed-state shape is already closed, but neighbor state, upper-block collision shape, `WALL_POST_OVERRIDE` tag membership, and notification-driven recalculation remain state-input dependencies for the actual `UP`/side values. No blanket claim that these producer outcomes are equal is made.

Waterlogged wall/bars liquid tick scheduling is not itself a direct local-player movement response. No server notification frequency or packet timing is required to establish the above conditional client query: the distinction is whether the relevant supplied local block states already have different directional properties when `Entity.move` samples them.

## PistonMovingBlockEntity: provider math closed, sampled state remains conditional

The existing provider/push-shape audit closes the named methods at equal moving-block-entity fields and state: `getCollisionShape` has the changed source-piston `SHORT` threshold (`1.15.2 :351`, `1.16.5 :353`); `getCollisionRelatedBlockState` changes the retracting head's `SHORT` selection (`old :89–96`, `new :92–99`); and `moveCollidedEntities` uses that shape to select and move entities. `MovingPistonBlock.getCollisionShape` dispatches to the block entity, and ordinary local-player `Entity.move` collects that shape. These are conditional provider deltas already documented and independently audited in `providers/coverage.md` and `provider-independent-audit/report.md`; they do not need server event-frequency proof.

The remaining item is the input boundary: 1.16.5 `PistonMovingBlockEntity.tick` retains a completed client block entity for up to five `deathTicks` (`:281–286`), and `finalTick` has a client-side cleanup condition when its block state is replaced (`:257–273`). Thus whether a later local-player collision sample has a moving-piston state plus its block entity is not established by the fixed-field provider comparison. Record that state-presence condition; do not require proof of server piston frequency, packet timing, or update ordering to keep the conditional provider claims source-covered.
