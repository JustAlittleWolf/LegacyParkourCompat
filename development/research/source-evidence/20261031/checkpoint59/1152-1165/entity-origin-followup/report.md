## Candidate row dispositions

### Direct player state writes found

- **`FireworkRocketEntity.tick` — movement-reachable local-player velocity writer; inspected 1.15.2 lines 100–150 and 1.16.5 lines 100–145.** Caller path: `FireworkRocketItem.use` (old lines 46–58; new 52–64) creates an attached rocket only when `player.isFallFlying()`; the entity constructor retains the player as `attachedToEntity` and publishes its entity id. On the logical client, the attached rocket resolves that target, checks `attachedToEntity.isFallFlying()`, then directly calls that entity's `setDeltaMovement` (old 112–126; new 111–125). The three-component formula, constants, addition order, and gate are the same. This is a concrete local-player write when the synced target is the local player and the elytra-state gate remains true; no endpoint delta in that direct response was found. The changed unattached-rocket horizontal acceleration/collision path (old 131–137 versus new 130–139) writes only rocket motion and is non-player projectile physics, outside scope. No changed packet interpretation is required to establish the unchanged player write; rocket target/item synchronization is an input to it.
- **`Boat.getDismountLocationForPassenger` / `LivingEntity.findStandUpPosition` plus added `DismountHelper` — movement-reachable server-origin position response with a changed endpoint algorithm.** Old dismount is not absent: `LivingEntity.stopRiding` (old line 2389) calls `findStandUpPosition` (old lines 1697–1792) after a successful detach under `!level.isClientSide`. For a boat, old code uses passenger yaw, passenger/boat widths plus `0.4`, a collision-free passenger box, and at most two upward candidate levels before falling back above the boat. New `stopRiding` (line 2568) calls `dismountVehicle` (new lines 1862–1871), which invokes the vehicle's location method unless the vehicle is removed or in a portal, then teleports the player. New Boat lines 677–703 computes a boat-yaw horizontal escape vector, skips candidates when the lower block is water, tries two floor heights for every dismount pose, sets the accepted pose, and falls back to the base vehicle location. Added helper lines 37–55 gates heights with finite-and-`< 1.0` and accepts only a pose-sized box with no block collisions. These paired source members differ in gates, geometry inputs, candidate order/height procedure, pose handling, and fallback. The caller is server-only, so this is a changed authoritative player-position response synchronized to the client, not client historical physics. The separate tick residual shows the server-player `teleportTo(double,double,double)` delegates to `connection.teleport(...)` unchanged in form (old line 1061/new 1183); client correction application is also covered there. Whether this server-origin difference should be represented in the client profile remains an open scope/dependency disposition. Do not count it as a closed no-route row.
- **`ThrownEnderpearl.onHit` — server-origin teleport response; disposition remains tied to server-origin/inbound-motion closure.** Old lines 46–117 and new 44–88 show the actual owner/entity-hit handling and destination operation. After the particle loop, old `!level.isClientSide` enters the authoritative path; new requires `!level.isClientSide && !removed`. For a connected, same-level, awake `ServerPlayer`, both versions detach a passenger if needed, teleport the owner to the pearl, clear fall distance, and apply fall damage; other non-null owners are teleported without player-only damage. Only the added `!removed` gate changes entry to these operations. The direct `teleportTo` is server-side; `ServerPlayer.teleportTo(double,double,double)` delegates to `connection.teleport(...)` (old line 1061/new 1183) in both versions, so the client receives position synchronization rather than executing this branch as historical local physics. The receiver's correction operation is same-form in the tick residual, but server-origin event production/timing is not closed here. The item caller `EnderpearlItem.use` (old/new lines 18–40) launches the pearl with the same `shootFromRotation` call. No local-player velocity write is present in that launch operation.
- **`ChorusFruitItem.finishUsingItem` — server-origin teleport route, no endpoint movement-operation delta in reviewed body.** Old lines 16–43/new 18–46 gate the entire random-teleport loop and cooldown under `!level.isClientSide`; both use the same 16 attempts, candidate arithmetic, passenger detach, `randomTeleport(..., true)` call, and player cooldown. The newer difference in the success block selects a Fox teleport sound; it does not alter destination or position write. `LivingEntity.randomTeleport` is paired same-form at old lines 2703–2747/new 2904–2948, including the loaded-chunk, downward-solid search, position rollback on failure, collision/liquid acceptance, and successful entity-event gates. Resulting position is server-origin and synchronized, not a client historical movement calculation. Keep any general server-origin/inbound-motion disposition open; do not claim an item movement difference from this sound change.
