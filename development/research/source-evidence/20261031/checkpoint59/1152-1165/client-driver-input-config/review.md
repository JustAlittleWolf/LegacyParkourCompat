- **Key state — `KeyMapping` (1.15.2 `:33–106,173–177`; 1.16.5 `:34–107,159–163`), `KeyboardHandler.keyPress` (1.15.2 `:269–379`; 1.16.5 `:274–381`) and `ToggleKeyMapping` (both `:6–22`):** `click`, `set`, `setAll`, `releaseAll`, `consumeClick`, and `setDown` preserve their state writes and gates. - **Movement option state — `Options` (1.15.2 `:95,113–161,270–343,531–553,585–603`; 1.16.5 `:87,105–155,276–349,569–591,623–641`) and `Option` (`AUTO_JUMP`: 1.15.2 `:233–235`, 1.16.5 `:364–366`; crouch/sprint toggle options: `:287–295` / `:424–432`; sensitivity: `:143–159` / `:239–260`):** defaults and forward/left/back/right/jump/sneak/sprint physical assignments are unchanged. Config loading/saving keeps the same values and setters for auto-jump, toggle crouch, toggle sprint and mouse sensitivity. However, `Options.keyMappings` adds `keySocialInteractions` (new default P) and renames `keySwapHands` (`key.swapHands`) to `keySwapOffhand` (`key.swapOffhand`). The `Options.load` binding loop matches serialized `key_` names against current `KeyMapping.getName`, so a prior custom `key_swapHands` setting will not match the new mapping and will fall back to its new default. Also, `KeyMapping.resetMapping` rebuilds the physical-key map by repeated `MAP.put(key, mapping)` over `ALL.values`; when a user assigns the new social-interactions or offhand binding to a movement key, collisions can change which mapping receives that event. These are conditional customized-key routes into sampled input; default movement bindings do not change. `Option.AUTO_JUMP` still reads/writes `options.autoJump`; toggle option callbacks still flip the same booleans; the sensitivity setter still assigns the supplied value. In changed `BooleanOption`, `CycleOption`, `ProgressOption`, and `LogaritmicProgressOption`, inspected changes convert UI label/result types from `String` to `Component`; underlying getters/setters and slider value math are unchanged. `FullscreenResolutionProgressOption` changes resolution labels only. Modified option helper implementations introduce no independent movement math delta.

## Remaining movement-adjacent route

`KeyboardHandler.handleDebugKeys` case 78 (F3+N; 1.15.2 `KeyboardHandler.java:151–160`, 1.16.5 `:146–155`) changes which `/gamemode` command is sent. In 1.15.2, creative requests spectator and every other mode requests creative; in 1.16.5, every non-spectator mode requests spectator and spectator requests `gameMode.getPreviousPlayerMode()`. The handler only sends chat commands; it does not write client abilities or key state. A server response could later change movement abilities, so treat this as a server-mediated mode/ability state origin for the parent to disposition; it is outside this direct input sampling and movement-tick eligibility/order slice. The changed key-name/additional-binding route above is the other remaining movement-input dependency; it is conditional on customized key assignments or old saved bindings. The remaining changed option helper rows are display-type changes only.
