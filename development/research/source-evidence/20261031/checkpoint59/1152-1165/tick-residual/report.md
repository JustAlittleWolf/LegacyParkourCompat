# Tick graph residual closure — Minecraft 1.15.2 → 1.16.5 (Mojmap)

## Scope and evidence boundary

This is a bounded source-only residual closure for the reachable local-player tick/travel/position/state/packet/effect/attribute paths identified as open in `.native-source/20261030/1152-1165-pool33/full-pair-audit/independent-source-audit.md`. It reuses the specifically named pool33 residual reports listed in `input-hashes.tsv`, then checks the exact paired canonical source files listed in `source-hashes.tsv` read-only. The corrected pair inventory says both literal Mojmap roots match their canonical manifests with zero missing/unlisted/mismatched paths; manifest hashes and source file hashes are recorded in the sidecars.

This closes only the bounded slices below. It does not claim full changed-path classification, pair freeze, acceptance, intermediate patch boundaries, or runtime/tick trajectory parity. Per coordinator routing, `FishingHook` and `TridentItem` rows/callers are excluded from this closure; the parent owns them.

## Ordered tick and reachable movement routes

- `Minecraft.tick` reaches `ClientLevel.tickEntities`; `ClientLevel.tickNonPassenger` and passenger traversal reach the entity tick methods. The endpoint driver files changed overall, but the prior full-pair audit and tick residuals confirm the local-player chunk-presence gate is retained. I did not classify unrelated client-driver changes as movement changes. `LocalPlayer.tick` then enters `super.tick`; `Player.tick`/`LivingEntity.tick`/`Entity.baseTick` update player and entity movement state before `LocalPlayer.aiStep` calls into `Player.aiStep` → `LivingEntity.aiStep` → travel. `Entity.move` remains the position/collision writer. These caller relations are recorded in the ordered map and the relevant entry methods; changed class hashes alone are not treated as behavior changes.
- **LocalPlayer input/cache residual, no independent delta in the examined members:** `isCrouching` changed from an on-demand pose/input predicate to a field read, with `LocalPlayer.aiStep` assigning that field from the same flight/swim/pose/sleep/shift expression before `input.tick(isMovingSlowly())`. The fixed-tick slowdown input is therefore the same under equal state. `Input` and `KeyboardInput` are byte-identical. The portal cooldown replacement only changes timer processing; the changed remaining LocalPlayer members are particle, rendering, sound, message, or recipe paths. The separately audited auto-jump scan/math is unchanged. These no-delta statements are restricted to those methods and fixed sampled state.
- **LocalPlayer changed movement gates:** the independently corrected LocalPlayer residual found that the newer `isSuppressingSlidingDownLadder` adds `!abilities.flying`; when old `onLadder` and new `onClimbable` both accept a non-scaffolding feet state, a flying, shift-held local player with negative Y velocity can retain downward motion clamped to `-0.15` in 1.16.5 where the old suppression zeros it. The helper result is installed before SELF movement; `Player.travel`'s later flying velocity reset does not undo the already applied position move. Vanilla default `CLIMBABLE` membership for blocks shared with 1.15.2 is shown to match the old hard-coded ladder/vine/scaffolding set; newer vine members are modern-only. Dynamic tag overlays remain outside the source roots. Other LocalPlayer changes (`onLadder`→`onClimbable` for Elytra request, eye-fluid reads, fluid descent gates, and closest-space response) belong to the separately named bounded slices, not this no-delta residual.
- **LivingEntity/player travel remains an in-scope delta graph:** water/lava/fall-flying branch structure and fluid predicates changed; the paired closures separately establish the lava jump/travel-depth deltas, cached eye-water ordering, new lava-current consumer, and Levitation fall-flying start/sustain gates. The Elytra glide operation order and constants are unchanged once that branch is selected. Jump impulse arithmetic and `jumpInLiquid`/water slowdown remain same-form; the `LivingEntity.aiStep` fluid jump-selection block is part of the separately closed fluid-height branch. The `getBlockSpeedFactor` Soul Speed route is post-1.15.2 and modern-only. These are source-level branch/state claims only; no trajectory is asserted.
- **Entity position/state residual, bounded no-delta:** outside the separately assigned collision/fluid/passenger paths, `moveRelative` preserves its input-vector normalization threshold and yaw rotation; `push(Entity)` preserves its overlap threshold, normalization, scale and velocity writes; fall-distance order, bubble-column response, stuck-block multiplier handling, raw/absolute position setter order, and dimension sizing are unchanged in the compared methods. The new server-only dimension refresh movement is gated away from client movement. The ordinary inherited tick delegation and unchanged block jump/speed factor lookup do not independently add a local-player movement delta. The separately assigned collision solver, fluid tracking/current, collision context and entity selection are not closed by this statement.

## Received state and movement modifiers

- **Position correction:** `ClientPacketListener.handleMovePlayer` keeps the same thread gate, relative/absolute coordinate handling, per-axis velocity preservation/zeroing, interpolation fields, position/rotation writes, acknowledgement and confirmation order. `absMoveTo` refactoring and `EntityDimensions.makeBoundingBox` preserve the same clamping and box arithmetic. The only extra handler branch is `tickCount > 0 && getVehicle() != null` then `removeVehicle()`; this is the existing separately routed mounted-correction direct response. The correction packet codecs are byte-identical. Thus there is no extra non-mounted correction delta in this slice.
- **Received motion:** `ClientboundSetEntityMotionPacket` is byte-identical; both handlers pass the decoded three-component velocity to `lerpMotion`. It is a same-form external velocity sink, not a second physics loop. Server knockback arithmetic changed, but its writer is server-side; this closure does not claim historical server physics.
- **Effects:** the receiver changed from `LivingEntity.addEffect` to `forceAddEffect`. For a stronger short effect with a weaker longer hidden fallback, a server update received after local expiration can be merged under the old expired active effect but replace the active entry in the new code. Jump Boost and Levitation readers are on the ordinary local movement path. The source route is closed by the effect/attribute residual; the difference is conditional on that state and packet timing, and does not itself establish a trajectory.
- **Attributes/equipment:** active modifier calculation order, sprint modifier math, Depth Strider lookup, Elytra gates, equipment/inventory slot updates, and active attribute packet arithmetic are unchanged for equivalent state. Packet modifier persistence representation changes to transient but preserves the active value. A separate ordinary death-respawn slice changes LocalPlayer attribute copying and can conditionally retain a sprint flag without the sprint-speed modifier in the newly constructed local attribute map. Its local movement read is `Player.getSpeed`/ground travel; the independent residual audit supplies the conditional path. The precise interval before a normalizing local/server update remains the named unresolved lifecycle timing dependency below.
- **Abilities/entity data:** paired ordinary ability application and shared entity-data application were traced where they feed sprint/fall-flying. The Levitation fall-flying sustain change is server-authored and arrives through entity-data sync; a particular local travel tick depends on packet ordering. The new-start denial is direct local input/state and does not require tag/resource membership in the clear-air case.
