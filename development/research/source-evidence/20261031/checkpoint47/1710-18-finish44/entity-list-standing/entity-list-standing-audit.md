## Query path and entity-list terminal operations

1.7.10 `World.getCollisions(Entity, Box)` (`world/World.java:972-1013`) clears and returns the world's shared collision list. 1.8 (`:873-923`) creates and returns a fresh `ArrayList`. Both scan block candidates first (block path is outside this entity-list slice), then query `getEntities(entity, shape.grown(0.25, 0.25, 0.25)` (old `:998-999`, new `:908-909`). The 0.25 expansion is broad-phase only; each result box is separately required to intersect the unexpanded query shape.

Entity membership is gathered by `World.getEntities` (old `world/World.java:2236-2254`, new `:2104-2123`) across loaded chunks. `WorldChunk.getEntities` (old `world/chunk/WorldChunk.java:683-706`, new `:699-721`) appends entities whose own shape intersects the expanded bounds and which are not the exact `exclude` entity; it also appends intersecting parts under the same identity check. These membership and bounds gates are equivalent for ordinary non-spectator entities; 1.8's default `EntityFilter.NOT_SPECTATOR` at `World.java:2104-2105` is a modern spectator-mode exclusion with no 1.7.10 counterpart. The no-filter old default also includes spectator-like entities if any existed, but 1.7.10 has no spectator mode.

For each returned entity, the terminal operations in `World.getCollisions` are:

- Append the returned entity's `getCollisionShape()` when non-null and intersecting the original query (`World.java:1002-1005` old; `:913-916` new).
- Append the moving/query entity's `getCollisionAgainstShape(returnedEntity)` when non-null and intersecting (`:1007-1009` old; `:918-920` new).
- No `isPushable`, `blocksBuilding`, player-type, or rider test is applied by these two append operations in either version. The ordinary entity base returns null for both hooks (`Entity.java:711`, `:1172` old; `:715`, `:1271-1272` new).

1.8 wraps both append operations in `if (entity.rider != var18 && entity.vehicle != var18)` at `World.java:912`, where `var18` is the whole returned `List`. This identity comparison is true for an Entity field versus a List object; it does not compare against the current list element and therefore excludes neither rider nor vehicle. The effective output is consequently the same as 1.7.10 for mounted partners. This is a source fact, not an assumption about intended behavior.

The only concrete non-null overrides of either collision-shape hook in the paired entity trees are vehicles: `BoatEntity` and `MinecartEntity`. For a local PlayerEntity query, the player-side `getCollisionAgainstShape` remains the base null result. Boat contributes its own box: old `BoatEntity.java:51-58`, new `:53-60`; both are its current entity shape (`shape` versus `getShape()`). The boat construction coordinate change preserves the same initial lower face: old `BoatEntity.java:31-36,65-72` sets eye height to half of 0.6 and calls `setPosition(x,y+eyeHeight,z)`; old `Entity.setPosition` (`Entity.java:215-223`) subtracts eye height. New boat constructor (`BoatEntity.java:34-38,67-74`) calls `setPosition(x,y,z)` and new `Entity.setPosition` (`Entity.java:225-232`) makes y the lower face. These formulas both yield the supplied y as the initial shape minimum. A player can therefore be directly clipped or supported by the boat's same AABB through `Entity.move`; this is a direct player response and is in scope, although boat physics is excluded.

Minecart's `getCollisionShape()` returns null on both sides (old `MinecartEntity.java:90-98`, new `:96-104`). Its `getCollisionAgainstShape(other)` returns `other.shape` / `other.getShape()` only when `other.isPushable()` (old `:90-93`, new `:96-99`). Since the query receiver for a local player is PlayerEntity, not MinecartEntity, minecart supplies no collision box to the player's movement list. Other entity movement and vehicle pushes are outside scope.

## Reachable local-player consumers and classification

- **Ordinary move and step/support clipping — checked, no entity-list delta.** Local player tick dispatch is established by the permitted ordinary-tick inventory. `Entity.move` calls the query for sneak-edge support and swept movement (old `Entity.java:383-584`; new `:370-608`; direct query lines old `:413,425,435,457,503`, new `:396,408,418,438,468`). It then clips Y, X, Z and step candidates against returned boxes; a vehicle box can set vertical collision/on-ground or clip position. The entity broad phase, two append gates and vehicle box formulas introduce no pair difference for the ordinary local-player path. The separate step-gate/candidate differences already recorded in the allowed collision slice are outside this entity-list verdict.
- **Can-move predicate — checked, no entity-list delta.** Old `Entity.canMove` queries moved shape and returns false for any collision or liquid (`Entity.java:377-381`); new routes through `doesNotCollide` with the same collision-empty and liquid gates (`:361-368`). This is a predicate, not a position writer; no player-specific change found.
- **Spawn/reset collision clearance — checked, no entity-list delta in query.** `Entity.resetPos` raises Y until the current box has no collisions (old `Entity.java:161-175`; new `:179-193`, with the added 256 world-height cap). It can be inherited by a player, but runs during spawn/position reset rather than each ordinary movement tick. The entity query treatment is as above; the Y cap is a separate non-entity-query change not pursued in this bounded audit.
- **Position correction collision lift — checked, no entity-list delta.** `Entity.lerpPositionAndAngles` sets requested position, queries the contracted box, finds the greatest collision maxY, and lifts position (`Entity.java:1272-1289` old; new `:1371-1394`, method has the added teleport flag). This is a direct position response if reached by a player. Returned vehicle AABBs participate identically in both query bodies. Full packet correction routing is not reopened here.
- **Dismount placement — direct player displacement checked; no entity-list dependency or paired delta found.** Old `PlayerEntity.startRiding(null)` (`entity/living/player/PlayerEntity.java:356-370`) and new inherited `LivingEntity.startRiding(null)` (`entity/living/LivingEntity.java:1476-1489`) clear rider/vehicle links and enter the placement search only under `!world.isMultiplayer` / `!world.isClient`, respectively. Player `rideTick` also only detaches on server (`PlayerEntity.java:374-377` old; `:387-391` new). That server-side search writes the player position via `this.teleport` and therefore is a direct PlayerEntity displacement; its paired bodies use the same candidate loop order, `(int)` coordinate conversion, moved-up player shape, block-only `getBlockCollisions` emptiness test, `hasSolidTop`/water checks, and x/z/y writes (old `LivingEntity.java:1040-1070`; new `:1051-1081`). It does not call `World.getCollisions` or use its entity list. Client-side calls skip the search on both sides. The drowning dismount guard is server-only as well (old `LivingEntity.java:208-210`; new `:216-218`). Generic base `Entity.startRiding(null)` writes vehicle x/z and vehicle shape minY + height (old `Entity.java:1244-1253`; new `:1343-1352`), but it is not the PlayerEntity override path when a player dismounts. Server-side player placement may be synchronized to a local client; packet routing is outside this bounded entity-list slice.
- **Push-away neighbor response — block-only; checked as a consumer boundary.** Player-specific suffocation response (`InputClientPlayerEntity.java:400-460` old; `LocalClientPlayerEntity.java:300-356` new per permitted collision slice) uses `getBlockCollisions`, and block full-cube/support predicates, not the entity-list query. `Entity.pushAwayFrom` likewise asks `getBlockCollisions` (old `Entity.java:1410+`, new `:1510+`). LivingEntity's `pushAwayCollidingEntities` asks `World.getEntities` and calls `isPushable`/`push` (old `LivingEntity.java:1450-1465`; new `:1460-1474`), but the routine moves other entities via `entity.push(this)`; that is non-player/vehicle push physics and does not write the local player's position. It is not counted as a player movement delta.

## Verdict and residual gaps

No actual 1.7.10-to-1.8 movement delta was found in `World.getCollisions`' entity-list assembly or in the direct local-player query consumers examined. The 1.8 rider/vehicle guard compares against the list object and is ineffective, so it does not change returned entities. Vehicle collision shapes that can directly affect a local player's move are equivalent for Boat; Minecart contributes no player-query box. Player dismount placement is server-gated and block-only; the paired player placement search is source-equivalent in this slice. Any server-to-client packet synchronization is not part of this entity-list audit.

Residual gaps: this is only the requested entity-list/support/displacement slice, not a pair freeze or runtime-parity claim. I did not enumerate every caller of `getEntities` outside the player movement response path; full push-away and non-player behavior remains excluded. I did not prove all entity subtype/part implementations outside the paired entity source tree or all network correction routing, and did not re-audit the block-only `getBlockCollisions` provider branches or world-border behavior. No source generation, builds, tests, or launches were performed.
