- **`sleep-response-placement.md`: ACCEPT after one accuracy edit.** The low-Y placement delta is confirmed for matching bed coordinates Y 0–127 in a loaded in-border chunk. The server's own-player teleport correction is sent before the sleep packet. In 1.7.10 that correction is handled by `ClientPlayNetworkHandler.handlePlayerMove`, which resets `eyeHeightSneakOffset` to `0.0F` before the following sleep handler. Therefore the actual response-path box delta has `o = 0`; the finding should state `oldMinY - newMinY = 0.04999999701976776` for this response, not leave `o` as an arbitrary preexisting offset. This is a precision and reachable-state correction, not a rejection of the placement finding.
- **`sleep-response-high-bed-coordinate-wrap.md`: ACCEPT after the same `o = 0` correction.** For a successful server sleep at Y=128 (and, by the same encoding, Y 128–255), the 1.7.10 packet reads the Y byte as a negative signed value; its client then fails the Y chunk gate and takes centered fallback. The 1.8 packed `BlockPos` preserves Y=128 and takes the loaded-bed placement path. In the actual response sequence the preceding 1.7.10 teleport correction resets the offset, so the old minY at Y=128 is exactly `-127.26250000298023`; remove `+ double(o)` from this finding's movement result.

These are **two separate accepted movement operations**: the low-Y finding concerns client placement/box construction (`PlayerEntity.trySleep` and `Entity.setPosition`); the high-Y finding concerns sleep-packet coordinate encoding/decoding (`PlayerSleepS2CPacket` and its buffer/position codec), which feeds a different client placement branch. ## Verified response order and gates

For both releases, server `ServerPlayerEntity.trySleep` first calls the superclass and sends a sleep packet only for status `OK` (1.7.10 lines 444–453; 1.8 lines 495–504). For the local player's connection the method call order is: entity-map broadcast, `networkHandler.teleport`, then `networkHandler.sendPacket(sleepPacket)`. `ServerPlayNetworkHandler.teleport` sends `PlayerMoveS2CPacket` to the player's network handler (1.7.10 lines 319–326; 1.8 lines 343–375). Thus the position correction precedes the sleep response packet on that ordered connection.

The 1.7.10 client correction handler unconditionally sets `minecraft.player.eyeHeightSneakOffset = 0.0F`, clears velocity, and applies corrected position/angles before returning (`ClientPlayNetworkHandler.handlePlayerMove`, lines 480–491). Its next sleep handler calls `trySleep` (`:620–621`) without a source write to that field in between. This closes the actual response-path `o` value as zero. In 1.8 the player has no such accumulator; the correction handler applies the absolute coordinates, then sleep handling calls `trySleep(BlockPos)` (`ClientPlayNetworkHandler.java:525–560, 683–686`).

Client sleep eligibility is skipped: 1.7.10 `PlayerEntity.trySleep` guards checks with `!world.isMultiplayer` (`PlayerEntity.java:1014–1038`), and its login handler sets the client world's `isMultiplayer=true` (`ClientPlayNetworkHandler.java:226–234`). 1.8 uses `!world.isClient` (`PlayerEntity.java:1071–1099`), while `ClientWorld` invokes its `World` constructor with `true` (`ClientWorld.java:47–50`; `World.java:104–110`). Both successful server responses therefore reach the client placement path without re-running server eligibility.

At old-server Y 128, server-side placement is possible because the 1.7.10 world loaded test accepts Y `<256` (`World.java:236–238`). The server sleep packet stores Y as `int`, but writes with `writeByte`; the client reads signed `byte` into `int` (`PlayerSleepS2CPacket.java:18–23,26–39`; `PacketByteBuf.java:486–489,606–609`). Thus 128 decodes as −128. The client loaded check rejects that negative Y and falls back to centered X/Z and requested Y `−128 + 0.9375F` (`PlayerEntity.java:1046–1068`). The 1.8 packet uses packed `BlockPos`; `writeBlockPos/readBlockPos` route through a packed long (`PacketByteBuf.java:57–63`; `BlockPos.java:8–14,120–128`). Its 12-bit signed Y field preserves 128, and `World.isChunkLoaded(pos)` accepts it when that in-border chunk is loaded (`World.java:159–174`).

For ordinary valid bed positions, both loaded placement branches use matching horizontal offsets and both fallback branches center X/Z. 1.7.10 `metadata & 3` maps 0/1/2/3 to SOUTH/WEST/NORTH/EAST-equivalent offsets (`HorizontalFacingBlock.java:10–12`; `PlayerEntity.java:1046–1068`). 1.8's `Direction.byIdHorizontal` map and loaded branch yield the same offsets (`BedBlock.java:199–204`; `Direction.java:11–14`; `PlayerEntity.java:1106–1127`). Out-of-world-border X/Z is outside these bounded candidate conditions because 1.8 `World.contains` checks the border while 1.7.10's Y/chunk check does not.

## Exact placement arithmetic and edits to make

1.7.10 sets size `0.2F × 0.2F`, assigns `eyeHeight = 0.2F`, then calls `setPosition(y + 0.9375F)` (`PlayerEntity.java:1044–1068`). `Entity.setPosition` computes minY as `requestedY - eyeHeight + eyeHeightSneakOffset` (`Entity.java:215–223`), with the requested Y stored as a `double`. 1.8 sets the same size and requests `posY + 0.6875F` (`PlayerEntity.java:1105–1127`); `Entity.setPosition` uses that requested Y directly as minY (`Entity.java:225–232`). At Y 0–127 the signed-byte packet leaves the coordinate unchanged. The server correction sets old `o=0`; therefore response-path minYs are exactly `bedY + 0.73749999701976776` and `bedY + 0.6875`, giving old-minus-new `0.04999999701976776`.

At Y=128, the old decoded request is −128, and the same old `setPosition` arithmetic with correction-reset `o=0` gives minY `-127.26250000298023`; the newer decoded position yields minY `128.6875`. Both formula differences are direct player-response placement effects; the packet Y wrap is a distinct serialization operation from the low-height placement formula.

Edits recommended without changing the findings here: remove the arbitrary `+ double(o)` term from both findings' stated successful-server-response results; in the low finding state the server correction resets the old field to zero; in the high finding report the exact old result with `o=0`. Keep the low placement scope at Y 0–127 and loaded in-border positions. Keep the high-coordinate finding anchored to Y=128 (or state 128–255 with the same signed-byte arithmetic). The separate operation boundary between placement math and packet-coordinate codec is justified by their independent source hooks and conditions.
