## Reachable callback path and inventory

`Entity.move` resolves collision and floor contact, then (where `makesSteps()`, not sneaking-step, and no vehicle) calls support `Block.onSteppedOn`; only afterwards does it update movement-distance/step sound. It then calls `Entity.checkBlockCollisions`, which scans the epsilon-inset player box in ascending X/Y/Z loops and calls each block's `onEntityCollision`. `PlayerEntity.mobTick` separately queries nearby entities and calls `entity.onPlayerCollision(player)`. Terminal callback inventory is below; common names map directly across versions, except state/position arguments changed from integer coordinates to `BlockPos`/`BlockState`.

`AbstractPressurePlateBlock`, `ButtonBlock`, `CactusBlock`, `CauldronBlock`, `CobwebBlock`, `DetectorRailBlock`, `EndPortalBlock`, `PortalBlock`, `SoulSandBlock`, `TntBlock`, `TripwireBlock`; plus base `Block` default (`1.7.10 Block.java:1133`, `1.8 Block.java:600`). No addition/removal of an override class in this paired inventory.

- `AbstractPressurePlateBlock` 1.7.10:92–99 / 1.8:93–100; gate `!world.isMultiplayer` / `!world.isClient`, only recalculates output signal and invokes state update. No player/entity movement field write. Its downstream behavior is redstone/state production.
- `ButtonBlock` 1.7.10:254–262 / 1.8:203–211; same server-only and wooden/unpressed gates, calls `updatePressed`, a redstone state/signal path; no player movement write.
- `CactusBlock` 1.7.10:116–118 / 1.8:98–100; applies cactus damage only (excluded damage resolution); no movement write.
- `CauldronBlock` 1.7.10:92–99 / 1.8:66–73; server-only; if entity burning, water level positive, and entity lower bound below `y+(6+3*level)/16`, extinguishes and decrements cauldron level. This writes fire state/world state, not position, velocity, onGround, sprint, sneak or jump; no subsequent same-tick travel branch is caused by it.
- `CobwebBlock` 1.7.10:19–21 / 1.8:22–24; unconditionally calls `Entity.onCobwebCollision`; paired bodies match. Entity method is 1.7.10:1486–1489 / 1.8:1579–1582: set `inCobweb=true`, `fallDistance=0`; paired and unchanged.
- `DetectorRailBlock` 1.7.10:36–44 / 1.8:44–50; server-only, only checks the powered bit and recalculates output state. Event/state production only; no player movement write.
- `EndPortalBlock` 1.7.10:60–64 / 1.8:61–65; same vehicle/rider-null and logical-server-only gates; calls `entity.changeDimension(1)`. Not a historical logical-client movement callback; excluded from client movement replay. Gate/call unchanged.
- `PortalBlock` 1.7.10:159–163 / 1.8:164–168; same `vehicle == null && rider == null` gate then `Entity.onPortalCollision()`. That method sets `inPortal`, and only computes portal-facing on logical server (`!world.isMultiplayer` / `!world.isClient`). Client-side entry signal and gate match; server-only orientation/dimension path is not client movement replay. No paired difference found in this route.
- `SoulSandBlock` 1.7.10:22–25 / 1.8:24–27; paired body always multiplies `velocityX` and `velocityZ` by `0.4`; no delta.
- `TntBlock` 1.7.10:94–102 / 1.8:91–100; server-only and requires an on-fire arrow; primes/removes TNT. Event/state path; the entity colliding is an arrow, not player, and no player movement write.
- `TripwireBlock` 1.7.10:130–136 / 1.8:151–157; server-only, checks the unpowered state and recalculates powered state. Event/state production only; no player movement write.

### `onPlayerCollision` override-name inventory (complete in `net.minecraft.entity`)

`ArrowEntity`, base `Entity`, `ExperienceOrbEntity`, `ItemEntity`, `PlayerEntity` dispatcher, `SlimeEntity`; same names both sides. `PlayerEntity` 1.7.10:461–475 / 1.8:478–491 loops nearby entities and calls `onPlayerCollision`; 1.8 adds `!isSpectator()` to the positive-health gate (spectator is a newer feature), otherwise dispatch is unchanged. Base `Entity.onPlayerCollision` is empty on both sides (1.7.10:915–916 / 1.8:955–956). Item/arrow/XP handlers are server-only pickup/inventory/XP updates and do not write player position/velocity or movement flags. `SlimeEntity.onPlayerCollision` is damage-only in both versions (1.7.10:173–181, 1.8:190–194); damage excluded. No callback in this inventory directly changes player movement. Non-player `Entity.push` differences were not treated as player movement: its `pushAwayCollidingEntities` caller is server-side and entity physics is excluded.

### `onSteppedOn` and fall callbacks

`onSteppedOn` overrides in 1.7.10 block tree: `RedstoneOreBlock`, `StairsBlock`, plus base `Block`; in 1.8: the same plus `SlimeBlock` (introduced in 1.8 and out of 1.7-era map scope). `StairsBlock` delegates to its base block. `RedstoneOreBlock` 1.7.10:36–39 / 1.8:40–43 calls `interact` and base; `interact` only emits particles and swaps unlit ore to lit ore (1.7.10:47–52 / 1.8:51–56). It does not write entity movement state; collision shape remains unchanged. The callback ordering/count differs: 1.7.10 invokes support callback only after `distanceMoved > blocksWalkedOn` (Entity.java:601–617); 1.8 invokes each eligible grounded move before distance accumulation (Entity.java:574–603). With the complete old-era override route closed, there is no reachable player position/velocity/flag delta or same-tick travel branch from that changed callback timing.

`onFallenOn` overrides are `FarmlandBlock` both sides and `SlimeBlock` only in 1.8; base `Block` default exists both sides. Old-era farmland path is fall/state/damage-side and does not change player velocity/position; fall damage is excluded. Slime bounce is introduced with the 1.8-only block and excluded under the modern-only-feature boundary. Block `beforeCollision` exists only in 1.8 and is overridden only by its new `SlimeBlock` in this inventory; exclude that newer feature.

## Compared movement/effect slices and verdicts

- `Entity.checkWaterCollisions` 1.7.10:741–783 / 1.8:745–790; same sampling box `shape.grown(0,-0.4F,0).contract(0.001,0.001,0.001)`, material WATER, splash-first-contact gate, and state writes to fall distance/inWater/fire timer. 1.8 extracts splash visuals into `doSplashEffect`; rendering/sound difference excluded.
- `World.applyLiquidDrag` 1.7.10:1573–1611 / 1.8:1462–1502; same floor/max+1 sampling bounds, y/x/z loops, liquid surface threshold (`bounds.maxY >= y+1-heightLoss`), accumulated flow normalization, coefficient `0.014`, and entity liquid-collision gate. 1.8 calls `isAreaLoaded(..., true)`; that is its default allow-empty mode and is equivalent to 1.7's loaded-area gate. Liquid `getHeightLoss` math also matches: `(state+1)/9.0F`, with state >= 8 treated as 0 (1.7.10 LiquidBlock.java:57–63 / 1.8:41–47). `containsMaterial` samples matching material and has no fluid-height test on both sides.
- `Entity.isSubmergedIn` 1.7.10:789–802 / 1.8:824–837 uses eye height, floored block coordinates, same liquid height loss minus `0.11111111F`; 1.8's extra player conditional is algebraically the same boolean result.
- `Entity.isInLava` paired: `containsMaterial(shape.grown(-0.1F,-0.4F,-0.1F), LAVA)` unchanged (1.7.10:808–810 / 1.8:839–841).
- `LivingEntity.jump` paired: initial Y `0.42F`, jump boost `(amplifier+1)*0.1F`, then sprint impulse `-sin(yaw)*0.2F`, `+cos(yaw)*0.2F`, velocityDirty (1.7.10:1080–1093 / 1.8:1088–1105; 1.8 factors jump strength through default method returning `0.42F`, with no PlayerEntity override). Water/lava jump branch has same `+0.04F` (1.7.10:1403–1410 / 1.8:1427–1435; 1.8 factors methods, both add 0.04).
- `PlayerEntity.moveRelative` sprinted flight delta: 1.7.10:1236–1250 assigns temporary `speedInAir=abilities.getFlySpeed()` for `abilities.flying && vehicle==null`, calls `super.moveRelative`, restores speed; 1.8:1277–1290 assigns `getFlySpeed() * (isSprinting() ? 2 : 1)` under same gate and same call/restore. With local control, `isLocallyControlled()` gates base movement; a flying, unmounted, sprinting local player with directional input has horizontal acceleration scale multiplied by two in 1.8. Default flySpeed is 0.05F; sprint flight scale is 0.05F in 1.7.10 and 0.1F in 1.8. Sources/hashes sent to coordinator in chat.
- `LivingEntity.moveRelative` adds Depth Strider water movement in 1.8 (1.7.10:1095 onward / 1.8:1115 onward); level capped 3 and halved off-ground, interpolate water friction `0.8F` toward `0.54600006F`, input scale `0.02F` toward `getSpeed()`. Level 0 follows old constants. Enchantment is absent in 1.7.10; disposition as newer modern-only feature.
- `LivingEntity.setSprinting` paired identical speed modifier UUID and operation (`0.3F`, op 2), with same remove-existing then add-if-true order (1.7.10:1007–1017 / 1.8:1022–1032). `StatusEffect.SPEED` and `SLOWNESS` modifier amounts/UUIDs/op match (`+0.2F`, `-0.15F`, op 2); `JUMP_BOOST` formula matches. No status/effect movement delta found.
- `MovingBlockEntity.moveEntities/tick` 1.7.10:80–135 / 1.8:80–148: progress transforms, collision query, moved-entity list, `amount=progress-lastProgress+0.0625F` on extension, terminal `0.25F` push and tick sequence match for ordinary moved blocks. 1.8 adds a moved-Slime-and-extending branch that writes the facing-axis velocity to +/-1 instead of `Entity.move`; slime block/behavior is new in 1.8, excluded for a 1.7 profile.

## Direct client player response confirmed

`ClientPlayNetworkHandler.handlePlayerMove(PlayerMoveS2CPacket)` is 1.7.10:480–499 and 1.8:525–568. 1.7.10 `PlayerMoveS2CPacket` reads/writes absolute X/Y/Z, yaw/pitch, onGround, with no relative-axis representation (`PlayerMoveS2CPacket.java:28–44`). Handler zeroes all three velocity components, resets `eyeHeightSneakOffset`, updates position/angles, then acknowledges with packet rotation/onGround. 1.8 packet adds relative-argument flags (`PlayerMoveS2CPacket.java:29–45`); handler applies X/Y/Z relative args by adding to current coordinate and preserving that axis velocity, otherwise leaves absolute coordinate and zeros corresponding velocity; relative yaw/pitch add current rotation. It updates and acknowledges with `onGround=false`. Source-level code delta confirmed; reachability is separate because native 1.7.10 logical packets cannot express the relative-axis cases. Applicability when an old profile consumes a newer protocol packet is left for master decision. Exact file hashes sent to coordinator in chat.

## Received client packet movement-state audit (follow-up)

Paired scope here is only `ClientPlayNetworkHandler` receive paths and packet payloads that can affect the local player's movement state or equipment/effects read during travel. `PacketUtils.ensureOnSameThread` is present in many 1.8 handlers and absent in the 1.7.10 counterparts; it does not change the field writes once executed on the client thread.

### Same logical/representable movement updates, no source-level movement delta

- `handleEntityVelocity(EntityVelocityS2CPacket)`: 1.7.10 `ClientPlayNetworkHandler.java:382–387`; 1.8 `:412–418`. Resolve entity ID; if found, call `Entity.lerpVelocity(packet.velocityX/8000.0, velocityY/8000.0, velocityZ/8000.0)`. The helper writes the three components directly on both sides. Packet carries entity ID and three signed shorts on each side; 1.8 changes only entity-ID encoding int→VarInt.
- `handleExplosion(ExplosionS2CPacket)`: 1.7.10 `:748–755`; 1.8 `:824–831`. After explosion handling, add packet's three float player-velocity components to local velocity in X/Y/Z order on both sides. The packet's player-velocity payload and addition order match; other explosion construction/block damage is outside this movement slice.
- `handlePlayerAbilities(PlayerAbilitiesS2CPacket)`: 1.7.10 `:1150–1158`; 1.8 `:1267–1276`. Same direct writes for flying, creative, invulnerable, canFly, flySpeed, walkSpeed. Packet classes carry the same four ability bits and two float speeds; flag/speed semantics match. These fields feed the already-reported flight-speed difference, but the receive operation itself has no delta.
- `handleEntityStatusEffect` / `handleEntityRemoveStatusEffect`: 1.7.10 `:1103–1118`; 1.8 `:1131–1139` and `:1219–1225`. Both resolve entity, require `LivingEntity`, create/add a status with same id/duration/amplifier/permanent state, and remove by same effect id. 1.8's packet adds a particle flag and uses VarInt entity/duration encoding; `particles` is not movement. Speed/slowness attribute transport is separately received by EntityAttributes; jump boost is consumed by the same paired jump formula. No movement difference from status packet reception itself.
- `handleEntityAttributes(EntityAttributesS2CPacket)`: 1.7.10 `:1308–1331`; 1.8 `:1495–1519`. Same entity lookup/type invariant; for each entry find/register attribute, set base, clear modifiers, re-add packet modifiers in order. Payload carries the same attribute names/base values/UUID/value/operation semantics; 1.8 uses VarInt counts/IDs and UUID helper methods instead of fixed int/short/long pairs. No source-level movement delta.
- `handleEntityEquipment(EntityEquipmentS2CPacket)`: 1.7.10 `:963–968`; 1.8 `:978–984`. Same entity lookup and `setEquipment(slot,item)` call. Packet ID encoding changes int→VarInt, but slot short and ItemStack semantics match. `handleInventoryMenuSlotContent` / `handleInventoryMenuContent` (1.7.10 `:847–869`, `:887–894`; 1.8 `:860–883`, `:902–910`) update local player inventory/menu slots for matching menu IDs; `handleSelectSlot` (1.7.10 `:441–445`; 1.8 `:480–485`) applies the same `[0,hotbarSize)` gate and selected-slot write. These are same-semantic transport paths; 1.8-only enchantment/equipment effects such as Depth Strider remain modern-only/applicability-open for an old profile.
- `handleEntityData(EntityDataS2CPacket)`: 1.7.10 `:390–395`; 1.8 `:421–427`. Both resolve entity, require non-null metadata entries, and update the synced-data tracker. Same payload meaning; entity-ID encoding changes int→VarInt. Synced flags can affect sprint/sneak predicates, but there is no handler delta for representable metadata.
- `handlePlayerRespawn(PlayerRespawnS2CPacket)`: 1.7.10 `:725–745`; 1.8 `:801–821`. Both optionally rebuild client world for dimension change, invoke `minecraft.respawnPlayer(dimension)`, then set game mode. The world flag assignment changes (`isMultiplayer=true` vs `ClientWorld`'s `isClient` model), with no packet-provided position/velocity change identified in this handler. Spawn restoration remains a separate player-respawn path and is not claimed as paired parity here.
- `handlePlayerSleep(PlayerSleepS2CPacket)` is a confirmed direct-response delta, separate from server-side bed-entry eligibility. Handler 1.7.10 `ClientPlayNetworkHandler.java:620–622`; 1.8 `:684–687`; both resolve the packet's addressed player ID and call `trySleep`. `PlayerSleepS2CPacket` 1.7.10 carries ID plus x/y/z integers (packet class `:9–61`); 1.8 carries ID plus `BlockPos` (`:10–50`). Client bypass gates match semantically: 1.7.10 skips eligibility when `!world.isMultiplayer` is false; 1.8 skips when `!world.isClient` is false. In the common post-gate response, both unmount if needed, set size to `0.2F x 0.2F`, choose matching facing-based X/Z offsets (`0.1F`, `0.5F`, `0.9F`; center fallback when chunk unavailable), mark sleeping, zero all velocity components, and record the bed position. Raw `Entity.y` differs: 1.7.10 sets eyeHeight to `0.2F` then calls setPosition with `bedY+0.9375F`; 1.8 calls setPosition with `bedY+0.6875F` and sets sleeping afterward. Normalize against paired position writers: old `Entity.setPosition` places box minY at `y-eyeHeight+eyeHeightSneakOffset`; 1.8 sets box minY directly to y. With the usual zero sneak offset, collision-box minY is bedY+`0.7375F` old versus bedY+`0.6875F` new, a `0.05F` lower physical placement in 1.8 (retain the old offset term if nonzero). Eye-height after sleeping matches at `0.2F`: 1.7 field write and 1.8 `PlayerEntity.getEyeHeight()` sleeping branch (`1.8 PlayerEntity.java:1635–1645`). This is post-receipt placement/velocity behavior only; bed-entry eligibility remains excluded. PlayerEntity file hashes: 1.7 `350901699E449537372E1C4AF6A79AE256DE39638CDAD049DFC7800B6607791C`; 1.8 `13FA1367B71035EFBFCCC593DE57838268B10A8CEEBB0AA76AD3D819B44CB0CA`. Sleep packet hashes: 1.7 `DA8A5443E9C2F3CC2788014ED090C0657CB0BC348A7FFED53043BC592B31A8DF`; 1.8 `19980BB6403941C405E59BDCC12DBE2C02585436B58D3020A450217D382A7350`.

### 1.8-only fields/paths; applicability remains separate

- `EntityMoveS2CPacket` and `EntityTeleportS2CPacket` add `onGround` fields in 1.8 (the 1.7 packets have none). `handleEntityMove` 1.8 `ClientPlayNetworkHandler.java:488–503` and `handleEntityTeleport` `:457–477` write that bit after position interpolation; 1.7 `handleEntityMove` `:448–461` and `handleEntityTeleport` `:425–438` do not. Handlers resolve an entity ID without a local-player exclusion, but the native server's self-correction route is `PlayerMoveS2CPacket`; classify these as remote-entity packet fields, with old-profile/new-protocol local applicability open rather than inventing a 1.7 counterpart.
- `CameraS2CPacket` and `handleCamera` exist only in 1.8 (`ClientPlayNetworkHandler.java:1168–1174`); it changes active camera entity. `LocalClientPlayerEntity.isCamera()` feeds the 1.8 local AI/input gate, so this is a newer spectator-camera feature and has no 1.7 native packet equivalent; applicability under old profile is open.
- 1.8 adds `EntitySyncS2CPacket`/`handleEntitySync` (`ClientPlayNetworkHandler.java:1323–1329`), which dispatches to `Entity.syncNbt`. The only `syncNbt` declaration in the 1.8 entity tree is base `Entity.syncNbt`, an empty method; no player movement state write is reachable through this path in the paired client sources.
- 1.8 `GameEvent` includes spectator/game-mode behavior absent as an equivalent 1.7 mode feature; classify as newer mode semantics, not old-profile movement. Common rain/game-mode packet branches do not directly write player movement fields.

### Path inventory boundaries and residuals

The local-player receive paths inspected were correction, sleep, velocity, explosion, abilities, entity metadata/status/add/remove effects, entity attributes, entity equipment/inventory slot/content/selection, respawn, and game mode/camera. Entity move/teleport paths were checked as entity-ID based, not local-player-specific; new onGround fields remain applicability-open if protocol routing ever targets the local entity. PlayerHealthS2CPacket is excluded by the assignment's health/food boundary. Other entity-event packets and non-movement presentation packets were not expanded. No ordinary travel delta beyond prior flight and Depth Strider findings surfaced in this receive-path audit.
