# 1.18.2→1.19.4 adjacent-edge collision/world inventory

## Scope and evidence

This is a source-only movement inventory for the collision/world lane, across the six exact Mojmap roots from 1.18.2 through 1.19.4. It is member-level and does not claim full-pair or runtime parity.

For each endpoint, the scan covered every Java file under `world/entity/`, `world/level/block/` (including nested block/entity and state packages), and `world/phys/shapes/`, plus the `CollisionGetter`, `BlockCollisions`, `BlockGetter`, `LevelReader`, `Level`, `WorldBorder`, `AABB`, `Vec3`, `FluidState`, `BlockPos`, `Vec3i`, `Mth`, and `BlockHitResult` core sources. The selected file hashes are in [source-hashes.tsv](source-hashes.tsv); all matched the version's source manifest. [source-identity.tsv](source-identity.tsv) records the requested manifest SHA-256 values, scanned file counts, and zero selected-file mismatches.

Collision/query routes reviewed include `Entity.move` → `maybeBackOffFromEdge` / `collide`, `CollisionGetter.noCollision` / `getBlockCollisions`, the default block collision shape path in `BlockBehaviour`, the block shape providers and static `VoxelShape` definitions, `BlockGetter` floor-height and clip routes, entity fluid-height sampling, pose/dimensions and bounding-box refresh code, and registration/state dependencies for block shapes. Neighbor-sensitive shape-provider classes were scanned for shape and placement/update methods. Resource/tag payloads are not part of the Java source trees; tag-controlled survival remains unresolved below.

## Eligible source-level candidate

### 1. `1.18.2→1.19`: Player edge-backoff adds a nonpositive-Y gate

**Source fact.** In 1.18.2, `Player.maybeBackOffFromEdge` starts with the flying, mover-type, ground-surface, and `isAboveGround()` gates (`Player.java:1032–1036`). From 1.19 through 1.19.4, the same condition additionally requires the requested movement's `y <= 0.0` (`Player.java:1060–1065` in 1.19; `:1041–1046` in 1.19.4). `Entity.move` calls this hook before collision resolution (`Entity.java:562` in 1.18.2, `:566` in 1.19, `:568` in 1.19.4). When enabled, its axis loops repeatedly call `level.noCollision` on the player's offset bounding box and trim X/Z by `0.05` (`Player.java:1038–1076` in 1.18.2; `:1070–1090` in 1.19; `:1051–1071` in 1.19.4).

**Movement inference, conditional.** For a player request with positive Y, the old hook can run the collision-tested horizontal trimming loops while 1.19+ skips them. If the old loops would trim that request against the tested boxes, the horizontal request reaching `Entity.collide` is reduced in 1.18.2 and is not reduced by this hook in 1.19+. The effect depends on the normal hook gates and the per-step `noCollision` results; no trajectory was executed.

**Boundary.** This is distinct from the separately reviewed `fallDistance` writer that feeds `isAboveGround()` and from the airborne-sprint timing scope. The `isAboveGround()` predicate itself remains a gate and is not re-audited here. The candidate concerns the newly added requested-Y condition.

## State-scope disposition (Leaves waterlogging; not drafted)

1.19 adds `WATERLOGGED` to the existing `LeavesBlock` state definition and makes `getFluidState` return `Fluids.WATER.getSource(false)` when true (`LeavesBlock.java:24–35, 105–108, 127–128`). `Entity.updateFluidHeightAndDoFluidPushing` samples fluid states under the entity bounds and updates fluid height / movement from sampled flow (`Entity.java:2769–2833` in 1.18.2; `:2797–2861` in 1.19; `:2887–2951` in 1.19.4).

This possible query difference depends on preserving the new `WATERLOGGED` state in a profile whose 1.18.2-era state model does not contain that property. Because applicability depends on mapping a newly introduced state/feature to historical movement behavior, this is not drafted as an eligible 1.18.2→1.19 finding under the project's modern-only-feature/state scope. The inventory records the source path for completeness, but leaves the mapping decision open.

### Provider and neighboring-state checks

- The public/protected `getShape`, `getCollisionShape`, `getBlockSupportShape`, `getVisualShape`, and `getOcclusionShape` methods and named static `VoxelShape` initializers were compared in existing provider classes at each edge. No existing block's movement collision geometry changed in these methods. The notable method delta is `SkullBlock.getShape` for PIGLIN, a new block type; regular existing skulls retain `SHAPE`.
- `ButtonBlock.getShape` is the same state-to-shape selection by floor/wall/ceiling face, facing, and powered state. The 1.19.3 switch-expression rewrite explicitly lists UP/DOWN in the old fallback branch. Registration factoring is checked through the `Blocks.java` helper bodies; both shared factories retain `noCollission()`, so these outline shapes do not become block collision shapes.
- The existing XZ/XYZ offset provider overrides in 1.18.2 are constant returns. Their 1.19+ registrations use those same constant values. In 1.19.4, `BlockBehaviour.Properties.offsetType` generates the corresponding XZ/XYZ lambda with the prior coordinate seed, bit masks, float casts, clamping, and output values. No state-dependent vanilla offset registration was found in the inspected `Blocks.java` registrations.
- `SnowLayerBlock.canSurvive` changes from a fixed set of block checks to `SNOW_LAYER_CANNOT_SURVIVE_ON` / `SNOW_LAYER_CAN_SURVIVE_ON` tags (`SnowLayerBlock.java:84–90` in 1.18.2 and `:90–96` in 1.19). Because snow-layer height controls its collision shape, changed tag membership could alter neighboring snow-layer persistence and hence later collision geometry. Java-only source evidence does not provide those tag payloads or the resulting world-state transitions, so this remains an environmental dependency, not an accepted movement finding.
- `MultifaceBlock.getStateForPlacement` is reorganized in 1.19 around `isValidStateForPlacement` (1.18.2 `MultifaceBlock.java:132–151`; 1.19 `:173–189`). The existing registered Glow Lichen block is `noCollission()` in both endpoints; the newly added Sculk Vein is a new block. The placement refactor can affect outline-face state evolution but does not add a movement collision shape for the existing registered block in this window.
- `CollisionGetter`, `VoxelShape`, and `Shapes` are byte-identical across the six endpoints. `BlockState` differs at 1.19.2→1.19.3 only in its registry codec expression. `LevelReader` changes in the inspected edges are light/pathfinding/registry APIs, not collision-query bodies. Pose enums add mob poses in 1.19 and 1.19.3; no corresponding player dimensions/pose-selection delta was found.
