# Addendum: fall-flying sprint gate can feed the existing airborne-speed finding

This addendum extends the applicability route of the existing 1.19.3→1.19.4 LocalPlayer airborne sprint-speed finding; it does not propose a separate movement operation.

1.19.3, Mojmap: `net/minecraft/client/player/LocalPlayer.java`, `aiStep`, 709–717, starts sprint when the sprint key is held and existing input/food/item/effect gates pass; it has no fall-flying exclusion. The following sprint-retention block at 719–728 keeps sprint when forward impulse remains, food is adequate, no collision gate applies, and the player is not entering the water-only cancellation path; key release alone does not clear sprint. `net/minecraft/world/entity/player/Player.java`, `aiStep`, 513–517, updates `flyingSpeed` only after `super.aiStep()` completes, from `0.02F` plus `0.006F` when sprinting.

1.19.4, Mojmap: `net/minecraft/client/player/LocalPlayer.java`, `canStartSprinting`, 1022–1030, adds `!this.isFallFlying()` and the sprint-key branch in `aiStep`, 696–698, calls that predicate. `net/minecraft/world/entity/player/Player.java`, `getFlyingSpeed`, 2112–2117, reads current sprint state and returns `0.025999999F` while sprinting or `0.02F` otherwise. `net/minecraft/world/entity/LivingEntity.java`, `travel`, 2048–2088 uses an Elytra-specific branch while fall-flying; after the same player state becomes non-fall-flying, ordinary air movement uses `getFrictionInfluencedSpeed`, 2197–2198, which calls `getFlyingSpeed()` in 1.19.4. In 1.19.3 this caller returns the `flyingSpeed` field at 2246–2247.

Conditional route: Start on foot, not sprinting, fall-flying, with enough food, no blindness or item use, forward input at or above the sprint threshold, and sprint key held. Keep forward input but release sprint before the fall-flying flag clears. With no collision and outside water, 1.19.3 can start sprint during glide and retains it after key release; 1.19.4 cannot start sprint while fall-flying and remains non-sprinting. Glide travel itself does not read sprint for its movement math, so this addendum makes no claim of a different in-glide movement response. On the first same tick after the shared fall-flying state clears, old LocalPlayer still retains sprint while new does not; the 1.19.3 airborne speed field still reflects the preceding sprinting tick, while 1.19.4's getter sees current non-sprinting state. The normal airborne movement branch therefore uses different horizontal input speed and changes resulting displacement. The state-clear packet/state producer is conditioned as a shared input; server production behavior is not inferred. The route also requires no intervening synchronized shared-flags write to replace the divergent sprint bit before ordinary air travel.
