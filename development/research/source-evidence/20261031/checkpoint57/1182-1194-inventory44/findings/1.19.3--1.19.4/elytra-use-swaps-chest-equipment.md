# Equipable use swaps occupied gear and changes player movement

1.19.3, Mojmap: `net/minecraft/world/item/ElytraItem.java`, `use`, 31–45, moves the held Elytra to the equipment slot only when that slot is empty; it returns failure when occupied. `net/minecraft/client/multiplayer/MultiPlayerGameMode.java`, `useItem`, 349–374, returns `PASS` in spectator mode, rejects an item on cooldown, otherwise invokes `Item.use` on the client player and applies the returned held stack.

1.19.4, Mojmap: `net/minecraft/world/item/ElytraItem.java`, `use`, 28–30, delegates to `Equipable.swapWithEquipmentSlot`. `net/minecraft/world/item/Equipable.java`, 22–42, equips the held stack when the current item has no binding curse and differs from the held stack, replacing a nonempty equipment slot by returning a copy to the hand. `net/minecraft/client/multiplayer/MultiPlayerGameMode.java`, `useItem`, 349–374, returns `PASS` in spectator mode, rejects an item on cooldown, otherwise invokes this on the client and applies the returned held stack.

Difference: 1.19.4 can equip an Elytra from hand over a nonempty, non-binding-cursed chest item; 1.19.3 fails that use. The helper mutates `Player.setItemSlot` on either logical side, including the client use path.

Movement meaning: After the successful local swap, a later ordinary airborne jump input with an enabled Elytra, no water or Levitation, and the existing jump/pose gates passes `LocalPlayer.aiStep` (1.19.3, 751–755; 1.19.4, 732–736). It reads the equipped Elytra and calls `Player.tryToStartFallFlying` (1.19.3, 1581–1590; 1.19.4, 1570–1580), which sets shared flag 7 locally through `startFallFlying` (1.19.3, 1593–1595; 1.19.4, 1582–1584). `LocalPlayer.aiStep` calls `super.aiStep` afterward (1.19.3, 814; 1.19.4, 795); `LivingEntity.travel` then selects the fall-flying movement branch instead of ordinary falling. This is a direct client-side player equipment/state response before server state production. The route assumes no intervening synchronized equipment/shared-flags update replaces the local state before that movement tick; no server item-use or flight-acceptance behavior is inferred.


Additional same-operation route: In 1.19.3 `net/minecraft/world/item/ArmorItem.java`, `use`, 110–124, likewise equips only when the target slot is empty and otherwise fails. In 1.19.4 `ArmorItem.use`, 110–112, also delegates to `Equipable.swapWithEquipmentSlot`; this is the same shared swap operation, not a separate finding. For held boots enchanted with Soul Speed and different prior boots explicitly lacking Soul Speed and the binding curse in the feet slot, the new client use can equip the enchanted boots while the old use fails. The client movement consumer reads that equipment directly: `LivingEntity.getBlockSpeedFactor` (1.19.3, 466–468; 1.19.4, 461–463) returns `1.0F` on a `SOUL_SPEED_BLOCKS` support block when Soul Speed is equipped; otherwise it falls through to `Entity.getBlockSpeedFactor` (1.19.3, 748–756; 1.19.4, 750–758). The vanilla tag provider includes `SOUL_SAND` and `SOUL_SOIL` in this tag on both sides, and `Blocks.SOUL_SAND` has speed factor `0.4F` on both. `Entity.move` (1.19.3, 657–659; 1.19.4, 659–661) multiplies current delta movement by the returned factor without a logical-side gate. Thus, after the same client-side equip swap while moving over existing soul sand, `Entity.move` applies a different horizontal factor to stored delta movement after the current move, changing subsequent horizontal movement. This route relies only on the local item-use mutation and direct movement predicate; `tryAddSoulSpeed` attribute-modifier writes are server-gated and are not part of this claim. As above, no intervening synchronized equipment update may overwrite the local slot before the movement call.
