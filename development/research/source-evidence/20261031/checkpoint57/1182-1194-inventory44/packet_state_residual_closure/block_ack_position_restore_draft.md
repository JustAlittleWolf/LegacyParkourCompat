# Block acknowledgement restores predicted player position

1.18.2, Mojmap: `net/minecraft/client/multiplayer/MultiPlayerGameMode.java`, `continueDestroyBlock` lines 219–226 sends the STOP action before invoking `destroyBlock`; `sendBlockAction` lines 452–456 captures `player.position()` in `unAckedActions`; `handleBlockBreakAck` lines 458–467 removes that action entry, compares current and acknowledged block states, and calls `Player.absMoveTo(saved.x, saved.y, saved.z)` only inside the outer correction gate and when the saved position exists, the level is the player's level, and `isColliding(pos, serverState)` is true. `net/minecraft/client/multiplayer/ClientPacketListener.java`, `handleBlockBreakAck` lines 2203–2205 passes the packet's position, state, action, and `allGood` flag to this method.

1.19, Mojmap: `net/minecraft/client/multiplayer/MultiPlayerGameMode.java`, `continueDestroyBlock` lines 238–244 wraps `destroyBlock` in `startPrediction`; `startPrediction` lines 256–261 opens and closes the handler around the action and sequenced packet, and `destroyBlock` lines 103–125 reaches `ClientLevel.setBlock`. `net/minecraft/client/multiplayer/ClientLevel.java`, `setBlock` lines 141–153 records the pre-prediction block state and current local-player position through `BlockStatePredictionHandler.retainKnownServerState`; `syncBlockState` lines 125–134 restores the recorded position using `Player.absMoveTo` when the current block state differs from the retained server state and the restored state collides with the player in that level. `net/minecraft/client/multiplayer/prediction/BlockStatePredictionHandler.java`, `retainKnownServerState` lines 17–25 retains the initial position (later predictions at the same position update only the sequence), while `endPredictionsUpTo` lines 37–48 closes entries with `sequence <= ack` and calls `syncBlockState`. `net/minecraft/client/multiplayer/ClientPacketListener.java`, `handleBlockChangedAck` lines 2237–2240 routes the acknowledged sequence to the level. Block update handlers call `setServerVerifiedBlockState` (1.19 `ClientPacketListener.java` lines 702–705; chunk-section updates lines 636–639); that updates the pending server state instead of replacing a predicted state when an entry exists.

Difference: the direct position restore remains a block-state-mismatch collision response, but its eligibility and target change. The 1.18.2 restore is additionally gated by the action result (`allGood` and action-kind expression in the outer condition) and returns to the player position captured when the matching action was sent. From 1.19, any closed pending prediction whose current block-state object differs from the retained server block state can reach the collision check, without an action-kind or `allGood` gate, and restores to the player position captured when the block was first predicted. The ACK sequence must close the prediction; state equality, a different level, or no collision suppresses the position write. This is a direct player position response to authoritative block-state input; this finding does not claim server-side production or historical world-state reconstruction.

Movement meaning: when a pending client block prediction is rejected or otherwise differs from the verified state and the verified block overlaps the local player, the client moves the player back to a stored position. The changed gate and capture point can therefore produce a different position correction for the same final verified block state. The exact introduction boundary inside 1.18.2→1.19 is unknown; 1.19.1, 1.19.2, 1.19.3 and 1.19.4 retain the 1.19 prediction-handler logic and the `syncBlockState` position-response form.
