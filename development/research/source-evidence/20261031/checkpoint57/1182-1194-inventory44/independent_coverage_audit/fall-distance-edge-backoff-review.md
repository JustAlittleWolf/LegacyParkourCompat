# Elytra slow-fall distance and player edge backoff

**Disposition: ACCEPT as a movement-relevant source difference; evidence confirmation only, not a new candidate.** This independently closes the 1.19.2→1.19.3 route for this audit.

In 1.19.2, `LivingEntity.travel`'s fall-flying branch assigns `fallDistance = 1.0F` whenever the current vertical delta is greater than `-0.5` (`net/minecraft/world/entity/LivingEntity.java:2107–2111`). In 1.19.3, the same branch calls `Entity.checkSlowFallDistance()` instead (`LivingEntity.java:2117–2119`); the extracted method only assigns `1.0F` when `fallDistance > 1.0F` (`net/minecraft/world/entity/Entity.java:2147–2151`). Thus an existing value below one is retained in 1.19.3, while 1.19.2 overwrites it.

The value is read by the local player's ground-support movement predicate: `Player.maybeBackOffFromEdge` requires `MoverType.SELF`/`PLAYER`, non-positive requested Y, shift-based `isStayingOnGroundSurface()`, and `isAboveGround()` (`1.19.3 Player.java:1050–1056`). `isAboveGround()` returns true off-ground when `fallDistance < maxUpStep` and the support probe is collision-free (`Player.java:1104–1107`). A fall-flying player is not excluded by `abilities.flying`. A reachable state with fall distance below `maxUpStep`, vertical delta above `-0.5`, shift held, and a non-positive self movement request therefore satisfies the route: 1.19.2 raises fall distance to `1.0F` before the support predicate, while 1.19.3 preserves the smaller value and can run the X/Z backoff probes. With a support lip where those probes are collision-free, the requested horizontal components can be trimmed in 0.05 increments (`Player.java:1060–1074`). This is a conditional collision response change, not a claim that every Elytra tick differs.
