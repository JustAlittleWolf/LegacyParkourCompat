## Revision 3 — packet helper equivalence and explicit candidate verdicts

This addendum supersedes the three-candidate list in Revision 2. Revision 2 is preserved at SHA-256 `DFC7EB87F82F70D37F2260DC734832D88D742F4C82407406E916544432823D78`.

### 1.18.2→1.19 codec introduction: REJECT as a movement difference

I compared the old helper, new codec, and their base lifecycle, not just the formula names:

- 1.18.2 `ClientboundMoveEntityPacket.updateEntityPosition` (source hash `D6DE63F34B54C42123EE4FCF5A99434A3A2F498C04B48912DBED3CF56BF74D35`, lines 31–36) computes each axis as `base` for a zero delta, otherwise `packetToEntity(entityToPacket(base) + delta)`. Its helpers are `entityToPacket(x) = Mth.lfloor(x * 4096.0)` and `packetToEntity(n) = n / 4096.0`.
- 1.19 `VecDeltaCodec.decode` (hash `d037d4f7d6e7c79c04cf31cfe0bb3cdb232de8e341a547f668990c0b4a7f66ae`, lines 10–26) uses the same per-axis zero-delta branch and the same `Mth.lfloor(base * 4096.0) + delta`, then `/ 4096.0`. The `ClientboundMoveEntityPacket` payload is unchanged between 1.19 and 1.19.2 (hash `91C6C950B7BC1048DEDA1FD4567BB173005F9740881184DADB2D55839A1F9EC0`).
- Base initialization and write order also match. In 1.18.2, `Entity.packetCoordinates` starts at `Vec3.ZERO`; `Entity.recreateFromPacket` writes the spawn coordinates before `moveTo`, `handleAddPlayer` writes the remote-player spawn coordinates before `absMoveTo`, and teleport writes the absolute packet coordinates before the controlled-instance gate. Relative move decodes from that base, writes the decoded base, then calls `lerpTo`. In 1.19, the codec starts at `Vec3.ZERO`; `recreateFromPacket` calls `syncPacketPositionCodec` before `moveTo`, `handleAddPlayer` syncs the same spawn coordinates before `absMoveTo`, teleport syncs the absolute packet coordinates before the same gate, and relative move decodes from the base, calls `setBase` with the decoded position, then calls `lerpTo`.

For the reachable LocalPlayer condition, the receive gate is eligible on both releases (per `route-audit.tsv`), but this helper substitution preserves the coordinate arithmetic and base state at each corresponding point. The apparent 1.18.2→1.19 codec-introduction candidate is therefore terminally no movement difference. This is a source semantic rejection of that candidate, not a statement about server packet producers.

### 1.19.2→1.19.3 `VecDeltaCodec` quantization: ACCEPT as an eligible source candidate

**Verdict: ACCEPT.** The changed encode/decode arithmetic is directly reachable for LocalPlayer when a clientbound relative move resolves its entity id to `minecraft.player`: `isControlledByLocalInstance()` remains false for a client-side LocalPlayer in both releases, and `handleMoveEntity` decodes the packet, stores the new base, and calls `lerpTo` (`ClientPacketListener.java:523–544` in 1.19.2; `:552–573` in 1.19.3). Exact codec hashes: 1.19.2 `d037d4f7d6e7c79c04cf31cfe0bb3cdb232de8e341a547f668990c0b4a7f66ae`; 1.19.3 `49fd5f98b636aa38e2448fd295ba47b5cf90fba763b139fa09d25b3b3e4997ba`.

Old decode rounds the base down with `lfloor(base * 4096.0)`; new decode rounds it with `Math.round(base * 4096.0)`. With a base of `0.75 / 4096` and a nonzero X relative delta of one quantization unit, old decode yields `1 / 4096` while new decode yields `2 / 4096`. This gives an exact reachable target-position difference of one unit (`1/4096`) before the same interpolation. The example establishes a source consequence; it does not assert a server producer or gameplay trajectory. This candidate is source-accepted for the reachable client response operation only.

### 1.19.3→1.19.4 control predicate: ACCEPT as an eligible source candidate

**Verdict: ACCEPT.** The paired `Entity.isControlledByLocalInstance` fallback changes from `!level.isClientSide` to `isEffectiveAi()` when no controlling passenger exists. The LocalPlayer override returns true in both releases. Therefore the method result for client LocalPlayer changes false→true, which changes two reachable movement routes:

- In 1.19.3, the negated gates in `ClientPacketListener.handleMoveEntity` and `handleTeleportEntity` admit the LocalPlayer and apply packet lerp/rotation/on-ground response. In 1.19.4 they filter those writes.
- `LocalPlayer.aiStep` calls `super.aiStep()` in both releases. `LivingEntity.aiStep` checks `isControlledByLocalInstance()` and, when true, clears `lerpSteps` and synchronizes the packet-position base to the current player position (`LivingEntity.java:2508–2516` in 1.19.3; `:2454–2462` in 1.19.4). This check is false for LocalPlayer in 1.19.3 and true in 1.19.4. It changes how pending position interpolation/base state is handled on the ordinary LocalPlayer tick. The `LivingEntity.travel` caller changes from `isEffectiveAi() || isControlledByLocalInstance()` to `isControlledByLocalInstance()`, but LocalPlayer's `isEffectiveAi()` is already true in 1.19.3 and its controlled predicate is true in 1.19.4, so that caller's outer gate stays true for this player.

Exact Entity hashes are 1.19.3 `8c35bdef3bf2de7b70ac76ad767ba2c194305e0dda2e03fdf6544983667adc32` and 1.19.4 `3667fee610cbc5f58012e3a8fb8d6c4849f649fb7fe5300595158112d8b4b58b`; paired LivingEntity hashes are `2b8befdc406176e01672175451dd480b14da0b52bfe11a982d368909c05e73db` and `c8d91af61f87aaa1666de79696d7cd9d4a8212d05f873bdaf28d7bb2926bf165`. The LocalPlayer `aiStep` super-call and `isEffectiveAi` override are verified in paired files; hashes are in the protocol `source-hashes.tsv` for LocalPlayer and the frozen manifest identity table for LivingEntity.

These are source-level eligible operation verdicts. They do not assert that a vanilla server emits a movement packet addressed to the local entity, and they do not claim trajectory/runtime parity.
