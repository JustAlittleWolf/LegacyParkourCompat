# Independent source-coverage audit: 1.20.4 → 1.20.5 (1.20.6 context)

## Verdict

**Source-coverage verdict: complete for this endpoint pair; no uncovered eligible movement terminal remains in the audited roster.** I independently validated the three-way source-path roster and retraced the LocalPlayer tick, direct player state responses, movement providers, collision/callback routes, and all supplied residual reports. The final item/equipment modifier terminal is now closed by an accepted, concrete vanilla-item-data witness. All eligible differences and same/no-delta routes in the audited scope have dispositions. This is a coverage result only: it does not itself freeze the pair, establish downstream trajectory parity, or decide implementation boundaries. Non-player, attack/damage and server-only paths remain excluded by project scope.

Five source-supported eligible differences have independent finding/review evidence in this lane: `Player.maybeBackOffFromEdge` collision-query footprint; `Entity.updateFluidOnEyes` sample height; the new grounded flight-enable call to `jumpFromGround`; sprint-jump horizontal impulse precision; and the `AttributeInstance` Set→UUID-map iteration change producing a one-float-ULP `Player.getSpeed()` difference for a valid pre-existing legacy item modifier list. Their existence does not establish a patch boundary inside 1.20.4→1.20.5. The `jumpFromGround` attribute/gate change is equivalent under ordinary 1.20.4-era vanilla inputs: the default jump strength and block factors give positive power, so the new suppression gate does not suppress that ordinary jump. Non-default jump-strength attribute behavior is a modern attribute input; its vanilla block-factor provider was checked separately.

No wiki, product implementation, product Git history, tests, builds, launches, source writes, or decompilation were used. Source-set and report inputs were read-only. Runtime overrides/datapacks are outside the assigned historical movement target; built-in tag defaults are resolved from the Java providers.

## Closed legacy item-data movement-speed terminal

The remaining item-data route is now closed by a bounded, independently accepted witness. The precise candidate input, source identities, NBT/datafix path, UUID-container iteration, and IEEE-754 arithmetic are in `legacy-item-order-witness/candidate.md` (SHA-256 `757FBA7173822A3ECC903A1755D17130F618DFF4E514BA8A69A7598931D61A57`). Independent review accepted that exact candidate hash at `legacy-item-order-review/review.md` (SHA-256 `924B79822333348FB0D884318FA53A9D4CEA9CA74B2C7E0A6D9A770F5D5ACC6F`).

The input is an otherwise ordinary boots stack with two valid pre-existing `AttributeModifiers` entries targeting the registered `minecraft:generic.movement_speed` attribute, both `MULTIPLY_TOTAL` and restricted to `feet`. The 1.20.4 stack path parses and applies those entries to the equipped Player; the 1.20.5 schema-2523 rename preserves the canonical namespaced key, and schema-3818.5 componentization preserves both entries before `LivingEntity.collectEquipmentChanges` applies them through `ItemStack.forEachModifier`. With candidate UUIDs A/B, old `HashSet` iteration is A→B and artifact-pinned fastutil 8.5.12 map iteration is B→A. Starting from Player's widened `0.1F` base, source-order results cast to `Player.getSpeed()` float bits `0x3dff5e2f` vs `0x3dff5e2e`. The exact custom amounts are data values on the vanilla item modifier feature, not a modded item, modern-only attribute, runtime tag override, server movement path, or damage result; under the assigned historical player-movement scope this is eligible input.

This closes the **applicability and source-value** terminal with a concrete changed movement-speed result. The witness does not measure a downstream displacement or establish a trajectory result. The ordinary vanilla effect/enchantment enumeration above remains a separate no-delta boundary; it does not subsume the item-data witness.

### Independent ordinary-vanilla AttributeInstance order check

I independently evaluated the exact 1.20.4 and 1.20.5 operation sequence from `AttributeInstance.calculateValue`, using every permutation as an upper bound and then the actual paired UUID order for sprint, Speed and Slowness. Inputs were base speed `0.1`, sprint off/on, each Speed and Slowness amplifier 0–255, Soul Speed levels 0–3, and powder-snow frozen ticks 0–140. Float-valued Soul Speed/powder modifiers were rounded as Java `float` before widening; the final sanitized attribute value was cast to `float`, matching `Player.getSpeed`.

- A conservative all-permutations pass over 564 distinct vanilla additive bases and both sprint states evaluated 295,698,432 orderings. It found one float mismatch only for an ordering that puts Speed before Slowness with sprint off (Speed amp 52, Slowness amp 3, full powder freeze). That order is not produced by the built-in modifier IDs: with sprint off, both versions order Slowness before Speed.
- A pass over the paired actual orders evaluated 73,924,608 cases: with sprint on, 1.20.4 is Slowness → sprint → Speed and 1.20.5 is sprint → Slowness → Speed; with sprint off, both are Slowness → Speed. There were zero differences in the Player speed float. The largest double difference before the float cast was `1.7763568394002505e-15`, and its float outputs were equal.

This closes the AttributeInstance ordering candidate for the enumerated built-in vanilla modifiers and their vanilla effects/enchantments. The separate valid legacy item-data witness above demonstrates an eligible difference for a non-default modifier set. This was an arithmetic enumeration from source constants, not a game run or a test task.

The movement-speed/equipment closure also verifies that Speed, Slowness, sprint, Soul Speed, Powder Snow and Swift Sneak retain their ordinary vanilla amounts/gates. Its raw input-reading and unrelated item callbacks remain outside that closure; they provide no additional changed Player movement path in the examined pair.

The player-targetable direct packet and callback routes are closed for the reviewed setters and gates. `ClientPacketListener` position correction/reset, velocity correction, remote-only ground setters, abilities, equipment, effects, attributes and respawn paths retain their paired response; `handlePlayerCombatEnter` is attack/damage knockback and excluded. The supplied callback cross-check verifies the unchanged movement operations in Honey, bubble-column, sweet-berry, bed, slime, block and piston callbacks. Generic collision, entity-contact push (including the new five-override residual), shulker motion and block-entity residuals have separate dispositions.
