# Water eye-fluid sampling height

1.20.4, Mojmap: `net/minecraft/world/entity/Entity.java`, `Entity.updateFluidOnEyes`, lines 1211-1223.
1.20.5, Mojmap: `net/minecraft/world/entity/Entity.java`, `Entity.updateFluidOnEyes`, lines 1227-1239.
Difference: The sample y changes from `getEyeY() - 0.11111111F` to `getEyeY()`. The method still selects the fluid at the block containing the sample and adds its tags only when the fluid surface is strictly above the sample.
Movement meaning: Hold the same eyeY/pose/position, prior `fluidOnEyes` tags, boat state and boat-gate result, current fluid state and height, with both sample points in the same block. For water surface `surfaceY` in `eyeY - 0.11111111F < surfaceY <= eyeY`, 1.20.4's sample passes its strict-above check while 1.20.5's does not; 1.20.4 records water over the eyes and 1.20.5 does not. The reachable local-player order is `LocalPlayer.tick` -> `Player.tick` -> virtual `LocalPlayer.updateIsUnderwater` -> `Player.updateIsUnderwater`, which reads the prior `fluidOnEyes` tags into `wasUnderwater` before `super.tick`; then `LivingEntity.tick` -> `Entity.tick` -> `Entity.baseTick`, which refreshes water contact, calls `updateFluidOnEyes` (clears and writes the newly sampled tags), then `updateSwimming`; `LivingEntity.tick` then calls virtual `LocalPlayer.aiStep` -> `Player.aiStep` -> `LivingEntity.aiStep`, which calls virtual `Player.travel`. The pre-super update reads tags from the preceding base tick, so the changed sample is consumed by `Player.updateIsUnderwater` on the following player tick. That tick's `updateSwimming`, `LocalPlayer.aiStep` sprint gates, and `Player.travel` swimming branch use the resulting underwater/swimming state; for an eligible sprinting player in water, this can change swimming entry and whether the swimming vertical-steering branch runs. 1.20.6 retains the 1.20.5 sample at `getEyeY()` (`Entity.updateFluidOnEyes`, lines 1227-1239), so it adds no further boundary within the inspected later context.
