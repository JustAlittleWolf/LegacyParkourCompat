## Findings and no-difference coverage

1. **Local crouch state is recomputed and cached in 1.16.1.** In 1.15.2 `LocalPlayer.isCrouching()` (lines 596–600) derives its answer on every call from `!abilities.flying`, `!isSwimming()`, `canEnterPose(CROUCHING)`, then `isShiftKeyDown()` or inability to fit standing while awake. In 1.16.1 `LocalPlayer.aiStep()` (652–end) assigns `crouching` before `input.tick(...)` (lines 662–666), using the same flying/swimming and crouch-fit guards plus `(isShiftKeyDown() || !isSleeping() && !canEnterPose(STANDING))`; `isCrouching()` now simply returns that field (625–627). This changes a live predicate into a per-aiStep snapshot and changes when downstream input/movement reads observe it. Reachability is direct through `LocalPlayer.aiStep()` and `isMovingSlowly()`. Candidate movement delta; raw input sampling/tick semantics and precise collision-fit results remain dependencies.

2. **Sneak cancels a pending double-tap sprint trigger in 1.16.1.** The sprint counters and eligibility branches in `LocalPlayer.aiStep()` otherwise retain the same visible predicates and ordering: impulse threshold (`forwardImpulse >= 0.8`, or `hasForwardImpulse()` underwater), ground/underwater and food-or-mayfly test for double-tap, optional sprint-key path, and stop conditions for missing forward impulse/food, collision, water or swimming. After `checkInBlock` and before computing `bl5` / evaluating auto-sprint, 1.16.1 adds `if (bl2) sprintTriggerTime = 0;` (`bl2` captured from `input.shiftKeyDown` at method entry); 1.15.2 has no corresponding write. Thus pressing sneak clears the pending seven-tick double-tap window, even though `!bl2` already blocks the auto-start branch on that tick. Candidate retention/eligibility delta. `LocalPlayer.setSprinting` still delegates and resets `sprintTime`; the shared threshold helper and visible sprint start/stop expressions otherwise match.

3. **Elytra-start climb exclusion follows a broader climbable predicate.** The local jump-to-Elytra gate is otherwise retained (`input.jumping`, not toggled flight, not previously jumping, not flying, not passenger, chest Elytra enabled, then `tryToStartFallFlying()` and send START_FALL_FLYING). Its final exclusion changes from `!onLadder()` in 1.15.2 (`LocalPlayer.aiStep`, around line 705) to `!onClimbable()` in 1.16.1 (around line 746). `LivingEntity.onLadder()` directly recognizes ladder, vine, scaffolding and the usable-trapdoor case (1.15.2 lines 1226–1238); `onClimbable()` uses `BlockTags.CLIMBABLE` plus the same trapdoor test and updates `lastClimbablePos` (1.16.1 lines 1361–1378). The new tag includes newly introduced vine blocks according to the pre-existing source inventory, but effective tag membership remains an external/resource input. Candidate gate change with tag-data applicability open.

4. **Levitation now prevents retaining fall-flight state.** `LivingEntity.updateFallFlying()` keeps the same shared-flag, airborne, non-passenger and enabled chest-Elytra checks, but 1.16.1 adds `!hasEffect(MobEffects.LEVITATION)` to the outer gate (1.15.2 line 2301 onward; 1.16.1 line 2476 onward). On a local player whose synchronized state has the fall-flying bit set while levitation is active, the local tick clears its local `bl` decision; the actual shared-flag write remains server-only in both versions. This changes the following travel branch only when the flag/effect state and local tick gates permit it. Candidate movement-state gate; effect/flag provenance is external packet/equipment state.

5. **Auto-jump geometry is unchanged in this slice; its entity query argument changes.** `LocalPlayer.canAutoJump()` retains its visible conditions (`autoJumpEnabled`, timer, on-ground, not staying on ground surface, not passenger, moving, block jump factor at least 1). `updateAutoJump()` retains the same distance fallback, normalization, forward dot threshold, headroom/step-height scan, float thresholds and timer write. At the collision query, 1.15.2 passes `Collections.emptySet()` while 1.16.1 passes `entity -> true` (`LocalPlayer.java` 862–974 and 899–1016 respectively). This call contract change is an unresolved candidate: the query/provider semantics and emitted collision shapes are explicitly outside this slice and already belong to the separate collision-provider work. Do not infer auto-jump trajectory equivalence from unchanged surrounding math.

6. **Local pose choice and resize math are otherwise unchanged; pose-fit gate differs.** `Player.updatePlayerPose()` is called in the same terminal part of `Player.tick()` and has the same pose priority and fallback order in both endpoints (fall-flying, sleeping, swimming, spin attack, shift crouch, standing; then target fit / crouch fit / swimming fallback). `Player.getDimensions(Pose)` returns the same pose map/default in both. `Entity.refreshDimensions()` uses the same old/new width comparison, box construction, eye-height update and server-only widening move. However `Entity.canEnterPose(Pose)` changes from `level.noCollision(this, getBoundingBoxForPose(pose))` (1.15.2 line 1605) to `level.noCollision(this, getBoundingBoxForPose(pose).deflate(1.0E-7))` (1.16.1 line 1620); the exact fit boundary can therefore differ. Collision/noCollision provider behavior, world-border behavior and shape context remain open dependencies; this finding does not duplicate or settle those lanes. `Entity.setPose` also changes visibility (`protected` → `public`), with unchanged body; no direct movement difference follows from the visibility change alone.

7. **Ground-jump response and ride/flight toggles:** The `LocalPlayer.aiStep()` ability-flight toggle and its mayfly / always-flying / jump-edge / swim gates are textually unchanged. `jumpFromGround()` retains the same operation sequence and sprint impulse addition at both endpoints. The containing `LivingEntity.aiStep()` jump selector is restructured in 1.16.1 around fluid eligibility and per-fluid heights/thresholds; those fluid-jump calculations are outside this assigned local-predicate slice and are not re-audited here. `Player.isAffectedByFluids()` is newly defined in 1.16.1 as `!abilities.flying`; consequently the local water-descent branch gains this gate (`isInWater && input.shiftKeyDown && isAffectedByFluids()` versus the older two-condition branch). Treat the actual fluid response as the separate fluid lane.

## Remaining dependencies and limits

- Input plumbing and raw shift/jump/forward state production (`Input`/`KeyboardInput` and options) are not examined; they determine the `bl`, `bl2`, current `input` fields, and `input.tick` timing.
- Pose-fit and auto-jump results require the separately assigned `Level.noCollision`, `EntityGetter`/collision-stream, collision-shape provider and query-context closure. The auto-jump predicate change is reported, not semantically closed here.
- Effective climbable tag contents and synchronized/custom tag tables are data inputs. Elytra slot/enabled state, game mode/abilities, levitation/effect state and fall-flight shared-flag state depend on equipment/effect/ability synchronization, not inspected in this bounded slice.
- Fluid heights, thresholds, water descent, fluid jump selection/current, and player fluid-response semantics remain for the fluid lane.
- The result is one source endpoint pair only; no exact intermediate cutover within 1.15.2–1.16.1 is established.
