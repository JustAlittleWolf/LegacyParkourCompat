# Independent audit: persisted login position response, 1.19 → 1.19.2 (Mojmap)

## Verdict

The source trace confirms a server-side persisted-position producer change and an unchanged direct client response. For finite saved NBT x/z with magnitude greater than 30,000,512, the login packet's absolute x/z payload may differ: 1.19 sends the saved coordinate, while 1.19.2 sends the ±30,000,512 loaded value. Both client handlers then clamp operative LocalPlayer x/z to ±30,000,000 through `Entity.absMoveTo` and zero x/y/z velocity for the empty-relative-flag login packet. Thus the final position and velocity after this handler are equal for corresponding server-side outcomes, though raw packet input and `xOld`/`zOld` can differ. This is not a client movement-operation difference; no pair freeze or runtime claim follows.

## Independently retraced path

1. `PlayerList.placeNewPlayer` calls `this.load(serverPlayer)` before establishing its connection and sends the saved server-player position with `teleport(x,y,z,yRot,xRot)` after the login packet (`1.19` `PlayerList.java:133–145,211`; `1.19.2` `:136–148,214`). The single-player loaded-player-tag path calls `ServerPlayer.load`; the ordinary path calls `PlayerDataStorage.load`. `PlayerDataStorage.load` reads the UUID `.dat`, applies the player data fixer, and calls `player.load(tag)` (`PlayerList.java:323–334` / `326–337`; `PlayerDataStorage.java:40–57` in both). No horizontal position clamp is added in those callers.
2. `Entity.load` reads `Pos` and `Motion`, replaces motion components whose absolute value exceeds 10 with zero, then assigns position and later copies the position into old-position fields. In 1.19 it passes NBT x/z directly to `setPosRaw` and clamps only y to ±2.0E7 (`Entity.java:1520–1532`). In 1.19.2 it clamps x/z to ±3.0000512E7 and y to ±2.0E7 before `setPosRaw` (`:1515–1532`). For `|Pos.x|` or `|Pos.z|` > 30,000,512, these two server-side values differ; within that new bound they remain equal. This is conditional on finite persisted coordinates and does not establish that ordinary gameplay creates such NBT.
3. `PlayerList.placeNewPlayer` invokes the five-argument teleport overload. That overload delegates with an empty relative-argument set and `dismountVehicle=false`. The full overload stores the expected teleport position and ID, calls server `player.absMoveTo(...)`, then builds the packet from its original method arguments (`1.19` `ServerGamePacketListenerImpl.java:951–975`; `1.19.2` `:986–1010`). The server `absMoveTo` itself clamps x/z to ±3.0E7, but does not rewrite the overload's local arguments. The packet can therefore preserve the pre-30.0M input (or the 1.19.2 NBT-clamped 30.000512M input).
4. The paired `ClientboundPlayerPositionPacket` stores and serializes three doubles, two floats, relative flags, teleport ID, and dismount flag in the same order. Its complete Java file hash is identical in both releases. On this login route, the relative set is empty and dismount is false.
5. The paired `ClientPacketListener.handleMovePlayer` method first writes the packet's absolute axes to `xOld/yOld/zOld` and briefly to `setPosRaw`; absolute axes set their velocity components to 0. It then calls `player.absMoveTo(...)`, sends the teleport acknowledgement, and sends a position/rotation response using getters (`1.19` `ClientPacketListener.java:549–614`; `1.19.2` `:563–628`). No world movement callback occurs between the temporary raw placement and `absMoveTo` in this handler.
6. Both `Entity.absMoveTo(x,y,z)` bodies clamp x and z to ±3.0E7, set `xo/yo/zo` to those clamped coordinates and call `setPos` (`1.19` `Entity.java:1207–1214`; `1.19.2` `:1202–1209`). Neither clamps y. Given the identical login packet flags and handler, final client x/z, y, rotation and delta movement are the same when the server-side payloads differ only by the NBT x/z clamp.

## State boundary and scope

The packet's raw x/z values also remain in LocalPlayer `xOld/zOld` because the response handler writes these fields before calling `absMoveTo`, and `absMoveTo` does not rewrite them. The immediate operative position `getX/getZ`, `xo/zo`, and horizontal delta movement are clamped/reset as above. `PowderSnowBlock.entityInside` reads `xOld/zOld` on the client only to choose snowflake particle emission; `SweetBerryBushBlock` gates its displacement/damage branch on `!level.isClientSide`. These are presentation/server-side consequences, not a local position or velocity delta. I do not assert equality of every transient/render field.

The changed `Entity.load`/NBT state and login packet construction are server-side producers. The client direct response was traced because it applies the position to LocalPlayer. No new client-side historical movement hook is supported by this evidence. Server acknowledgement/correction logic, invalid or modded NBT production, vehicle state, and runtime resource inputs remain outside this bounded review.
