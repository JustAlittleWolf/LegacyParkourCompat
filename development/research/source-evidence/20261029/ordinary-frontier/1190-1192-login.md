# Persisted-player login position: 1.19 → 1.19.2 (Mojmap)

## Result

The candidate reaches the changed `Entity.load` operation on the **server-side persisted ServerPlayer** login path. A saved `Pos` outside the new horizontal bound can change the absolute `ClientboundPlayerPositionPacket` coordinates sent during login. However, both clients apply the same stricter ±30,000,000 horizontal clamp in `Entity.absMoveTo` while handling that packet. The resulting LocalPlayer x/z and velocity are the same after the direct response. No local-player movement finding is established from this clamp.

Separate the observations:

- **Changed producer input:** 1.19.2 clamps loaded NBT x/z to ±30,000,512 before login; 1.19 leaves those coordinates unclamped. `PlayerList` later passes the loaded ServerPlayer coordinates to its absolute teleport sender.
- **Unchanged direct response:** the packet still has no relative position flags for this login teleport. Both clients apply the packet through the same `ClientPacketListener.handleMovePlayer`, then `Entity.absMoveTo` clamps resulting x/z to ±30,000,000. For equivalent received packets, client position response semantics are identical. Even when the packet payload differs because the server-side NBT producer clamps, both sides finish the handler at the same horizontal coordinate cap.
- **Scope boundary:** `Entity.load`/`PlayerList`/server packet construction are server-side state production. The client response remains an in-scope direct response and was traced explicitly. Server teleport acknowledgement validation or any later server correction is server behavior and is not evidence of historical client movement. The raw pre-clamp packet value remains in `xOld` and is briefly passed through `setPosRaw`; observed client uses of `xOld` here are render/particle interpolation, outside movement scope.

## Exact source path and order

### Persistence and load

1. `PlayerDataStorage.save(Player)` (`1.19` and `1.19.2`, `PlayerDataStorage.java:26–36`) calls `Player.saveWithoutId(new CompoundTag())`, writes compressed NBT to a temporary file and replaces the UUID `.dat` file. It does not validate or clamp `Pos` itself.
2. `Entity.saveWithoutId` (`Entity.java:1437–1444` in 1.19; line offset by release) writes `Pos` as a three-double NBT list from the entity's current x/y/z (when riding, x/z are taken from its vehicle and y from the entity). Thus the serialization path preserves the values held by the entity; it adds no horizontal bound.
3. `PlayerList.placeNewPlayer` (`PlayerList.java:133–145`) first calls `this.load(serverPlayer)`, then chooses the saved dimension, then sets the player level. In `PlayerList.load(ServerPlayer)` (`:323–334`), the single-player loaded-player tag path calls `serverPlayer.load(tag)` directly; the ordinary player-data path calls `PlayerDataStorage.load(serverPlayer)`. `PlayerDataStorage.load` (`PlayerDataStorage.java:40–57`) reads the `.dat`, applies the PLAYER data fixer, then calls `player.load(fixedTag)`. Neither path adds a position bound before `Entity.load`.
4. `Entity.load` reads `Pos`, reads and applies each Motion component (components with absolute value greater than 10 become 0), then writes position, then restores rotation and old-position state, and later calls subclass `readAdditionalSaveData`. In 1.19 (`Entity.java:1520–1532`), x and z are raw `Pos[0]` and `Pos[2]`; y is clamped to `[-2.0E7, 2.0E7]`. In 1.19.2 (`:1515–1532`), after the same motion operation it declares `3.0000512E7` and calls `setPosRaw(clamp(Pos[0], -3.0000512E7, 3.0000512E7), clamp(Pos[1], -2.0E7, 2.0E7), clamp(Pos[2], -3.0000512E7, 3.0000512E7))`. Rotations and `setOldPosAndRot` follow in the same order. The later default `repositionEntityAfterLoad()` calls `reapplyPosition`; it does not undo the new clamp. The player subclass's loaded fields do not rewrite x/z.

There is no NBT field or loader-side rejection that prevents a serialized finite x/z outside ±30,000,512 from reaching this operation. This establishes the conditional source path for such persisted data; it does not establish that ordinary valid vanilla gameplay writes such coordinates. Non-finite coordinates are rejected by the existing entity load validity check after the initial position write.

### Login packet producer (server side)

5. `PlayerList.placeNewPlayer` (`1.19` `PlayerList.java:211`, same login operation in 1.19.2 with chat-only call-site changes) sends `connection.teleport(serverPlayer.getX(), getY(), getZ(), getYRot(), getXRot())` after restoring saved player state. This is the ordinary absolute position update after the login packet has established the session.
6. The five-argument `ServerGamePacketListenerImpl.teleport` delegates with `Collections.emptySet()` and `dismountVehicle=false` (`1.19` `ServerGamePacketListenerImpl.java:951–974`; corresponding method in 1.19.2). The full overload computes packet position/rotation by subtracting the current position only for arguments marked relative; for this empty set it sends the supplied x/y/z and yRot/xRot unchanged, increments/stores the teleport id and expected position, calls server-player `absMoveTo`, then creates `ClientboundPlayerPositionPacket` from the original supplied target values. Server-side `Entity.absMoveTo` itself clamps x/z to ±3.0E7, but the packet is built from the original teleport parameters, not the now-clamped server player's getter values. The NBT clamp therefore can change the packet's absolute x/z input for values beyond ±30,000,512.
7. `ClientboundPlayerPositionPacket` has fields `(double x,y,z; float yRot,xRot; relativeArguments; id; dismountVehicle)`. Its writer serializes three doubles, two floats, one packed relative-argument byte, a VarInt id and the dismount boolean (`ClientboundPlayerPositionPacket.java:8–55`). The packet class is byte-identical between releases. On this login call the flags are empty, id is the teleport acknowledgement id, and dismount is false.

### Client creation and direct position response

8. `ClientPacketListener.handleLogin` constructs/sets up the local player and calls `LocalPlayer.resetPos` (`1.19` `ClientPacketListener.java:332–395`; 1.19.2 `:346–409`). It does not deserialize player NBT. The subsequent position packet targets `minecraft.player`, which is the LocalPlayer.
9. `ClientPacketListener.handleMovePlayer` (`1.19` `:549–614`; 1.19.2 `:563–628`) is unchanged in behavior. It handles the optional dismount, checks X/Y/Z relative flags, uses exact packet coordinates for absolute axes (and zeroes that axis's velocity), writes `xOld/yOld/zOld` and `setPosRaw`, sets `xo/yo/zo`, sets resulting velocity, resolves rotation relative flags, then calls `player.absMoveTo(...)`, sends teleport acknowledgement and echoes the final position/rotation in `ServerboundMovePlayerPacket.PosRot` with on-ground false.
10. `Entity.absMoveTo(x,y,z)` clamps x and z to `[-3.0E7,3.0E7]`, leaves y unchanged, writes `xo/yo/zo`, then calls `setPos` (`1.19` `Entity.java:1207–1214`; 1.19.2 `:1202–1209`). The method behavior is the same in both releases. `absMoveTo(x,y,z,yRot,xRot)` calls this method before applying rotation/pitch clamps, also unchanged.

For the empty-flag login packet, both client handlers set `xOld/yOld/zOld` to the incoming absolute target and briefly place the raw target with `setPosRaw`; no world callback or movement computation occurs between that write and `absMoveTo`. The position that survives the handler is therefore `(clamp(packet.x, -30,000,000, 30,000,000), packet.y, clamp(packet.z, -30,000,000, 30,000,000))`, with zero x/y/z velocity and packet rotation. `Entity.load`'s new ±30,000,512 bound is wider than the client response's ±30,000,000 cap. For finite saved coordinates in every range, the final LocalPlayer x/z is ±30,000,000 or the saved coordinate if its magnitude is ≤30,000,000 on both client versions. The y path is also the same because `Entity.load` uses the same ±20,000,000 y clamp on both sides and `absMoveTo` does not further clamp y.

### Movement-scope disposition

- For persisted x/z with magnitude ≤30,000,512, `Entity.load` produces the same x/z on both server versions; above that bound, the server-side loaded coordinate and absolute packet payload differ.
- For any packet x/z, the client response's final player coordinate is capped at ±30,000,000 by the unchanged `absMoveTo`. Thus the changed source does not change LocalPlayer's final login position or velocity, despite different raw packet values for the conditional out-of-bound case.
- The temporary raw coordinate is followed immediately by the clamp; no movement callback runs between those operations. `xOld` can retain the packet target and influence interpolation/render/particle behavior, but those are outside the requested movement scope. `PowderSnowBlock.entityInside` uses `xOld` on the client only to decide whether to emit a snowflake particle; `SweetBerryBushBlock`'s displacement damage check is guarded to server only. Neither changes client-player position or velocity here.
- A saved RootVehicle tree can also load nested entities through `EntityType.loadEntityRecursive`, whose `loadStaticEntity` uses the same generic `Entity.load`; `PlayerList` attempts to reattach the saved vehicle after the initial login teleport. That producer side may affect vehicle/non-player state and is excluded by project scope. It does not change the direct LocalPlayer packet handler/cap analyzed above.
- `ClientPacketListener.handleRespawn` creates a replacement LocalPlayer and resets it, then the server respawn path sends a position packet through the same handler. The respawn position is selected from a spawn point/current ServerPlayer transfer; it is not the persisted-login `PlayerDataStorage` load in this candidate.

## Audit reconciliation and limits

This independent canonical traversal was completed before reading the sibling full audit, as assigned. The audit correctly identified the `PlayerList → Entity.load → login teleport → LocalPlayer` chain and correctly kept the pair unfrozen. Its remaining claim that an outside-limit NBT coordinate may change the *position received by the client* is true of the raw absolute packet values. The chain closure here adds the omitted final client operation: `Entity.absMoveTo` has the tighter ±30,000,000 x/z cap in both versions. Therefore the changed NBT producer does not create a final LocalPlayer position/velocity difference. The packet handler still deserves inclusion in an audit because the raw input and `xOld` differ; the latter's observed client consumers are presentation-only.

This conclusion is source-only and conditional on arbitrary serialized coordinates. It does not prove how often malformed/out-of-range player data occurs, verify online-server reconciliation, establish behavior for modded loaders, inspect resource data, or close the separate removed-entity `aiStep` question. No pair freeze is claimed. No runtime scenario, test, build or gameplay/server launch was performed.
