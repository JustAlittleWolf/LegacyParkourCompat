## Ordered ordinary local-player movement path

The ordinary locally controlled path remains `LocalPlayer.tick()` → `Player.tick()` → `LivingEntity.tick()` → virtual `LocalPlayer.aiStep()` → `Player.aiStep()` / `LivingEntity.aiStep()` → virtual `Player.travel()` → `LivingEntity.travel()` → `Entity.move()` and post-move callbacks → packet sender in `LocalPlayer.tick()`. Movement state is read from local input and current player/world state; client-received state writers are outside this bounded inventory and owned by a sibling closure.

1. **Input and local pre-travel.** `LocalPlayer.aiStep()` snapshots jump/shift, updates crouching, ticks input, applies item-use impulse damping, client auto-jump and space nudges, evaluates sprint entry/exit, flight toggle, elytra start, water descent, vertical flight input, and riding-jump input. In 1.18.2 (`LocalPlayer.java:642–803`) and 1.19 (`:725–887`), the gates/order are the same after local-variable renaming, except for the sneak-speed factor below. Key impulses remain `-1/0/1`; diagonal normalization is downstream and unchanged in this bounded diff.
2. **Living jump and travel selection.** `LivingEntity.aiStep()` handles jump selection, jump impulse and invokes travel from `xxa/yya/zza`. Exact changed-path review found no ordinary jump/travel arithmetic edit relevant to this call chain besides support-state compatibility calls listed below. The 1.17.1→1.18.2 source ledger covered adjacent travel branches and confirms the 1.18.2 baseline; this task did not re-audit its already inspected method bodies.
3. **Travel and collision entry.** `LivingEntity.travel(Vec3)` selects water, lava, fall-flying, or ordinary ground/air motion; it consumes input, movement-speed attribute, block friction, fluid predicates, jump/fall effects, and invokes `Entity.move`. Exact movement numerical comparison of every branch was not repeated here; their source hashes and the adjacent inventory are retained, while any additional provider semantics remain open. Collision provider internals are excluded and owned by the collision pool.
4. **Contact modifiers and movement attributes.** `LivingEntity.onChangedBlock`, `tryAddSoulSpeed`, `tryAddFrost`, `getBlockSpeedFactor`, and the `Entity.getOnPos*` helpers feed Soul Speed and freezing slowdown. In 1.18.2, Soul Speed and frost contact gates call `getBlockStateOn()`, which uses `getOnPos()` with `floor(y - 0.2F)`. In 1.19 these movement modifier gates call `getBlockStateOnLegacy()` / `getOnPosLegacy()`, explicitly delegating to the same 0.2F offset/fence-wall-gate fallback. The new public `getOnPos()` instead uses `1.0E-5F`, but that value is not used by these local-player movement modifier paths. Therefore the observed call-site rewrite preserves the old contact selection for these modifiers; the new generic query is a changed dependency for other consumers and is not treated as a movement delta here.
5. **Post-travel / tick close.** Entity movement updates position/velocity/box and collision flags, then local/player tick bookkeeping and `LocalPlayer.sendPosition()` uses current position, rotation, on-ground, sprint and shift state. Local-player movement sender and packet classes are unchanged according to the reused 1.19→1.19.2 ledger. Exact direct-response handlers are excluded from this ordinary-input slice.

## Changed ordinary movement slices

### Sneaking input scale: new Swift Sneak-only branch

- 1.18.2 `LocalPlayer.aiStep()` calls `input.tick(this.isMovingSlowly())` (`:656`). `KeyboardInput.tick(boolean)` (`KeyboardInput.java:22–34`) reads key states, maps them to `-1/0/1`, then when slow multiplies forward/left impulses by literal `0.3F`.
- 1.19 `LocalPlayer.aiStep()` computes `Mth.clamp(0.3F + EnchantmentHelper.getSneakingSpeedBonus(this), 0.0F, 1.0F)` and passes it to `input.tick(isMovingSlowly(), factor)` (`LocalPlayer.java:739–740`). `KeyboardInput.tick(boolean,float)` (`:21–34`) preserves the same key mapping and multiplies by that factor only under the same slow-input boolean.
- 1.19 `EnchantmentHelper.getSneakingSpeedBonus` returns `getEnchantmentLevel(Enchantments.SWIFT_SNEAK, entity) * 0.15F` (`EnchantmentHelper.java:193–195`); `Enchantments.SWIFT_SNEAK` is a new legs-slot enchantment (`Enchantments.java:30`). `LocalPlayer.isMovingSlowly()` remains `isCrouching() || isVisuallyCrawling()` (`LocalPlayer.java:684–686`).
- Consequence is conditional: for the same state with no Swift Sneak level, `factor` is exactly `0.3F`, matching 1.18.2. With a positive Swift Sneak level while crouching/crawling, the locally sampled horizontal input is multiplied by a larger clamped factor. Swift Sneak is introduced in 1.19, so this is a post-profile feature gate rather than a demonstrated reachable 1.18.2 historical movement difference. The method also changes `Input` superclass signature while the base tick method is empty; input-device implementations other than `KeyboardInput` are not assessed. Treat the feature's equipment/application and resource registration as unexamined dependencies, not as an old-version patch finding.

### Legacy support-position helpers: audited call-path preservation

- Old `Entity.getOnPos()` floors X/Z and `y - 0.2F`, then falls back one block for fences, walls, or fence gates when the candidate is air (`1.18.2 Entity.java:704–718`). Old `getBlockStateOn()` reads that position.
- 1.19 splits this into `getOnPosLegacy()` → `getOnPos(0.2F)` and `getOnPos()` → `getOnPos(1.0E-5F)` (`Entity.java:710–731`); `getBlockStateOnLegacy()` reads the legacy position (`:1133–1139`). The shared helper retains floor and fallback logic.
- 1.19 `LivingEntity.tryAddSoulSpeed`, `tryAddFrost`, and `onChangedBlock` switch from `getBlockStateOn()` to `getBlockStateOnLegacy()`. Thus for these movement modifiers, exact offset and candidate fallback are preserved. `Entity.move()` likewise uses `getOnPosLegacy()` for its existing movement-emission contact position. The newer epsilon `getOnPos()` / `getBlockStateOn()` can change other consumers, but their movement reachability and consequences are not closed by this task.
- Dependency boundary: this concludes only the ordinary-source call sites and position calculation. Collision-provider, shape, loaded-chunk and block-state semantics remain with the collision pool; no claim is made about broader contact-state equivalence.

### Other changed core-source methods

- `Entity.move` changes movement-emission bookkeeping for climbable/powder-snow blocks to compute a boolean local; walking-distance math remains the same. The new branch additionally affects STEP game-event emission on ground/zero-y/powder-snow/climbable contexts. Game-event/redstone consequences and non-player consumers were not analyzed; no changed player velocity/position write was found in this hunk.
- `LivingEntity.onChangedBlock` and modifiers above are the only changed core ordinary movement call sites found in the `LivingEntity.java` diff. The numeric Soul Speed modifier, frost modifier, movement attribute read in travel, and block-speed-factor formula are unchanged. Block speed factor still multiplies horizontal velocity by the factor after `Entity.move` in the same place.
- `Vec3.java` adds codec support and `relative(Direction,double)`; no edited ordinary travel caller was found. `BlockPos.java` only changes random-source parameter types for random enumeration. `FluidState`, `WaterFluid`, and `LavaFluid` changes in this diff are `Random`→`RandomSource` signatures in animation/random ticking, not movement-height or flow computations. `AbstractClientPlayer`, `Player`, `MobEffect`, `RemotePlayer`, and other modified files in the complete TSV need not be assumed irrelevant from path hashes alone; this bounded review only traced ordinary local-player movement references and reports no direct input/travel arithmetic delta from them.
