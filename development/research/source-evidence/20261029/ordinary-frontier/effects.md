## Result

No new movement difference was found in the reviewed effects, attribute, equipment, pose, or dimension consumers. Files often have changed source hashes because of decompiler-local renaming or unrelated class edits; the relevant paired methods below retain their operations, gates, and order. This is only a bounded no-difference result and does not close the pair.

### Received effect state and movement consumers

- `ClientPacketListener.handleUpdateMobEffect` (1.17.1 around line 1387; 1.18.2 around line 1329) resolves the entity and effect ID, constructs `MobEffectInstance` from the same duration/amplifier/ambient/visible/icon fields, sets the same no-counter flag, then calls `LivingEntity.forceAddEffect(instance, null)`. The removal handler resolves the entity and calls `removeEffectNoUpdate` with the packet effect in both versions (around 1562 / 1490). These direct client handlers apply/remove active effect state; this is the applicable received-state path for movement predicates.
- `LivingEntity.jumpFromGround` reads jump boost through `getJumpBoostPower`, adds it to `getJumpPower`, writes vertical velocity, then applies the same sprint impulse. Both versions use `0.42F * getBlockJumpFactor()` and, when `JUMP` is active, `0.1F * (amplifier + 1)` with the same float-to-double expression and order (1.17.1 lines 1967–1985; 1.18.2 lines 1973–1990).
- `LivingEntity.travel` selects the same water/lava/fall-flying/ordinary branches in the same order. Relevant gates and constants are unchanged: downward-or-zero velocity plus `SLOW_FALLING` changes gravity from `0.08` to `0.01` and resets fall distance; water movement reads `DEPTH_STRIDER`, caps at 3, halves it off-ground, modifies slowdown/input factor, and overrides slowdown to `0.96F` under `DOLPHINS_GRACE`; ordinary travel applies the same `LEVITATION` adjustment and fall-distance reset. The reset spelling changes from direct `fallDistance = 0.0F` to `resetFallDistance()` in 1.18.2; the paired helper is exactly that assignment. These checks establish no movement-formula delta for these effects in this slice.
- `MobEffectInstance` add/update/tick/expiry and hidden-effect promotion logic has no relevant semantic change. The active-effect writer path and tick-driven duration state are equivalent in the inspected methods. Exact per-tick equality of unrelated rendering/icon or effect-particle behavior is not claimed.

### Received attributes, movement speed, and equipment

- `ClientPacketListener.handleUpdateAttributes` (around 2248 / 2106) resolves the living entity, finds each corresponding `AttributeInstance`, sets the packet base value, removes current modifiers, then adds the packet modifiers as transient modifiers. Order and handling of a missing attribute are the same. `AttributeInstance.calculateValue` still applies addition modifiers, then `MULTIPLY_BASE` against the additive result, then sequential `MULTIPLY_TOTAL` factors. `Player.getSpeed()` still returns the movement-speed attribute value cast to `float`; ordinary travel consumes that value through `getFrictionInfluencedSpeed`, and water/depth-strider travel uses it in the same interpolation.
- `ClientPacketListener.handleSetEquipment` still writes each packet slot/item stack to the target entity in packet iteration order. `EnchantmentHelper.getDepthStrider` delegates to the same enchantment-level lookup; `LivingEntity.tryAddSoulSpeed` and its block-speed/attribute helpers use the same slot/enchantment checks and same modifier constant/formula. These read current equipment and vanilla block state. This closure does not assert which equipment packets a server emits for a particular local-player inventory event.
- Effect attribute modifier production is separated from client movement state: `LivingEntity.onEffectAdded`, `onEffectUpdated`, and `onEffectRemoved` guard attribute mutation with `!level.isClientSide` in both versions. Client movement speed supplied by effects therefore comes through the received attribute packet path above; active effects such as jump boost/slow falling/levitation/dolphin's grace are directly installed in the client effect collection. Server-only effect/attribute production is not evidence of a client movement delta and is not replayed here.
- `setSprinting` removes the sprint UUID modifier if present and re-adds the same transient modifier when enabling sprint; no formula/order change was found in the paired method. Player walking-speed ability assignment remains a distinct received ability path; packet application writes the same `flying`, `instabuild`, `invulnerable`, `mayfly`, flying-speed, and walking-speed fields in both versions. Exact input-device and flight-mode inventory is outside this bounded closure.

### Pose and dimensions

- `Player.updatePlayerPose` keeps the same outer `canEnterPose(SWIMMING)` gate, priority order (fall-flying, sleeping, swimming, spin attack, crouching, standing), and fallback sequence (chosen pose, crouching, swimming). A local input/pose transition remains reachable through the normal local-player tick path.
- `Entity.canEnterPose` still checks `noCollision` for the candidate pose bounding box deflated by `1.0E-7`. `refreshDimensions` still obtains pose dimensions and eye height, reapplies position, and only performs the expansion/free-position correction under the same server-side non-player guards. Player resizing continues through the pose-dependent dimensions and bounding box. `EntityDimensions.makeBoundingBox`, `scale`, `scalable`, and `fixed` retain the same float width/height calculations and box construction. `Pose.java` itself is byte-identical across the endpoints (hash in TSV).
- The `Entity`, `EntityDimensions`, and `Player` files changed as a whole, so this does not clear their other modified methods. Collision geometry providers and `noCollision` internals are explicitly outside this closure.

## Changed versus unchanged callers and remaining gates

Changed file hashes do not imply changes to the reviewed calls. In the examined path, packet handlers still populate equivalent effect/attribute/equipment/ability state; `LivingEntity` still consumes the same effect gates and modifier formulas; `Player` still supplies the same movement-speed and pose/dimension consumers. The exact paired consumers have no movement-semantic change identified here.

Not closed: exact packet payload serialization/quantization and upstream production/ordering; received player correction, velocity, or explosion state; client inventory/container packet paths that may change the local player's equipment; full `AttributeSupplier` registry/default-registration dependency across entity classes; all other changed members of the listed classes; collision/no-collision provider behavior; block/fluid state dependencies; non-effects movement inventory. Jump Boost, Slow Falling, Levitation, Dolphin's Grace, speed modifiers, depth-strider and soul-speed equipment use are traced only for the consumer and direct received state path, not for their server producer or every means of state acquisition. Equivalent received values are assumed when comparing these consumer formulas. No trajectory is inferred and no intermediate release boundary is established.

**Disposition:** bounded consumer/source closure only. The 1.17.1 → 1.18.2 pair remains un-frozen; full inventory, provider dependencies, other packet writers, and independent whole-pair coverage remain open.
