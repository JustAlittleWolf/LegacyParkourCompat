## Source facts

### Block collision traversal

- **1.17.1** `CollisionGetter.getBlockCollisions` returns a sequential `Stream<VoxelShape>` backed by `CollisionSpliterator` (`CollisionGetter.java:61–71`). `CollisionSpliterator` is an `AbstractSpliterator`; each `tryAdvance` first performs its one-time source-entity border check when an entity was supplied, then advances the `Cursor3D` (`CollisionSpliterator.java:22–59, 103–134`).
- **1.18.2** `CollisionGetter.getBlockCollisions` returns an `Iterable<VoxelShape>` whose iterator is a `BlockCollisions` (`CollisionGetter.java:73–75`). `BlockCollisions` extends Guava `AbstractIterator`, ends with `endOfData()`, and contains no border check (`BlockCollisions.java:18–25, 65–96`).
- Both constructors build the same cursor bounds, in X/Y/Z order: `floor(min - 1.0E-7) - 1` through `floor(max + 1.0E-7) + 1`, inclusive through `Cursor3D` (`CollisionSpliterator.java:48–54`; `BlockCollisions.java:41–47`). Both process cursor entries in `advance()` order and skip cursor type `3` (`CollisionSpliterator.java:61–67`; `BlockCollisions.java:65–72`).
- For ordinary block collision traversal, candidate admission is structurally the same: retrieve chunk for candidate X/Z section; skip missing chunk; set mutable position and read `BlockState`; apply the type-1 `hasLargeCollisionShape()` and type-2 moving-piston gates; get collision shape with `CollisionContext.empty()` for null entity or `CollisionContext.of(entity)` otherwise; for the canonical `Shapes.block()` use AABB-vs-unit-cube `intersects`; otherwise translate the shape and require `Shapes.joinIsNotEmpty(..., entityShape, AND)`. Each iterator emits/returns the first passing shape, then resumes at the next cursor entry on demand (`CollisionSpliterator.java:67–94`; `BlockCollisions.java:71–90`).
- Differences in that traversal: 1.17 has a supplied `BiPredicate<BlockState, BlockPos>` checked before cursor-type shape gates, and no suffocating-only flag (`CollisionSpliterator.java:31–47, 71–75`). 1.18 replaces that predicate with `onlySuffocatingBlocks`, tested before cursor-type gates (`BlockCollisions.java:25, 34–40, 75–79`). 1.18 caches the last non-null `BlockGetter` by packed chunk position; 1.17 asks the collision getter for each candidate (`CollisionSpliterator.java:96–101`; `BlockCollisions.java:50–63`). Since the cache hit guard requires `cachedBlockGetter != null`, null chunk results are queried again.
- A canonical full block shape returns a translated shape only when the query box intersects the unit block. The non-full shape path uses translated-shape intersection against `Shapes.create(queryBox)` in both releases. Empty or nonintersecting shapes are skipped; iteration terminates only after cursor exhaustion.

### `noCollision` and collection APIs

- **1.17.1** overloads route to `noCollision(entity, box, predicate)`; that method returns `getCollisions(...).allMatch(VoxelShape::isEmpty)`. `getCollisions` concatenates block-collision stream first, then entity-collision stream; the predicate is forwarded to entity collision collection (`CollisionGetter.java:39–58`).
- **1.18.2** removes the predicate overload. `noCollision(entity, box)` loops block shapes first and returns false on the first nonempty shape, then returns false if the entity collision list is nonempty; with null entity it returns true at that point; otherwise it obtains `borderCollision(entity, box)` and returns true only when absent or disjoint from the query AABB (`CollisionGetter.java:38–63, 77–81`). The method signatures are now `List<VoxelShape> getEntityCollisions(entity, box)` and `Iterable<VoxelShape> getCollisions(entity, box)`; entity shapes precede block shapes in `getCollisions` (`CollisionGetter.java:65–75`).
- The old iterator's border check applies only to a non-null source entity and examines `source.getBoundingBox()`, not its iterator query box. It tests `!isBoxFullyWithinWorldBorder`, then tests the border shape against the deflated box and inflated box, emitting the border shape before any block candidate when the conditions pass (`CollisionSpliterator.java:103–134`). The 1.18 block iterator has no border stage; `noCollision` handles border after block and entity checks.

### Requested movement, clipping, step-up, flags

- In both `Entity.move` implementations, `noPhysics` directly adds requested coordinates and bypasses collision. Otherwise piston moves are restricted first (and may early return at zero), then stuck-speed multiplier is applied if its squared length exceeds `1.0E-7` (and delta movement is zeroed), then `maybeBackOffFromEdge` adjusts the request, and `collide` returns the clipped vector. `setPos` receives the clipped vector only when its squared length exceeds `1.0E-7` (`Entity.java:534–557` in 1.17.1; `543–575` in 1.18.2). For collision interpretation, “requested” below means this post-piston/stuck/edge-adjusted vector entering `collide`, not the original caller argument.
- **1.17.1** `collide` makes a rewindable stream from entity collisions over `currentBox.expandTowards(request)` followed by a conditional world-border shape. The border stream is suppressed when the current box deflated by `1.0E-7` intersects border shape. Zero-length requests skip clipping. The initial clipped vector sets per-axis difference booleans; step-up is attempted iff `maxUpStep > 0`, entity is on ground or downward Y was clipped, and X or Z was clipped. Candidate 1 clips `(reqX,maxUpStep,reqZ)`; candidate 2 clips pure upward movement against a horizontally expanded box; if candidate 2 rises less than max step, candidate 3 clips horizontal motion from the raised box and is added to candidate 2. Candidate 3 replaces candidate 1 only for strictly larger horizontal distance squared. The selected step path wins over initial clipped movement only for strictly larger horizontal distance squared, then clips vertical `(0,-stepY+reqY,0)` and adds that result (`Entity.java:750–789`).
- The 1.17 heuristic chooses `collideBoundingBoxLegacy` when at least two request components are nonzero; that path joins the rewindable stream with block collisions over the expanded box. Otherwise it calls `collideBoundingBox`, passing the `LevelReader`, context and rewindable stream. Both clip Y first; then X/Z are ordered by `abs(X) < abs(Z)` (Z first only when true; ties X first); the AABB is shifted after a nonzero Y and first horizontal clip before clipping the remaining horizontal axis (`Entity.java:791–872`). The heuristic/legacy path differs by clipping against the supplied shape stream; the single-axis/two-axis path's `Shapes.collide` also receives reader and context.
- **1.18.2** `collide` first materializes entity collision shapes over the swept AABB. Each `collideBoundingBox` call builds a list in this order: those entity shapes; border shape if entity is non-null and `WorldBorder.isInsideCloseToBorder(entity, sweptBox)`; block collisions over that swept box. It then invokes a single `collideWithShapes` (`Entity.java:777–854`). Step-up gate, candidate order, strict horizontal-distance comparisons, Y/X/Z clipping order and AABB updates are the same as 1.17. The 1.18 clipper applies the same axis displacement order directly to the supplied `List<VoxelShape>`; it no longer has the 1.17 heuristic split or reader/context `Shapes.collide` overload (`Entity.java:803–854`).
- **Post-clip flags and velocity:** 1.17 uses `!Mth.equal(reqX, clippedX) || !Mth.equal(reqZ, clippedZ)` for horizontal collision; `reqY != clippedY` for vertical collision; `onGround = verticalCollision && reqY < 0`; and independently zeros X or Z delta movement only when that component differs by exact `!=` (`Entity.java:561–563, 570–577`). In 1.18 the same `Mth.equal` horizontal flag and exact vertical inequality feed `horizontalCollision`, `verticalCollision`, `verticalCollisionBelow = verticalCollision && reqY < 0`, `minorHorizontalCollision` (computed only when horizontal collision is true); delta movement is then adjusted by the Mth.equal-derived X/Z booleans under one horizontal-collision branch (`Entity.java:579–590, 597–600`). `onGround` remains `verticalCollision && reqY < 0`.

### World border source-side gate

- The border collision shape construction in `WorldBorder` still subtracts the floored-min / ceiled-max interior box from `Shapes.INFINITY` in both releases (`WorldBorder.java:333–357` in 1.17.1; corresponding `MovingBorderExtent.getCollisionShape` in 1.18.2). This confirms the geometric border-shape expression is unchanged for this slice.
- Border *admission* into collision operations changed. 1.17's iterator uses `isBoxFullyWithinWorldBorder` with strict checks for all AABB min/max X/Z against `floor(minBorder)` and `ceil(maxBorder)`; when not fully within, its inflation/deflation overlap tests decide whether to emit border (`CollisionSpliterator.java:103–134`). Separately, `Entity.collide` supplies the border shape based on overlap of the current box's deflated interior (`Entity.java:753–759`).
- 1.18 has `WorldBorder.isInsideCloseToBorder(entity, box)`: `margin=max(absMax(box.width,box.depth),1.0)`; require `getDistanceToBorder(entity) < margin*2.0` and entity X/Z strictly within border bounds expanded by margin (`WorldBorder.java:76–79`). `Entity.collideBoundingBox` applies this predicate to each swept box and adds border shape after entity shapes but before block shapes (`Entity.java:809–815`). `CollisionGetter.noCollision` uses the same helper after block and entity checks, and tests border/query overlap (`CollisionGetter.java:57–63, 77–81`).

## Outcome boundary

The source establishes changed types, gates, collection/materialization, border admission location, candidate order, and flags. The cursor bounds and ordinary block-shape admission/intersection sequence are preserved. It does **not** establish a concrete differing trajectory or exact direction/magnitude: that depends on particular world/entity collision results and downstream `Shapes.collide` semantics. Treat possible changed outcomes near border and in no-collision queries as hypotheses until the downstream sources and a concrete reachable state are checked. No runtime execution was performed.

## Unresolved dependencies / explicit omissions

- Exact `Shapes.collide` and `VoxelShape` axis-clipping internals were not part of the assigned source slice; they are needed to close all lazy-reader versus materialized-list interactions.
- `Level` implementations of `getEntityCollisions` and their eligibility/order rules were not examined; entity/non-player collision behavior was outside assignment. Only the `CollisionGetter` call sites and collection types/order are recorded.
- Player-specific overrides of `maybeBackOffFromEdge`, `isHorizontalCollisionMinor`, and other caller-side behavior were not audited. The report bounds requested motion to the vector entering `Entity.collide`.
- Block/state shape providers, DDA/ray callbacks, and non-player collision behavior were excluded as assigned. This closes only the collision collection/clipping slice, not the player tick inventory or 1.17.1→1.18.2 pair.
