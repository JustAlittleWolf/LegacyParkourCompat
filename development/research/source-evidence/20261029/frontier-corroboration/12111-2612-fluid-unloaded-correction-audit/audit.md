## Findings

The correction's central dispatch and fallback account is supported:

- On 1.21.11, `Entity.touchingUnloadedChunk()` calls `level().hasChunksAt(...)`; inherited `LevelReader.hasChunksAt` iterates inclusive chunk coordinates through virtual `hasChunk`. `ClientLevel.hasChunk` returns `true` unconditionally (`ClientLevel.java:392–394`). So that old broad gate cannot abort for an absent chunk on the local-client path.
- The old scan uses the deflated entity box and calls `level().getFluidState` for each scanned block (`Entity.java:3514–3532`). `Level.getFluidState` obtains the chunk through `getChunkAt` (`Level.java:346–352`); the default chunk request has `loadOrGenerate=true` (`LevelReader.java:124–133`). `ClientChunkCache.getChunk` returns its shared `EmptyLevelChunk` for an absent requested chunk in that mode (`ClientChunkCache.java:33–40, 69–78`), and `EmptyLevelChunk.getFluidState` returns `Fluids.EMPTY.defaultFluidState()` (`EmptyLevelChunk.java:36–38`). Thus absent old scan coordinates contribute no fluid while reads of installed chunks in the actual scan can still contribute.
- The old eye updater performs a separate single-position `getFluidState` read after the height/current sampler (`Entity.java:1524–1535`), so it uses the same empty-chunk fallback and is not covered by a neighbor preflight. An eye position in an installed chunk can produce an old eye-water result only when that position's queried fluid is water and its fluid top is strictly above eye Y. Merely having a nonempty/flowing water state in the eye block is insufficient if its surface is at or below eye height. The correction's phrases “containing water” and “fluid-filled” should carry this explicit surface condition.
- In 26.1.2, `EntityFluidInteraction.update` resets trackers, derives the unexpanded block bounds, and invokes `hasFluidAndLoaded` with one extra block on each horizontal side (`EntityFluidInteraction.java:32–42`). The helper requests every X/Z chunk in those bounds at `ChunkStatus.FULL` with `loadOrGenerate=false`; the first null returns false before scanning (`:91–118`). `Level.getChunk` delegates to the chunk source and returns the null result when loading is false (`Level.java:202–208`); `ClientLevel.getChunkSource()` supplies `ClientChunkCache` (`ClientLevel.java:694–696`), whose no-load absent/out-of-range case returns null (`ClientChunkCache.java:69–78`). This path does not use the always-true `ClientLevel.hasChunk` check. A missing halo chunk therefore aborts the entire collector even if other positions in the actual scan box are installed.
- Trackers are reset before that early return: water/lava heights become zero, eye flags false, current accumulators `Vec3.ZERO` and counts zero (`EntityFluidInteraction.java:32–33, 153–163`). The collector's scan, height accumulation, current accumulation, and integrated eye test are all behind the successful preflight (`:43–89`). The correction is right that installed-position contributions are suppressed together with missing-position reads on this new path. The `hasFluid` check also cannot produce fluid output when it returns false: all requested chunks have first been confirmed non-null and no queried section has fluid.

The correction's immediate-versus-future eye timing is also supported. Old `updateFluidOnEyes` snapshots the previous eye-water predicate before clearing and refreshing eye tags (`1.21.11 Entity.java:1524–1535`); new `baseTick` snapshots before `updateFluidInteraction` (`26.1.2 Entity.java:523–524`). The refreshed `isEyeInFluid` result can therefore differ immediately after that tick's update, while `wasEyeInWater` captures the prior tracker. `isUnderWater` uses `wasEyeInWater && isInWater()` (`26.1.2 Entity.java:1526–1528`). If a missing halo chunk aborts the same tick's collector, water height/occupancy is zero, so no underwater result follows from the just-refreshed eye difference on that tick. A later underwater difference requires a later tick where the new preflight succeeds and water occupancy is positive while the eye snapshot still reflects the preceding difference. Persistent failed preflight cannot itself satisfy that water-occupancy gate.

## Bound and limits

The corrected contrast is source-supported under the correction's loaded-state assumptions, sharpened as follows: an absent chunk must be touched by the new one-block X/Z halo; the old sampled coordinates being relied on must be installed and contain qualifying fluid; and, for an old eye-water result, the eye position must be installed with water surface strictly above eye Y. The new collector resets and suppresses the complete scan when its halo preflight sees the absent chunk. No runtime occurrence, chunk timing, or trajectory is claimed.

The correction's list of affected fields and downstream effects is supported when the relevant old fluid sample qualifies and the downstream gates apply. In particular, `isInLava()` has a `!firstTick` gate on both endpoints; fluid-current application requires a player pushed by fluid; fall-distance reset and the entering-water splash path require the water sample; and underwater consumption also requires positive water occupancy. These conditions should remain attached to any later statement of effects. `updateSwimming()` follows the fluid update and reads water/underwater state, so swimming state is another conditional downstream consumer (`1.21.11 Entity.java:1491–1497`; `26.1.2 Entity.java:1548–1556`).

No source, original report, prior audit, or correction was edited. No tests, builds, game launches, or Git operations were performed.
