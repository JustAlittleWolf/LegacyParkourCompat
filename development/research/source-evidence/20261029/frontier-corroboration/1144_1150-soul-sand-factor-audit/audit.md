# Independent audit: 1.14.4 → 1.15 Soul Sand speed factor

## Verdict

**Accepted for the bounded source claims.** I independently traced the 1.14.4 Mojmap and 1.15 Mojmap code paths in the published source roots. The report's operation, registration, movement order, player gates, and ordinary dry-travel caller claims are supported. Its numeric note correctly distinguishes a double literal in the old callback from a float property widened for the new `Vec3.multiply(double, double, double)` call. The report makes no trajectory claim and does not infer particular contacted or queried blocks.

## Retraced source claims

1. **Old callback and registration:** In 1.14.4, `SoulsandBlock.entityInside` writes `entity.getDeltaMovement().multiply(0.4, 1.0, 0.4)` to the entity. `Vec3.multiply` accepts doubles. `Blocks.SOUL_SAND` is registered without a speed-factor property. The old `Block` fields and `Block.Properties` contain friction but no speed factor, and a recursive `*.java` search of the entire 1.14.4 Mojmap tree for `getBlockSpeedFactor`, `speedFactor`, `getSpeedFactor`, and `speedFactor(` returned no matches. The compared old `Entity.move` has no generic speed-factor application.
2. **Old contact sequence:** Old `Entity.move` reaches `checkInsideBlocks()` after updating collision/position state in its collision-enabled branch. `checkInsideBlocks` checks `hasChunksAt` for the endpoint cells, loops the box inset by `0.001`, obtains each state, calls `entityInside`, and then calls `onInsideBlock`. This supports the report's order and its explicit caveat that actual contacted cells and callback count are world/runtime dependent.
3. **New property and application:** In 1.15, `Blocks.SOUL_SAND` sets `.speedFactor(0.4F)`. `Block.Properties` defaults the factor to `1.0F`, offers `speedFactor(float)`, and `Block.getSpeedFactor()` returns the stored float. `SoulsandBlock` has no `entityInside` override, while base `Block.entityInside` is empty. New `Entity.move` invokes `checkInsideBlocks()` and then scales stored X/Z delta by `getBlockSpeedFactor()`; this occurs after that move's displacement resolution and only in the collision-enabled branch. New `getBlockSpeedFactor` reads the block at `new BlockPos(this)`, special-cases water and bubble columns, and otherwise falls back to `getBlockPosBelowThatAffectsMyMovement()` only when the first factor compares equal to `1.0`. The support position is `(x, boundingBox.minY - 0.5000001, z)`. The report correctly describes the lookup without assigning actual cells.
4. **Player gates and local path:** In 1.15, `LocalPlayer extends AbstractClientPlayer`, which extends `Player`; the `Entity.move` virtual call therefore reaches `Player.getBlockSpeedFactor`. That override returns `1.0F` for abilities flight or fall flight and delegates otherwise. `noPhysics` skips the factor-bearing collision branch; zero piston movement returns before its work. `LocalPlayer.tick` conditionally reaches `super.tick`, its `isEffectiveAi()` returns true, and `LivingEntity.travel` enters movement when effective AI or local control is true. In the non-water/non-lava, non-fall-flying travel branch, `moveRelative` and climbable handling precede `move(MoverType.SELF, getDeltaMovement())` at line 1891. Later travel velocity updates occur after this call; the audited report does not claim their numeric trajectory effect.

## Numeric and scope assessment

The old `0.4` is a double literal passed directly to the double-parameter vector method. In 1.15, `.speedFactor(0.4F)` stores a float; the getter returns float and Java widens that value to double for the vector method. This is a real source-level operand-type change. The two source expressions do not by themselves establish a movement trajectory, accumulated rounding outcome, or endpoint. The report appropriately limits its conclusion to changed source operation and timing, eligible player gates, and reachable next ordinary travel call. No material correction is required.
