# Independent source coverage audit — 1.20.1 to 1.20.2 passenger placement

## Verdict

**Seat-placement writer coverage: complete. Transition/path coverage: complete after this audit’s bounded additions.** My full-tree declaration inventory matches the author’s seat-placement inventory exactly: no missing or extra passenger placement writer, rider offset provider, vehicle offset provider, or attachment point. The author report independently covers the tick reachability and writer call order. This audit adds the packet-entry method and the dismount destination methods omitted from its writer tables, then checks those transition bodies across the pair. They do not consume the changed Player rider offset.

One correction is material: my sibling `source-writer-inventory.md` incorrectly says the 1.20.1 Player offset was `-0.6` (double), and also incorrectly says Player overrides `LivingEntity.getMyRidingOffset` in 1.20.2. The decompiled source says 1.20.1 `Player.getMyRidingOffset()` returns **`-0.35` (double)**; in 1.20.2 `Player.ridingOffset(vehicle)` returns **`-0.6F`**, and Player inherits `LivingEntity.getMyRidingOffset(vehicle)`, which multiplies the float offset by `getScale()`. At normal Player scale `1.0F`, the effective offset is `-0.6F` promoted into the Y calculation. The excerpted source and its SHA-256-bound manifest entries are correct; this audit supersedes those two prose claims.

Reachability is closed for every listed writer. `LocalPlayer` extends `AbstractClientPlayer` → `Player`; both versions’ `ClientLevel.tickPassenger` ticks `Player` passengers, snapshots old position/rotation, increments tick count, calls `rideTick`, then recursively ticks child passengers. `Entity.rideTick` writes zero delta movement, calls `tick`, and, if still riding, dispatches to `vehicle.positionRider(this)`. The rider offset is added after the attachment point is translated/rotated.

`startRiding(target, force)` in both releases first rejects same vehicle, cycle, and `!target.couldAcceptPassenger()`. `force` skips the ordinary rider `canRide` and target `canAddPassenger` checks; it does not skip the `couldAcceptPassenger` gate. The client passenger packet uses force. The only `couldAcceptPassenger` override that rejects a passenger is Marker, which has no placement/attachment override. Every class in the listed placement inventory can therefore reach the virtual placement API through the passenger relationship path (subject to a loaded entity and valid relationship).

The author’s exact formula inventories agree with the source snippets for the old offset overrides and new attachment points, including the player-dependent branches: Camel index/front/rear and removed checks, Boat side/animal slots and bamboo height, Minecart's Player `0.1875F` attachment, scale/body-yaw handling, and the Strider bob formula. Ride-tick velocity zeroing precedes Player tick and position write. ## Bounded transition closure absent from the author’s writer tables

The author report summarizes mount/dismount state, but its writer tables do not identify the packet listener or vehicle dismount-location overrides. I checked these directly in both trees:

* `ClientPacketListener.handleSetEntityPassengersPacket` (`ClientPacketListener.java:966` in 1.20.1; `:923` in 1.20.2) resolves the vehicle; warns for an unknown vehicle; remembers whether the local player was already an indirect passenger; ejects the vehicle’s current passengers; then for each loaded passenger ID calls `startRiding(vehicle, true)`. For a newly-mounted LocalPlayer on a Boat it sets previous/current Y yaw and head yaw from the Boat, then emits the on-board overlay/narrator prompt. It does **not** write LocalPlayer position. Its normalized method body matches across releases. The next `ClientLevel.tickPassenger`/`rideTick` performs seat placement. On an empty passenger update, `ejectPassengers` calls `stopRiding`; LocalPlayer’s `removeVehicle` resets `handsBusy` in both releases. Packet handler SHA-256: 1.20.1 `8b21ccd4106abb0698f6872250e665ae3f0fc942c8953b9ddd45976660ed624b`; 1.20.2 `0208f6942035adaf2e787546851ca296f0e7ec2179d3610f694911eda5283264`.
* `Entity.startRiding`, `LivingEntity.stopRiding`, `LivingEntity.dismountVehicle`, `Player.removeVehicle`, `LocalPlayer.startRiding`, `LocalPlayer.removeVehicle`, and the client packet handler have matching normalized method bodies between releases. LocalPlayer’s `startRiding` first delegates to Entity state installation and retains its vehicle-specific minecart sound behavior. The server-only LivingEntity stop path checks whether a valid vehicle remains and is outside a portal; otherwise it uses current coordinates with `Y=max(playerY,vehicleY)`. It then calls `dismountTo`; this path is gated off on logical clients.
* Dismount destination writer declarations are present and have matching normalized method bodies in the two versions: `Entity.getDismountLocationForPassenger` (`Entity.java:2925` / `:2955`), `Boat` (`Boat.java:698` / `:713`), `AbstractMinecart` (`AbstractMinecart.java:156` / `:160`), `Pig` (`Pig.java:183` / `:182`), `AbstractHorse` (`AbstractHorse.java:1112` / `:1102`), and `Strider` (`Strider.java:216` / `:213`). Entity defaults to `(vehicleX, boundingBox.maxY, vehicleZ)`. Boat searches valid floor candidates around a width-scaled horizontal escape vector and tries the passenger’s dismount poses; Minecart/Pig/Strider choose motion-direction neighbor offsets and test candidate floors/poses; Horse tries arm-dependent side escape candidates then falls back to vehicle position. These methods do not call the changed Player rider-offset method.
* Their `DismountHelper` dependency implementations also match between versions: `offsetsForDirection`, `isBlockFloorValid`, both `canDismountTo` overloads, `nonClimbableShape`, `findCeilingFrom`, and `findSafeDismountLocation`. The dismount destination path is separate from the recurring passenger seat-position writer and does not create an extra `positionRider`/attachment writer.

The pair has no source writer gap after these additions. Vehicle motion/animation production, physics, damage, remote rendering/interpolation, and logical-server historical physics remain outside this closure. Dismount location formulas were checked as unchanged transition dependencies; this audit does not claim they consume or verify the changed seat offset.
