# Passenger-scale and helper-relocation follow-up

**Disposition: ACCEPT; no additional passenger-scale fallback is needed for this operation.** Checked product tip `2dc5e3402e28c18b97657d592a66b73f3ad4d2d9`.

In exact 1.20.2 Mojmap, `Player.ridingOffset(Entity)` returns `-0.6F` (`Player.java` SHA-256 `25f263692fd6b2a737aa813315022a0caf4e18c3661ba3bd706c6297f909f25c`) and `LivingEntity.getMyRidingOffset(Entity)` multiplies that by `getScale()` (`LivingEntity.java` SHA-256 `5c481da1ffc8684c4b30171c92e61fad751e6a3a708d5bc6486ac9f96ff69828`, lines 3435–3436). In that source release `LivingEntity.getScale()` is only `isBaby() ? 0.5F : 1.0F`; `Player.isBaby()` is false, so the Player passenger offset is 1.0-scaled. The accepted 1.20.1 Player offset is a constant `-0.35` and does not use player dimensions.

The current 26.2 runtime has a generic `Attributes.SCALE` (`LivingEntity.java` SHA-256 `7ffd9c70966edc50c9cb4d9a8fe17a518e2678ff44c8026e763d0b94ac0ae51a`), but current seat placement no longer derives the player's vertical rider offset from that value. Current `Entity.positionRider` subtracts `passenger.getVehicleAttachmentPoint(vehicle)` (Entity.java SHA-256 `7afb9c1294893ffe73e3b1acffcad41c648f15de8378bff3dffaff869bb811d5`, lines 2395–2398). `Entity.getVehicleAttachmentPoint` reads `EntityAttachment.VEHICLE`; its default fallback is `AT_FEET`, whose point is `Vec3.ZERO` independent of dimensions/scale (`EntityAttachment.java` SHA-256 `c756a88c02e5d4cc50d4725cb37c4331eb45764f8aa70e5d730ba069c8facfa4`; `EntityAttachments.java` SHA-256 `f8fb02ec47a0e8e74618980b752c4d5b32f5ac1c4f32ad7ea73b2381d6fdd08a`). Thus a non-default Player scale affects the player's dimensions/bounding box, which this integration preserves through the original `MoveFunction`/`setPos`, but it does not alter the current seat position being replaced. Vehicle scale remains checked because vehicle attachment geometry does depend on it.
