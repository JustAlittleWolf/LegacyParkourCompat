# Synchronous inside-block callback lifecycle

## Scope and verdict

Compared canonical Mojmap source for Minecraft 1.21.2, 1.21.3, and 1.21.4. Scope was `Entity` movement records, `applyEffectsFromBlocks`, `checkInsideBlocks`, its synchronous callbacks and gates, the `LivingEntity` caller, and the bounded traversal counter in `BlockGetter`. The final-query-box/recentered-geometry topic was excluded.

There is no class or symbol literally named `StepBasedCollector` in these vanilla Mojmap sources. The closest bounded vanilla lifecycle is `Entity.movementThisTick` plus `BlockGetter.boxTraverseBlocks` / `addCollisionsAlongTravel`.

**Operation delta:** 1.21.2 and 1.21.3 use the live movement list while callbacks run and clear it only after callback traversal and the fire/lava summary. 1.21.4 snapshots that list with `List.copyOf` and clears the live list before callback traversal. The callback order and traversal budget are otherwise unchanged in the checked slices.

## Source facts

- In all three releases, `LivingEntity` invokes `applyEffectsFromBlocks()` after `travel()` under `!level().isClientSide() || isControlledByLocalInstance()`. This is a player-reachable caller: `Player` is a `LivingEntity`; its normal movement tick reaches this caller after travel. `Entity.isAffectedByBlocks()` further requires the entity not be removed and not have `noPhysics`.
- In 1.21.2/1.21.3 `Entity.applyEffectsFromBlocks(from,to)` first calls the supporting block's `stepOn` if `onGround()`, then appends the movement and passes the live `movementThisTick` list to `checkInsideBlocks`. After that traversal, it evaluates whether the accumulated `blocksInside` contains fire/lava, then clears `movementThisTick` and `blocksInside`.
- In 1.21.4 the same method order is `stepOn`, append current movement, `List.copyOf(movementThisTick)`, clear the live list, then call `checkInsideBlocks(snapshot, blocksInside)`. The fire/lava summary and `blocksInside.clear()` follow the callbacks.
- In each checked `checkInsideBlocks`, a second `isAffectedByBlocks()` gate surrounds the whole sweep. It iterates movement records in list order, then positions returned by `BlockGetter.boxTraverseBlocks`. It aborts when `!isAlive()`. For each non-air state at a position newly added to `visitedBlocks`, it gets the entity-inside collision shape; when that shape gate passes, it calls `BlockState.entityInside(level,pos,entity)` and then virtual `Entity.onInsideBlock(state)` synchronously in that order. Exceptions are wrapped in a `ReportedException`; after the callbacks, the state is added to `blocksInside`. `visitedBlocks` is cleared after a completed sweep.
- `Player.java` declares `Player extends LivingEntity` in all three releases and has no `onInsideBlock` override; the base method is empty. Vanilla `BlockState.entityInside` remains a synchronous callback and is reachable for a player through the `LivingEntity` caller above. `ServerGamePacketListenerImpl.handleMovePlayer` records an accepted player packet movement segment after updating the player position (`recordMovementThroughBlocks`, lines 930 in 1.21.2/1.21.3 and 990 in 1.21.4). That queued segment is available to the later server-side `LivingEntity` block-effects call. The additional recorder call at lines 452/454 concerns an entity vehicle, not the player.
- `BlockGetter.addCollisionsAlongTravel` uses the same `while` condition and `if (counter++ > 16) break` guard in all three releases; the guard permits up to 17 advancement/clip bodies before breaking on the next loop. No callback collector or budget change was found in that bounded helper.
- The 1.21.2 and 1.21.3 checked `Entity`, `LivingEntity`, and `BlockGetter` method bodies are textually the same in these callback lifecycle slices. This statement is limited to the checked slices, not a general source-alias claim.

## Behavior inference and limit

The live-list iteration in 1.21.2/1.21.3 means a synchronous callback that appends another `Entity.Movement` to `movementThisTick` could modify the list currently being traversed; a later iterator advance can fail fast, and an append at the end would be cleared without being swept. The 1.21.4 snapshot prevents such an append from joining the current sweep; it remains in the live list for a later `applyEffectsFromBlocks` call, subject to other writers such as `teleportSetPosition` clearing that list.

This is a conditional consequence of the public `recordMovementThroughBlocks` writer. The player-reachable source path is concrete: an accepted `ServerboundMovePlayerPacket` handled in `ServerGamePacketListenerImpl.handleMovePlayer` records the old-to-new position segment (1.21.2/1.21.3 line 930; 1.21.4 line 990); the player then reaches the `LivingEntity` post-travel block-effects call on the server tick, where the queued movement records are traversed and callbacks are invoked. A separate recorder call at lines 452/454 in these releases is for an entity vehicle and is outside player movement scope. The 1.21.4 snapshot ensures the batch of packet-recorded segments is stable while those callbacks run; absent a callback-side write/clear of `movementThisTick`, the same records are traversed in the same order, so this change alone does not establish a different vanilla player callback sequence. Source-wide reference searches found no `recordMovementThroughBlocks` call from an inside-block callback; the only call sites found are the player packet handler and vehicle packet handler. The player also inherits the empty `onInsideBlock`. Therefore the changed queue boundary is player-reachable, but a trajectory consequence caused by a callback modifying that queue remains unproven.

## Unresolved gate and next action

The 1.21.4 lifecycle delta and the server player packet-to-block-callback path are established. Whether a vanilla inside-block callback can append or clear the movement queue during the sweep remains unresolved; no callback-side recorder call was found. Keep the queue-boundary difference distinct from any claimed player trajectory effect until a reachable callback writer is identified. This report does not establish runtime parity, full-pair coverage, or acceptance.
