## Source facts

1. `PistonMovingBlockEntity.tick` takes the active-progress branch when `progressO < 1.0F`, computes `progress + 0.5F`, calls `moveCollidedEntities`, then `moveStuckEntities`, and only then stores/clamps the new progress. In `moveCollidedEntities`, the entity movement amount is computed from overlap with piston movement areas; only amounts greater than zero enter `moveEntityByPiston`. After that helper returns, a retracting source piston may call `fixEntityWithinPistonBase`, which can call the same helper again for that entity.

2. `moveEntityByPiston` has the same order in all three releases: set the piston `NOCLIP` direction; call the entity's virtual `move(MoverType.PISTON, vector)`; call `entity.applyEffectsFromBlocks()`; clear `NOCLIP`. There is no `try/finally` or movement-success check around these calls. The helper always reaches `applyEffectsFromBlocks()` if `move` returns normally, including when `Entity.move` returns early for a limited piston vector equal to `Vec3.ZERO`.

3. For a `LocalPlayer`, virtual dispatch first enters `LocalPlayer.move`; it calls `super.move`, then updates auto-jump and `walkDist`, and returns to the piston helper. The subsequent `applyEffectsFromBlocks()` call is therefore after the entire `LocalPlayer.move` override. The local player class does not override `onInsideBlock`; the inherited `Entity.onInsideBlock` is an empty hook.

4. The no-argument `Entity.applyEffectsFromBlocks()` supplies `oldPosition()` and the current `position`. `oldPosition()` constructs a vector from stored `xOld`, `yOld`, and `zOld`; the piston helper does not capture a pre-piston position or pass explicit movement endpoints. Consequently, each piston helper invocation uses that stored old position as the newly appended segment's origin, not a locally captured position immediately before that particular piston displacement. If the retraction fix invokes the helper a second time in the same progression call, it again obtains the stored old position and the then-current position.

5. In 1.21.2/1.21.3, when `isAffectedByBlocks()` is true, `applyEffectsFromBlocks` first calls `stepOn` when grounded, appends the passed segment to `movementThisTick`, synchronously calls `checkInsideBlocks` with that mutable list, checks the collected states for fire/lava, then clears `movementThisTick` and `blocksInside`. `checkInsideBlocks` iterates the movement records, traverses the associated block positions, queries each non-air block's entity-inside collision shape, calls `BlockState.entityInside`, then `Entity.onInsideBlock`, and adds the state to the result set after the callback succeeds. Callback/query throwables are wrapped in `ReportedException` and rethrown.

6. In 1.21.4, the same effects method appends the supplied segment, takes `List.copyOf(movementThisTick)`, clears the mutable `movementThisTick`, then synchronously calls `checkInsideBlocks` with the snapshot. It checks the collected states and clears `blocksInside` after the callback walk. `recordMovementThroughBlocks` still appends a segment to the mutable list. Thus normal callback processing consumes the previously queued segments plus the new piston call's `oldPosition`→current-position segment in insertion order, but the list is detached and cleared before callbacks begin.

## Exceptional and zero-displacement paths

- `Entity.move`'s `noPhysics` branch sets position and skips the ordinary movement path. `applyEffectsFromBlocks` then returns at its `isAffectedByBlocks()` gate because that predicate rejects `noPhysics` entities (and removed entities); no piston-triggered inside-block traversal runs on that path.
- For a physics-enabled entity whose limited piston vector is `Vec3.ZERO`, `Entity.move` returns before the ordinary movement update, but this is a normal return to `moveEntityByPiston`; the helper still calls `applyEffectsFromBlocks`. The effects method can therefore process the `oldPosition`→current-position record and any queued records even when that piston move itself did not displace the entity.
- If `Entity.move` throws, the effects call and `NOCLIP.set(null)` are skipped. If `applyEffectsFromBlocks` throws during synchronous block work, `NOCLIP.set(null)` is also skipped, and the retraction-base fix is not reached. In either case there is no cleanup `finally` in the piston helper.
- If a callback/query throws, `checkInsideBlocks` rethrows a wrapped `ReportedException`. In 1.21.2/1.21.3 the `movementThisTick.clear()` after `checkInsideBlocks` is not reached, so the appended piston record and any records already queued remain in the list. There is no retry inside that invocation; a later effects invocation can receive the retained list again, subject to its state and visited-block guards. In 1.21.4 the copied list was already removed from `movementThisTick`, so that failed snapshot is not replayed on the next effects call. In both cases the later `blocksInside.clear()` is skipped on the throw, and `checkInsideBlocks`' final visited-block clear is also skipped.
- The movement-list processing/cleanup in `applyEffectsFromBlocks` is under `isAffectedByBlocks()`. If that gate is false, the method neither appends the no-argument segment nor clears a previously queued list. `teleportSetPosition` independently clears `movementThisTick` after resetting stored old position; this is a separate reposition path, not piston replay logic.

## Bounded conclusion and remaining gates

Source supports a definite caller-order and bookkeeping distinction: piston movement invokes block effects after virtual movement even on a normal zero-vector early return; its no-argument segment starts at stored `oldPosition`; and 1.21.4 snapshots and clears pending movement records before synchronous callbacks, while 1.21.2/1.21.3 clear them only after callback processing returns normally. The piston source itself has no branch-specific cleanup/replay behavior. A failed callback is not retried inside the same invocation; in 1.21.2/1.21.3 the retained mutable list can be presented to a later invocation, whereas 1.21.4 has already removed that snapshot. These are source facts; any trajectory or compatibility consequence remains an inference requiring separate product-level assessment and runtime evidence.
