## Callback path and gates

- `Entity.baseTick` updates fluid state (`updateInWaterStateAndDoFluidPushing`, then eye-fluid/swimming work) before living travel: 1.21.2/1.21.3 `Entity.java:430-451`; 1.21.4 `Entity.java:434-455`.
- During travel, `Entity.move` calls its collision resolution (`collide`) before setting the resolved position: 1.21.2/1.21.3 `Entity.java:619-704`; 1.21.4 `Entity.java:627-713`. This is geometry selection; it does not itself call the inside-block entity callback.
- The living tick reaches `travel(...)`, then calls `applyEffectsFromBlocks()` only when `!level().isClientSide() || isControlledByLocalInstance()`: 1.21.2/1.21.3 `LivingEntity.java:2771-2775`; 1.21.4 `LivingEntity.java:2782-2786`. A local controlled client player passes this gate.
- `applyEffectsFromBlocks(from,to)` is gated by `isAffectedByBlocks() == !isRemoved() && !noPhysics`. If grounded, it first invokes the support block's `stepOn`; it then appends the supplied movement segment and traverses the recorded segments: 1.21.2/1.21.3 `Entity.java:740-770`; 1.21.4 `Entity.java:751-782`.
- For each traversed block position, `checkInsideBlocks` returns if the entity is no longer alive, ignores air, and de-duplicates positions through `visitedBlocks`. It obtains the entity-inside collision shape; if that shape is not the full block shape, it calls `collidedWithShapeMovingFrom` and skips the callback when the shape was not crossed. On a qualifying state it calls `BlockState.entityInside(level,pos,entity)` followed by `Entity.onInsideBlock(state)`, catches failures as a collision crash report, and adds the state to `blocksInside` only after those callbacks: 1.21.2/1.21.3 `Entity.java:1038-1070`; 1.21.4 `Entity.java:1050-1082`. `BlockGetter.boxTraverseBlocks` supplies the positions (`BlockGetter.java:172+`); its detailed traversal geometry is outside this assignment.
- Base `Entity.onInsideBlock(BlockState)` is empty (`Entity.java:1086` in 1.21.2/1.21.3; `:1098` in 1.21.4). No `onInsideBlock`, `applyEffectsFromBlocks`, `checkInsideBlocks`, or `entityInside` declaration/override occurs in the inspected `Player.java` or `LocalPlayer.java`; the block state's `entityInside` callback remains the side-effecting block callback. This separates callback effects from the collision geometry already used to resolve movement.

## Cross-release delta: callback-list snapshot timing

In 1.21.2 and 1.21.3, `applyEffectsFromBlocks` appends the current segment to the entity's live `movementThisTick`, passes that same list to `checkInsideBlocks`, and clears it only after callbacks finish (`Entity.java:748-752`). In 1.21.4, it appends the current segment, snapshots with `List.copyOf`, clears the live list, and passes the snapshot to `checkInsideBlocks` (`Entity.java:759-763`).

This changes when recorded movement is consumed relative to callback side effects: the earlier releases expose the live list throughout traversal, while 1.21.4 freezes the segments for this pass and clears the live collection before traversal. Thus movement newly recorded reentrantly by a callback would be outside the current 1.21.4 snapshot and remain in the live collection; the earlier version traverses its live collection and clears it afterward. This is a collection-timing difference, not a change to collision-shape selection or the path already resolved in `Entity.move`.

The inspected vanilla Player/LocalPlayer classes do not create such a reentrant `recordMovementThroughBlocks` call. The only other direct call sites found in the source trees are server packet handling (`ServerGamePacketListenerImpl`), outside the local-client player callback path. Therefore the timing delta is established at the general Entity callback boundary, but a concrete vanilla local-player trajectory consequence from reentrant list mutation is not established by this bounded evidence. The ordinary player-reachable `BlockState.entityInside` callback still runs after travel and resolved movement, and may have its own side effects; no geometry change is inferred from those effects here.
