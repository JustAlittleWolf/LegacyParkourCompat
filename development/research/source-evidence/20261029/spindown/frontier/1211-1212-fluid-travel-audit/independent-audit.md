# Independent audit: 1.21.1 → 1.21.2 fluid travel

## Verdict and bound inputs

**Accept, bounded to water/lava travel for an ordinary nonflying, nonpassenger local player given equal current movement, fluid, effect, attribute, input, and collision-query results.** The 1.21.2 refactor factors these branches into `LivingEntity.travelInFluid`; I found no change to their calculated vector under those equal-input assumptions. This does not close the pair, packaged inputs, collision providers, or runtime/trajectory parity.

## Independent source retrace

At `LivingEntity.travel` (1.21.1 lines 2091–2150; 1.21.2 lines 2178–2265), both paths require `isControlledByLocalInstance()`, read the fluid at `blockPosition()`, and skip fluid motion when `!isAffectedByFluids()` or `canStandOnFluid` is true. Player's identical override makes fluid influence false while flying. The old dispatcher tests water before lava. The new dispatcher tests either fluid and delegates to a helper whose first branch is water, preserving water priority even if both flags are true. `Player.travel` (1.21.1 line 1456; 1.21.2 line 1445) preserves the swim adjustment and inherited travel order for a nonpassenger; the outer passenger restructuring skips only the same swim assist for passengers.

The water branch retains the `0.9F` sprint slowdown/`getWaterSlowDown()` choice, `0.02F` base acceleration, float cast and off-ground half of water-movement efficiency, the `0.54600006F` / `getSpeed()` blends, Dolphins Grace `0.96F`, `moveRelative`, then self-move, climbable Y correction, `(slowdown, 0.8F, slowdown)` scaling, fluid-falling adjustment, and the horizontal-collision/free-space Y=`0.3F` correction. 1.21.1 stores the scaled vector before calling the adjustment helper; 1.21.2 passes the same vector value into the helper and stores its return. Both use the pre-move Y in the final bounce test.

The lava branch preserves `0.02F` relative movement and self-move, the cached lava-height/eye-threshold split, either `(0.5, 0.8F, 0.5)` scaling plus fluid-falling adjustment or uniform `0.5` scaling, then `-gravity / 4.0` on Y when nonzero and the same final collision/free-space bounce. 1.21.1 captures pre-move Y inside each branch; 1.21.2 captures it once before choosing water/lava. The inputs are unchanged at that point. The old inline gravity/Slow Falling expression is equivalent to the new `getEffectiveGravity()` expression for equal `getGravity()`, Y-velocity, and effect state.

I independently whitespace-normalized and compared bodies for `Entity.isInWater`, `isInLava`, `getFluidHeight`, `getFluidJumpThreshold`, `touchingUnloadedChunk`, `setDeltaMovement(Vec3)`, and `updateFluidHeightAndDoFluidPushing`; `LivingEntity.isAffectedByFluids`, `getWaterSlowDown`, `canStandOnFluid`, and `getFluidFallingAdjustedMovement`; `Player.isAffectedByFluids` and `getSpeed`; `Level.getFluidState`; `LevelChunk.getBlockState`/`getFluidState`; `LevelChunkSection.getFluidState`; and `FluidState.isEmpty`, `getHeight`, `getFlow`, and `is(tag)`. Each compared body matched after whitespace normalization. Player also overrides `isPushedByFluid()` in both releases with the same `!abilities.flying` gate, used by the identical scan.

One transitive query uses a renamed bound API: old `Entity.touchingUnloadedChunk()` calls `LevelReader.hasChunksAt`, whose vertical guard is `y2 >= getMinBuildHeight && y1 < getMaxBuildHeight`; the new guard is `y2 >= getMinY && y1 <= getMaxY`. Old max height is `min + height` exclusive, while new max Y is `min + height - 1` inclusive, so these integer block-coordinate predicates are equivalent. The horizontal section loop is unchanged. Both `ClientLevel.hasChunk` overrides return `true`.

The relevant `Attributes` values retain their defaults/ranges/sync settings but registry keys change from `generic.gravity`, `generic.movement_speed`, and `generic.water_movement_efficiency` to `gravity`, `movement_speed`, and `water_movement_efficiency`. Therefore identical *effective values* remain an explicit assumption; delivery/translation of those values is not established. Fluid-tag contents are likewise resource/data-pack inputs, not established by these Java sources.

## Swim-assist and water-state qualification

The nonpassenger swim-assist condition differs only in accessor: old `Player.travel` checks `getBlockState(pos).getFluidState().isEmpty()`, new checks `getFluidState(pos).isEmpty()`. `Level.getFluidState` and both ordinary `LevelChunk`/section routes are source-equivalent. In debug levels, `LevelChunk.getBlockState` synthesizes y=60/y=70 block states, whereas `getFluidState` reads section fluid state; the source alone does not establish those values coincide, so the report correctly keeps this special world outside ordinary parkour applicability.

The supplement's `Boat` → `AbstractBoat` gate is present in `Entity.updateInWaterStateAndDoWaterCurrentPushing` (1.21.1 line 1251; 1.21.2 line 1304). For the assigned unmounted player, `getVehicle()` is null and both paths run the same water scan. I also found the same type-guard rewrite in `Entity.updateFluidOnEyes` (1.21.1 line 1270; 1.21.2 line 1323); it is likewise passenger/vehicle-only and outside this unmounted-player comparison. The water-scan body is unchanged. No ordinary local-player delta is established by these vehicle guards.

## Remaining limits

The comparison assumes equal received/effective attribute and effect values, fluid tags/heights, movement flags/vector, and collision/query results. Packaged tag membership, renamed registry value delivery, shape/provider behavior, and the debug-level accessor case remain open. Passenger/vehicle state is excluded. This audit establishes only the bounded source result above, not complete 1.21.1 → 1.21.2 coverage or pair freeze.
