## Bounded finding draft

# Swimming state refresh gate

1.13.0, Ornithe Feather Gen2: `net/minecraft/entity/living/player/PlayerEntity.java`, `updateSwimming()`, lines 1464–1480.
1.13.1 and 1.13.2, Ornithe Feather Gen2: same file/member, lines 1471–1485.
Difference: In 1.13.0, flight clears swimming; otherwise `super.updateSwimming()` runs only when `!isSwimming()` or `doesNotSuffocate(new BlockPos(this)) && !world.getBlockState(pos.up()).getMaterial().blocksMovement()`. The helper requires the current and upper block states both to report `!isSolid()`. In 1.13.1/.2, flight still clears swimming, but the non-flying branch always calls `super.updateSwimming()`; the block-position/material gate is removed. The inherited `Entity.updateSwimming()` body is unchanged: when already swimming it recomputes the flag from `isSprinting() && isInWater() && !isRiding()`, otherwise from sprinting plus submerged-water eligibility and not riding.
Movement meaning: For an already swimming, non-flying player in the old gate's blocked-position case, when the inherited eligibility becomes false (for example, sprinting ends while the player remains swimming under an upper movement-blocking block), 1.13.0 can preserve the swimming flag by skipping the inherited recomputation; 1.13.1/.2 recompute and clear it that tick. `PlayerEntity.moveRelative()` has a swimming-only vertical-velocity adjustment (`getLookVector().y`, factor `0.085` or `0.06`, conditionally applied), so this retained/cleared state can change the subsequent player movement branch. The difference is established at source level; no trajectory/runtime result is asserted.
