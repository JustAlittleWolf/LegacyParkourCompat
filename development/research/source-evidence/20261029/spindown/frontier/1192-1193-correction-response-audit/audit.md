## Independent trace

- Packet dispatch is `ClientboundPlayerPositionPacket.handle` → `ClientGamePacketListener.handleMovePlayer`. Its fields are position doubles, yaw/pitch floats, packed relative arguments, integer acknowledgement id, and dismount boolean in both versions. `PacketUtils.ensureRunningOnSameThread` either continues on the client event loop or schedules the handler and rechecks connection state. The handler uses `minecraft.player`; it does not look up or compare a packet entity id. Dismount occurs first.
- Per-axis position and velocity behavior matches: relative axes add the packet value to current position and preserve that velocity component; absolute axes use packet coordinate and zero that component. Both versions acknowledge the packet id and immediately send a resolved `PosRot` with `onGround=false`.
- In 1.19.2, the handler updates `xOld/yOld/zOld`, sets raw position and `xo/yo/zo` to the resolved target, sets velocity, calculates relative rotations in locals, then invokes `absMoveTo`. `Entity.absMoveTo` clamps X/Z to ±3.0E7, sets `xo/yo/zo` to those clamped coordinates, rebuilds the box via `setPos`, applies yaw `% 360.0F`, clamps pitch to [-90.0F, 90.0F] before `% 360.0F`, and synchronizes old rotations to resulting rotations.
- In 1.19.3, each positional branch updates both `xOld/yOld/zOld` and `xo/yo/zo` (adding relative deltas or assigning absolute coordinates), then calls `setPos` and writes velocity. Relative rotations use `setXRot(current + packet)` / `setYRot(current + packet)` and add raw packet values to `xRotO/yRotO`; absolute rotations assign packet values to current and old fields. Those setters reject only non-finite values. The handler therefore skips the coordinate and angle limits on this path. Relative corrections also preserve the prior position interpolation origin plus the delta, unlike 1.19.2, which sets the origin to the resolved destination before `absMoveTo` (subject to its X/Z clamp).
- `getPosition(float)` / `getEyePosition(float)` consume `xo/yo/zo`, and interpolated view angles consume `xRotO/yRotO`. These are interpolation/render-facing effects; they do not establish a physics delta. `Entity.baseTick` copies current rotation to old rotation as the next local tick starts; it does not reset position history there. `xOld/yOld/zOld` also affect the client Powder Snow particle predicate; the damage-like sweet-berry use is server-gated. These peripheral observations do not change the primary direct-state finding.
- `LocalPlayer.tick` is chunk-gated. Inside that gate it calls `super.tick()` before its later movement-report path; passengers send passenger movement, while non-passengers call `sendPosition`. That sender's normal report is controlled-camera-gated and compares position/rotation with `xLast/yLast1/zLast` and rotation baselines. The correction handler leaves those baselines untouched. The candidate's description of this follow-up is supported.
- The server writer calls `player.absMoveTo` with its requested arguments but constructs the outgoing packet from the requested coordinate/rotation deltas, flags, token, and dismount value. Thus server-side clamping does not rewrite the serialized fields. The server listener retains invalid-value disconnect and pending-teleport retry paths; the 1.19.3 collision-rejection branch adds `doCheckFallDamage` after `teleport`. This does not prove arbitrary requests are reachable through ordinary vanilla call sites: the candidate correctly leaves call-site provenance and general reachability open.

## Verdict and limits

The candidate's packet flow, changed position/history/rotation writes, server-writer distinction, next-tick gate, and scope qualification are source-supported. No material correction is needed. The concrete direct-state difference is the 1.19.2 `absMoveTo` clamp/angle normalization omitted by the 1.19.3 response handler. Interpolation history is a separate rendering-facing consequence. Arbitrary packet-value reachability from normal vanilla producers remains unestablished; an equivalent received packet state reaches the client handler. This bounded review makes no claim about intermediate patches, full-pair coverage, runtime behavior, or tick parity.
