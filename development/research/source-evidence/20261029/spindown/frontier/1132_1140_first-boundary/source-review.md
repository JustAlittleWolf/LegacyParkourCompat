# 1.13.2 → 1.14 first-release movement boundary

## Assignment and limits

This is a bounded comparison of ordinary local-player input/tick/travel roots and selected direct client responses between the exact `1.13.2` and `1.14` releases. The release directory is named `1.14`; it is the first 1.14 release, not a claimed `1.14.0` source directory. Both sides use the same Ornithe Feather namespace, with exact build 2 artifacts. This report records source-visible differences and checked no-difference response methods; it does not establish trajectory, runtime parity, implementation readiness, or a full-pair freeze.

## Ordinary local-player input and tick

`LocalClientPlayerEntity.mobTick` polls and installs movement input before the inherited living-entity jump/travel phase (`1.13.2` lines 653 onward; `1.14` lines 619 onward). The keyboard axes and opposing-key cancellation remain the same. The input slowdown gate changes:

- In 1.13.2, `KeyboardInput.tick()` applies the 0.3 factor only when the freshly polled sneak key is down (`KeyboardInput.java:13–46`).
- In 1.14, `LocalClientPlayerEntity.mobTick()` computes `bl4 = m_63723874() || m_99544176()` before the keyboard poll, then calls `input.tick(bl4, isSpectator())` (`LocalClientPlayerEntity.java:619–632`). `KeyboardInput.tick(boolean, boolean)` applies 0.3 when the current sneak key **or** `bl` is true, unless the spectator argument is true (`KeyboardInput.java:13–26`).
- `m_63723874()` is false while flying; otherwise, when the sneaking pose fits, it is true for the existing sneak input or when the standing pose does not fit (`LocalClientPlayerEntity.java:596–598`; `Entity.m_87715359`, `Entity.java:1576`). `m_99544176()` is `isSwimming() && !isInWater()` (`Entity.java:1770–1772`). Thus the 1.14 input gate includes a non-flying forced-sneak/standing-clearance state and the just-left-water swimming pose, and explicitly exempts spectators. These predicates feed the input vector before travel and the later sprint thresholds. Applicability beyond these source gates is not a runtime claim.

## Movement math and climb gates

The inherited travel/move-relative operation changes representation and numeric procedure. In 1.13.2, `LivingEntity.moveRelative(float,float,float)` calls `Entity.updateVelocity(float,float,float,float)`; the latter accumulates a float squared-input magnitude, returns for `<1.0E-4F`, takes a float square root, and transforms float sideways/forward/upward inputs using float yaw sine/cosine before adding to the velocity fields (`Entity.updateVelocity`, `Entity.java:1057–1075`; `LivingEntity.java:1478 onward`). In 1.14 the caller supplies a `Vec3d`, and `Entity.updateVelocity(float,Vec3d)` delegates to `m_51093791`: it measures a double squared magnitude, returns below `1.0E-7`, conditionally normalizes the vector, scales it, rotates with float sine/cosine and adds the result through a vector setter (`Entity.java:1010–1027`). This is an exact source-level math/threshold change. Standard local input is keyboard-backed on both sides; this check did not establish an ordinary local witness entering the old `<1.0E-4F` cutoff, nor a trajectory result.

Ground travel also rewrites the acceleration factor. The 1.13.2 grounded branch uses `t = slipperiness * 0.91F`, then `getSpeed() * (0.16277137F / (t*t*t))`; it reads the same underfoot state again before applying horizontal friction after movement (`LivingEntity.java:1537–1558`). The 1.14 branch reads slipperiness once, computes `getSpeed() * (0.21600002F / (slipperiness*slipperiness*slipperiness))` in `m_70235197`, and uses `slipperiness * 0.91F` for friction (`LivingEntity.java:1832–1839, 1954–1956`). These formulas are structurally related but use different float operation order/constants; no numerical witness is claimed here.

For old-era climbing blocks, 1.13.2 sets the climbing boost after movement only under `collidingHorizontally && isClimbing()` (`LivingEntity.java:1576–1578`). In 1.14 the dry, non-fall-flying path sets the post-move vertical component to `0.2` under `(collidingHorizontally || jumping) && isClimbing()` (`LivingEntity.java:1837–1842`). The local player's inherited tick copies current input jumping into the living-entity `jumping` state before the travel phase (`LivingEntity.mobTick` and `LocalClientPlayerEntity.serverTickAi`). The `isClimbing` predicate in both releases recognizes ladder/vine and open trapdoor-over-matching-ladder, subject to spectator exclusion; 1.14 adds scaffolding, which is a new block and not part of this old-era comparison (`LivingEntity.java:1046–1065` vs `1232–1258`). The jump-OR-horizontal-collision source gate is a candidate operation difference for era-existing climbable states. Collision overlap and provider reachability are not closed by this report.

Other movement changes requiring separate closure include the full `Entity.move` collision pipeline rewrite (1.13.2 scalar deltas, `Entity.java:473`; 1.14 vector input and extracted movement helpers, `Entity.java:433`) and the changed unloaded-chunk/gravity preflight in `LivingEntity.moveRelative`. In the older client branch, gravity is withheld unless the chunk is both reported loaded and its retrieved chunk is loaded; the newer client branch only checks `!world.isChunkLoaded(blockPos)` before using the old Y fallback. The exact client chunk/cache implementation and collision dependencies were not closed here. New-only scaffolding handling is not treated as an old-profile feature.

## Selected direct client responses

- **Player position correction:** both `ClientPlayNetworkHandler.handlePlayerMove` methods resolve relative position/rotation against the local player, clear velocity components for absolute axes, call `updatePositionAndAngles`, acknowledge the teleport ID and send the same follow-up position packet (`1.13.2:621–657`; `1.14:650–704`). In 1.14, clearing axes is expressed by copying the delta vector, zeroing components, and setting it once; equal packet/current inputs yield the same velocity components. The newer handler additionally updates `prevX/prevY/prevZ` for relative/absolute axes before the same position update. This report does not treat that interpolation-history state as a physics delta.
- **Entity velocity:** the packet remains the three integer components divided by `8000.0` in `handleEntityVelocity`; `Entity.lerpVelocity` writes those same three resulting doubles in both versions (`ClientPlayNetworkHandler.java:507–512` / `535–540`; `Entity.java:1730–1734` / `1700–1702`).
- **Explosion knockback:** after the same `Explosion.damageBlocks(true)`, old code adds each packet float to the corresponding velocity field; 1.14 adds the three values to the current `Vec3d` and writes the resulting vector (`ClientPlayNetworkHandler.java:968–975` / `1037–1045`). The equal-input component operation is equivalent in source; this does not close explosion block/provider effects.
- **Abilities/effects/attributes:** selected `handlePlayerAbilities`, `handleEntityStatusEffect`, and `handleEntityAttributes` bodies match (`ClientPlayNetworkHandler.java:1537, 1396, 1934` / `1595, 1451, 2054`). They apply received values to the current client player/entity. Upstream packet production and effective tags/resources are not included.
- **Respawn:** the old handler delegates to `Minecraft.respawnPlayer`, which creates a replacement local player and calls `resetPos` (`ClientPlayNetworkHandler.java:944–965`; `Minecraft.java:1454–1483`). The 1.14 handler performs the same broad replacement/reset path inline and then explicitly sets the new player's yaw to `-180.0F` (`ClientPlayNetworkHandler.java:989–1033`); the old path does not assign yaw after `resetPos` (which resets velocity and pitch only, `Entity.java:260–277`). This is a source-visible direct player-state difference. Server packet order and whether a subsequent position correction overwrites it before movement are unresolved.
