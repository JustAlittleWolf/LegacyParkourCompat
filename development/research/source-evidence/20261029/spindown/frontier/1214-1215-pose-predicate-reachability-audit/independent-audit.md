# Independent source-only audit: 1.21.4 → 1.21.5 pose overlap

## Verdict

**Accept, bounded to the conditional local swimming/fall-flying overlap and pose-selection order.** The canonical source supports a local-player path in which both shared flags are true when pose selection runs, and the two releases choose different pose values. The path requires a dry fall-flying start, an unclimbable route into water, a sprinting player who reaches the underwater swimming gate, and the common swimming-fit guard to pass. The report is correct that sleeping overlap is not established. This audit makes no claim about a resulting position or trajectory difference, server packet production, collision-provider behavior, runtime parity, or full-pair coverage.

## Independent retrace

1. **Dry fall-flying start is local and immediate.** `LocalPlayer.aiStep` has the jump-edge, ability-toggle, and `!onClimbable()` gates before calling `Player.tryToStartFallFlying` (1.21.4 `LocalPlayer.java:749`, `Player.java:1528`; 1.21.5 `LocalPlayer.java:770`, `Player.java:1507`). That method requires `!isFallFlying()`, `canGlide()`, and `!isInWater()`, then directly calls `startFallFlying`; that setter writes shared flag 7 immediately (`Player.java:1537` / `:1516`). `LivingEntity.isFallFlying()` reads flag 7 (`LivingEntity.java:3277` / `:3268`). The later server command is not needed for this local source-state path.

2. **A source-reachable transition can preserve the flag while entering water.** A local player can start gliding in air with a usable glider, sufficient forward input and food, and no ground/passenger/levitation or climbable gate. The player then moves through a non-climbable route into water. `LivingEntity.travel` tests water/lava before the fall-flying branch in both versions (`LivingEntity.java:2189` / `:2213`), so once the player is in water it selects `travelInFluid`; that route does not call `stopFallFlying`. The fall-flying travel path only stops the flag on a climbable, which is excluded by the route condition here. `LivingEntity.updateFallFlying` clears the flag only inside its logical-server branch when `!canGlide()` (`:2825` / `:2815`); it has no water-specific clear. The client-side `updateFallFlying` path therefore does not clear it.

3. **The swimming flag can be set before the same tick's pose selection.** `LocalPlayer.tick` calls `Player.tick`; `Player.tick` calls `super.tick()` before `updatePlayerPose()` (`Player.java:283,329` / `:298,344`). The `Entity.tick` call reaches `Entity.baseTick`, which updates current fluid contact, refreshes eye-fluid state, then calls `updateSwimming` (`Entity.java:430–455` / `:438–463`). `updateSwimming` sets flag 4 when the player is sprinting, under water, not a passenger, and the block at its position has water (`Entity.java:1306–1313` / `:1336–1343`). `Player.updateSwimming` clears swimming only for ability-flight; otherwise it delegates (`Player.java:1479–1484` / `:1457–1462`). `isSwimming` reads flag 4, with `Player.isSwimming` additionally excluding spectator and ability-flight states (`Entity.java:2358` / `:2326`; `Player.java:1818` / `:1759`).

   The time order requires care: fluid contact and eye-fluid observations are refreshed in `baseTick`, before local AI and movement. A sufficient ordinary entry is a gliding, sprinting player whose eyes register in water before the body-contact tick; on a later base-tick, `wasEyeInWater` and current `isInWater` make `isUnderWater()` true while the block-position water gate passes. Forward input, enough food, and no shift keep the local swim-sprint stop gate false. With no passenger, spectator or ability-flight state, `updateSwimming` can therefore set flag 4 while flag 7 remains set. The report's conditional "sprinting/submerged" state is source-sufficient; the timing qualification above states how the local tick order reaches it without depending on a server producer.

4. **The selector difference is exact, with a common fit gate.** Both versions first check `canPlayerFitWithinBlocksAndEntitiesWhen(Pose.SWIMMING)` (`Player.java:435` / `:450`). In 1.21.4 `updatePlayerPose` chooses fall-flying before sleeping and swimming (`:434–444`); in 1.21.5 `getDesiredPose` checks sleeping and swimming before fall-flying (`:465–476`). Under the reachable overlap with `isSleeping()==false`, old selects `FALL_FLYING` and new selects `SWIMMING`. The `POSES` maps give both poses identical `0.6F × 0.6F` dimensions and `0.4F` eye height on both endpoints (`Player.java:142–143` / `:143–144`). If the common swimming-fit query passes, the old desired-pose fit query passes for the same box and position, so the crouching/swimming fallback does not erase the selected-pose difference.

5. **Sleeping remains unproven.** The selectors establish precedence for a simultaneous sleeping/fall-flying state, but this review did not trace sleep-entry or received state producers. I accept no claim that such an overlap is reached in ordinary local play.

## Limits

The finding is a conditional difference in the selected `Pose` value. Since the two relevant pose dimensions and eye heights are equal, this report does not infer a body-box, eye-position, collision, or trajectory difference from pose selection alone. The common fit gate is assumed true for the claimed conditional; no `noCollision` provider or shape implementation was inspected. A compatible plain open-water state suffices for that gate, but no environmental witness or runtime execution is claimed. Packet/server synchronization after the local flag write is also outside this source-only audit.
