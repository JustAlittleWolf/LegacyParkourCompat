# 1.21.1 → 1.21.2 fluid-travel dependency closure

## Bounded verdict

For an ordinary, nonflying local player in a non-debug level, the 1.21.1 and 1.21.2 water/lava travel calculations are source-equivalent when the same current movement vector, fluid flags/heights, attributes, effects, input vector, and movement/collision results are supplied. 1.21.2 factors the branches into `LivingEntity.travelInFluid`; it does not change the water or lava arithmetic, the fluid-height scan, or the final fluid collision-bounce predicate in the checked methods.

This is a bounded source comparison, not pair closure or runtime/trajectory evidence. The water-efficiency, movement-speed, and gravity attribute registry keys change names between endpoints, packaged fluid-tag membership is outside these Java trees, and collision/provider inputs remain unclosed. A separate `Player.travel` swim-assist query also changes accessor; its ordinary-world source path agrees, with a debug-level caveat recorded below.

## Fluid-branch order and dependencies

`Player.travel` in 1.21.1 applies the swim-look vertical adjustment only when swimming and not a passenger, then calls `LivingEntity.travel`; 1.21.2 puts passenger handling outside the remaining branch but reaches the same inherited fluid travel for a nonpassenger. `LivingEntity.travel` in both releases requires `isControlledByLocalInstance()`. The local-player path is eligible through `Entity.isControlledByLocalInstance()` and `Player.isLocalPlayer()`; remote, non-locally-controlled entities do not run this travel calculation. `Player.isAffectedByFluids()` is unchanged and returns `!abilities.flying`; base `LivingEntity.canStandOnFluid` is unchanged and returns false, with no `Player` override.

The 1.21.1 dispatcher tests water first, then lava, then fall-flying/air. The 1.21.2 dispatcher tests `(isInWater() || isInLava())`, then calls `travelInFluid`, whose inner `if (isInWater()) ... else ...` preserves water priority when both flags are true. When the local player is not affected by fluids or can stand on the current fluid, both versions skip fluid travel. `Player` disables fluid travel while flying; for a flying local player both versions therefore pass to the later branch.

Under the same fluid and attribute/effect inputs, the water branch preserves this order and math in both versions: choose sprint slowdown `0.9F` or `getWaterSlowDown()` (`0.8F`); start acceleration at `0.02F`; cast water-movement-efficiency attribute value to `float`, halve it off-ground, and for positive efficiency blend slowdown toward `0.54600006F` and acceleration toward `getSpeed()`; override slowdown with Dolphins Grace `0.96F`; `moveRelative`, then `move(SELF, deltaMovement)`; raise Y to `0.2` on horizontal collision while climbable; multiply X/Z by slowdown and Y by `0.8F`; apply fluid-falling adjustment; finally perform the same horizontal-collision/free-space bounce, setting Y to `0.3F`. In 1.21.1 the scaled vector is stored and re-read before fluid-falling adjustment; in 1.21.2 it is held in a local vector and stored after adjustment. The unchanged `Entity.setDeltaMovement(Vec3)` is a direct field assignment, and the helper returns the same vector for the same inputs, so this factoring does not change the computed fluid-branch vector.

The lava branch preserves `moveRelative(0.02F)` and `move(SELF, deltaMovement)`. When cached `getFluidHeight(FluidTags.LAVA) <= getFluidJumpThreshold()`, both versions multiply `(0.5, 0.8F, 0.5)` and apply fluid-falling adjustment; otherwise both scale by `0.5`. Both then apply `-gravity / 4.0` to Y only when gravity is nonzero, followed by the same `horizontalCollision && isFree(x, y + 0.6F - currentY + preMoveY, z)` bounce. 1.21.1 captures the pre-move Y separately in each medium branch; 1.21.2 captures it once at the start of the helper, before either medium moves.

`getFluidFallingAdjustedMovement` is token-identical across the two source versions: when gravity is nonzero and not sprinting, falling near the `0.005` / `gravity / 16.0` thresholds may set Y to `-0.003`; otherwise it subtracts gravity/16. The old inline gravity selection (`getGravity()`, with slow-falling clamp to `0.01` only for `deltaMovement.y <= 0.0`) is token-equivalent to 1.21.2 `getEffectiveGravity()`. The water/lava helper, gravity calculation, cached fluid inputs, and final vector setter do not establish a branch-specific arithmetic delta.

Exact whitespace-normalized method bodies matched for `Entity.isInWater`, `isInLava`, `getFluidHeight`, `getFluidJumpThreshold`, `updateFluidHeightAndDoFluidPushing`, `touchingUnloadedChunk`, and `setDeltaMovement(Vec3)`; `LivingEntity.isAffectedByFluids`, `canStandOnFluid`, `getWaterSlowDown`, `getFluidFallingAdjustedMovement`; `Player.isAffectedByFluids`; `Level.getFluidState`; `LevelChunk.getBlockState` and both `getFluidState` overloads; `LevelChunkSection.getFluidState`; and the relevant `FluidState.isEmpty`, `getHeight`, `getFlow`, and `is(TagKey<Fluid>)` methods. `FluidTags.WATER` and `.LAVA` keys are unchanged. The fluid-height scan still obtains the same shrunken bounding box and floored/ceiled block range, reads each `FluidState`, tests the tag, gets height/flow, and stores the same cached tagged height. Actual tag membership remains a resource/data-pack input, not proven by these Java trees.

## Direct inputs and remaining gates

The branch reads current player delta movement, local `isInWater`/`isInLava` flags and cached lava height, current fluid state at `blockPosition()`, input vector and yaw through `moveRelative`, sprint/on-ground state, current movement speed, water-efficiency/gravity attributes, Slow Falling and Dolphins Grace, fluid tags/heights, climbable/horizontal-collision state, and `isFree` collision queries. With equal received/effective values, checked calculations match. The effect registry source is identical; fluid-tag key declarations are identical, but the packed tag contents are unverified.

`Attributes` renames the registry keys used here: `generic.gravity` → `gravity`, `generic.movement_speed` → `movement_speed`, and `generic.water_movement_efficiency` → `water_movement_efficiency`. The corresponding numeric base/default/range/sync settings are unchanged (`0.08`, `0.7`, and `0.0`, respectively). This source diff changes which registry identities name the read attributes; equal attribute values are a comparison assumption, and server/resource/attribute-state translation is not closed here.

Adjacent to the inherited water calculation, `Player.travel` changes its swim-look query at `(x, y + 1.0 - 0.1, z)` from `level.getBlockState(pos).getFluidState().isEmpty()` to `level.getFluidState(pos).isEmpty()`. In ordinary, in-height levels, both resolve the same chunk section state: `Level.getFluidState` uses the same `getChunkAt` path; `LevelChunkSection.getFluidState` reads the fluid state from the same stored block-state palette. The query can affect the pre-travel upward swim assist only when swimming, not a passenger, looking upward, not jumping, and the queried cell is empty. A special case remains: `LevelChunk.getBlockState` synthesizes debug-level states while `LevelChunk.getFluidState` reads the stored section fluid state. The two access paths can therefore differ in a debug level; applicability to ordinary parkour worlds is not established by this assignment.

Unclosed dependencies: packaged fluid-tag membership and data-pack overrides; meaning/arrival of the renamed gravity, movement-speed, and water-efficiency attributes; fluid-height refresh inputs when tags/resources differ; `move` collision response, climbable providers, `isFree`, and query shapes; and the debug-level swim-assist exception. This report makes no claim about packet producers, historical resource payloads, pair-wide movement coverage, runtime behavior, or implementation readiness.
