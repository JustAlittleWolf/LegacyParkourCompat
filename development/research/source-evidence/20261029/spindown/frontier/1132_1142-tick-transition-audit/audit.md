# Independent source-only audit: 1.13.2 → 1.14.2 local-player tick transition

## Verdict

The exact source identity and selected source-map bindings in the submitted report are verified. The source supports the sprint-stop threshold difference, the forced-sneak keyboard slowdown input, the float-to-double movement-input normalization change, and the added `jumping` alternative in the post-move climbing boost. The climbing predicate/provider and collision reachability still limit that claim.

I reject the report's claimed ground-friction sampling phase difference: the 1.13.2 support samples both occur before its movement call. The 1.14.2 support sample also occurs before movement. The report therefore does not establish an old-post-move versus new-pre-move sample boundary. The acceleration-factor expressions are written differently and were not numerically compared here; do not treat the broader ground-acceleration operation as closed.

This is a bounded source audit, not a pair freeze, runtime/trajectory result, or implementation-readiness decision.

## Claim checks

1. **Sprint stop — supported with the report's stated gates.** In 1.13.2 `LocalClientPlayerEntity.mobTick`, after keyboard input refresh, a sprinting player is stopped when `movementForward < 0.8F` or the food/flying condition fails; horizontal collision and shallow-water conditions are additional stop gates. `KeyboardInput.tick()` scales forward input to `0.3F` when sneak is held. In 1.14.2, the corresponding stop gate uses `!input.method_20622()` where the helper returns `movementForward > 1.0E-5F`; with forward+sneak input, that predicate is true after the same `0.3F` slowdown. For an already-sprinting, non-swimming player with adequate food, no item-use/blindness stop, and no horizontal collision, the older `<0.8F` gate stops sprint while the newer positive-forward gate does not. The report correctly treats this as a source-level gate consequence, not a demonstrated trajectory.

2. **Forced-sneak pose slowdown — supported, subject to pose admission.** The 1.13.2 keyboard provider applies the factor only when the sneak key is pressed. The 1.14.2 player passes `isInSneakingPose() || shouldLeaveSwimmingPose()` into `Input.tick`; `KeyboardInput.tick(bl, spectator)` applies the factor when the player is not a spectator and either the sneak key or `bl` is true. `isInSneakingPose()` can be true without the key when standing pose cannot be admitted. This supports the bounded direct-input difference. The actual pose/collision admission is not audited here; the report's exclusion of the swimming-exit leg avoids expanding this claim.

3. **Ground-friction sample phase — not supported as reported.** In 1.13.2 `LivingEntity.moveRelative`, the first support lookup is at line 1542. The second lookup resets the same pooled position from the current `x`, bounding-box `minY - 1`, and `z` at lines 1555–1557. Both are before the old movement call at line 1575; the horizontal friction multiplication follows afterward. Thus the second read is not after movement and does not use updated coordinates. In 1.14.2 the support block is read at line 1825, then input velocity is computed and `move(...)` is called at line 1829; the previously computed horizontal factor is applied at line 1849. Both sampled positions are pre-move. The report's crossing-block/leave-support timing witness does not follow from these methods. The coefficients are expressed as `0.16277137F / (slipperiness * 0.91F)^3` in the older path and `0.21600002F / slipperiness^3` in the newer helper; this audit did not establish bitwise/numerical equivalence of those float expressions, so that separate arithmetic question remains open.

4. **Input normalization — supported as a math-path difference.** The 1.13.2 `Entity.updateVelocity(float,float,float,float)` computes squared length, square root, normalization, scaling and yaw rotation in float variables, with a `1.0E-4F` squared-length cutoff. The 1.14.2 overload calls `movementInputToVelocity(Vec3d, float, float)`, which calculates squared length and normalization from double vector components, uses a `1.0E-7` cutoff, then rotates the result. Digital keyboard diagonal values exceed both cutoffs. The changed calculation path is source-confirmed; the report appropriately does not claim a measured output difference for a particular trajectory.

5. **Climbing boost — gate change supported; applicability conditional.** After movement, 1.13.2 assigns vertical velocity `0.2` only when `collidingHorizontally && isClimbing()`. The 1.14.2 travel path uses `(horizontalCollision || jumping) && isClimbing()` before the same `0.2` assignment and shared vertical continuation. This confirms the added jump alternative at the call site. The two `isClimbing()` providers are not proven equivalent: old code floors `x`, shape `minY`, and `z`, while new code reads `new BlockPos(this)` and recognizes a different set of constants. Whether the no-horizontal-collision overlap is reachable on equivalent old-era climbing states depends on those provider/position and collision gates, which remain open.

## Other checked slices and boundaries

The cited jump gate has matching shallow-water/lava/ground and cooldown structure at the two endpoints. Base jump behavior retains `0.42F`, jump-boost addition, and sprint impulse components in the checked methods. This verifies only those cited slices, not every path through the broader travel methods.

The report correctly separates server teleport producers from client received-state responses. Its `ClientPlayNetworkHandler` hashes match the two source maps. The cited client handlers apply received position/velocity/explosion state; those packet inputs are distinct from the local tick candidates reviewed above. This audit did not close server velocity production or other packet producers.

Remaining dependencies include old/new climbable block-provider and position semantics, collision-produced horizontal/on-ground flags, exact ground acceleration-factor arithmetic, and the report's unexamined pose/fluid/modifier/callback inventory. No complete pair coverage or runtime result follows from the present claims.
