## Tick and movement roots examined

The local-player wrappers are `LocalClientPlayerEntity.tick()` (1.13.2 `:181–199`) and `ClientPlayerEntity.tick()` (1.14.2 `:172–190`); each calls its superclass before sending movement state. In 1.13.2 `LivingEntity.tick()` enters the overridable `mobTick()` path (`:1689`, `:1852`), where `LocalClientPlayerEntity.mobTick()` updates input before calling `super.mobTick()` (`:653–842`). In 1.14.2 `LivingEntity.tick()` enters `tickMovement()` (`:1962–2029`); `ClientPlayerEntity.tickMovement()` processes input and then calls `super.tickMovement()` (`:607–766`), followed by `PlayerEntity.tickMovement()` and the `LivingEntity.tickMovement()` jump/travel path (`:475–535`, `:2133–2220`).

### Candidate movement differences

1. **Sprint can persist at sneak-scaled forward input.** In 1.13.2, `LocalClientPlayerEntity.mobTick()` stops sprint in the non-swimming branch when `input.movementForward < 0.8F` (`:748–757`). The keyboard input provider scales a held sneak input by `0.3` first (`KeyboardInput.java:44–49`, called at `LocalClientPlayerEntity.java:698–704`). In 1.14.2, the equivalent stop gate uses `!input.method_20622()` (`ClientPlayerEntity.java:667–675`), and the helper returns `movementForward > 1.0E-5F` (`Input.java:22–24`). With a forward+sneak keyboard input (`movementForward == 0.3F`), an already-sprinting player on dry ground with no horizontal collision remains sprinting through this forward-input gate in 1.14.2, while 1.13.2 stops sprint. Other stop gates still apply. This can preserve sprint movement speed while the input vector is sneak-scaled.

2. **Keyboard slowdown also follows forced sneaking pose.** 1.13.2 `KeyboardInput.tick()` applies the `0.3F` scalar only when the sneak key is pressed (`:13–49`). 1.14.2 `ClientPlayerEntity.tickMovement()` passes `isInSneakingPose() || shouldLeaveSwimmingPose()` into `Input.tick(...)` (`:614–619`); `KeyboardInput.tick(bl, bl2)` scales when `!bl2 && (sneaking || bl)` (`:13–25`). The new `bl` path therefore also scales movement when the player is in a forced sneaking pose without the sneak key. That can alter acceleration below an overhead obstruction. I do not claim the swimming-exit leg here; the assigned 1.13.0 first-stable swimming-gate report is intentionally not duplicated. The pose admission call depends on pose/collision checks; collision/shape internals remain with the collision lane.

3. **Ground drag samples slipperiness at different points in the tick.** 1.13.2 `LivingEntity.moveRelative()` samples the support block before movement for ground acceleration (`:1537–1554`), then samples again after `move(...)` at the updated `x/z` before multiplying horizontal velocity by friction (`:1555–1600`). 1.14.2 `LivingEntity.travel()` samples slipperiness and derives `w` before movement (`:1823–1829`), then uses that same `w` for horizontal drag after movement (`:1849`). Crossing from one block slipperiness to another during a grounded move, or leaving support, can therefore leave a different horizontal velocity for the following tick. This is a player-visible movement candidate on era-existing blocks; the collision result/`onGround` producer is an unresolved dependency, and its implementation was not analyzed.

4. **Movement-input normalization changed from float to double arithmetic.** 1.13.2 `Entity.updateVelocity(float,float,float,float)` accumulates squared components, takes a float square root, clamps length and scales each float component before yaw rotation (`:1057–1074`). 1.14.2 `Entity.updateVelocity(float,Vec3d)` calls `movementInputToVelocity`, whose squared length, normalization and multiplication are performed through `Vec3d` double components, with a lower squared-length cutoff (`:1011–1025`). The same diagonal keyboard input is widened from float component values and normalized with double precision in 1.14.2 rather than the 1.13.2 float procedure; the resulting acceleration may differ by rounding. The legacy float cutoff is `1.0E-4F`, versus `1.0E-7` squared in the newer helper; ordinary keyboard inputs are above both cutoffs, so no low-magnitude keyboard reachability claim is made.

5. **Climbing vertical boost adds a jump gate.** 1.13.2 applies the post-move climb boost only for `collidingHorizontally && isClimbing()` (`LivingEntity.java:1575–1578`). 1.14.2 applies it for `(horizontalCollision || jumping) && isClimbing()` (`LivingEntity.java:1887–1894`). If a player is climbing, jumping and has no horizontal collision, 1.14.2 sets the intermediate vertical velocity to `0.2` before the shared levitation/gravity/drag continuation, while 1.13.2 does not take this boost branch. Reachability of that exact no-horizontal-collision overlap on the old climbing blocks remains open pending the collision lane; this is a source-confirmed gate difference, not a runtime trajectory claim.

### Checked without an independent finding

- The common jump/cooldown order remains: water-height gate at `0`/`0.4`, lava upward response, then ground-or-shallow-water jump when cooldown is zero, with a ten-tick reset; compare 1.13.2 `LivingEntity.java:1903–1917` with 1.14.2 `LivingEntity.java:2187–2201`.
- The base jump result remains `0.42F`, jump boost adds `0.1F * (amplifier + 1)`, and sprint jump impulse is `-sin(yaw)*0.2F` / `cos(yaw)*0.2F`; compare 1.13.2 `LivingEntity.java:1451–1464` and `PlayerEntity.java:1431–1439` with 1.14.2 `LivingEntity.java:1739–1755` and `PlayerEntity.java:1351–1359`. The Player method also updates statistics/exhaustion, outside movement output scope.
- Keyboard direction signs and the jump/sneak key reads are equivalent for digital directional inputs; the differences above are in the slowdown predicate and forward-sprint stop predicate.
- The movement API shifts from `moveRelative(sidewaysSpeed, verticalSpeed, forwardSpeed)` (1.13.2 `LivingEntity.java:1920–1926`) to `travel(new Vec3d(sidewaysSpeed, upwardSpeed, forwardSpeed))` (1.14.2 `LivingEntity.java:2204–2211`) and `PlayerEntity.travel()` (`:1362–1390`). The swim vertical-control portion is not restated as a separate claim.

## State provenance and boundary classification

- **Server producers:** 1.13.2 `ServerPlayNetworkHandler.teleport()` (`:801–814`) builds `PlayerMoveS2CPacket`; 1.14.2 `ServerPlayNetworkHandler.teleportRequest()` (`:808–821`) builds `PlayerPositionLookS2CPacket`. These are server-produced correction events, not locally generated movement. The server movement loop was not compared. An older-version server velocity-packet sender was not closed in this slice.
- **Direct received-state client responses:** 1.13.2 `ClientPlayNetworkHandler.handlePlayerMove()` (`:621–670`) applies absolute/relative coordinates, clears velocity on absolute axes and acknowledges the teleport. 1.14.2 `ClientPlayNetworkHandler.onPlayerPositionLook()` (`:642–694`) performs the corresponding client correction/ack path; `onVelocityUpdate()` applies received velocity (`:529–535`) and `onExplosion()` adds received player impulse (`:1020–1026`). These are external response inputs and are not attributed to the ordinary local-player tick findings above.
- **Collision-owned dependencies:** `Entity.move()` supplies collision flags and the `onGround` value consumed by the travel/jump branches; support-block/shape access is also involved in friction sampling. I enumerated these dependencies but did not inspect collision, shape or DDA bodies. `isClimbing()` is a non-collision provider that also changed: 1.13.2 checks the block at floored `x`, bounding-box `minY`, `z` and recognizes ladder/vine plus its trapdoor predicate (`LivingEntity.java:1046–1058`); 1.14.2 reads `method_16212()` and checks three block constants plus its trapdoor predicate (`:1222–1240`). The extra constant and exact position equivalence are left unresolved rather than guessed.
- The target is a bounded endpoint comparison only. This report does not establish the exact patch where any change entered, complete pair coverage, closed dependencies, independent audit, finding acceptance or runtime parity.
