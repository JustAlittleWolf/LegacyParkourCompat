## Compared slices and classification

- **Local client tick / flight activation**: `LocalClientPlayerEntity.java`, `tick()` and the fall-flying action path. In 1.9→1.9.1, the only change there is starting `ElytraOnPlayerSoundInstance` immediately after sending START_FALL_FLYING (1.9.1 line 708; corresponding 1.9 line 707). This is audio-only, not a player movement state/response change. The 1.9.2→1.9.3 diff in this class adds nullability metadata and does not change tick/movement statements; 1.9.3 and 1.9.4 are byte-identical for this class.
- **Generic entity collision movement**: `entity/Entity.java`, `move(double,double,double)` including sneak edge reduction, ordered Y/X/Z clipping, step-height alternative and collision-box application (1.9.2 Entity.java line 438; 1.9.3 Entity.java line 441). The compared bodies are identical. This is a source-body review, not a runtime parity claim.
- **Client and living/player movement**: `ClientPlayerEntity.java`, `LivingEntity.java`, and `PlayerEntity.java`. 1.9.2→1.9.3 changes in these classes are nullability annotations/signatures and UUID/NBT plumbing; no movement/tick/jump/travel arithmetic changes appeared in the diffs. 1.9.3→1.9.4 PlayerEntity only advances its NBT DataVersion constant. For 1.9→1.9.1, LivingEntity adds armor-toughness damage handling and guards world-border damage when damage-per-block is nonpositive; this concerns damage calculation (excluded scope), with no movement method delta. It also registers the armor-toughness attribute.
- **Block collision dispatch**: `World.getCollisions(Entity, Box)` still iterates the same expanded block-coordinate bounds in the same order and calls `BlockState.addCollisions`; the block-state forwarding method still invokes `Block.addCollisions`, which obtains `state.getCollisionShape(world,pos)`, translates that box by block position, and intersects/adds it. Compared sources: World.java around lines 893-1008 (1.9.2) / 899-1015 (1.9.3), Block.java around lines 313-328 / 337-353, and StateDefinition.java around lines 348-359 / 359-370. API additions/deprecation and nullable metadata are visible, but the shape-forwarding math/body is unchanged. Neighbor callback dispatch in 1.9.3 is routed through `BlockState.neighborChanged` to `Block.neighborChanged`; the callback signature is reordered and the body simply forwards, with no direct movement effect established.
- **Representative shape/effect providers**: `SoulSandBlock.getCollisionShape` returns the same static shape in both versions; `IceBlock` changes only nullable annotations on its mining callback; `LadderBlock.neighborChanged` reorders arguments while retaining the same survival check/drop/removal sequence. No shape value delta was found in these reviewed providers.
- **Flowing-liquid provider**: 1.9.2 `FlowingLiquidBlock` calls `getLiquidState(world,pos.up())` twice in the same branch; 1.9.3 stores one result from `getLiquidState(world.getBlockState(pos.up()))`. `LiquidBlock.getLiquidState` correspondingly accepts `WorldView, BlockPos` and reads the state twice in 1.9.2, versus accepting a captured `BlockState` and reading its material/LEVEL in 1.9.3. The adjacent-state check therefore removes redundant reads, with no state write between them in this path; no changed liquid result or direct movement consequence is established. Other `getLowestDepth` call sites similarly pass a single state. This source difference should remain a candidate until the exact source provenance gap is closed; do not promote it as a finding based on aliases alone.
- **World bounds candidate, 1.9.2→1.9.3**: `World.contains` is refactored to use `isOutsideWorldHeight`; `isChunkLoaded(BlockPos,...)` stops checking the old combined horizontal-and-vertical bounds; and `getBlockState`/`setBlockState` switch to height-only bounds (1.9.3 World.java lines 170, 173, 186, 248, and 621-624; corresponding 1.9.2 methods begin at lines 180, 240, and 614). This is a real world-access behavior change at horizontal coordinates outside `[-30,000,000, 30,000,000)`. The normal player collision route also consults WorldBorder and substitutes stone at border crossings (World.java `getCollisions` above), so no normally reachable movement path is established here. Exact reachability/dependency tracing for outside-border entity states and the missing `.2`/`.3` source provenance remain open; this is not an accepted movement finding.
