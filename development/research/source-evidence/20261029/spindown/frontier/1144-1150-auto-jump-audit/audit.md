# Independent source audit: 1.14.4 → 1.15 auto-jump correction

## Verdict

The correction to the sneak/stay-surface gate is confirmed for the local player: 1.15's `isStayingOnGroundSurface()` virtually calls `isShiftKeyDown()`, and `LocalPlayer` overrides that method to read current `input.shiftKeyDown`. The old 1.14.4 local gate reads current `input.sneakKeyDown` through `isSneaking()` → `isTryingToSneak()`. It is not a shared-entity-flag difference on this local-player path.

The 1.15 eligibility expression adds `getBlockJumpFactor() >= 1.0`; the existing enabled, timer, on-ground, passenger, and nonzero-input gates remain. The candidate/reference Y operands also change from AABB `minY` to entity Y in the stated points and rise comparisons. However, the supplement's statement that scan arithmetic otherwise retains the same source-level procedure is incomplete: its inverse-square-root call resolves to a different overload with a different approximation algorithm. Numeric equivalence and trajectory effect are unproven. Collision/provider dependencies remain open. This is a bounded audit, not pair-coverage acceptance.

No Yarn staging source was used as evidence.

## Retraced gates and input dispatch

- 1.14.4 `LocalPlayer.updateAutoJump` (`LocalPlayer.java:856-861`) gates on auto-jump enabled, timer, `onGround`, `!isSneaking()`, `!isPassenger()`, then either nonzero component of `input.getMoveVector()`. `LocalPlayer.isSneaking()` delegates to `isTryingToSneak()` (`:583-590`), which reads `input.sneakKeyDown`. `LocalPlayer.aiStep()` calls `input.tick(...)` before inherited travel (`:625-630,772`); `KeyboardInput.tick()` fills `sneakKeyDown` from the sneak key (`KeyboardInput.java:13-24`).
- 1.15 `LocalPlayer.canAutoJump` (`LocalPlayer.java:962-975`) checks enabled, timer, `onGround`, `!isStayingOnGroundSurface()`, `!isPassenger()`, `isMoving()`, then `getBlockJumpFactor() >= 1.0`. `isMoving()` is the same disjunction of input-vector components against `0.0F` as the old inline gate. In `Player.java:294-296`, `isStayingOnGroundSurface()` returns `this.isShiftKeyDown()`. That call is virtual. The only 1.15 declaration of `isStayingOnGroundSurface()` is in `Player`, and `LocalPlayer.java:591-593` overrides `isShiftKeyDown()` to return `input != null && input.shiftKeyDown`; `Entity.java:1783-1785`'s shared-flag implementation is therefore not selected for a `LocalPlayer`. Local AI refreshes input before travel (`LocalPlayer.java:632-636,778`), and `KeyboardInput.tick()` writes `shiftKeyDown` from the shift key (`KeyboardInput.java:13-25`).
- In both `LocalPlayer.move` methods, `super.move(...)` precedes the auto-jump scan (`1.14.4 LocalPlayer.java:845-850`; 1.15 `:851-856`), so the gate observes the post-super-move `onGround`. The supplement's short-circuit gate ordering and same-position movement-vector comparison are source-confirmed.
- The additional 1.15 predicate calls `Entity.getBlockJumpFactor()` (`Entity.java:584-588`), which checks current and support block jump factors. This audit does not close jump-factor producers/registrations or old-side applicability.

## Scan operands and arithmetic

- Confirmed point operands: 1.14.4 uses AABB `minY` for candidate start/end points (`LocalPlayer.java:861-862`) and for both rise comparisons (`:927-930,946-949`); 1.15 uses `position()`/entity Y for those operands (`:864-866,931-934,950-953`). Both retain the initial block probe at AABB `maxY` (`1.14.4 :884-889`; 1.15 `:888-893`). These are operand changes only; numeric equality under pose/dimension/bounds transitions is not established.
- Additional arithmetic change omitted from the supplement: 1.14.4 `LocalPlayer.java:878` effectively assigns `float n = (float) Mth.fastInvSqrt(i)`. The 1.14.4 `Mth.java` exposes only `fastInvSqrt(double)` (`:395-403`), so `i` is widened to double, the double approximation is evaluated, then cast to float. In 1.15, the same call `float n = Mth.fastInvSqrt(i)` (`LocalPlayer.java:882`) selects `fastInvSqrt(float)` (`Mth.java:394-400`), which uses a 32-bit float bit approximation; the older double overload remains separately available. The method bodies use different bit widths/constants and float-vs-double intermediates. Thus it is incorrect to say that scan math otherwise retains the same source-level procedure. This identifies a source-level changed operand type/algorithm, not a demonstrated movement delta.
- I found no other change in the examined scan body that alters the listed thresholds/order beyond the documented Y operands and the inverse-square-root overload: fallback direction, dot threshold, reach expression, AABB inflation, edge offset, collision enumeration, obstacle height/effect allowance, and timer acceptance are structurally retained. `getX()/getZ()` replace direct field reads at the block probe; the accessors return those coordinates, so no distinct numeric change is shown there.

## Remaining gates

Collision-shape provider behavior and collision aggregation/iteration, `onGround` production, pose/dimension and bounding-box synchronization, jump-factor block providers and old-side applicability remain unclosed. The change from AABB minimum Y to entity Y and the changed normalization approximation both have unproven numerical equivalence/effect. No runtime trajectory conclusion follows.
