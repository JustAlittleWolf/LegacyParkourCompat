## Verdict

The landing-specific finding is supported. In 1.10.2, a gated server-side farmland trampling callback changes the block state to dirt; in 1.11, the callback instead calls `setDirt`, which changes the state and moves intersecting entities to the dirt collision box's `maxY`. The callback's side and entity gates are unchanged across the four releases. The 1.11.1 and 1.11.2 farmland files are identical.

For this landing conversion, no immediate `ServerPlayNetworkHandler.teleport` or `PlayerMoveS2CPacket` send is called by `setDirt`. Any later server correction is conditional. On the receiving client, `handleBlockUpdate` delegates to `ClientWorld.setBlockStateFromPacket`; the latter's `WorldChunk.setBlockState` callback calls `Block.onAdded` only when `!world.isClient`, so this incoming block update does not invoke the farmland `onAdded` reposition path on the client. An inbound `PlayerMoveS2CPacket` instead reaches the local player's `updatePositionAndAngles`; that handler is identical in all four releases. Thus equal position packet values take the same client handler path in all four versions.

Correction to the author report's helper-caller inventory: 1.11.1 and 1.11.2 add `FarmlandBlock.onAdded` (lines 105–109), which also calls `setDirt` if the block above is solid. This call is server-only in effect because `WorldChunk.setBlockState` guards `onAdded` with `!world.isClient` (line 464–466). It does not alter the landing-specific conclusion or make the inbound client block update reposition the local player. The report's two other helper callers—dry farmland decay and `neighborChanged`—are also present as stated.

## Trace and call order

- Farmland collision shape is unchanged: `SHAPE = new Box(0,0,0,1,0.9375,1)` and `getShape` returns it (`FarmlandBlock.java`: 1.10.2 lines 21–33; 1.11+ lines 19–31).
- 1.10.2 `onFallenOn` at lines 61–70 requires server side, random float `< fallDistance - 0.5F`, living entity, player or `mobGriefing`, and `width * width * height > 0.512F`; it writes dirt and then calls `super`. It has no position write.
- 1.11 / 1.11.1 / 1.11.2 `onFallenOn` at lines 59–68 has the same gate and call order, but calls `setDirt`. The helper at lines 71–79 writes dirt, obtains `blockState.getCollisionShape(world, pos).move(pos)`, queries entities in that box, then calls `entity.setPosition(entity.x, box.maxY, entity.z)` for each. The callback has no further landing-specific logical-side branch beyond `!world.isClient`.
- The common entity landing callback is reached only for `landed` and `fallDistance > 0.0F` (`Entity.checkFallDamage`: 1.10.2 lines 808–818; 1.11 lines 830–840; 1.11.1 lines 880–890; 1.11.2 lines 873–883). Server player `handleFall` resolves the supporting state and calls `super.checkFallDamage` (`ServerPlayerEntity`: 1.10.2 lines 581–598; 1.11 lines 585–602; 1.11.1/1.11.2 lines 606–623).
- Server `handlePlayerMove` calls `player.handleFall(...)` near its end, after the movement and collision/correction branches, then records `lastGoodX/Y/Z` (`ServerPlayNetworkHandler`: call and save at 1.10.2 lines 480–483; 1.11 lines 482–485; 1.11.1/1.11.2 lines 487–490). The handler includes earlier explicit `teleport(...)` branches. `teleport(...)` itself creates and sends a `PlayerMoveS2CPacket`; the farmland helper does not call this routine or create/send that packet. This establishes no immediate teleport packet from the helper, not that a later correction cannot occur.
- `ClientPlayNetworkHandler.handleBlockUpdate` only ensures client-thread handling and invokes `world.setBlockStateFromPacket` (`ClientPlayNetworkHandler`: 1.10.2 lines 644–647; later lines 657–660). `ClientWorld.setBlockStateFromPacket` clears a pending block reset and invokes `super.setBlockState(pos, state, 3)` (`ClientWorld.java`: lines 237–243 in all four). `WorldChunk.setBlockState` only calls `block.onAdded` when `!world.isClient` and the block instance changes (lines 464–466 in all four). It therefore does not invoke the newer farmland's `onAdded` repositioning on the local client when this packet updates the block.
- `ClientPlayNetworkHandler.handlePlayerMove` resolves relative coordinates against the local player, zeros velocity on absolute axes, calls `playerEntity.updatePositionAndAngles(d,e,f,g,h)`, then acknowledges the teleport and sends a client position packet. The complete extracted method body has the same SHA-256 `0938d46b9efb4eb3eca4ec195b747c09c43156079ddcb926aff87a5ad79a381c` in all four source files. The complete `handleBlockUpdate` body likewise matches across all four (`2e0586e3c1bdc3b9077cdbd41d97793d821358137cb6374f4c66aff6e261239a`); `PlayerMoveS2CPacket.java` itself is also byte-identical across the four (`8bad09e146ce746085103081b7e3c6d09855114868267e12be8d869f34f0e77e`).
