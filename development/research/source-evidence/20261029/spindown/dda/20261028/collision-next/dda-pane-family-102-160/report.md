# 1.8.9 pane provider and state alias closure: IDs 102 and 160

## Result

Source closure is complete for the two requested registered block families and their state/color aliases. The evidence does **not** establish whole DDA traversal parity or universal current-neighbor equivalence. It establishes that the historical provider is live-neighbor-driven and writes mutable block bounds, that the pane's historical ray-trace path recomputes those bounds, and that current pane collision geometry is selected from stored connection properties. A future provider must preserve the historical query-time connection predicate and geometry where selected; a stored modern pane shape cannot be assumed equivalent for arbitrary neighborhoods.

## Old block identities and state

The canonical 1.8.9 `Block.java` registry registers ID 102 as `glass_pane` (`Block.java:1041`) and ID 160 as `stained_glass_pane` (`:1180`). ID 102 constructs `PaneBlock(Material.GLASS, false)`; `PaneBlock.getMetadataFromState` returns zero and the base state definition has the four cardinal virtual Boolean properties (`PaneBlock.java:154-160`). ID 160 constructs `StainedGlassPaneBlock` (`Block.java:1180`), whose default has the same four directions plus `COLOR=WHITE`; metadata decoding uses `DyeColor.byId(metadata)`, and encoding returns the color ID (`StainedGlassPaneBlock.java:20-22,49-60`). The 1.8.9 dye enum IDs 0–15 are white, orange, magenta, light_blue, yellow, lime, pink, gray, silver, cyan, purple, blue, brown, green, red, black (`net/minecraft/item/DyeColor.java`, enum declarations).

The directions in the state are virtual/derived: `PaneBlock.resolveVirtualProperties` computes them from four neighboring block identities (`PaneBlock.java:33-39`), but collision collection does not trust those cached flags. `PaneBlock.addCollisions` reads north, south, west, and east live from `World` each call (`:62-66`), then emits one or two axis strips by setting the shared block bounds and invoking `Block.addCollisions` (`:67-90`). The strips have width 2/16, height 16/16, and extend to connected sides. With no connectable neighbors, both axis branches take their fallback and emit a full-length X strip and full-length Z strip, producing a cross rather than a central post (`:67-90`). This conclusion describes the method's emitted boxes; it is not a full movement or DDA claim.

Historical neighbor admission is `neighbor.isOpaque() || neighbor == this || neighbor == Blocks.GLASS || neighbor == Blocks.STAINED_GLASS || neighbor == Blocks.STAINED_GLASS_PANE || neighbor instanceof PaneBlock` (`PaneBlock.java:134-141`). In particular all pane variants share the `PaneBlock` superclass and connect regardless of color; color itself does not alter the pane's collision geometry. This rule is not a general equivalence to 26.2's face-sturdy/exception, iron-bars, and wall-tag rule.

The legacy mutable-bounds ray path has an important limit for cache conclusions: `Block.rayTrace` invokes virtual `updateShape(world,pos)` before reading the block's bounds (`Block.java:456-457`). Pane's override re-reads the same four live neighbors and sets an aggregate outer shape (`PaneBlock.java:100-131`). Therefore this family is not evidence that its ray trace reads stale pane bounds from an earlier provider query. The collision method still mutates the shared bounds while adding its component boxes; `Block.addCollisions` constructs a box from the current bounds and intersects it with the query (`Block.java:339-350`).

## 26.2 identities, aliases, and provider

Current `EntityBlockStateFix` retains the old numeric identity anchors 102=`minecraft:glass_pane` and 160=`minecraft:stained_glass_pane` (`EntityBlockStateFix.java:124,182`). `Blocks.GLASS_PANE` registers an `IronBarsBlock` with glass material/strength and `noOcclusion`, without `noCollision` (`Blocks.java:2360-364`). Thus the registration uses the default collision-enabled property; `BlockBehaviour.Properties` starts with `hasCollision=true`, and only `.noCollision()` changes it (`BlockBehaviour.java:985,1094-1096`).

Current stained panes are a 16-entry `ColorCollection` of registered `StainedGlassPaneBlock` instances (`Blocks.java:2963-968`). `ColorCollection`'s fixed order and `prefixWithColor` name rule yield white, orange, magenta, light_blue, yellow, lime, pink, gray, light_gray, cyan, purple, blue, brown, green, red, black (`ColorCollection.java:17-35,65-67`). The current dye enum confirms IDs 0–15 in that order (`world/item/DyeColor.java:32-47`). `BlockStateData` independently maps every legacy `stained_glass_pane` state for each color and all 16 directional masks to the corresponding current color-specific key: white at line 7108, orange 7128, magenta 7148, light_blue 7168, yellow 7188, lime 7208, pink 7228, gray 7248, light_gray 7268, cyan 7288, purple 7308, blue 7328, brown 7348, green 7368, red 7388, black 7408. The same 16-state rows retain the old `color` value and direction booleans as the legacy key (`:7108-7424`). This proves the `silver` (old ID 8) to `light_gray` alias, not a same-name guess. The flattening item table separately confirms numeric legacy color 0–15 to the same current item suffixes (`ItemStackTheFlatteningFix.java:132-147`); item data is corroboration, not the block-state mapping basis.

`Blocks.STAINED_GLASS_PANE` uses `StainedGlassPaneBlock::new` and properties without `.noCollision` (`Blocks.java:963-968`). `StainedGlassPaneBlock` extends `IronBarsBlock`, stores its dye color on the block instance, and defaults the four direction properties false and WATERLOGGED false (`StainedGlassPaneBlock.java:8-24`). `IronBarsBlock`'s state has four directions plus waterlogged; it derives directions on placement and updates the one direction facing the changed neighbor (`IronBarsBlock.java:30-78,121-123`). Its `attachsTo` predicate is `!isExceptionForConnection(state) && faceSolid || state.getBlock() instanceof IronBarsBlock || state.is(BlockTags.WALLS)` (`:105-107`).

For collision shape, `CrossCollisionBlock.makeShapes` begins with a centered post and unions an arm for each stored true directional property (`CrossCollisionBlock.java:53-68`); `getCollisionShape` selects its collision-shape function from the state (`:82-84`). The pane constructor uses post and arm widths of 2/16, full height, and the directional arms, with the modern no-connections result a central 2/16 post. `WATERLOGGED` is included in the cached state-shape function inputs but does not alter this geometry formula (`CrossCollisionBlock.java:46-68`). Accordingly, when all four connection bits agree and at least one bit is true, the historic strips and current post-plus-arms describe the same directional union at source level. When all bits are false, the old live-query branch emits the cross described above, whereas modern state geometry returns only the central post. A runtime world must also keep the stored flags synchronized to the historical live-neighbor predicate before the conditional geometry comparison applies.

## Bounded consequences

- Closed: registered old IDs, valid stained metadata/colors 0–15, all sixteen old block-state color aliases (including silver → light_gray), current pane registrations and collision-enabled default, provider query data and mutable bounds behavior, and the stated geometry difference for no-connect neighbors.
- Conditional: for nonempty identical connection masks, old strip union and modern post-plus-arms collision geometry agree; this does not establish that their neighbor predicates or state-update timing agree.
- Not established: old World DDA visit sequence, old-vs-modern ray hit selection, all current block-neighbor predicate equivalence, chunk/load boundary behavior, or movement/runtime reachability. The old ray method's call to `updateShape` specifically prevents using this pane family as a stale-ray-bounds witness.
- Provider implementation boundary: calculate legacy connection eligibility from the exact old identity/opaque predicate for a bounded historical-neighbor domain; derive the emitted geometry from those live results. Preserve native fallback for unsupported/modern-only neighbor cases until they are explicitly bounded. Do not substitute current stored pane flags as proof of historical live-query parity.
