## Legacy registration and state decoding

`Block.java` registers ID 26 as `bed` (line 879), ID 92 as `cake` (1028), ID 127 as `cocoa` (1110), and ID 175 as `double_plant` (1208).

- **Bed, ID 26.** `BedBlock` stores horizontal `FACING`, `PART`, and `OCCUPIED` (lines 21–29). Metadata obtains facing through `Direction.byIdHorizontal(metadata)`; bit 8 selects head and bit 4 supplies occupied for the head (200–205). `Direction.byIdHorizontal` uses the horizontal direction array indexed by `abs(id % length)` (Direction.java:172–174). Foot-state virtual-property resolution can read `OCCUPIED` from the neighboring head at `pos.offset(FACING)` (208–217); that read does not feed the bed shape writer. The bounds are independent of all three properties and of neighbors.
- **Cake, ID 92.** `BITES` is 0–6; metadata maps directly to/from that property (CakeBlock.java:19–25, 127–134). The supported state domain in this report is bites 0–6.
- **Cocoa, ID 127.** Metadata sets horizontal facing from `Direction.byIdHorizontal(metadata)` and age from `(metadata & 15) >> 2` (CocoaBlock.java:20–26, 163–171). `AGE` is 0–2, so the valid metadata projection is the twelve states for ages 0–2 and four horizontal facings; metadata values yielding age 3 are outside the property domain. Shape geometry uses only this cell's facing and age. The separate support check reads the neighboring block for placement/survival but is not part of `updateShape` geometry (CocoaBlock.java:35–44, 70–90).
- **Double plant, ID 175.** The old variants are sunflower, syringa, grass, fern, rose, and paeonia; metadata bit 8 selects the upper half while lower-half metadata bits 0–2 select the variant (DoublePlantBlock.java:24–34, 222–225). Upper-half virtual-state resolution reads the lower cell and copies its variant (229–237). This paired-cell read reconstructs state identity, but it does not feed the bound writer or movement provider.

## Historical movement and ray providers

The default 1.8.9 `Block.addCollisions` calls `getCollisionShape` and appends its non-null result; default `getCollisionShape` constructs an AABB from the block instance's mutable `min/max` fields (Block.java:339–350). Default `rayTrace` first invokes virtual `updateShape(world,pos)` before clipping against those fields (Block.java:456–460). The three blocks use different routes:

- **Bed:** construction sets a 1×9/16×1 box, and each ray-time `updateShape` resets the same constant box (BedBlock.java:25–29, 103–106, 128–130). The inherited movement getter reads shared bounds without refreshing them, but the cache value is state-invariant. Old collision is therefore the full footprint from y=0 through 9/16 for either part/facing/occupied state. Old neighbor state is not needed to calculate this box.
- **Cake:** ray-time `updateShape` writes bounds from the bite count in `world.getBlockState(pos)` (CakeBlock.java:28–34). Movement does not consume that cache: the overridden `getCollisionShape` builds a box directly from the passed state's `BITES` (44–49). For bite count `b` in 0–6, the box is x=`[(1+2b)/16, 15/16]`, y=`[0, 8/16]`, z=`[1/16,15/16]`.
- **Cocoa:** the overridden movement getter calls `updateShape(world,pos)` before delegating to the inherited mutable-bound getter (CocoaBlock.java:58–61). `updateShape` reads the current cell's facing and age, then writes the facing- and age-specific bounds (70–90). Thus each movement collision read refreshes the shared cache from the world state at that position; the old provider does not rely on a prior ray's cocoa bounds. Ray clipping uses the same writer through default `Block.rayTrace`.
- **Double plant:** it inherits `PlantBlock.getCollisionShape`, which returns null (PlantBlock.java:62), so the full-cube ray-time bounds are not consumed by legacy movement collision. `DoublePlantBlock.updateShape` writes the unit cube for both halves without reading state or neighbors (DoublePlantBlock.java:40–42). Its upper-half state resolver does read the lower half's variant, but this does not affect the constant bounds or null movement provider.

## 26.2 aliases and collision providers

- **Bed:** `BlockItemIds.BED` is a color collection generated from the `bed` base name (BlockItemIds.java:750, 784), registered by `Blocks.BED` with `BedBlock` and `.noOcclusion()` (Blocks.java:696–708). BlockStateData rows 416–419 and 424–431 explicitly accept legacy `minecraft:bed` facing/part/occupied states and map them to canonical `minecraft:red_bed` states. Current `BedBlock.getShape` selects a horizontal shape from `PART` and `FACING` (BedBlock.java:55–59, 188–190); `OCCUPIED` does not select its shape. It is a central full-footprint column from y=3/16 to 9/16 plus two 3/16-high corner legs, rotated for facing. Current beds have collision enabled: `BlockBehaviour.Properties.hasCollision` defaults true (line 985), `.noCollision()` is the method that clears it (1094–1097), and default `getCollisionShape` returns `state.getShape(...)` when enabled (327–328). The bed registration does not call `.noCollision()`. Relative to the old full box, current shape leaves most of the lower y=0..3/16 layer empty; only its corner-leg boxes remain there. This is a provider-geometry difference, not a claim about a particular player trajectory.
- **Cake:** `BlockItemIds.CAKE` and `Blocks.CAKE` retain the `cake` key (BlockItemIds.java:676; Blocks.java:2142–2145); BlockStateData enumerates bites 0–6 (1472–1478). Current `CakeBlock.getShape` selects `Block.box(1+2*b, 0, 1, 15, 8, 15)` for bites `b` (CakeBlock.java:34–51). The default enabled collision provider returns this state shape. Its normalized box matches the historical state-derived collision box above for every supported bite count.
- **Cocoa:** `BlockItemIds.COCOA_CROP` uses block key `cocoa` (with `cocoa_beans` as the item key) and `Blocks.COCOA` registers `CocoaBlock` without `.noCollision()` (BlockItemIds.java:740; Blocks.java:2636–2645). BlockStateData lists the twelve `AGE`/`FACING` states at rows 2032–2043. Default enabled collision uses `CocoaBlock.getShape`, whose shape is generated from `Block.column(4+2*age, 7-2*age, 12)`, offset along the north axis by `(age-5)/16`, and rotated for facing (CocoaBlock.java:28–30, 67–69; Block.java:177–184; Shapes.java:404–424). Expanding that expression gives the same state-specific bounds as the historical four-facing formulas at CocoaBlock.java:77–89 for valid ages and facings. Current collision is state-derived rather than a shared mutable Block-instance cache.
- **Double plant:** BlockItemIds names sunflower, lilac, tall grass, large fern, rose bush, and peony (BlockItemIds.java:455–460); Blocks registers these as `TallFlowerBlock` or `DoublePlantBlock` with `.noCollision()` (Blocks.java:3088–3158). Current `DoublePlantBlock` defines `HALF` only; the species is represented by the registered block identity. BlockStateData maps the six old lower-variant states to those modern keys with `half=lower` (rows 2800–2805). For old upper-half states, the same table lists `minecraft:peony`/`half=upper` as the canonical target while accepting all six `double_plant` variant names (rows 2808–2811). This records the datafix table's mapping; it does not establish paired-cell reconstruction from an upper cell alone. All these current registrations disable collision; the current default outline shape remains a cube because `DoublePlantBlock` does not override `getShape`.

## Limits

This closure addresses only these IDs and their individual provider inputs/results. It does not close the 1.8.9 world traversal, provider visitation, first-hit behavior, any other ray provider, or a complete historical-state adapter. The bed shape comparison identifies a lower-layer geometry difference; cake and cocoa formula comparisons establish provider-shape correspondence only under the named valid state mapping. No game, runtime, test, or build evidence is included.
