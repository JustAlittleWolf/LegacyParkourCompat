# DDA and provider closure: 1.8.9 → 26.2

## Finding

The ray DDA used by block clipping/picking is not a player-movement provider walk. Both endpoints stop at the first non-null ray result; they do not visit every provider on the ray. That result reaches target-selection, LOS, projectile, or fall-reset consumers, not the player’s position/velocity movement writer.

There is a separate 26.2 swept-block traversal that is movement-relevant: `BlockGetter.forEachBlockIntersectedBetween` is called from `Entity.checkInsideBlocks` after movement, and visits block positions along each recorded movement segment to run block/fluid inside effects. In 1.8.9 the corresponding entity callback scan is only the block-cell range overlapped by the final entity box (`Entity.checkBlockCollisions`); no swept-ray walk is used there. This difference can directly affect player movement. Example provider: a cobweb callback reached along a movement segment can set the 26.2 `stuckSpeedMultiplier`, consumed by a later `Entity.move`; the 1.8.9 cobweb callback sets `inCobweb` only if the player’s final box scan reaches the web, then a later `move` scales requested motion and zeros velocity. The exact endpoint comparison does not establish when this change entered the game.

The actual solid-block movement collision provider traversal is separate from both DDA helpers: 1.8.9 enumerates the expanded AABB’s integer block range through `World.getCollisions` and dynamically dispatched `Block.addCollisions`; 26.2 obtains block shapes through `CollisionGetter`/`BlockCollisions` over a Cursor3D box range, then resolves the movement vector against the collected shapes. Entity and border collision shapes participate in the movement collision path, but not in the block ray DDA.

## Ray traversal and result consumers

- **1.8.9, `net/minecraft/world/World.java:625–761`, `rayTrace(Vec3d, Vec3d, …)`:** overloads forward to the five-argument method. It rejects NaN endpoints, floors both ends, and tests the starting cell first. The block provider path is `getBlockState` → `getBlock` → optional `getCollisionShape` when `ignoreBlocksWithoutCollision` → `canRayTrace(state, allowLiquids)` → `Block.rayTrace`. The DDA chooses X when its crossing fraction is strictly less than both others, otherwise Y when strictly less than Z, otherwise Z (ties go to Z); it nudges `-0.0` crossing fractions to `-1.0E-4`, updates the entered voxel from `floor(from)` with face correction, and tests one provider per step. It ends at the destination cell or after the bounded loop; first non-null hit returns immediately. Non-raytraceable blocks update the optional last MISS. `Block.java:339–350, 356–362, 456–` supplies default collision box, ray-trace eligibility and shape-intercept math; block subclasses can override either provider.
- **26.2, `net/minecraft/world/level/BlockGetter.java:44–63, 65–96, 114–173`:** both `isBlockInLine` and `clip` use `traverseBlocks`. `clip` reads state and fluid state for each visited position; obtains block shape from `ClipContext`; calls `clipWithInteractionOverride`; obtains fluid shape; clips both; returns the nearer result. The traversal epsilon-lerps both endpoints by `-1.0E-7`, visits the initial cell, then steps the smallest `t` (ties fall to Z), stops when no `t` is `<=1.0`, and returns immediately on the first non-null consumer result. There is no ray-loop iteration cap. The block provider depends on `ClipContext.Block`: COLLIDER uses `getCollisionShape`, OUTLINE uses `getShape`, VISUAL uses `getVisualShape`, and FALLDAMAGE_RESETTING uses tag/player portal gates. Fluid provider modes are NONE, SOURCE_ONLY, ANY, WATER. `BlockBehaviour.java:686–695, 780–784` delegates state-level shape and callback methods to each concrete block. `clipWithInteractionOverride` only tries interaction shape after a block-shape hit; when the interaction hit is closer it preserves the original result and takes the override direction (source fact, no inference).
- **Returned values and consumers:** 1.8.9 `Entity.rayTrace` (`Entity.java:1029–1034`) builds an eye/look segment and returns `World.rayTrace`; `GameRenderer.java:325` stores it in `Minecraft.crosshairTarget`. Other direct 1.8.9 consumers include item selection (`Item.java:275`), boat placement, projectile collisions, path navigation, entity line-of-sight, and a world visibility check. 26.2 `LocalPlayer.raycastHitResult` (`LocalPlayer.java:1242–1281`) uses attack-range selection and then `cameraEntity.pick`; `Entity.pick` calls `level.clip` (`Entity.java:2008–2010`); `Minecraft.java:2951` stores the result in `hitResult`. Entity picking is separately performed by `ProjectileUtil.getEntityHitResult`. Other clip consumers found are camera obstruction, item/projectile collision, explosion visibility, AI/LOS, and `Entity.java:745` fall-damage-reset lookup; `isBlockInLine` is used for vibration occlusion. These are target, visibility, projectile/other-entity, or fall-state paths, not the player movement position/velocity writer. No entity or vehicle provider participates in either block DDA itself.

## Movement and all-provider callback traversal

- **1.8.9 direct movement collision:** `Entity.move` (`Entity.java:371–636`) applies the prior `inCobweb` flag to requested `dx/dy/dz` at `380–388`, queries `World.getCollisions` on an expanded box (`439`, and for step-up at `469`), clips Y then X then Z against returned boxes, optionally retries step height, writes the shape/position and collision flags (`446–548`), and zeros velocity components blocked horizontally (`563–569`). `World.getCollisions` (`World.java:891–945`) scans integer X/Z columns then Y cells from `floor(minY)-1` to `floor(maxY+1)` and invokes `Block.addCollisions` on each loaded-cell provider (`905–923`); `World.getBlockCollisions` (`967–996`) is a similar block-only scan. Default `Block.addCollisions` calls virtual `getCollisionShape`, checks box intersection and appends it (`Block.java:339–350`). The entity-collision branch additionally includes nearby entity `getCollisionShape` and source-relative `getCollisionAgainstShape` boxes (`World.java:927–942`; vehicles/riders are conditionally screened there). Thus collision-shape providers, entities and world-border block stand-ins enter the actual movement collision result through a non-DDA route.
- **1.8.9 block-inside callback:** after movement, `Entity.move` invokes `checkBlockCollisions` (`Entity.java:607–614, 648–670`). It checks the final current box’s inset min/max block coordinates and, only if that area is loaded, visits every cell in its inclusive XYZ range and calls virtual `Block.onEntityCollision`; it does not examine intermediate movement cells. `CobwebBlock.onEntityCollision` (`CobwebBlock.java:21–24`) calls `Entity.onCobwebCollision` (`Entity.java:1581–1583`) to set `inCobweb`; `PlayerEntity` overrides it (`PlayerEntity.java:1402–1407`) and suppresses the flag while flying. A subsequent `Entity.move` consumes/clears that flag and scales movement `(0.25, 0.05F, 0.25)`, then zeroes all three velocities (`Entity.java:380–388`). This is an actual player movement response, though the provider scan is endpoint-only.
- **26.2 actual collision-shape movement path:** `Entity.move` (`Entity.java:711–`), after no-physics/piston gates, consumes `stuckSpeedMultiplier` at `728–735`, applies edge handling and calls movement collision resolution (`737 onward`). `collideBoundingBox` / `collectCollidersIgnoringWorldBorder` (`Entity.java:1195–1259`) gathers entity shapes, optional world-border shape, and all block collision shapes, then runs `Shapes.collide` in `Direction.axisStepOrder`. `CollisionGetter.java:84–106` supplies entity-plus-block or context-based block iterables. `BlockCollisions.java:19–61, 78–110` iterates a Cursor3D range around the query AABB; filters cursor face types, unloaded chunks, suffocation/large-shape/moving-piston cases; gets the context-sensitive collision shape; and yields every intersecting translated shape. This movement collision provider walk is box-range enumeration, not the ray DDA.
- **26.2 swept inside-effects traversal:** `LivingEntity` performs travel and then, on server or a local-authoritative instance, calls `applyEffectsFromBlocks` (`LivingEntity.java:3131–3145`). `Entity.applyEffectsFromBlocks` (`Entity.java:903–961`) records/combines movement segments, invokes `checkInsideBlocks`, and applies/clears collected effects. `checkInsideBlocks` (`Entity.java:1278–1375`) processes segments (or axis-split movement), keeps a per-call `visitedBlocks` set, and limits work to 16 movement iterations per segment, with a final-position fallback when the budget is exhausted. For each position delivered by `BlockGetter.forEachBlockIntersectedBetween` it reads `BlockState`, skips air, obtains `getEntityInsideCollisionShape(level,pos,this)`, tests the movement segment against that translated shape (`Entity.java:1334–1345`), and tests fluid intersection. If block/fluid effects intersect and the position is newly visited, it dispatches `BlockState.entityInside` and `FluidState.entityInside` (`1346–1365`); it continues to the next provider unless the entity is dead or iteration limit is reached. The helper (`BlockGetter.java:175–208, 211–288`) starts by visiting the starting volume’s candidate cells, uses a DDA on the furthest AABB corner and `AABB.clip` against unit cells to order intermediate swept-volume cells, deduplicates positions, then visits the destination volume. This is the all-provider-style movement callback traversal; it is bounded/short-circuitable, not the first-hit block ray traversal.
- **Concrete modern movement writer:** `BlockBehaviour.BlockStateBase` delegates `entityInside` to the concrete block (`BlockBehaviour.java:780–784`). `WebBlock.entityInside` (`WebBlock.java:27–41`) calls `Entity.makeStuckInBlock`, setting `(0.25, 0.05F, 0.25)` by default or `(0.5, 0.25, 0.5)` with WEAVING; `makeStuckInBlock` resets fall distance and stores the multiplier (`Entity.java:2943–2946`). A later `Entity.move` multiplies the requested delta by that value and clears the multiplier/velocity (`728–735`). Modern `isAffectedByBlocks` gates removed/no-physics entities (`Entity.java:977–979`); unlike the inspected old `PlayerEntity.onCobwebCollision` override, that gate has no player-flight check in the base method. Fluid callbacks share the traversal but their full block/fluid-specific bodies were not inventoried here.

## Open gates / scope limits

- This closes only the supplied 1.8.9/26.2 source endpoints. It does not identify intermediate patch boundaries or assert a specific release when the swept movement callback traversal was introduced.
- The block-ray traversal is closed as a non-movement result path. The movement-relevant DDA is the separate swept-AABB inside-effects helper; it has a hard 16-iteration segment cap, deduplication, entity-alive short-circuit, and a final-position fallback.
- The shared callback API’s full inventory of concrete block/fluid overrides was not enumerated; WebBlock is the concrete provider traced end-to-end to a player movement response. If acceptance requires every historical callback override rather than the traversal/provider footprint and one direct movement witness, that override inventory remains open.
- No implementation, build, tests, runtime launch, or wiki/product/history inspection was performed.
