## Ray visitation and its writes

In 1.8.9, `World.rayTrace(Vec3d,Vec3d,boolean,boolean,boolean)` (`World.java:633–761`) reads the initial block/state, then runs a one-cell-at-a-time voxel DDA. Per visited cell it calls `getBlockState`, `getBlock`, optionally `getCollisionShape` when `ignoreBlocksWithoutCollision` is true, then `canRayTrace`, then virtual `block.rayTrace`. Camera picking uses `(allowLiquids=false, ignoreBlocksWithoutCollision=false, allowHitInStartPosition=true)`. The initial cell is checked before the loop; each visited provider can return a hit and terminate the ray immediately. The loop is bounded by `o=200; while (o-- >= 0)`, uses strict X/Y comparisons with Z as tie fallback, and nudges `-0.0` fractions to `-1.0E-4`.

`Block.rayTrace` (`Block.java:456–516`) calls virtual `updateShape(world,pos)` before testing its shape planes. Therefore every default-raytrace provider visited before the first hit can write its shared provider shape even if that provider misses the segment. `Block.setShape` (`Block.java:292–298`) writes all six instance fields `minX,minY,minZ,maxX,maxY,maxZ`; the default `getCollisionShape` (`346–350`) later reads those same fields and translates them to the collision query's position, without restoring them from the supplied state.

Because the bound fields belong to singleton block instances, the last eligible provider visit of each block type before ray termination determines that type's residual cache. A miss still writes; an earlier ray hit prevents later cells from writing. A later render pick can replace those last writers again before the movement query.

The canonical 1.8.9 block package has these public `updateShape(WorldView,BlockPos)` overrides dispatched by default `Block.rayTrace` (including custom raytrace overrides that explicitly call `super.rayTrace`; the non-reaching `MovingBlock` exception is stated below): `AbstractPressurePlateBlock`, `AbstractRailBlock`, `AnvilBlock`, the wall-banner inner class in `BannerBlock`, `BedBlock`, `ButtonBlock`, `CakeBlock`, `CarpetBlock`, `ChestBlock`, `CocoaBlock`, `DaylightDetectorBlock`, `DoublePlantBlock`, `DoorBlock`, `EndPortalBlock`, `FenceBlock`, `FenceGateBlock`, `HopperBlock`, `LadderBlock`, `LeverBlock`, `MovingBlock`, `PaneBlock`, `PistonBaseBlock`, `PistonHeadBlock`, `PortalBlock`, `SkullBlock`, `SlabBlock`, `SnowLayerBlock`, `StairsBlock`, `StemBlock`, `TrapdoorBlock`, `TripwireBlock`, `TripwireHookBlock`, `VineBlock`, `WallBlock`, and `WallSignBlock`. The base `Block.updateShape` (`596–597`) is empty. Most shape-changing implementations use `setShape` directly or through class-local helpers. The full list is a writer inventory, not a claim that every writer has a movement-visible stale shape; null/noncolliding, constant-shape, and movement-refreshing providers do not have the Anvil/Chest read path described below.

Two additional mutable writer details matter to close the field inventory:

- `StairsBlock.rayTrace` (`StairsBlock.java:502–535`) writes `isCorner=true` and loops `stairType` across eligible sub-boxes. Each call to `super.rayTrace` dispatches back to `StairsBlock.updateShape` (`49–62`), which writes bounds from `stairType`. The class's extra shared fields are `isCorner` and `stairType` (`33–34`). Its ray query evaluates all of its permitted sub-boxes internally before returning a chosen hit. Its movement `addCollisions` (`383–394`) rebuilds collision boxes from the queried stair state/neighbors and restores the full bound at return, so the residual ray cache is overwritten before movement reads it.
- `TorchBlock.rayTrace` (`TorchBlock.java:138–155`) writes the six shared bounds directly from its queried facing before calling `super.rayTrace`; Torch has no dynamic `updateShape` override. Its movement collision-shape override returns `null`, so this cache does not constrain player movement.
- `StemBlock.updateShape` (`StemBlock.java:114–118`) directly writes `maxY` from queried `AGE`, then writes all six bounds through `setShape`. `StemBlock` inherits `PlantBlock.getCollisionShape`, which returns `null` (`PlantBlock.java:61–64`), so the cache has no solid-player movement collision consumer. `MovingBlock.updateShape` (`MovingBlock.java:133–158`) can write the moved block's cache and its own bounds directly, but `MovingBlock.rayTrace` returns `null` (`106–108`), so the camera ray provider does not reach that method. Its movement `getCollisionShape` is an independent moving-block path (`118–181`). `WallBlock.getCollisionShape` (`107–111`) refreshes neighbor shape and sets `maxY=1.5` before delegating to the base getter.

For `ignoreBlocksWithoutCollision=true` callers, the DDA's prefilter invokes dynamic `getCollisionShape` before `canRayTrace`; it is an additional potential writer route. The camera-pick flags do not take it. State-refreshing overrides verified in this source include Cocoa, Door, Skull, Trapdoor, and Wall. This flag-specific route does not remove the camera-path Anvil/Chest cache write, which occurs in `Block.rayTrace` itself.

## Later movement consumers and verdict

The 1.8.9 movement consumer is direct: `Entity.move` calls `World.getCollisions` on the expanded movement box (`Entity.java:439`, with the step-up query at `469`), then resolves Y/X/Z and can zero blocked velocity components (`442–569`). `World.getCollisions` scans the box's cell range and dynamically calls `block.addCollisions` (`World.java:891–945`). Default `Block.addCollisions` calls virtual `getCollisionShape`, intersects that returned box and appends it (`Block.java:339–350`). For anvil and chest, no `addCollisions` or `getCollisionShape` override refreshes the cache during that call. The camera ray's last `updateShape` for that singleton block type can therefore supply the wrong orientation/neighbor-derived bounds to the player's later movement collision query. This can change the collected collision boxes and consequently the resolved player movement/velocity. There is also an indirect movement reader: `MovingBlock.getCollisionShape` (`MovingBlock.java:118–129, 162–181`) asks the moved-state block for its collision shape before translating the returned box; a moved Anvil therefore reads its shared cached bounds through that helper. The coordinator's accepted camera-tick finding establishes the ordinary camera-pick-before-entity-movement order and the anvil/chest per-state writers; no particular trajectory is asserted here.

Other mutable writers are not automatically equivalent to Anvil/Chest: movement providers with custom `addCollisions` rebuild their state-dependent boxes (e.g. stairs, fences, panes, slabs, piston providers); collision getters for Cocoa, Door, Skull, Trapdoor and Wall call `updateShape` for the current query; Stem returns no solid collision shape; several remaining cached shapes are state-invariant or noncolliding. The Anvil/Chest classes are the independently accepted direct stale-cache consumers in the supplied source-only evidence.

26.2 closes this writer path: `BlockGetter.clip` (`BlockGetter.java:65–82`) passes the queried `BlockState`, `ClipContext` shape getter and position to the consumer; `traverseBlocks` (`114–173`) returns on its first non-null consumer result, after endpoint epsilon shifts, but does not invoke a mutable `Block.rayTrace` method. `BlockBehaviour.BlockStateBase.getShape` delegates to the block with the current state (`BlockBehaviour.java:678–684`); its collision-shape cache is initialized per block state in `initCache` (`511–520`) and held in a `final` field (`922–944`), rather than shared mutable geometry on the block singleton. `ClipContext.OUTLINE` selects that state shape; movement `CollisionGetter`/`BlockCollisions` also calls the queried state collision shape with `CollisionContext` (`CollisionGetter.java:96–106`; `BlockCollisions.java:78–110`). The traced AnvilBlock and ChestBlock providers return shapes from the current state (`AnvilBlock.java:77–79`; `ChestBlock.java:193–202`); no shared `Block` min/max cache is written by ray visitation and later consumed by movement. Thus old DDA *visitation and last-writer order* can affect player movement through shared cached block bounds; modern DDA order remains relevant to pick results, but it has no analogous shared mutable shape-cache movement effect in these traced providers.
