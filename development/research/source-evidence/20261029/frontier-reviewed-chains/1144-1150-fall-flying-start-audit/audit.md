# Independent audit: 1.14.4 to 1.15 fall-flying start closure

## Verdict

The report's central local-path comparison is supported by the exact Mojmap source trees: 1.14.4's `LocalPlayer.aiStep()` requires negative vertical movement and only sends `START_FALL_FLYING`; 1.15's local path calls a shared `Player.tryToStartFallFlying()` helper with no negative-Y requirement, sets shared flag 7 on success, then sends the command, all before `super.aiStep()`. The 1.15 local caller adds the passenger and same-tick mayfly-toggle guards, and the helper requires not-in-water. This establishes a source-level reachable rising/level start path when the other gates pass; it establishes no trajectory claim.

One source identity citation in the report needs correction: it attributes 1.14.4 `startFallFlying()` at line 1276 to `world/entity/player/Player.java`. The method is actually `net/minecraft/server/level/ServerPlayer.java:1276-1278`. This distinction reinforces the client/server separation: 1.14.4's client `LocalPlayer` has only the request producer in this slice; the server's `ServerPlayer` method sets flag 7 after server validation. The report should identify `ServerPlayer.java` and include that source hash wherever it uses this method as evidence.

## Retraced source paths

- **1.14.4 local producer:** `net/minecraft/client/player/LocalPlayer.java:625, 707-712` snapshots prior jump state, ticks input, then checks `input.jumping && !bl && !onGround && deltaMovement.y < 0.0 && !isFallFlying() && !abilities.flying`, followed by Elytra identity and enabled checks. It sends `START_FALL_FLYING`; it does not set flag 7 there. The request precedes `LocalPlayer.aiStep()`'s `super.aiStep()` at line 772.
- **1.14.4 server consumer:** `ServerGamePacketListenerImpl.java:1122-1128` validates airborne, descending, not already fall-flying, not in water, and equipped/enabled Elytra before calling the `ServerPlayer.startFallFlying()` method cited above. The client producer and server acceptance path are separate.
- **1.15 local producer/helper:** `LocalPlayer.java:632-635` snapshots prior jump state. `:695-713` sets `bl8` when the mayfly flying state changes. `:715-719` requires jump pressed, no mayfly-state update that tick, a new jump edge, not flying, and not passenger; it checks Elytra identity/enabled before invoking `tryToStartFallFlying()`, then sends the packet only on helper success. `Player.java:1586-1600` requires `!onGround && !isFallFlying() && !isInWater()`, rechecks Elytra identity/enabled, calls `startFallFlying()`, and sets shared flag 7. No delta-Y predicate occurs in this local call chain. The success and packet send both precede `LocalPlayer.aiStep()`'s `super.aiStep()` at line 778.
- **1.15 server consumer:** `ServerGamePacketListenerImpl.java:1137-1140` calls the same Player helper and stops fall flying on failure. In this handler the call is server eligibility/state enforcement; the local `LocalPlayer` caller is the separate client path. This source comparison does not imply historical server-side physics.
- **Inherited validity update:** `LivingEntity.java:2235-2253` (1.14.4) and `:2299-2317` (1.15) both read flag 7, require airborne and not passenger plus a valid enabled Elytra to preserve a true candidate, damage the Elytra server-side on the same 20-tick cadence, and write the resulting shared flag only when `!level.isClientSide`. The bodies and ordering are materially the same in this slice. `updateFallFlying()` is called before `travel()` at `:2221-2223` and `:2285-2287` respectively. Thus this updater does not erase the client-local helper's write during the local pass.
- **Pose:** `Player.updatePlayerPose()` at 1.14.4 `:344-372` and 1.15 `:357-385` chooses `FALL_FLYING` first under the same outer `canEnterPose(SWIMMING)` gate and uses the same spectator/passenger/can-enter/fallback structure. The crouch naming/input predicate differs, but no new fall-flying selection rule appears in these bodies. Collision behavior behind `canEnterPose` remains outside this audit.

## Bounded conclusion

The reported distinction is source-supported: a local airborne 1.15 player with a valid Elytra can enter the start helper on a rising or level tick if the input-edge, passenger, toggle and water gates pass; 1.14.4's local producer will not request start unless vertical movement is negative. The 1.15 helper is shared by the local client and server packet handler, but the two callers represent different execution sides. No trajectory, downstream Elytra travel, full pair coverage, or intermediate patch boundary is established here.
