# Piston-family provider closure: IDs 29, 33, 34, 36

Scope: source-only local provider facts for 1.8.9 `ornithe-feather` versus 26.2 `unobfuscated`. This does not establish ray traversal visitation, first-hit parity, player-response parity, or readiness of a complete historical provider adapter.

## Identity and state projection

1.8.9 `Block.java:882, 886–889` registers ID 29 as `sticky_piston`, ID 33 as `piston`, ID 34 as `piston_head`, and ID 36 as `piston_extension`. IDs 29 and 33 are separate instances of `PistonBaseBlock` parameterized with `sticky=true/false`; ID 34 is `PistonHeadBlock`; ID 36 is `MovingBlock`.

The current registry uses `Blocks.STICKY_PISTON` and `Blocks.PISTON` (`26.2 Blocks.java:715, 827`), `Blocks.PISTON_HEAD` (`Blocks.java:828–832`), and `Blocks.MOVING_PISTON` (`Blocks.java:844–847`). The corresponding resource keys are declared in `BlockItemIds.java:556–557` and `BlockIds.java:15–16`. `EntityBlockStateFix.java:49–58` preserves the four old numeric identities by their legacy names. `BlockStateData.java:528–541` retains the piston base facing/extended state combinations; lines 544–557 encode piston-head facing/type and current `short`; lines 576–589 map old `piston_extension` states to current `moving_piston` facing/type states.

Old direction metadata is the `Direction.byId` order: 0 down, 1 up, 2 north, 3 south, 4 west, 5 east (`Direction.java:11–17, 168–172`). Base metadata uses low three bits for facing and bit 8 for `extended` (`PistonBaseBlock.java:227–230, 352–369`). Head and moving-block metadata use low three bits for facing and bit 8 for sticky/default type (`PistonHeadBlock.java:170–185`; `MovingBlock.java:205–225`). `PistonHeadBlock.SHORT` exists in the old state definition but is not included in its metadata encoder/decoder; the old head shape methods also do not branch on it (`PistonHeadBlock.java:30–33, 170–196`). Current head state adds a `short` property and uses it to select a different shape (`26.2 PistonHeadBlock.java:38–42, 60–61`).

## Base piston providers

The old base's mutable cached box is updated from the **world state at the queried position**, not just the passed state. If that state is this base block and `extended=true`, `updateShape` cuts a 1/4-thick cap on the side selected by facing; otherwise it resets to the unit cube (`PistonBaseBlock.java:174–204`). Its `getCollisionShape` calls `updateShape` before returning the superclass box (`217–219`). Its `addCollisions` first resets the box and calls superclass collection (`211–214`); that collection calls `getCollisionShape`, so the state-derived cap is applied again. The inherited `Block.rayTrace` also calls `updateShape` before clipping against the cached min/max fields (`Block.java:456–460`), leaving the base's facing/extended box in shared block-instance fields after the ray call. The default `canRayTrace` is true (`Block.java:356–361`).

The current base returns a state-derived shape: full cube when not extended, and a rotated plate with thickness 4/16 when extended (`26.2 PistonBaseBlock.java:55, 70–71`). The direction and extension inputs align at the source-state level, while the old provider mutates reusable bounds and the current provider returns an immutable `VoxelShape`; no general old/current shape-equivalence claim is made here.

## Piston-head providers

Old movement collision is emitted as two sequential boxes: the facing end plate, then the central arm; the cached box is reset to the unit cube after both (`PistonHeadBlock.java:87–92, 100–120`). In contrast, old `updateShape` sets only the facing plate (`123–151`). Since inherited `Block.rayTrace` invokes `updateShape`, the old head ray provider clips against the plate box only, not the arm, and leaves that plate in shared mutable bounds. The movement collision provider and ray provider therefore intentionally have different source paths.

Current `PistonHeadBlock.getShape` returns a union of platform and arm shapes; the full variant extends its arm endpoint to 20/16, and the short variant to 16/16 (`26.2 PistonHeadBlock.java:40–42, 60–61`; `Block.java:187–198` defines the `boxZ` coordinate scaling). The default state is `short=false`; collision defaults to using the state shape when `hasCollision` is enabled (`BlockBehaviour.java:327–328`). Thus the current state shape is not a safe substitute for the old ray box or the old two-call collision construction without a specific old-provider reconstruction.

## Moving piston providers and required context

The old moving block is not a normal inherited ray-box provider: it overrides `rayTrace` to return null (`MovingBlock.java:106–108`). Its default `canRayTrace` remains true, so the world may invoke this override, but it yields no hit. The block's collision shape is instead read from a `MovingBlockEntity` at the same position; absent that entity it returns null (`118–130`). The entity supplies moved state, facing, extending/source flags, and interpolated progress (`MovingBlockEntity.java:33–58`). The old provider derives progress at `tickDelta=0`, inverts it for extension, calls the moved block's collision provider, and adjusts the moved box's face along the movement axis (`MovingBlock.java:118–130, 162–193`). Reconstructing this provider therefore requires the block-entity payload and the old identity/state/provider for the moved block, not only the current `moving_piston` state.

Old `MovingBlock.updateShape` separately reads the moving entity, calls the moved block's `updateShape(world,pos)`, then writes six translated cached bounds from that block's current bounds and the movement progress (`MovingBlock.java:133–159`). Because `MovingBlock.rayTrace` overrides the inherited implementation with null, do not infer that this updater is called by its ray-trace path. Other callers and moved-block provider side effects are outside this bounded closure.

Current `MovingPistonBlock.getShape` is empty, while `getCollisionShape` delegates to a `PistonMovingBlockEntity` or returns empty if missing (`26.2 MovingPistonBlock.java:102–109`). That entity's collision provider depends on moved state, direction, extending/source, current progress and a thread-local no-clip direction; it may add a piston-head/base shape and then a translated moved-state collision shape (`PistonMovingBlockEntity.java:74–115, 366–393`). The old and current moving providers are therefore context-bearing operations, not shapes recoverable from a plain block state. The old movement block also mutates shared block bounds in its `updateShape`; the modern provider returns shapes and does not use the old mutable-bound path.

## Bounded adapter implication

An old-compatible provider callback for this family must receive (1) the exact legacy block identity and legacy state/metadata, (2) a `WorldView`-equivalent query for the base/head cell, and (3) for moving piston states, the old moving-block-entity fields and the moved block's old identity/state plus any world/context inputs that moved provider reads. It must preserve the distinction between base/head inherited ray clipping and the moving block's explicit null ray result, as well as the separate head ray-box and movement-box paths. This family report does not close the complete provider/state/neighbor matrix and does not authorize using current shapes as a blanket fallback.
