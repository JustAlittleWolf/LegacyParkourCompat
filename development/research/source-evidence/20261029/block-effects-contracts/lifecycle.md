## Boundary findings

### 1.21.4 → 1.21.5: movement batches and staged callbacks

In 1.21.4, `Entity.move(MoverType, Vec3)` does not append its accepted displacement to the `movementThisTick` list. `recordMovementThroughBlocks(from,to)` appends one `Movement` (`Entity.java:1046–1048`), and the source-wide call search found its callers only in `ServerGamePacketListenerImpl`; those are server packet paths and are outside client movement emulation. `Entity.applyEffectsFromBlocks()` supplies `(oldPosition(), position)`. Its two-position overload appends that `Movement`, snapshots the list with `List.copyOf`, clears the live list, then calls `checkInsideBlocks` (`Entity.java:747–765`). The ordinary client player reaches the no-argument call after `LivingEntity` travel under `!clientSide || isControlledByLocalInstance` (`LivingEntity.java:2779–2787`). The reused 1.21.3→1.21.4 closure establishes the older client piston caller; it invokes `move` and then `applyEffectsFromBlocks()` during piston movement.

1.21.5 changes the live field to `List<List<Entity.Movement>>`. On a physical `Entity.move`, after resolving displacement, it constructs one ordered list of axis-aligned subsegments using `axisStepOrder(resolvedDisplacement)` and appends that list before `setPos` (`Entity.java:636–681`). The record gate is `resolved.lengthSqr() > 1.0E-7 || requested.lengthSqr() - resolved.lengthSqr() < 1.0E-7`; the no-physics early path and a zero result from `limitPistonMovement` return without a movement record. The no-argument application method flattens the batches into a separate final list, clears the live list before callbacks, then either adds `(oldPosition, position)` if empty or appends a residual segment from the last recorded endpoint when squared distance to the current position is greater than `9.9999994E-11F` (`Entity.java:768–779`). There is no 100-record cap in this release.

The `InsideBlockEffectApplier.StepBasedCollector` is introduced in this boundary. `checkInsideBlocks` calls `advanceStep(visitorStep)` immediately before a passing block callback and before a passing fluid callback (`Entity.java:1079–1120`). The collector flushes queued operations when the step number changes; its flush order is `InsideBlockEffectType.values()`, with each type’s `runBefore` consumers, coalesced `apply` effect, and `runAfter` consumers in that order. After segment scanning, `applyAndClear(entity)` flushes the last step, executes collected final effects in order while the entity remains alive, clears them, and resets its step. Thus only callback operations explicitly submitted through this applier are deferred; direct block callback code still runs synchronously during scanning. `Entity.applyEffectsFromBlocks(List)` keeps grounded `stepOn` before scanning and performs its subsequent rain/fire bookkeeping after `applyAndClear` (`Entity.java:791–815`).

The local player still reaches the ordinary post-travel application through `LivingEntity.tick` (`:2764–2771`). Piston push handling now captures the current position, calls `move(MoverType.PISTON, delta)`, immediately scans the explicit pre/post positions, then removes that move’s batch (`PistonMovingBlockEntity.java:186–192`). The old server-side path now removes a latest batch through `removeLatestMovementRecordingBatch`; it is excluded. This is a distinct immediate client piston callback phase at the piston helper call site; the relative ordering against the ordinary post-travel callback depends on enclosing client tick order and is not established here.

### 1.21.5 → 1.21.6: capped deque and a resolved-displacement axis flag

1.21.6 replaces nested batches with `ArrayDeque<Entity.Movement>(100)`. The capacity argument is an initial capacity, not the limit: `addMovementThisTick` explicitly checks `size() >= 100`, removes the two oldest records, inserts a merged `(first.from, second.to, false)` record at the front, then appends the new record (`Entity.java:798–807`). The stored record count therefore remains 100 after a full-queue append. This merge preserves only the outer endpoints and drops axis-independent subdivision information.

Each accepted `Entity.move` now writes one record `(currentPosition, currentPosition + resolvedDisplacement, true)` before `setPos` (`Entity.java:663–698`). The record is `Movement(from,to,axisIndependant)`. During callback collection, a true flag makes `checkInsideBlocks` split the resolved `to-from` vector at collection time using `Entity.axisStepOrder(resolvedDisplacement)`; a false flag or no hint uses one straight segment (`Entity.java:1113–1135`). This still selects traversal order from resolved motion, not from pre-collision attempted motion. The final-list drain keeps the 1.21.5 flatten/clear, old-position fallback, and `9.9999994E-11F` terminal residual check (`:785–796`). `removeLatestMovementRecordingBatch()` becomes `removeLatestMovementRecording()` because each move contributes one record. `PistonMovingBlockEntity` continues to scan its explicit before/after positions and removes the last single record (`:185–191`).

A `clearMovementThisTick()` helper is added and called at the end of `Entity.teleportSetPosition` after position, rotation, and delta movement are replaced (`Entity.java:815–817, 2924–2935`). I verified the clearing call in the shared entity method; I did not establish a client-local packet caller for it in this assignment.

### 1.21.8 → 1.21.9: original attempted movement becomes an optional axis-order hint

1.21.9 changes the movement record to `Movement(from,to,Optional<Vec3> axisDependentOriginalMovement)` (`Entity.java:3962–3967`). For a physical move, `Entity.move` first limits piston movement, consumes the stuck multiplier, and backs off from edges; it then resolves collision into `$$3`. If the existing accepted-movement condition passes, it records `(currentPosition, currentPosition + resolvedDisplacement, $$1)` before `setPos`, where `$$1` is the post-piston-limit/stuck-multiplier/edge-backoff attempted movement, not the resolved displacement (`Entity.java:670–711`).

At callback time, an absent hint uses one direct segment. With a present hint and nonzero resolved displacement, the checker orders the resolved component segments using `Direction.axisStepOrder(originalMovement)` (`Entity.java:1134–1158`). Thus the first observed boundary that supplies attempted-motion order is 1.21.9; 1.21.6–1.21.8 order from resolved displacement. The 100-record merge remains at the same point in the lifecycle, but its two-argument `Movement(from,to)` constructor creates an empty optional, so the merged path has no attempted-motion hint (`Entity.java:811–820`). Explicit `applyEffectsFromBlocks(from,to)` calls likewise construct a no-hint movement record (`:832–834`), which is relevant to the piston immediate scan.

The drain order remains: copy live records into `finalMovementsThisTick`, clear the live deque, add old/current fallback or the terminal residual, then scan callbacks and call `insideEffectCollector.applyAndClear` (`Entity.java:798–809, 836–861`). The 1.21.9 checker also gives each movement record a 16-step visitation budget with an endpoint check if it is exhausted; exact voxel traversal, ties, and epsilon math are assigned to a separate source closure and are not inferred here. `InsideBlockEffectApplier` is byte-identical to 1.21.8, while `InsideBlockEffectType` adds `CLEAR_FREEZE` after `FREEZE` and before fire/lava/clear-fire types, changing the enum-derived queued-effect order at this boundary. `LivingEntity.tick` still invokes no-argument application after its travel branch under `!clientSide || isLocalInstanceAuthoritative` (`:2846–2853`); `PistonMovingBlockEntity` still applies the explicit segment and removes the latest movement record (`:185–191`).

## Direct client consumers and exclusions

The ordinary local-player segment queue is consumed after `LivingEntity` travel, before the later client animation work. The applicable local-client gate is the controlled/local-authoritative predicate (`LivingEntity.java:2769–2771` in 1.21.5; `2821–2823` in 1.21.6–1.21.8; `2851–2853` in 1.21.9). `LocalPlayer.isLocalPlayer()` returns true; `Player.isLocalClientAuthoritative()` delegates to it. The ordinary local player therefore follows this client callback path. `Entity.isAffectedByBlocks()` additionally excludes removed and `noPhysics` entities.

Client piston displacement is a second direct player response: the block-entity helper performs the move, invokes the immediate segment scan, then removes the just-recorded movement so the later tick drain will not process that same push again. The accepted 1.21.3→1.21.4 caller report binds the older reachability and the exact source hashes in this report bind the later implementations. Other `applyEffectsFromBlocks` callers serve vehicles, projectiles, items and other entities and are out of the assigned player scope. Server packet listeners’ movement-record removal/packet logic is server-only and is not a client historical replay path.
