# Immutable class-dependency closure supplement

This supplement corrects the source dependency ledger for the original `FINDING.md` and `old-opaque-roster.csv`; neither original file nor `source-hashes.json` is modified. The original ledger hashes the registered concrete class sources that were collected directly, but does not include every source file named by the CSV's `class_ancestry_to_basis` or the source hierarchy needed to substantiate inherited `isSolidRender` methods. The reviewer reported 19 omitted class files. Independently comparing all 198 roster class/ancestry tokens with the canonical 1.8.9 block source tree found **17 existing `.java` files absent from the original ledger**. I verified two likely false positives in the broader dependency list: `AbstractLeavesBlock.java` and `SlabBlock.java` are already present in the original ledger. The two nested tokens `BannerBlock.Standing` and `BannerBlock.Wall` have no standalone source files and resolve to `BannerBlock.java`, which is also already present. Thus all extant source files for the CSV class/ancestry tokens are covered by the original ledger plus the 17-file supplement.

`dependency-closure-source-hashes.json` binds the exact roster CSV SHA-256 and original source-ledger SHA-256, then records canonical path, byte count, and SHA-256 for each omitted source. This closes the ancestry-file dependency set: every registered concrete class or ancestry token with a corresponding source file is either in the original source ledger or this supplement. Tokens without their own `.java` file were verified against their enclosing class source.

The omitted files are `AbstractLogBlock`, `AbstractPressurePlateBlock`, `AbstractRailBlock`, `AxisBlock`, `BlockWithBlockEntity`, `ButtonBlock`, `DiodeBlock`, `FallingBlock`, `FlowerBlock`, `HorizontalFacingBlock`, `LiquidBlock`, `PlantBlock`, `RedSandstoneSlabBlock`, `SignBlock`, `StoneSlabBlock`, `TransparentBlock`, and `WoodenSlabBlock`. The supplemented rows cover inherited registration hierarchy, direct `isSolidRender` overrides, and concrete slab `isDouble` dispatch as applicable. This is only evidence-ledger repair; roster classifications and current-mapping boundaries are unchanged.

Static validation rerun: roster has exactly 198 records with IDs 0 through 197 in order, every field is populated, `opaqueCube` counts remain 72 true / 126 false / 0 OPEN, and every source digest in both ledgers matches its current canonical bytes. No runtime or product code was used.
