## Source verdict

- **Separate block and item identities:** `Block.java` registers numeric ID `161` as key `leaves2` with `Leaves2Block` (1.8 `:1075`; 1.12.2 `:1129`). `Blocks.LEAVES2` resolves the `leaves2` key (1.8 `Blocks.java:235`; 1.12.2 `:302`). `Item.java` separately registers `new LeavesItem(Blocks.LEAVES2)` (1.8 `:309`; 1.12.2 `:411`). The same registrations were checked in every roster release; this is not the ordinary `leaves`/Oak registry entry.
- **Legal species and persistent placement:** `Leaves2Block` permits plank variants with ID at least 4. The variant enum has only Acacia ID 4 and Dark Oak ID 5 in that range (1.8 `Leaves2Block__84491018.java:5-7`, `PlanksBlock__Variant.java:10-11`; 1.12.2 `Leaves2Block.java:20-26`, `PlanksBlock.java:61-62`). Metadata decoding uses `(metadata & 3) + 4`; decay flags use bit 4 for `DECAYABLE` and bit 8 for `CHECK_DECAY` (1.8 `Leaves2Block.java:54-75`; 1.12.2 `:61-82`). `LeavesItem.getBlockMetadata` returns `metadata | 4`, and `BlockItem` passes that result to `getPlacementState` (1.8 `LeavesItem.java:16-18`, `BlockItem.java:49-52`; 1.12.2 `LeavesItem.java:16-18`, `BlockItem.java:38-42`). `Leaves2Block.addToCreativeMenu` emits the two legal item stacks with metadata 0 and 1 (1.8 `:43-45`; 1.12.2 `:50-52`), and it does so in every roster release. Those values place species metadata 4/5 with `DECAYABLE=false`. I make no claim about malformed or out-of-domain metadata.
- **Inherited material, including the class-hierarchy transition:** In 1.8, `Leaves2Block` extends `AbstractLeavesBlock`, which extends `TranslucentBlock`; its constructor passes `Material.LEAVES` through to `Block` (`Leaves2Block.java:17`, `AbstractLeavesBlock.java:18,25-27`, `TranslucentBlock.java:8-13`). From the evolved superclass form, `AbstractLeavesBlock` directly extends `Block` and calls `super(Material.LEAVES)` (1.12.2 `AbstractLeavesBlock.java:18,24-26`). `Material.LEAVES` is an ordinary `Material` configured as flammable, translucent, and piston-destroyable; it is not configured replaceable (1.8 `Material.java:13,63-64,86-92`; 1.12.2 `:15,71-72,94-100`). The base `blocksMovement()` returns true. Translucency changes `isSolidBlocking()`, not `blocksMovement()`. The `Leaves2Block` implementations contain no material, replaceability, liquid, or falling override; their class-specific methods cover variants, metadata, drops, and creative/item handling. The material and leaf superclass bodies were checked across each distinct source body in the roster.
- **Fixture applicability:** The bounded Oak evidence has the dry horizontal leaf side, a level-0 center source, and a confined level-1 north water cell. `leaves2` has no material or propagation exception for either legal species, so the already accepted material predicate treats that side state exactly like Oak. This adds no new flow caller or geometric claim and predicts no different provider result for the supplied states.

The author's bounded conclusion agrees with this independent review. There is no separately resolved `leaves2` operation here; this is a second legal block provider for the already accepted material predicate. Invalid metadata, other leaf species, other liquid callers or directions, and broader movement coverage are outside this verdict.
