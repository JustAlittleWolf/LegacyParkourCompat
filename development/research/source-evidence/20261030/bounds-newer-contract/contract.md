# Newer shape-provider contract for the 1.8.9 shared-bounds finding

## Result

The 1.8.9 mutable-`Block`-bounds lifecycle is absent in 1.9, remains absent in the checked 1.9.4 source, and is structurally absent from the 26.2 integration target. The exact source transition is bounded by 1.8.9 versus 1.9; the 1.9.4 check closes persistence through that release, but does not prove every unexamined intermediate patch. For the checked source points, a historical movement operation must supply the legacy shape for each queried block state and position at the movement read. A camera/render shape refresh is no longer a shared mutable cache input to a later movement query.

This closes the cross-version shape-provider/read path for the previously accepted conditional P-to-Q lifecycle fact. It does not itself authorize a camera-ray / DDA replacement: the old and new ray traversals, provider eligibility, and hit ordering are separate operations and remain governed by their own contract.

## Paired provider facts

In 1.8.9, registry IDs 54 and 146 are distinct singleton `ChestBlock(0)` and `ChestBlock(1)` providers; ID 145 is an `AnvilBlock`. `ChestBlock.updateShape(world,pos)` checks neighboring blocks by identity in north, south, west, east order and writes bounds to the singleton object. `AnvilBlock.updateShape(world,pos)` reads that position's `FACING` axis and writes one of two boxes. Inherited collision collection later reads the current fields (`Block.addCollisions` -> `getCollisionShape`) without refreshing them. Camera `Block.rayTrace` and rendering can call `updateShape`, so an intervening write for P can affect the later movement read for Q as described by the accepted old lifecycle report.

In 1.9 and 1.9.4, `Block` no longer exposes the six mutable per-instance bounds or the old `updateShape(WorldView, BlockPos)` shape writer for these providers. Each `BlockState` resolves `getShape(world,pos)` / `getCollisionShape(world,pos)` through its `StateDefinition` to the block provider. `ChestBlock.getShape(state,world,pos)` checks the world neighbors at the requested position in the same N/S/W/E first-match order and returns the corresponding static box (or the single-chest box). The old neighbor-sensitive result is therefore a position-time provider result, not a remembered result from a camera query at another coordinate. It is still allowed to depend on the current world neighborhood. `AnvilBlock.getShape(state,world,pos)` selects its static box from the requested state's `FACING` axis. In both versions, base `Block.getCollisionShape(state,world,pos)` delegates to `state.getShape(world,pos)`; base `Block.addCollisions` obtains that value for the scanned position before translating and intersecting it with the entity query box. The same state shape provider is used by `Block.rayTrace` for its ray intersection.

The 1.9.4 provider methods and inherited query path retain these semantics. No per-position bounds refresh or movement-time stale shared-bounds read was found in the paired sources.

## Call gates and separate ray operation

The old movement read remains `Entity.move` -> `World.getCollisions` -> block collision callback -> inherited collision-shape getter. The 1.8.9 ordering from the accepted report is: local camera `pick` may refresh shared bounds before world entity ticking, then player movement reads them later. In 1.9/1.9.4 the same style of tick pick and movement collision calls exists, but the earlier pick calls a state ray provider which computes the shape for each visited state/position. Its result is not retained as collision input; when movement subsequently scans another cell, that cell's state provider is evaluated for that cell.

1.9/1.9.4 `Entity.rayTrace` still calls `World.rayTrace(..., false, false, true)`. The ray loop's `ignoreBlocksWithoutCollision=false` gate means it does not first reject cells by an empty collision-shape test, and it then invokes virtual `BlockState.rayTrace` / block ray provider. This resembles the old camera call's broad cell eligibility in that particular respect, but it does not establish equal DDA traversal, overrides, hit result or operation ordering. Do not infer a historical ray adapter from the collision-shape contract.

At the 26.2 endpoint, the player movement path asks `CollisionGetter.getBlockCollisions(source,box)`, which creates a `CollisionContext` from the entity and enumerates `BlockCollisions`; block state collision shapes may therefore be context-sensitive and are not interchangeable with outline shapes. Picking uses `BlockGetter.clip(ClipContext)`, which obtains the clip-selected block shape, clips it, then separately checks an interaction shape for hit-direction adjustment and compares against the fluid result. A modern `clip`/outline result is not a substitute for the movement collision provider. Exact 26.2 `BlockBehaviour.BlockStateBase.getCollisionShape(level,pos,context)` dispatches to the block provider when uncached; shape caching exists for cacheable states, not as the old cross-position mutable singleton lifecycle.

## Inputs required for a legacy shape projection

- **Anvil (145):** the queried legacy state’s facing axis is sufficient for the old two-box choice. Damage is not read by `updateShape` and is not a shape input.
- **Chest (54) and trapped chest (146):** preserve their distinct legacy identities. At each queried position, evaluate legacy-compatible neighboring identities in N, S, W, E order with first-match precedence, then choose the matching directional box or single box. The 1.9 provider reads those neighbor states directly. At 26.2, chest shape is encoded using state `TYPE` plus `FACING`, so blindly using the outline shape or assuming a modern chest `TYPE` reproduces the old first-match rule is unsupported; projection needs the queried chest kind and the compatible neighboring arrangement (or an equivalent proof that the encoded modern states carry exactly that old rule).
- The active collision query's actual position and any shape-provider context are part of the call contract. A projection must supply the old result at that queried position. There is no `P` cache value to carry from ray/render to movement in 1.9+.

## Version applicability statement

The accepted conditional stale-bounds operation belongs to the exact 1.8.9 source contract. Checked 1.9 and 1.9.4 sources use per-state/per-position provider calls and cannot exhibit that shared cache lifecycle for these IDs. The 26.2 target likewise separates ray/outline/interaction and movement collision shape operations. The absence boundary is proven at checked 1.9; 1.9.4 confirms it persists at that concrete endpoint. Do not claim every patch release in 1.9 without intermediate inspection, or extend a 1.8.9 compatibility implementation beyond the last verified applicable version by endpoint inference alone.
