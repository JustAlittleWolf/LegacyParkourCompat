# Collision lane supplement: block contact, climbing, and fluid response

This supplement extends the immutable `report.md` coverage with the post-movement callback/dependency slice requested by the coordinator. Sources are the same exact, read-only 1.9.4/1.10.2 Ornithe Feather trees and manifests described there. Supplemental source hashes are in `callbacks-source-hashes.tsv`.

## Dispatch and order

`net/minecraft/entity/Entity.java`, `move(double,double,double)`: after axis clipping, it selects the support block at floor(x), floor(y−0.2F), floor(z); when that state is AIR, it checks one block below and substitutes fence, wall, or fence-gate support. It calls `checkFallDamage(dy,onGround,state,pos)`, zeroes horizontal velocity components clipped by the sweep, then calls `beforeCollision(world, entity)` when the requested vertical `h` differs from resolved `dy`. Step contact is gated by `makesSteps() && !bl && !isRiding()` and block `!= LADDER` for vertical distance counting; `onSteppedOn(world,pos,entity)` is called only when selected `block2 != null && onGround`. Footprint block callbacks run after that in `checkBlockCollisions()` over integer coordinates from `floor(min + .001)` to `floor(max − .001)`, inclusive, only if the whole region is loaded. It invokes `Block.onEntityCollision(world,pos,state,entity)` for every block state in the resulting box. Callback exceptions are reported and rethrown as a crash, not suppressed. Compared dispatch, gates, scan order, epsilon and callback order are equivalent across the pair.

`net/minecraft/block/Block.java`: default `onSteppedOn`, `onEntityCollision`, and `beforeCollision` are no-ops on both sides. No provider overrides `beforeCollision` in either release. Existing `onSteppedOn` and `onEntityCollision` provider method bodies and registration/call sites are unchanged. Override providers are: `AbstractPressurePlateBlock`, `ButtonBlock`, `CactusBlock`, `CauldronBlock`, `CobwebBlock`, `DetectorRailBlock`, `EndPortalBlock`, `LilyPadBlock`, `PortalBlock`, `RedstoneOreBlock`, `SlimeBlock`, `SoulSandBlock`, `StairsBlock`, `TntBlock`, `TripwireBlock`. All paired files have identical SHA-256 except files whose unrelated non-callback code changed: `Block.java`, `EndPortalBlock.java`, `PortalBlock.java`, and `RedstoneOreBlock.java`; inspection of their callback methods found no change. `MagmaBlock` newly appears in 1.10.2 with `onSteppedOn` damage behavior; it is a newly introduced block and its callback is damage only, outside the assigned historical-era existing-block movement scope.

## Climb and fluids

`LivingEntity.isClimbing()` and its `canClimbTrapdoor` helper read the current block at floor(x), floor(shape.minY), floor(z); spectators return false; otherwise ladders/vines are climbable, plus an open trapdoor aligned with a ladder below. The method body, lookup order, state gates, and helper are identical in both releases. Ladder/Vine providers have no contact callback override; shape / vine-state logic was already inventoried in the primary report.

`Entity.isInWater()` tests the grown-down, contracted entity box and calls `World.applyLiquidDrag`; `Entity.isInLava()` and `isInWaterOrRain()` preserve their respective block/material predicates. `World.applyLiquidDrag`, `containsLiquid`, `containsLiquid(Box,Material)`, and the flow vector/velocity accumulation loop were compared. Bounds floor/ceil, loaded-area gate, x/y/z loops, liquid material/state level tests, `LiquidBlock.getHeightLoss`, accumulation order and threshold are equivalent. A double local initialized to `0.014` is inlined as `0.014` in 1.10.2; expression precision/order is unchanged. Paired liquid provider behavior was not found to change in the reviewed methods. No resource-tag dependency occurs in this source-era contact dispatch; liquid levels are vanilla state properties.
