## Beacon effect: malformed storage versus legal selection

The only changed movement-state producer under discussion is `net/minecraft/block/entity/BeaconBlockEntity.java` (1.8.4 SHA-256 `dc4a5b60ec087b2f4715769dfb242a20b319eab76309130b711cf767327ac361`; 1.8.5 SHA-256 `a8be3009efe15803df64b9e88b54cfb8e4033946d1c478b64ea0dcf08ab2a1cf`). As reported, 1.8.4 `readNbt` and `setData` preserve arbitrary primary/secondary numeric IDs, whereas 1.8.5 filters both through `getBeaconEffect`, whose accepted IDs are exactly Speed, Haste, Resistance, Jump Boost, Strength, and Regeneration. The common `spreadEffects` path only runs in an active server-world beacon with positive levels and primary ID, and adds the selected effect to nearby players.

The normal selection path is constrained to the same six effects: `BeaconBlockEntity.EFFECTS` at line 32 enumerates them; unchanged `net/minecraft/client/gui/screen/game/inventory/BeaconScreen.java` builds buttons from those arrays (1.8.4 lines 51–85) and submits only the chosen button ID (lines 104–129). Thus a normal UI selection cannot choose Slowness (ID 2). The concrete discrepancy requires malformed or externally supplied persisted beacon state (e.g. `Primary: 2`) or an equivalent non-UI `setData` caller. The source establishes that 1.8.4 can spread Slowness in that state and 1.8.5 clears it; `StatusEffect.java` is byte-identical (SHA-256 `f9bb4d1839337229cb6f6d8dc9ae17a49cfad757a42388e00abbaa68be2b21a3`) and registers Slowness with a `MOVEMENT_SPEED` modifier of `-0.15F` (lines 28–31). This is a changed server-side effect producer, not a changed client movement operation.

## Received status and attribute state on the client

The status path requires a precise client/server distinction. `ServerPlayerEntity` sends `EntityStatusEffectS2CPacket` when a server player effect is applied (the supplied report cites lines 772–780); the packet class is hash-identical across the pair (`EntityStatusEffectS2CPacket.java`, SHA-256 `a7513a7f748875fd3f1a282cfb0f9550772d9bc41503d2b85cf9b4e23528b171`). The unchanged client handler (`ClientPlayNetworkHandler.java`, SHA-256 `7fa3d587325068eaa158526cb59e4850b704ac237938df6592d1a09148db40c3`) resolves the entity, creates the received effect, and calls `LivingEntity.addStatusEffect` for a living entity (lines 1133–1142).

However, the unchanged `LivingEntity.onStatusEffectApplied` applies the effect's attribute modifiers only when `!world.isClient` (lines 578–582); receiving that effect on the client does not itself install Slowness's movement-speed modifier. Client movement speed is read from `PlayerEntity`'s `MOVEMENT_SPEED` attribute (same file hash both endpoints, `e66cb294fc93118148a444bbafdf4dd57cbf66a23d69b1e8892cefccc690ab88`, lines 449–459 and 1297–1300). The client receives the authoritative attribute values/modifiers through `EntityAttributesS2CPacket` and `ClientPlayNetworkHandler.handleEntityAttributes` (lines 1581–1605); packet source is hash-identical (`EntityAttributesS2CPacket.java`, SHA-256 `b24f98567111cb698abb89770b24607000a6b8c5b2d2a970db076ee69e53ce41`).

Accordingly, if the server-side beacon delta leads to different status and/or attribute packets, those are unequal received movement-relevant inputs. The difference may matter to ordinary play or a server/client divergence analysis, but it is not a same-input client movement difference. Under equal received effect state, equal received movement attributes, and equal world/block/player state, this BeaconBlockEntity change has no remaining client movement path: its changed methods filter server-owned selection/storage state, while the client effect consumer and movement-speed reader are unchanged. Equal received attribute state is the important condition because this 1.8.4 → 1.8.5 pair also contains the separately identified `EntityAttributes.java` delta.

## EntityAttributes disposition and packaged defaults

`net/minecraft/entity/living/attribute/EntityAttributes.java` differs (1.8.4 SHA-256 `945f39931934b378359d428a2f0fb0b57c97bb2e162dcec7e5d8562efaf663aa`; 1.8.5 SHA-256 `573689391528a81df3a1e221cc5055c4fbc30b3ad3a55adc0acf14647b5456c0`). It is the movement-speed attribute-cap operation already dispositioned as accepted in the supplied ordinary report; this supplement reuses that disposition and does not redo or broaden its evidence. When assessing the Beacon candidate, hold the received attribute state equal so the two independent questions are not conflated.

For a narrow packaged-resource check, I enumerated all entries in the provenance-matched cached client JARs and compared entry content hashes: each has 5,597 files; all 5,597 entry paths match and 43 contents differ. Of those, the only non-class game resource difference is `assets/minecraft/texts/splashes.txt` (the other differing non-class entries are JAR signatures/manifest); there are no packaged data/registry JSON resources or movement-default resources changed. This addresses packaged default inputs only; it does not establish equality of user-installed resource packs or world/server state. The source-backed status-effect registry and beacon effect table are Java declarations: `StatusEffect.java` is identical as above, and the beacon UI table is explicitly six legal effects. The report's complete Java changed-path inventory accounts for `EntityAttributes.java` separately and identifies no other movement provider/registry source delta.

## Closure and remaining gates

- Same received status-effect and attribute state, plus equal movement-relevant world/player state: no 1.8.4 → 1.8.5 Beacon-driven client movement difference is established.
- The Beacon filter is a real behavior change only for unsupported stored/injected IDs (such as Slowness); legal UI selection does not reach it. Its possible consequence is conditional on server-side effect production and subsequent received authoritative state differing.
- `EntityAttributes.java` remains the separately accepted cap operation, reused without review here.
- No default packaged resource/registry input delta relevant to movement was found in the provenance-matched client JARs. External packs, malformed saves, and server-generated state are outside that default-input finding.
- The adjacent pair can be recommended for **same-input source freeze** with this supplement attached. This is not a claim of equal behavior for unequal server-produced state, not runtime parity, and not a determination of the separate 1.8.3 → 1.8.4 portal/vine boundary questions carried forward by the residual report.
