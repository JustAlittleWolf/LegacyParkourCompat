# Correction supplement: raw beacon effect payload reachability

This supplement corrects and sharpens the precondition wording in `184-185-same-input-closure/report.md`. It is bound to the same canonical read-only Ornithe Feather Gen2 build 2 sources reviewed there. It preserves the original report and independent review.

## Raw `MC|Beacon` input reaches `setData`

In 1.8.4, `net/minecraft/server/network/handler/ServerPlayNetworkHandler.java` reads two raw integers from an `MC|Beacon` custom payload and, if the player currently has a `BeaconMenu` and its payment slot contains an item, calls `inventory.setData(1, k)` and `inventory.setData(2, l)` without validating either effect ID. The relevant path is lines 1046–1059; source SHA-256: `c2de662af504d7128a855efd1b105097667f662a80919f569bdc922787d5197a`.

The 1.8.4 target `net/minecraft/block/entity/BeaconBlockEntity.java` stores those values directly in `setData` (lines 327–337) and likewise accepts NBT `Primary`/`Secondary` values without filtering in `readNbt` (lines 206–210); source SHA-256: `dc4a5b60ec087b2f4715769dfb242a20b319eab76309130b711cf767327ac361`. Thus a client that sends primary effect ID 2 through the existing channel can set Slowness when the menu/payment gates hold. This is a concrete injected-packet precondition in addition to malformed or externally supplied persisted beacon NBT.

The vanilla selector still offers only the six `BeaconBlockEntity.EFFECTS` entries (1.8.4 lines 31–33; `BeaconScreen.java` lines 51–87 construct buttons from that table and lines 105–128 submit its selected IDs). `BeaconBlockEntity.java` SHA-256 is `dc4a5b60ec087b2f4715769dfb242a20b319eab76309130b711cf767327ac361`; unchanged `BeaconScreen.java` SHA-256 is `85a485004f675d7bbfcc7638f2434e663db4686b51121a72d4dbeb2b0d555bec`. Therefore ordinary vanilla UI selection cannot produce ID 2, but the server's existing custom-payload handler accepts it from a nonconforming client under the stated menu/payment gates.

## 1.8.5 filter and movement-state consequence

The 1.8.5 custom-payload handler still reads and forwards the raw integers under the same gates (`ServerPlayNetworkHandler.java`, lines 1076–1089; SHA-256 `de2a90e177d03d7ce674c8e93ce1d730b036a4e05d3ec0819932087e41166692`). The changed `BeaconBlockEntity.java` then applies `getBeaconEffect` in `setData` (lines 343–353), which accepts only Speed, Haste, Resistance, Jump Boost, Strength, and Regeneration (lines 205–219); unsupported ID 2 becomes 0. Its source SHA-256 is `a8be3009efe15803df64b9e88b54cfb8e4033946d1c478b64ea0dcf08ab2a1cf`. `readNbt` applies the same filter to persisted primary and secondary values (lines 222–226).

The effect spread remains server-world-only and requires an active beacon, positive levels, and a positive primary ID (`BeaconBlockEntity.spreadEffects`, lines 56–79 in both releases). Slowness remains effect ID 2 with a `-0.15F` `MOVEMENT_SPEED` modifier (`StatusEffect.java`, lines 28–31; identical source SHA-256 `f9bb4d1839337229cb6f6d8dc9ae17a49cfad757a42388e00abbaa68be2b21a3`). On the server, `ServerPlayerEntity.onStatusEffectApplied` sends `EntityStatusEffectS2CPacket` (lines 772–775; identical source SHA-256 `047158bda6fa8fe2ea8a097972c098c5abe492ffbbe280006ae7592cd97fbb81`), while the effect modifier is applied under `!world.isClient` (`LivingEntity.java`, lines 578–582; identical source SHA-256 `082831c6578e3a70fa6cea5b90bc3eefc26678259b66334470de22b90b5b0e4e`). Tracked attribute changes are sent separately in `TrackedEntity.java`, lines 264–271 and 317–323 (identical source SHA-256 `c8f4c2115e2bd348c85be8cc4a35f18eece8edcce5560989dfa45cacb39f9b15`); the client applies `EntityAttributesS2CPacket` values and modifiers in `ClientPlayNetworkHandler.handleEntityAttributes`, lines 1581–1605 (identical source SHA-256 `7fa3d587325068eaa158526cb59e4850b704ac237938df6592d1a09148db40c3`). `PlayerEntity` reads its movement speed from `MOVEMENT_SPEED` (lines 449–459 and 1297–1300; identical source SHA-256 `e66cb294fc93118148a444bbafdf4dd57cbf66a23d69b1e8892cefccc690ab88`).

This is a changed server-side effect producer/filter that can result in different received status and attribute state. Such state is an unequal client movement input and is excluded from same-input client movement equivalence. Preserve the pair recommendation only conditionally: under equal received effect state, equal received movement-attribute state, and equal movement-relevant world/player state, this Beacon change establishes no remaining client movement difference. This supplement does not alter the separate disposition of `EntityAttributes.java` or claim pair-wide freeze by itself.
