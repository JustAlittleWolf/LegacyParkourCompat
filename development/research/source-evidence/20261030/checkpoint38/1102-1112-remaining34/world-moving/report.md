## Lower-Y collision collector and moved-fence provider reach local-player pose

1.10.2 `World.getCollisions(Box)` (`net/minecraft/world/World.java:1022–1059`) scans x/z columns with `q`; for an edge column (`q == 1`) it skips both `r == k` and `r == l - 1`. 1.11.2 routes this boolean query through the shared private collector (`World.java:974–1001,1058–1059`), which skips the upper endpoint for edge columns but admits the lower endpoint. Its state call remains `BlockState.addCollisions(..., entity=null, forceShape=false)` and returns as soon as any collision box is appended.

This boolean query is on the actual player pose writer path in both versions: `PlayerEntity.tick()` calls `updatePlayerPose()` (`PlayerEntity.java:249–250` newer; `250` older), and `LocalClientPlayerEntity.tick()` reaches the superclass tick on the loaded client-player path (the paired direct-response audit records both exact callers). `updatePlayerPose()` builds a candidate box at the current minimum corner with width 0.6 and target height 1.8 for standing, then calls `world.getCollisions(box)` before `setSize` (`PlayerEntity.java:295–318` newer; `296–319` older). The query has no logical-side gate. Thus this is a local-player pose/dimension decision, not the excluded bed-respawn boolean query.

The moved fence exposes both changed inputs. For the audited moving entity at cell `(4,0,4)`, facing east, retracting at progress `0.5`, the east-connected fence arm translates to world bounds `[5.125,5.5] × [0,1.5] × [4.375,4.625]`. A standing candidate player box `[5.2,5.8] × [1.1,2.9] × [4.2,4.8]` strictly overlaps it. Its scanned cell `(4,0,4)` is on the collector's x-edge column and is the lower-Y endpoint (`k = floor(1.1)-1 = 0`). The old boolean collector skips it; the new collector visits it.

Provider behavior also changed: old `MovingBlock.getCollisionShape()` obtains `MovingBlockEntity.getShape()`, which translates the moved state's ordinary shape; old `MovingBlockEntity.getShape()` calls `movedState.getShape()` (`MovingBlock.java:134–137; MovingBlockEntity.java:80–89`). The east fence outline tops out at y=1.0, so the stated candidate box does not intersect that old box. New `MovingBlock.addCollisions()` dispatches to `MovingBlockEntity.addCollisions()` (`MovingBlock.java:135–139`); the moving entity calls the moved state with `forceShape=true` and translates its collision boxes (`MovingBlockEntity.java:318–345`). The east fence collision arm reaches y=1.5. Since the new World collector includes the lower endpoint, the boolean query sees this box and refuses the standing resize; the old query sees no such collision and permits it, subject to other cells being clear. This is a source-level pose-query consequence with a concrete reachable local-player caller. The query deliberately reflects both the collector and moved-provider changes; it does not attribute the result to either one alone or claim a complete prior-tick piston trajectory.

The list-returning `World.getCollisions(Entity,Box)` likewise reaches ordinary local-player `Entity.move` through the SELF travel solver. Its changed lower-Y edge gate and the old/new moved-fence providers therefore also change a collision-list input to local movement. The prior moving-fence audit correctly treated its earlier y=1.2 witness as combined: old outline top y=1.0 versus new collision arm top y=1.5, plus the changed lower-Y gate. The paired piston response closure separately establishes a concrete local-player moving-block response for the extending-stair case. No further solver trajectory is inferred for this distinct fence retraction layout.

## Client `setBlockEntity` order is closed as observer-only

The exact `World.setBlockEntity` order differs only in the non-ticking branch: 1.10.2 calls `addBlockEntity(blockEntity)` before `getChunk(pos).setBlockEntity(pos, blockEntity)` (`World.java:1783–1785`); 1.11.2 reverses the two calls (`World.java:1751–1753`). `addBlockEntity` adds to the world's active/ticking lists and, when `isClient`, synchronously calls `notifyBlockChanged` with the same block state as old and new (`World.java:1378–1388`; paired 1.11.2 lines 1379–1389). The only client `WorldEventListener` implementation is `WorldRenderer`; its `notifyBlockChanged` marks the surrounding render section dirty (`client/render/world/WorldRenderer.java:1890` old, `1889` new). The other listener implementation, `PathNavigationListener`, is path navigation and does not write player dimensions or movement state. No callback in this notification path runs local-player pose resizing or collision solving.

On return from `setBlockEntity`, both the World registration lists and chunk map contain the same block entity. Movement collision lookup uses `MovingBlock.getMovingBlockEntity()` → `WorldView.getBlockEntity(pos)` → the chunk's map; it does not query the World active-ticking list. The client pose/move queries run after this synchronous setter has returned, while the client `World.tickEntities()` later ticks the same registered moving entity without a side gate. The ordering can expose a transient difference to the render-dirty notification, but the observed receiver only marks rendering dirty; it cannot produce a different local-player movement or pose query result.

This path is reachable on clients during block-state receipt: paired `WorldChunk.setBlockState` bodies create a missing provider block entity and call `world.setBlockEntity` (`WorldChunk.java:472` in both). For moving blocks, client collision/pose code subsequently consumes the chunk's vanilla state plus the registered moving-block entity. The producer remains ordinary server piston/block-state creation and packet state/NBT; it is not historical movement emulation. The local client consumes that same vanilla state for its own movement collision and client ticking. No historical server physics is implied.

## Closure and limits

The prior-open `World.java` lower-Y collision-list/boolean collector dependency is now source-closed to local-player movement and pose queries. The reversed `setBlockEntity` registration order is closed as render-notification timing with no local-player movement consumer. The prior-open `MovingBlockEntity.java` moved-fence provider dependency is source-closed as a concrete changed local-player pose query, while its full retraction-to-player travel trajectory remains unasserted; the independently accepted extending-stair piston response stands unchanged. These closures are limited to the named dependencies and do not freeze the full pair, establish runtime parity, or change any source finding's intermediate patch boundary.
