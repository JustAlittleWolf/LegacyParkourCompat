# Independent audit: world and moving-block closure

## Verdict: ACCEPT WITH A BOUNDED REACHABILITY QUALIFICATION

I retraced the claimed 1.10.2 → 1.11.2 source paths in the read-only canonical Ornithe Feather trees. The lower-Y collector difference, the old/new moving-fence provider path, the player pose consumer, and the synchronous block-entity registration notification order are supported by the exact sources. The report's closure is appropriately narrow: it establishes a changed local-player standing-pose collision query for a concrete input state and closes registration order as non-movement notification timing. It does not establish a full retracting-piston trajectory that produces that state, and explicitly leaves that trajectory open. Do not promote the witness to a demonstrated end-to-end piston encounter without that missing trajectory evidence.

## Findings

### Boolean pose query: gate and provider differences are real

- `PlayerEntity.tick()` invokes `updatePlayerPose()` in both versions; the loaded-chunk branch of `LocalClientPlayerEntity.tick()` invokes its superclass tick. `updatePlayerPose()` forms the proposed box from the current box minimum corner with `(width,height) = (0.6,1.8)` in the standing case, calls `world.getCollisions(box)`, and applies `setSize` only when the query is false (`PlayerEntity.java:175–250,296–319`; `LocalClientPlayerEntity.java:152–154` older and `159–161` newer). This establishes an actual local-client pose consumer without relying on bed-entry or server movement.
- Older `World.getCollisions(Box)` computes `k=floor(minY)-1` and excludes both `r==k` and `r==l-1` when a scanned x/z column is an edge column (`World.java:1022–1059`). Newer `getCollisions(Box)` delegates to the shared collector with `entity=null`, `enforceWorldBorder=true`; on an edge column it excludes only `q==l-1`, so the lower endpoint is visited (`World.java:960–1010,1058–1059`). In the report's proposed box `[5.2,5.8] × [1.1,2.9] × [4.2,4.8]`, scan bounds make cell `(4,0,4)` an x-edge/non-z-edge column and the `y=0` lower endpoint. Old skips it; new visits it. The newer collector uses `BlockState.addCollisions(..., entity, false)`; the moving-block override then dispatches to its moving entity.
- The geometry arithmetic checks out for the report's stated east-connected moved fence and retracting progress `0.5`: the ordinary east outline reaches local x `1`, y `1`; the east collision arm is x `[0.625,1]`, y `[0,1.5]`, z `[0.375,0.625]` (`FenceBlock.java:25–50,59–80`). A half-block east translation from cell `(4,0,4)` puts the collision arm at `[5.125,5.5] × [0,1.5] × [4.375,4.625]`, intersecting the candidate box. The old `MovingBlock.getCollisionShape()` routes to `MovingBlockEntity.getShape()`, which uses `movedState.getShape()` and unions current/last outline boxes (`MovingBlock.java:134–137`; `MovingBlockEntity.java:80–89`). Its vertical maximum stays `1.0`, so it cannot intersect a proposed box whose minimum Y is `1.1`. In 1.11.2, `MovingBlock.addCollisions()` dispatches to the entity, which supplies translated collision boxes (`MovingBlock.java:135–139`; `MovingBlockEntity.java:318–345`). For the reported non-source fence case the piston-head source special case is inapplicable; the fence collision is queried with `forceShape=true` and then translated. Thus the changed boolean result on this query is supported by both interacting deltas, not attributed to either in isolation.
- The witness establishes a changed *pose decision input* if the stated player box, loaded chunk, moving block entity and moved fence state coexist. The local-player call route is exact. The inspected source does not establish that the precise retracting-piston/fence/player layout is dynamically produced by an ordinary tick history; the report correctly disclaims that broader trajectory.

### Collision-list consumer

The report's related list-query claim is consistent with the code path: `LivingEntity` travel calls `move(MoverType.SELF, ...)`, and `Entity.move` builds collision boxes through `world.getCollisions(this, ...)` in the solver. The list overload in 1.11.2 delegates to the same private collector, while the 1.10.2 list overload has the prior endpoint gate (`World.java:903–1019` older; `World.java:960–1050,1013–1017` newer; `LivingEntity.java` travel call sites; `Entity.java` movement solver). This confirms a player-motion query consumer exists. The report appropriately does not infer a trajectory for the distinct fence layout from this call path alone.

### `setBlockEntity`: changed ordering is closed for player movement

- The changed order occurs in the non-ticking branch after the same outside-height, null/removed, and ticking gates: 1.10.2 calls `addBlockEntity` then `getChunk(pos).setBlockEntity`; 1.11.2 writes the chunk map then calls `addBlockEntity` (`World.java:1767–1785` older; `1735–1755` newer). In the ticking branch both defer to `pendingBlockEntities` and have no ordering delta.
- On the client, `addBlockEntity` first adds to world registration/ticking lists, then calls `notifyBlockChanged` with identical current state arguments (`World.java:1378–1388` older; `1379–1389` newer). The client renderer callback only calls `setDirty` for the surrounding render region (`WorldRenderer.java:1890` older; `1889` newer). `PathNavigationListener` checks collision-shape equality and may recompute mob navigation; it does not run player pose or collision solving (`PathNavigationListener.java:22–47`). Its same-state checks see the same shape twice within each callback. Thus the ordering difference produces no player movement/pose consumer in this synchronous callback.
- After return, collision lookup of the moving block entity uses `World.getBlockEntity`/the chunk's block-entity map, while active ticking uses the world's tick list. The callback's render dirty mark is deferred rendering work; it does not call a player movement or pose routine. The shared `WorldChunk.setBlockState` path can call `world.setBlockEntity` for a missing required provider entity, making the registration path client-reachable, but this does not alter the above result.

## Limits / no new open gate

The named collector and provider dependencies are source-closed to the local-player pose query under the report's explicit state preconditions. The registration-order dependency is source-closed as non-movement callback timing. The exact retracting piston event sequence remains unproven and should remain outside the accepted claim; this matches the report's stated limit. This audit is not a full pair inventory, runtime parity result, or proof of intermediate patch applicability.
