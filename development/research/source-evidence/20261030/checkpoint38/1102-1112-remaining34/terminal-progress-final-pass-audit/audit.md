# Independent audit — terminal progress final pass (1.10.2 → 1.11.2)

## Verdict

**Supported as written; the paired player-history gate correctly remains open.** I found no source error in the stored-progress sequence, old-only terminal call, candidate eligibility, conditional X displacement, or the reason the conditional layout does not establish an ordinary paired history. The old call can produce the stated conditional push, but the reviewed source does not carry one common player AABB through the previous half-step responses and player tick into that final overlap. This is not evidence of unreachability.

## Evidence retraced

Sources are the read-only canonical `decompiled_minecraft/{1.10.2,1.11.2}/ornithe-feather` trees. Their ready markers identify the endpoint versions, Feather mapping artifacts and the same source-manifest hashes reported in the witness: 1.10.2 `91b0f478acb7b6f13463c35b268a30d2806f583402631a56f54ce2eb70d1ec71`; 1.11.2 `d908c2af76598ad26999563bfef0089f1d3c8c32483eee6b108f0defa2773df0`. The directly checked `MovingBlockEntity.java`, `World.java`, `Entity.java`, `WorldChunk.java`, `Box.java` and `PistonBaseBlock.java` hashes match the witness.

- **Progress and phase order.** In 1.10.2, `MovingBlockEntity.tick()` copies progress to `lastProgress`, and if below one adds/clamps `0.5F` before `moveEntities()`; on the subsequent tick it sets `lastProgress` to one, calls `moveEntities()` once more, then removes/completes the entity (`MovingBlockEntity.java:165–184`). `getShape()` unions the shapes at stored `progress` and `lastProgress` (`:80–89`). In 1.11.2, the half-step computes `f = progress + 0.5F`, calls `moveEntities(f)` before committing `progress = f`; the next tick removes/completes at progress one without a `moveEntities` call (`:272–290`). Both `World.tickEntities()` methods run the player/ordinary entity phase before iterating ticking block entities (`World.java:1270–1324`); on the client, the local player is added to the ordinary entity list by `Minecraft` and therefore is in that pre-block-entity phase once registered. The witness's distinction between stored progress for collision/response and interpolated render progress is also correct (`MovingBlockEntity.java:56–78` old, `:72–94` new).
- **Old candidate selection.** Old `moveEntities()` uses the moved shape box and calls `world.getEntities(null, box)` (`MovingBlockEntity.java:91–100`). The two-argument world overload supplies `EntityFilter.NOT_SPECTATOR` (`World.java:2156–2160`); chunk collection additionally requires `entity.getShape().intersects(bounds)` and excludes only the specified entity/filter (`WorldChunk.java:667–679`). Base `Entity.getPistonMoveBehavior()` returns `NORMAL` (`Entity.java:2306–2308`), and no player-class override exists in these sources. Thus an eligible nonspectator player strictly overlapping the queried box is a candidate; prior swept-area contact alone is insufficient.
- **Conditional -1.11 X response.** For an EAST retracting piston the old code selects the opposite direction, WEST. For the stated player box `[0.50, 1.10]` against the extended EAST base box `[0, 0.75]`, the old negative-X branch takes `entity.maxX - box.minX`, adds `0.01`, and multiplies by WEST's `-1`, yielding `-(1.10 - 0 + 0.01) = -1.11` (`MovingBlockEntity.java:91–147`; base shape `PistonBaseBlock.java:28–35,47–68`). In the regular old `Entity.move`, the negative-X clip only applies when the moving box is wholly on the obstacle's EAST side (`Box.java:143–160`, used by `Entity.java:514–537`). The example overlaps the base in X, so that base does not clip the request; a clear west corridor and no movement modifiers/gates are still required. The witness names these conditions and presents the box as conditional, not source-reached.
- **Why the history is still open.** The source proves the candidate and displacement only for an AABB already overlapping at final query time. It does not prove that the same paired local-player state survives the preceding `0.5 → 1.0` response (old union-shape push versus new swept response) and the subsequent player collision tick. The ordinary axis solver's separation-only clip cannot be promoted into a general depenetration or reachability proof. Keeping this gate open is the supported conclusion.
