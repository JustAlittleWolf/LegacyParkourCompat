## Paired source findings and dispositions

### Fluid-state reads, flow, heights and shapes

- `net/minecraft/world/level/material/FluidState.java`: 1.16.5 lines 32–108; 1.17.1 lines 34–114. Delegation for source/empty tests, amount, height, own height, flow, tags and fluid shape is unchanged. The 1.17.1 additions are amount constants and `isSourceOfType(Fluid)`; no existing movement consumer in this trace switches to it. Both `getShape` paths delegate to the fluid type.
- `net/minecraft/world/level/material/FlowingFluid.java`: 1.16.5 `getOwnHeight`/`getShape` lines 473–482; 1.17.1 lines 474–483. The existing amount-to-height division (`amount / 9.0F`) and full-source shape gate are unchanged. Diff in `canHoldFluid`, 1.16.5 lines 397–408 and 1.17.1 lines 398–407, replaces block-level tag/identity checks with equivalent block-state predicates for signs, ladder, sugar cane and bubble column; the material gates remain. The newly abstract `getAmount(FluidState)` declaration is an API refactor; Water/Lava implementations retain their amount logic.
- `net/minecraft/world/level/material/Fluid.java`, `WaterFluid.java`, `LavaFluid.java`: no changed movement flow/height/shape provider was found. Added pickup-sound methods are unrelated. `WaterFluid.beforeDestroyingBlock` changes the block-entity predicate but is resource/drop handling. `LavaFluid.isFlammable` changes its vertical query bounds to active build height; this is the already-closed dimension/minY query-admission topic and is not reopened here.
- `net/minecraft/world/level/block/LiquidBlock.java`: `getFluidState` and the fluid-level shape provider are unchanged. In `shouldSpreadLiquid`, 1.16.5 lines 130–154 loops all directions except DOWN; 1.17.1 lines 134–157 loops `DOWN, SOUTH, NORTH, EAST, WEST` and queries each opposite direction. These produce the same ordered neighbors (`UP, NORTH, SOUTH, WEST, EAST`), preserving water-contact checks and lava block replacement order. Bucket pickup API changes do not affect player movement.

### Bubble-column and liquid block providers

- `net/minecraft/world/level/block/BubbleColumnBlock.java`: both releases return a source water `FluidState` from `getFluidState` (1.16.5 line 84; 1.17.1 line 83), and the block remains registered without collision. The 1.17.1 rewrite changes column creation/repair scheduling (`onPlace`/`growColumn` become tick-driven `updateColumn`; neighbor updates schedule a five-tick block tick). Those paths create server world block states. They do not change the client player contact response; the entity callback below is unchanged. Under the fixed vanilla-state boundary, this is world-state production, not a historical player physics change.
- `net/minecraft/world/level/block/Blocks.java`: WATER, LAVA, SOUL_SAND, MAGMA_BLOCK and BUBBLE_COLUMN remain present at both endpoints. Their relevant provider registrations retain the old block classes/material/collision configuration. The BUBBLE_COLUMN registration is `Material.BUBBLE_COLUMN`, no collision, no drops at 1.16.5 lines 2608–2609 and 1.17.1 lines 2691–2692. No existing fluid registry entry or provider replacement was found in `Fluids.java` (same whole-file hash at both endpoints).
- `net/minecraft/world/level/block/SoulSandBlock.java` and `MagmaBlock.java`: scheduled bubble-column checks now call `updateColumn` with their block state instead of `growColumn(..., false/true)`. These again change server block-state production. `MagmaBlock.stepOn` keeps the same hot-floor damage gate; its new `BlockState` callback parameter is unused and the damage-source overload is outside movement scope.

### Player fluid contact and block callbacks

- `net/minecraft/world/entity/Entity.java`: 1.16.5 `onInsideBubbleColumn(boolean)` lines 1944–1955 and 1.17.1 lines 2103–2114 retain the same vertical velocity caps/deltas (`max(-0.3, y - 0.03)` for drag-down; `min(0.7, y + 0.06)` otherwise), write the same horizontal components and clear fall distance. `BubbleColumnBlock.entityInside` reaches this callback in both versions (1.16.5 lines 67–71; 1.17.1 lines 71–75). This is a direct client player response when the current block state is a bubble column, but its implementation is unchanged.
- `Entity.updateSwimming`: 1.16.5 lines 949–955 has the sprint/underwater/non-passenger entry predicate. 1.17.1 lines 1056–1064 adds `level.getFluidState(blockPosition).is(FluidTags.WATER)` on the not-already-swimming branch. Entity tick reaches this method; LocalPlayer inherits the Entity path. This is an actual source predicate delta, independently matching the prior 1.17.0–1.17.1 source inventory. Concrete runtime fluid/tag states satisfying the changed gate remain unverified because tag/resource payloads were not in the permitted source-tree inputs. Keep this as an unresolved candidate pending that gate; do not infer tag contents from the Java tag declarations.
- `net/minecraft/world/level/block/Block.java`: contact callback signatures gain a `BlockState` argument for `stepOn` (1.16.5 line 314; 1.17.1 line 364) and `fallOn` (1.16.5 line 347; 1.17.1 line 397). The base step callback remains empty. Base fall dispatch changes only because the damage API now requires `DamageSource.FALL`; damage calculation is excluded. Entity fall contact dispatch supplies the new state argument but makes no movement calculation change.
- `SlimeBlock` and `HoneyBlock` `fallOn`, plus `MagmaBlock.stepOn`, are signature updates with no changed player motion response in the paired method bodies. Slime bounce remains in `updateEntityAfterFallOn`; its override is textually unchanged at the compared body. Honey’s slide handling and thresholds are unchanged. The fall-damage call signature change is excluded.
- `CollisionSpliterator.getChunk` changes `i >> 4` / `j >> 4` to `SectionPos.blockToSectionCoord(i/j)` (same signed floor-to-section arithmetic). `CollisionGetter` renames/inverts `noBlockCollision` to `hasBlockCollision` while preserving its nonempty-shape meaning; the new `findFreePosition` helper is additive. `VoxelShape` adds clipped min/closest-point helpers and rewrites `findIndex` for ray clipping. These are collision-query infrastructure changes, not fluid-contact provider changes; this slice did not trace all general movement collision consumers, so they remain outside this bounded finding set rather than being asserted as a full collision audit.

### Tags and state predicates

- `net/minecraft/tags/FluidTags.java` retains the `WATER` and `LAVA` named tags. Its Java helper moves to registry-based tag collection and adds `getStaticTags`; no named fluid membership changed in Java. `BlockTags.java` adds new unrelated named tags; existing names used in `FlowingFluid.canHoldFluid` remain. Exact tag/resource contents were not inspected because the assignment permits only exact Mojmap source trees and the decompiled Java trees do not include those payloads.
- `BlockBehaviour.BlockStateBase.is(Block)` and `.is(Tag<Block>)` move from delegating through `Block` helpers to direct identity / tag containment. `FlowingFluid` changes its callers accordingly. For the built-in `Block` and `Tag` APIs these preserve the same predicates. Additional block-state properties mostly support newer blocks; no old fluid state definition changes were found.
