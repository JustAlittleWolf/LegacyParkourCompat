## Jump Boost discrepancy requiring reconciliation

### Corrected source claim and cutover

The latest pool corrections define one fixed-stream witness: the 1.15.2 server first sends ordinary LEAPING (amp 0, long duration), then STRONG_LEAPING (amp 1, shorter duration), later restores amp 0, and eventually removes the weaker effect. The 1.14.4 client's `MobEffectInstance.update()` ignores the lower-amplifier restoration even when longer; its client `LivingEntity.tickEffects()` retains the local amp-1 instance at duration zero until the remove packet. 1.15.2's hidden chain restores amp 0 locally. During the remaining weak-effect duration, a grounded jump therefore gets amp 1 / `+0.2F` on the old client and amp 0 / `+0.1F` on the new client. The corrections explicitly exclude the unreachable strong-first/weak-longer packet premise, compare both client procedures under the same 1.15.2 packet stream, and bound the divergence to the window before the later removal packet.

The source cutover is closed at stable 1.15.2 for the checked releases: `MobEffectInstance.java` SHA-256 is `80cc2a91b77d4687a9b36bcb38e3107e3b2b8f859c69893e4eec0e98b4941b5e` and byte-identical in 1.14.4, 1.15, and 1.15.1; 1.15.2 is `4999d12cd468e402506f067dbd8694b1c8125dd9131e4f8a2fcc1848f616f180` and contains the new `hiddenEffect` field/update/tick fallback. `ClientPacketListener.java` is byte-identical across 1.15, 1.15.1, and 1.15.2 (`d806d286af4b93d7c61c3c884f344a5870ce1871fb0a811506031adf78fafc30`), so the newer mechanism is effect-state logic rather than a newly introduced packet path. Exact source reports and follow-ups are in `.native-source/20261030/1144-1152-pool33/findings/jump-effect-hidden-fallback*.md`.

### Product contract and current-target packet path

`JumpBoostHiddenFallback@V1_15` and its `JumpBoostFallbackMixin` are registered; the class observes `LivingEntity.addEffect(MobEffectInstance, Entity)Z` and `tickEffects()V`. But the current target is 26.2, whose exact client packet route does not call that `addEffect` overload. `ClientPacketListener.handleUpdateMobEffect(ClientboundUpdateMobEffectPacket)V` constructs each packet effect with `hiddenEffect = null` and calls `LivingEntity.forceAddEffect(MobEffectInstance, Entity)V`. `forceAddEffect` directly replaces the active map entry, copies blend state, and calls `onEffectUpdated`; it does not call `MobEffectInstance.update`. The later `handleRemoveMobEffect(ClientboundRemoveMobEffectPacket)V` calls `removeEffectNoUpdate(Holder<MobEffect>)`.

Consequences for the weak-first → strong → server-restored-weak stream:

- The mixin's `addEffect` HEAD/RETURN injections do not run for either packet update, so `JumpBoostHiddenFallback.effectUpdated` does not observe the packet replacement or the later removal.
- `tickEffects()` and the mixin's HEAD/TAIL injections do run client-side. The current `forceAddEffect`-created instance has no hidden effect, so `MobEffectInstance.tickClient()` leaves the strong amp-1 entry at duration zero if that tick happens first. HEAD/TAIL see amp 1 on both ends of that tick. If/when the server's amp-0 update arrives, `forceAddEffect` replaces it between ticks; later HEAD/TAIL see amp 0 on both ends. The state machine therefore cannot detect a hidden downgrade from that stream.
- After the amp-0 packet reaches the current target, native `getJumpBoostPower()` produces amp 0's `+0.1F`. The corrected pre-1.15.2 procedure must keep the lower update from replacing amp 1 and continue using amp 1's `+0.2F` until the removal packet. This is an actionable profile mismatch even though the product's existing hidden-fallback mixin is present.

There is a second, distinct profile requirement. The exact 1.15.2 receiver calls `addEffect`, whose `MobEffectInstance.update(MobEffectInstance)Z` stores the weaker-longer instance as a hidden fallback; its client tick restores that instance locally. Current 26.2 `MobEffectInstance.update` also has a hidden chain and `tickClient()` downgrades it, but the network receiver's force-replacement path bypasses both operations. For selected `V1_15_2`, product currently has no profile-specific operation restoring this incoming-effect behavior. Do not infer 1.15.2 hidden-chain parity merely because 26.2's effect class still contains a hidden field.

The existing return-injection policy is not a substitute for either receiver contract: `JumpBoostHiddenFallback.afterEffectTick` only toggles a `restoredFallback` flag; `JumpBoostFallbackMixin.legacy$ignoreRestoredJumpBoost` overwrites `getJumpBoostPower()` with `0.0F` when that flag is set. For profiles resolving `FloatJumpBoostAddition`, this suppresses the contribution entirely; for earlier profiles, `JumpBoostResponseHook.jumpPower()` can return the native base instead of the historical amp-1 contribution. Also, because the packet path is force-replacement, the state flag normally is not set by this corrected packet sequence in 26.2.

### Minimal patch requirement and source boundary

Reconcile the actual current receiver seam, not only the old `addEffect` callback: `ClientPacketListener.handleUpdateMobEffect(ClientboundUpdateMobEffectPacket)V` → `LivingEntity.forceAddEffect(MobEffectInstance, Entity)V`. Keep this as one independently resolved received-effect operation with source-version providers, rather than hard-coding exact profile checks inside a mixin. Preserve separate profile behavior at the established boundary:

- For profiles before `V1_15_2`, match the old lower-amplifier ignore and duration-zero active entry through the later explicit Jump Boost removal. Do not create/use the current hidden fallback for these profiles. The ordinary strong-effect update still replaces the earlier weak amp, and a later lower amp update must not replace it.
- For `V1_15_2`, restore the observed 1.15.2 client `addEffect`/`MobEffectInstance.update` path so weak-then-strong packet updates build the hidden chain and local client expiry restores amp 0. The 26.2 `update`/`tickClient` implementation appears to contain this operation, but the exact current effect behavior and any relevant side effects still require independent source review before relying on it.
- At the jump consumer, leave the selected profile's existing numeric operation/order intact. The pre-1.15.2 case should expose the active amp-1 contribution (`+0.2F`) rather than zero; the 1.15.2 hidden-chain case should expose amp 0 (`+0.1F`) after its local fallback. Scope remains local-player Jump Boost and this received-effect sequence; this does not authorize broad effect-packet replay or server physics.

The current `JumpBoostHiddenFallback@V1_15` registration is the natural old-side hook candidate: `V1_15` is selected for older profiles and 1.15/1.15.1, while a new provider annotated at `V1_15_2` would be selected for that exact boundary. Preserve this registration split only if the packet operation's interface expresses the real receiver/update contract; the present state-and-suppress response contract does not.
