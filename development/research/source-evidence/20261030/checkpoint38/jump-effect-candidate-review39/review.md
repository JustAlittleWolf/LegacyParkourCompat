# Independent review: jump-effect receiver candidate 38

**Candidate:** `.native-candidates/jump-effect-receiver38`, commit `7399f4026f37481e521faf87a8701f34a6c1150e`

**Decision: REQUEST CHANGES before product integration.** The receiver mechanics are largely consistent with the compared source, but integration must reconcile the existing jump-boost fallback state/response and must keep the implementation within the accepted finding's bound. Runtime parity remains unverified.

## What checked out

- The candidate observes only the local player's Jump Boost update/removal packet fields after vanilla handling (`ClientPacketListenerMixin.java:25–50`). This matches current 26.2 `ClientPacketListener.handleUpdateMobEffect` / `handleRemoveMobEffect`, whose update path calls `forceAddEffect` and therefore does not preserve a hidden chain in the vanilla map. The cached 26.2 merged/deobfuscated JAR exposes both handler methods, `LivingEntity.tickEffects`, `LivingEntity.getJumpBoostPower`, and the packet accessors used by the mixin.
- `LegacyJumpBoostEffectReceiver` (`:30–58`) retains a stronger amplifier against lower-amplifier updates, extends only an equal-amplifier duration, and holds a zero-duration entry until REMOVE. These are the relevant 1.14.4 and 1.15.1 client receiver/read semantics in the accepted audit.
- `HiddenJumpBoostEffectReceiver` (`:68–108`) follows the 1.15.2 `MobEffectInstance.update` branches: retain a shorter-duration active effect under a stronger incoming effect, update/merge a longer hidden instance, decrement hidden duration during active ticks, and restore it when the active duration reaches zero. Shadow ticking at `LivingEntity.tickEffects` tail is before the local player's later jump stage; the restored amplifier is consequently available for that tick's jump read.
- The raw Jump Boost power expression is `0.1F * (amplifier + 1)`, consistent with the current 26.2 getter and the source-reviewed jump contribution. The candidate does not mutate Minecraft's active-effect map or model health/rendering.
- The resolver's closest-applicable rule selects the receiver change at `V1_15` for 1.14/1.15, `V1_15_2` for 1.15.2, and the no-op `V1_16` fence for 1.16 onward. `CURRENT` resolves to no historical changes.

## Required reconciliation

1. **Consolidate the existing hidden-fallback state and response.** Product already has `change/v1_15/JumpBoostHiddenFallback.java` implementing `JumpBoostFallbackStateHook` and `JumpBoostResponseHook`, with capture/suppression in `JumpBoostFallbackMixin.java`. The candidate adds a second receiver shadow and another `getJumpBoostPower` return writer. These are independently resolved hook types, so both can be active at once (the old response remains applicable at 1.15.2+ even though the new receiver has a 1.15.2 change). Integrate one authoritative effect-state/read path and remove or explicitly neutralize the duplicate old state/suppression for the receiver-covered profiles. In particular, prove that `JumpBoostFallbackMixin` cannot overwrite the candidate's reconstructed contribution with `0.0F`, and that the 1.13 direct-raw-effect `JumpPowerHook` path remains unaffected for older selections.
2. **Respect the accepted applicability bound.** The immutable audit accepts the difference only for the weak-first stream with weaker remaining duration `w > 1800`, a shorter stronger update, and the local strong-expiry-before-REMOVE window; it explicitly says implementation authorization is the pre-1.15.2 receiver behavior under that condition and excludes strong-first / `w <= 1800` cases. The candidate currently reconstructs and substitutes a receiver state for every local-player Jump Boost packet sequence and every selected profile resolved to these changes. Narrow its application to the accepted state/window, or provide a separately frozen and independently accepted source finding that authorizes this broader receiver emulation. Preserve normal native reads outside the accepted behavior.
3. **Record lifecycle handling in the integration.** The per-player weak maps naturally become collectible across current 26.2 respawn because `handleRespawn` creates and installs a new `LocalPlayer`, but this was only source-inspected, not runtime-tested. Confirm join/respawn effect packets seed the new receiver before movement reads; if a native effect can predate receiver observation, define a bootstrap/reset path that does not infer hidden history from the modern force-replaced map. Profile switching remains undefined by project policy.

## Limits

This is a static implementation/product reconciliation review. It does not verify runtime packet scheduling, tick-for-tick parity, or client lifecycle behavior in a game. No build, tests, game launch, or source generation was run.
