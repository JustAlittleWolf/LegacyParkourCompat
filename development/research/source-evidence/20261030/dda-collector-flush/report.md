# DDA stage labels and inside-effect collection: 1.21.2/1.21.3 vs 26.2

## Scope and verdict

This closes the bounded ordinary `LocalPlayer` post-travel block-contact path: DDA visit/stage labeling, position deduplication, synchronous block callbacks, fluid callbacks, and `InsideBlockEffectApplier.StepBasedCollector` timing. It does not revisit the old 17-clip-body cutoff, query-box or shape-predicate math, movement-record production, or runtime parity.

**Verdict:** Keeping an old position visitation sequence while feeding 26.2 callbacks through its `StepBasedCollector` is not source-faithful to 1.21.2/1.21.3. The old path has no callback stage numbers or collector and calls qualifying block callbacks synchronously in visitation order. 26.2 assigns DDA iteration labels, groups effects by label, appends type-ordered effects to a deferred queue, deduplicates typed effects per step, and adds a swept-fluid callback. Some block callbacks still write movement state immediately in 26.2, so those writes remain interleaved with the scan; collector-submitted writes execute only after the scan.

The source contract for a historical path must preserve the old candidate/visit and eligibility gates as separately accepted by their own audit, invoke `BlockState.entityInside` then virtual `onInsideBlock` synchronously at each accepted block, add its `BlockState` to the old sweep summary only after both callbacks return, and omit swept `FluidState.entityInside` callbacks. Do not route those visits through `StepBasedCollector` or apply collector type coalescing/flush semantics. Any modern callbacks reused by a compat path need explicit per-callback historical semantics; retaining only position order is insufficient.

## Source comparison

### Old traversal and callback contract

In 1.21.2/1.21.3, `Entity.applyEffectsFromBlocks(Vec3, Vec3)` appends the supplied segment to the live `movementThisTick` list and immediately calls `checkInsideBlocks`; after the sweep it summarizes collected block states for fire/lava, clears movement and block-state sets, then updates fire ticks/sound (`Entity.java:740–767`). In the ordinary locally controlled player path, `LivingEntity` reaches this after travel (`LivingEntity.java:2771–2776`; `LocalPlayer.tick` enters the normal super tick chain at `LocalPlayer.java:189–192`).

Old `checkInsideBlocks` iterates movement records, then consumes the ordered `BlockGetter.boxTraverseBlocks(from,to,box)` iterable. It aborts if dead, ignores air, and calls `visitedBlocks.add(pos)` **before** checking whether a partial inside-shape was crossed. A newly seen non-air position calls `BlockState.entityInside`, then `onInsideBlock`, both synchronously; only after they return is the block state added to `blocksInside` (`Entity.java:1038–1078`). Thus a failed partial-shape test still reserves that position for the remainder of the sweep. A callback's immediate entity or world writes can be seen by later position callbacks and later eligibility checks. The only old DDA counter is internal to `BlockGetter.addCollisionsAlongTravel`; it is not passed to the entity callback. There is no per-position `step` argument or collector in these sources (`BlockGetter.java:172–247`; `Entity.java:1047–1070`).

The old swept pass invokes block-state callbacks only. `BlockGetter` produces `BlockPos` values, and the `Entity.checkInsideBlocks` body invokes `state.entityInside(...)` without calling `FluidState.entityInside`. Old fluid exposure/pushing is instead updated in `Entity.baseTick` before travel (`Entity.java:449`, `1295+`). Consequently, the old traversal does not have an equivalent of 26.2's swept fluid callback ordering or effect registration.

### 26.2 visit stages and collector lifecycle

26.2 `BlockGetter.forEachBlockIntersectedBetween` gives its visitor an integer iteration. For a sub-threshold move it supplies `0` to positions in the target box; otherwise start-box positions from `aabbAtTarget.move(travel.scale(-1.0))` use `0`, the collision walk increments the iteration for each accepted clip hit and supplies that iteration to all positions in that crossing slab, and tail target-box positions use `iterations + 1` (`BlockGetter.java:175–209, 211–284`). This is a stage label, not a count of callback-worthy blocks. Entity checks the per-call label against its remaining movement-iteration allowance, sets its returned progress from labels actually visited, and uses the label only when a qualifying block or fluid is about to callback (`Entity.java:1278–1304, 1308–1377`). The legacy visitor never exposed an equivalent label. The audited ordinary `LocalPlayer` path reaches this finalizer after travel under the local-authority condition (`LocalPlayer.java:227–234`; `LivingEntity.java:2765, 2804–2806, 3043, 3140–3145`).

For one qualifying position, 26.2 computes both `insideBlock` and `insideFluid`; it adds the position to the shared `visitedBlocks` set only if either is true. If the block condition passes, order is `advanceStep(iteration)` → `BlockState.entityInside(..., effectCollector, isPrecise)` → `onInsideBlock(state)`. If fluid also passes, the same position then does `advanceStep(iteration)` → `FluidState.entityInside(..., effectCollector)` (`Entity.java:1342–1365`). Because the label is unchanged for the cell, that second advance does not flush. A cell can therefore invoke both callbacks, block first, fluid second, with their registered typed effects coalesced into one stage.

`StepBasedCollector.advanceStep` calls `flushStep` only when the numeric iteration differs from `lastStep`; that method transfers the previous group's operations into the ordered `finalEffects` queue and does **not** execute them. The step is not forcibly closed at movement-segment or axis-segment boundaries, so equal labels at the end of one segment and start of the next remain one group. `applyAndClear` closes the last group only after the full block/fluid traversal, then executes the complete queue in order while the entity remains alive, clears `finalEffects`, and resets `lastStep` (`InsideBlockEffectApplier.java:32–95`; `Entity.java:949–965`). A stage group is queued in enum order `FREEZE`, `CLEAR_FREEZE`, `FIRE_IGNITE`, `LAVA_IGNITE`, `EXTINGUISH`. For each type it appends all registered `runBefore` consumers in registration order, appends the type's `apply` effect at most once because `effectsInStep` is an `EnumSet`, then appends all `runAfter` consumers in registration order. So typed `apply` calls deduplicate within a step; `runBefore`/`runAfter` calls do not. Different callback positions in a step can thus be reordered by effect type, while registrations of the same before/after class keep their local registration order. All such writes remain deferred until `applyAndClear` after the sweep.

On position deduplication, both generations share a per-sweep visited-position set, but mark at different times and under different conditions. Old code marks every non-air candidate before testing its partial block shape. 26.2 marks only after `(insideBlock || insideFluid)` succeeds. New fluid eligibility can reserve a position for both callback types; old had no fluid eligibility. These are observable deduplication differences even if an externally supplied sequence of candidate positions were held equal.

### Concrete callback families and entity/world writes

These examples show why preserving visit order alone cannot restore the old interleaving:

- **Fire:** old `BaseFireBlock.entityInside` adjusts fire ticks, calls `igniteForSeconds(8.0F)` and then `hurt(inFire, fireDamage)` directly at each visit (`BaseFireBlock.java:130–147`). In 26.2 the callback registers `CLEAR_FREEZE`, `FIRE_IGNITE`, and per-position `runAfter(FIRE_IGNITE, hurt)`; the type effects and hurt consumers run at a collector flush (`BaseFireBlock.java:131–141`; `InsideBlockEffectType.java:6–24`). Multiple fire callbacks in one step collapse `FIRE_IGNITE` to one write but retain one post-ignite hurt consumer per callback. The old path performs each fire's ignition and damage before the next block callback.
- **Lava and water:** 26.2 `LavaFluid.entityInside` and `LavaCauldronBlock.entityInside` schedule `CLEAR_FREEZE`, `LAVA_IGNITE`, and a `runAfter(LAVA_IGNITE, Entity::lavaHurt)`; the collector applies the type once per step but retains each lava-hurt registration (`LavaFluid.java:119–123`, `LavaCauldronBlock.java:47–58`). 26.2 `WaterFluid.entityInside` schedules `EXTINGUISH` (`WaterFluid.java:87–89`). The old swept callback body has no corresponding fluid callback. Legacy water-current clearing/pushing occurs in the earlier base-tick fluid update rather than as another DDA visit (`Entity.java:449, 1295–1324`).
- **Powder snow:** old `PowderSnowBlock.entityInside` immediately calls `makeStuckInBlock`, sets `isInPowderSnow`, may destroy the block when a burning player is eligible, and clears the shared on-fire flag on server (`PowderSnowBlock.java:60–88`). 26.2 keeps `makeStuckInBlock` inline, but registers destruction with `runBefore(EXTINGUISH)`, then `FREEZE` and `EXTINGUISH` (`PowderSnowBlock.java:62–103`). The `FREEZE` effect at flush sets `isInPowderSnow` and increments frozen ticks (capped at required ticks), so later same-stage callbacks observe the pre-flush frozen/snow state. The old callback writes those fields before scanning the next position.
- **Cauldron writes:** 26.2 layered water cauldrons register fire-driven `lowerFillLevel` as `runBefore(EXTINGUISH)` and then register `EXTINGUISH`; `lowerFillLevel` changes block state and emits a block-change game event (`LayeredCauldronBlock.java:85–104, 113–117`). Those world writes are queued during traversal and run after it, at the `EXTINGUISH` position in the final effect order, rather than being performed at that block's visit.
- **Callbacks that remain inline:** Honey still tests sliding and writes entity velocity/reset fall distance immediately in `doSlideMovement`; web still calls `makeStuckInBlock` immediately; precise bubble-column callbacks immediately call the entity's bubble movement response (`HoneyBlock.java:64–78, 103–137`; `WebBlock.java:27–41`; `BubbleColumnBlock.java:53–70`). These direct writes remain ordered by actual callback traversal, but that does not make the separately collected fire/freeze/fluid effects immediate or position-ordered.

## Implementable contract and limit

For an old-profile post-travel sweep, the source-grounded contract is:

1. Use the historical candidate order and traversal/cutoff/geometry rules from their independently bounded source review; do not infer equality with the 26.2 DDA stage labels.
2. Keep the old `visitedBlocks` insertion point: insert each non-air position before the historical block-shape gate.
3. At a qualifying position, synchronously invoke the block callback, then `onInsideBlock`, and only after success add the returned block state to the old inside-state summary. Preserve immediate callback writes and exception behavior in that order.
4. Do not invoke 26.2 swept fluid callbacks or defer callbacks through `StepBasedCollector`. Preserve the old post-sweep fire/lava summary and collection clearing at the historical boundary.
5. Keep this callback execution contract separate from query-box/shape eligibility, the old 17-clip-body cap, movement-record production, and the unresolved client trajectory caused by any untraced callback path.

This closes the collector-vs-old-callback-order question for the exact inspected endpoints and LocalPlayer-reachable callback boundary. It does not establish a first intermediate patch boundary, full pair coverage, or runtime trajectory parity. No product files, source corpus, backlog, tests, build, game, or decompiler were changed or run.
