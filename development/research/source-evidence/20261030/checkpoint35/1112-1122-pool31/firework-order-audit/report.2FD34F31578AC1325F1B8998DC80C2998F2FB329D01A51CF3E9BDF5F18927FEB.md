## Ordered source trace

1. **A same-dimension respawn retains the client world.** `ClientPlayNetworkHandler.handlePlayerRespawn` constructs and installs a new `ClientWorld` only when the packet dimension differs from the current player dimension (`1.11.2` lines 896–914; `1.12.2` lines 905–923). Same-dimension handling therefore calls `Minecraft.respawnPlayer` against the existing world.

2. **The replacement receives the previous entity ID, while surviving entities keep their list positions.** `Minecraft.respawnPlayer` saves the old player's ID, calls `world.unloadEntities()`, removes the old player, creates a new local player, copies its synced-data entries, resets position, adds it to the existing world, runs `interactionManager.initPlayer`, and finally restores the old ID (`1.11.2` lines 1906–1930; `1.12.2` lines 1965–1994). The client-world unload pass only removes already-removed entities; it does not clear living entities such as an active rocket (`ClientWorld.unloadEntities`, `1.11.2` lines 305–345; `1.12.2` lines 308–348). Base `World.addEntity` appends successful entities to `entities` (`World.addEntity`, lines 881–903 in 1.11.2 and 885–907 in 1.12.2). Thus the replacement is appended after a surviving earlier rocket. `World.tickEntities` walks that list in order and calls `tickEntity` on each non-removed entry (`World.tickEntities`, 1.11.2 lines 1271–1295; 1.12.2 lines 1275–1299). Removal marks the old player removed; it does not move earlier rockets behind the replacement.

3. **The local lookup and Firework cache allow a not-yet-ticked rocket to bind the replacement.** `ClientWorld.getEntity(id)` returns `minecraft.player` whenever the queried ID equals that player's ID (`ClientWorld.java`, lines 220–224 in both versions). `forceEntity(id, entity)` installs spawned entities, replacing a duplicate current mapping, assigning the packet ID, then adding the entity and indexing it (`ClientWorld.java`, lines 205–218 in both versions). Client spawn type 76 constructs a `FireworksEntity` and forces it into the world (`ClientPlayNetworkHandler.java`, 1.11.2 lines 296–405; 1.12.2 lines 309–418); `handleEntityData` applies synced entries by the rocket's entity ID (`1.11.2` lines 460–466; `1.12.2` lines 473–479). The source packet route exists on the server too: `FireworksItem.startUsing` creates an attached rocket only when the player is fall-flying and adds it to the server world (`FireworksItem.java`, lines 33–48 in both versions); `EntityMap.onEntityAdded` starts tracking Fireworks (`EntityMap.java`, lines 75–109); and `TrackedEntity.updatePlayer` sends the rocket spawn packet then its synced data in that order (`TrackedEntity.java`, lines 316–325, 484–486, identical files). In the byte-identical `FireworksEntity.tick`, `ATTACHED_ENTITY_ID` is looked up only while `attachedEntity == null`; a living match is cached and is never re-queried. A positive attached ID plus a fall-flying cached player reaches `getLookVector` and writes X/Y/Z velocity (`FireworksEntity.java`, lines 90–117, identical files). Therefore a rocket whose spawn and attachment metadata are received but whose first entity tick has not happened can look up the replacement; an already-cached rocket keeps the old object and cannot write the replacement's velocity.

4. **There is a source-reachable yaw/headYaw divergence before the replacement's first entity tick.** Both `LivingEntity` constructors initialize `yaw` from a random value in `[0, 2π)` and immediately copy it to `headYaw` (`LivingEntity.java`, 1.11.2 lines 162–173; 1.12.2 lines 165–176). Both `ClientPlayerInteractionManager.initPlayer` then writes `player.yaw = -180.0F` only (`ClientPlayerInteractionManager.java`, lines 80–82 in 1.11.2 and 84–86 in 1.12.2); neither it nor `Entity.resetPos` writes `headYaw` (`Entity.java`, 1.11.2 lines 246–255; 1.12.2 lines 249–258). The new local player's copied synced-data does include the old fall-flying flag (`LivingEntity.isFallFlying`, 1.11.2 around line 2145 and 1.12.2 lines 2184–2185; it reads synced flag 7), while the constructor's angle fields are not copied. A permitted fresh constructor sample such as 2.0F therefore leaves `headYaw = 2.0F`, `yaw = -180.0F` after `initPlayer`.

5. **The server's respawn correction preserves the mismatch, and the rocket can run first.** In both versions the server respawn method sends `PlayerRespawnS2CPacket` and then teleports the replacement through a `PlayerMoveS2CPacket` (`PlayerManager.respawn`, 1.11.2 lines 435–447; 1.12.2 lines 454–466). The client `handlePlayerMove` calls `updatePositionAndAngles` on `minecraft.player` (`ClientPlayNetworkHandler.java`, 1.11.2 lines 565–600; 1.12.2 lines 578–612); that method writes yaw and pitch, not headYaw (`Entity.java`, 1.11.2 lines 1070–1093; 1.12.2 lines 1093–1116). `Minecraft.runGame` drains queued main-thread packet tasks before it enters the client tick (`1.11.2` lines 832, 847–860; `1.12.2` lines 876, 884–896), and `PacketUtils.ensureOnSameThread` puts off-thread handler calls into that queue (identical `PacketUtils.java`, line 8). So a queued spawn plus attachment-data update, followed by same-dimension respawn and its correction, can all be applied before the next `World.tickEntities`. The earlier rocket is then ticked before the appended replacement; it resolves the replacement by the restored ID and sees the copied fall-flying bit before the player's first `LivingEntity.tick` can invoke local-player `serverTickAi`. `LocalClientPlayerEntity.isLocallyControlled()` returns true (`1.11.2` lines 468–469; `1.12.2` lines 485–487); `LivingEntity.tick` invokes `serverTickAi` for locally controlled living entities (`1.11.2` lines 1770–1782; `1.12.2` lines 1814–1826). `PlayerEntity.serverTickAi` is the later equality repair (`headYaw = yaw`, lines 410–414 in 1.11.2; 406–410 in 1.12.2).

6. **The dispatch delta is consumed at that write.** In 1.11.2, `LivingEntity.getLookVector` calls `getRotationVector(1.0F)`; its `tickDelta == 1.0F` branch uses `(pitch, headYaw)` (`LivingEntity.java`, lines 1915–1928). In 1.12.2 the implementation is inherited from `Entity.getLookVector` and calls `getRotationVector(pitch, yaw)` (`Entity.java`, line 1690; `LivingEntity` no longer declares the override). On the sequence above, with the legal divergent angles, the Firework's first attached velocity write therefore uses headYaw-derived direction in 1.11.2 and yaw-derived direction in 1.12.2, and its resolved target is the current client player. This establishes a concrete, narrow, source-permitted local-player response path for the changed dispatch. It does not claim that every respawn or every attached rocket enters this packet/tick window.

## Pending, re-entry, and limits

`ClientWorld.addEntity` adds a failed insertion to `pendingEntities`; re-entry processing retries up to ten pending entities at the start of `ClientWorld.tick`. `forceEntity` explicitly puts the requested ID in the ID map after `addEntity`, and `getEntity` special-cases the current local player's ID. For the attached rocket near its player in a loaded chunk, normal immediate insertion is the direct route above; if a spawn takes the pending path, the re-entry loop occurs in `world.tick()` after `Minecraft.tickEntities()` in both client tick implementations, so that delayed rocket does not get an earlier-than-player first tick merely by being pending. Repeated `addEntity`/`notifyEntityAdded` and removal bookkeeping for `forcedEntities` does not rewrite a Firework's already cached reference. These paths do not negate the immediate-insertion sequence.

Bounded scope: this establishes a reachable transient response difference, not a new Fireworks implementation delta or a general proof about packet arrival frequencies. FireworksEntity and packet receive bodies are identical; the changed operation is the player `getLookVector` response selected by the fixed client version. No pair-freeze or full tick-coverage claim is made.
