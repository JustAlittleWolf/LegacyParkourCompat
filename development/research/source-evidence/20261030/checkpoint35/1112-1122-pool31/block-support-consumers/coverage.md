## Ordered coverage and findings

1. **Reachable block collision dispatch and player state predicates — examined.** Paired `Entity.move` / `World.getCollisions` paths use the same collision collection and vertical collision callback gate: `Entity.java` 1.11.2 lines 564–724, 1.12.2 lines 567–727; `World.java` 1.11.2 lines 960–1059, 1.12.2 lines 964–1063. `Entity.move` selects the underfoot block state, invokes `beforeCollision` only when requested vertical movement differs from resolved vertical movement, then performs the same collision bookkeeping. `LivingEntity.isClimbing` is behaviorally identical at 1.11.2 lines 978–1000 and 1.12.2 lines 1006–1028: spectators return false; otherwise the feet state is climbing iff the block is Ladder or Vine, or it is an open Trapdoor with the matching Ladder directly below. The same predicate gates the living movement ladder clamp, fall-distance reset, sneak descent stop, and horizontal-collision upward response (1.11.2 `LivingEntity.java` around 1462–1479; 1.12.2 around 1499–1516). No FaceShape query was added to the player climb predicate. `LocalClientPlayerEntity`'s block collision adjustment was inspected at its corresponding `getCollisionShape`/`getCollisions` loop; no movement consumer change was found there.

2. **Ladder, Vine, SnowLayer — provider deltas examined; support-only differences.** Ladder's collision geometry is unchanged. Its attachment/placement and neighbor survival changed from generic `isSolid` checks to `FaceShape.SOLID`, with additional attachment exceptions and `!isSignalSource` (1.11.2 `LadderBlock.java` 52–98; 1.12.2 65–94). Vine retains the empty collision shape; its support, survival, growth and state derivation now use face-shape queries and explicit block exclusions (1.11.2 `VineBlock.java` 44–48, 82–125; 1.12.2 44–48, 83–137, with update/growth logic through 265). SnowLayer's collision-height construction is unchanged (1.11.2 `SnowLayerBlock.java` 59–66; 1.12.2 64–71); `canBePlaced` support rules change to `FaceShape.SOLID` and add Barrier exclusion (1.11.2 79–93; 1.12.2 83–94). These support/placement and block-state evolution effects are dependencies only for this movement slice; they do not alter collision geometry for a given block state or direct player climb/environment predicates.

3. **Stairs, fences, panes, walls — providers and derived-state consumers examined.** Stairs' `addCollisions`/box generation and virtual corner-state resolution are unchanged; 1.12.2 adds `getFaceShape` derived from those same virtual stair properties. Fence, pane and wall collision construction remains based on the existing connection properties and same collision boxes. Their connection predicates and neighbor/placement state derivation change to consult face shape: fence `shouldConnectTo` and updates (1.11.2 `FenceBlock.java` 121–177; 1.12.2 124–192); pane equivalents (1.11.2 `PaneBlock.java` 107–153; 1.12.2 107–165); wall equivalents (1.11.2 `WallBlock.java` 145–195; 1.12.2 146–198). A different connection property can change those blocks' resulting vanilla state and therefore the collision arms chosen from that state; this is block-state/update behavior, not a different collision box for identical state properties. No independent movement delta is claimed for those support/connection changes under the fixed vanilla-state boundary.

4. **FaceShape API and remaining consumers — examined.** `FaceShape.java` is added in 1.12.2; `Block.getFaceShape` supplies the default SOLID face, and `StateDefinition.State.getFaceShape` delegates to the owning block (1.12.2 `Block.java` around 361–365, `StateDefinition.java` 415–417). Grepping all 1.12.2 `getFaceShape` call sites found block support/placement/update logic in Ladder, Vine, SnowLayer, fence/pane/wall, button, torch, trapdoor, tripwire hook and related block classes, plus `FollowOwnerGoal` and the debug solid-face renderer. None is a player movement predicate or changes collision geometry for the same state. The only relevant downstream possibility is support-driven block state evolution; it is not asserted as a movement delta here.

5. **Bed direct collision response — movement delta found.** 1.11.2 `BedBlock.java` has no `beforeCollision` or `onFallenOn` override. 1.12.2 adds `onFallenOn` (halves the value passed to the inherited fall handler) and `beforeCollision` at lines 136–149. The latter calls the no-op base callback only when sneaking; otherwise, when `entity.velocityY < 0.0`, it writes `entity.velocityY = -entity.velocityY * 0.66F`, with an extra `* 0.8` only for non-`LivingEntity`s. The unchanged `Entity.move` callback above makes a player landing on a bed with downward velocity and not sneaking a reachable trigger; player is a `LivingEntity`, so the rebound multiplier is `0.66F` and the nonliving multiplier does not apply. The subsequent living travel path applies its normal gravity/friction after `move`, so the callback writes a positive rebound velocity before those unchanged operations. This is a direct player velocity response, distinct from bed collision geometry and bed-entry eligibility. The separate fall-distance scaling only bears on fall damage, which is out of scope. The exact introduction is only bounded to 1.11.2–1.12.2.

6. **Other block callbacks — examined.** Paired search for `beforeCollision`, `onFallenOn`, `onSteppedOn`, and `onLandedUpon` across `net/minecraft/block` found the existing Slime, Farmland, Hay, Magma, Redstone Ore and base callbacks on both sides; Bed is the only newly added movement-response override. Slime callback bodies are unchanged. No other additional block-to-player movement response was identified in this bounded scan.
