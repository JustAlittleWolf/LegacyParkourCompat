# Independent scoped source audit: 1.11.2 → 1.12.2

## Verdict

The submitted modifier/effect report is correct about the argument plumbing: a player passes `sidewaysSpeed`, `verticalSpeed`, and `forwardSpeed` through `PlayerEntity.moveRelative` unchanged; `LivingEntity.moveRelative` then calls `Entity.updateVelocity(forwards, sideways, upwards, scale)`. Thus `verticalSpeed` becomes the callee's `forwards` operand and is added to `velocityY`. `PlayerEntity` never writes the inherited `verticalSpeed` field in these sources; its declaration defaults to positive zero, and the only explicit field assignment in 1.12.2 is in `MobEntity`.

The added operation is conditional on the normalized-input threshold (`!(f < 1.0E-4F)`). When it executes with player `verticalSpeed == +0.0F`, `velocityY += forwards` will turn an incoming `-0.0D` into `+0.0D`. This verifies the report's signed-zero observation. It does not establish a reachable ordinary player tick where the negative zero survives to this call: `LivingEntity.mobTick` first damps velocity and replaces any `abs(velocityY) < 0.003` with the positive-zero literal before input dispatch. No downstream player movement branch distinguishing the two zero signs was established. I therefore leave this as an unresolved exact-state edge, not an accepted trajectory finding.

The changed item/effect callbacks checked here add server advancement/stat bookkeeping or route water-potion fire removal through `World.extinguishFire`. Potion and milk effect application/removal remain in the same order and use the same effect APIs. The fire helper still removes only `Blocks.FIRE`; fire has an empty collision shape. No player movement delta was found in these callbacks. The helper changes the target position/face semantics for fire removal, but that is a fire/environment side effect outside this modifier/effect movement slice.
