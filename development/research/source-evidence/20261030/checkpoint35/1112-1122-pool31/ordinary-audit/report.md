## Retraced claims

- **Look-vector implementation:** 1.11.2 `Entity.getLookVector()` returns `null` (`entity/Entity.java:1664–1666`) and `LivingEntity.getLookVector()` overrides it with `getRotationVector(1.0F)` (`entity/living/LivingEntity.java:1916–1918`); this resolves through the one-argument interpolation method using `headYaw` (`LivingEntity.java:1921–1928`). 1.12.2 removes the LivingEntity override; `Entity.getLookVector()` returns `getRotationVector(this.pitch, this.yaw)` (`entity/Entity.java:1690–1692`), while LivingEntity's angle-based rotation-vector implementation remains. Thus the polymorphic call semantics differ in general when yaw and headYaw differ.
- **All callers in 1.12.2 entity sources:** `LivingEntity` elytra travel (`entity/living/LivingEntity.java:1434–1459`), `FireworksEntity` attached fall-flying boost (`entity/FireworksEntity.java:103–110`), and `ProjectileEntity.onHit` (`entity/projectile/ProjectileEntity.java:187+`). The latter uses attacker look direction to set projectile velocity; it does not write player velocity. Source search found no additional entity call sites. The 1.11.2 projectile caller is guarded for null; its body is unchanged at 1.12.2.
- **Ordinary elytra travel:** the local player is `isLocallyControlled()` (`client/entity/living/player/LocalClientPlayerEntity.java:485–486`), so `LivingEntity.tick` executes its local `serverTickAi`; `PlayerEntity.serverTickAi` writes `headYaw = yaw` (`entity/living/player/PlayerEntity.java:406–410`) before travel. Consequently the changed source expression receives equal yaw and headYaw on this path.
- **Fireworks ordering/gates:** `World.tickEntities` calls `tickPlayers()` and then iterates regular entities in insertion order (`world/World.java:1275–1293`); base client-world `tickPlayers()` is empty (`World.java:1380–1382`), so client players are ticked in that regular list. `World.addEntity` appends to `entities` (`World.java:885–906`). A normally reachable attached-firework boost is created/attached after the player exists; the player is ticked first, and its `serverTickAi` synchronizes head yaw before the later firework's `tick`. The boost itself requires `attachedEntity != null` and `attachedEntity.isFallFlying()` (`FireworksEntity.java:103–105`) and then directly modifies the attached entity velocity (`:108–110`). For the local player in this path the look vector therefore has equal yaw/headYaw. World tick order does not leave an open dependency for this ordinary local-player route.
- **Reachability boundary:** A remote client-side player can have server-updated yaw/headYaw values that differ; remote player movement is not the local-client fixed-profile movement path under this assignment. The same Fireworks code runs on logical servers, but server movement is expressly outside the emulation target. Neither establishes a local player path with a yaw/headYaw gap at the boost call. If another assignment includes non-local player movement responses, that scope would need a separate disposition.
