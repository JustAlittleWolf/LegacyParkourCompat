## Ordered reachable local-player tick and terminal graph

1. **World entry and entity dispatch.** `Minecraft.tick` reaches `world.tickEntities`; `World.tickEntities` runs player-list handling and then traverses the world's entity list in order. It skips removed entities and server players, then calls `tickEntity`. `Minecraft.setWorld`/`respawnPlayer` and `World.addEntity` register the local player in the client world's entity list. The 1.11.2 `tickEntity` area-loaded gate is moved inside a non-player branch in 1.12.2, but the local client world returns `allowEmpty || !chunk.isEmpty()` for `isChunkLoadedAt`; the `allowEmpty=true` query makes this area gate pass for that client path. The unchanged `requireLoaded && entity.inChunk` gate still controls `ticks++` and the actual entity tick. This is not a player tick difference.

2. **Client player tick and input.** `LocalClientPlayerEntity.tick` gates on its current chunk and delegates into the player/living/entity tick chain before sending movement packets. In a locally controlled living tick, `PlayerEntity.serverTickAi` synchronizes `headYaw=yaw`, and the local override copies `Input`'s sideways, forward and jump state. `LocalClientPlayerEntity.mobTick` handles sprint, double-tap flight, elytra start, horse input and creative-flight velocity, then reaches `LivingEntity.mobTick`. `Input`, keyboard normalization and packet input contain only horizontal axes plus jump/sneak. Tutorial notification and recipe/menu additions do not write a movement field. The `verticalSpeed` expansion in 1.12.2 has no vanilla `PlayerEntity` writer; the only assignment is in `MobEntity`. The player receives `+0.0F`; the extra normalized input term and Y addition introduce no established trajectory difference. A signed-zero edge was checked: preceding `LivingEntity.mobTick` clamps `abs(velocityY)<0.003` to a positive-zero literal before input dispatch, and no distinct downstream movement branch was found.

3. **Travel and state effects.** The virtual `moveRelative`/travel call selects land, air, water/lava, climbing, levitation and elytra branches; `LivingEntity` applies gravity/friction and eventually calls local-player `move`, which delegates to `Entity.move`. Paired input, sprint/jump, movement-speed, flight speed, attribute/modifier application, potion/effect registrations and updates, Depth Strider/Frost Walker reads, and player equipment paths have no established movement delta. `MathHelper` only renames `floorDiff` to `fractionalPart` with identical expression and a renderer-only caller; `Vec3i` changes its string helper only. `Rotation` normalizes values, but its instances are armor-stand pose values and the checked callers do not feed player movement.

4. **Collision and block response.** `Entity.move` performs the same no-clip/piston/sneak gates, collision enumeration, Y-X-Z resolution, step-up selection, flags/fall bookkeeping, support-block lookup, vertical callback, and contact/step methods. Player calls reach `World.getCollisions`, which invokes `BlockState.addCollisions(..., forceShape=false)`. That query dynamically resolves Fence/Pane/Wall virtual connections against neighboring states; see the confirmed geometry candidates below. Bed `beforeCollision` runs after a downward movement is clipped without a client-side guard. Changed farmland relocation stays inside a server-only block replacement gate. Changed dismount position selection is called only by `LivingEntity.stopRiding` under `!world.isClient`.

5. **Fluid and velocity terminal.** `Entity.checkWaterCollisions` writes the `inWater` and fall-distance state and calls `World.applyLiquidDrag` for intersecting water unless mounted on a boat. `LiquidBlock.applyMaterialDrag` passes the flow vector to the same world aggregation, which can write all three entity velocity components when the resulting vector is nonzero and the entity accepts liquid collision. The level-8 bed-face candidate is a direct input to this terminal writer and requires an unmounted, non-flying player. Position/box/velocity, collision flags, falling, climbing, sprint, ability and local player movement terminal writes are otherwise unchanged along the checked ordinary chain.

6. **External terminal responses.** Client correction, entity-velocity, explosion, relative/absolute movement, teleport, abilities, status/effect, metadata, respawn and entity lifecycle handlers were compared at their movement write sites; movement-bearing packet classes and handler methods have no paired delta. Server correction packet construction, dimension/respawn replacement and the relevant entity tracker paths were checked. Piston displacement and knockback math are unchanged for the player path. Ender pearl cross-dimension clearing and farmland/dismount position writes are server gated, so do not represent logical-client movement execution.

7. **Pose-only state.** `LivingEntity` changes the body-yaw target for rearward movement. Its identified consumer is body/model orientation and the compared branch does not write player yaw, position, velocity, box or dimensions. Keep this source state difference with the rendering exclusion, not as a movement finding.

## Paired movement-relevant changed-path dispositions

### Confirmed direct player response: bed bounce

1.11.2 `Block.beforeCollision` zeros `entity.velocityY`; `BedBlock` has no override. 1.12.2 `BedBlock.beforeCollision` delegates to that base callback only while sneaking. Otherwise, if `velocityY < 0.0`, it writes `-velocityY * 0.66F` (the extra `0.8` is restricted to non-living entities). The unchanged `Entity.move` caller invokes the selected support block only when resolved Y differs from requested Y. A non-sneaking local `PlayerEntity` falling onto an era-existing bed reaches that gate and receives upward velocity in 1.12.2 instead of zero in 1.11.2. This is a direct player velocity response, not bed-entry eligibility or fall-damage scaling. Exact source anchors: `1.11.2 block/Block.java:624–626`; `1.12.2 block/BedBlock.java:141–150`, `block/Block.java:643–645`; paired `entity/Entity.java:723–728`.

### Confirmed direct fluid response: level-8 water beside bed

1.11.2 `LiquidBlock.isFaceSolid` rejects water and ice but delegates other side faces to `Block.isFaceSolid`, which reads `Material.isSolid`; bed's wool material inherits `true`. 1.12.2 rejects attachment exceptions and stairs and requires the queried neighbor `BlockState.getFaceShape(...)=SOLID`; `BedBlock.getFaceShape` returns `UNDEFINED`. The unchanged `getFlow` at level ≥8 checks each horizontal neighbor and the block above it, and on the first solid side adds a downward `-6` term before normalization. Flowing-liquid ticking can create level 8 by spreading a level-0–7 state downward with depth `i + 8` (`FlowingLiquidBlock.java:84–95` in both endpoints). With a level-8 current, the bed side, air below/other sides, and zero horizontal depth gradient, the old predicate produces downward flow while the new predicate produces zero. `World.applyLiquidDrag` passes the current into player velocity (`+0.014` times normalized aggregate) when the water bounds intersect and `hasLiquidCollision()` is true. `PlayerEntity.hasLiquidCollision` is `!abilities.flying`; `Entity.checkWaterCollisions` bypasses this whole response while riding a boat. Therefore the concrete player precondition is **unmounted and non-flying**. Anchors: old `block/LiquidBlock.java:83–91`, `block/Block.java:343–345`; new `block/LiquidBlock.java:82–100`, `block/BedBlock.java:327–329`; shared level gate `LiquidBlock.getFlow`; `entity/Entity.java:927–934` / `:948–955`; `world/World.java:1571–1613` / `:1579–1621`.

### Confirmed query-time collision geometry: Fence, Pane, Wall against straight stairs

This is not merely a change in which neighbor-derived bits get stored. On both endpoints `World.getCollisions` calls `BlockState.addCollisions(..., false)` for player movement. `FenceBlock.addCollisions` and `PaneBlock.addCollisions` call `resolveVirtualProperties(world,pos)` whenever `forceShape` is false; `WallBlock.addCollisions` does the same. Those resolutions read the raw neighboring `BlockState` during the collision query. The 1.11.2 predicates admit solid full cubes/materials (plus each block's legacy exceptions); `StairsBlock.isCube()` is false, so the straight-stair witness is rejected. In 1.12.2 Fence, Pane and Wall call the neighboring state's directional `getFaceShape`; a straight north-facing stair returns `SOLID` on its NORTH face. With the stair on the south side of the queried fence/pane/wall, each resolver selects its SOUTH connection arm in 1.12.2 and not in 1.11.2. The add-collision methods then add the arm box to the player's collision list. This changes movement geometry for identical center and neighbor block states, within the historical geometry scope.

Anchors: old `world/World.java:997`, `block/FenceBlock.java:59–80, 121–177`, `block/PaneBlock.java:48–75, 107–153`, `block/WallBlock.java:102–107,148–195`, `block/StairsBlock.java` (`isCube=false`); new `world/World.java:1001`, `block/FenceBlock.java:59–80,124–192`, `block/PaneBlock.java:48–75,107–165`, `block/WallBlock.java:100–105,146–198`, `block/StairsBlock.java:140–161`. The old Wall resolver also has an unconditional `block==this || block instanceof FenceGateBlock` branch; retain it in any general summary. This audit independently confirmed the raw-neighbor query and directional face-shape caller chain. Separate operation hooks/findings should be reconciled for Fence, Pane and Wall.

This audit binds them to the verified endpoint sources but does not create permanent findings, determine an intermediate patch boundary, or establish runtime parity.
