## Ordered coverage and dispositions

1. **Player movement superclass and writer closure — changed; movement-relevant / partial semantic gate.** `Entity.updateVelocity` expands the input vector to three components; `LivingEntity.moveRelative`/`travel` and `PlayerEntity.moveRelative` adopt the matching three-component signature. The `PlayerEntity` travel call passes `(sidewaysSpeed, verticalSpeed, forwardSpeed)`; the expanded method maps these into the same X/Z formulas as 1.11.2 and adds `velocityY` from the vertical component. Source search found `verticalSpeed` assignments only in `MobEntity`, not `PlayerEntity` or client player classes, so this signature expansion does not by itself change player horizontal travel on this path. `LivingEntity` also changes walk animation to include Y displacement only for `FlyingAnimal`, and changes body-yaw selection based on movement direction; these are non-player animation/heading behavior. `Entity.getLookVector` changes from a 1.11.2 `LivingEntity` implementation using `getRotationVector(1.0F)` to a 1.12.2 `Entity` implementation using `getRotationVector(pitch, yaw)`. See Firework response gate below.
2. **Direct player block/dismount/position response — changed; one reachable candidate.** `LivingEntity.dismountRider(Entity)` changes candidate collision-box construction and changes the first candidate-box vertical offset from `+1.0` to `0.0`, with the follow-up test still at `+1.0`. `Entity.stopRiding` calls the mount's `dismountRider`; a player can dismount a PigEntity, which is a living mount and does not take the BoatEntity/HorseBaseEntity special-case branch. This is a player position-response difference to retain for exact comparison of the dismount helper and candidate ordering. No player pose or dimensions writer changed in this slice. `Entity.onBlockCollision` is newly called after block collision callbacks, but the only override found is server-side `ServerPlayerEntity` and it fires an advancement criterion; the client player inherits the no-op hook.
3. **External client receive writers and lifecycle — checked; changed handler deltas are unrelated, receive paths unchanged.** In both versions `ClientPlayNetworkHandler` directly handles server player correction (`handlePlayerMove`: relative X/Y/Z handling, zeroing absolute velocity components, `updatePositionAndAngles`, teleport ack and outgoing correction), entity velocity (`lerpVelocity`), explosion velocity addition, respawn/player recreation, sleep, abilities, effects, entity metadata, attributes, equipment, teleport/relative entity movement, spawn, and removal. None of these method bodies is within a changed hunk in the handler diff. The two changed client play handler files add/modify recipe, advancement, tutorial, chat, and screen work; no movement receive logic changes. Movement-bearing sibling S2C packet sources (`PlayerMoveS2CPacket`, `EntityVelocityS2CPacket`, `ExplosionS2CPacket`, `PlayerAbilitiesS2CPacket`, `PlayerRespawnS2CPacket`, `PlayerSleepS2CPacket`, `EntityTeleportS2CPacket`, `EntityDataS2CPacket`, `EntityStatusEffectS2CPacket`, `EntityAttributesS2CPacket`) are byte-identical across the pair.
4. **Player respawn/re-entry — closed for the examined replacement path.** Both `Minecraft.respawnPlayer` methods remove the previous local player, construct a replacement, copy synced data, reset its position, add it to the same client world, and restore its network id. 1.12.2 adds recipe-book transfer to the constructor; the position/reset/insertion sequence is unchanged. The 1.12.2 server respawn path still sends `PlayerRespawnS2CPacket` then a teleport after placement/collision lifting; its insertion/collision-lift order in `PlayerManager.respawn` is unchanged. 1.12.2 moves the copy routine from `PlayerEntity.copyFrom(PlayerEntity,...)` to `ServerPlayerEntity.copyFrom(ServerPlayerEntity,...)`, adding recipe/advancement/shoulder persistence but no position/velocity transfer. `ServerPlayerEntity.stepHeight` changes `0.0F` to `1.0F`; this is server-side movement and outside the client historical-physics lane.
5. **Firework attached-player response and replacement gate — unchanged caller, changed look-vector dispatch; exact player reachability remains partial.** `FireworksEntity` is byte-identical and its tick resolves `ATTACHED_ENTITY_ID` lazily while `attachedEntity == null`; once cached, it does not re-query. When the attached living entity is fall-flying, it writes all three attached-entity velocity components from `getLookVector`, with no logical-side guard, so the same caller is present on client and server. `PlayerEntity.serverTickAi` sets `headYaw = yaw`; `LivingEntity.tick` invokes it for locally controlled players. Thus a stable player-tick boundary has equal yaw/head yaw; a concrete local-player difference requires the rocket tick to observe a yaw update before that assignment, which source order in the bounded classes does not establish. Next bounded action: compare `ClientWorld` entity iteration / local input and network yaw update order against the firework tick to establish whether that transient state is reachable for the local player. Do not treat the helper relocation alone as an accepted player finding. On same-dimension client respawn, the existing rocket can remain while `Minecraft.respawnPlayer` replaces the player with the same network id; a cached old-player reference is not rebound, whereas a null unresolved reference may bind once the replacement is inserted. This cache behavior is identical on both sides; it does not establish a newly introduced respawn delta.
6. **Ender-pearl response — changed source; server-only gate means client applicability remains partial.** 1.12.2 adds `EnderPearlEntity.changeDimension`: when the pearl's `dimension` differs from the target it clears `thrower`, then delegates. `Entity.tick` reaches this only after portal time and calls `changeDimension` on the server; `Entity.changeDimension` itself requires `!world.isClient`. `EndPortalBlock.onEntityCollision` is also explicitly server-only and calls `entity.changeDimension(1)`. The pearl's later `onCollision` teleports its thrower only inside `!world.isClient` and the ServerPlayer branch requires the thrower, connected connection, same world, and not sleeping. Thus this prevents a cross-dimension pearl from later teleporting its server-side thrower; the compared source does not show a client-side direct position writer. Treat as vanilla-server response behavior outside historical client movement execution unless pair reconciliation identifies an eligible client-side mirror.
7. **Remaining changed entity rows — classified and no other local-player writer found.** AI control/goal/path navigation and changed mob subclasses are non-player AI/mob physics. Vehicle classes (`BoatEntity`, `TntMinecartEntity`, horse and pig movement overrides) affect vehicle/mount physics, which is excluded; `LivingEntity.dismountRider` above is separately retained because it repositions the player itself. `ProjectileEntity`, `ThrownEntity`, and `ShulkerBulletEntity` changes are brightness accessor changes or visibility only; `PotionEntity` only routes extinguish-fire block state through a face-aware helper; `FishingBobberEntity` only removes the explicit zero initializer from `life`. `EntityAttributes` adds a flying-speed attribute and `Entities` adds Parrot/Illusioner registration; neither adds a player motion writer. `SyncedData`/`DataSerializers` add defensive copies and NBT compound serialization used for shoulder-parrot metadata, not player position, velocity, size, pose, or movement response. The other changed item/projectile/entity rows are listed with exact status and hashes below and fall into these non-player/vehicle/protocol categories; no separate player-state write was found on their changed methods.
8. **Changed packets, client entities, and client handlers — closed as unrelated except the two partial direct-response gates above.** Recipe/advancement packets are new; inventory, chat/tab-list, settings, keepalive, handshake, and status changes are protocol/UI/inventory behavior. The `EntityEquipmentS2CPacket` change copies empty stacks rather than reusing the empty singleton; receiver logic is unchanged and this constructor-only copy does not change the movement-relevant equipment state. `RemoteClientPlayerEntity` changes `stepHeight` from 0 to 1 while retaining `noClip=true`; remote entities use server interpolation and are not the local movement actor. `LocalClientPlayerEntity` only changes recipe-book construction, movement-send visibility, tutorial input notification, and closing inventory UI during portal UI teardown.
