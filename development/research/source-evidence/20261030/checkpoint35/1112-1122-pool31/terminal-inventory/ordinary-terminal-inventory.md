- Scope: local-client player tick terminal writes and directly reachable player callbacks; ordinary shared movement-core math is treated as a dependency for the core worker.

## Ordered inventory

1. **Client tick entry, dispatch and lifecycle — examined.** `Minecraft.tick()` calls `world.tickEntities()` (1.11.2 `Minecraft.java:1419`; 1.12.2 `:1468`). `World.tickEntities()` walks `entities`, skips only `ServerPlayerEntity`, and invokes `tickEntity` (`World.java:1274-1295` / `:1278-1299`), so a registered `LocalClientPlayerEntity` is dispatched. `Minecraft.setWorld` and `respawnPlayer` add the local player to the world (`Minecraft.java:1892-1895, 1918-1929` / `:1951-1955, 1977-1994`); `World.addEntity` treats players as teleporting, adds them to the player list and chunk, then to `entities` (`World.java:881-901` / `:885-905`).

   `World.tickEntity(Entity, boolean)` does change: 1.11.2 `World.java:1408-1413` wraps the entire tick path in `!requireLoaded || isAreaLoaded(x±32,0,z±32,true)`; 1.12.2 `:1412-1420` limits that area gate to non-`PlayerEntity` instances. **No local-client movement delta follows:** `World.isAreaLoaded` checks vertical bounds and passes `allowEmpty=true` to `ClientWorld.isChunkLoadedAt`; both versions' `ClientWorld.java:105-106` return `allowEmpty || !chunk.isEmpty()`, so this client-side area check short-circuits true. The player still has the same `requireLoaded && entity.inChunk` tick gate in both versions. The World change is therefore generic/server-side for this assignment, not a client tick divergence.

2. **Local input, mode and network-send state — examined, no movement delta found.** `LocalClientPlayerEntity.tick()` calls `super.tick()` and sends riding/non-riding movement at `:159-179` / `:165-179`; `sendMovementToServer()` changes visibility only (public → private) and its movement packet conditions/body are unchanged. Paired `serverTickAi()`, `isSneaking()`, `mobTick()`, `setSprinting()`, and local `move()` retain their movement state writes/order. In `mobTick()` the only additions are (a) closing an inventory menu on portal entry and (b) `tutorial.onPlayerInput(input)` immediately after `input.tick()` (`1.11.2 :632-795`; `1.12.2 :649-810`). The latter callback is the only new call in the local input path; no movement field is written by it in this source. The existing sprint, double-tap flight toggle, fall-flying request, creative vertical velocity changes, horse jump input and final `super.mobTick()` are otherwise unchanged. `Input.java` is byte-identical per matrix.

3. **Position/box/collision/fluid/climbing terminal writers — examined, with core dependency.** `Entity.setPosition`, `setShape`, `setSize`, `move`, collision flag/fall-distance updates and `checkWaterCollisions()` were inspected at `Entity.java:271-302, 459+, 927-942` / `:273-304, 462+, 948-963`; no paired movement-body change was found. `checkWaterCollisions()` uses the same `world.applyLiquidDrag(shape.grown(0,-0.4F,0).contract(0.001), WATER, this)` call and the same in-water/fall-distance writes. New `Entity.checkWaterState()` (`1.12.2 :944-946`) uses a deeper box, but a whole-source call-site search found no caller. New `onBlockCollision` callback is invoked after block collision (`1.12.2 Entity.java:824-843`) but the base implementation is empty and no entity override exists in these sources; it has no local-player state effect here.

   `LivingEntity.isClimbing()` is unchanged (`1.11.2 :978-990`; `1.12.2 :1006-1018`): non-spectators test the block at the player's floored x/z and shape-minY for ladder/vine identity or a climbable trapdoor. Step height is still `0.6F` in `LivingEntity` construction. `VineBlock` and `LadderBlock` do change support/attachment predicates to use the new `FaceShape` API; this is a block-state support dependency, not a changed local player terminal write. No changed player collision shape was established in the selected block checks. Keep the dependency open for the block/shape lane; do not infer a movement delta for an unchanged fixed vine/ladder state.

   **Core handoff:** 1.12.2 adds `LivingEntity.verticalSpeed`, changes `moveRelative`/`Entity.updateVelocity` to three input axes, updates `LivingEntity.travel` call sites, and changes `PlayerEntity.moveRelative` accordingly (`LivingEntity.java:1425, 1494, 1543, 1574, 1847`; `PlayerEntity.java:1386-1400`; `Entity.java:1050-1070`). This is the ordinary movement-core slice. The local-player source contains no `verticalSpeed` assignment; the only source assignment found is `MobEntity.java:475`. Forward/sideways input and local creative flight still feed their existing path. Reconcile this with the core worker rather than treating it as a new terminal-state finding here.

4. **Direct dismount player-position response — concrete paired candidate, with caller gate recorded.** `LivingEntity.dismountRider(Entity)` changes (`1.11.2 LivingEntity.java:1282-1327`; `1.12.2 :1321-1364`) and is inherited by `PlayerEntity`/`LocalClientPlayerEntity`. For mounts other than `BoatEntity` and `HorseBaseEntity`, 1.11.2 builds candidate clearance box Y bounds as `[player.shape.minY - mount.height, player.shape.maxY - mount.height]` and probes `box.moved(dx,1.0,dz)`; 1.12.2 uses `[mount.shape.minY, floor(mount.shape.minY)+player.height]` and probes `box.moved(dx,0.0,dz)`. The ordered horizontal candidates and later tests are unchanged: collision-free/full block at player y teleports to `y+1`; collision-free with full block or water below updates fallback to `y+1`; blocked candidate with one-block-up clearance/full block above sets fallback to `y+2`; after the loop it teleports to the selected fallback. This can select a different player exit position; the exact trajectory/selected candidate depends on `World.getCollisions` and block shapes (still an open dependency).

   The other mount-class branch is explicit and unchanged: `BoatEntity` or `HorseBaseEntity` uses a width-derived lateral offset, arm-side offset except for boats, and collision checks at `mount.y + mount.height + 0.001`, then `+1.001`, then fallback above the mount. Local `startRiding` delegates to the superclass (`LocalClientPlayerEntity.java:129-145` / `:135-151`), so both class branches are reachable for player mounts in general. **Execution gate:** the only call site is `LivingEntity.stopRiding()` (`1.11.2 :1863-1870`; `1.12.2 :1907-1914`), and it calls `dismountRider` only when `!world.isClient`. Thus it is not executed directly on the logical client; retain the changed player position response as a source candidate per coordinator ruling, and keep the server-only producer / client application policy as a separate scope decision. Client `handlePlayerMove(PlayerMoveS2CPacket)` applies server coordinates with `updatePositionAndAngles`, zeros velocity axes that are not relative, acknowledges teleport and sends the player's current position (`ClientPlayNetworkHandler.java:565-614` / `:578-627`); the relevant method body is unchanged.

5. **Network corrections, explosion impulse, abilities and respawn — examined, no paired movement-body delta found.** In `ClientPlayNetworkHandler`, `handleEntityVelocity`, `handleEntityData`, `handleEntityTeleport`, `handlePlayerMove`, `handlePlayerRespawn`, `handleExplosion`, and `handlePlayerAbilities` were checked. Their player position, velocity, on-ground/synced state, flight ability and respawn writes are unchanged; file hash changes in this class occur outside those state-writing bodies. `ClientWorld`'s only diff hunk is ambient cave sound distance gating, unrelated to movement. `RemoteClientPlayerEntity` changes `stepHeight` from `0.0F` to `1.0F`, but it is a remote replica with `noClip=true`, not the local player's movement object.

## Examined, partial and unexamined

- **Examined:** common `Entity` position/box/move/water/flag writer methods; `LivingEntity` climb predicate, step-height initialization, dismount callback and relevant travel interface; `PlayerEntity` tick/move-relative/dismount inheritance; `LocalClientPlayerEntity` tick, input, sprint/fly/sneak, outbound movement and local move callback; generic and client entity tick dispatch; client correction/ability/respawn/explosion handlers; bounded Vine/Ladder/FaceShape support path.
- **Partial:** collision-dependent dismount candidate selection (requires complete paired `World.getCollisions` and block collision-provider coverage); block support/shape dependencies for all changed block classes; direct vanilla callback override search was bounded to `Entity.onBlockCollision` and local player methods, not every changed entity subclass or all external player responses.
- **Unexamined:** full changed block-provider inventory and all collision/shape dependency classes; all item/effect/equipment and external packet paths that may assign local-player movement fields; all direct player event/response methods outside the selected entity/client/world/network path; server-side movement checks and vehicle physics. No pair freeze/audit claim.
