## Ordered coverage and dispositions

1. **Client input and ordinary caller chain — no input difference found.** `Input.java` and `ClientPlayerEntity.java` are byte-identical. `LocalClientPlayerEntity.mobTick` adds only `minecraft.getTutorial().onPlayerInput(this.input)` after `input.tick()` (1.12.2 `LocalClientPlayerEntity.java:694–700`); its only checked listener, `MovementTutorialStep.onPlayerInput` (`client/tutorial/MovementTutorialStep.java:105–109`), reads directional/jump booleans and sets tutorial progress, without changing the input. `sendMovementToServer` changes visibility from public to private; its body and calls are unchanged. The earlier source report owns the key normalization/sprint/jump rows and is not reopened here.

2. **Travel helper and horizontal input wiring — no ordinary horizontal-player difference identified.** `LivingEntity.moveRelative` / `Entity.updateVelocity` change from two to three input axes (1.11.2 `LivingEntity.java:1391+`, `Entity.java:1028+`; 1.12.2 `LivingEntity.java:1425+`, `Entity.java:1049+`). The local-player tick calls `moveRelative(sidewaysSpeed, verticalSpeed, forwardSpeed)` (1.12.2 `LivingEntity.java:1842–1848`); `LocalClientPlayerEntity.serverTickAi` is locally controlled and delegates to `PlayerEntity.serverTickAi`, which sets `headYaw=yaw`, then fills only sideways/forward/jump from `Input` (`LocalClientPlayerEntity.java:485–487, 631–640`; `PlayerEntity.java:406–410`). No vanilla player assignment to `verticalSpeed` was found; its sole vanilla setter is `MobEntity.setVerticalSpeed` (`MobEntity.java:474–476`). Thus player calls supply zero as the new Y input. For finite horizontal inputs the added square is `+0.0`, the X/Z formulas retain the old side/forward terms, and Y receives `+0.0F`; no nonzero vertical-input player route was found. This closes the 3-axis helper as a player delta, while the exact signed-zero state edge from adding `+0.0` to a negative-zero velocity is not established as reachable and is not promoted to a finding.

3. **Elytra look-vector consumer — candidate reachable velocity delta; caller-order gate open.** In 1.11.2 `Entity.getLookVector()` returns null (`Entity.java:1664–1666`) while `LivingEntity` overrides it as `getRotationVector(1.0F)` (`LivingEntity.java:1916–1918`); that one-tick vector uses `headYaw` (`LivingEntity.java:1921–1928`). In 1.12.2 the `LivingEntity` override is removed and `Entity.getLookVector()` returns `getRotationVector(this.pitch, this.yaw)` (`Entity.java:1690–1692`), so polymorphic player look switches from head yaw to entity yaw. The same inherited call is in local-player fall-flight travel (`LivingEntity.java:1429–1459`) and in the unchanged `FireworksEntity.tick` attached-player boost, which directly rewrites attached `velocityX/Y/Z` from the returned vector when `isFallFlying()` (`FireworksEntity.java:103–110`). The player's own travel path resets `headYaw=yaw` in `serverTickAi` before reaching `moveRelative`, so that call is equal for the locally controlled player on that path. The external firework tick's order relative to local-player yaw/head-yaw synchronization was not traced through the complete world entity iteration. If it can run with `yaw != headYaw`, the directly written player velocity vector differs; retain as an open source caller-order dependency rather than an accepted finding until reachable precondition is established.

4. **Body-yaw pose update — definite state delta, movement-physics effect not found.** In the inherited `LivingEntity.tick` body-yaw target calculation, for horizontal displacement squared above `0.0025000002F`, 1.11.2 directly selects movement angle `k` (`LivingEntity.java:1651–1655`). 1.12.2 computes the same `k`, then selects `k - 180.0F` when `95.0F < abs(wrapDegrees(yaw) - k) < 265.0F`, otherwise `k` (`LivingEntity.java:1689–1699`). `bodyMovement` consumes this value (`:1710–1712`). The predicate and assignment are reached by a moving player; this changes `bodyYaw` pose target for sufficiently rearward movement relative to player yaw. The compared code has no write to player yaw, position, velocity, collision box or dimensions from this branch; the identified consumer is body/model orientation, so it has no established movement-physics delta. Flag for the pair owner because pose was explicitly in this lane, and keep the project rendering exclusion separate from the source fact.

5. **Dimensions, sleeping/sneaking pose, and direct size writers — no core dimension delta found.** `Entity.setSize` / shape construction and `PlayerEntity.getEyeHeight`, sleep entry/exit, `isSleeping`, and local `isSneaking` methods have no movement-relevant body change in the paired diff. The 1.12 sleep path adds `dropShoulderEntities()` before its unchanged `setSize(0.2F,0.2F)`; shoulder entities are a 1.12-only feature and their spawn/collision behavior was not analyzed, so any indirect entity-collision effect is a modern-feature/provider boundary, not attributed to player dimensions here. Existing movement collision response/shape dependencies remain with the collision pool.
