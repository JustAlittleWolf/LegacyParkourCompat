# Independent audit: 1.8.1 enum-switch metadata remediation

## Decision

**Revision required before commissioning the patch.** The diagnosis is plausible and the pipeline has a sound place to apply an input-only repair, but the proposal currently conflates a metadata-only change with changing the helper's binary name. Those are materially different transforms. It also does not yet give a bounded eligibility predicate that prevents accidental treatment of unrelated flattened classes. This is a static-feasibility review only; no transformation or decompile was run, so it does not prove that the change yields zero Vineflower errors.

## Verified against the checked-in pipeline and cache

- The engine remaps into a jar, then sends that jar to Vineflower. No nesting reconstruction occurs between those stages. ASM core/tree is already an implementation dependency in `buildSrc/build.gradle`.
- Every Vineflower `ERROR` increments the failure count; a nonzero count throws before failed-method scan, required-source checks, manifest creation, or publication. Those later gates remain necessary and are not substitutes for the zero-ERROR gate.
- The cached 1.8.2 `BlockElement$85922567` is synthetic (`ACC_SUPER | ACC_SYNTHETIC`), with a synthetic static final int-array field, `InnerClasses` naming `BlockElement` as owner, and `EnclosingMethod` naming `BlockElement` with no method. The 1.8.1 flattened `BlockElement__85922567` is likewise synthetic according to `javap`, but has no nesting attributes. This confirms the proposed relationship for this concrete example.
- `InnerClasses` metadata alone can represent a member whose binary name remains flattened: the entry's inner class is the actual helper name, outer class is `BlockElement`, and inner name is the suffix. The `EnclosingMethod` class can likewise identify `BlockElement` while its method name/descriptor are null, matching the 1.8.2 classfile. This is the narrower metadata-only candidate. Whether Vineflower 1.12.0 reconstructs the enum switch from that shape remains unverified.

## Required constraints for a safe candidate patch

1. **Gate exactly by input identity.** Initially run only for exact Minecraft `1.8.1` plus mapping source `ornithe-feather` and the pinned mapping artifact identity already recorded in cache. Do not apply based only on class-name regex or to all pre-1.9 inputs.
2. **Use an explicit, reviewed helper-to-owner allowlist** derived from that exact mapping artifact. For each allowlisted helper, require the exact flattened mapped internal name, expected outer name and suffix, mapped owner class present, no existing `InnerClasses`/`EnclosingMethod`, and no conflicting class with the proposed canonical `$` name. Unknown or ambiguous candidates must fail closed or remain untouched and be reported; do not heuristically guess ownership.
3. **Prove the helper shape before rewriting.** Require `ACC_SYNTHETIC`; exactly the expected synthetic static-final `[I` switch-map field(s); a `<clinit>` containing the recognizable enum `$VALUES`/`values()` length allocation, ordinal-indexed integer writes, and `NoSuchFieldError`-guarded enum constant assignments; and correspondence between the owner bytecode's switch-map field references and helper field(s). Check the expected enum owner types and assignment keys. Reject additional non-synthetic fields, unexpected methods, multiple possible owners, or deviations from the known shape. Do not assume the `__` spelling itself proves Java nesting.
4. **Prefer metadata-only first.** Preserve the helper's actual `this_class`, jar entry name, all constant-pool references, fields, methods, method code, descriptors, signatures, annotations, and other attributes. Add `InnerClasses` with `inner_class_info` equal to the actual flattened helper name, `outer_class_info` equal to owner, and `inner_name` equal to the mapped suffix; add `EnclosingMethod(owner, null, null)`. Match access flags to the confirmed companion class (at minimum `ACC_STATIC | ACC_SYNTHETIC` in the inner entry). A separate canonical `$` rename is not metadata-only: it changes the class identity and requires consistent rewriting of every reference/entry across the jar and collision checks. Do not bundle that broader transform into the first patch without separate evidence and review.
5. **Assert bytecode preservation.** Compare a stable pre/post representation that includes class version/access, superclass/interfaces, all fields/methods and their code/instruction operands, exception tables, and non-nesting attributes; allow only the intended class-level `InnerClasses` and `EnclosingMethod` additions. Hashing method/field code alone would miss changes in class identity, signatures, references, or other attributes. Also verify every modified class parses and that no unrelated jar entry changes.
6. **Retain strict pipeline behavior.** Keep the ERROR counter/abort, failed-method-marker scan, required movement source checks, provenance and publication checks unchanged. Any eventual authorized exact-version generation must complete all of them before its output can be accepted.

## Semantic and technical risks

- Incorrect owner metadata can cause Vineflower to merge a class into the wrong outer source or alter decompiled Java structure. A flattened helper name with accurate attributes may or may not be treated identically to the canonical `$` name by Vineflower's class pool; source inspection establishes feasibility, not equivalence.
- A `$` rename affects symbolic class references in owner methods/fields and possibly other attributes, bootstrap data, annotations, signatures, and jar paths. Rewriting only the helper class's `this_class` would create an inconsistent archive. ASM tree visitation can preserve instruction opcodes while still changing symbolic operands, so it must not be described as bytecode-identical metadata-only repair.
- More generic discovery can incorrectly classify ordinary synthetic classes or lambdas. Exact mapping evidence plus the expected switch-table initializer pattern is required; the predicate must reject unfamiliar shapes rather than broaden silently.
- Even if the known `BlockElement` error is fixed, the remaining 58 diagnostics may have other causes. Passing this eligibility predicate does not imply all ERRORs are attributable to lost nesting metadata.

## Evidence boundary

The prior diagnosis's 59 `const(1) not found` messages and abort are accepted as reported evidence, as are the compared cached class names and the 1.8.2 nesting attributes. This review independently checked the engine's remap/decompile order and strict gate, the ASM dependencies, and cached `javap` details for the concrete 1.8.1/1.8.2 helper pair. No build, test, decompile, generation, cache mutation, source mutation, download, or launch was performed. Static feasibility is accepted; zero-ERROR decompile proof remains open and requires an explicitly authorized exact-version preparation run by the designated owner.
