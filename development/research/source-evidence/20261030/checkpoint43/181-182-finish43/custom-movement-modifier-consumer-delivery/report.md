## Paired modifier path

1. **Candidate source and parse.** `ItemStack.getAttributeModifiers` reads the `AttributeModifiers` NBT list when present, decodes the `AttributeName`, UUID, amount and operation through `EntityAttributes.fromNbt`, and accepts nonzero UUID halves (1.8.1 `ItemStack.java:669–687`, `EntityAttributes.java:95–101`; 1.8.2 `:667–687`, `:95–101`). The registered player attribute `generic.movementSpeed` is trackable on both sides (`EntityAttributes.java:18–20`). This is a custom-NBT route, not a vanilla default armor route; the paired item-provider inventory in `equipment-modifiers/report.md` found vanilla default Sword/Tool modifiers target attack damage only and no armor override.
2. **Apply, replace, and remove on the server.** `LivingEntity.tick` gates the equipment loop on `!world.isClient`, checks slots `0..4` in ascending order, and on a mismatch sends the equipment-state packet to viewers, removes the old stack's modifiers, adds the new stack's modifiers, then copies the current stack into its remembered equipment state (1.8.1 `LivingEntity.java:1261–1291`; 1.8.2 `:1259–1289`). Player slot 0 means selected hand and slots 1–4 mean armor (`PlayerEntity.java:1578–1590` / `:1580–1592`). `AbstractEntityAttributeContainer.removeModifiers/addModifiers` resolve the string name against registered attributes; addition removes a matching modifier before adding it, so a later slot's repeated UUID replaces an earlier one (old/new `AbstractEntityAttributeContainer.java:49–67`). The application order and gates match.
3. **Modifier math and collection order.** `ModifiableEntityAttributeInstance` marks the instance dirty on base/modifier updates and recomputes as base plus operation-0 amounts, then adds operation-1 contributions calculated from that operation-0 result, then multiplies by `(1 + amount)` for operation 2, finally clamping to the attribute range (old `ModifiableEntityAttributeInstance.java:42–46,76–96,99–155`; new `:42–46,76–96,99–154`). Modifier buckets and the per-operation calculation use sets; no stable intra-operation insertion order is promised. Both endpoints use the same three-operation order, set collection, and arithmetic.
4. **Server-to-owning-client delivery.** Movement speed is trackable and `EntityAttributeContainer.track` places changed instances in `getTracked`; `getTrackable` includes it for initial tracking (old/new `EntityAttributeContainer.java:42–70`). `EntityMap.onEntityAdded` starts a `TrackedEntity` for `ServerPlayerEntity` (old `EntityMap.java:56–65,119–137`; new `:57–66,120–137`). `TrackedEntity.sendDataAndAttributes` wraps the dirty set in `EntityAttributesS2CPacket` and clears the set; crucially, `sendPacketToAll` sends to tracking viewers **and also directly to the tracked `ServerPlayerEntity`'s own connection** (old `TrackedEntity.java:255–283`; new `:258–285`). This closes the owner-delivery uncertainty left in the earlier equipment report. The ordinary equipment packet uses `EntityMap.sendPacket`/`TrackedEntity.sendPacket`, which goes to viewers; the owner’s movement attribute is delivered by the attribute packet.
5. **Packet payload and client sink.** `EntityAttributesS2CPacket` carries entity ID, attribute name, base, and each modifier's UUID, amount, and operation; read/write field order and widths match (old packet `:21–65`; new `:21–70`). `ClientPlayNetworkHandler.handleEntityAttributes` resolves the entity, obtains/registers the named attribute, sets base, clears modifiers, and adds the packet modifiers (old `:1495–1519`; new `:1581–1607`). `ClientWorld.getEntity` explicitly resolves the local player's own network ID to `minecraft.player` (both `ClientWorld.java:188–190`). Thus a dirty `generic.movementSpeed` update reaches the local movement attribute state; the receiver ordering and writes match.
6. **Movement consumer.** `PlayerEntity.getSpeed()` reads `EntityAttributes.MOVEMENT_SPEED` directly (old `PlayerEntity.java:1295–1298`; new `:1297–1300`). In the locally controlled grounded branch, `LivingEntity.moveRelative` scales input by `getSpeed() * 0.16277136F / (slipperiness * 0.91F)^3` before `updateVelocity` (old `LivingEntity.java:1121–1142`; new `:1119–1140`). Air acceleration instead uses `speedInAir`; player flight substitutes ability fly speed. Consequently a custom movement-speed item modifier can change grounded horizontal input acceleration, while this consumer does not make that modifier a jump-strength change. Player `mobTick` also reads the attribute to set its speed field and preserves the same server-only walk-speed base assignment and sprint air-speed adjustment (old `PlayerEntity.java:425–453`; new `:431–459`).
