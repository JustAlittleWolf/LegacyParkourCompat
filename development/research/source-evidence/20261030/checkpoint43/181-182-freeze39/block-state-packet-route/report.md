## Checked routes

- **Single and multi-block updates:** `ClientPlayNetworkHandler.handleBlockUpdate` (1.8.1 `:602–605`, 1.8.2 `:599–602`) and `handleBlocksUpdate` (`:571–576`, `:568–573`) first marshal to the client thread, then apply each decoded vanilla state through `ClientWorld.setBlockStateFromPacket`. The latter clears the local block-reset range and calls `World.setBlockState(pos, state, 3)` (`ClientWorld.java:202–207`, both). `World.setBlockState` writes the chunk state, checks light, and notifies the client listeners under the same flags and gates. The packet layouts match: a single packed block position plus state-registry VarInt; a multi-update's chunk X/Z ints, count VarInt, then local-position short and state-registry VarInt per entry. The 1.8.2 nested update class is a decompiler/type-layout change; field widths and order are unchanged.
- **Chunk and bulk-chunk installation:** `handleWorldChunk` (`ClientPlayNetworkHandler.java:580–598` / `:577–595`) retains the same full-chunk behavior: a zero section mask unloads; otherwise a full packet loads; reset markers are cleared; decoded data is installed into the fetched chunk; the region is notified; border checks are reset under the same dimension condition. `handleWorldChunks` (`:1005–1020` / `:1004–1019`) loops in packet order, loads, clears reset markers, installs full chunk data, notifies the region, then applies the same border-check gate. `WorldChunk.update` (`:893–950` / `:905–962`) consumes section block-state chars low byte then high byte, block light, optional sky light, and full-chunk biomes in that order; it removes omitted sections on full updates, validates counters, populates the height map and clears block-entity caches. No player callback is run during this installation. The installed states feed later collision/shape queries through the ordinary world/chunk state lookup used by player movement. Single-chunk and bulk-chunk codecs preserve coordinate, full/light flag, section-mask, length/data ordering and widths.
- **Explosion destruction and velocity:** `handleExplosion` (`:824–831` / `:821–830`) constructs the same destructive client explosion from packet coordinates, power and damaged-block list, calls `damageBlocks(true)`, then adds packet X/Y/Z velocity to the local player in that order. `Explosion.damageBlocks` removes each listed non-air block with `World.setBlockState(... AIR ..., 3)` before the block's `onExploded` callback in both versions. Server `ServerWorld.explode` performs entity damage, `damageBlocks(false)`, clears the list only for non-destructive explosions, then sends the packet to players within squared distance `< 4096`; order and gate match. Explosion packet fields match: four floats, block count int, signed-byte coordinate offsets from `(int)`-truncated origin coordinates, then three velocity floats. The receiver therefore has the same terrain-removal route and direct player-velocity write.
- **Piston block event and direct player response:** `ClientPlayNetworkHandler.handleBlockEvent` (`:993–996` / `:992–995`) marshals to the client thread and calls `World.addBlockEvent(pos, block, type, data)`. That calls the packet-provided block's `doEvent` with the current state (`World.java:2459–2461` / `:2487–2489`). `PistonBaseBlock.doEvent` uses the same client path to start/finish piston movement and install/remove moving-block states; its server-side signal recheck is gated by `!world.isClient`. `MovingBlockEntity.moveEntities` (`:80–108`, both) is the direct movement response: intersecting entities are moved by `amount * facing offset`, except extending slime movement writes the facing-axis velocity. Block-event codec order is packed position, type byte, data byte, and block ID VarInt masked with 4095 in both versions. Server `ServerWorld.addBlockEvent` deduplicates equal events in the active queue. `doBlockEvents` flips queue index, runs each event against the current state only when its current block identity matches, then sends the same block event to viewers within radius 64 only when `doEvent` returns true. This queue/recheck/send order is unchanged.
- **Ordinary state-update producer ordering:** `ServerWorldEventListener.notifyBlockChanged` routes into the chunk map. The chunk holder records the section bit and deduplicates local positions; `sendChanges` sends one single-block packet for exactly one change, a partial chunk packet at 64 changes, or a multi-block packet otherwise, then sends applicable block-entity updates, and clears dirty counters last. The paired 1.8.1 separate `ChunkMap__ChunkHolder` and 1.8.2 nested `ChunkMap.ChunkHolder` bodies preserve this ordering and thresholds. Initial chunk delivery also sends one full-chunk packet or one bulk packet before block-entity updates and entity tracking in both `ServerPlayerEntity` bodies. Direct interaction rollback producers send the same per-position block updates in the inspected branches.

## Source delta and scope

`PistonBaseBlock.shouldExtend` (`:83–103` on each side) differs at the self-position power check: 1.8.1 tests `world.hasSignal(pos, Direction.NORTH)` at `:90`; 1.8.2 tests `Direction.DOWN`. The surrounding neighbor loops and `PistonBaseBlock.doEvent` server gate/order match. This predicate can change whether the server queues/executes a piston extension/retraction and sends a block-event packet. If an event is sent, the client callback path above can move a local player (including the extending-slime velocity write). This is an authoritative world-state producer difference; the client packet receiver and direct response implementation show no paired difference, and no historical server-physics claim follows from it. It is the same adjacent candidate already noted in the earlier tick-terminal inventory and should be dispositioned against that ownership record.
