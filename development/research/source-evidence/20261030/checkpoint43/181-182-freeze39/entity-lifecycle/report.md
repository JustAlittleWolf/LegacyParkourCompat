## Ordered evidence

1. **Equality and chunk membership container differ.** In 1.8.1, `net/minecraft/util/TypeInstanceMultiMap.java:3-13,49-70` stores per-type values in Guava `HashMultimap` and its set-backed values; `add` uses `put`, while `remove` uses multimap value removal. In 1.8.2, `TypeInstanceMultiMap.java:13-19,54-87` uses an `ArrayList` for base instances and per-type lists; `add` appends and `remove` calls `List.remove`. The list container therefore allows repeated memberships and does not depend on a value's old hash bucket.
2. **Entity identity is network-ID-based in both.** `net/minecraft/entity/Entity.java` 1.8.1 `equals/hashCode` at `176-182`, and 1.8.2 at `172-178`, compare/hash `networkId`. `setNetworkId` is a plain mutable field write (1.8.1 `135-137`; 1.8.2 `131-133`). This makes hash-container membership sensitive to changing an entity's network ID after insertion.
3. **Chunk add/remove consumes that container.** `net/minecraft/world/chunk/WorldChunk.java` 1.8.1 `572-611` and 1.8.2 `582-621` perform the same coordinate/Y clamp, set `inChunk` and chunk coordinates, then `entities[section].add(entity)`; removal calls `entities[section].remove(entity)`. The list/map insertion and removal methods themselves have no duplicate guard. Chunk-query code (1.8.1 `700-725`; 1.8.2 `710-737`) selects by Y section, shape intersection and object-reference exclusion, and does not reject `removed` entities.
4. **Normal local-player ID mutation is reachable, but self-excluded from local player movement queries.** On game join, `ClientPlayNetworkHandler` calls `Minecraft.setWorld(world)` before `player.setNetworkId(packet.getEntityId())` (1.8.1 handler `256-259`; 1.8.2 `250-253`). `Minecraft.setWorld` adds the local player to the world (`Minecraft.java` 1.8.1 `1740-1755`; 1.8.2 `1773-1790`). Respawn likewise removes the old local player, creates a replacement, adds it, then restores the previous network ID (1.8.1 `1767-1790`; 1.8.2 `1802-1825`). If this changes the inserted object's hash, 1.8.1 hash-backed chunk removal can fail when it later crosses chunk sections; the same object can remain in an old chunk container as it is added to the new one. The 1.8.2 list removal searches by equality after the mutation and removes the old membership. For the local player's own `Entity.move` collision query, however, `WorldChunk.getEntities` excludes the exact same player object by reference; `World.getCollisions` calls `World.getEntities(entity, ...)` (1.8.1 `873-927`; 1.8.2 `891-945`), and `Entity.move` calls that collision routine (1.8.1 `443` and step branch `473`; 1.8.2 `439` and step branch `469`). `PlayerEntity`'s post-tick entity query also passes itself as the excluded object (1.8.1 `478-485`; 1.8.2 `484-491`). Thus stale extra memberships of the local player do not put the local player into its own movement candidate list. Effects on other entities' collision queries are outside this assignment's player-movement consumer and the project excludes non-player physics.
5. **Packet spawn/remove replacement is a distinct conditional route.** `ClientWorld.forceEntity` in both versions (`ClientWorld.java:172-185`) gets an existing object by network ID, calls `removeEntity(existing)` if found, then sets the incoming ID, calls `addEntity`, and writes the ID map. `ClientWorld.removeEntity(int)` (`192-200`) removes the ID-map/set entry and marks the object removed through `removeEntity(Entity)`; ordinary non-player cleanup from `World.tickEntities` is deferred to the removed entity's slot (`World.java` 1.8.1 `1187-1221`; 1.8.2 `1205-1239`). A remove-ID packet followed by a new spawn with that same ID before the next world tick can therefore leave both distinct objects in the chunk container temporarily in 1.8.2. In 1.8.1 the set-backed container treats the distinct objects as equal by network ID and does not admit the new value while the old value remains. The 1.8.2 query does not filter the old object's `removed` flag, and `World.getCollisions` consumes returned collision shapes. `BoatEntity` is a concrete viable provider in both versions: its `getCollisionShape()` returns its own box and `getCollisionAgainstShape(other)` returns the other entity's box (`BoatEntity.java:52-60`). If old and new colliders have different positions/shapes and overlap the local player's queried region, this is a conditional in-scope movement divergence.
6. **Packet and tick order permit that window, given the ID-reuse precondition.** `PacketUtils.ensureOnSameThread` schedules off-thread packet handlers through `Minecraft.executeTask` (both `PacketUtils.java:8-12`). `Minecraft.runGame` drains scheduled tasks before calling `tick` (1.8.1 `800-813`; 1.8.2 `818-831`); `Minecraft.tick` invokes `world.tickEntities()` at 1.8.1 `1599` / 1.8.2 `1634` (the entity/player tick pass), then calls `world.tick()` at 1.8.1 `1615` / 1.8.2 `1650`; `connection.tick()` is later at 1.8.1 `1640` / 1.8.2 `1675`. For an already-queued ordered remove+spawn sequence, the resulting world mutation happens before the next `World.tickEntities`. That tick walks `world.entities` in insertion order and removes a flagged object only when reaching its own slot. Game join inserts the local player before later remote spawns; a replaced remote object is consequently later in the list than the local player, so the local player's `tickEntity`/movement can query chunk membership before the old object's deferred cleanup that tick. This establishes client-side timing; it does not prove vanilla server ID reuse.
7. **Same-object repeat insertion is not shown as a valid vanilla caller path.** `ClientWorld.tick` retries pending entities only when `!entities.contains(entity)` (1.8.1/1.8.2 `69-74`). `World.addEntityAlways` also guards `!entities.contains(entity)` (1.8.1 `2443-2445`; 1.8.2 `2471-2473`). `forceEntity`'s packet callers construct a new entity for each add packet: `handleAddEntity`, `handleAddExperienceOrb`, `handleAddPainting`, `handleAddPlayer`, and `handleAddMob` then call `forceEntity` (1.8.1 handler `268-379`, `405-449`, `690-716`; 1.8.2 `262-369`, `395-441`, `687-713`). Therefore the container's allowance of duplicate insertions of the exact same object is an API-level possibility, not a reachable vanilla client spawn/retry/respawn path established here. A spawn packet reusing a currently live ID without a preceding removal is an invalid duplicate-live-ID world invariant. A local-player-ID spawn collides with `ClientWorld.getEntity`'s explicit self-player branch (`ClientWorld.java:187-190`) and is likewise not a valid server spawn for the local player.

## Coverage and verdict

- **Examined:** paired `TypeInstanceMultiMap` equality/container semantics; `Entity.equals/hashCode/setNetworkId`; `WorldChunk` add/remove and entity query; `World.addEntity` and tick-order cleanup; `ClientWorld` add/force/remove/pending retry; client packet spawn, remove and respawn callers; `Minecraft.setWorld`/local-player respawn insertion order; player `Entity.move`/`World.getCollisions` and post-tick entity query; boat collision-shape provider. Hashes for these compared files are in the paired provenance and local source identity above.
- **No in-scope movement difference established for the normal local-player ID mutation route:** it can leave stale 1.8.1 membership, but the local player's movement queries exclude that same object by reference. Other-entity consequences are outside this player-movement slice.
- **Conditional movement candidate, applicability unresolved:** distinct old/new same-network-ID objects can coexist in 1.8.2 chunk membership before the old removed entity's list slot is cleaned, with a viable collision-shape path (e.g. boat). An ordered remove-ID plus ID-reuse spawn is sufficient on the client. A duplicate spawn while the old ID is live is invalid. This slice did not inspect exact server entity-ID allocation/tracking, so it cannot classify same-tick ID reuse as a valid vanilla server emission. Do not accept an unconditional movement finding from this report alone.
- **Partial/unexamined:** vanilla server ID allocation/tracker packet ordering and all entity subclass-specific collision shapes beyond the boat witness. No intermediate release inspected. No independent coverage audit performed.
