# Independent source audit: entity index candidate, 1.8.1 → 1.8.2

## Verdict

**Accept as a conditional, source-supported movement candidate.** The report correctly identifies the collection change and the client-side pre-tick window. Its unresolved server-reachability gate can be narrowed: vanilla allocates entity IDs with a static Java `int` increment, so a given ID recurs after a full 2^32 entity-constructor increments. `EntityMap` rejects an ID while it is already tracked, but removing the old entity first removes that map entry and sends its removal packet; a newly constructed entity that receives the wrapped ID can then be tracked and spawn normally. Thus the reported sequence is possible in vanilla after the wrap precondition, though it is not ordinary ID reuse. It must remain explicitly conditional on the old and new boats' geometry and packet handling before the next client tick.

This does **not** establish a general same-ID-replacement behavior for ordinary entity lifetimes. The server's active-ID uniqueness check rejects concurrent reuse. The report's boat witness is pertinent to the wrap case. Server player respawn also copies the old player ID to the replacement after removing the old tracker, but the generic entity collision-shape method returns null for players; that path alone does not establish the boat collision witness.

## Verified source chain

- `Entity` has a static `int nextNetworkId`; its constructor assigns `nextNetworkId++` (1.8.1 lines 57, 143–145; 1.8.2 lines 53, 139–141). Java `int` overflow makes the same ID recur after 2^32 constructions.
- `EntityMap.startTracking` checks `entitiesById.containsKey(id)` and rejects/logs a duplicate; `onEntityRemoved` removes the ID entry before calling `TrackedEntity.onRemoved` (both versions: 1.8.1 `EntityMap.java:123–167`, 1.8.2 `:124–177`). `TrackedEntity.onRemoved` sends removal packets to viewers (1.8.1 `TrackedEntity.java:285–289`, 1.8.2 `:288–292`). `ServerWorldEventListener` connects world add/remove notifications to the tracker (both `:28–36`).
- A concrete vanilla boat route exists after the wrap precondition: `PlayerManager.remove` immediately calls `removeEntityNow(player.vehicle)` for a departing player's mount (1.8.1 `PlayerManager.java:257–264`; 1.8.2 `:290–298`), which notifies the server tracker and sends its removal to viewers. `BoatItem` constructs and adds a boat server-side when another player places one (1.8.1 `BoatItem.java:66–80`; 1.8.2 `:65–78`). With the old tracked boat retained until the counter is about to recur, that removal can precede construction/tracking of a new boat with the wrapped ID; after removal, the tracker guard permits it, and the add is emitted to eligible viewers. This establishes a source-reachable remove/add pair with the explicit 2^32-construction and packet-before-client-tick conditions. It is not ordinary same-tick allocator behavior.
- Client packet handlers use `PacketUtils.ensureOnSameThread`; off-thread handlers enqueue work via `Minecraft.executeTask` (1.8.1 `PacketUtils.java:7–13`, `Minecraft.java:2284–2304`; 1.8.2 `PacketUtils.java:7–17`, `Minecraft.java:2390–2410`). The task queue is FIFO (`tasks.add` and `tasks.poll`; 1.8.1 `Minecraft.java:800–805`, 1.8.2 `:818–823`) and drains before `tick` (`:811–813` / `:829–831`). Therefore a server-ordered remove/add pair already queued before the frame's tick executes in that order before player movement.
- On the client, `removeEntity(int)` removes the ID-map entry and calls `removeEntity(old)`, which sets `old.removed` but does not immediately remove it from the world/chunk lists (`ClientWorld.java:192–200`, `World.java:831–846` / 1.8.2 `:849–864`, `Entity.java:200–202` / `:196–198`). `forceEntity` then adds the replacement and updates the ID map (`ClientWorld.java:172–185`). `World.tickEntities` processes the existing `entities` list in order, skipping a removed object's tick and removing its chunk membership only at that object's list slot (`World.java:1187–1221` / `:1205–1238`). With the local player earlier in the list than the replaced remote entity, its movement query occurs before old-object chunk cleanup.
- `WorldChunk.getEntities` checks shape intersection and reference exclusion, with no `removed` check (`WorldChunk.java:700–724` / `:710–736`). `World.getCollisions` consumes the resulting entities' collision shapes without a removed-flag filter (`World.java:909–924` / `:927–944`). In 1.8.1 the hash-backed set sees old and new entities as equal by their unchanged shared network ID, so the replacement is not added while old is present. In 1.8.2 the base/per-type `ArrayList`s admit both (`TypeInstanceMultiMap.java:10–13,49–69` / `:13–19,54–86`; `Entity.equals/hashCode` at 1.8.1 `:176–182`, 1.8.2 `:172–178`). A boat supplies a concrete collision shape (`BoatEntity.java:52–60` on both sides). If the replacement boat intersects the local player's collision query and the old boat does not, only 1.8.2 contributes the new boat's box during that movement query.

## Normal local-player ID mutation route

The report's no-delta conclusion is supported. Login calls `Minecraft.setWorld` before assigning the server entity ID (`ClientPlayNetworkHandler.java:245–260` / `:240–254`); `setWorld` inserts the local player into the world before that assignment (`Minecraft.java:1698–1755` / `:1733–1790`). Mutating the ID can therefore leave a hash-backed chunk membership stale when removal later uses the new hash. But local `Entity.move` collision queries pass the exact player object as the exclusion (`World.java:909–910` / `:927–928`; `Entity.move` at 1.8.1 `:443,473`, 1.8.2 `:439,469`), and `WorldChunk.getEntities` excludes by reference. The post-tick player entity query likewise excludes self by reference (`PlayerEntity.java:478–485` / `:484–491`). The stale self-membership does not enter those local-player query results, so this route establishes no movement delta.
