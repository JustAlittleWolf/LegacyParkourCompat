## Paired entity index storage role

Both versions use `Entity.equals/hashCode` by `networkId`; therefore 1.8.1 membership deduplicates distinct Entity objects that share an ID, while 1.8.2 list insertion retains both. The 1.8.2 `contains` implementation walks the class-typed view; no corresponding override exists in 1.8.1. This is a data-structure/membership behavior change whose movement consequence depends on lifecycle reachability and query timing.

## Direct client-world lifecycle route identified; needs final timing audit

Both `ClientWorld.forceEntity(int, Entity)` bodies have the same relevant sequence: lookup entity by network id; if present, call `removeEntity(old)`; add replacement to `forcedEntities`; set its network id; call `addEntity(replacement)`; and replace `entitiesById` entry. Both paired `World.removeEntity(Entity)` bodies call `entity.remove()` but do not synchronously remove chunk membership or the entity from the world entity list. `Entity.remove()` only sets `removed = true`. `WorldChunk.addEntity` unconditionally inserts into its per-section TypeInstanceMultiMap and has no membership guard; `WorldChunk.removeEntity` removes from the section selected by stored chunkY. `World.addEntity` also appends to the world entity list without a duplicate check.

Therefore a same-network-ID `forceEntity` replacement can temporarily create membership of old (removed) and replacement entities in the same chunk section until the world's removal pass deletes the old membership. The existence and duration of an interval where a local-player collision query observes both must be confirmed by exact packet-thread/task ordering and local-player/world tick ordering. If observed, this is distinct shapes, so the old set-backed map can leave only the old equal member while the new list can include both. The edge is potentially reachable with a despawn/reuse or force replacement sequence; it cannot be dismissed solely as an invalid duplicate-ID invariant because `forceEntity` explicitly implements replacement on ID collision. Whether this sequence is a valid server packet lifecycle and intersects a player movement query remains unresolved pending child audit.

Paired callsite trace already established in prior source evidence: `World.getCollisions` asks `World.getEntities`; `World.getEntities` reaches `WorldChunk.getEntities`; that routine walks the section `TypeInstanceMultiMap`, tests shape intersection and appends entity candidates; `Entity.move` reduces candidates by Box axis clipping.
