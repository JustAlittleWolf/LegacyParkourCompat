## Residual candidates and gate assessment

### Entity index change: conditional source-supported movement candidate

The paired `TypeInstanceMultiMap` sources confirm a storage-semantic delta. In 1.8.1, the base-type view is a Guava `HashMultimap` set; in 1.8.2, the base instances are held in an `ArrayList`. `Entity.equals/hashCode` use the mutable network ID in both versions. Thus distinct old/new entities sharing an ID are deduplicated by the old set while both can be retained by the new list. The paired `Box.intersectX/Y/Z` operations are order-independent for ordinary finite collision boxes, and repeated identical boxes are idempotent; those facts close the enumeration-order question but do not close the different-shape membership case.

The required same-ID server precondition is now source-closed to an extreme wrap case, not ordinary ID reuse: the server entity constructor increments a static Java `int` without an overflow guard, so the ID can recur after 2^32 constructions. The server tracker rejects an ID while it is actively tracked, but removal clears the old tracking entry; after the wrap, a removed old boat and a newly constructed boat can therefore be emitted as an ordered remove/add pair. The client schedules packet work FIFO and drains it before `Minecraft.tick`; its removal marks the old entity but chunk cleanup is deferred until the old entity's later slot in the world entity list. The local player is earlier in that list. The chunk query does not reject `removed` entities, and a boat supplies a non-null collision shape. If the old and new boat boxes differ such that only the new box intersects the local player's movement query, the 1.8.2 list can add a clipping box that the 1.8.1 set omits.

**Disposition:** preserve this as a conditional, source-supported movement candidate with explicit `2^32` constructor-wrap, old-tracked-entity removal, ordered packet-before-tick, and differing collision-box/query preconditions. Do not generalize it to normal ID reuse or demand a forced runtime witness for source acceptance. The evidence has not measured a particular trajectory or demonstrated a quantitative position divergence.

### Piston trigger: confirmed server-side predicate delta, movement disposition open

`PistonBaseBlock.shouldExtend` uses a self-position signal test with `Direction.NORTH` in 1.8.1 and `Direction.DOWN` in 1.8.2. The surrounding `checkExtended` and `doEvent` signal recheck are gated by `!world.isClient` in both versions. This is a real source delta in the authoritative server-side trigger/state producer. Paired client packet routing and `MovingBlockEntity.moveEntities` show that a delivered piston event can directly move intersecting entities, including applying the extending-slime velocity response; the checked client response operations have no reported delta.

**Disposition:** do not label this a historical server-physics change. It can change the vanilla world state/event delivered to the client, so the server-only gate does not by itself close its effect on the client movement environment. The assigned owner/crosswalk must decide whether and how this source delta belongs in the pair inventory and close the exact signal → queued event → delivered state/event → player-response dependency before freeze.

## Exact remaining gaps preventing freeze

1. **Player tick and environment terminal coverage remains partial.** The independent coverage table leaves the full game-loop/entity dispatcher partial, the rest of `Entity.baseTick` and environment interaction partial, and other status/equipment/attribute branches only partly re-audited. The core and independent reports leave fluid world scans and changing liquid-state providers open. The tick inventory explicitly did not audit server scheduled block ticks or all client-side state changes that feed later movement.
2. **No pair-wide terminal role/method crosswalk is present.** The freeze39 `all-java-method-join` note closes the entity-index role and the prior reports document selected flattened/nested roles; it does not enumerate every player-tick, collision-provider, state-provider, callback, and external-input terminal role with a case-sensitive paired method or a verified absence on the other side. The 2,500/1,612 manifest counts do not substitute for that crosswalk. The referenced `development/research/.native-source/20261030/early18-pool34/1.8.1--1.8.2-entity-query-order/order-analysis.md` was not present in this checkout. Its relevant order discussion is partly present in `core-scan.md` and the freeze39 entity-index/all-java-join reports, but that missing artifact cannot be treated as additional reviewed evidence.
3. **External client state/input inventory is not exhaustive.** The reports compare named packet paths and payloads, but explicitly leave full packet registration/dispatch coverage and other packet-to-player-state routes open. The block-state report closes selected single/multi/chunk/bulk/explosion/event paths, not every server world-state producer. The server-producer report likewise scopes its end-to-end codec checks to named replicated inputs.
4. **The local custom movement-modifier route remains open.** The paired item parser supports custom NBT `AttributeModifiers` naming `generic.movementSpeed`, while default item/armor modifiers do not change player movement. The reports do not close whether an equipment-derived custom modifier reaches the owning local player's predicted movement state through the complete inventory/equipment update, attribute mutation, tracking, packet and client-sink sequence. This is a specific owner-local dependency gate, not evidence of a 1.8.1→1.8.2 delta.
5. **Resources and tags are absent from the source evidence.** The reports identify mapped Java trees only and make no resource/tag absence claim. Any relevant resource/tag-dependent movement state must remain unexamined until exact-version resource inputs and hashes are supplied; otherwise the pair record must retain this explicit gate.
