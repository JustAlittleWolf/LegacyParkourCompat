## Findings

1. **The `V1_9` empty barrier leaves accepted 1.9 aliases unimplemented and also leaves the distinct 1.8.9 response unimplemented.** In candidate `src/client/java/me/wolfii/legacyparkourcompat/change/v1_9/piston/NativeCobblestoneStairPush.java:12-23`, `clearance` always returns empty. With closest-applicable `emulates >= selected` resolution, this makes 1.9 profiles retain 26.2's modern collision-box response despite the accepted early-alias report `.native-source/20261030/piston-early-aliases38/report.md` establishing the same `+0.36 X` old response for 1.9–1.9.4. For 1.8.9 the same witness requests `+0.5625 X`, a different historical rule, not native 26.2 behavior. Add the accepted 1.9 behavior at the 1.9 boundary and handle 1.8.9 with its own proven rule or explicitly keep the candidate's applicability and product support scope above those profiles. The existing lower barrier does prevent the 1.10.1 change from falling through to 1.8.9, but it does not provide 1.8.9 behavior.

2. **The branch override is anchored at `JUMP IFLE`, not the exact local `STORE` seam requested for this review.** Candidate `src/client/java/me/wolfii/legacyparkourcompat/mixin/PistonMovingBlockEntityMixin.java:54-60` uses `@ModifyVariable(at = @At(value = "JUMP", opcode = Opcodes.IFLE), ordinal = 1)`. The mapped 26.2 source has `delta` initialized at line 167, updated in the per-shape loop at lines 169-176, and tested by `if (!(delta <= 0.0))` at lines 180-182. Pin the injection to the audited `delta` local's precise `STORE` occurrence/ordinal before that gate, with the target method descriptor, and ensure the edit affects only that local after the shape loop. The present ordinal is only a type-local ordinal at a jump, so it does not demonstrate the requested store binding and is brittle against compiler/local-layout changes. The native 26.2 mapped source signatures give `moveCollidedEntities(Level, BlockPos, float, PistonMovingBlockEntity): void` (`(Lnet/minecraft/world/level/Level;Lnet/minecraft/core/BlockPos;FLnet/minecraft/world/level/block/piston/PistonMovingBlockEntity;)V`) and `moveEntityByPiston(Direction, Entity, double, Direction): void` (`(Lnet/minecraft/core/Direction;Lnet/minecraft/world/entity/Entity;DLnet/minecraft/core/Direction;)V`). There is no compiled class artifact in the supplied canonical source tree, and compiling was out of scope, so binary descriptors were not independently checked against a compiled artifact.

3. **The recipient is captured before the native `IGNORE` decision, not after it.** In candidate `PistonMovingBlockEntityMixin.java:45-51`, the handler stores the local player in context before obtaining and returning the native push reaction. The current stair witness uses an ordinary admitted player, and the inner native scan overwrites context as it advances, so I found no counterexample in the bounded witness. Still, make the context recipient conditional on the returned native reaction being non-`IGNORE`, or use a seam after the native admission branch. This satisfies the required admitted-recipient contract and avoids reliance on the current vanilla player reaction implementation.

## Confirmed bounded behavior

- The candidate's `CobblestoneStairPush` resolves only the modern `minecraft:cobblestone_stairs` registry identity, consistent with the accepted reconciliation's semantic mapping from historical `stone_stairs` (which was cobblestone-backed) and the 26.2 registration. It rejects retracting movement, builds the old current/previous unit-outline union using float progress offsets, checks the old positive intersection gate, and derives the axis clearance from that union.
- For the accepted bottom straight stair witness at old profile 1.10.2 and 26.2 target state, the candidate computes the unpadded `1 - 0.65 = 0.35` clearance; its native `Math.min` redirect returns that amount and the unchanged native `+0.01` yields `+0.36 X`. Thus the accepted witness itself is implemented on profiles where the `V1_10_1` hook is selected. The candidate's native delta sentinel only opens the existing positive branch; nonpositive historical clearance keeps the native no-push branch.
- The seam is per-recipient and leaves other recipients' native delta untouched. It does not replace world entity enumeration, reorder the loop, replace block state or globally alter stair collision shapes. `moveEntityByPiston` remains the movement/callback path, preserving native PISTON/noClip and movement bookkeeping. The existing product `PistonMovement` change is needed to retain old uncapped/untyped movement semantics; it remains independently resolved. This review does not establish equivalence of all callback side effects.
- `PistonMovingBlockEntityMixin` is already present in the product checkout as the callback-origin adapter, and the candidate has another class of the same package/name. Product reconciliation must merge the candidate injections into that existing class and retain its `@ModifyArg` callback-origin handler. Product `legacyparkourcompat.mixins.json` currently has no `PistonMovingBlockEntityMixin` entry; the candidate's config adds it to the client list. Integration must register the merged mixin client-side, without adding a duplicate class.
- The candidate only modifies the client mixin config; its `MovementRuntime.appliesTo` gate checks player, client level and enabled profile. The response override is further limited to `entity == Minecraft.getInstance().player`. No logical-server movement is introduced.
