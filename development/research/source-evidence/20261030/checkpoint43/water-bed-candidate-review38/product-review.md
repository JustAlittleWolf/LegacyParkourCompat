## Reachability and parity at the predicate seam

In the exact 26.2 unobfuscated source, `EntityFluidInteraction.update(Entity, boolean)V` scans cells and calls `FluidState.getFlow(BlockGetter, BlockPos)Vec3` (`EntityFluidInteraction.java:32, 74`). `FluidState.getFlow` delegates to the fluid receiver’s `getFlow(BlockGetter, BlockPos, FluidState)Vec3` (`FluidState.java:95–97`). For a falling water state, `FlowingFluid.getFlow` (`FlowingFluid.java:55, 89–94`) checks each horizontal direction at the side and then, only if needed, at `side.above()`. Both calls bind to `isSolidFace(BlockGetter, BlockPos, Direction)Z` (`FlowingFluid.java:106–112`); for a horizontal non-ice bed with no same-fluid state, that method reaches `BlockState.isFaceSturdy(BlockGetter, BlockPos, Direction)Z`.

The product `@WrapOperation` targets that exact `isFaceSturdy` invocation. It receives the raw queried `BlockState`, the `FlowingFluid` receiver and direction. The existing `EntityFluidInteractionMixin` wraps the exact `FluidState.getFlow(BlockGetter, BlockPos)Vec3` invocation and establishes `MovementRuntime.localPlayerFluidCurrent()` only while a profile-enabled `LocalPlayer` is being scanned (`EntityFluidInteractionMixin.java:41–48`; `MovementRuntime.java:186–205`). Thus the bed hook is reached by the actual native fallback scan for the accepted falling-water witness. If a bed is the side candidate the first predicate returns true and the existing `||` short-circuits; if the side is not solid but its above-cell is a bed, the second predicate call reaches the same hook.

The source contrast is bounded and matches the implementation: 1.11.2’s `LiquidBlock.isFaceSolid` delegates to `Block.isFaceSolid`, whose material check regards `BedBlock`’s `Material.WOOL` as solid. From 1.12, the liquid predicate checks directional face shape and bed returns `UNDEFINED`. On the accepted level-eight, zero-gradient witness, the old predicate therefore lets native `getFlow` apply its existing normalized downward term; the new-side predicate leaves the bed non-solid. The candidate changes only that one boolean and leaves native side/above order, early exit, `normalize().add(0,-6,0)`, and final normalization intact.

## Scope and preserved behavior

The new keyed variant is `minecraft:red_bed`. The implementation returns true only when the flow receiver is water, the scoped player is non-flying and not riding an `AbstractBoat`, and the queried raw state is red bed; all other calls use `vanilla.get()`. The client-only Mixin config and existing local-player context retain the client/profile gate. The falling-water call site supplies the high-level gate: 26.2 `LiquidBlock` maps level 8 to `getFlowing(8, true)` (`LiquidBlock.java:72–77, 124–127`), which reaches the `FALLING` branch. No broader scan, height, provider or aggregation behavior is added. Current `WaterScan` still sends `LEVEL >= 8` through native current fallback, so this predicate has an execution path for that case.

Variant dispatch is by the queried state’s block identifier (`MovementRuntime.find(..., state.getBlock(), player)`). The red-bed implementation cannot alter other queried block types or colored beds. The existing chorus-flower V1_19_3 native and V1_20 implementations only changed method parameters; their `vanilla.get()` and horizontal-face logic are unchanged (`NativeChorusFlowerFallingFluidFace.java:27–30`, `ChorusFlowerFallingFluidFace.java:36–40`). A non-water fluid reaches the bed hook only if the red-bed variant resolves, then fails the water tag test and returns native. A non-bed/non-chorus block has no matching variant and uses the native supplier. With no red-bed hook at V1_12 or later, those profiles retain the new native bed-face behavior.

The lower V1_10_1 native variant prevents backdating into the uninspected 1.10.1 member of that enum group. It consequently also leaves exact 1.10.2 native, despite the supplementary audit finding the old predicate there; this review accepts the assigned 1.11.2-to-1.12.2 profile boundary only. The product classes use the existing discovered, keyed hook and client mixin, with no new mixin, context, registration loop, or JSON entry.

No blocker was found in the requested predicate wiring. The source evidence and this review do not verify historical scan bounds/current aggregation outside the accepted witness, and do not prove runtime parity.
