# Bounded independent source audit: eye-water point sampling

## Verdict

**Supported for the bounded current-tick sampling operation.** The direct-point form is present in 1.15, 1.15.1, and 1.15.2. The cached-read form first appears in 1.16 and remains in 1.16.1 through 1.16.5. In 1.16, `Player.tick` still calls `updateIsUnderwater()` before `super.tick()`, but the call now reads `isEyeInFluid(WATER)` from the cache. `Entity.baseTick` refreshes that cache only later in the superclass tick. `LocalPlayer.isUnderWater()` returns `Player.wasUnderwater`; its sprint gates and the player swimming update therefore consume the result assigned before that refresh during this movement tick.

This accepts one operation and its local-player movement consumers. It does not close the pair inventory, freeze the pair, or establish an intermediate patch boundary more precise than first verified in 1.16.

## Exact source evidence

All inputs are the read-only canonical Mojmap roots at `D:\Javastuff\LegacyParkourCompat\decompiled_minecraft\<version>\mojmap`. The release records and verified per-source SHA-256 entries are in `source-hashes.json`. I checked the visible parent `mojmap.ready.json` / `mojmap.sources.sha256` markers where present and the embedded `.decompile-provenance.json` manifests for 1.16.3 and 1.16.4; every recorded target source file matched its ledger or embedded source map.

For 1.15, 1.15.1, and 1.15.2, the exact method fingerprints match for `Player.tick`, `Player.updateIsUnderwater`, and `Entity.isUnderLiquid(Tag<Fluid>, boolean)`. `LocalPlayer.isUnderWater()`, `LocalPlayer.updateIsUnderwater()`, and its sprint impulse helper also match. This confirms those releases share the relevant direct-query operation despite unrelated file-level changes.

For 1.16 through 1.16.5, `Player.tick` and `Player.updateIsUnderwater` retain the same method fingerprints. The latter assigns `wasUnderwater = isEyeInFluid(FluidTags.WATER)`. The `Entity.baseTick` and `updateFluidOnEyes` bodies have a later 1.16.2 alias group: the eye-producer boat bounding-box gate changes from `contains(vec3)` in 1.16/1.16.1 to a Y interval check in 1.16.2–1.16.5. That does not affect the accepted non-boat case. The consumer precondition below also excludes boat/tag ambiguities rather than assuming producer equivalence for them.

### Tick order and consumers

- **1.15.2:** `Player.tick` calls `updateIsUnderwater()` at `Player.java:236` before `super.tick()` at `237`. `Player.updateIsUnderwater()` at `Player.java:298–300` assigns from `isUnderLiquid(FluidTags.WATER, true)`. `Entity.isUnderLiquid(Tag<Fluid>, boolean)` at `Entity.java:1040–1052` rejects boat passengers, uses the current `getEyeY()`, requires the selected chunk to be loaded when the boolean is true, checks the water tag, and compares the eye against the fluid-height cutoff. The `LocalPlayer` override at `LocalPlayer.java:1004–1020` calls that super implementation and retains the result in `wasUnderwater`; `isUnderWater()` at `999–1001` returns that field.
- **1.16.5:** `Player.tick` calls `updateIsUnderwater()` at `Player.java:233` before `super.tick()` at `234`; `Player.updateIsUnderwater()` at `291–293` reads the cached tag. `Entity.tick()` calls `baseTick()` (`Entity.java:354–359`); `baseTick()` invokes `updateInWaterStateAndDoFluidPushing()`, `updateFluidOnEyes()`, then `updateSwimming()` (`380–382`). `updateFluidOnEyes()` (`981–1005`) first copies the previously cached water-tag result to `wasEyeInWater`, clears `fluidOnEyes`, and then samples the eye-height point and stores its first matching fluid tag. It does not rewrite `Player.wasUnderwater`. `LocalPlayer.isUnderWater()` (`1011–1012`) returns `wasUnderwater`, and its override of `updateIsUnderwater()` (`1016–1032`) retains the `Player` assignment while handling local sounds.
- **Sprint:** `LocalPlayer.aiStep()` in 1.15.2 (`658–692`) and 1.16.5 (`668–703`) uses `isUnderWater()` in sprint start and cancellation decisions. `hasEnoughImpulseToStartSprinting()` (`1.15.2:977–980`; `1.16.5:989–992`) uses `input.hasForwardImpulse()` when underwater and `forwardImpulse >= 0.8` otherwise. This is a predicate change in the same local-player AI step, not a claim that all threshold crossings change sprint state.
- **Swimming:** `Player.updateSwimming()` calls the entity implementation unless ability-flying (`1.15.2:1481–1486`; `1.16.5:1420–1426`). `Entity.updateSwimming()` (`949–954`) uses `isUnderWater()` when transitioning from not swimming. For `LocalPlayer`, virtual dispatch reaches the override returning `wasUnderwater`, so the refreshed `fluidOnEyes` value is not substituted into that tick's swimming decision.
- **Water travel:** local AI reaches `LivingEntity.travel` later in the tick. The water branch selects `0.9F` when sprinting and otherwise `getWaterSlowDown()` (`1.15.2:1929`; `1.16.5:1924–1926`), so a changed sprint decision can reach movement friction. This movement consequence is restricted to a non-flying player in the water-travel branch. 1.15.2 excludes flying players from its water branch (`LivingEntity.travel:1840`); in 1.16.5 `Player.isAffectedByFluids()` is `!abilities.flying` (`Player.java:1005–1007`) and the branch requires that predicate (`LivingEntity.travel:1924`).

## Scoped gates and arithmetic

The accepted comparison assumes corresponding world/fluid-tag inputs on both sides, a loaded chunk, no boat vehicle, a fixed pose while comparing the two decisions, a non-flying local player, and no other wrapper tag preceding WATER for the sampled fluid. The eye point may advance across the water boundary between the prior cache sample and the current direct query. In 1.15.2, the direct query uses `FluidTags.WATER`; in 1.16.5, `updateFluidOnEyes()` scans `FluidTags.getWrappers()` and returns on the first matching wrapper. No datapack tag-production or overlapping-wrapper claim is made. The new producer's boat condition is also outside the accepted non-boat precondition.

The fluid-height provider remains the same in the inspected releases: `FluidState.getHeight()` delegates to the fluid type, and `FlowingFluid.getHeight()` returns `1.0F` when the same fluid is above or the own height otherwise; `getOwnHeight()` returns `amount / 9.0F` (`FlowingFluid.java:470–476` in 1.15.2; `468–474` in 1.16 and 1.16.5). The eye point uses the live `getEyeY()` and therefore the current pose. The old direct comparison adds `0.11111111F` to the float height before adding block Y (`Entity.java:1052`); the cached producer subtracts `0.11111111F` from the double eye Y and compares it with block Y plus float height (`1.16.5 Entity.java:984, 993–1000`). I verified the distinct source expression and operand types but make no separate float-boundary witness claim here; the temporal cache difference alone supports this finding.

## Acceptance boundary

Accepted: `Player.updateIsUnderwater` changes from a direct current-point water-tag query to a cached eye-fluid read, first verified at 1.16; the late-in-tick refresh and `LocalPlayer` consumers make this a current movement-tick difference at an eye-water transition. The movement effect is conditional through sprint/swim gates and water-travel friction.

Not accepted by this audit: a numeric float-boundary witness, boat passenger behavior, overlapping/datapack fluid-tag behavior, flying movement, a full pair freeze, or runtime parity.
