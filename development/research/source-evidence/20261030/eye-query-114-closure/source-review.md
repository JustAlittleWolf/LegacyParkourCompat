## Versioned source contract

### 1.13.2

`net/minecraft/entity/Entity.java`, `isSubmergedIn`, lines 1042–1051: reject when `getMount() instanceof BoatEntity`; compute `double d = this.y + this.getEyeHeight()`; build `BlockPos(this.x, d, this.z)`; read `world.getFluidState(blockPos)`; require `fluidState.is(tag)` and `d < blockPos.getY() + (fluidState.getHeight() + 0.11111111F)`. This point query has no loaded-chunk branch. `net/minecraft/fluid/FlowingFluid.java`, `getHeight`, lines 447–450, is state-only and returns `state.getLevel() / 9.0F`.

The player caller is `PlayerEntity.tick`: `updateWaterSubmersion()` runs before `super.tick()` (`PlayerEntity.java:206–208`); `updateWaterSubmersion` assigns the result of `isSubmergedIn(WATER)` (`257–260`). The ordinary entity water-state update calls its own point query before `updateSwimming` (`Entity.java:947–950`, `979–980`). Local client player `updateWaterSubmersion` delegates to the player implementation (`LocalClientPlayerEntity.java:1004–1020`).

### 1.14 family, including patch alias variants

In the 1.14, 1.14.1, 1.14.2, and 1.14.3 Yarn sources, the player refresh runs before `super.tick()` (`PlayerEntity.java:217–219`, with a one-line shift in 1.14.3 at 218–220); `updateInWater` calls `isSubmergedIn(WATER, true)` (`267–270` in 1.14–1.14.2; `268–271` in 1.14.3). The entity query uses the same boat veto and point sample as 1.13.2, then checks `bl && !world.isChunkLoaded(blockX >> 4, blockZ >> 4)` before reading fluid (`Entity.java:986–998` in 1.14; `Entity.java:1032–1044` in 1.14.3). Thus ordinary public queries with `false` remain unguarded, while player cache refresh with `true` returns false before the fluid lookup if the eye block's chunk is not loaded. The matching 1.14.4 Feather helper is `m_69330161(tag, bl)` (`Entity.java:1039–1052`): same operation and argument meaning. `PlayerEntity.tick` calls `updateWaterSubmersion` before `super.tick` (`1.14.4 PlayerEntity.java:234–235`), and its update passes `true` (`284–286`).

The point height becomes contextual in 1.14.0: `BaseFluid.getHeight(state, blockView, pos)` returns `1.0F` when the above cell has the same fluid; otherwise it returns `state.getLevel() / 9.0F` (`1.14 BaseFluid.java:430–436`). The method persists through 1.14.1–1.14.3 (`BaseFluid.java:430–436` in .1/.2, `426–432` in .3) and 1.14.4 (`FlowingFluid.java:442–449`). The changing Yarn alias is the state fallback in 1.14.3, `arg.method_20785()`, for 1.14–1.14.2 `arg.getLevel() / 9.0F`; it is a name remap with the same float division. The 1.14.4 Feather fallback is likewise `state.m_10879879()` (`FlowingFluid.java:452–454`). The same-fluid-above predicate compares fluid identity/type, not the full fluid-state object.

The ordinary public query uses the helper with `false`; the internal refresh also has an explicit caller gate. In 1.14.4, `m_61708540` calls `m_69330161(WATER, true)` at `Entity.java:974–976`; that water-state routine then calls `updateSwimming` in order (`Entity.java:942–946`). In 1.14.3, `updateWetState` uses the loaded check for water at `Entity.java:967–969`; `updateSwimming` follows in the enclosing tick path. No inspected 1.14 patch source changes the eye query or contextual height rule. The point contract and loaded-check split are present in 1.14.0 and remain in the inspected .1–.4 patch sources.

### 26.2 comparison boundary

26.2 no longer calculates this point query when `Player.updateIsUnderwater` runs. `Player.tick` calls `updateIsUnderwater` before `super.tick()` (`Player.java:259–260`); that method reads `isEyeInFluid(WATER)` (`304–307`), which returns the existing tracker (`Entity.java:1738–1739`). Later, `Entity.baseTick` captures the same pre-refresh value in `wasEyeInWater`, then calls `updateFluidInteraction()` and `updateSwimming()` (`Entity.java:528–532`). `EntityFluidInteraction.update` resets tracker flags, scans the deflated/vehicle-adjusted fluid box and only scans after `hasFluidAndLoaded` succeeds for its x/z range expanded one block (`EntityFluidInteraction.java:32–89`). The eye witness is assigned only for the eye X/Z cell when `eyeY >= fluidBottom && eyeY <= fluidTop` (`68–70`). The preflight requires every intersecting chunk to be FULL without loading and at least one fluid-bearing section (`91–119`).

The provider must therefore preserve the 26.2 cached-result and prior-sample ordering when selected for that release; a point-query implementation would be the wrong provider contract for 26.2. 26.2 is included as a comparison-side closure only, not evidence that the 1.14 point operation continued through later releases.

## Exact arithmetic and reachable witnesses

- Legacy 1.13.2 computes eye Y in `double`; `BlockPos(double,double,double)` floors the point for the sample position. Its fluid height and `+ 0.11111111F` addition are `float` operations before the comparison with `double d`. Do not promote the addition or move the epsilon outside the parentheses.
- 1.14.x retains the same `double d`, floored point sample, strict `<`, and float epsilon addition. Only the height supplier changes to `getHeight(world, pos)`. The loaded test uses the integer sample coordinates shifted right four; it occurs before `getFluidState` and applies only when the boolean is true.
- A normal player eye at `x=15.25, z=8`, in water in block `(15, y, 8)`, is a loaded-chunk witness. With the player chunk `(0,0)` loaded and neighboring chunk `(1,0)` absent, the 1.13.2 point query can read the eye water state and succeed. The 1.14 player-refresh route rejects before reading it because the sampled eye block's chunk is not loaded; the eye cell itself is in the player chunk. This witness concerns the player `true` route, not the unguarded public `false` route.
- A separate fully loaded witness demonstrates contextual height: use a tagged flowing-fluid state with `state.getLevel()/9.0F < eyeY - blockY - 0.11111111F` and the same fluid immediately above. 1.13.2 uses only the lower state height and returns false; 1.14 obtains `1.0F` for the sampled cell and returns true for an eye below `blockY + (1.0F + 0.11111111F)`. This does not conflate the chunk gate with the height delta.
- The modern scan's inclusive `eyeY <= fluidTop`, padded full-chunk/section preflight, tracker membership, and vehicle-adjusted fluid box are separate query semantics. The prior 20261028 eye-admission source note covers the 26.2 loaded-edge witness; this review rechecked the query and caller lines above. Its 1.13.2 vs 26.2 statement should not be used as 1.14 implementation evidence without the 1.14 sources in this review.

## Minimal provider contract and closure gates

For 1.13.2–1.14.4, a minimal point-query provider must receive the requested fluid tag, player/entity eye sample inputs and world access; derive the floored eye `BlockPos`; enforce the boat veto; and perform the exact release-selected fluid-height procedure. It must retain the 1.14.x `checkLoaded` argument and gate before `getFluidState`; the player cache refresh requests the gate while the public query does not. The provider must not collapse the context-aware height into a state-only lookup. For 26.2, route through the tracker-backed cache with its refresh ordering and preflight instead of the point provider.

**Ready:** source method bodies; sample coordinates, casts and comparison boundaries; player and entity caller ordering; 1.14 contextual-height rule and fluid-above comparison; loaded-check gate; patch alias family; movement-relevant path through `updateSwimming`; and a reachable player result witness are supported by the listed exact sources.

**Open:** this review does not inspect 1.13.3–1.13.9 or versions after 26.2, so it cannot set a hidden first-patch commit/date or a wider cutover interval. The 1.14.0–.3 legacy Yarn folders have provenance-contained per-file hashes but lack separate canonical ready markers/source manifests; those hashes were verified against the provenance objects. No product implementation, wiki, backlog, tests, build, or runtime evidence was consulted.
