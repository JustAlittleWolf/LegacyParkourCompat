# Fluid contact and current closure: 1.13.2 → 1.14.4

## Scope and endpoint

Source-only comparison of Ornithe Feather Gen2 build 2 at the two assigned canonical roots. The allowed pair-audit review supplied the surfaced lava-contact and stacked-fluid claims. No product/wiki/backlog/history or other reports were consulted. No build, test, launch, generation, decompile, or canonical source write was performed.

Verdict: the lava-contact and stacked-height source changes are supported. The central flow-vector arithmetic is materially the same. The fluid scan's chunk-area API changes, but the client implementations both make the tested loaded checks pass; server-side implementation differences are outside historical player-movement execution and were not used as a movement witness. Reachable player-state/trajectory witnesses remain source-level and partial; no runtime parity is claimed.

## Paired findings

### A. Lava contact becomes a post-move cached callback flag

- **1.13.2 direct predicate:** `Entity.isInLava()` at `Entity.java:1053–1055` calls `world.containsMaterial(getShape().contract(0.1F, 0.4F, 0.1F), Material.LAVA)` every time. `World.containsMaterial(Box, Material)` at `World.java:1310–1332` floors each contracted minimum, ceils each maximum, then checks block material in its nested x/y/z loops. This is a cell/material test, not fluid-shape clipping. Its cell range is narrower than the entity shape in X/Z by 0.1 and in Y by 0.4 before floor/ceil.
- **1.14.4 cached predicate and producer:** `Entity.isInLava()` at `Entity.java:1058–1060` returns `f_01064147`. `Entity.move(MoverType, Vec3d)` at `Entity.java:540–548` clears that flag immediately before `checkBlockCollisions()`. The latter scans the post-move box inset by 0.001 at `Entity.java:797–826`, guarded by `world.isAreaLoaded(min,max)` at `:805`; for each intersected cell it calls `BlockState.onEntityCollision(...)` before `Entity.onBlockCollision(...)` at `:810–814`. `LiquidBlock.onEntityCollision` at `LiquidBlock.java:168–172` sets the flag only when that block's fluid is tagged LAVA. The setter is `Entity.m_43101496()` at `Entity.java:1054–1056`.
- **Consumer/order closure:** Both versions' `Entity.baseTick()` run `m_03231680()` (water-state refresh), then fire-state handling, then lava damage via `isInLava()`; old `Entity.java:394–415`, new `:357–378`. The movement consumer `LivingEntity.moveRelative` gates the land/fall-flying branch with `!isInWater()` and `!isInLava()` (old `LivingEntity.java:1478–1488`; new `:1786–1797`). The jump phase also reads `isInLava()` before travel (old `LivingEntity.java:1903–1914`; new `:2205–2215`, with source review's checked exact lines `:2207–2214`). Thus 1.13.2 queries the shape at each consumer call; 1.14.4 consumers read the flag written by the prior completed move until the next `move` clears and re-populates it from the post-move callback scan. The new callback is not run by the old `LiquidBlock`; old liquid blocks have no entity-collision override in the inspected file.
- **Predicate delta and witness limit:** The old predicate tests block material from a deliberately contracted box; the new callback tests lava-tagged cells selected by a much smaller inset of the post-move box and stores the result. This supports the surfaced broader-cell-selection/timing claim, while “only the extra 0.001 margin” is not supported. Ordinary player motion across a lava cell boundary can reach different before/after query timing; exact movement start state, first-tick/spawn setup, and a full player-state witness were not closed here. A callback is also skipped whenever the post-move box's area is not loaded, leaving the reset false unless a scanned callback re-sets it. No numeric trajectory is asserted.

### B. Body-fluid contact and stacked height

- **Body-contact scan:** Both versions' `Entity.m_69693160(Tag<Fluid>)` contract `getShape()` by `0.001`, derive floor/ceil cell bounds, require an area-loaded check, and scan cells with strict upper-exclusive integer loops (`Entity.java:2509–2571` old; `:2563–2622` new). For a matching fluid they compare the fluid surface `q + height` to `box.minY` with `>=`, track max immersion depth, and, if `hasLiquidCollision()` is true, sum flow vectors for qualifying cells. The per-cell order is x, y, z. It averages by contributor count, normalizes for non-players, and adds a `0.014` flow impulse. These operations/order are equivalent in the inspected method apart from the loaded-area API and the height query below.
- **Stacked predicate:** Old `FlowingFluid.getHeight(FluidState)` at `FlowingFluid.java:447–450` returns `state.getLevel()/9.0F`. New context-aware `getHeight(state, world, pos)` at `:447–449` returns `1.0F` when the same fluid type occupies `pos.up()` (`:442–444`), otherwise the raw level height (`m_78356736`, `:451–454`). New body contact consumes the world/position overload at `Entity.java:2586–2591`; old uses context-free `fluidState.getHeight()` at `:2532–2537`. The stacked full-height shortcut therefore can change contact only where the entity's contracted lower face lies above the unstacked surface and at/below the cell top. For level-8 fluid, this is the upper one-ninth of that cell; lower-level stacked fluid expands the interval.
- **Eye predicate:** Old `Entity.isSubmergedIn(tag)` at `Entity.java:1042–1051` checks current eye block, matching tag, and strict `eyeY < blockY + (rawHeight + 0.11111111F)`. New delegates to `m_69330161(tag,false)` (`Entity.java:1035–1052`), which applies the same strict threshold with context-aware height. Therefore a level-8 cell without a same-fluid block above does not create a broad eye-state delta: `8/9 + 0.11111111` is essentially one block, leaving no ordinary interior interval. A lower-level flowing cell stacked with same fluid above can create a nonempty eye interval where old returns false and new true. `m_61708540()` updates cached `submergedInWater`; `m_03231680()` calls that after `checkWaterState()` and before `updateSwimming()` (new `Entity.java:942–953`; old `:947–959`). Direct drowning logic also calls `isSubmergedIn(WATER)` (`LivingEntity.java:266` old; `:301` new). No particular player eye placement/state witness was completed.

### C. Flow vectors and adjacent travel producer/consumer reads

- `FlowingFluid.getFlow` is structurally the same horizontal-neighbor gradient and falling-wall response in both endpoints (`FlowingFluid.java:54–99` old; `:54–100` new). New uses raw-height accessor `m_10879879()` for the current/neighbor states where old uses `getHeight()`; that is the level-derived height, not the new world-context stacked overload. Neighbor direction order, blocked-down-neighbor fallback, `0.8888889F` term, falling-fluid downward bias, and normalization are unchanged in these bodies. The body-fluid scan is its movement-side producer and applies the same `0.4` depth scale, averaging, non-player normalization, then `0.014` impulse. No complete fluid-state/data producer inventory was attempted.
- In ordinary water travel, both paths call `move`, then damp velocity (`x/z` by friction and Y by `0.8F`), then apply gravity and horizontal-collision step-up. Old checks the *post-damping* `velocityY <= 0` in the gravity snap branch (`LivingEntity.java:1639–1653`). The new path caches `bl = current velocityY <= 0` at `LivingEntity.java:1786–1792`, before travel, and tests `bl` after move/damping at `:1911–1921`. This is the surfaced adjacent water-threshold path: if water steering/collision crosses the sign within that call, the gate may diverge. This report verifies the dependency/order only; no concrete trajectory is closed.
- The contact flag's use is not an isolated predicate: new lava state is refreshed after each `move` callback, whereas the water body/submerged state refresh is in `baseTick`; this matters to same-tick travel. This source trace does not enumerate every block callback or every external player position/velocity producer.

## Loaded-area and query closure

- Old body-fluid scan calls `world.isAreaLoaded(i,k,m,j,l,n,true)` (`Entity.java:2517`); old `WorldView.isAreaLoaded(..., allowEmpty)` checks every covered X/Z chunk with `isChunkLoaded(x,z,allowEmpty)` (`WorldView.java:308–327`). Old `ClientWorld.isChunkLoaded(..., allowEmpty)` returns `allowEmpty || getChunkSource().getChunk(..., true, false) != null` (`ClientWorld.java:112–114`); since the caller passes true, the client fluid scan gate passes, including empty chunks.
- New body-fluid scan calls `world.isAreaLoaded(i,k,m,j,l,n)` (`Entity.java:2571`); new `WorldView` checks each covered X/Z chunk with no `allowEmpty` argument (`WorldView.java:235–254`), and `WorldAccess.isChunkLoaded` delegates to `ChunkSource.isChunkLoaded` (`WorldAccess.java:53–56`), whose base implementation asks for a `FULL_CHUNK` without loading (`ChunkSource.java:30–32`). New `ClientWorld.isChunkLoaded` returns true (`ClientWorld.java:221–224`), so this gate is also true for the client-side movement scan. Server implementation/eligibility is outside this player-movement closure.
- Lava direct query (`World.containsMaterial`) has no area-loaded precheck in either endpoint. Old loops over `getBlockState` (`World.java:1310–1332`); new streams the same floored/ceiled integer region and calls the same block-state/material predicate (`World.java:711–720`). Evaluation mechanics differ (nested short-circuit loops vs `streamRegion().anyMatch`), but no distinct cell-set/material condition was found. Chunk-loading consequences of arbitrary server-side direct queries were not treated as a client witness.
- Post-move block callbacks use the same `Entity.checkBlockCollisions` method body in both endpoints (hash below): 0.001 inset, area-loaded guard, inclusive x/y/z iteration, block callback followed by entity callback. Therefore the lava change is not from an altered callback dispatch loop; it is the new reset/flag writer plus the new LiquidBlock override. The queried fluid contact area gate and post-move block collision gate are separate paths.

## Coverage ledger

- **Examined:** lava query, flag writer/reset and callback order; current-position/body fluid contact scan; eye/submerged-water predicate; context-aware stacked height producer; fluid-gradient flow vector and entity-side accumulation; entity travel's water/lava reads and the surfaced cached water gravity sign; area-loaded call chains and client-side implementations.
- **Partial:** ordinary-player numeric witness for lava entry/exit or stacked height; state/position setup timing, fluid-flow field producers and all other block callbacks; server-side loaded-chunk implementation effects (not movement-eligible); whether resulting float/state differences alter an exact player trajectory.
- **Unexamined:** full input/state/data packet provenance, all direct external teleport/velocity/explosion/piston causes, complete fluid spread/state production, all historical block collision callbacks, other pair candidates and intermediate-release cutover. No pair freeze or implementation decision is supported by this closure.
