## Ordered coverage

1. **Client authoritative player position packet.** Compared `ClientPlayNetworkHandler.handlePlayerMove(PlayerMoveS2CPacket)` (1.12.2 lines 578–612; 1.13.2 lines 621–655). The method bodies are text-identical: non-relative axes clear that velocity component; relative axes add the local player coordinate; relative rotations add local rotation; `updatePositionAndAngles` then the teleport ack and position/angle response packet follow in the same order. No difference found.
2. **Explosion and velocity packets.** Compared `handleExplosion` (1.12.2 lines 928–936; 1.13.2 lines 968–976) and `handleEntityVelocity` (1.12.2 lines 464–470; 1.13.2 lines 507–513); method bodies are text-identical. Explosion handling runs `damageBlocks(true)` then adds each packet component to local player velocity. Entity velocity handling resolves the entity ID and calls `lerpVelocity` with each integer component divided by `8000.0`. The server's `ServerWorld` explosion packet creation is the same player-specific construction at 1.12.2 lines 932–940 and 1.13.2 lines 831–839.
3. **Server position correction producer.** Compared `ServerPlayNetworkHandler.teleport(..., relativeArgs)` (1.12.2 lines 538–559; 1.13.2 lines 801–814). The server representation changed: 1.12.2 builds the authoritative target by adding the current coordinates for relative axes and sends the unadjusted tuple; 1.13.2 stores and applies the absolute target, then subtracts current coordinates/angles for relative fields in the packet. The paired client handler is unchanged and reconstructs the same requested absolute target from either representation. No local-client response delta found in this protocol rewrite.
4. **Velocity packet production and damage knockback.** Compared `TrackedEntity` velocity update / `sendPacket` / `sendPacketToAll` paths (both releases lines 217–299), the player-attack direct velocity packet path in `PlayerEntity` (1.12.2 lines 1059–1064; 1.13.2 lines 1097–1102), and `LivingEntity.applyKnockback` (1.12.2 lines 971–987; 1.13.2 lines 1011–1027). Knockback arithmetic and the direct packet to a player target follow the same order. 1.13.2 adds `entity.velocityDirty` to the *tracker broadcast* condition; that uses `sendPacket`, which iterates only the other tracked players. The unchanged `sendPacketToAll` adds the owning `ServerPlayerEntity` for the `damaged` path. Thus the tracked-only change does not alter the local player's packet response. Damage calculation is not assessed here.
5. **Login/respawn/world replacement.** Compared `ClientPlayNetworkHandler.handleLogin` (1.12.2 lines 286–305; 1.13.2 lines 316–340), `handlePlayerRespawn` (1.12.2 lines 905–925; 1.13.2 lines 944–965), and `Minecraft.respawnPlayer` (1.12.2 lines 1965–1998; 1.13.2 lines 1454–1487). The world replacement gate/order, scoreboard carry, player replacement, synced-data copy, `resetPos`, entity registration, network ID restoration, and interaction-manager adjustment are preserved. Dimension representation changes from integer ID to `DimensionType`; the recipe-book implementation also changes. No position/velocity response difference found in these local transition routines.
6. **World-transfer position generation.** Compared `PlayerManager.changeDimension(Entity, ...)` (1.12.2 lines 514–567; 1.13.2 lines 521–574). The Nether/Overworld scale factors and world-border clamps, End/forced-spawn selection, angle reset, integer coordinate clamp, portal-forcer call, and position/world update order are preserved; only integer dimension IDs become `DimensionType` comparisons. The corresponding `PlayerManager.changeDimension(ServerPlayerEntity, ...)` sends respawn, performs the transfer, then sends the absolute-position correction and world data in the same order (1.12.2 lines 487–512; 1.13.2 lines 494–519).
7. **Cross-world spectate response.** Compared `ServerPlayNetworkHandler.handlePlayerSpectate` (1.12.2 lines 672–722; 1.13.2 lines 926–942), called by the player's spectate packet. Both require spectator mode and a found target. In 1.12.2 the cross-world branch sends `PlayerRespawnS2CPacket`, moves the player to the target's exact position and angles, moves the player between worlds, then calls `teleport` to emit the position correction. 1.13.2 routes the same target world/position/angles through `ServerPlayerEntity.teleport(ServerWorld, ...)` (lines 1228–1258), which preserves that respawn → set target transform/world → position correction order. The client respawn method recreates at spawn before the subsequent correction in both versions. No final local position/velocity response difference found for this path.
8. **Status/effect response.** Compared packet add/remove handlers and `LivingEntity.addStatusEffect` / effect registration. The packet add handler applies an effect to a matching `LivingEntity` in both versions; the removal handler body is text-identical. The local player's server effect application sends `EntityStatusEffectS2CPacket` from `ServerPlayerEntity.addStatusEffect` (1.12.2 lines 969–978; 1.13.2 lines 989–998), which reaches this client handler. The 1.13.2 `StatusEffect` registry adds Slow Falling (registration line 286; `StatusEffects.SLOW_FALLING` line 36), and `LivingEntity.moveRelative` adds a player-reachable branch (lines 1478–1484): when locally controlled or movement-authoritative and `velocityY <= 0.0`, presence of Slow Falling changes the gravity operand from `0.08` to `0.01` and clears `fallDistance`; later gravity subtraction uses that operand only when gravity is enabled. This is a newer-side effect addition; detailed source finding draft: `findings/slow-falling-gravity-response.md`.
9. **Item-use response.** Searched item sources for direct player position/velocity setters. No 1.12.2 item writes player motion in this path. 1.13.2 adds `TridentItem.stopUsing` (lines 56–109); after at least 10 use ticks and the Riptide/water-or-rain gate, a Riptide level above zero computes and adds a look-directed velocity. If the player is on ground, it additionally performs `move(MoverType.SELF, 0.0, 1.1999999F, 0.0)`. A local interaction path calls `player.stopUsingItem()` from `ClientPlayerInteractionManager` (1.13.2 line 411); `LivingEntity.stopUsingItem` dispatches to the active stack (lines 2288–2291), whose `ItemStack.stopUsing` delegates to the item's `stopUsing`. This is a newer-side item addition; detailed source finding draft: `findings/riptide-self-launch.md`.
10. **Piston entity response.** Compared the `MovingBlockEntity` push call sites (1.12.2 lines 143–164 and 231–243; 1.13.2 lines 127–148 and 219–231) and the `Entity.move(MoverType.PISTON, ...)` accumulator branch (1.12.2 lines 467–500; 1.13.2 lines 480–512). Player pushes use the same overlap-derived distance, `+0.01`, axis offset, and per-tick clamp / epsilon return order. The secondary push volume changes from `Block.FULL_BLOCK_SHAPE` to `VoxelShapes.block().bounds()`; 1.12.2 defines the former as `(0,0,0)-(1,1,1)`, and 1.13.2 defines `VoxelShapes.block()` as the full 1×1×1 unit voxel. This spelling change yields the same bounding box for this piston response. No difference found.

## Findings and dispositions

- **Newer-side additions, no backport delta for the older profile:** Slow Falling motion response and Riptide self-launch. Each is reachable in 1.13.2 and absent as a feature in 1.12.2. Both have draft finding files. A selected 1.13.2 client already executes these native operations; a 1.12.2 profile cannot obtain these 1.13-only inputs through vanilla. The master should decide how these endpoint additions fit the pair's compatibility scope.
- **Compared with no local response difference:** PlayerMove correction, explosion impulse, entity velocity packet application, login/respawn reset sequence, portal and spectate world-transfer position paths, damage knockback packet routing, and piston entity push.

## Gaps and next action

- This assignment did not cover the full pair. It did not audit the complete player tick, all shape/collision providers, every event callback, or independently retrace the parent pair's other source lanes.
- The status-effect movement branch is identified only where packet-applied state reaches an explicit local-player gravity write; the full effect/tick update graph belongs to the assigned movement/effects coverage owner.
- Master action: reconcile the two newer-side additions against the central source-only projection and other lanes; obtain an independent audit of this bounded inventory before any source acceptance. Do not treat this report as full-pair closure.
