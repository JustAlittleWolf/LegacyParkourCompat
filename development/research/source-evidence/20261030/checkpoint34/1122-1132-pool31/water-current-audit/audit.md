# Independent audit: water contact and current query

## Verdict

The draft is substantially supported by the assigned canonical sources, and the cited file hashes and mapping identities match. Before using it as a frozen source finding, narrow the movement claim in two places: the query box changed along with the aggregation, and 1.13.2 scales each contribution by the running maximum immersion depth, not necessarily that contributor's own depth. The single-cell shallow-current precondition is valid when the same fluid cell is included by both queries and its flow is nonzero. The draft does not establish a general trajectory or parity result.

## Source trace and claims

- **1.12.2 entry and contact bounds:** `Entity.tick` calls `checkWaterCollisions` (`Entity.java:382`). That method calls `World.applyLiquidDrag` with `getShape().grown(0.0, -0.4F, 0.0).contract(0.001)` (`Entity.java:948-963`). It also has the boat branch and updates `inWater` from the drag call's contact result.
- **1.12.2 cell test and impulse:** `World.applyLiquidDrag` derives integer scan bounds with floor/ceil, checks area loading, scans cells, requires `blockState.getMaterial() == material`, and checks `ceil(bounds.maxY) >= p + 1 - LiquidBlock.getHeightLoss(level)` before adding that block's material drag (`World.java:1579-1621`). After scanning, it applies current only if the sum is nonzero and `entity.hasLiquidCollision()`, normalizes the accumulated vector, then adds `0.014` times each component. `LiquidBlock.getFlow` produces a normalized per-block direction and `applyMaterialDrag` adds it to the sum (`LiquidBlock.java:139-185`). The old surface check has no separate `surface >= bounds.minY` test; candidate integer cells still come from the box scan.
- **1.13.2 entry and contact bounds:** `Entity.tick` calls the obfuscated private wrapper, which calls `checkWaterState` (`Entity.java:394, 947-948`). `checkWaterState` uses the full shape contracted by `0.001` through `m_69693160(FluidTags.WATER)` (`Entity.java:961-976`). The query scans loaded candidate cells, filters by the supplied fluid tag, and requires `q + fluidState.getHeight() >= box.minY` (`Entity.java:2509-2571`). Thus the new query changes the vertical scan interval and adds an explicit lower-surface test as well as changing the aggregation.
- **1.13.2 provider chain:** `World.getFluidState` handles out-of-height positions as empty and delegates to the chunk (`World.java:529-535`); `WorldChunk` selects its section (`WorldChunk.java:380-398`); `WorldChunkSection` reads the stored `BlockState` and delegates through `BlockState` to `Block.getFluidState` (`WorldChunkSection.java:34-35`, `BlockState.java:313-314`, `Block.java:678-681`). `LiquidBlock.getFluidState` indexes its source/flowing state list using the block `LEVEL` capped at 8 (`LiquidBlock.java:68-71`). `FluidState.getHeight/getFlow` delegate to the fluid (`FluidState.java:29-30, 67-69`); `FlowingFluid.getHeight` returns level divided by `9.0F`, and `getFlow` derives a vector from neighboring fluid heights and normalizes it (`FlowingFluid.java:54-98, 443-450`).
- **1.13.2 aggregation:** `m_69693160` captures `hasLiquidCollision`; for each matching tagged state whose surface reaches the box bottom, it updates `d = max(surface - box.minY, d)`. If the liquid-collision gate is true, it gets that state's flow, scales it by the current `d` when `d < 0.4`, sums it, and increments `o`. A nonzero sum is divided by `o` when positive. It is normalized only when the entity is not a `PlayerEntity`, then multiplied by `0.014` and added to velocity. This confirms the player-specific normalization exception and the draft's averaged, unnormalized player result, with the gate qualification below.
- **Player/client reachability and gate:** In both releases `PlayerEntity.tick` invokes `super.tick`; both `ClientPlayerEntity` classes extend `PlayerEntity` and inherit that tick method. The base entity tick therefore reaches the water check for the local-player class. Both `PlayerEntity.hasLiquidCollision` implementations return `!abilities.flying`; for a non-flying player the current gate is true, while a flying player receives no current impulse from these queries. The source-level result is a reachable local-player path, not a runtime parity check.

## Required draft corrections

1. **State the bounds change as part of the comparison.** The older contact/current scan uses a box shrunk vertically by `0.4F`; the newer query uses the full player box with only `0.001` contraction. Candidate fluid/block cells can therefore differ. Qualify the normalized-versus-scaled impulse comparison with the condition that the same relevant cell(s) are visited by both queries and both resulting current vectors are nonzero. Otherwise a shallow cell can be counted only by the new query, or omitted by the old query, so “smaller” is not a general statement about every shallow-water placement.
2. **Describe the exact depth arithmetic.** In 1.13.2 `d` is a running maximum over matching cells visited so far and is updated before scaling the current cell's flow. It is not always that cell's own depth. For a single contributing cell, the claim reduces to the cell depth and is exact; for multiple unequal surfaces, contribution scaling can depend on scan order. Say this explicitly or bound the statement to one contributing cell.
3. **Make the impulse gate explicit.** The comparison concerns a non-flying player (`hasLiquidCollision() == true`) and a nonzero result. The code still computes contact state for a flying player, but does not gather/apply current for that player.

## Concrete shallow-current precondition

The proposed single-cell witness is source-valid. Let the sole fluid cell under the player's horizontal box have block Y coordinate `p`, water surface `p + 8/9`, and let the player's box bottom be `p + 0.55`. In 1.12.2, a water block with level 0 has surface `p + 1 - (0 + 1)/9 = p + 8/9`; the shrunken-box lower bound is `p + 0.951`, whose floor still includes cell `p`. Its upper scan bound includes the cell, and `ceil(bounds.maxY) >= p + 8/9`, so the old query can add its flow. In 1.13.2 the level-0 liquid block maps to its source fluid state, whose height is `8/9`; the same box includes it and its immersion depth is `8/9 - 0.55 = 0.338888… < 0.4`.

Give that cell one same-fluid neighbor at the next lower surface level and keep the player box within the central cell horizontally, with no other fluid cells inside it. The old `LiquidBlock.getFlow` level-difference sum and the new `FlowingFluid.getFlow` height-difference sum are both nonzero for that arrangement. For a non-flying player, the older one-cell sum is normalized to magnitude 1; the newer one-cell flow is scaled by `d`, and the player path skips final normalization, yielding magnitude `d` before the same `0.014` component increment. This demonstrates a concrete query-level shallow case; it does not prove a complete in-game trajectory or a general placement-independent effect.
