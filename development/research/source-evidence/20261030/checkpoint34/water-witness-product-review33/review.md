# Product reconciliation: accepted shallow-water current witness

## Verdict

**No product delta is needed for the accepted single-cell witness.** The current client implementation already routes a supported 1.12-profile witness through the old contact geometry, old water-level eligibility, old per-cell flow and old normalized non-flying impulse. For the matching 1.13.2 profile, those legacy hooks do not apply, leaving its native tagged-fluid query and player-specific depth-scaled aggregation active. This is source-path reconciliation only; no runtime parity claim is made.

The disposition is deliberately limited to the independent WATER witness: a non-flying, nonswimming player with ordinary fluid features disabled, a single level-0 water cell at `y=p` with surface `p+8/9`, player box bottom `p+0.549` (contracted 1.13.2 bottom `p+0.55`), and a nonzero current. Choose the horizontal box wholly inside that central cell and arrange one horizontal neighbor at water level 1, the other three horizontal neighbors as air, and the below states of those air neighbors as air. Choose an interior height such as `p=64`. There are no other water cells in either query. This concrete provider arrangement satisfies the accepted witness and every provider input is in the current legacy provider's supported set.

## Accepted evidence boundary

The accepted inputs reviewed here are the immutable 1.12.2-to-1.13.2 water comparison and its independent correction (`.native-source/20261030/1122-1132-pool31/water-current-audit/audit.md`, SHA-256 `8fb1d972e480c92f07f3f06bc65bec2e99233a55d41d860af41ebab2d6ef3eed`; `collision-contracts/correction-supplement-2.md`) plus the separate exact alias closure for 1.12, 1.12.1 and 1.12.2 (`old-112-alias-closure/report.md`, corrected digest note in `old-112-alias-closure/correction-supplement.md`). The water audit narrows the comparison to a common contributing cell, nonzero flow, non-flying player and one contributor: the 1.12.2 query shrinks the player box by `0.4F` on Y and normalizes the nonzero aggregate before the `0.014` velocity increment; 1.13.2 scans the almost-full contracted box, scales the sole flow by `d=8/9-0.55=0.338888…`, and skips final normalization for `PlayerEntity`. The alias closure independently establishes that 1.12.2's named contact/current/provider method bodies are also present in 1.12 and 1.12.1. The corrected audit warns that multiple contributors use a running maximum and can be scan-order-dependent; this review does not extend to that case.

## Product path on the witness

- Profile-resolved `WaterBodyContact` is annotated for `V1_12` and returns the historical query box by applying `body.minY - -0.4F` / `body.maxY + -0.4F`, followed by `deflate(0.001)` (`src/client/java/me/wolfii/legacyparkourcompat/change/v1_12/WaterBodyContact.java:15-25`). Its surface predicate is the historical `cellY + 1 - (level+1)/9.0F` compared with the scan's exclusive upper Y. The level-0 cell passes.
- `WaterCurrent` is likewise annotated for `V1_12`. It sums the supplied per-cell flow and, for a nonzero sum and `flying == false`, normalizes then scales each component by `0.014` (`src/client/java/me/wolfii/legacyparkourcompat/change/v1_12/WaterCurrent.java:34-44`). The matching 1.12 profile therefore selects these old operations; the 1.13.2 profile has no later-emulating water-current override in this product path and keeps native behavior.
- `WaterScan.scan` uses the resolved body probe as `selected`. With no `V1_12` flow-bound override, it falls back to `selected` as `flowBox`, computes the half-open scan bounds from it and resolves current because both the current hook and selected body probe exist (`src/client/java/me/wolfii/legacyparkourcompat/mechanic/water/WaterScan.java:52-71`). This preserves the old shrunken-Y interval for this profile. Its flow membership uses the same integer-ceiling surface formula (`WaterScan.java:237-248`); at `p=64`, both old and new query loops include the central cell.
- The shared traversal adds only water cells in the flow domain; a level `>=8` would reject the current replacement, but the witness's sole level-0 contributor passes. The provider is called only for that cell (`WaterScan.java:165-185`). It adds the resulting impulse to player velocity before the native contact expression returns (`src/client/java/me/wolfii/legacyparkourcompat/mixin/water/EntityWaterMixin.java:44-67`). The profile lookup is through `MovementRuntime.find`, whose lookup is gated by client-player applicability (`src/client/java/me/wolfii/legacyparkourcompat/mechanic/MovementRuntime.java:208-217`).
- Every finite block-state input needed by this witness is accepted by `WaterCurrent.flow`: central level 0; one horizontal water neighbor level 1 (nonfalling and lower-surface); other horizontal neighbors air; their below states air. `supported` accepts tagged water in a `LiquidBlock` with level `<8`, air, stone, cobblestone, dirt and bedrock, and rejects any other provider state for the bundle (`WaterCurrent.java:55-84, 96-106`). In the listed witness layout, the neighbor difference is nonzero and no unsupported state causes the hook to return empty. The old 1.12 world provider's nonzero one-cell direction normalizes to the same direction; the product's final normalization supplies the accepted magnitude-1 old result before the shared `0.014` factor.

`WaterScan.supportsFeatures` intentionally declines replacement for swimming/visually swimming, sprinting underwater or with eyes in water, Slow Falling and Dolphin's Grace (`WaterScan.java:36-44`). Those are outside this witness's ordinary-feature preconditions. The review does not treat those bounded fallbacks as missing gates, and does not claim that every arbitrary neighboring block/fluid provider state is covered by `WaterCurrent`.

## Reconciliation outcome

For the accepted finite witness, the pre-existing `V1_12` body-contact/current implementation and its thin client dispatch already provide the required operation. No new hook, provider expansion, product/backlog edit, implementation export or code candidate is warranted on this evidence. The prior generic provider-closure concern is resolved only for this bounded witness by choosing explicit accepted neighboring states; it remains a valid limitation for other provider arrangements. No build, tests, source generation, game/runtime launch, network access or changes to product code/history were performed.
