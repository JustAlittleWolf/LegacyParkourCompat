## Additional reachable source paths missed by the surfaced drafts

These are source-confirmed differences discovered during this audit. They need their own focused candidate disposition and collision/input witness review; this audit does not convert them into accepted findings.

1. **Climb boost gate widened.** Old dry travel writes `velocityY = 0.2` after move only when `collidingHorizontally && isClimbing()` (`1.13.2 LivingEntity.java:1575–1578`). New travel uses `(collidingHorizontally || jumping) && isClimbing()` (`1.14.4 LivingEntity.java:1846–1850`). A player pressing jump while climbing can enter the new branch without horizontal collision; this is a reachable gate difference not listed as a draft.
2. **Water gravity threshold caches pre-travel vertical sign.** Old water branch tests `this.velocityY <= 0.0` after movement/damping (`1.13.2 LivingEntity.java:1644–1649`). New method caches `bl = velocityY <= 0.0` before the travel branch (`1.14.4 LivingEntity.java:1788–1792`) and uses that cached value after the move/damping at `:1911–1921`. Water steering/collision can change the sign within the call, so the sign gate can diverge. Trace this with the water-state and movement dependencies.
3. **Dry swimming-pose input slowdown.** New local-player tick passes `isSneakingPose || (isSwimmingPose && !isInWater())` into `KeyboardInput.tick` (`LocalClientPlayerEntity.java:625–631`; `Entity.java:1798–1824`). The keyboard scales axes by 0.3 when this flag or current sneak input is true (`KeyboardInput.java:22–25`). Old keyboard scales only for current sneak input (`1.13.2 KeyboardInput.java:44–49`). A non-spectator player in the swimming fallback pose outside water therefore has slowed input next tick. This is directly reachable through the pose fallback above and not represented by its two pose drafts.
4. **Submerged sprint-forward threshold changes.** Old sprint gates use `movementForward >= 0.8F` (`1.13.2 LocalClientPlayerEntity.java:723–745`). New `m_03985577()` uses `movementForward > 1.0E-5F` only while submerged, retaining the 0.8 threshold otherwise (`1.14.4 LocalClientPlayerEntity.java:961–964`); the sprint-key start gate calls it at `:669–676`. Sneak/item-use-scaled positive input while submerged can satisfy the new threshold and fail the old one. The reports mention a prior overlap but no permitted source-only upstream disposition was available here; retain the pair-level coverage fact for coordinator deduplication.
5. **Resolved movement cutoff in collision move.** Old collision resolution enters for any nonzero requested axis and applies the clipped result (`1.13.2 Entity.java:578–599,676`). New computes the resolved vector but updates shape/position only when `resolved.squaredDistanceToOrigin() > 1.0E-7` (`1.14.4 Entity.java:463–468,656–666`). Thus a nonzero player move clipped to a remaining vector of length at most about `3.1623E-4` is discarded by the new path, while the old path applies any nonzero remainder. This is a reachable near-contact geometry gate requiring query/shape closure and a witness.
6. **Camera-flight simultaneous vertical input arithmetic.** In local camera flight, old code subtracts `flySpeed*3.0F` for sneak and then adds it for jump sequentially (`1.13.2 LocalClientPlayerEntity.java:797–806`). New accumulates the two booleans into integer `j` and performs one vector addition (`1.14.4 LocalClientPlayerEntity.java:728–742`); simultaneous sneak+jump cancels to no operation in the new source. Whether the residual old float operations produce a movement-relevant difference needs a narrow arithmetic/reachability disposition; do not silently treat this as closed by ordinary input coverage.
