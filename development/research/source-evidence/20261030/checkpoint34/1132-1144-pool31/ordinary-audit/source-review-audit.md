## Claims checked

- **Tick ordering:** both `PlayerEntity.tick()` implementations call `super.tick()` before their trailing `updatePlayerPose()` call (1.13.2 `PlayerEntity.java:176–208, 252–255`; 1.14.4 `:207–235, 279–282`). The 1.14.4 call is the final statement of that method. The local-player subclass supplies its input from `mobTick`; it inherits this player tick. The report's pose update is therefore after the inherited tick/movement work, as claimed.
- **1.13.2 dimensions:** `PlayerEntity.updatePlayerPose()` prioritizes fall-flying, sleeping, swimming/spin attack, sneaking, then standing; sneaking selects `0.6F × 1.65F`. If desired width/height differs, it forms a box from the current shape's minimum coordinates and applies `setSize` only if `world.hasNoCollisions(null, box)` succeeds (`PlayerEntity.java:334–360`). It has no smaller-pose retry after a failed target fit. The draft's description is accurate.
- **1.14.4 dimensions and gate:** player dimensions map `Pose.SNEAKING` to dynamic `0.6F × 1.5F` and `Pose.SWIMMING` to dynamic `0.6F × 0.6F` (`PlayerEntity.java:109–118`). `updatePlayerPose()` first tests `m_87715359(Pose.SWIMMING)`; only inside that outer `if` does it choose the desired pose, allow it directly for spectator/riding/fitting cases, otherwise fall back to fitting sneaking or swimming, then set the pose (`PlayerEntity.java:343–370`). `m_87715359` calls `world.hasNoCollisions(this, poseBox)` (`Entity.java:1628–1630`); `m_16672198` centers the requested dimensions on x/z and anchors y at the entity y (`:2300–2305`).
- **Dimension application:** setting the synchronized pose calls `onDataValueChanged` synchronously through `SyncedData.set` (`SyncedData.java:120–127`); the entity callback detects the pose attribute and invokes `m_84943753` (`Entity.java:2239–2242`). That method installs the selected dimensions and rebuilds the shape (`:2245–2266`). Thus the report's pose-to-dimensions dependency is present on the local entity. The shape/collision provider semantics remain open as the report says.
- **Modifier checks:** the inspected attribute aggregation still runs addition, multiply-base using the post-addition value, then multiply-total, before clamping (old `ModifiableEntityAttributeInstance.java:147–164`; new `:141–158`). Status-effect modifier installation removes the prior modifier, adds the scaled `modifier * (amplifier + 1)` with its existing operation, and speed/slowness definitions retain the cited `0.2F` / `-0.15F` total-multiply values (old `StatusEffect.java:178–198, 209–222`; new `:150–170`). These checked claims are supported; the report's external attribute/equipment provenance caveat remains appropriate.
