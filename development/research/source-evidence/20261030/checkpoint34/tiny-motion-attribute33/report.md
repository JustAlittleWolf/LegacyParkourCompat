## Constructive legal attribute path

Both `PlayerEntity.initAttributes` bodies set `generic.movementSpeed` base to `0.1F` (1.12.2 `PlayerEntity.java:153-160`; 1.13.2 `PlayerEntity.java:155-162`). The attribute is ranged with minimum `0.0` (`EntityAttributes.java:19-21` both releases). `ModifiableEntityAttributeInstance.computeValue` adds operation-0 modifiers to the base in `double`, then clamps (`:147-164` both releases).

Vanilla's `SetAttributesFunction.run` accepts a configured attribute, operation and amount provider; it creates an `AttributeModifier` with `amount.getFloat(random)` and stores it on an `ItemStack` (`world/gen/loot/functions/SetAttributesFunction.java:33-45`, same source in both releases). `ItemStack.getAttributeModifiers` reads the modifier from its `AttributeModifiers` NBT (`item/ItemStack.java:720-740` in 1.12.2, `:723-743` in 1.13.2); `EntityAttributes.fromNbt` reads `Amount` with `getDouble` (`entity/living/attribute/EntityAttributes.java:102-112`). On the server, `LivingEntity` removes old equipment modifiers and applies the newly equipped item's modifiers (`LivingEntity.java:445-459` in 1.12.2, `:477-491` in 1.13.2). Movement speed is trackable. `TrackedEntity.sendDataAndAttributes` sends changed attributes to tracking clients and also to the tracked `ServerPlayerEntity` itself (`server/TrackedEntity.java:271-299`); initial tracking sends trackable attributes as well (`:316-334`). The client receives the entity id and double base/modifiers in `EntityAttributesS2CPacket`, resolves the entity, then sets the base and reapplies modifiers in `ClientPlayNetworkHandler` (`:1796-1814` in 1.12.2; `:1940-1958` in 1.13.2). Thus this is reachable client-local player state through the vanilla item/equipment and vanilla attribute-sync path, not a synthetic `Entity.move` argument.

For a constant loot modifier amount `-0.09999995F`, operation 0, and a nonzero UUID, Java float conversion gives `-0.09999994933605194`. Added to the player's exact `0.1F` base (`0.10000000149011612`) in double, it yields `5.21540641784668e-8`, which the movement-speed clamp preserves. `PlayerEntity.getSpeed` casts the attribute value to `float` in both versions (`PlayerEntity.java:1406-1409` in 1.12.2; `:1487-1490` in 1.13.2). This modifier amount is expressible by the vanilla `SetAttributesFunction` float provider and has ordinary nonzero UUIDs; the witness requires an item carrying that configured modifier to be equipped in its designated slot. It does not rely on an invalid negative effective attribute, a jump, residual velocity, or an arbitrary direct call to `move`.

## Reachable per-tick request

Use a non-sprinting, grounded player on ordinary stone, outside water/lava/climbing/fall-flying, with zero horizontal velocity before the tick, forward input `1`, no jump, and yaw `-90` degrees. `LocalClientPlayerEntity.mobTick` ticks input before `LivingEntity.mobTick`; the inherited `<0.003` component clamp precedes local input copying and travel (`LocalClientPlayerEntity.java:698-702`, `:631-640` in 1.12.2; `:702-706`, `:635-640` in 1.13.2; `LivingEntity.java:1781-1847` and `:1852-1926`). The clamp therefore erases prior tiny velocity but does not erase this tick's subsequent acceleration.

Both ordinary grounded `LivingEntity.moveRelative` branches compute acceleration as `getSpeed() * (constant / s^3)`, where `s = slipperiness * 0.91F`, then call `updateVelocity`, then `move(SELF, velocityX, velocityY, velocityZ` (1.12.2 `LivingEntity.java:1478-1496,1514`; 1.13.2 `:1538-1557,1575`). Stone uses ordinary `0.6F` slipperiness; the factor is approximately one. `Entity.updateVelocity` leaves a unit forward input at unit magnitude, rotates the forward component using the sine lookup, and adds it to velocity X (`Entity.java:1049-1065` in 1.12.2; `:1057-1073` in 1.13.2). At yaw `-90`, the indexed sine is exactly `-1`; with the zeroed prior velocity the resulting positive X request is approximately `5.2154e-8` (static float arithmetic: 1.12.2 factor `0.9999998211860657`, request `5.215405352032576e-8`; the 1.13.2 factor is likewise within one float ULP of one). The request is strictly positive, below `1e-7`, and greater than the cited `1e-8` gap.

For the existing conditional geometry witness, use a full-cube stone floor and a full-cube stone wall with the player's leading X face `1e-8` before the wall's X face, while keeping the player's Y/Z intervals overlapping the wall. Both releases' base `Block.getShape` is a full block (`Block.java:307-309` in 1.12.2; `:388-394` in 1.13.2 for shape/collision), and `Blocks.STONE` is present in both registries. This follows the previously audited collision arithmetic and does not claim closure of the audit's complete provider inventory.

## Verdict and boundary

**Reachability established for the bounded witness.** The old `0.003` component cleanup was a false blocker because it runs before newly generated grounded input acceleration. A valid movement-speed equipment modifier can make that acceleration enter the collision operation in `(0, 1e-7)`, and the selected value exceeds the old/new audit's `1e-8` gap. The collision consequence remains the source-arithmetic result already recorded by the bound audit; this report supplies reachability, not a game/TAS parity result or a full-pair freeze.
