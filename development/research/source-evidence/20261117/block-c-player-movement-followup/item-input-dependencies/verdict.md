## Verdict and examined scope

- **Input path and order:** `LocalPlayer.applyInput` (controlled-camera branch) passes `input.getMoveVector()` to `modifyInput`; `ClientInput.getMoveVector` returns the stored vector. Both versions use the same guards and order in `LocalPlayer.modifyInput`: preserve zero input; scale by `0.98F`; if using an item and not a passenger, scale by the used stack's speed multiplier; if moving slowly (crouching or visually crawling), scale by the effective `SNEAKING_SPEED`; then call the same unit-square normalization/clamp path. No cast, arithmetic-order, guard, or helper difference was found. Sources: `client/player/LocalPlayer.java` (`applyInput`, `modifyInput`, `modifyInputSpeedForSquareMovement`, and `itemUseSpeedMultiplier`; 26.1.2 lines 567–568, 692–734; 26.2 corresponding methods) and `client/player/ClientInput.java:13–14` in both.
- **Ordinary use default and explicit item override:** both `UseEffects.DEFAULT` values are `(false, true, 0.2F)`. `USE_EFFECTS` has the same persistent codec and network stream codec; `COMMON_ITEM_COMPONENTS` installs that default, and the ordinary `Item` initializer draws from common components. For an item with no per-item override, active item use therefore uses `0.2F` in both. The vanilla sword property explicitly supplies `new UseEffects(true, false, 1.0F)` in both; this gives the same explicit factor. Sources: `world/item/component/UseEffects.java:9–24`, `core/component/DataComponents.java` (`USE_EFFECTS`, `COMMON_ITEM_COMPONENTS`), and `world/item/Item.java` (default initializer and sword component; 26.1.2 line 542, 26.2 line 543).
- **Component overrides and lookup:** `ItemStack` reads through its `PatchedDataComponentMap`; `get` delegates to the same patch-plus-prototype lookup in both. A stack-specific component value overrides its item prototype value; a removed value suppresses the prototype; `getOrDefault` supplies the same call-site fallback. `LocalPlayer.itemUseSpeedMultiplier` reads `USE_EFFECTS` from the used stack with `UseEffects.DEFAULT` as fallback in both. Thus the comparison’s ordinary no-override case and the explicit sword override have the same precedence and result; arbitrary custom values remain dependent on the supplied stack state. Sources: `core/component/PatchedDataComponentMap.java` (`get`, `set`, `remove`), `core/component/DataComponentPatch.java` (patch/prototype lookup), and `world/item/ItemStack.java` (`getComponents`, `getComponentsPatch`, component reads) in both.
- **Sneaking attribute and enchantment input:** `SNEAKING_SPEED` is syncable, defaults to `0.3`, has `[0.0, 1.0]` bounds, and is included by `Player.createAttributes` in both. `ItemStack.forEachModifier` reads the `ATTRIBUTE_MODIFIERS` component and then enchantment modifiers; the common component default is empty. Swift Sneak adds `LevelBasedValue.perLevel(0.15F)` to `SNEAKING_SPEED` with `ADD_VALUE` in both. For an ordinary unmodified player, the slow-input multiplier is therefore `0.3`; with the same equipment/enchantment state, both versions resolve the same modifier inputs. Sources: `world/entity/ai/attributes/Attributes.java` (26.1.2 lines 79–80; 26.2 lines 92–93), `world/entity/player/Player.java` (`createAttributes`), `world/item/ItemStack.java` (`forEachModifier`), `core/component/DataComponents.java` (`ATTRIBUTE_MODIFIERS`, common default), and `world/item/enchantment/Enchantments.java` (Swift Sneak definition).
- **Server/client synchronization:** the `SNEAKING_SPEED` attribute remains client-syncable. `AttributeMap` queues syncable changed values; `ServerEntity` sends syncable attributes at pairing and sends dirty attribute updates to tracking players and self; `ClientPacketListener.handleUpdateAttributes` applies base values and transient modifiers. The same-state effective value is thus available to the local `getAttributeValue` consumer through the same examined path. `USE_EFFECTS` also keeps its component stream codec and network-synchronized registration in both versions. Sources: `world/entity/ai/attributes/AttributeMap.java`, `server/level/ServerEntity.java` (initial and dirty attribute packets), `client/multiplayer/ClientPacketListener.java` (`handleUpdateAttributes`), and `core/component/DataComponents.java` / `world/item/component/UseEffects.java` in both.

## Bounds and exclusions

This audit covers the ordinary built-in default item state, the cited vanilla sword override, component patch/prototype precedence, the direct Swift Sneak attribute input, and server/client synchronization for the same supplied item/equipment/attribute state. It does not enumerate every vanilla item registration, custom or modded item/component values, data-pack or resource-pack content, arbitrary resource-defined attribute state, or different server-provided values. No unrelated effects, fluids, block/environmental input, or other movement branches were examined. Those limits leave no open dependency for the stated same-state ordinary/default slice.
