# Forward-input sprint threshold comparison

## Scope and result

Compared only the local-player sprint-start and sprint-continuation input decisions for exact source directories `1.13.2/ornithe-feather`, `1.14/yarn`, `1.14.1/yarn`, `1.14.2/yarn`, `1.14.3/yarn`, and `1.14.4/ornithe-feather`. For 1.14.4, the parallel `mojmap` LocalPlayer source was also checked for name-readable confirmation. Water predicates are treated as supplied booleans; fluid detection and movement are outside this comparison.

The forward-input behavior has a cutover at 1.14.2. In 1.13.2, 1.14.0, and 1.14.1, sprint starting requires a forward float impulse `>= 0.8F` in every water state. From 1.14.2, the start gate is conditional: when the selected water predicate is true it accepts `movementForward > 1.0E-5F`; otherwise it requires `movementForward >= 0.8` (a double literal). The continuation rule also changes at 1.14.2 from a `< 0.8F` cutoff to the positive-forward boolean `movementForward > 1.0E-5F`, regardless of water state. 1.14.3 matches 1.14.2. In 1.14.4 the boolean start branch selects on `isSubmergedInWater()` instead of 1.14.2/1.14.3 Yarn's `isInWater()`; continuation remains the boolean test.

The float-versus-double comparison does not change the classification of any representable float input at the ordinary 0.8 boundary: float `0.8F` is approximately `0.800000011920929`, so it passes `>= 0.8`; the preceding float is approximately `0.799999952316284`, so it fails. The new water branch is a real input-classification change: it admits every positive float greater than `1.0E-5F`, including a sprint-key start with sneak-scaled `0.3F`, where old `>= 0.8F` rejected it. Item use itself is excluded by the separate start gates.

## Exact decisions and tick ordering

- **1.13.2 Feather** — `LocalClientPlayerEntity.tickMovement`: snapshots `bl3 = input.movementForward >= 0.8F` before `input.tick()` (698–703), then applies item-use scaling (704–708). Double-tap start uses `(onGround || isSubmergedInWater())`, `!bl3`, and current `movementForward >= 0.8F` (722–735). Sprint-key start uses `(!isInWater() || isSubmergedInWater())` and current `movementForward >= 0.8F` (738–746). Continuing sprint sets `bl6 = movementForward < 0.8F || !bl5`; that feeds cancellation with collision/water gates (748–757). All forward comparisons are inclusive at float `0.8F`.
- **1.14.0 Yarn build.21 and 1.14.1 Yarn build.10** — `ClientPlayerEntity.tickMovement` snapshots `bl3 = input.movementForward >= 0.8F` before `input.tick(...)` and item scaling (614–625). Double-tap and sprint-key starts both use direct `movementForward >= 0.8F` (642–665); continuing uses `movementForward < 0.8F` in `bl7` (667–676). No boolean forward-impulse test appears in these decisions. The ordinary inclusive float threshold is unchanged from 1.13.2.
- **1.14.2 Yarn build.7 and 1.14.3 Yarn build.13** — `ClientPlayerEntity.tickMovement` snapshots `bl3 = method_20623()` before `input.tick(...)` and item scaling; the helper is used in double-tap and sprint-key starts (616–624, 641–665). The helper is `isInWater() ? input.method_20622() : input.movementForward >= 0.8` (949–952). `Input.method_20622()` is strictly `movementForward > 1.0E-5F` (Input.java:22–24). Thus start eligibility is boolean in the selected water state and inclusive numeric threshold otherwise. Continuing sprint uses `!input.method_20622()` in `bl7` (667–675), so any sufficiently positive forward impulse is enough to keep sprinting; this continuation boolean is not conditioned on the water predicate. The 1.14.2 and 1.14.3 source bodies and input helper are identical for these operations.
- **1.14.4 Feather** — `LocalClientPlayerEntity` snapshots the helper before `input.tick(...)`/item scaling; both start paths call it (roughly 618–636, 653–677), and continuation calls the positive-forward boolean (679–688). Its helper at 961–964 is `isSubmergedInWater() ? input.m_49149051() : input.movementForward >= 0.8`; the input helper is `movementForward > 1.0E-5F` (Input.java:23–24). The 1.14.4 Mojmap names the same helper `hasEnoughImpulseToStartSprinting` and the input predicate `hasForwardImpulse` (LocalPlayer.java:960–963 and 678–686), confirming the selected predicate difference without resolving how water state is computed.

Start eligibility retains the neighboring gates. In the compared 1.13.2 source double-tap starts on ground or submerged, while sprint-key start permits either not-in-water or submerged. 1.14.0–1.14.3 use their own `isInWater`/`isInsideWater` predicates at those gates; 1.14.4 uses `isSubmergedInWater`/`isInWater`. Those gates are reported only as decision context. The boolean forward selector itself is explicitly identified above, with no claim equating the different water predicates across releases.

## Threshold witnesses and margins

- Vanilla keyboard input produces forward impulse `+1` for forward only, `-1` for back only, and `0` when neither or both are pressed (1.13.2 Feather `KeyboardInput.java:13–28`; 1.14 Yarn `KeyboardInput.java:18`; 1.14.4 Feather `KeyboardInput.java:18`). Therefore normal forward passes every start and continuation threshold; neutral and back fail the start threshold and fail the new continuation boolean. These ordinary digital witnesses alone do not distinguish the old and new rules.
- Sneak scales forward input by `(float)(impulse * 0.3)` (`1.13.2 KeyboardInput.java:44–49`; 1.14 Yarn `KeyboardInput.java:24`; 1.14.4 Feather `KeyboardInput.java:24`). A forward+sneak value near `0.3F` fails the old and ordinary non-water `>= 0.8` start gate, but passes the boolean branch of sprint-key start when its selected water predicate is true (double-tap start also has its own sneak-key gate). The same positive value continues an existing sprint under the new continuation test, while the old unconditional `forward < 0.8F` continuation predicate treats it as insufficient (other sprint-cancel gates still apply).
- Item use multiplies the forward field by `0.2F` before the start checks in these sources (1.13.2: 704–708; 1.14.0/1.14.1: 621–625; 1.14.2/1.14.3: 620–624; 1.14.4: 631–635), but the actual start gates also require `!isUsingItem`; item-slowed input is therefore not a reachable sprint-start witness. For continuation classification, a positive input near `0.2F` is below the old cutoff but above `1.0E-5F`. The pre-input snapshot used by the double-tap branch is taken before this scaling, so its `bl3` result is based on the prior input state and predicate evaluation order.
- The new boolean comparison is strict: `1.0E-5F` itself does not pass; a float greater than it does. Zero, negative forward, and neutral/back keyboard input do not pass. The ordinary threshold is inclusive. Source changed from float literal `0.8F` through 1.14.1 to double literal `0.8` in 1.14.2 onward, but the nearest float values on either side classify identically at that boundary.

## Coverage boundary

This report closes the bounded comparison of sprint start and continue forward-impulse predicates across the six requested release points. It does not establish intermediate patch introduction dates beyond the checked endpoints, and it does not audit other sprint gates, movement, fluid calculations, or runtime parity. The precise Feather mapping artifact identities for 1.13.2 and 1.14.4 remain unverified because the canonical trees have no provenance manifests.
