# Bed bounce source facts

Scope: the player vertical response when colliding with a bed, including the exact block callback and the inherited player movement path. Exact stable releases inspected: 1.11.2, 1.12, 1.12.1, and 1.12.2. Mapping family: Ornithe Feather for all four.

## Result

Among these four releases, the bed bounce first appears in **1.12**. It is absent from `BedBlock` in 1.11.2, where the inherited `Block.beforeCollision` sets vertical velocity to zero. The 1.12 `BedBlock.beforeCollision` implementation is byte-identical in 1.12.1 and 1.12.2 (same file SHA-256); its formula and guards therefore remain identical through 1.12.2. This bounds the observed cutover to after 1.11.2 and by 1.12.0; no exact intermediate patch boundary is established.

## Operation and reachable player path

- In 1.11.2, `BedBlock` has no `beforeCollision` override. `Block.beforeCollision(World, Entity)` assigns `entity.velocityY = 0.0` (1.11.2 `Block.java:624-626`).
- In 1.12, 1.12.1, and 1.12.2, `BedBlock.beforeCollision(World, Entity)` is at `BedBlock.java:141-150` and reads the entity's sneaking predicate and vertical velocity, not a block-state property or world value. In source order: if sneaking, call `super.beforeCollision` (the base behavior zeroes `velocityY`); otherwise, only if `velocityY < 0.0`, assign `velocityY = -velocityY * 0.66F`; then multiply by `0.8` only when the entity is not a `LivingEntity`. Upward or zero vertical velocity is unchanged in the non-sneaking branch. A player is a `LivingEntity`, so it receives the `0.66F` response and skips the extra `0.8` multiplication. The `world` argument is not consulted by this method, and there is no logical-side guard in this callback.
- In each release, `Entity.move(MoverType, double, double, double)` dispatches the selected collision block's callback from `blockState.getBlock()` only on the non-`noClip` path and under the source guard `o != y`; this call is `Entity.java:724` in 1.11.2 and `Entity.java:727` in 1.12 through 1.12.2. The callback dispatch and bed response contain no `world.isClient` guard. The movement call is in the common inherited `Entity` implementation.
- The client player type hierarchy is `LocalClientPlayerEntity -> ClientPlayerEntity -> PlayerEntity -> LivingEntity -> Entity` in all four inspected versions. `LivingEntity` invokes inherited `this.move(MoverType.SELF, velocityX, velocityY, velocityZ)` in its movement paths. Thus an ordinary local player reaches the common collision callback; `BedBlock` receives the player as the `Entity` argument. This is a source-path claim, not a runtime test.

## Bounds and uncertainty

This is a bounded exact-source comparison of the four named releases and the bed collision response only. It establishes that 1.12 is the first differing release among the four checked and that the source implementation is identical across 1.12, 1.12.1, and 1.12.2. It does not identify an exact intermediate patch introduction between 1.11.2 and 1.12.0, examine other releases, establish runtime parity, or make a product implementation/acceptance claim.
