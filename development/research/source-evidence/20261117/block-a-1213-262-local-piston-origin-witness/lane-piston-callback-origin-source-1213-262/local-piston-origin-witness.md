# Local-player piston callback origin witness: 1.21.3 → 26.2

## Result

A source-backed logical-client witness exists in both exact releases. With the normal client tick unpaused, the loaded LocalPlayer live, unmounted, unfrozen, nonspectating, nonflying and in a clear dry fall, source order permits ordinary travel to move it from `oldPosition()` at the start of its entity tick to a different pre-piston position before the same tick's block-entity pass. A moving ordinary piston can select that LocalPlayer in the same pass when its collision sweep intersects the player's bounding box and its computed push amount is positive. A cobweb in the intervening ordinary fall path is an eligible `entityInside` callback for the 1.21.3 piston no-argument scan, while a short horizontal explicit 26.2 piston span below the web does not contain it.

This is a conditional exact-source witness, not a run/gameplay observation. It separates the input coordinates supplied by the piston caller from the two releases' distinct movement-record and block-traversal algorithms. No nonempty live movement queue is assumed at piston time; the preceding ordinary LocalPlayer block-effects call has cleared it.

## Tick order and local-player reachability

- In 1.21.3, `Minecraft.tick` calls `level.tickEntities()` (Minecraft.java:1731); `ClientLevel.tickEntities()` first iterates entities and only then calls `tickBlockEntities()` (ClientLevel.java:248–258). `tickNonPassenger()` snapshots `setOldPosAndRot()` before `entity.tick()` (269–274). Client connection setup adds `minecraft.player` through `ClientLevel.addEntity()` (ClientPacketListener.java:430–443); the entity-storage ticking callback adds it to `tickingEntities` (ClientLevel.java:965–978). For a live, non-passenger, unfrozen LocalPlayer, the tick loop therefore snapshots the position before its movement and invokes moving block entities after that entity tick.
- In 26.2, `Minecraft.tick()` orders `level.tickEntities()` before `level.tickBlockEntities()` (Minecraft.java:1804–1812). `ClientLevel.tickEntities()` ticks its live, non-passenger, unfrozen `tickingEntities` (450–456); `tickNonPassenger()` likewise calls `setOldPosAndRot()` before `entity.tick()` (467–472). Packet setup adds the local player to the ClientLevel (ClientPacketListener.java:529–538), and the ticking callback adds it to the list (ClientLevel.java:1287–1300). `LocalPlayer.tick()` reaches its normal superclass tick when `connection.hasClientLoaded()` (LocalPlayer.java:226–231).
- Local authority is source-explicit: 1.21.3 LocalPlayer returns `true` from `isEffectiveAi()` (LocalPlayer.java:477–480); its `LivingEntity.travel()` is gated by `isControlledByLocalInstance()` (LivingEntity.java:2178–2188). 26.2 LocalPlayer returns true from `isLocalPlayer()` (LocalPlayer.java:377–380), and Player gates both `canSimulateMovement()` and `isEffectiveAi()` on the local-player result in a client level (Player.java:1280–1296); `LivingEntity.aiStep()` calls `travel()` when both are true (LivingEntity.java:3137–3145).
- In both source versions, the ordinary air-travel path moves using the current delta movement, then subtracts effective gravity and applies vertical air friction: 1.21.3 LivingEntity.java:2191–2213, 2351–2355; 26.2 LivingEntity.java:2468–2496, 2676–2680. Both exact Attributes sources set the gravity attribute default to `0.08` (Attributes.java:41–43 and 55–57). The normal path imposes no per-tick movement-distance cap in `Entity.move` (1.21.3 Entity.java:619–652; 26.2 Entity.java:711–755). Repeated unimpeded falling therefore supplies source-permitted ticks with more than one block of vertical travel; with a sufficiently developed fall, a `2.85`-block request is permitted by these equations.
- A non-slime piston moving-block tick with `progress < 1` sets `newProgress = progress + 0.5` and invokes `moveCollidedEntities` (1.21.3 PistonMovingBlockEntity.java:286–318; 26.2:310–342). That helper requires a nonempty piston collision shape, queries `level.getEntities` in the piston shape's swept movement AABB, filters out only `PushReaction.IGNORE` for the non-slime path, and calls `moveEntityByPiston` when the computed push delta is positive (1.21.3:110–176; 26.2:120–190). `Entity.getPistonPushReaction()` defaults to `NORMAL` in both releases (1.21.3 Entity.java:3184–3186; 26.2 Entity.java:3631–3633). Thus an unmounted live LocalPlayer whose bounding box intersects such a positive normal-piston sweep is eligible; the helper itself has no client-player exclusion.

## Cobweb geometry and callback witness

Take a standing, nonspectator, nonflying LocalPlayer in a loaded clear-air vertical column, with its foot position at `(0.5, 1.05, 0.5)` at the start of the entity tick and an ordinary falling displacement to approximately `(0.5, -1.8, 0.5)` before the block-entity phase. Put a cobweb at block cell `(0, 0, 0)`. The 1.21.3 player dimensions are standing width `0.6` and height `1.8` (`Player.java:136`); in the stated pose, the old box is above the cobweb and the post-fall box ends just below its bottom. The y-span is about `2.85`, while a normal piston push is at most `0.51` block for this tick (`min(delta, deltaProgress) + 0.01`, with `deltaProgress = 0.5`). Place a west-facing moving piston head at block `(1, -2, 0)` at progress `0`, moving west, with its normal base behind it at `(2, -2, 0)`. The long west head shape has a cap x-range `[0, 0.25]` and a west arm x-range `[0.25, 1.25]`; at the stated block position its arm y-range is `[-1.625, -1.375]` and z-range `[0.375, 0.625]` (PistonHeadBlock.java:39–53). The player box at `(0.5, -1.8, 0.5)` is x `[0.2, 0.8]`, y `[-1.8, 0]`, z `[0.2, 0.8]`, At rest, the piston head is just east of the player; it is the westward movement sweep, rather than the resting head shape, that intersects the box. In the first piston tick, `deltaProgress = 0.5`; `PistonMath.getMovementArea` gives the westward swept slice, and the west cap slice is x `[0.5, 1]`, y `[-2, -1]`, z `[0, 1]` (PistonMath.java:7–28). It intersects the player box; `getMovement(WEST)` returns `player.maxX - sweep.minX = 0.8 - 0.5 = 0.3`, so the helper's `min(delta, deltaProgress) + 0.01` sends a positive `0.31`-block push (PistonMovingBlockEntity.java:157–176 / 167–186, 1.21.3 / 26.2). At the post-move x position the player box remains below the web; the push is horizontal and cannot raise its top into the web cell.

The 1.21.3 player callback at the end of its ordinary `LivingEntity.aiStep()` runs after travel when `!level.isClientSide() || isControlledByLocalInstance()` (LivingEntity.java:2774–2776), and `Entity.applyEffectsFromBlocks()` uses `oldPosition()` to current position (Entity.java:736–767). The inside-block scan uses the current deflated player box and `BlockGetter.boxTraverseBlocks(from, to, box)` (Entity.java:1038–1078). `boxTraverseBlocks` switches to path traversal for a span of at least `0.99999` blocks and enumerates cells crossed by the moving box (BlockGetter.java:172–190). Since the ordinary falling span exceeds that threshold, the web cell lies on the swept box path even though the endpoint box is below it.

At the later 1.21.3 piston callback, `moveEntityByPiston()` calls no-argument `applyEffectsFromBlocks()` after `move(PISTON, ...)` (PistonMovingBlockEntity.java:182–186); this again supplies `oldPosition()` and post-piston current position. Thus it again traverses the prior-tick-start-to-post-piston fall span and includes the same cobweb cell. `Blocks.COBWEB` uses `WebBlock` and is registered `.noCollission()` in both releases (1.21.3 Blocks.java:701–712; 26.2 Blocks.java:716–727), but `BlockBehaviour.getEntityInsideCollisionShape()` defaults independently to `Shapes.block()` (1.21.3 BlockBehaviour.java:353–355; 26.2:331–333). The movement callback scan accepts that full inside shape without requiring a solid movement collision. The cobweb's `WebBlock.entityInside()` calls `entity.makeStuckInBlock(...)` (1.21.3 WebBlock.java:25–33; 26.2:27–41); `Player.makeStuckInBlock()` applies it when not flying in both versions (1.21.3 Player.java:1581–1588; 26.2:1514–1521).

In 26.2, ordinary `LivingEntity.aiStep()` has already passed through its gated no-argument effects call before `ClientLevel` reaches block entities (LivingEntity.java:3143–3145). That no-argument method copies the live movement queue to `finalMovementsThisTick`, clears the live queue, then either supplies old-position-to-current when the copy was empty or adds any required tail connector (Entity.java:903–914). The preceding fall movement is processed there; by the later piston call the live queue is empty. The piston helper explicitly samples the LocalPlayer's current position immediately before moving and calls the two-argument overload with that sample and its post-piston position (PistonMovingBlockEntity.java:192–198). The overload builds a two-field `Movement` with no axis-dependent original vector (Entity.java:945–947 and 4120–4127), so its scan uses only the short piston segment.

For the stated geometry, the 26.2 scan's `aabbAtTarget` remains below the cobweb and its horizontal pre/post segment does not intersect the web cell. `BlockGetter.forEachBlockIntersectedBetween()` enumerates from the target box shifted back by that segment through the target box and the blocks crossed by that short segment (BlockGetter.java:175–209). `Entity.checkInsideBlocks()` uses that span and shape test before dispatching `WebBlock.entityInside()` (Entity.java:1308–1375). The piston-produced explicit input therefore skips the cobweb candidate while the 1.21.3 input includes it.

## Delimited mechanisms and conclusion

- Producer coordinates: 1.21.3 piston callback uses old tick sample → post-piston position; 26.2 uses immediately pre-piston sample → post-piston position. Tick order supplies a reachable separation between old sample and pre-piston sample.
- Independent scan/record mechanics: 1.21.3 `boxTraverseBlocks` has its short-span endpoint-box branch and path branch; 26.2 uses `Movement` records, a 16-step traversal budget, axis-dependent splitting for three-argument ordinary records, and a different `forEachBlockIntersectedBetween` scan. The piston explicit two-argument record carries no axis-dependent movement. This witness relies on a long ordinary vertical path and a short horizontal piston segment; it does not assert the two scan algorithms are equivalent.
- Queue state: ordinary LocalPlayer block-effects processing completes before the block-entity pass and clears the live queue in both source paths. No nonempty historical queue is used to establish this witness.
- Conclusion: the exact source flow establishes a reachable `oldPosition() != prePistonPosition` local-player state and a cobweb cell on the 1.21.3 repeated old-origin sweep but outside the short 26.2 piston callback span. The finding concerns callback eligibility/input only; it does not claim observed runtime traces or a net trajectory outcome.
