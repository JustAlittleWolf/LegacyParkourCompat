## Receiver-specific availability gates

In 1.21.11, `Entity.tick` calls `updateInWaterStateAndDoFluidPushing`, which clears fluid heights and calls the water/lava samplers (`Entity.java:504-505,1501-1513`). `updateFluidHeightAndDoFluidPushing` calls `touchingUnloadedChunk()` first, then samples `getBoundingBox().deflate(0.001)` across its integer cells (`Entity.java:3509-3554`). The unloaded check inflates the entity box by 1.0 and passes block-coordinate endpoints to `LevelReader.hasChunksAt` (`Entity.java:3576-3583`). That default enumerates section coordinates and calls virtual `this.hasChunk` (`LevelReader.java:197-211`). For the client LocalPlayer receiver, `ClientLevel.hasChunk()` returns true unconditionally (`ClientLevel.java:391-394`); hence the old gate cannot detect an absent cache slot and does not suppress the local scan.

In 26.1+, base `Entity.tick` updates fluid interaction before the subsequent movement path (`Entity.java:524`; 26.2: 531). The update resets trackers and invokes `EntityFluidInteraction.update` (`Entity.java:1558-1560`; 26.2: 1645-1647). An unmounted entity's interaction box is its bounding box deflated by 0.001 (`Entity.java:4015-4022`). The helper computes inclusive scan cells as `floor(min)` through `ceil(max)-1`, then expands those cells by one in X/Z. `hasFluidAndLoaded` converts that expanded volume to chunk coordinates and directly calls `level.getChunk(chunkX,chunkZ,ChunkStatus.FULL,false)`; any null chunk aborts before the scan (`EntityFluidInteraction.java:32-43,91-118`). `Level.getChunk` delegates to the chunk source (`Level.java:202-210`), `ClientLevel.getChunkSource()` returns the `ClientChunkCache` (`ClientLevel.java:694-696`), and its nonloading lookup returns null for an absent/out-of-range cache entry (`ClientChunkCache.java:69-78`). It neither loads nor requests that neighbor. The fact that 26.x `ClientLevel.hasChunk()` also returns true is bypassed by this direct lookup.

After a successful preflight, the new helper samples every scan cell, tracks matching water/lava height and eyes, and accumulates `FluidState.getFlow` when current is not ignored (`EntityFluidInteraction.java:44-87,122-145`). Entity configures trackers for `FluidTags.WATER` and `FluidTags.LAVA` (`Entity.java:249`). A non-flying Player is pushed by fluid (`Player.java:1673-1675`), so on-foot LocalPlayer collects current. Base `updateFluidInteraction` applies it only when its tracker reports water/lava and the Player is pushed (`Entity.java:1558-1580`). `Tracker.applyCurrentTo` requires a sample count and accumulated-current length squared at least `1.0E-5F`, then adds the scaled impulse (`EntityFluidInteraction.java:171-194`). A failed new preflight happens after reset and before any samples, leaving zero scan-derived height, eye flag, or current. This is a whole-scan skip in each implementation, never a per-side partial skip.

`LocalPlayer.tick` invokes `super.tick()` after the client connection is loaded and sends position when on foot (`LocalPlayer.java:227-245` in 26.1). `LocalPlayer.isLocalPlayer()` is true; `Player.isLocalClientAuthoritative()` delegates to this and the local client player is permitted to simulate (`LocalPlayer.java:378`; `Player.java:1260-1275`). This consequence is on the client-local player path; it does not rely on server-side historical movement.

## Corrected isolated geometry

Let chunk `(0,0)` be in the client cache and chunk `(1,0)` be absent. Place an ordinary on-foot player at `(x=14.9, y=64, z=8.5)`. `EntityType.PLAYER` dimensions are `0.6F x 1.8F` (`EntityType.java:1189-1195`), giving the bounding box:

- X `[14.6,15.2]`; Y `[64,65.8]`; Z `[8.2,8.8]`.
- After deflating by `0.001`, the fluid sampling box is X `[14.601,15.199]`, Y `[64.001,65.799]`, Z `[8.201,8.799]`.
- Both old and new actual scan cells are X `14..15`, Y `64..65`, Z `8` (`floor(min)` through exclusive `ceil(max)` in the old source; inclusive `ceil(max)-1` in the new source).

For 1.21.11, inflating the original box by 1.0 gives X `[13.6,16.2]`, Z `[7.2,9.8]`. `touchingUnloadedChunk` passes X block endpoints 13 and 17 and Z endpoints 7 and 10. The inherited check maps these to chunk X `0..1` and chunk Z `0..0`, but every virtual `ClientLevel.hasChunk` call returns true. The old sampler therefore reads its real scan cells in loaded chunk `(0,0)` despite missing `(1,0)`.

For 26.1+, scan cells X `14..15`, Y `64..65`, Z `8` yield preflight block bounds X `13..16`, Y `64..65`, Z `7..9`. Section/chunk conversion requests chunk X `0..1`, Y section `4`, Z chunk `0`. The direct cache lookup of `(1,0)` is null, so the newer helper skips before sampling either X cell. Z is deliberately centered at 8.5: this preflight does not touch chunk row `z=-1`, isolating the single missing neighbor `(1,0)`.

## Conditional current witness and calculation limits

Use this local loaded arrangement near the player:

- Water source `(14,64,8)` with source amount 8 and no same-type water above. Its own height is `8/9.0F ≈ 0.8888889F`; fluid top is `64 + 8/9.0F ≈ 64.8888889`.
- East cell `(15,64,8)` is nonblocking air, with source water directly below it at `(15,63,8)`, also with own height `8/9.0F`.
- The source's other horizontal neighbors `(13,64,8)`, `(14,64,7)`, `(14,64,9)` are motion-blocking; their fluid states are empty.

The sampled source is in the player's scan cells. No other WATER-tagged cell lies in the scan volume X `14..15`, Y `64..65`, Z `8`, in particular none at Y=65; the listed lower east water is at Y=63, outside that scan. The source cell has no same-type water above, so both providers use height `8/9.0F ≈ 0.8888889F`, making its top Y `≈64.8888889`, above both the old scan minY `64.001` and new interaction-box minY `64.001`. Both source predicates therefore accept it. Old `FluidState.is(FluidTags.WATER)` matches; new fluid type maps to its WATER tracker. In each exact `FlowingFluid.getFlow` implementation, empty east neighbor is passable; the same-fluid source below has own height `8/9.0F`, so its gradient term is `(8/9) - ((8/9) - 0.8888889) = 0.8888889` toward +X. Each other neighbor blocks the below-cell check. The method normalizes the resulting vector to unit +X (`FlowingFluid.java:55-93` on both sides). All those finite cells are in chunk `(0,0)` and preflight's Z range `7..9` remains within chunk row 0.

For this arrangement only, both scan loops visit one contributing fluid cell, and the current scaling branch is false: the old height is approximately `64.8888889 - 64.001 = 0.8878889`; the new height is approximately `64.8888889 - 64 = 0.8888889`; both are at least 0.4. With non-flying Player and starting delta movement zero, the old sampler passes its nonzero-flow check and adds `+0.014` X. If chunk `(1,0)` is present, the new helper's one-sample current accumulator has squared length 1 (above `1.0E-5F`) and also adds `+0.014` X. The old and new heights differ as shown; this example only establishes the same unscaled unit current in this particular setup, not general depth/current equivalence. If `(1,0)` is missing, the new preflight skips the scan after reset and adds no current impulse. This equality is specific to the stated witness; the algorithms' height origins, aggregation and gates differ, so do not generalize current/depth equivalence.

This is a concrete conditional source-level player movement consequence, with explicit finite fluid cells and a single missing chunk. It is not runtime confirmation, a demonstrated trajectory, or a claim that every fluid configuration changes movement.
