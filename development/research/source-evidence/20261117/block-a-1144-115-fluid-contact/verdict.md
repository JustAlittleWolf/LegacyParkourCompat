## Per-operation verdicts

### 1. Body-water current/contact updater and order — NO DIFFERENCE

`Entity.updateWaterState` orders body contact, eye immersion and swimming identically in both versions; `baseTick` calls it after sprint-state update. `updateInWaterState` makes the same boat check, water query, entry-splash gate, fall-distance reset, latch write and fire clear. `Entity.checkAndHandleWater` uses the same deflated AABB, floor/ceil bounds, exclusive-upper-bound loops, loaded-area gate, maximum surface depth, per-sample flow scaling, sample count/average, Player normalization exemption, `0.014` velocity addition, and water-height/contact writes. The compared `FlowingFluid.java` has the identical full SHA-256 in both trees (`e8a395552e53f33bcb5648325615d31bc1796ce2a8aeb501bdda3127622dccdf`); the fluid-state delegation is source-equivalent. `Player.isPushedByWater` returns `!abilities.flying` on both sides.

The base-tick update precedes the living jump/travel phase in both versions. The post-move `LivingEntity.checkFallDamage` refreshes water contact only while not already latched in both releases, so a move that first enters water can add current after branch selection and affect the next tick in the same order. `LocalPlayer.tick` has the same chunk-admission check before `super.tick`; only field access was rewritten to getters. References: 1.14.4 `Entity.java` 341–364, 960–994, 2588–2647; `LivingEntity.java` 237–241 and 2217–2224; `LocalPlayer.java` 178–181. 1.15 `Entity.java` 348–379, 943–977, 2593–2652; `LivingEntity.java` 244–248 and 2282–2288; `LocalPlayer.java` 179–181.

### 2. Already-latched lava travel, input/current predicate and vertical response — NO DIFFERENCE

For the assigned already-latched slice, ordinary local-player travel uses the same `isInLava()` branch gate (with the same flying-player exception). The preceding input damping remains `xxa *= 0.98F; zza *= 0.98F`. The lava branch performs `moveRelative(0.02F, input)`, moves by current velocity, scales resulting velocity by `0.5`, and conditionally adds `-d / 4.0` gravity, with the same slow-falling gate and constants. The horizontal-collision escape test uses the same translated-box clearance expression and sets vertical velocity to `0.3F` only when clear. The jump phase has the same water-height/jumping gate, checks the existing lava latch, and calls tag-agnostic `jumpInLiquid`; that method adds `0.04F` vertically in both versions. The excluded earlier latch producer is not adjudicated here.

References: 1.14.4 `LivingEntity.java` 1774–1776, 1782–1792, 1864–1876, 2200–2211 and 2217–2224; 1.15 `LivingEntity.java` 1823–1825, 1831–1841, 1913–1925, 2265–2276 and 2282–2288. Changes from direct coordinate fields to getters do not change the examined operation.

### 3. Fluid-exit clearance and loaded area/cache gates — NO DIFFERENCE for the LocalPlayer client path

`Entity.isFree` still translates the current player box and requires `noCollision(entity, box) && !containsAnyLiquid(box)`. `containsAnyLiquid` performs the same floor-minimum/ceil-maximum, exclusive-upper-bound scan and tests nonempty fluid state without its own chunk guard. The default collision query still accepts only empty collision shapes; the same block-collision enumeration and `false` chunk-load request are used. The 1.14.4 default is in `LevelReader`; in 1.15 it moved to `CollisionGetter` and `LevelReader.getChunkForCollisions` now supplies `ChunkStatus.EMPTY,false`.

There is a source-level requested-status change: 1.14.4 `Level.statusForCollisions()` overrides the old default with `ChunkStatus.FULL`, used by its collision iterator. For this assigned client path that does not change results. In both releases the client `ClientChunkCache.getChunk(i,j,status,false)` ignores the `ChunkStatus` argument, returns the same cached valid chunk when present, and otherwise returns `null` (the empty-chunk fallback is selected only when the boolean is `true`). The legacy collision path and the new `getChunkForCollisions` path both pass `false`. `MultiPlayerLevel.hasChunk` (1.14.4) and `ClientLevel.hasChunk` (1.15) both return `true`, so the `hasChunksAt`/eye-chunk/LocalPlayer tick predicates have the same client behavior; `hasChunksAt` retains the same vertical `[0,256)` bound checks. Thus the FULL-versus-EMPTY status difference does not establish a reachable LocalPlayer clearance or loaded-area movement change. No server behavior is inferred.

## Scope boundary

These are three bounded, independently audited operation slices only. All three are **NO DIFFERENCE** for the exact 1.14.4 → 1.15 Mojmap comparison. The FULL-versus-EMPTY requested collision status is a source-level API difference but is neutralized by the exact client cache method for this LocalPlayer path. The result does not claim complete pair coverage, close unrelated dependencies, inspect the excluded lava-latch introduction, establish any intermediate release boundary, or prove runtime parity.
