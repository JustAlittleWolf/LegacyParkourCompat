# 1.14.2 → 1.14.4 portal passenger dismount slice

## Outcome

No independent movement difference is supported by this bounded comparison. The dismount position search and server correction flow keep the same explicit gates and operation order in the inspected releases. The Nether portal callback also keeps the same passenger/vehicle exclusion; the names differ with the mappings. This records a bounded source result, not full-pair coverage or an independent audit.

## Dismount and portal interaction

In 1.14.2 Yarn, `LivingEntity.stopRiding` saves the old vehicle, calls `Entity.stopRiding`, and calls `method_6038(oldVehicle)` only when the saved vehicle is non-null, differs from the resulting vehicle, and `world.isClient` is false (`LivingEntity.java:2311-2317`). In 1.14.4 Mojmap, `LivingEntity.stopRiding` makes the same old-vehicle / detached-relationship / server-side check before `findStandUpPosition(oldVehicle)` (`LivingEntity.java:2324-2330`). The base entity method only clears `vehicle` and removes the passenger; the living-entity override owns the server-side position selection (`Entity.java:1591-1597`; `Entity.java:1651-1657`).

For mounts other than boats and horse classes, the helper starts with the vehicle's x/z and top y, then tests the same ordered eight-neighbor pattern (including its repeated final north candidate), using the mount's motion direction and the player's width/depth. At the first collision-free candidate it prefers a full support face at the player's current y and moves to y+1; otherwise it retains a candidate at y+1 when the block below has a full support face or contains water. If the initial candidate box collides, it records a y+2 candidate only when the raised box is clear and the block at y+1 has a full support face. It finally teleports to the selected or original fallback coordinates. Boat/horse mounts use the same width-based yaw/main-arm offset, then try y=mount-top+0.001, y=mount-top+1.001, and mount-centered y=player-height+0.001 when the union collision check fails (`LivingEntity.java:1656-1727`; `LivingEntity.java:1664-1741`). The search has no portal block/tag branch.

The separate Nether portal callback in both releases requires the entity to have no vehicle/passengers and to be dimension-capable before marking portal contact: 1.14.2 `!hasVehicle() && !hasPassengers() && canUsePortals()` (`PortalBlock.java:100-105)); 1.14.4 `!isPassenger() && !isVehicle() && canChangeDimensions()` (`NetherPortalBlock.java:106-111`). Both generic entity methods default the capability predicate to true. A mounted player therefore does not mark portal contact through this callback. Dismount placement itself is not conditional on being in a portal. The registered Nether portal has no collision in both versions (`Blocks.java:596-601`; `Blocks.java:583-586`), so its empty collision shape cannot satisfy the dismount helper's full-upward-face support check. The paired support predicates both obtain the entity-contextual collision shape and test whether its upward face is full (`BlockState.java:208-210`; `BlockState.java:210-212`).

## Server correction and local-player write

Both server-player overrides save the old vehicle, call `super.stopRiding()`, then request a teleport correction only if the vehicle relationship changed and the server connection exists. Since the superclass performs the server-side stand-up placement first, the correction uses the selected post-dismount x/y/z and the player's current yaw/pitch: 1.14.2 `ServerPlayerEntity.stopRiding` (`ServerPlayerEntity.java:758-766)); 1.14.4 `ServerPlayer.stopRiding` (`ServerPlayer.java:763-771`).

The dismount call uses the no-relative-arguments overload: 1.14.2 `requestTeleport` delegates with `Collections.emptySet()` (`ServerPlayNetworkHandler.java:804-806)); 1.14.4 `teleport` delegates with `Collections.emptySet()` (`ServerGamePacketListenerImpl.java:860-862`). Each handler stores the target position, advances its teleport ID, sets server player coordinates, and sends a position packet containing x/y/z, yaw/pitch, relative flags, and ID. With the empty flag set supplied for dismount, the packet coordinates are absolute. Packet field order and encoding are unchanged in the inspected bodies: doubles x/y/z, floats yaw/pitch, a flag bitfield, then a VarInt ID (1.14.2 `ServerPlayNetworkHandler.java:808-821`, `PlayerPositionLookS2CPacket.java:10-51`; 1.14.4 `ServerGamePacketListenerImpl.java:864-877`, `ClientboundPlayerPositionPacket.java:9-50`).

The local client's own `stopRiding` does not select or write dismount coordinates: 1.14.2 clears `riding` after its superclass call (`ClientPlayerEntity.java:155-159`); 1.14.4 clears `handsBusy` (`LocalPlayer.java:161-165`). These are local input-state assignments, separate from the XYZ correction. The server position packet handler later applies each relative coordinate when flagged, otherwise takes the supplied absolute coordinate, zeros velocity on absolute axes, and calls the direct entity position writer with x/y/z and rotation. There is no riding or portal suppression around that write in the inspected handler bodies (1.14.2 `ClientPlayNetworkHandler.java:642-689`, `Entity.java:1047-1058`; 1.14.4 `ClientPacketListener.java:658-706`, `Entity.java:1116-1127`).

## Compared slices and limits

Paired slices checked: living/base stop-riding path; generic stand-up position search; player/server-player overrides; Nether portal contact callback and default portal-capability predicate; portal registration/collision setting; support-face predicate; dismount server teleport overload and position packet fields; client position packet application and local-player stop-riding override.

Dependencies closed for this slice: superclass dispatch and relationship state; server-side gate; the portal block callback gate; entity-contextual collision shape used for support; request-teleport overload, relative flag set, packet fields, and client application. No trajectory prediction or runtime parity claim is made. Mapping namespaces differ across the pair; each side's exact source and mapping identity is recorded in the roster. No same-family 1.14.4 Yarn tree was available in the prepared source roots, so this comparison uses the exact prepared 1.14.2 Yarn and 1.14.4 Mojmap outputs.
