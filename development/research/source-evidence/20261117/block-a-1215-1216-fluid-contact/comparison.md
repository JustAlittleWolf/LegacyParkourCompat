# Fluid contact and travel comparison: 1.21.5 → 1.21.6

## Result

No player-reachable fluid movement delta was found in the assigned operations. The matched source intervals cover body fluid contact/current sampling, fluid cache refresh and reads, water/lava travel response, and fluid exit clearance. No canonical finding is warranted. The added `LivingEntity.travelFlying` overload in 1.21.6 is outside this LocalPlayer path: LocalPlayer inherits `LivingEntity.travel`, whose dispatch goes to `travelInFluid`, `travelFallFlying`, or `travelInAir`; the added overload is not called there.

The checked Java witnesses for the built-in water and lava tag keys match. The decompiled publications do not contain vanilla datapack tag JSON, so exact tag membership (including the default membership of waterlogged fluid states) cannot be independently closed from these Java source trees alone. The movement code itself has no tag-key change: it samples `BlockState.getFluidState()` and asks that `FluidState` whether it matches `FluidTags.WATER` or `FluidTags.LAVA`. This is the bounded remaining evidence gap for tag contents, not a discovered movement delta.

## Tick and sampling order

- `LocalPlayer.tick` calls `super.tick` on both sides (1.21.5 `LocalPlayer.java:191–215`; 1.21.6 `LocalPlayer.java:197–220`). `LivingEntity.tick` calls `super.tick()` before `aiStep()` (1.21.5 `LivingEntity.java:2460–2500`; 1.21.6 `LivingEntity.java:2512–2552`), so `Entity.baseTick` samples body fluids before the living-player travel phase (1.21.5 `Entity.java:442–463`; 1.21.6 `Entity.java:472–493`). It clears the per-entity `fluidHeight` map, updates water current/contact, samples lava, updates eye fluid state, and then swimming state in the same order.
- Movement calls `Entity.move`; after resolved movement, its authoritative-local-instance path calls `checkFallDamage` (1.21.5 `Entity.java:700–704`; 1.21.6 `Entity.java:717–721`). `LivingEntity.checkFallDamage` refreshes only water contact/current when cached `isInWater()` is false (1.21.5 `LivingEntity.java:327–331`; 1.21.6 `LivingEntity.java:341–345`), then delegates to `Entity.checkFallDamage`. This ordering is identical. In particular, an exit from water while the pre-travel cached water flag is true is not refreshed by this conditional callback; the next base tick recomputes contact. When the cached flag is false, a movement callback may sample water and push current after the move.
- There is no post-travel lava refresh in this path. Lava height and `isInLava()` remain the base-tick cache until the next base tick. `isInLava()` is `!firstTick && fluidHeight[LAVA] > 0` on both versions (1.21.5 `Entity.java:1449–1451`; 1.21.6 `Entity.java:1526–1528`).

## Body-fluid contact and current inputs

`Entity.updateFluidHeightAndDoFluidPushing(tag, pushScale)` is unchanged (1.21.5 `Entity.java:3241–3305`; 1.21.6 `Entity.java:3414–3478`). It returns false without sampling if `touchingUnloadedChunk()`. Otherwise it deflates the entity AABB by `0.001`, floors min X/Y/Z and ceils max X/Y/Z, and iterates each integer coordinate with exclusive upper bounds. For each `level.getFluidState(pos)` whose state matches the requested tag, it computes `surfaceY = blockY + fluidState.getHeight(level,pos)` and admits it when `surfaceY >= deflatedBox.minY`. The stored height is the maximum admitted surface depth. If `isPushedByFluid()` is true, each admitted cell contributes `getFlow(level,pos)`, scaled by the current maximum depth when that depth is `< 0.4`; contributions are averaged. Non-Player entities normalize that average; Player does not. The average is scaled by `pushScale`; if current X and Z speeds are both below `0.003` and push length is below `0.0045000000000000005`, the push is normalized and raised to that minimum length. It is then added to current delta movement. The method stores the sampled height for the requested tag and returns whether any cell was admitted.

Water is sampled first at push scale `0.014`. A non-underwater `AbstractBoat` vehicle suppresses water contact/current outright. Otherwise, a positive water sample can splash on transition (`!wasTouchingWater && !firstTick`), resets fall distance and sets `wasTouchingWater`; no sample clears it. Lava follows at `0.007` in ultra-warm dimensions and `0.0023333333333333335` otherwise. Both versions use the same tag keys, constants, loop bounds, current averaging/normalization, dead zone and map writes. `isInWater()` reads `wasTouchingWater`; the body contact flag and the two per-tag depth entries are cache observations, not immediate re-queries.

The Player overrides are also identical: `isAffectedByFluids()` and `isPushedByFluid()` both return `!abilities.flying` (1.21.5 `Player.java:1021–1023,1768–1770`; 1.21.6 `Player.java:1033–1035,1783–1785`). Thus flying suppresses fluid push accumulation and selects the air/fall-flying route in `LivingEntity.travel`, but the base tick still records body fluid state and height. Native waterlogged blocks reach this sampler only through their produced `FluidState`; the sampler does not inspect a `WATERLOGGED` block property. `FluidTags.WATER` and `.LAVA` still key `minecraft:water` and `minecraft:lava`; `FluidState.is(TagKey)` still asks the fluid registry holder for that tag. Slab and trapdoor waterlogged states still produce `Fluids.WATER.getSource(false)` (`SlabBlock.java:99–102`, `TrapDoorBlock.java:164–167`, both releases). The compared source publication lacks the tag data resource needed to verify default tag membership itself.

## Water/lava travel and exit response

`LivingEntity.travel(Vec3)` has the same selection gate and order in both releases (1.21.5 `LivingEntity.java:2213–2222`; 1.21.6 `LivingEntity.java:2245–2254`): it reads the current block's `FluidState`, then chooses `travelInFluid` only when cached water or lava contact is true, `isAffectedByFluids()` is true, and `canStandOnFluid(state)` is false. Player inherits `canStandOnFluid`, which returns false. Otherwise it selects fall-flying or air travel.

The water branch in `travelInFluid` matches exactly (1.21.5 `LivingEntity.java:2249–2278`; 1.21.6 `LivingEntity.java:2301–2330`). It reads prior `deltaMovement.y <= 0`, Y position, effective gravity, `isInWater`, sprinting, `getWaterSlowDown()` (`0.8F` base value), water-movement-efficiency attribute (cast to float and halved off-ground), movement speed, Dolphin's Grace, horizontal collision, and climbability. Sprinting sets horizontal drag to `0.9F`, otherwise it starts from water slowdown; acceleration starts at `0.02F`. Positive water efficiency interpolates drag toward `0.54600006F` and acceleration toward `getSpeed()`. Dolphin's Grace then forces drag to `0.96F`. It applies relative input, moves, replaces Y with `0.2` when horizontally colliding on a climbable, multiplies X/Z by drag and Y by `0.8F`, then calls `getFluidFallingAdjustedMovement`.

The lava branch also matches exactly (1.21.5 `LivingEntity.java:2279–2293`; 1.21.6 `LivingEntity.java:2331–2345`). It applies relative input at `0.02F`, moves, and compares cached lava height with `getFluidJumpThreshold()`. At or below threshold it multiplies velocity by `(0.5, 0.8F, 0.5)` and applies fluid-falling adjustment; above threshold it scales the vector by `0.5`. Nonzero effective gravity then subtracts `gravity / 4.0` from Y. After either fluid branch, horizontal collision plus `isFree(vx, vy + 0.6F - getY() + pre-moveY, vz)` sets Y velocity to `0.3F`. Formulas, casts, comparisons and caller gates match.

`getFluidFallingAdjustedMovement(gravity, wasDescending, velocity)` is unchanged (1.21.5 `LivingEntity.java:2406–2419`; 1.21.6 `LivingEntity.java:2458–2471`): only when gravity is nonzero and the player is not sprinting, it subtracts `gravity / 16.0` from Y; if previously descending and `abs(y - 0.005) >= 0.003` and `abs(y - gravity/16) < 0.003`, it substitutes `-0.003`. X/Z are preserved. Otherwise it returns the supplied vector.

## Coverage boundary

Examined the LocalPlayer tick entry and its inherited entity fluid sampling, per-move water refresh callback, player fluid gates, water/lava travel dispatch and branches, fluid-falling adjustment, exit clearance, relevant tag-key/state predicates, and slab/trapdoor waterlogged-state witness. The new `LivingEntity.travelFlying` overload is recorded as unreachable from the LocalPlayer travel dispatch and excluded as non-player behavior. Not examined: fluid tag JSON memberships (not present in these source publications), eye-fluid effects except call ordering, vehicle/non-player movement, portal/bubble/block-sweep behavior, and other independent tick lanes.
