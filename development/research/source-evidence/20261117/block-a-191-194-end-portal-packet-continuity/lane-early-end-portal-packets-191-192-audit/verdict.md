# Independent source audit: 1.9.1 → 1.9.2 End portal transfer packets

## Verdict

**The bounded no-difference finding is supported, with a required correction to the tick/arrival account.** The author’s nine paired source files all match the exact source manifests and are byte-identical across the pair. I independently froze a 13-path roster before opening the author’s normalized report. The added tick/arrival trace confirms the same relevant behavior in both versions, but disproves the report’s statement that source order does not establish the post-tick coordinate write: an End transfer during `ServerPlayNetworkHandler.tick()` is followed synchronously in that same handler call by an unconditional write of its pre-player-tick `firstGoodX/Y/Z` values.

This is source-call analysis only. It does not claim packet delivery timing or a later runtime trajectory.

## Source call and packet trace

Both versions have identical full-file hashes for the bounded transfer, packet, world, and network-handler classes in the frozen roster. The author’s summarized transfer ordering and packet descriptions are accurate with these details:

1. `EndPortalBlock.onEntityCollision` invokes `entity.changeDimension(1)` only when the entity is not riding, has no passengers, can use portals, is server-side, and its shape intersects the portal shape (`block/EndPortalBlock.java:62–69`). `ServerPlayerEntity.changeDimension` takes the Overworld→End branch (`dimension == 0 && requested == 1`), marks teleportation state, and routes through `PlayerManager.changeDimension`. On return, it sends world event 1032 at the origin (`ServerPlayerEntity.java:455–484`).
2. `PlayerManager.changeDimension(player, 1)` captures old dimension `i` before writing `player.dimension = 1`. It sends `PlayerRespawnS2CPacket` first, using dimension 1 with difficulty and generator still read from `player.world`; calls `updatePermissions`; removes the player from the source; then invokes the helper with captured `i == 0` (`PlayerManager.java:488–513`). `updatePermissions` is a method call, not a separate portal event. The helper reads the already-updated `entity.dimension` for its first branch, but uses its old-dimension argument for spawn selection and `dimension != 1`. For this Overworld→End call, the old argument selects `toWorld.getForcedSpawnPoint()`, then the non-1 placement path runs (`PlayerManager.java:515–568`).
3. The End `PortalForcer.onDimensionChanged` branch lays the platform at floored entity X/Z and `floor(Y)-1`, calls `setPositionAndAngles(i,j,k, entity.yaw, 0)`, and zeros all three velocity components (`PortalForcer.java:30–57`). Then the helper adds the player to the target world, calls `toWorld.tickEntity(entity, false)`, and finally assigns `entity.world = toWorld`. The manager updates dimension tracking and calls the five-argument network-handler `teleport` with the resulting player XYZ/yaw/pitch (`PlayerManager.java:499–508`). This is the correction payload’s source: the five-argument overload supplies an empty relative-argument set; the handler stores requested XYZ, updates player position, and constructs `PlayerMoveS2CPacket` with those values and empty flags (`ServerPlayNetworkHandler.java:490–516`).
4. The move packet serializes XYZ doubles, yaw/pitch floats, flags byte and teleport VarInt ID in that order (`PlayerMoveS2CPacket.java:22–51`). With the empty flag set all XYZ are absolute. The client adds coordinates only for relative axes; each absolute XYZ axis zeros its corresponding velocity; it applies position/angles, sends `AcceptTeleportC2SPacket(id)`, then sends a position/angles response with shape min-Y and `onGround=false` (`ClientPlayNetworkHandler.java:545–590`). The respawn handler changes the client world only when dimension differs and then calls `Minecraft.respawnPlayer`; that method and `PlayerEntity.resetPos` have identical relevant bodies in both releases. A matching acknowledgement ID makes the server restore `requestedTeleportPosition`; while teleportation state is active it also updates `lastGoodX/Y/Z` and completes that state, then clears the request (`ServerPlayNetworkHandler.java:348–363`).

## Tick/arrival correction

The report correctly describes `ServerPlayNetworkHandler.tick()`’s position write but stops short of the source-proven call order. The following paired call path is verified:

- `MinecraftServer.tickWorlds()` runs each `ServerWorld.tick()`/`tickEntities()` before ticking the connection listener (`server/MinecraftServer.java:545–609`; this exact slice is equal across releases even though the whole file hash differs).
- `ConnectionListener.tick()` ticks each connected `Connection`; `Connection.tick()` invokes its `Tickable` packet listener. `ServerPlayNetworkHandler.tick()` first captures the current player XYZ in `resetPosition()`, calls `player.tickPlayer()`, then unconditionally calls `player.updatePositionAndAngles(firstGoodX, firstGoodY, firstGoodZ, ...)` (`ServerPlayNetworkHandler.java:161–165, 226–233`; `ConnectionListener.java:155–165`; `Connection.java:222–229`).
- During `tickPlayer`, `PlayerEntity.tick()` reaches `LivingEntity.mobTick()`; on the logical server `LivingEntity.isLocallyControlled()` is true (`!world.isClient`), so player `moveRelative` may call `Entity.move`. `Entity.move` calls `checkBlockCollisions`, which dispatches the End portal callback (`LivingEntity.java:1293–1448, 1636–1707, 1832–1834`; `Entity.java:688–695`). Thus when the ordinary End portal collision fires in that player tick, `PlayerManager`’s absolute destination correction is sent from inside the call, and the handler’s captured pre-tick XYZ write executes after the transfer returns, in the same handler tick. It is not merely a later, unordered source write.
- `World.tickEntity(entity, false)` does not call `entity.tick()`: the body calls it only under `requireLoaded && entity.inChunk` (`world/World.java:1391–1407`). The source/target calls in the transfer helper therefore perform world bookkeeping, not a full entity tick. The target insertion/world assignment happens during the connection phase after that server tick’s world phase; the next target-world entity tick is in a later server tick. The handler’s same-call XYZ overwrite happens before then. The ack path can subsequently restore the stored destination request if its ID matches.

The tick-path support is not a claim about when the client receives/flushed packets, nor about exact post-ack movement. The destination spawn/platform coordinates remain dependent on the world’s forced spawn data; no fixed numeric XYZ is inferable from these sources alone.

## Pair status

No 1.9.1→1.9.2 source delta was found in the audited End transfer or packet behavior. Preserve the no-difference verdict, but revise the report to state the same-handler-tick `firstGoodX/Y/Z` overwrite and to distinguish transfer-time world bookkeeping from a full destination entity tick. No product changes, tests, builds, launches, network access, or Git operations were performed.
