# 1.9.1 → 1.9.2: End portal transfer and position packets

## Source identity

Both sides use exact decompiled `ornithe-feather` source roots with hidden `.decompile-provenance.json` manifests. The manifests identify Feather Gen2 build.2 and the exact Mojang client/version metadata inputs. The full manifest SHA-256 values, input artifact SHA-256 values, and programmatically recomputed hashes for every listed source file are in `roster.json` and `sha256.txt`. Every listed source hash matches its own manifest; all nine paired source files are byte-identical by full SHA-256.

## Source comparison

**Result: no source difference found in the bounded operations.** The following source chain is identical in both releases.

- `block/EndPortalBlock.java`, `onEntityCollision` (62–69): calls `entity.changeDimension(1)` only when the entity is neither riding nor carrying passengers, can use portals, the world is not client-side, and entity shape intersects the portal block shape.
- `server/entity/living/player/ServerPlayerEntity.java`, `changeDimension` (455–485): sets teleportation state. For an Overworld player requesting dimension 1, increments the End-entry statistic and routes to `PlayerManager.changeDimension`; after that call it sends world event 1032 at origin with data 0 and `global=false`. The separate End-to-End branch removes the entity, marks `leavingTheEnd` once, and conditionally sends game event 4.
- `server/PlayerManager.java`, `changeDimension(ServerPlayerEntity,int)` (488–513): captures old dimension in `i`, obtains source world, writes `player.dimension = dimension`, resolves the destination world from that new field, then constructs/sends `PlayerRespawnS2CPacket` before the helper placements. At this call site, the respawn packet uses the newly assigned dimension while difficulty and generator are read from the still-current `player.world`. The helper is invoked with captured old `i` (`0` for the bounded Overworld→End case). `onChangedDimension` (264–272) updates chunk tracking and requests the current-position chunk; the manager then calls the network handler's five-argument `teleport` with current XYZ/yaw/pitch.
- `server/PlayerManager.java`, `changeDimension(Entity,int,ServerWorld,ServerWorld)` (515–568): its branch tests the already-updated `entity.dimension`, while the spawn-point choice and later `dimension != 1` placement gate use the captured old-dimension argument. For Overworld→End, the already-written entity dimension is 1, old argument is 0, so the `else` branch selects `toWorld.getForcedSpawnPoint()`, copies its integer X/Y/Z, sets position/angles to yaw `90.0F`, pitch `0.0F`, and calls `fromWorld.tickEntity(entity, false)` if alive. Since old argument 0 satisfies `dimension != 1`, the subsequent placement section clamps `(int)d` and `(int)e`, then, if alive, sets position/angles, calls destination portal-forcer placement using the originally captured yaw, adds the entity and calls `toWorld.tickEntity(entity, false)`; finally `entity.setWorld(toWorld)` is unconditional. These source writes do not prove exact post-tick coordinates.
- `server/network/handler/ServerPlayNetworkHandler.java`, `teleport` (490–516): the five-argument overload delegates with `Collections.emptySet()`. It stores the requested position, updates server position/angles, and sends `PlayerMoveS2CPacket` with supplied XYZ/angles and that empty relative-argument set. Thus this call's coordinates and angles are encoded as absolute fields. `tick` (161–165) calls `resetPosition()`, then `player.tickPlayer()`, then writes XYZ from `firstGoodX/Y/Z` through `updatePositionAndAngles`, with no spectator conditional around that assignment. The reset captures the current player XYZ in `firstGoodX/Y/Z` (226–233). If the transfer executes during this `player.tickPlayer()` call, the XYZ write follows it unconditionally in the same `ServerPlayNetworkHandler.tick()` invocation and uses the pre-player-tick coordinates.
- `network/packet/s2c/play/PlayerMoveS2CPacket.java`: stores XYZ as doubles, yaw/pitch as floats, relative-axis flags and teleport ID; serialization order is XYZ, yaw/pitch, one flags byte, VarInt ID.
- `client/network/handler/ClientPlayNetworkHandler.java`, `handlePlayerMove` (545–590): starts with packet coordinates. For each XYZ relative flag it adds that coordinate to the current player coordinate; when an XYZ axis is absolute, it zeros only the corresponding velocity component. Yaw and pitch are independently added only when their flags are relative. It applies XYZ/angles with `updatePositionAndAngles`, sends `AcceptTeleportC2SPacket(teleportId)`, then sends a position/angles response using player X, shape min-Y, Z, yaw, pitch and `onGround=false`. `handlePlayerRespawn` (854 onward) changes the client world only when packet dimension differs from the current player dimension.
- `server/network/handler/ServerPlayNetworkHandler.java`, `handleAcceptTeleport` (348–363): applies the stored requested position only when acknowledgement ID matches; when the player is in teleportation state it also updates last-good XYZ and completes that state, then clears the requested position. No spectator test wraps this acknowledgement path.


## Tick and position writer correction

In both exact versions, `ServerPlayNetworkHandler.tick()` calls `resetPosition()`, invokes `player.tickPlayer()`, then unconditionally calls `player.updatePositionAndAngles(firstGoodX, firstGoodY, firstGoodZ, yaw, pitch)` (`ServerPlayNetworkHandler.java:161–165`; reset body at 226–233). `resetPosition()` captured the player's current XYZ before `player.tickPlayer()`. Therefore, **if** the Overworld→End transfer executes during this handler call's `player.tickPlayer()`, the transfer returns to this same handler invocation and the unconditional assignment writes those captured pre-player-tick XYZ values. The condition is limited to transfer execution inside this call path; this report does not claim every portal collision is processed there.

The transfer helper's source- and destination-world calls are `tickEntity(entity, false)`. In `World.tickEntity`, `entity.tick()` / `entity.rideTick()` are called only inside `if (requireLoaded && entity.inChunk)`; with `false`, neither full entity tick runs (`World.java:1391–1407`). These calls do not themselves constitute a full source or destination entity tick.

The manager's `networkHandler.teleport(...)` and its `PlayerMoveS2CPacket` send are distinct from the handler tick's later server-side XYZ assignment. The source proves the conditional call order and the absolute packet payload at send time; it does not prove transport arrival, client receipt or application order, or any later trajectory. A matching teleport acknowledgment has its separately sourced server-side handling described above.

The server source calls send the respawn packet before the destination helper and calls the absolute position teleport after it. This is source-call order only; the separate same-handler-call XYZ write is conditional on the transfer occurring during player.tickPlayer(). No packet delivery or client arrival order is inferred.
