## Source trace

`block/EndPortalBlock.java`, `onEntityCollision` (both versions, lines 63–70), has the same entry gates: the entity is neither riding nor carrying passengers, can use portals, the world is server-side, and the entity shape intersects the portal shape. It calls `entity.changeDimension(1)`. `ServerPlayerEntity.changeDimension` (lines 458–487, byte-identical) sets teleportation state; for current dimension 0 and requested dimension 1 it increments the End-entry statistic and calls `PlayerManager.changeDimension`, then sends the same world event and resets the same last-sent XP, health, and hunger sentinels.

`PlayerManager.changeDimension(ServerPlayerEntity,int)` and its entity-transfer helper (lines 489–550 onward, byte-identical) preserve the same call order. The manager saves the old dimension/world, assigns the target dimension, resolves its world, sends `PlayerRespawnS2CPacket`, updates permissions, removes the player from the old world, clears `removed`, and invokes the helper. For this ordinary 0→1 case the helper receives a player whose dimension has already been assigned 1. Its fallback branch selects `toWorld.getSpawnPoint()` when the requested dimension is 1; `getForcedSpawnPoint()` is the other-dimension branch. It takes that block's integer X/Y/Z directly, sets yaw 90 and pitch 0, and calls `fromWorld.tickEntity(entity,false)` only if alive. It has no safe-position search or collision check in that branch. Because the requested dimension is 1, the later `dimension != 1` placement/portal-forcer branch is skipped; the helper then calls `entity.setWorld(toWorld)`. This records source behavior only and does not assert the resulting post-tick coordinates.

After the helper, the manager calls `onChangedDimension`, issues `networkHandler.teleport(player.x, player.y, player.z, player.yaw, player.pitch)`, changes the interaction-manager world, then sends abilities, world info, player info, and each active status effect. These are source call/send statements; this audit does not infer packet arrival or runtime execution order.

`ServerPlayNetworkHandler.teleport` and `PlayerMoveS2CPacket` are byte-identical across the pair. The ordinary overload supplies `Collections.emptySet()`: the requested XYZ values and angles are absolute. The handler stores the requested position, increments `requestedTeleportId` (wrapping to 0 when it reaches `Integer.MAX_VALUE`), updates the server player position/angles, and sends the packet with that id. The client `handlePlayerMove` method is byte-identical: for each non-relative X/Y/Z component it zeros the matching player velocity component; it applies the packet XYZ/angles with `updatePositionAndAngles`, sends `AcceptTeleportC2SPacket(packet.getTeleportId())`, then reports its position, shape-minY, angles, and `onGround=false` in a C2S move packet. The server accepts only a matching id, updates position from `requestedTeleportPosition`, conditionally updates last-good coordinates and completes teleportation state, then clears the requested position.

The same `PlayerRespawnS2CPacket` handling changes the client world/dimension when needed, calls `minecraft.respawnPlayer`, and updates game mode. `Minecraft.respawnPlayer` has the same implementation in both versions: it resets world spawn state, unloads/removes old entities, creates a local player carrying the prior stats and synced data, assigns the dimension, calls `resetPos`, and adds/initializes the replacement. The server transfer loop resends active status effects after the absolute move request; no transfer-specific velocity packet or extra client effect operation was found in the traced path.

## Pair difference and boundary

Across the 20 frozen paths, 18 are raw-byte identical. The only two differing files have unrelated release metadata: `PlayerEntity.java` changes the NBT `DataVersion` constant from 183 to 184; `MinecraftServer.java` changes the displayed/returned version string from 1.9.3 to 1.9.4. The supplemental `Minecraft.java` differs only in the title and `X-Minecraft-Version` strings. The portal gates, dimension/forced-point choice, permissions/respawn sequence, absolute packet flags and TeleportID handshake, client XYZ/velocity response, and effect resend are source-identical.

This accepts **no movement finding** for this operation at this endpoint pair. It does not establish the exact patch where any behavior first appeared, every intervening release, or runtime parity.
