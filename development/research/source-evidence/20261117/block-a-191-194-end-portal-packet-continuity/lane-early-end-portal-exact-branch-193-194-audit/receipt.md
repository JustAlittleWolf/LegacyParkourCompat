# Exact-source correction receipt — 1.9.3 → 1.9.4 End portal transfer

## Outcome

**Correction confirmed.** The comparison and earlier audit misidentify which dimension operand selects the spawn point. On the ordinary Overworld (0) → End (1) ServerPlayer route, `PlayerManager.changeDimension(ServerPlayerEntity,int)` captures old dimension 0 in local `i`, updates `player.dimension` to destination 1, and passes `i` (0) to the generic helper. The generic helper's spawn branch uses its `dimension` parameter, so it selects `toWorld.getForcedSpawnPoint()`, not `toWorld.getSpawnPoint()`. That same old-dimension parameter makes `dimension != 1` true, so the helper's later placement / PortalForcer section runs. The two distinct `tickEntity(entity,false)` calls are both present and separately guarded by `entity.isAlive()`.

The author addendum agrees with this exact source trace. The bounded no-difference conclusion remains supported for the traced server transfer and correction path because every Java source in the frozen rosters has the same raw SHA-256 at both endpoints. This receipt does not validate wider client packet handling, full movement coverage, runtime execution, packet arrival, or post-tick position.

## Prior-claim correction boundary

- The comparison's statement that updated `entity.dimension == 1` selects the regular End spawn is wrong for the accessor decision. The updated field chooses the generic helper's `else` branch; the helper parameter `dimension` chooses `getSpawnPoint()` versus `getForcedSpawnPoint()`. That helper parameter is the captured old dimension 0 here, so the exact route uses the forced spawn point.
- The comparison correctly notes that old `dimension == 0` makes the later `dimension != 1` placement block run, but this also means its claim that the regular spawn accessor is selected cannot be retained.
- The earlier audit's description of the generic helper choosing `getSpawnPoint()` for the requested destination 1 repeats the same operand misread.
- The author addendum explicitly separates the updated field from the helper argument and matches the source at all cited operand gates, including forced spawn, both tick calls, PortalForcer, and the correction call outside helper gates.
- Since all eight rostered server-side call-chain / packet-writer Java files are raw-byte identical across the pair, this operand correction does not create a 1.9.3→1.9.4 difference. The receipt does not restate or renew claims outside this exact bounded trace.
