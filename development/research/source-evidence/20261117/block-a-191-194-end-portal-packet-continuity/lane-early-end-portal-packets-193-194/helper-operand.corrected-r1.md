# Helper operand correction: 1.9.3 → 1.9.4 End transfer

This supplement corrects the generic-helper spawn operand description in `comparison.md`. The original files remain unchanged. The same statements and line ranges below were checked in both exact `1.9.3` and `1.9.4` `ornithe-feather` sources; the relevant `EndPortalBlock.java`, `ServerPlayerEntity.java`, and `PlayerManager.java` files have identical hashes across the pair.

## Distinct operands on the ordinary Overworld → End route

1. `EndPortalBlock.onEntityCollision` calls the virtual `entity.changeDimension(1)` only when its source gates pass (`net/minecraft/block/EndPortalBlock.java:63-70`, both releases). For a server player, dispatch reaches the override `ServerPlayerEntity.changeDimension(int dimension)` (`net/minecraft/server/entity/living/player/ServerPlayerEntity.java:458-482`). On current dimension 0 and requested argument 1, the override leaves the requested destination as 1 and calls `PlayerManager.changeDimension(this, 1)`.
2. The specialized `PlayerManager.changeDimension(ServerPlayerEntity player, int dimension)` (`net/minecraft/server/PlayerManager.java:489-503`) captures `int i = player.dimension` while it is still 0, then sets `player.dimension = dimension` (1). Its generic-helper call is `this.changeDimension(player, i, serverWorld, serverWorld2)`: the generic helper's `dimension` argument is **old dimension 0**, while the helper's `entity.dimension` field is already **destination dimension 1**.
3. The generic helper (`PlayerManager.java:516-569`) tests the updated field first. Since `entity.dimension` is neither -1 nor 0, it enters the `else` spawn branch. Inside that branch, the spawn choice instead tests the helper argument: `dimension == 1` chooses `toWorld.getSpawnPoint()`, otherwise it chooses `toWorld.getForcedSpawnPoint()`. Here the argument is old dimension 0, so this ordinary 0→1 transfer uses **`getForcedSpawnPoint()`**, not `getSpawnPoint()`. It copies that point's X/Y/Z into the entity and calls `setPositionAndAngles(..., 90.0F, 0.0F)`.
4. The first `if (entity.isAlive())` then gates `fromWorld.tickEntity(entity, false)` (lines 547-550). This is the old-world tick after the forced-spawn coordinates/angles have been assigned.
5. After the `moving` section, the helper's `if (dimension != 1)` also tests the helper argument, old dimension 0; it is therefore true. This `placing` section integer-casts and clamps the saved X/Z values. A second `if (entity.isAlive())` gates all of: the second position/angle write, `toWorld.getPortalForcer().onDimensionChanged(entity, g)`, `toWorld.addEntity(entity)`, and `toWorld.tickEntity(entity, false)` (lines 554-563). Thus both `tickEntity(..., false)` calls are separately alive-gated; the End PortalForcer call belongs to the second, destination-placement gate. `entity.setWorld(toWorld)` at line 568 is outside those alive and `dimension != 1` gates.

## Final correction packet gate

After the generic helper returns and `onChangedDimension` runs, the specialized manager directly calls `player.networkHandler.teleport(player.x, player.y, player.z, player.yaw, player.pitch)` (`PlayerManager.java:503-506`). This source call is outside the helper's `dimension != 1` and `entity.isAlive()` conditions: on the ordinary 0→1 player route, it is not suppressed by either helper gate. The `ServerPlayNetworkHandler.teleport` writer sends the absolute `PlayerMoveS2CPacket` with an empty relative-argument set (`net/minecraft/server/network/handler/ServerPlayNetworkHandler.java:490-516`).

The named helper argument must therefore not be read as the destination merely because the call originated from `changeDimension(..., 1)`: it is old dimension 0. The updated `entity.dimension` field selects the spawn branch; the old-dimension helper argument selects **forced spawn**, opens the later placement/PortalForcer section, and does not gate the final correction packet. This operand behavior is identical in 1.9.3 and 1.9.4, so the pair disposition remains no difference for this operation.
