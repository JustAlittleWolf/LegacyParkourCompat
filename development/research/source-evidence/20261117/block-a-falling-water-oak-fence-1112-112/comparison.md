# Falling-water wall-face comparison

## Bounded operation and version coverage

This comparison covers the falling-water side-face cue in the per-fluid flow vector used for ordinary player current, plus the immediate vanilla-state query it depends on. It checks Feather 1.8, 1.8.9, 1.9, 1.9.4, 1.10.2 and 1.11.2 against published, source-native 26.2 (`unobfuscated`). The exact patch introduction inside the 1.11.2–26.2 interval is not established by these endpoints.

In 1.8, `LiquidBlock.getFlow(WorldView, BlockPos)` accumulates horizontal liquid-depth differences. For the current cell only when `LEVEL >= 8`, it checks each horizontal side neighbor and the block above it, passing the same horizontal `Direction` to `isFaceSolid`; on a hit, it replaces the horizontal magnitude with `normalize() + (0,-6,0)`, breaks, then normalizes the resulting vector (1.8 `LiquidBlock.java:129-161`). This uses the queried direction as-is, not its opposite. `LiquidBlock.isFaceSolid` rejects the same material, returns true for `UP`, rejects `Material.ICE`, and otherwise delegates (1.8 `LiquidBlock.java:74-82`). The base `Block.isFaceSolid` ignores face and block shape and returns the state block material's `isSolid()` (1.8 `Block.java:282-284`). 1.8.9 keeps this policy and call order (`LiquidBlock.java:129-161`, `Block.java:329-331`).

The same falling-side gate, two tested positions, same-direction argument, down-bias and final normalization are present in 1.9, 1.9.4, 1.10.2 and 1.11.2 (`LiquidBlock.java:128-168` in 1.9; `131-171` in 1.9.4/1.10.2/1.11.2). 1.9 moves the base material lookup to `BlockState.getMaterial().isSolid()` (`Block.java:305-307`); 1.9.4, 1.10.2 and 1.11.2 retain that material-level predicate (`Block.java:327-329`, `332-334`, `343-345`). In each, the liquid override compares the neighbor material with the liquid's material, special-cases `UP` and `Material.ICE`, then delegates to the base predicate. No wall-face behavior change is present among the inspected Feather versions.

In 26.2, `FlowingFluid.getFlow(BlockGetter, BlockPos, FluidState)` still adds the horizontal normalized vector to `(0,-6,0)` when its falling-state gate finds a qualifying side, then normalizes again (`FlowingFluid.java:55-100`). It checks the neighbor at `pos.offset(direction)` and that neighbor's `above()` position using the same horizontal `direction` (`:82-97`). `isSolidFace` returns false for same-fluid neighbors, true for `UP`, false for `IceBlock`, and otherwise calls `BlockState.isFaceSturdy(level,pos,direction)` (`:106-115`). The default face-sturdy query is `SupportType.FULL`; FULL requires a full face in the block support shape (`BlockBehaviour.java:291-293, 892-897`; `SupportType.java:11-16`; `Block.java:346-352`). The default support shape is the collision shape, so this query can distinguish partial horizontal faces of era-existing fences, walls and stairs from full cubes. The old `Material.isSolid()` test cannot distinguish those faces. Ice remains an explicit false case on both sides, although its source type changes from `Material.ICE` to `IceBlock`.

## Reachable ordinary-player current witness

Use one falling-water cell at `pos` (`LEVEL=8` in the inspected legacy states; `FALLING=true` in 26.2), no horizontal liquid-depth/height gradient, and a dry oak fence at `pos.north()` with no other tested side solid (including above that fence). The old source registers oak fence with `Material.WOOD` (1.8 `Block.java:936`; `Material.java:55-57`); the old material predicate therefore counts it as solid regardless of the queried face. Its side hit turns the zero horizontal vector into a downward vector through `normalize() + (0,-6,0)`. In 26.2 the queried fence support face is not a full face, so `isFaceSturdy(..., Direction.NORTH)` is false; with no horizontal gradient, the flow vector remains zero. The chosen water cell intersects the player's fluid-interaction box. The 26.2 oak-fence default state has no arms; `FenceBlock` builds its support from a narrow post and optional arms (`Blocks.java:2021-2026`; `FenceBlock.java:37-42`; `CrossCollisionBlock.java:46-68`), so its queried horizontal face is not full.

This reaches player movement current: 1.8 `Entity.checkWaterCollisions` calls `World.applyLiquidDrag` (`Entity.java:745-746`); the world aggregates the per-cell flow, normalizes it and adds the 0.014 impulse when the entity has liquid collision (`World.java:1462-1499`); `PlayerEntity.hasLiquidCollision()` is true while not flying (`PlayerEntity.java:1612-1614`). In 26.2 `Entity.tick` invokes `updateFluidInteraction` (`Entity.java:531`), which obtains flow per intersected fluid state and applies the water current; `Player.isPushedByFluid()` is true while not flying (`Entity.java:1645-1668`, `Player.java:1694-1696`). `LocalPlayer` extends `AbstractClientPlayer`, which extends `Player`, and its tick calls `super.tick()` (`LocalPlayer.java:108, 227-230`; `AbstractClientPlayer.java:15`); it does not override the fluid-push predicate. Therefore a non-flying ordinary local player can receive the old downward current in this witness and receive no current from this falling-water cell under the 26.2 face test. This witness isolates the wall-face predicate; it does not rely on multi-cell current aggregation.

## Provenance and source-byte verification
