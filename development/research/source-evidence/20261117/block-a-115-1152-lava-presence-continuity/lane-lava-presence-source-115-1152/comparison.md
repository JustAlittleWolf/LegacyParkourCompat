# Lava-presence source comparison: 1.15 → 1.15.2

## Result

No source difference was found in either assigned behavior from 1.15 through 1.15.2. The exact Mojmap method slices compared here are byte-identical across 1.15, 1.15.1, and 1.15.2 after normalizing the extracted lines to UTF-8 LF with a final LF. This establishes alias continuity across the required middle release for the bounded members, not an implementation cutover or full-pair freeze. Full-file hashes for `LivingEntity.java`, `LocalPlayer.java`, and `Player.java` differ in 1.15.2 because of other contents; the scoped slices remain identical (see `comparison-slices.sha256`).

## Producer: reset, visit, callback

- `Entity.move` (1.15/1.15.1/1.15.2, `Entity.java:450-541`) runs the producer only in its `noPhysics == false` branch. The piston path returns before this producer if piston-limited movement equals `Vec3.ZERO` (`:455-460`). After collision/location, contact, and sound work, it sets `isInLava = false` and calls `checkInsideBlocks` (`:533-535`). If the checked region is not loaded, the flag therefore remains false for that move.
- `checkInsideBlocks` (`Entity.java:791-824`) uses the post-move bounding box. It floors positions inset by `0.001` at both min and max (`:795-800`), requires `level.hasChunksAt(min,max)` for the entire region (`:803`), then visits every integer x/y/z cell in inclusive loops (`:804-812`). It calls `BlockState.entityInside` and `onInsideBlock` for each visited state (`:810-812`); exceptions are converted to a crash report and rethrown (`:813-818`). The callback path uses neither a fluid-height test nor a collision-shape intersection test. `Blocks.LAVA` is explicitly registered with `noCollission()` (`Blocks.java:94-96`), and this block-cell callback still runs.
- `BlockState.entityInside` dispatches directly to its block (`BlockState.java:248-250`). `LiquidBlock.entityInside` calls `entity.setInLava()` exactly when its configured fluid satisfies `FluidTags.LAVA` (`LiquidBlock.java:171-175`); it does not inspect the passed block state, block position, player's height, or fluid surface. `Entity.setInLava` sets the field; `isInLava` returns it (`Entity.java:1055-1061`).
- No local-player, logical-side, view, fog, rendering, or camera predicate guards the producer. The normal collision path is presentation-independent. Its gates are the `noPhysics` branch, the early zero-piston return, loaded chunks for the full inset box, and whether a lava-tagged block cell is in that box. Vanilla's collision shapes do not constrain this callback traversal.

## Ordinary lava and a surface witness

The decompiled data-tag provider explicitly puts both `Fluids.LAVA` and `Fluids.FLOWING_LAVA` in `FluidTags.LAVA` (`FluidTagsProvider.java:17-21`). `Blocks.LAVA` uses `Fluids.LAVA` (`Blocks.java:94-96`). `LiquidBlock` seeds fluid-state index 0 with `getSource(false)` and uses block level 0 as the default state (`LiquidBlock.java:36-48`). `LavaFluid.Source` reports amount 8 and source=true (`LavaFluid.java:233-242`); `FlowingFluid.getHeight` uses the own height unless the same fluid is above, while own height is `amount / 9.0F` (`FlowingFluid.java:465-477`). Thus an ordinary level-0 source lava cell at y=64, with no lava cell above, has its fluid surface at y=64+8/9 ≈ 64.8889.

Concrete state witness: take a loaded source-lava block at (0,64,0), no lava above it, and a non-flying player's post-move box centered over that cell with `minY = 64.90` (ordinary width/height, e.g. 0.6 × 1.8). `minY + 0.001` still floors to y=64, so `checkInsideBlocks` converts the inset coordinate with `BlockPos.PooledMutableBlockPos.acquire(double, double, double)`, which applies `Mth.floor` (`BlockPos.java:411-413`), so it visits the source block cell even though the player's feet are above the 64.8889 fluid surface. The block has no collision; `LiquidBlock.entityInside` observes its lava fluid tag and sets `isInLava`. This is a cell-overlap signal, not a claim that the player is submerged in the fluid volume. It supplies a reachable airborne/pathing precondition; no custom block state or extra tag is needed, and membership in the vanilla lava tag is verified above.

## Local tick timing and consumers

- `LocalPlayer.tick` calls `super.tick()` when the chunk at its x/z is loaded (`LocalPlayer.java:179-196`). The inherited `LivingEntity.tick` calls `super.tick()` first, so `Entity.baseTick` observes the flag left by the preceding movement before `LivingEntity.tick` reaches `this.aiStep()` (`LivingEntity.java:2024-2025, 2103`; `Entity.java:340-346, 348-384`).
- `LocalPlayer.isEffectiveAi()` returns true (`LocalPlayer.java:490-492`). Each local `aiStep` refreshes input before delegating (`:631-648`; `this.input.tick(...)` at `:635`), and auto-jump may set `input.jumping = true` at `:643-648`. Dynamic dispatch proceeds from `LocalPlayer.aiStep` to `Player.aiStep` and then `LivingEntity.aiStep` (`LocalPlayer.java:625, 778`; `Player.java:497-517`). In `LivingEntity.aiStep`, an immobile entity first clears `jumping`; otherwise this effective local player runs `serverAiStep` before the jump section (`LivingEntity.java:2253-2264`). The LocalPlayer override copies `input.jumping` to `jumping` only when `isControlledCamera()` (`LocalPlayer.java:607-617, 620-622`). So with the local camera controlled and the entity mobile, a held jump is presented to the lava check on that same AI step; auto-jump can also synthesize the same input. The jump section precedes travel (`LivingEntity.java:2265-2288`), so both read the flag from the preceding movement before this tick's travel move can recompute it.
- With `jumping == true`, the held-jump section first gives `waterHeight` priority: it takes the non-deep-water arm when `!(waterHeight > 0.0) || onGround && !(waterHeight > 0.4)`. In that arm, `isInLava()` selects `jumpInLiquid(FluidTags.LAVA)` (`LivingEntity.java:2265-2276`). `jumpInLiquid` adds `0.04F` to vertical delta movement; its tag argument is not read (`:1823-1825`). On the non-flying source-lava witness with no water, `waterHeight == 0`, so held jump reaches that branch. No edge-trigger gate exists in this section: the local held input is copied each effective local AI step.
- `Player.travel` has the same body in all three releases after accounting for its line shift: 1.15/1.15.1 `Player.java:1455-1486`, 1.15.2 `Player.java:1447-1478`. It adds its swimming adjustment only for swimming non-passengers, then delegates to `LivingEntity.travel` unless the player is flying without being a passenger. For this non-swimming, non-flying witness, it reaches `LivingEntity.travel`, which runs for effective AI or a locally controlled instance (`LivingEntity.java:1831-1832`); `Entity.isControlledByLocalInstance` recognizes a controlling `Player` that is local (`Entity.java:2521-2524`). Travel first tests water, then tests `isInLava()` with a flying-player exception (`LivingEntity.java:1840-1842`). In the non-flying source-lava witness, the lava branch calls `moveRelative(0.02F, input)`, moves, halves the resulting delta movement, applies `-d/4` vertical gravity when gravity is enabled, and can set vertical movement to `0.3F` for the stated horizontal-collision/free-space condition (`:1913-1925`). The branch's move recomputes `isInLava` after the current travel/jump decisions, so the result produced by one move is consumed by the next local AI step. Leaving the lava cell likewise leaves the previous true value available until the next move refreshes it.

## Separate fluid-height state and bounded exclusions

`waterHeight` is not the lava-presence flag. `Entity.baseTick` calls `updateWaterState` (`Entity.java:348-364`); `updateInWaterState` calls `checkAndHandleWater(FluidTags.WATER)` (`:943-972`). That helper separately iterates fluid-state cells from a `0.001`-deflated AABB, requires its own chunk coverage, reads `FluidState.getHeight`, accumulates a depth, stores it in `waterHeight`, and returns water-contact status (`:2593-2655`). If its chunk check fails (`:2601-2603`), it returns before assigning the height, so the previous `waterHeight` may remain. This water-height value is current for the ordinary witness because its covered region is loaded. The jump branch uses this water-depth value for water-vs-ground arbitration, but `isInLava` comes from the block callback above and has no fluid-height query. This is the requested separate height map.

This assignment did not compare other lava consumers as independent operations. `Entity.baseTick` also reads `isInLava` for `lavaHurt()` and halves `fallDistance` (`Entity.java:381-384`); health/damage handling is outside the requested travel and held-jump checks. No tick loop beyond this producer/consumer chain was inventoried, and no behavior after 1.15.2 is inferred.
