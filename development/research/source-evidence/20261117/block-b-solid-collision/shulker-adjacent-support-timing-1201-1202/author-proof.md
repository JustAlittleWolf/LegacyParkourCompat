# Shulker adjacent support timing: 1.20.1 → 1.20.2

## Evidence identity

Exact canonical decompilations: Minecraft 1.20.1 and 1.20.2, Mojmap, published in `decompiled_minecraft/<version>/mojmap/`. Their `mojmap.provenance.json` records `versionId`/`namespace`, the shared exact run, and the build-2026-10-07 batch (`decompileMinecraft --versions=1.20.1,1.20.2,1.20.4,1.20.6 --mappings=mojmap`). Each `mojmap.ready.json` says `status: ready`; each source-manifest SHA is recorded there. The relevant per-source SHA-256 entries are:

- 1.20.1 `ShulkerBoxBlockEntity.java`: `54d5bff4c0541fcd762c65d818e88bf88fe3b6115bc6c67489126aa20e161721`; `ShulkerBoxBlock.java`: `cbac44132ca5feae1563c7590afbd941a581860941b7f2306b29cfd85e75224c`.
- 1.20.2 `ShulkerBoxBlockEntity.java`: `7884f7fd47585e5b4c1c98de22cdd5123a478d01b08e2a9debdc286fee371565`; `ShulkerBoxBlock.java`: `7d04605ccfc899fec7f448b465edecf79f2953d21cbf4bcefc46ffc3e4fe593e`.
- Shared unchanged helper hashes in both source manifests: `FenceBlock.java` `b9b38034baf9829bcd80a18d1eb60aabfdd9fb9885f37c69f4126fcbdc42c174`; `Block.java` `0c2df3d958078929c4cc2985e0d6a6a766cbbbb02066e6c9ac471981aa858656`; `BlockBehaviour.java` `1d2212b891fd218765ff58f277b0d5a17f7fbef0a5cd8d5f8a924d74fd19151d` in 1.20.1 and `a6d88726ce4642fc0a61f46a01347bb0b74887b61ef55af7e7c76723789a0b57` in 1.20.2.

## Source trace and difference

1.20.1 Mojmap `ShulkerBoxBlockEntity.updateAnimation` (lines 66–92) advances OPENING/CLOSING progress and only calls `doNeighborUpdates` at the terminal status transition. Its block-event callback `triggerEvent` (130–147) changes to OPENING/CLOSING and immediately calls `doNeighborUpdates` (135/140); helper (149–151) is only `BlockState.updateNeighbourShapes(level,pos,3)`.

1.20.2 `updateAnimation` (66–100) adds a neighbor update at the first animation tick: opening, after progress is advanced by 0.1, when `progressOld == 0.0F` (74–76); closing, after progress is reduced by 0.1, when `progressOld == 1.0F` (88–90). Terminal status updates remain (78–82, 92–96). `triggerEvent` (137–152) now only stores `openCount` and switches status; it does not notify. The helper (154–157) calls `updateNeighbourShapes` first, then `Level.updateNeighborsAt`.

Both ShulkerBoxBlock versions have the same selectors: `getBlockSupportShape` is full-block `Shapes.block()` only while BE status is exactly CLOSED; for OPENING, OPENED, or CLOSING it returns the 1/16-thick full face plane keyed by `FACING.getOpposite()` (`ShulkerBoxBlock.java`, 1.20.1 lines 228–239; 1.20.2 lines 224–235). Thus, for FACING=EAST, only the WEST-facing support face remains full when not CLOSED; the other five faces cease to be full. The plane shapes are the explicit full-width/full-height sixteenth-thick `Block.box` definitions (1.20.1 lines 51–66; 1.20.2 lines 49–64). `FenceBlock.updateShape` tests `isFaceSturdy(..., FULL)` on the neighbor's opposite face and returns a new direction property from that result (95–104, identical in both versions). A fence north of this east-facing box tests the box's NORTH face; its `SOUTH` property is true when CLOSED and false once BE status is non-CLOSED.

A concrete legal dry setup: box at P with FACING=EAST, oak fence at P.north(), and clear space in the box's eastward opening sweep. `canOpen` checks only the eastward expansion AABB (`ShulkerBoxBlock.java` lines 115–122), so this adjacent fence does not occupy the opening sweep. It is an approximate witness for the stale fence collision-shape bit; exact world collision interactions are not asserted here.

## Notification order and state visibility

`BlockBehaviour.State.updateNeighbourShapes` visits six neighbors synchronously in `UPDATE_SHAPE_ORDER` WEST, EAST, NORTH, SOUTH, DOWN, UP, dispatching `neighborShapeChanged` (1.20.1 lines 79–81, 656–667; same call structure in 1.20.2). The level's collecting neighbor updater runs shape updates immediately when not already draining its queue. It calls the neighbor's `updateShape`, then `Block.updateOrDestroy` stores the returned property state via `setBlock` (1.20.1 `NeighborUpdater.java` 24–38; `CollectingNeighborUpdater.java` 28–31, 48–64, 67–83; `Block.java` 143–169). For the fence, this means the SOUTH boolean is synchronously stored as false on the opening shape notification, and restored true on the closing notification that observes CLOSED.

The added second 1.20.2 operation is distinct: `ServerLevel.updateNeighborsAt` dispatches ordinary `neighborChanged` calls to six neighbors in `NeighborUpdater.UPDATE_ORDER` WEST, EAST, DOWN, UP, NORTH, SOUTH (1.20.1 `ServerLevel.java` 979–986 and `NeighborUpdater.java` 15–30, same behavior in 1.20.2). It runs after the preceding shape-update sweep and fence state storage. Oak Fence has no direct `neighborChanged` override; its connection is selected/stored by `updateShape`, so the extra callback does not add a second fence-connection transition.

The 1.20.2 stale-state interval is source-reachable, not merely a race inferred from unrelated callbacks. On the server, `ServerLevel.blockEvent` queues the event; `runBlockEvents` applies it before entity ticking and before `tickBlockEntities` in the level tick (1.20.1 `ServerLevel.java` 333–375, 1040–1068). Processing the event changes the BE status to OPENING but does not yet update the fence. The subsequent entity phase therefore runs before the first BE animation phase: during that entity phase support queries already see partial support, while the stored fence connection still reflects CLOSED. Then the first BE animation tick advances to 0.1 and the ordered notifications store the new fence state before later entity phases. For a closing from OPENED, the first tick runs with CLOSING and support remains partial; only the terminal tick sets CLOSED and immediately notifies/stores full support, so no entity tick intervenes between CLOSED and the corresponding neighbor update.

On clients, the block-event packet handler invokes `ClientLevel.blockEvent` synchronously once handled (`ClientPacketListener.handleBlockEvent`, 1.20.1 lines 1273–1277). `ClientLevel.tick` ticks client entities before block entities (245–254). Therefore, if the event has been handled before a client simulation tick, that tick's player phase precedes the first shulker BE animation tick just as on the server. The exact packet-arrival position relative to a particular client tick is not established by these source methods; the conditional client window is established, and the server's same-tick entity-before-BE ordering is explicit.

## Movement relevance, kept separate

This is an effective server block-state/neighbor timing fact, not historical server physics: the repository invariant excludes historical movement on logical servers. On the logical client, a legal event-before-tick ordering yields a movement tick where the shulker BE already reports OPENING, but the adjacent fence still stores its CLOSED-derived connection bit; the box's collision `getShape` remains progress-derived and at the pre-animation progress until the BE tick. Thus a one-tick stale secondary fence collision geometry window is objectively reachable client-side under that ordering, while the event-arrival phase is not universally fixed. The native selectors themselves are not different; the changed notification timing is what permits the stale stored fence state. Closing has no corresponding player tick between setting CLOSED and synchronously refreshing the neighbors.
