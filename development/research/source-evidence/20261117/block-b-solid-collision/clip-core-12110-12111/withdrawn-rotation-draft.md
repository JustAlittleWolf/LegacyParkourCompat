# Rotated block collision shape coordinate mapping

1.21.10, Mojmap: `net/minecraft/world/phys/shapes/DiscreteVoxelShape.java`, `rotate(OctahedralGroup)`, lines 23–51; `net/minecraft/world/phys/shapes/Shapes.java`, `rotate(VoxelShape, OctahedralGroup, Vec3)`, lines 296–325.
1.21.11, Mojmap: `net/minecraft/world/phys/shapes/DiscreteVoxelShape.java`, `rotate(OctahedralGroup)`, lines 24–58; `com/mojang/math/OctahedralGroup.java`, `rotate(Vector3i)`, lines 155–161; `net/minecraft/world/phys/shapes/Shapes.java`, `rotate(VoxelShape, OctahedralGroup, Vec3)`, lines 295–317.
Difference: 1.21.10 constructs transformed voxel sizes/cells and coordinate-axis flips by selecting the source axis through `group.permute(targetAxis)` and remapping the group inversion flags through that axis. 1.21.11 rotates signed integer size/cell vectors and applies a fixup for negative dimensions; `Shapes.rotate` now flips the selected coordinate axes using target-axis inversion flags. For a `(2,1,1)` discrete shape with only cell `(0,0,0)` full and `ROT_90_Y_NEG` / `BLOCK_ROT_Y_90`, 1.21.10 places the output cell at `(0,0,1)` in the `(1,1,2)` grid, while 1.21.11 places it at `(0,0,0)`. `Shapes.rotateHorizontal` feeds such rotated shapes into block-facing maps; for example, `DoorBlock` builds `SHAPES` with it and returns the facing-specific shape from `getShape` (both releases `net/minecraft/world/level/block/DoorBlock.java:52,79–83`). The default block collision path returns that block shape (`BlockBehaviour.java:313–315` / `312–314`), so a player sweep intersecting only the changed component can have a different collision result. The fixture confirms the source-level shape difference, not a runtime trajectory.
Movement meaning: This changes a block collision-shape input on some rotated/facing variants before the otherwise unchanged entity axis clipper runs; exact player trajectories and the first patch introduction are unresolved.
