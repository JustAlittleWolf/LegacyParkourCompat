## Changed dependency and route audit

- Skull family: 1.20.2 `AbstractSkullBlock.java` adds `POWERED`, sets it on placement from `hasNeighborSignal`, and updates it in `neighborChanged` (1.20.2 lines 22–29, 64–79; no corresponding 1.20.1 implementation). `SkullBlock.getShape` remains a type-only choice (`SHAPE`/`PIGLIN_SHAPE`); `WallSkullBlock.getShape` remains a `FACING` lookup. Both methods are source-identical across the pair. Inherited placement now carries POWERED, while skull rotation and wall-facing selectors are retained. `AbstractSkullBlock` descendants checked: `PlayerHeadBlock`, `PlayerWallHeadBlock`, `WitherSkullBlock`, `WitherWallSkullBlock`, and `PiglinWallSkullBlock`; the only additional changed hunk was `PlayerHeadBlock` owner-profile UUID initialization. 1.20.2 `SkullBlockEntity.animation` reads POWERED for the animation counter (`SkullBlockEntity.java:92–98`); this is animation/render state and does not enter collision/support shape math.
- Shared shape route: `BlockBehaviour.getCollisionShape` remains `hasCollision ? state.getShape(...) : Shapes.empty()` (both versions, lines 290–292). `BlockBehaviour.BlockStateBase.isFaceSturdy` and its cache route remain source-identical (both versions around lines 807–812 and 858–889). `Block.java` and `BlockState.java` are byte-identical; changed `BlockBehaviour` hunks concern particle flags, Optional API, holder query and naming, not collision/support methods. `BushBlock`, `DoublePlantBlock`, `BaseEntityBlock` and the relevant head/wall subclasses are byte-identical where checked.
- Shulker loaded route: `ShulkerBoxBlock.getBlockSupportShape` (1.20.1 lines 229–233; 1.20.2 lines 225–229) still selects the open support envelope only from BE `!isClosed()` and the opposite `FACING`; `getShape` (1.20.1 lines 236–241; 1.20.2 lines 232–237) still derives collision envelope from `getBoundingBox`. BE `getProgress`, `getBoundingBox`, and `moveCollidedEntities` preserve the same progress interpolation, swept-AABB and displacement expression. The indexed loop became enhanced-for over the same `List<Entity>` with the same filter and move call.
- Shulker neighbor-update timing did change. In 1.20.1 `triggerEvent` calls `updateNeighbourShapes` immediately when `openCount` changes to 0 or 1 (`ShulkerBoxBlockEntity.java:130–145`). In 1.20.2 those calls are removed; `updateAnimation` calls them on the first opening/closing tick when `progressOld` is 0/1, and at the animation endpoint (`:62–98`). `doNeighborUpdates` also adds `Level.updateNeighborsAt` (`:153–156`). This shifts adjacent-shape/redstone notification timing by a tick on the ordinary loaded route and adds a block-neighbor notification. The Shulker direct collision/support selector output and push formula are unchanged, but secondary neighbor-state effects on a particular contraption are outside this bounded shape-provider audit and are not closed here.
- Shulker comparator route: 1.20.1 `ShulkerBoxBlock.getAnalogOutputSignal` calls `getRedstoneSignalFromContainer`; 1.20.2 calls `getRedstoneSignalFromBlockEntity`, whose wrapper dispatches to the same Container method. The fullness formula was rewritten: old code returns `floor(f * 14) + 1` iff a slot is nonempty; new `Mth.lerpDiscrete(f,0,15)` is `floor(f * 14) + 1` iff `f > 0`. For a valid Shulker container, `f > 0` iff any slot has positive count, so comparator output is identical. This loaded route was followed because it is called by the changed provider; no comparator-strength difference was found for ordinary Shulker inventory.
