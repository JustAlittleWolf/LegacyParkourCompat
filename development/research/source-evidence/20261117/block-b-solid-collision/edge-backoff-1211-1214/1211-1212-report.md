# 1.21.1–1.21.2 edge-probe/support gate coverage

## Verdict

No difference found in the bounded `Player.maybeBackOffFromEdge` operation or its checked support, projection, and collision-shape dependencies. The three horizontal probes retain the same order and math, and the ordinary loaded, entity-clear, border-clear path reaches the same block-shape result for a full cube and a dry bottom slab. This does not close final movement parity: the enclosing `Entity.move` continuation changes after `collide` in 1.21.2 (unresolved below).

## Compared slices and result

- `net/minecraft/world/entity/Entity.java`: `move` dispatches to `maybeBackOffFromEdge` before `collide` in both versions (1.21.1 lines 617–618; 1.21.2 lines 639–640). The Player override is therefore the operation under comparison for the requested SELF/PLAYER input.
- `net/minecraft/world/entity/player/Player.java`: 1.21.1 `maybeBackOffFromEdge` lines 1070–1119; 1.21.2 lines 1066–1115. The gate is identical: not flying; requested Y is not positive; mover is SELF or PLAYER; `isStayingOnGroundSurface()`; and `isAboveGround(maxUpStep)`. `isStayingOnGroundSurface()` is `isShiftKeyDown()` in both (lines 338–340 and 345–347).
- The body makes three sequential probes in both releases: X only, then Z only, then both axes. Each probe uses `canFallAtLeast`; each nonzero component is reduced by `Math.signum(component) * 0.05`. A component with absolute value at most `0.05` is set to zero; the diagonal loop applies that rule independently to X then Z. The returned vector retains the original Y. The statements, types, comparisons, and operation order are identical.
- `isAboveGround` is identical (1.21.1 lines 1121–1123; 1.21.2 lines 1117–1119): on-ground suffices; otherwise fall distance must be below the step height and the downward probe by `stepHeight - fallDistance` must collide. `canFallAtLeast` is identical (1.21.1 lines 1125–1128; 1.21.2 lines 1121–1124): it translates both X bounds by `dx`, both Z bounds by `dz`, and spans Y from `minY - stepHeight - 1.0E-5F` through `minY`, then calls `level().noCollision(this, box)`.
- `net/minecraft/world/level/CollisionGetter.java`: 1.21.1 lines 46–63 and 1.21.2 lines 48–69 preserve block, entity, then world-border rejection. In 1.21.2 the two-argument `noCollision(entity, box)` delegates to the three-argument overload with `false`, which selects `getBlockCollisions`, not block-and-liquid collisions. For the assigned ordinary loaded case, an entity-clear box away from the border therefore reaches the same block collision query; nonempty entity collisions reject, and a nearby overlapping border shape rejects.
- `net/minecraft/world/level/BlockCollisions.java`: the per-entity context, cell cursor bounds, full-block fast path, and nonempty shape intersection are the same (1.21.1 lines 32–46, 64–89; 1.21.2 lines 32–50, 68–94). The 1.21.2 overload stores the same `CollisionContext.of(entity)` for this call. Its provider-result path is unchanged.
- `net/minecraft/world/level/block/state/BlockBehaviour.java` and `net/minecraft/world/level/block/SlabBlock.java`: the default collision provider still returns the state's shape when collision is enabled (1.21.1 `BlockBehaviour` lines 308–310; 1.21.2 lines 312–314). `SlabBlock.getShape` returns `Shapes.block()` for DOUBLE and `BOTTOM_AABB` for BOTTOM in both (1.21.1 lines 56–66; 1.21.2 lines 59–69); `BOTTOM_AABB` is `Block.box(0, 0, 0, 16, 8, 16)` in both (lines 32–33 and 35–36). Thus the checked full-cube and dry bottom-slab provider shapes are identical.

## Lawful case and movement meaning

A crouching, nonflying, nonriding player on a full-cube floor or dry bottom slab, with `onGround()` true, can enter the gate while moving horizontally with SELF or PLAYER and nonpositive Y. When the translated-and-downward probe clears the support edge, the same ordered probes shave signed 0.05 increments from X, then Z, then both until the candidate no longer clears the support probe or the relevant component reaches zero. The function consequently trims the requested horizontal displacement while preserving its vertical component. This is a source-derived reachable case; no runtime trajectory was tested.

## Coverage boundary and unresolved point

Examined: the edge-backoff override and its three loops; crouch and above-ground eligibility; projected probe axes/epsilon; the ordinary `noCollision` block/entity/border path; block collision iteration; and default, full-cube, and dry-bottom-slab shape providers.

Not examined: unrelated movement operations, custom/state-dependent collision providers beyond the named examples, unloaded-chunk behavior, the step solver, support-position logic, and autojump. These were outside the assignment or needed no resolution for the stated loaded ordinary case.

Unresolved adjacent dependency: after `collide`, `Entity.move` has a changed acceptance condition. In 1.21.1 the position update is guarded by `collided.lengthSqr() > 1.0E-7` (lines 618–620); in 1.21.2 it is guarded by `collided.lengthSqr() > 1.0E-7 || requested.lengthSqr() - collided.lengthSqr() < 1.0E-7` (lines 640–642). The edge-backoff return and its checked gates are unchanged, but this downstream difference was not analyzed for final position-write effects, so whole-move parity for this case remains open.
