## Findings and verdicts

### 1.20.6 → 1.21 — no difference found in the bounded operation

**Accepted.** I independently retraced the ordinary player edge-backoff operation and confirm the report's no-difference verdict for this scope. `Player.maybeBackOffFromEdge`, `isAboveGround`, and `canFallAtLeast` have the same bodies: 1.20.6 `Player.java` lines 1067–1125 and 1.21 lines 1070–1128. The crouch predicate `isStayingOnGroundSurface()` returns `isShiftKeyDown()` at 1.20.6 line 330 and 1.21 line 338. `Entity.move` calls the hook after the stuck-speed multiplier and before `collide`: 1.20.6 lines 609–617; 1.21 lines 610–618.

The operation gates on not flying, nonpositive Y motion, `MoverType.SELF` or `PLAYER`, the ground-surface predicate, and `isAboveGround(maxUpStep)`. It snapshots X/Z, computes signed double `0.05` steps, reduces X first and Z second, then reduces remaining diagonal motion; axis loops zero a remainder at absolute magnitude `<= 0.05`. The returned vector retains original Y. `isAboveGround` is `onGround()` or, while `fallDistance < step`, a negative `canFallAtLeast(0, 0, step - fallDistance)` result. `canFallAtLeast` queries `noCollision(this, AABB(minX + dx, minY - step - 1.0E-5F, minZ + dz, maxX + dx, minY, maxZ + dz))`; the epsilon is a float literal promoted in the double expression.

### 1.21 → 1.21.1 — no difference found in the bounded operation

**Accepted.** The complete `Player.java` and `Entity.java` source files have identical SHA-256 values at 1.21 and 1.21.1, so the gate, reduction loops, helper methods, and movement call order are byte-identical for this pair. The bounded support/collision dependencies are also byte-identical: `CollisionGetter.java` (`f21daa1e…`), `BlockCollisions.java` (`3313a38f…`), and `SlabBlock.java` (`2085c939…`). The `AABB.intersects` method at 1.21.1 lines 237–239 is the same strict interval comparison as at 1.21 lines 237–239; the collision-shape delegation is likewise unchanged (`BlockBehaviour.java` lines 308–310).

## Applicability witness and dependency audit

The stated support witness is valid in a controlled local world: one support block, air to the sides, no colliding entities, loaded queried blocks, and a distant world border. For a player box resting on a full cube with `minY = 1`, the probe extends from `1 - step - 1.0E-5F` up to `1`, so it has positive vertical overlap with the cube below. For a dry bottom slab with `minY = 0.5`, it similarly extends below `0.5` into the slab's `[0, 0.5]` collision shape. The horizontal projection overlaps the support until the footprint clears it, making `noCollision` false while supported and true after clearing in this controlled world. `SlabBlock.getShape` returns `BOTTOM_AABB` for `TYPE=BOTTOM` (lines 32, 56–65 at both 1.21 endpoints); the collision shape delegates to the state shape when collision is enabled. Waterlogged state is not consulted by this shape branch.

`CollisionGetter.noCollision` checks block collisions, entity collisions, then (for a non-null entity) the world border; `getBlockCollisions` supplies `BlockCollisions`. The iterator queries each state collision shape and intersects it with the projected query shape. For full cubes it uses strict `AABB.intersects`; for the slab's non-full shape it uses `Shapes.joinIsNotEmpty(..., BooleanOp.AND)`. The query extends downward by the step and epsilon, so it has positive volume overlap with either support shape rather than merely touching its top face. The unchanged AABB intersection uses strict interval overlap on all three axes.

## Scope limit

This verdict covers only the ordinary player crouch/SELF-or-PLAYER edge-backoff gate, its signed X/Z/diagonal `0.05` probe reductions, and the projected-AABB `noCollision` support check for the stated dry bottom slab/full-cube cases. It does not assess the step-up solver, post-move support tracking, AutoJump, other movement operations, runtime parity, or an exact intermediate patch boundary.
