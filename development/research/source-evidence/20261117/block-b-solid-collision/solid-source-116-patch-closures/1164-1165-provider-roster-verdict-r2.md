# 1.16.4 → 1.16.5 Mojmap solid collision/support audit

## Verdict

**No source-confirmed difference affects ordinary solid-block player collision or support in this pair.** The exact Java source path roster is identical (3,523 paths each); 3,519 paired files have identical SHA-256, and the only four content changes are `DetectedVersion.java`, `core/Direction.java`, `PoiSection.java`, and `BaseFireBlock.java`. The changed Direction API only feeds BaseFireBlock's portal-axis check. PoiSection is villager POI bookkeeping. DetectedVersion changes release metadata. BaseFireBlock's candidate change affects portal creation eligibility/orientation, not the solid collision/support shape returned by fire.

This is a Java-source bounded verdict. Exact version-root evidence exists for both sides: 1.16.4 `mojmap/.decompile-provenance.json`, and 1.16.5 `mojmap.ready.json`, `mojmap.provenance.json`, `mojmap.sources.sha256`, and `artifacts.sha256`. The 1.16.5 readiness marker identifies version 1.16.5/Mojmap and its complete source manifest; all local source hashes and byte count match. Artifact sidecar hashes are recorded as source publication inputs, but this audit did not inspect or re-hash the archived raw artifact binaries. The decompiler outputs contain Java sources only; this audit does not prove parity of external data/resources, registry inputs, or runtime behavior.

## Provenance correction and limits

The 1.16.5 source tree is not an unprovenanced legacy directory: its exact-version-root readiness and hash manifests independently bind the current 3,523 local Java files to a source-manifest digest. This corrects the initial report. The sidecar `artifacts.sha256` lists input artifact digests, and the readiness file binds the manifest digest and raw client digest; this check verified sidecar file hashes and local Java source hashes, not the archived raw binary files themselves. This distinction leaves the Java roster verdict intact while correcting the source identity claim.

## Changed operations and movement relevance

- `core/Direction.java`: the only source delta is the new `Direction.Plane.getRandomAxis(Random)` method (1.16.5 line 428). It chooses from the plane's existing `axis` array; `HORIZONTAL` has X and Z. Existing neighboring `getRandomDirection(Random)` (face selection from `faces`) is unchanged. A source-wide call search finds the new method used only by `BaseFireBlock.isPortal`; no block collision/support provider, cache, player tick, or block-state predicate calls it. Other `getRandomDirection` uses are random feature/structure placement and do not change here.
- `BaseFireBlock.java`: `getShape(...)` is unchanged and returns `DOWN_AABB` in both files (1.16.4 lines 45–47; same method in 1.16.5). The changed `isPortal(...)` path (1.16.4 line 185; 1.16.5 lines 185–191) chooses the counter-clockwise axis for horizontal directions as before; for a non-horizontal direction, 1.16.5 chooses a random horizontal axis rather than applying `getCounterClockWise()` to a vertical direction. This gates `PortalShape.findEmptyPortalShape`, i.e. fire-to-portal creation. It does not alter collision/support geometry. `Blocks.java` is byte-identical and registers FIRE and SOUL_FIRE with `.noCollission()`; `BlockBehaviour.getCollisionShape` therefore returns `Shapes.empty()` for fire even though BaseFireBlock's separate outline `getShape` is a thin slab. Fire damage/ticks and portal transfer are outside this solid-shape verdict.
- `PoiSection.java`: duplicate POI registration behavior changes from always throwing on a different type at an already occupied section-relative position (1.16.4 lines 69–84) to throwing only when `SharedConstants.IS_RUNNING_IN_IDE`, otherwise logging and replacing/inserting the record (1.16.5 lines 69–91). It changes villager POI consistency recovery; it supplies no player collision/support shape or movement predicate.
- `DetectedVersion.java`: built-in name, world version, and release target values change from 1.16.4/2584 to 1.16.5/2586. This identifies the game release and has no solid collision/support operation.
