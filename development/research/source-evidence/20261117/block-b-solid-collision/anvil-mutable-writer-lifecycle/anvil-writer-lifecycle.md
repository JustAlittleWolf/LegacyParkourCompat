## Paired source facts

- **1.8.9** `net/minecraft/block/AnvilBlock.java:67–74`: `updateShape(world,pos)` reads the current block state’s `FACING`, then mutates this block object’s shape via `setShape`: X-axis sets local bounds `(0,0,0.125)–(1,1,0.875)`; Z-axis sets `(0.125,0,0)–(0.875,1,1)`. `Block` owns these six mutable fields (`Block.java:292–299`). The singleton block’s ray and collision operations therefore share the last-written bounds.
- **1.8.9 ray writer:** `Block.java:456–465` calls `updateShape(world,pos)` at the start of `rayTrace`, then its intersection calculations read `this.min*`/`this.max*`. `World.java:633–652, 739–750` walks the ray’s block cells and dispatches `block.rayTrace(...)`; a successful hit returns immediately. A player ray therefore writes bounds only when it visits an Anvil cell, and the visited Anvil’s facing determines the shared values.
- **1.8.9 movement reader:** `Block.java:339–350` builds a fresh world-space collision `Box` from the current shared bounds and the queried block position; it does not refresh those bounds from the queried state. `World.java:891–925` gathers such boxes for the requested swept player box. `Entity.java:439–459` queries `world.getCollisions` once for the movement-expanded box, then clips Y, X and Z against that list. `Box.java:93–110` clips positive X movement to the obstacle’s `minX` when X/Z/Y overlap.
- **1.9 replacement:** `AnvilBlock.java:32–34, 97–100` declares immutable `SHAPE_X` and `SHAPE_Z` boxes and selects one from the supplied state’s `FACING`. `Block.java:313–323, 326–327, 434–439` obtains collision and ray shapes from that state; `World.java:648–654` invokes `blockState.rayTrace`. `StateDefinition.java:348–364` forwards those calls with the state object. In this paired source, ray selection for one Anvil cannot leave orientation-dependent bounds for a later Anvil collision query.

## Concrete render-independent event order

The 1.8.9 source permits the following bounded local-player path; it does not need a renderer pass or a frame-frequency assumption:

1. At feet position `(0.8, 1.0, 0.75)`, the local player stands partly over an X-facing Anvil A at block `(0,0,0)`. Its X shape spans the player’s center and supports the feet. A Z-facing Anvil B is at `(1,1,1)`, with an ordinary solid support beneath at `(1,0,1)`. The player width is `0.6` (`Entity.java:143–144`), so the body box is approximately `x=[0.5,1.1]`, `z=[0.45,1.05]`. The player is clear of B at rest: B’s correct local shape would start at `x=1.125,z=1.0`.
2. Aim straight down. In `Minecraft.runGame` the fixed-tick loop calls `Minecraft.tick()` before rendering (`Minecraft.java:804–832`, then `840–854`). Within that tick, `Minecraft.tick()` calls `gameRenderer.pick(1.0F)` (`Minecraft.java:1303–1318`). `GameRenderer.pick` uses `getCamera().rayTrace(reach,tickDelta)` (`GameRenderer.java:318–326`); `Entity.rayTrace` traces from the camera eye through `World.rayTrace(..., allowHitInStartPosition=true)` (`Entity.java:1029–1033`). The vertical ray crosses the top of A at `(x≈0.8,z≈0.75)`, inside A’s X shape. The hit dispatch calls `AnvilBlock.updateShape` for A, which writes the shared X bounds, and returns the actual block hit.
3. With no use/attack input, the calls between pick and entity ticking are bounded: `ClientPlayerInteractionManager.tick` only updates the selected hotbar slot and network connection (`ClientPlayerInteractionManager.java:249–256`); later, `gameRenderer.tick` (`Minecraft.java:1619–1622`; `GameRenderer.java:256–302`) and `worldRenderer.tick` (`Minecraft.java:1624–1627`; `WorldRenderer.java:942–947`) have no Anvil `updateShape` call. `world.tickEntities` follows (`Minecraft.java:1629–1636`); choose a scene with no other entity or particle action that writes Anvil bounds before the local player tick. The local player is ticked as an entity and its normal living movement reaches `Entity.move` (`LocalClientPlayerEntity.java:104–115`; `World.java:1205–1220, 1330–1347`; `LivingEntity.java:1140–1165`). The main loop renders only after the fixed-tick loop (`Minecraft.java:830–832, 840–854`), so this event order is inside the simulation tick and does not require a render pass. `renderWorld` does pick again (`GameRenderer.java:1012–1019`), but that is after the movement in this example.
4. Let ordinary SELF movement request `dx=+0.1,dz=0` while the player stands at that position. Its expanded query box reaches `x=1.2` and still has `z.max=1.05`. If B were queried by its own state, its translated Z box would be `x=[1.125,1.875], z=[1,2]`, so it intersects the swept player box. `World.getCollisions` would include B, and the positive-X clip would reduce `dx` to `1.125−1.1=0.025`. With the immediately preceding ray’s shared X bounds, the same B is instead constructed as `x=[1,2], z=[1.125,1.875]`, which misses the query at `z.max=1.05`; absent other obstacles, the X movement remains `0.1`. The support below B only touches the query at `y=1` and does not intersect it.

## Applicability gate

This establishes a **conditional 1.8.9 player movement witness**, not unconditional behavior for every client tick. It requires the local camera pick to hit an X-facing Anvil after the last shape write that could affect movement, and requires no intervening writer before the SELF collision query. Known competing writes include Anvil `updateShape` calls reached through other block rays, projectile/block interactions or particles, and renderer block-shape work; the player’s own relevant pick is tick-scheduled as well as render-scheduled, while `renderWorld` calls pick again (`GameRenderer.java:1012–1019`). The bounded event uses a no-input, no-local-projectile/particle/block-interaction interval and the fixed tick order above. Any external event that writes another Anvil orientation between the pick and movement invalidates this particular witness; its reachability in a populated scene is not established here. The cause of the ray visit is the ordinary player camera pick, but the source alone does not establish that arbitrary camera orientations, competing ticks, or all schedules produce stale collision bounds.

## Result

Source confirms mutable Anvil bounds shared between ray tracing and player collision in 1.8.9, replaced by state-derived boxes in 1.9. The explicit tick-scheduled camera-pick-before-SELF-move path makes the dependency independent of render rate. Applicability remains gated by absence of intervening Anvil shape writers, as bounded above.
