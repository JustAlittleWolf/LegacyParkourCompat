## Paired source facts

- **1.8.9 writer:** `AnvilBlock.updateShape` reads the facing at the supplied world position and mutates six bounds fields on the shared block object. X-facing sets `(0,0,0.125)–(1,1,0.875)`; Z-facing sets `(0.125,0,0)–(0.875,1,1)` (`AnvilBlock.java:67–74`; fields assigned by `Block.java:292–299`). `Block.rayTrace` calls this writer before testing the ray against those fields (`Block.java:456–465`). `World.rayTrace` dispatches the ray to each visited block and returns when one hits (`World.java:633–652, 739–750`).
- **1.8.9 reader:** `Block.getCollisionShape` constructs a positioned `Box` from the current mutable bounds and does not refresh them from the queried block state (`Block.java:339–350`). `World.getCollisions` collects those boxes (`World.java:891–925`). `Entity.move` builds a movement-expanded query and clips Y, then X, then Z (`Entity.java:439–459`); positive X clipping uses the obstacle’s `minX` only when the current player box overlaps it on Y and Z (`Box.java:93–110`).
- **1.9 replacement:** `AnvilBlock` declares immutable X and Z boxes, selected by the passed state’s `FACING` (`AnvilBlock.java:32–34, 97–100`). Collision and ray calls forward the state through `Block` and `StateDefinition` (`Block.java:313–328, 434–439`; `StateDefinition.java:348–364`). A ray against one Anvil therefore does not leave orientation-dependent shared bounds for another state’s collision query.

## Conditional player witness

A concrete geometry supports a difference in 1.8.9 without requiring a main-thread render pass:

1. Place X-facing Anvil A at `(0,0,0)`. Put Z-facing Anvil B at `(1,1,1)` and an ordinary solid support below B at `(1,0,1)`. A local player at feet `(0.8,1.0,0.75)` has default width `0.6` and height `1.8`, giving a body box approximately `x=[0.5,1.1]`, `y=[1,2.8]`, `z=[0.45,1.05]` (`Entity.java:139–145`). A supports the player; B’s correct shape starts at `x=1.125,z=1.0`, so the player is clear of B at rest.
2. With the local player as camera and pitch straight down, the tick-scheduled `GameRenderer.pick(1.0F)` ray from the eye reaches the top of A inside its X-facing footprint. `Minecraft.tick` calls that pick before `world.tickEntities` (`Minecraft.java:1303–1318, 1629–1636`); `GameRenderer.pick` calls the camera’s `rayTrace` (`GameRenderer.java:318–326`), which reaches `World.rayTrace(..., allowHitInStartPosition=true)` (`Entity.java:1029–1033`). The hit dispatch writes X bounds through A’s `updateShape` before returning the hit.
3. The fixed-tick loop runs before the main-thread render in `runGame` (`Minecraft.java:804–832, 840–854`). With lateral input/state requesting `dx=+0.1,dz=0` while the player keeps looking down, the ordinary local-player tick reaches the normal living movement and `Entity.move` (`LocalClientPlayerEntity.java:104–115`; `World.java:1205–1220, 1330–1347`; `LivingEntity.java:1119–1165`). `World.getCollisions` queries a box reaching `x=1.2` and `z.max=1.05`.
4. If B is read by its Z state, its translated box is `x=[1.125,1.875], y=[1,2], z=[1,2]`. It intersects the movement query; positive-X clipping limits the first horizontal path to `1.125−1.1=0.025`. If the shared X bounds from A remain, B is instead constructed as `x=[1,2], y=[1,2], z=[1.125,1.875]` and is absent from the query. Without other obstacles that alter the movement result, that collision query does not clip against B. The support below B touches the player at the bottom face and is not itself a horizontal clip at the unraised position.

## Lifecycle gates required for this witness

The trace establishes only a **conditional, single-tick 1.8.9 player movement witness**. The six shape fields belong to the shared Anvil block object, so a writer for any Anvil may change the values read for both A and B. For the ray-written X bounds to persist until the SELF collision query, all of these conditions are required:

- The camera is the local player, its tick-scheduled pick actually hits X-facing A, and no later pre-move call rewrites the shared Anvil bounds.
- **Rain sampling does not write an Anvil first.** `Minecraft.tick` calls `gameRenderer.tick` before entity ticking (`Minecraft.java:1619–1636`); `GameRenderer.tick` calls `tickRain` (`GameRenderer.java:256–291`). When rain strength is nonzero, that sampling path calls `block.updateShape(world, blockPos3)` for selected non-air precipitation blocks (`GameRenderer.java:1209–1265`). Require clear weather (`getRain(1.0F)==0`) or establish that this tick’s samples select no Anvil.
- **No concurrent Anvil-containing chunk compilation writes the shared fields.** Chunk rendering uses `ChunkRenderDispatcher` workers; `ChunkRenderWorker` calls `RenderChunk.compile`, which dispatches block-model rendering. Anvil’s render path reaches `BlockModelRenderer.render`, whose `updateShape` call is a writer (`ChunkRenderDispatcher.java:25–49`; `ChunkRenderWorker.java:55–75`; `RenderChunk.java:97–151`; `Block.java:253–255`; `BlockRenderDispatcher.java:50–66`; `BlockModelRenderer.java:25–29`). Because every Anvil shares this block object, exclude any active or queued chunk compilation that reaches any Anvil during the interval, not only compilation of A or B. The shape fields have no synchronization in the inspected source; the main-thread tick-before-render order cannot exclude a worker race.
- No intervening processed task or packet changes the setup or starts relevant chunk work; no attack/use/item action, projectile/entity ray, or other entity tick writes the shared Anvil bounds before the local player’s turn. `world.tickEntities` iterates entities in its list, so other entity behavior and ordering remain dependencies unless the scene excludes such writers.
- No unrelated writer reaches the shared bounds in the interval. Other source-confirmed writers include main-thread block-model/outline rendering, frame-scheduled picking, arrow block checks, rain-splash particle ticks and dye particle setup. The particle tick pass follows entity movement in this main tick (`Minecraft.java:1670–1672`), but its source presence still matters to later ticks. Main-thread rendering after the tick loop does not prove that worker compilation or other scheduled work was absent before movement.

The concrete setup therefore demonstrates a legal source-level order only under an explicit quiet interval: a successful pick on A, clear weather or no Anvil sampled by rain, no other pre-move block/entity writer, and no active/queued concurrent compilation that updates Anvil bounds. Source review does not establish how often a populated client satisfies those conditions, general tick determinism, or parity across arbitrary schedules. No unconditional parity claim follows.
