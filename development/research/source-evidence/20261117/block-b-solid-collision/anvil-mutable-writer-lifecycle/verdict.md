# Independent review: 1.8.9–1.9 Anvil mutable-writer lifecycle

**Disposition:** The mutable-bounds source difference is confirmed, and the scratch's geometric witness is valid. The event-order conclusion needs two explicit gates before it is accepted as a bounded source witness: no rain-sampling write and no concurrent Anvil-containing chunk compilation. The scratch currently says `GameRenderer.tick` has no Anvil writer and that no render-pass timing is needed; both statements omit real writer paths.

## Confirmed difference and geometry

In 1.8.9, `AnvilBlock.updateShape` reads the facing at the supplied position and writes six shape fields on the shared block object: X-facing uses `(0,0,0.125)–(1,1,0.875)`; Z-facing uses `(0.125,0,0)–(0.875,1,1)` (`AnvilBlock.java:67–74`, `Block.java:292–299`). `Block.rayTrace` refreshes those fields before intersecting the ray (`Block.java:456–465`). By contrast, `Block.getCollisionShape` copies the current fields into a positioned box without refreshing from the collision target’s state (`Block.java:339–350`). `World.getCollisions` calls that collision path; `Entity.move` uses the resulting list and clips Y, then X, then Z (`World.java:905–925`; `Entity.java:439–459`).

The scratch’s setup is geometrically consistent with that behavior. At feet `(0.8,1.0,0.75)`, the player’s default `0.6 × 1.8` AABB is `[0.5,1.1] × [1,2.8] × [0.45,1.05]` (`Entity.java:139–145`). X-facing Anvil A at `(0,0,0)` overlaps the footprint and supports the player. The downward camera ray intersects A’s top within its X bounds. Z-facing Anvil B at `(1,1,1)` has the correct box `[1.125,1.875] × [1,2] × [1,2]`; the player is clear of it at rest by `0.025` on X. A `+0.1` X swept box overlaps B’s X, Y and Z intervals, so a state-correct query clips X movement to `1.125−1.1 = 0.025`. If A’s ray left the shared X bounds in place, B instead yields `[1,2] × [1,2] × [1.125,1.875]`, outside the swept box’s `z.max=1.05`, so B is absent from the collision list. The support block below B only touches the player’s bottom face and does not block the horizontal clip.

The scheduled camera path is real: `Minecraft.tick()` calls `gameRenderer.pick(1.0F)` before entity ticking (`Minecraft.java:1303–1318`, `1635`); `GameRenderer.pick` ray-traces the camera (`GameRenderer.java:318–326`), `Entity.rayTrace` uses the exact eye position and rotation at delta `1.0F` and calls `World.rayTrace(..., allowHitInStartPosition=true)` (`Entity.java:1029–1033`), and the world ray traversal dispatches each visited Anvil through `Block.rayTrace` (`World.java:633–652, 739–750`). Pitch straight down can hit A; lateral input can request +X movement while retaining that view direction (movement uses the player’s yaw and sideways/forward input: `LivingEntity.java:1119–1140`; `Entity.java:844–859`).

In 1.9 the two Anvil boxes are immutable constants selected by `state.get(FACING)` (`AnvilBlock.java:32–34, 97–100`). `Block.getCollisionShape` and ray tracing use the supplied state’s shape (`Block.java:313–328, 434–439`; `StateDefinition.java:348–364`). The prior ray therefore cannot leave an orientation-dependent shared box for B’s collision query.

## Required lifecycle correction

1. **Rain is an in-tick writer.** `Minecraft.tick` calls `gameRenderer.tick()` before `world.tickEntities()` (`Minecraft.java:1619–1636`). `GameRenderer.tick()` calls `tickRain()` (`GameRenderer.java:256–291`). When rain strength is nonzero, `tickRain()` samples nearby precipitation blocks and calls `block.updateShape(world, blockPos3)` on every selected non-air block before producing its drop particle (`GameRenderer.java:1209–1265`). Either require clear weather (`getRain(1.0F) == 0`) for this witness, or prove that none of those samples is an Anvil in that tick. The draft’s statement that the renderer tick has no Anvil writer is false as an unconditional statement.
2. **Chunk model compilation can race the tick.** `ChunkRenderDispatcher` starts two `ChunkRenderWorker` threads (`ChunkRenderDispatcher.java:25–49`). A worker calls `RenderChunk.compile`, which iterates states and calls `BlockRenderDispatcher.render` (`ChunkRenderWorker.java:55–75`; `RenderChunk.java:97–151`). Anvil inherits render type 3 (`Block.java:253–255`), so the dispatcher reaches `BlockModelRenderer.render`, whose first action is `block.updateShape(world,pos)` (`BlockRenderDispatcher.java:50–66`; `BlockModelRenderer.java:25–29`). This is a concurrent writer to the same Anvil block object; no lock protects its six shape fields. A chunk compile containing A or B can overwrite X bounds after the camera pick and before SELF collision. The witness must exclude a relevant active/queued chunk compile during that interval. Because chunk tasks are enqueued by renderer/chunk work and execute on workers, the main thread’s “render happens after the tick loop” order does not by itself exclude this race.

Other reachable writers are also source-confirmed: ordinary render block-outline and model work (`WorldRenderer.java:1675–1692`; `BlockModelRenderer.java:25–29`), frame-scheduled `pick` (`GameRenderer.java:1012–1019`), in-ground arrow checks (`ArrowEntity.java:157–164`), rain-splash particle ticks (`RainSplashParticle.java:49–54`), and dye particle setup (`DyeItem.java:98–106`). The particle manager ticks after entity movement in the main tick (`Minecraft.java:1670–1672`), so that specific particle pass is not an in-tick pre-move writer. Arrow/projectile ray traces and other nearby entity ray queries can write earlier depending on entity tick order; exclude those for the bounded event. Suppress attack/use/item actions that change the scene, and keep the relevant chunks and both facing states loaded and unchanged.

Main-thread rendering occurs after the fixed-tick loop (`Minecraft.java:830–832, 840+`), and the tick-scheduled pick overwrites earlier state if it still hits X-facing A. Thus the supplied event can be independent of *main-thread frame rendering* under the stated conditions. It is not independent of renderer scheduling as a whole: a chunk worker can run concurrently, and prior render passes affect the shared value whenever the next tick’s pick does not hit an Anvil. Main-thread packet tasks are drained before the tick loop (`Minecraft.java:819–832`); packet/chunk changes can still alter the setup or enqueue worker compilation for this or a later tick. No source-only argument establishes the absence of such external work in a populated runtime.

**Final audit result:** retain the 1.8.9→1.9 source difference and the scratch geometry. Amend the applicability gate to require clear weather (or no Anvil selected by rain sampling), no other pre-move Anvil writer, and no concurrent chunk compilation touching the tested Anvils. Treat this solely as a conditional, single-tick movement witness; it does not show generally deterministic stale bounds or general tick parity.
