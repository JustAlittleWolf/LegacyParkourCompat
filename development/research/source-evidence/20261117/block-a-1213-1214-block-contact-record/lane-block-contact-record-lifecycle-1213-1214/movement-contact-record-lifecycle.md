# Block-contact movement record lifecycle

## 1.21.3 → 1.21.4

1.21.3, Mojmap: `net/minecraft/world/entity/Entity.java`, `movementThisTick`, `move`, `applyEffectsFromBlocks`, `recordMovementThroughBlocks`, and `checkInsideBlocks` (lines 250, 619–769, 1034–1084, 2721–2732, 3608–3609).
1.21.4, Mojmap: `net/minecraft/world/entity/Entity.java`, corresponding members (lines 250, 627–780, 1046–1095, 2749–2760, 3632–3633).

**Movement records.** In both releases `Entity` owns a per-instance `movementThisTick` list (1.21.3 line 250; 1.21.4 line 250) of `Movement(Vec3 from, Vec3 to)` records (lines 3608/3632). The overload `applyEffectsFromBlocks(Vec3, Vec3)` appends exactly the supplied pair after the optional `stepOn` callback. Its no-argument overload supplies `oldPosition()` and current `position` (1.21.3 lines 736–749; 1.21.4 lines 747–760). `oldPosition()` returns the stored `xOld/yOld/zOld`; the destination is the entity's current actual `position`. The ordinary position write remains `Entity.move` → collided displacement → `setPos(...)` (1.21.3 lines 619–646; 1.21.4 lines 627–656); `setPos` updates raw position and bounding box (1.21.3 lines 399–404; 1.21.4 lines 399–408). Neither `Entity.move` nor `LocalPlayer.move` writes a movement record.

The explicit public `recordMovementThroughBlocks(from,to)` appends another record directly (1.21.3 lines 1034–1035; 1.21.4 lines 1046–1047). This API is not called from either inspected `Entity.move` or `LocalPlayer.move`; direct server call-site bodies are excluded. The `MoverType.PISTON` branch in `Entity.move` applies `limitPistonMovement` and returns early for a zero result before the normal movement pipeline (1.21.3 lines 622–626; 1.21.4 lines 630–634). This piston-specific gate is unchanged in the pair and does not itself append a record. Otherwise the movement type flows through the ordinary position update, still without a list write.

**List lifecycle difference.** 1.21.3 appends the current old-position→current-position record, passes the mutable accumulated list directly into `checkInsideBlocks`, computes the fire/lava-state predicate, then clears `movementThisTick` (lines 740–752). 1.21.4 appends the same record, snapshots the whole accumulated list with `List.copyOf`, clears the mutable list before invoking `checkInsideBlocks(snapshot, ...)`, then performs the predicate and clears `blocksInside` (lines 751–763). Thus callback-time additions/clears cannot mutate the active iteration in 1.21.4 and new appends after the pre-check clear remain in the fresh accumulator; 1.21.3 checks the live list and clears it only after that check. Both releases also clear `movementThisTick` in `teleportSetPosition` after position/orientation/delta-movement reset (1.21.3 lines 2721–2732; 1.21.4 lines 2749–2760).

**Record-specific bounds difference.** 1.21.3 computes one `getBoundingBox().deflate(1.0E-5F)` before iterating records, then uses that same current entity AABB for every `from`/`to` segment (lines 1038–1046). 1.21.4 instead computes `makeBoundingBox(to).deflate(1.0E-5F)` inside the movement-record loop (lines 1050–1059), so each stored segment's destination supplies the swept AABB endpoint. `AABB` helper source is byte-identical in these releases (same source hash): no change to `deflate`, `move`, or `expandTowards` was found in the reviewed helpers.

Movement meaning: The callback consumer now uses a segment-endpoint-specific entity AABB and checks a snapshot of accumulated movement records cleared from the live list before callbacks. For the ordinary LocalPlayer movement path, the inspected tick appends one old-position→final-position record after travel and no per-move record append was found; the bound AABB difference alone has no demonstrated effect for that single segment. Additional accumulated segments could be sensitive to the changed per-record bounds and list-consumption timing, but no additional in-scope LocalPlayer writer was found.

## Callback consumer contract

`checkInsideBlocks` iterates each `Movement`, passes its `from`, `to`, and selected AABB to `BlockGetter.boxTraverseBlocks`, then preserves the same alive/non-air/visited-state gates and `entityInside` → `onInsideBlock` callback order in both releases. The independent cell-traversal delta is recorded in `movement-contact-block-cell-traversal.md`; no solid collision outcome is assessed here.

## Local-player reachability and closed no-diff gate

`LocalPlayer.tick` calls `super.tick` (1.21.3 line 191; 1.21.4 line 195, after `hasClientLoaded()`), through `AbstractClientPlayer` → `Player` → `LivingEntity`. `Player.tick` delegates to its superclass (1.21.3 line 280; 1.21.4 line 283); `LivingEntity.tick` executes `travel(...)` and then invokes `applyEffectsFromBlocks()` under `!level.isClientSide() || isControlledByLocalInstance()` (1.21.3 lines 2774–2777; 1.21.4 lines 2785–2788). `LocalPlayer.isEffectiveAi()` returns true (lines 478–480 / 483–485); `Entity.isControlledByLocalInstance()` falls back to that method when the entity has no controlling passenger (Entity lines 3149–3150 / 3173–3174), so the client-side gate is reachable for the local player.

The inspected `LocalPlayer.move` override only calls `super.move` and performs auto-jump/walk-distance updates; it contains no record append in either release (1.21.3 lines 873–881; 1.21.4 lines 903–911). For this ordinary local-player tick path, the in-scope automatic append is after travel and uses the final current position as `to`; no per-axis/per-move writer was found in the inspected client-player or Entity movement methods. The per-record AABB change therefore has no demonstrated divergence for that single automatically appended segment when no other in-scope append occurs. This is a bounded no-difference witness for record creation during LocalPlayer movement, not a claim that the separate BlockGetter candidate traversal is unchanged.
