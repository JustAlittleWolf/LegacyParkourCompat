## Loaded-box preflight: exact release boundary and client behavior

- 1.15.2 water sampler `Entity.checkAndHandleWater(Tag<Fluid>)`, `Entity.java:2593-2652`, computes `aABB = getBoundingBox().deflate(0.001)`, floors each minimum and ceils each maximum, then calls `level.hasChunksAt(i,k,m,j,l,n)` before scanning. This six-int gate remains in 1.16.0, 1.16.1, 1.16.2, 1.16.3, 1.16.4, and 1.16.5 inside `Entity.updateFluidHeightAndDoFluidPushing`, lines 2633 or 2641-2651 by patch. 1.17.0 first surveyed source is the first with a different preflight; it and 1.17.1 call `touchingUnloadedChunk()` before the same deflated-box scan. Therefore the release-level change is between 1.16.5 and 1.17.0; the exact new behavior is present in 1.17.0, and remains in 1.17.1.
- The six-int `LevelReader.hasChunksAt` receives `(minX,minY,minZ,maxX,maxY,maxZ)`. In 1.15.2 and 1.16.5 its first condition is `maxY >= 0 && minY < 256`, then it shifts X/Z block coordinates right by 4 and checks every inclusive chunk coordinate. With the sampler’s rounded arguments this means `ceil(deflated.maxY) >= 0 && floor(deflated.minY) < 256`. It is an integer-bound preflight, not a strict geometric overlap test and not a requirement that the full box be inside height limits. If it fails, the subsequent half-open Y loop cannot visit any in-height block Y: below the world its exclusive upper bound is <0; above the world its starting bound is >=256.
- In every surveyed version, `ClientLevel.hasChunk(int,int)` returns true. The six-int preflight’s X/Z component therefore cannot reject an ordinary client; only its old vertical integer-bound conditions can. The 1.17 replacement inflates the un-deflated entity box by `1.0`, computes floor(minX/minZ) and ceil(maxX/maxZ), and invokes four-int `LevelReader.hasChunksAt`; that overload checks inclusive X/Z section coordinates and contains no Y test. Since the receiver is still a `ClientLevel` whose `hasChunk` returns true, the added X/Z rejection is unreachable for local-client entities. This is not historical client chunk admission behavior.
- `LocalPlayer.tick` on both sides itself passes a `BlockPos(x,0,z)` / XZ admission query to the same `ClientLevel.hasChunk` implementation; it does not prevent an ordinary local tick at an out-of-height Y.
- Entity tick wrappers matter for outcome. 1.16.0 first introduces the `fluidHeight.clear()` at the start of `updateInWaterStateAndDoFluidPushing`; 1.16.1–1.17.1 retain it. Thus when the old six-int Y preflight fails, the ordinary tick has already cleared the map; a failed water/lava sample leaves the absent tag value at 0. In 1.17, if the client-only XZ preflight passes while the scan bounds are wholly outside build height, `Level.getFluidState` returns empty and the sampler writes zero. The ordinary wrapper exposes zero on either side. If the scan overlaps in-height cells, the old Y preflight passes and the same cells are sampled. So the 1.17 guard rewrite has an operation-level difference, but no distinct ordinary-client movement result through the wrapper. The old public sampler early-return would preserve a manually/stale-populated map if called in isolation; that is not the ordinary caller path.

## Separate 1.15.2 stale water-height behavior

This is a separate state-model difference from the 1.17 loaded-box predicate change.

In 1.15.2, a successful water scan assigns the primitive `waterHeight` at the end of `checkAndHandleWater` (`Entity.java:2650`). If its six-int preflight returns false, the method exits at `Entity.java:2601-2603`, before that assignment. `updateInWaterState` sets `wasInWater=false` when the sample returns false (`Entity.java:957-972`) but never clears `waterHeight`. In 1.16.0, the fluid-height map and `fluidHeight.clear()` are present before water and lava calls (`Entity.java:947-972`); 1.16+ failed preflight therefore leaves the just-cleared value at the map’s default zero.

The stale primitive can affect ordinary movement in a conditional but physically reachable map case, without a position packet or custom dimension. Use standard 1.15.2 build limits 0..256 and a vanilla water block at Y=0 (a map may place it there; this is not a guarantee about generated terrain). In standing pose, Player dimensions are 0.6 by 1.8 (`Player.java:111`). When the player's feet are at Y=0 and the deflated box overlaps water at Y=0, the sampler records positive `waterHeight`. With feet at Y=0, the deflated max Y is about 1.799; the old preflight only fails below it when `ceil(maxY) < 0`, which requires the following deflated max Y to be at most -1. Thus the tick must move the player downward by about 2.8 blocks. This is physically available after a long fall: air travel updates vertical velocity as `(vy - 0.08) * 0.98`, which approaches -3.92 (`LivingEntity.java:1907-1911`); when the Y=0 sample marks the player in water, the water branch calls `move()` with that current velocity before water drag (`LivingEntity.java:1927-1956`). An entry speed below -2.8 blocks/tick clears the box below the integer gate in one ordinary movement step. At that following tick, `ceil(deflated.maxY) < 0`, the old preflight returns false, and `waterHeight` remains positive while `wasInWater` is reset false. `LocalPlayer.tick` still calls `super.tick()` because `ClientLevel.hasChunkAt(BlockPos(x,0,z))` resolves to `ClientLevel.hasChunk`, which returns true (`LocalPlayer.java:179-197`, `ClientLevel.java:240-242`). Then `LivingEntity.aiStep` checks `waterHeight > 0` in its jump branch without requiring `isInWater`; with a normal jump input, this invokes `jumpInLiquid(FluidTags.WATER)` (`LivingEntity.java:2266-2276`; `LocalPlayer.serverAiStep` supplies `jumping` from input at `LocalPlayer.java:607-618`). That differs from the 1.16 map-cleared path, where the same out-of-height sample leaves water height zero and an airborne jump does not take the stale-water branch.

This witness is conditional on a Y=0 water block and a player reaching it with enough downward velocity. It is not dependent on a custom dimension or network position update. It is plausible for a void/map build with water at the vanilla lower boundary; it should not be generalized to generated worlds whose Y=0 cell is bedrock. The movement consequence is a single-tick false liquid jump while falling below world height, so retain it as a separate bounded finding, not as a consequence of the 1.17 X/Z gate.

## Disposition

The 1.17 sampler preflight switch is an exact-source operation change, but its XZ rejection is source-only/unreachable on ordinary clients and its Y-only delta is neutral through the ordinary wrapper after `fluidHeight.clear()`. Do not submit it as an independent player-movement finding. The separate 1.15.2 primitive stale-water jump survives the normal local-player sequence under the explicit lower-bound water/fall conditions above; its map-clearing counterpart first appears in 1.16.0.
