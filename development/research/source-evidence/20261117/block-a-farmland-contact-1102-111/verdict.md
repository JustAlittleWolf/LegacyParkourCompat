## Source-confirmed behavior

The draft is correct that the farmland fall trigger's gate and numeric predicate are unchanged across this pair. In `FarmlandBlock.onFallenOn`, both versions first require `!world.isClient`, then draw `world.random.nextFloat() < fallDistance - 0.5F`, then test `LivingEntity`, player-or-mobGriefing, and `width * width * height > 0.512F`. 1.10.2 sets the state to dirt; 1.11 calls `setDirt`, which sets dirt, gets the dirt collision shape moved to the block position, and calls `setPosition(entity.x, box.maxY, entity.z)` on every entity returned by `world.getEntities(null, box)`. This Y write preserves the selected entity's X/Z and is not filtered to the callback entity or to players. Sources: 1.10.2 `FarmlandBlock.java:61-70`; 1.11 `FarmlandBlock.java:59-78`.

The same 1.11 helper is also used by `FarmlandBlock.tick` when farmland is dry, moisture is zero, and no crop is above it. In 1.10.2 that same gate directly sets dirt without repositioning entities. Farmland opts into random ticking in both versions; `Block.randomTick` forwards to `tick`, and the compared random-block-tick loop is in `ServerWorld`. Thus the ordinary farmland random-tick reversion path is server-side as well. Sources: 1.10.2 `FarmlandBlock.java:25-28,47-57`; 1.11 `FarmlandBlock.java:23-27,45-54`; both `Block.java` (`randomTick` forwards to `tick`); both `ServerWorld.java:377-392`. The client `ClientWorld` code at `tickAmbienceAndLight` performs ambience work and does not dispatch gameplay random block ticks.

The server-player fall callback route is reachable. Although `ServerPlayerEntity.checkFallDamage` is empty in both versions, the server movement handler calls `player.handleFall(...)` after processing a `PlayerMoveC2SPacket`; `ServerPlayerEntity.handleFall` chooses the support block and explicitly calls `super.checkFallDamage(...)`, reaching `Entity.checkFallDamage` and then the block's `onFallenOn` for a positive fall distance. Sources: 1.10.2 `ServerPlayNetworkHandler.java:367-480`, `ServerPlayerEntity.java:570-598`, `Entity.java:808-817`; 1.11 `ServerPlayNetworkHandler.java:369-482`, `ServerPlayerEntity.java:574-601`, `Entity.java:830-839`.

The local-client route is different: `LocalClientPlayerEntity.tick` runs the client entity tick and then sends its movement to the server. Its local `FarmlandBlock.onFallenOn` call stops at `!world.isClient`, before the random draw, dirt mutation, or `setDirt` position writes. Sources: both versions' `LocalClientPlayerEntity.java` around `tick`/`sendMovementToServer` (1.10.2 lines 152-164, 168-213; 1.11 lines 159-171, 175-220), plus the farmland ranges above.

The dirt block mutation can reach the client. The one-state overload of `World.setBlockState` uses flags `3`; on a populated chunk, the server's block-change listener routes the mutation through `ServerWorldEventListener.notifyBlockChanged` → `ChunkMap.onBlockChanged` → `ChunkHolder.sendChanges`, which emits `BlockUpdateS2CPacket` for one changed block (or batched chunk/block updates). `ClientPlayNetworkHandler.handleBlockUpdate` applies that state through `ClientWorld.setBlockStateFromPacket`. This is block-state synchronization, not a player-position packet. Sources: `World.java` (1.10.2 lines 247-280; 1.11 lines 251-286), both `ServerWorldEventListener.java` (`notifyBlockChanged`), `ChunkMap.java:196-202`, `ChunkHolder.java:150-173`, `ClientPlayNetworkHandler.java` (1.10.2 lines 644-647; 1.11 lines 657-660), and `ClientWorld.java:237-242`.

A server player-position packet is issued by the explicit `ServerPlayNetworkHandler.teleport` path, which updates the server player and sends `PlayerMoveS2CPacket`; `ClientPlayNetworkHandler.handlePlayerMove` applies that packet to the local player. The farmland helper only calls `Entity.setPosition`; it does not invoke `teleport` or send `PlayerMoveS2CPacket`. The ordinary local-player `PlayerMoveC2SPacket` path sends client position to the server, not a server correction to the client. Sources: 1.10.2 `ServerPlayNetworkHandler.java:494-515`, `ClientPlayNetworkHandler.java:552-593`; 1.11 `ServerPlayNetworkHandler.java:496-517`, `ClientPlayNetworkHandler.java:565-606`; `LocalClientPlayerEntity.java` movement-send ranges above.

## Scope disposition

The draft establishes a **server-side** player-position mutation associated with the fall callback; 1.11's dry random-tick reversion also uses that mutation. It establishes a server-to-client block update. It does not establish a direct local-client player-position mutation or a server-to-client player-position packet caused by either `setDirt` call. A generic server `setPosition` call is therefore insufficient to accept this as a historical client movement delta. Treat the claimed client movement consequence and its proposed finding as excluded for this pair's client movement scope; retain the server-side source observation only as supporting context if later needed. This verdict does not claim that a separate later server correction can never occur; that would require its own path and applicability evidence.

## Earlier markers and direct-impact no-difference checks

`Entity.checkFallDamage` has the same relevant order in both versions: on landing, invoke `onFallenOn` only when `fallDistance > 0.0F`, then zero `fallDistance`; otherwise add `-dy` with a float cast only when `dy < 0`. The step callback remains a separate `onGround` dispatch (`Entity.java:673` in 1.10.2; `:695` in 1.11); `Block.onSteppedOn` remains empty, and FarmlandBlock adds no step override.

The paired callback bodies checked with no movement difference include `Block.onFallenOn` (default `takeFallDamage(fallDistance, 1.0F)`), `HayBlock.onFallenOn`, `SlimeBlock.onFallenOn`/`beforeCollision`/`onSteppedOn`, and `MagmaBlock.onSteppedOn`; Hay, Slime, and Magma source files are byte-identical across the pair. These remain native direct-impact behavior. This is bounded coverage for the assigned queue, not a complete pair inventory or pair freeze.
