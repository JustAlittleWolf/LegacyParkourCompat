## Individual claim verdicts

1. **Portal-state branch added in 1.15 — ACCEPT.** In `LivingEntity.findStandUpPosition(Entity)`, 1.14.4 branches first on `Boat` / `AbstractHorse`; the generic placement path has no portal test (lines 1664–1741). In 1.15 the first condition checks `level.getBlockState(new BlockPos(entity)).getBlock().is(BlockTags.PORTALS)` and calls `setPos(entity.getX(), entity.getY(1.0) + 0.001, entity.getZ())` before the vehicle-type branches (lines 1697–1700). That predicate uses the vehicle current block position and portal tag; no origin or dimension-transfer condition is present. The endpoint comparison establishes introduction only in `(1.14.4, 1.15]`.
2. **Server-only actual dismount placement gate — ACCEPT.** Both `LivingEntity.stopRiding()` implementations save the vehicle, delegate to `Entity.stopRiding()`, then call `findStandUpPosition` only if the vehicle changed and `!level.isClientSide` (1.14.4 lines 2324–2331; 1.15 lines 2388–2395). `Entity.stopRiding()` clears the vehicle and removes the passenger (1.14.4 lines 1651–1657; 1.15 lines 1615–1621). Therefore the portal predicate and its direct placement do not run during a local `LivingEntity` detach.
3. **Ordinary sneaking / shift route — ACCEPT, with input-version detail.** The server `Player.rideTick()` checks `!level.isClientSide`, passenger state and sneak/shift; it calls `stopRiding()` when true (1.14.4 lines 455–459; 1.15 lines 459–463, with `wantsToStopRiding()` reading shift state at lines 290–292). While mounted, `LocalPlayer.tick()` sends the sneak input in `ServerboundPlayerInputPacket` (1.14.4 lines 178–190; 1.15 equivalent); `ServerGamePacketListenerImpl.handlePlayerInput` stores it on the server player (1.14.4 lines 276–285; 1.15 lines 278–287). This is the ordinary key-driven server path.
4. **Client detach on passenger-list packet — ACCEPT, but distinguish immediate detach from subsequent position correction.** `ClientPacketListener.handleSetEntityPassengersPacket` ejects current passengers and rebuilds the list (1.14.4 lines 932–950; 1.15 lines 960–978); `Entity.ejectPassengers()` calls passenger `stopRiding()` (1.14.4 lines 1645–1648; 1.15 lines 1609–1612). `LocalPlayer.stopRiding()` delegates to `Player` then clears `handsBusy` (1.14.4 lines 162–165; 1.15 lines 163–166). Because the client's `LivingEntity.stopRiding()` fails the logical-server gate, this packet-driven local detach does not itself invoke the portal test or directly write the portal branch XYZ.
5. **Server-to-local immediate XYZ route — ESTABLISHED; omitted from both drafts.** `ServerPlayer.stopRiding()` overrides the base method in both releases. After `super.stopRiding()`, it checks that the vehicle changed and `connection != null`, then calls `connection.teleport` with the server player current x/y/z and rotation (1.14.4 lines 764–770; 1.15 lines 751–757). Thus, when 1.15 portal placement uses `setPos`, this override immediately sends the resulting coordinates to the client. `ServerGamePacketListenerImpl.teleport` sets the server player position with `absMoveTo` and sends `ClientboundPlayerPositionPacket` (1.14.4 lines 860–878; 1.15 lines 872–890). The empty relative-argument set passed by this overload makes XYZ absolute.
6. **Client application and follow-up — ESTABLISHED through the immediate response only.** `ClientPacketListener.handleMovePlayer` applies the authoritative XYZ to the local player (1.14.4 lines 659–705; 1.15 lines 669–716), then acknowledges the teleport and sends a position/rotation packet (1.14.4 lines 704–706; 1.15 continuation lines 722 onward). So “not local-client XYZ emulation” is accurate for the detach operation itself, but should not be read as “the portal placement never changes local XYZ”: the subsequent server correction does. This review stops at that immediate correction/acknowledgement path; later movement acceptance or additional corrective packets are not attributed to this branch.
7. **1.14.4 immediate-correction nuance — source-visible, not part of the 1.15 portal branch.** On the 1.14.4 generic vehicle path, `findStandUpPosition` ends by invoking virtual `teleportTo(l,m,n)` (line 1718); `ServerPlayer.teleportTo(double,double,double)` calls `connection.teleport` (1.14.4 `ServerPlayer.java` lines 1087–1089). Then the outer `ServerPlayer.stopRiding()` override sends its post-detach teleport too. For the 1.15 portal-tag path, the branch uses `setPos`, so the outer override sends the direct position correction after the base method returns. This difference reinforces that the local detach itself and the server-authored correction are separate events.

## Source identity and review boundary

The source-file SHA-256 values in the frozen roster match the version-level Mojmap source manifests. The ready markers identify Minecraft 1.14.4 and 1.15 and their Mojmap roots; the provenance and source-manifest hashes are recorded in the identity addendum. This review used only the primary local decompiled trees and the two specified author drafts. No wiki, product implementation, backlog, build, tests, runtime or network was consulted.

The accepted source difference is a server-side player dismount response that can reach the local player through a position correction. It does not establish that historical physics should run on a logical server. The project invariant excluding historical server physics remains a separate applicability / architecture gate for implementation. The class also has other 1.14.4-to-1.15 changes outside the narrow portal predicate claim; this verdict does not accept them as part of this finding.
