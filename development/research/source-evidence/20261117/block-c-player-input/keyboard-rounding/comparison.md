## Source facts

### 1.21.1 / 1.21.2 / 1.21.3: signed axis values, entity-side diagonal normalization

- \`1.21.1/mojmap/net/minecraft/client/player/KeyboardInput.java:12-34\`: \`calculateImpulse(boolean, boolean)\` returns float \`0.0F\`, \`1.0F\`, or \`-1.0F\`; \`tick(boolean,float)\` stores raw signed forward and lateral components, then, only when the boolean is true, multiplies lateral then forward by the supplied float.
- \`1.21.2\` and \`1.21.3/mojmap/net/minecraft/client/player/KeyboardInput.java:13-39\`: same calculation/store order, reading booleans from \`keyPresses\`; \`tick(boolean,float)\` scales left then forward only if requested.
- \`1.21.3/mojmap/net/minecraft/client/player/LocalPlayer.java:652-664\`: obtains slow-movement predicate and sneaking-speed attribute, passes them to \`input.tick\`; later item-use/not-passenger branch scales left then forward by \`0.2F\` and clears sprint trigger. Sneak multiplication precedes item-use multiplication.
- \`1.21.1/.2/.3/mojmap/net/minecraft/world/entity/LivingEntity.java\` travel section (1.21.3 near 2754-2758; .1 2666-2667; .2 2756-2757): multiplies \`xxa\`, then \`zza\`, by \`0.98F\` immediately before travel input construction. \`LocalPlayer.serverAiStep\` copies input left impulse into \`xxa\`, then forward into \`zza\` when camera-controlled.
- \`1.21.3/mojmap/net/minecraft/world/entity/Entity.java:1403-1417\`: \`moveRelative\` calls \`getInputVector\`; it calculates a double squared length from \`Vec3\`, returns zero below \`1.0E-7\`, otherwise normalizes only when squared length exceeds double \`1.0\`, scales by float speed, then computes float yaw sine/cosine and rotates. This is the earlier diagonal-normalization site. Two nonzero keyboard components reach this 3D length check.

### 1.21.5: keyboard normalization, LocalPlayer damping and square correction

- \`1.21.5/mojmap/net/minecraft/client/player/KeyboardInput.java:14-38\`: computes forward then lateral as floats, stores them in locals in that order, creates \`new Vec2(lateral, forward)\`, calls \`normalized()\`, and assigns the result to \`ClientInput.moveVector\`. \`ClientInput.java:6-14\` stores/returns that vector; \`hasForwardImpulse\` checks vector y \`> 1.0E-5F\`.

Thus diagonal rounding goes through float products/sum, double sqrt, float cast, float divides. A digital diagonal is approximately \`(±0.70710677F, ±0.70710677F)\`; exact decimal is not written literally in source.
- \`LivingEntity.java:2712\` calls virtual \`this.applyInput()\` in the ai section before jump/travel. Previous versions applied the two \`0.98F\` input multiplies at the start of travel. Base \`LivingEntity.applyInput()\` at 2806-2809 multiplies \`xxa\` then \`zza\` by \`0.98F\`.

## Verdict-ready claims and candidate separation

1. **Keyboard vector normalization (candidate operation, .4 -> .5):** keyboard input changes from float axis fields to normalized float \`Vec2\` (lateral, forward); diagonal rounding moves into the input producer. \`Entity.getInputVector\` remains for yaw-relative rotation and its length check, but ordinary digital input already has length at most one. Witness: forward+left with no opposing keys gives two \`+1.0F\` impulses and normalized float diagonal components. Source-proven; no runtime trajectory was measured.
2. **LocalPlayer speed correction (candidate operation, .4 -> .5):** camera-controlled input is transformed by a new override: 0.98F damping and context factors, followed by explicit float square correction. Earlier LocalPlayer supplies component impulses and Entity handles diagonal normalization. Algebraically, for an unmodified diagonal, correction can restore unit diagonal magnitude after 0.98F because \`min(length * sqrt(2), 1)\` reaches one; an axial vector remains 0.98F. This is a source-based prediction; float rounding and parity require a separate runtime check.
3. **Sneak/item factor order (.3 -> .4, separate candidate):** when both item-use and slow movement apply, factors are multiplied in opposite order across float components. This is a possible operation-order/rounding delta. It is not diagonal normalization or square correction.
4. **The 0.98F constant alone is not new at .5:** .1-.4 already multiply xxa then zza by 0.98F immediately before travel. .5 moves default damping to virtual \`applyInput\` before jump/travel and LocalPlayer replaces the base operation for controlled camera with its vector transform. Candidate is the LocalPlayer transform and call/store order, not the constant alone.

Dependency closure for this slice: KeyboardInput -> ClientInput/Vec2 -> LocalPlayer.aiStep/applyInput -> LivingEntity.aiStep virtual call -> LivingEntity.applyInput default -> LivingEntity travel vector -> Entity.moveRelative/getInputVector; numerical helpers Mth.sqrt/square. This is not full-pair closure: remaining player movement branches, non-keyboard controls and other dependencies are unreviewed. No patch cutover inside release intervals is asserted.
