## Verdict

**ACCEPT the three bounded source claims**, with the limits below. This is an independent review of the assigned keyboard/local-player input operations, not a complete movement-pair coverage audit or runtime parity verdict.

1. **Keyboard diagonal normalization, 1.21.4 → 1.21.5: accepted.** In 1.21.4, `KeyboardInput.tick()` stores signed forward and lateral float components without normalizing them (`KeyboardInput.java:22-37`); ordinary two-axis input remains unnormalized for the later `Entity.getInputVector` double-length check/conditional normalization (`Entity.java:1403-1417`; corroborated in 1.21.3 at the same lines). In 1.21.5, `KeyboardInput.tick()` computes forward then lateral float impulses, constructs `Vec2(lateral, forward)`, and assigns `.normalized()` (`KeyboardInput.java:23-36`). `Vec2.normalized()` computes float products and sum, calls float `Mth.sqrt`, then divides float components (`Vec2.java:48-50`; `Mth.java:56-57`). Thus the digital diagonal's normalization and rounding are in the keyboard producer in .5, rather than being deferred to entity-side vector normalization. Entity's later check remains in the path (`Entity.java:1453-1467` in .5); for the ordinary digital vector its conditional `> 1.0` normalization is not the producer operation being compared.

2. **Local-player damping and square correction, 1.21.4 → 1.21.5: accepted.** The .5 controlled-camera `applyInput()` calls `modifyInput`, stores its returned float x/y in `xxa`/`zza`, and sets jump (`LocalPlayer.java:608-620`). `modifyInput` preserves exact zero, then scales nonzero input by `0.98F`, conditionally by item-use `0.2F`, conditionally by sneaking-speed, then invokes square correction (`LocalPlayer.java:623-639`). The correction uses float length, a reciprocal-length direction, `distanceToUnitSquare`, `min(length * distance, 1.0F)`, and a final float scale (`LocalPlayer.java:641-658`). In .4 the player input is raw and item-use then slow-movement multipliers apply in `aiStep` (`LocalPlayer.java:662-678`); `LivingEntity` later multiplies `xxa` then `zza` by `0.98F` at the start of travel (same section as .3/.4). In .5 base `LivingEntity.applyInput()` still multiplies those components in x-then-z order, but the virtual call occurs in the ai section before travel (`LivingEntity.java:2712, 2806-2809`); camera-controlled `LocalPlayer` replaces it with its vector transform. For a digital diagonal, the stated correction formula can raise post-damping magnitude to its unit cap; for an axis it leaves the .98-scaled magnitude. Those are source-derived mathematical consequences, not measured trajectories.

3. **Sneak/item multiplier ordering, 1.21.3 → 1.21.4 and retained in the .5 transform: accepted as a distinct source operation.** In .3 `KeyboardInput.tick(slow, speed)` scales lateral then forward for sneak before returning; `LocalPlayer.aiStep()` subsequently scales lateral then forward by `0.2F` for item-use and clears `sprintTriggerTime` (`KeyboardInput.java:21-34`; `LocalPlayer.java:657-664`). In .4 `KeyboardInput.tick()` emits raw axes, then `LocalPlayer.aiStep()` applies item-use to lateral then forward before slow-movement speed to lateral then forward (`KeyboardInput.java:22-37`; `LocalPlayer.java:662-678`). In .5 `modifyInput()` applies item-use then sneak to the vector (`LocalPlayer.java:628-638`). Reversing the two float multiplications can change the last stored float bit for some values when both gates are true. This is separate from diagonal normalization and square correction. The item-use path's sprint-trigger reset/gating should not be conflated with the speed-factor order: .3/.4 clear the trigger in the item-use branch; .5 resets it for shift, item-use without passenger, or backward key before its sprint-start handling (`LocalPlayer.java:718-732`).

## Ordinary keyboard witness and boundaries

With forward+left pressed and neither opposing key pressed, `calculateImpulse` returns `+1.0F` for each axis (`KeyboardInput.java:14-20`), and the source assembles the vector in `(lateral, forward)` order. This is sufficient to witness the ordinary diagonal path. With one axis pressed, the same code emits a unit axial vector. With opposite keys both held on an axis, the equal-boolean gate yields zero. The .5 normalization also returns zero for vector length below `1.0E-4F`; the .5 LocalPlayer transform separately returns exact zero when `lengthSquared() == 0.0F`. These thresholds/gates are part of the source boundary and should be preserved.
