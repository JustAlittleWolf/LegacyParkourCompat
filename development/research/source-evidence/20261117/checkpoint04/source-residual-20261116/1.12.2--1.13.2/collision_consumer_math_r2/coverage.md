## Paired source behavior

In 1.12.2 `StairsBlock.addCollisions` ( `decompiled_minecraft/1.12.2/ornithe-feather/net/minecraft/block/StairsBlock.java:66-84`) iterates `getCollisionShapes`: it always supplies the base box and separately supplies its step box(es). `Block.addCollision` translates each box and adds it only when that individual box intersects the expanded query (`.../block/Block.java:372-380`). `World.getCollisions` forwards the entity's expanded movement box to the block (`.../world/World.java:964-1002`); `Entity.move` clips Z against the resulting boxes (`.../entity/Entity.java:567-600`). Thus a base box intersecting the starting player box does not, by itself, suppress a distinct step box.

In 1.13.2 stairs expose a composite `VoxelShape`: `makeShape` unions the base with selected step pieces (`decompiled_minecraft/1.13.2/ornithe-feather/net/minecraft/block/StairsBlock.java:57-75`), and `getShape` returns that combined shape (`:99-102`). The movement query builds a swept shell from the expanded player box while retaining the original box as `excludeBlock` (`.../world/WorldView.java:158-163`). In `getBlockCollisions`, if the original box overlaps the block's composite collision shape, the method returns an empty shape for that block before the swept-shell predicate can emit the composite (`.../world/WorldView.java:112-145`, especially `:138-140`). Since the exclusion test is against the composite union, overlap with its base can discard a distinct step component intersecting the swept shell. `Entity.move` then clips against the returned collision shapes using `VoxelShapes.calculateMaxOffset` (`.../entity/Entity.java:580-600`; implementation at `.../block/shape/VoxelShapes.java:194-205`).

## Concrete clipping witness and limit

Take one bottom, straight, north-facing stair at block coordinates `[0,1]` on each axis, with no other collision shapes nearby. In both versions its base occupies `x=[0,1], y=[0,.5], z=[0,1]`; the forward step occupies `x=[0,1], y=[.5,1], z=[0,.5]` (1.12.2 constants and selector: `StairsBlock.java:33-42, 76-99`; 1.13.2 base/quadrant constants and composite selector: `StairsBlock.java:38-53, 63-75, 99-104`, where north's horizontal facing id selects the two north quadrants). Consider the ordinary 0.6-wide, 1.8-high entity box from position `(0.5, .4, .85)`: `x=[.2,.8], y=[.4,2.2], z=[.55,1.15]` (dimensions and box construction: 1.13.2 `Entity.java:187-193, 309-315`). Set `onGround=false` to keep the collision result from entering the separate step-up branch (`Entity.java:602`), and request only `dz=-.2`.

The starting box overlaps the stair base by positive volume and does not overlap the step. The swept shell reaches `z<.5` and overlaps the step. In 1.12.2 both boxes are independently offered; the step is in the expanded query, and its north-facing boundary at `z=.5` clips the negative Z request to `-.05` (`Box.intersectZ`, `.../util/math/Box.java:225-241`). In 1.13.2 the base overlap makes `VoxelShapes.overlap(excludeBlock, stairShape, AND)` true, so the entire stair shape, including the step that lies in the swept shell, is omitted for this query. With the stated empty surroundings, that stair therefore clips by `-.05` in 1.12.2 and by `0` in 1.13.2 (requested displacement remains `-.2`). This refutes a general no-displacement inference from individual-box overlap and demonstrates that the composite gate can change clipping.

This is a source-level player-sized box witness, not proof that this start-overlap state is reachable from a collision-free ordinary tick. The witness deliberately begins penetrating the base; source alone here does not establish how a normal player arrives in that state. Therefore retain the exact composite stair gate's ordinary-game applicability/reachability as open pending independent audit or further source-path evidence. Do not promote the witness to an unconditional player trajectory finding.

## Separate collision-presence gate

Keep `hasCollision` distinct from the composite-overlap gate. In 1.13.2 `Block.getCollisionShape` returns the state's shape only when `hasCollision` is true, otherwise empty (`decompiled_minecraft/1.13.2/ornithe-feather/net/minecraft/block/Block.java:90, 231, 393-395`); the property defaults true (`:1901`) and stairs use the ordinary collidable block properties. The composite witness assumes this gate passes. It says nothing about no-collision blocks. The 1.12.2 base `Block.getCollisionShape` returns the state's shape without that field gate (`.../1.12.2/ornithe-feather/net/minecraft/block/Block.java:372-389`); stairs instead override collision collection to supply their component boxes. Do not fold these separate source facts into the stair overlap conclusion.
