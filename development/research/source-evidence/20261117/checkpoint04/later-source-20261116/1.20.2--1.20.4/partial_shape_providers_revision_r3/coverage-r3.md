## Compared operations

**Snow layers.** `SnowLayerBlock.SHAPE_BY_LAYER` contains the same empty zero entry and full-width boxes at heights 2, 4, 6, 8, 10, 12, 14, and 16 sixteenths at both endpoints. The default is one layer. `getShape` and `getBlockSupportShape` select the entry indexed by `LAYERS`; `getCollisionShape` selects `LAYERS - 1`, so the default one-layer state has empty collision while its outline/support shape is 2/16 high. The paired survival and update path retains the same `SNOW_LAYER_CANNOT_SURVIVE_ON` veto, `SNOW_LAYER_CAN_SURVIVE_ON` allow, full-top-face test, full eight-layer snow-stack exception, and removal to air when survival fails. Placement retains the same clicked-layer increment, capped at eight. The compared methods and array values are equal; 1.20.4 adds a `MapCodec` declaration/override outside these operations. Anchors: `SnowLayerBlock.java` 1.20.2 lines 27–39, 42, 60–72, 90–104, 126–136; 1.20.4 lines 29–41, 49, 67–79, 97–111, 133–143.

**Carpets.** `CarpetBlock.getShape` returns the same full-footprint, 1/16-high box. Its `canSurvive` and `updateShape` paths remain the same: any non-empty block below supports it; otherwise neighbor update removes it. Neither `CarpetBlock` nor `WoolCarpetBlock` overrides collision selection. The shared `BlockBehaviour.getCollisionShape` still returns the state's shape when `hasCollision` is true and empty otherwise; `Properties.of()` still defaults `hasCollision` to true. Moss carpet and all 16 dye-carpet registrations still construct the same provider classes with the same movement-relevant default collision setting; per-color map colors do not enter the shape methods. Wool carpet continues to inherit `CarpetBlock` geometry; 1.20.4 adds codecs to the provider classes but no movement-shape override. Anchors: `CarpetBlock.java` 1.20.2 lines 13–33; 1.20.4 lines 15–48; `WoolCarpetBlock.java` 1.20.2 lines 6–19; 1.20.4 lines 8–29; `BlockBehaviour.java` 1.20.2 lines 290–292, 908, 945–946; 1.20.4 lines 334–336, 960, 997–998; `Blocks.java` 1.20.2 lines 1573–1576, 2190–2203, 3575–3652, 6085–6096, 7229–7234; 1.20.4 lines 1588–1591, 2193–2206, 3549–3626, 6015–6026, 7397–7402.

**Ladders.** The four directional boxes are unchanged: the north/south/east/west facing selects the corresponding 3/16-thick wall-side box. Default state remains north-facing and not waterlogged. The support predicate still reads the adjacent state's `isFaceSturdy` on the face toward the ladder; survival derives that position/face from `FACING`. Neighbor update still removes the ladder only when the changed side is its support side and survival fails, then schedules water if waterlogged. Placement keeps the same nearest-looking horizontal-direction order, chooses the opposite-facing wall, requires survival, and sets waterlogging from the clicked position's water fluid. The direct shape, attachment, update, and placement operations match. 1.20.4 adds codec members only. Anchors: `LadderBlock.java` 1.20.2 lines 26–34, 36–74, 76–115; 1.20.4 lines 33–41, 43–81, 83–122.

**Scaffolding.** State properties and defaults remain `DISTANCE=7`, `WATERLOGGED=false`, and `BOTTOM=false`. Stable/unstable shape boxes and composition are identical. Outline selection remains full-block while holding the scaffolding item, otherwise bottom selects unstable shape and non-bottom selects stable shape. Collision selection remains a stable shape when the context is above the block and not descending; otherwise it returns the 2/16 bottom plate only when distance is nonzero, `BOTTOM` is true, and context is above the translated block below; all other cases are empty. The placement/distance selector is unchanged: inspect below first, inherit a scaffolding distance or return zero for a sturdy upper face, then inspect horizontal neighbors and take `min(distance + 1)`, early stopping at one. `isBottom` remains based on positive distance and absence of scaffolding directly below. The compared shape arrays, gates, state defaults, and support selector match. The newer codec declaration is outside these bodies. Anchors: `ScaffoldingBlock.java` 1.20.2 lines 27–38, 47–58, 66–74, 112–123, 130–155, 157–168; 1.20.4 lines 29–45, 54–65, 73–81, 119–130, 137–162, 164–175.

The direct registration excerpts retain the same provider classes and movement-relevant property setters: ladder uses `forceSolidOff`, strength 0.4, ladder sound, `noOcclusion`, and destroy push reaction; snow retains layer-count-based view blocking and its other property calls; scaffolding retains `noCollission`, dynamic shape, never-valid spawn/redstone-conductor predicates, and destroy push reaction; carpets retain the same `WoolCarpetBlock`/`CarpetBlock` types and do not opt out of collision. Other property semantics and runtime state availability are not inferred here.

## R2 audit correction: ladder collision selection

The ladder collision route inherits `BlockBehaviour.getCollisionShape` at both endpoints: `LadderBlock` overrides `getShape` with the same four facing-selected 3/16-thick boxes (1.20.2 lines 36–48; 1.20.4 lines 43–55), but does not override `getCollisionShape`. The inherited method returns `state.getShape(...)` when `hasCollision` is true (1.20.2 `BlockBehaviour.java` lines 290–292; 1.20.4 lines 334–336). `Properties` defaults `hasCollision=true` (1.20.2 line 908; 1.20.4 line 960). The `Blocks.LADDER` registration uses `.noOcclusion()` but not `.noCollission()` (1.20.2 `Blocks.java` lines 1573–1576; 1.20.4 lines 1588–1591): `noOcclusion()` only clears `canOcclude`, while `noCollission()` clears both `hasCollision` and `canOcclude` (1.20.2 `BlockBehaviour.java` lines 993–1001; 1.20.4 lines 1060–1068). Therefore, the registered ladder's collision shape is the same facing-selected 3/16 box as its outline at both endpoints. The applicable `BlockBehaviour.java` and `Blocks.java` file hashes are already bound in the exact source-hash table above; no source identity or prior comparison changed.
