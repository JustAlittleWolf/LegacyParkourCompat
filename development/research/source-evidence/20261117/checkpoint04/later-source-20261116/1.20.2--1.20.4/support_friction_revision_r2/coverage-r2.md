## Ordered coverage

1. **Support-position selector inspected, production dependency partial.** `net/minecraft/world/entity/Entity.java`, `getBlockPosBelowThatAffectsMyMovement` delegates to `getOnPos(0.500001F)` in both versions (`Entity.java`, 1.20.2 lines 792–815; 1.20.4 lines 793–816). `getOnPos(float)` prefers `mainSupportingBlockPos`. Its return condition keeps the recorded support position for a `WALLS` block or `FenceGateBlock` unconditionally, and for a `FENCES` block only when the offset is `<= 0.5`; otherwise it uses `support.atY(floor(position.y - offset))`. Thus this selector's `0.500001F` offset disables the fence-specific support-Y exception, while wall/gate exceptions still retain support Y. With no recorded main support, it floors X/Z and Y-offset. The endpoint bodies match. The writer/population of `mainSupportingBlockPos` is in the excluded Entity.move kernel and was not examined.
2. **Jump-factor selection inspected.** `Entity.getBlockJumpFactor` reads the block at `blockPosition()` and the support position; it uses the support block's factor only when the in-entity factor compares exactly equal to `1.0`. `LivingEntity.getJumpPower` multiplies the selected factor by `0.42F` before adding jump-boost power. The selected bodies match across endpoints. `Player.jumpFromGround` calls `super`; ordinary player `travel` calls `super.travel`, with a separate ability-flight branch. No factor-selection difference found in these bodies.
3. **Speed-factor selection inspected; player tick caller path traced.** `Entity.getBlockSpeedFactor` reads the block at `blockPosition()`, except that water and bubble-column state return that in-entity factor directly; otherwise an exact `1.0` factor falls through to the support block. `LivingEntity.getBlockSpeedFactor` overrides this to return `1.0F` with Soul Speed enchantment on a `SOUL_SPEED_BLOCKS` support, otherwise delegates. `Player` returns `1.0F` while flying or fall-flying, otherwise delegates. The relevant endpoint bodies match. In both versions, `Player.tick` calls `LivingEntity.tick`; that calls `Entity.tick`, whose `this.baseTick()` dispatches to `LivingEntity.baseTick` for a player; `LivingEntity.baseTick` calls `super.baseTick()`, reaching `Entity.baseTick`. In its block-state processing branch, `Entity.baseTick` invokes `this.getBlockSpeedFactor()` and multiplies horizontal delta movement by the result, so virtual dispatch reaches the Player override and, when it delegates, the LivingEntity and Entity rules. A source-tree call-site search also finds Camel's separate non-player use in its jump impulse; it does not establish another player caller. The support-dependent living/player rule is therefore source-reachable on the player tick path. The source pair remains partial for the separate tag-resource and support-position-production dependencies below.
4. **Ground friction path inspected.** In `LivingEntity.travel`, the ordinary non-fluid/non-fall-flying branch takes `getBlockPosBelowThatAffectsMyMovement()`, reads that state's block friction, computes on-ground `friction * 0.91F` (otherwise `0.91F`), then passes friction to `handleRelativeFrictionAndCalculateMovement`. Player `travel` delegates to `super.travel` outside its flight branch. The relevant selector/read/order/math match at the endpoints. The wider travel flow is outside ownership.
5. **Provider/default production inspected.** `BlockBehaviour.Properties` defaults are friction `0.6F`, speed factor `1.0F`, jump factor `1.0F`; setters assign each field directly, and `Block` accessors return those stored floats unchanged. All occurrences of these setters in `world/level/block/*.java` were enumerated in both releases. The same override set and values occur: ice, packed ice, frosted ice `friction(0.98F)`; blue ice `0.989F`; slime `0.8F`; soul sand `speedFactor(0.4F)`; honey `speedFactor(0.4F)` and `jumpFactor(0.5F)`. No block/provider-value difference found. Ordinary default blocks retain the values above.
6. **Tag/resource dependency identified, unresolved.** `BlockTags.SOUL_SPEED_BLOCKS` is the same tag key in both Java trees. The canonical decompiled roots contain only Mojmap Java source (`mojmap/`) and no data/resource tree, so the tag JSON's actual entries and endpoint equality were not verified. Do not infer its effective membership from the tag constant.
