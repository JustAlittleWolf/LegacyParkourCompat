## Bounded comparison

1. **Value function is unchanged.** The inherited `LivingEntity.getKnockback(target, damageSource)` reads the attacker's `Attributes.ATTACK_KNOCKBACK` effective value. For a `ServerLevel`, it passes that value through `EnchantmentHelper.modifyKnockback(...)`, then divides by `2.0F`; otherwise it divides the attribute value by `2.0F` directly (26.1.2 `LivingEntity.java:1511-1516`; 26.2 `LivingEntity.java:1540-1545`). The paired bodies are identical. `Player` has no declaration overriding `getKnockback` in either source file, so this is the inherited Player calculation.

2. **Default player value is zero absent modifiers.** `Attributes.ATTACK_KNOCKBACK` is a ranged attribute with default `0.0` and bounds `0.0..5.0` in both versions (`Attributes.java:15` in 26.1.2; `:18` in 26.2). `LivingEntity.createLivingAttributes` includes it in both versions (`LivingEntity.java:318-340`; 26.2 `:332-355`). `Player.createAttributes` extends that builder and adds no separate attack-knockback value (`Player.java:205-218`; 26.2 `:206-219`). Therefore the unmodified Player base produces zero from the local non-server branch; the source does not establish that every equipped player has zero effective value.

3. **Item attribute modifiers have a generic application path, but the equipment-update caller is server-gated.** `ItemStack.forEachModifier` visits the item's `ATTRIBUTE_MODIFIERS` component and then `EnchantmentHelper.forEachModifier` (`ItemStack.java:1011-1014` in both versions). The helper enumerates the held enchantments' `EnchantmentEffectComponents.ATTRIBUTES` entries when the enchantment matches the slot (`EnchantmentHelper.java:392-408`, body identical). `LivingEntity.collectEquipmentChanges` applies each current, unbroken item's modifiers to matching attribute instances; the modifier application itself has no `ServerLevel` condition, while subsequent location-based enchantment effects are guarded by `this.level() instanceof ServerLevel` (26.1.2 `LivingEntity.java:2892-2925`; 26.2 `:2959-2992`). However, `LivingEntity.tick` calls `detectEquipmentUpdates` only inside `if (!this.level().isClientSide())` in both releases (26.1.2 `LivingEntity.java:2703-2728`; 26.2 `:2769-2794`), and that method delegates to `collectEquipmentChanges` (26.1.2 `:2882-2883`; 26.2 `:2949-2950`). Therefore this periodic equipped-item modifier-collection path is established for server-side entities, not as a LocalPlayer client-side equipment update. This does not exclude an effective client attribute value established through another path such as synchronized attributes; that path was not traced here. Packaged item/enchantment component values and LocalPlayer effective modifier state remain unverified.

4. **Direct knockback enchantment contribution is server-only in this helper.** `EnchantmentHelper.modifyKnockback` initializes a mutable value from the input and applies each held enchantment's `modifyKnockback` effect (`EnchantmentHelper.java:204-209`, identical). `Enchantment.modifyKnockback` applies the `KNOCKBACK` enchantment value effect (`Enchantment.java:293-302`, identical). Both methods take `ServerLevel`, and `LivingEntity.getKnockback` only calls that helper inside its `level() instanceof ServerLevel` branch. This direct enchantment addition therefore is not part of the source calculation on a client-side level. It may affect server-side attack resolution; it does not establish ordinary LocalPlayer prediction.

5. **`dealsKnockback` is a separate caller gate.** `Player.stabAttack` returns early for `cannotAttack(target)`, can also return on the `dealsKnockback && deflectProjectile(target)` branch, and only then enters its knockback block when `dealsKnockback` is true. In 26.2 that block calls `causeExtraKnockback` first with `0.4F`, then with `getKnockback(...)`; in 26.1.2 it made one combined call (`Player.java:1193-1222` vs `26.2:1213-1243`). This report does not re-evaluate the already separately covered call split; it identifies the inputs that can make the second amount positive.

   The source call sites show that `PiercingWeapon` passes its `dealsKnockback` field into `stabAttack`; the codec defaults that boolean to true when the field is omitted (`PiercingWeapon.java:25-38, 75-80`, same relevant behavior in both). `KineticWeapon` sets it only when `knockbackConditions` is present and its condition test passes (`KineticWeapon.java:125-131`, same relevant behavior in both). The item component's concrete data values and the ordinary client invocation route are not examined here.
