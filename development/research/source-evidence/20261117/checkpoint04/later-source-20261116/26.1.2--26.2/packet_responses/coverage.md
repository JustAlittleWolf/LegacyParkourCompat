## Ordered route and comparison

All checked client packet handlers begin with `PacketUtils.ensureRunningOnSameThread(packet, this, this.minecraft.packetProcessor())`; `PacketUtils` schedules the packet/listener on the packet processor when called off-thread, then throws the handoff sentinel. The scheduling helper is byte-identical in both releases (`PacketUtils.java:17-24`). The state writers below therefore execute on the client packet processor. Where handlers respond to a packet, their relevant statement order and gates match across the pair.

1. **Position, rotation and velocity synchronization.** `handleSetEntityMotion` resolves `level.getEntity(packet.id())`, null-checks, and calls `entity.lerpMotion(packet.movement())` (`ClientPacketListener.java:623-629 in 26.1.2; 622-628 in 26.2`). `handleMovePlayer` targets `minecraft.player`; only when it is not a passenger does it call `setValuesFromPositionPacket`, then sends accept-teleportation and current position/rotation acknowledgments and invalidates block-state predictions (`26.1.2:796-807; 26.2:795-806`). The shared helper calculates absolute values, compares squared positional delta to `4096.0`, chooses interpolation only when requested and below that bound, and writes position, delta movement, rotation and old interpolation values in the same order (`26.1.2:809-829; 26.2:808-828`). `handleTeleportEntity` resolves by ID; a missing formerly removed player vehicle routes the change directly to the player and sends a position/rotation acknowledgment; otherwise it computes relative position flags and interpolation gates and handles passenger repositioning (`26.1.2:668-702; 26.2:667-701`). `handleEntityPositionSync` and `handleMoveEntity` both resolve the packet entity and preserve the same `isLocalInstanceAuthoritative()` split; passenger repositioning and ground-state updates are unchanged (`26.1.2:642-666, 732-756; 26.2:641-665, 731-755`). `handleRotatePlayer` calculates relative rotation and updates current/old player rotation in the same order (`26.1.2:832-844; 26.2:831-843`). All six handler/helper bodies compared byte-for-byte equal.

2. **Direct knockback and carried-player response.** `handleExplosion` always adds the packet's optional player knockback to `minecraft.player` after the sound/particle/effect calls (`26.1.2:1361-1379; 26.2:1359-1377`). Its body is byte-identical. Entity-position/teleport handlers reposition an indirect player passenger and update old player position/rotation under the same gates; this is a player response, while vehicle physics itself remains outside this lane.

3. **Pose and synced state.** `handleSetEntityData` resolves the packet entity ID then assigns packed synchronized values (`26.1.2:633-639; 26.2:632-638`). `DATA_POSE` is defined on `Entity`; `SynchedEntityData.assignValues` invokes `onSyncedDataUpdated` for updated accessors; the `Entity` callback refreshes dimensions for `DATA_POSE`, while `LocalPlayer` delegates to that callback before its unchanged shared-flag behavior (`Entity.java:270, 3306-3310; LocalPlayer.java:583-600; SynchedEntityData.java:108-116 in 26.1.2; `Entity.java:271, 3379-3383; LocalPlayer.java:583-600; SynchedEntityData.java:108-116 in 26.2`). The same local-player callback starts/stops item use when server-synced living flags change. `LocalPlayer.startUsingItem` / `stopUsingItem`, `isSlowDueToUsingItem` and `itemUseSpeedMultiplier` are byte-identical, so this state reaches the same can-sprint and item-use-speed gates in both releases (`LocalPlayer.java:549-575 in both). `Entity.setPose`, `refreshDimensions` and `reapplyPosition` match exactly. The packet handler, synced-data writer and player override also match exactly; no pose or dimension-response difference was found.

4. **Equipment and inventory candidates.** `handleSetEquipment` resolves the entity ID to a `LivingEntity` and applies packet slots in order via `setItemSlot` (`26.1.2:1512-1516; 26.2:1510-1514`). The matching writer in `LivingEntity.setItemSlot` and its attribute modifier update body are identical. The selected-hotbar packet path (`handleSetHeldSlot` → `Inventory.setSelectedSlot`) and direct player-inventory path (`handleSetPlayerInventory` → `Inventory.setItem`) are identical (`26.1.2:724-728, 1448-1452; 26.2:723-727, 1446-1450`). `handleContainerSetSlot`/`handleContainerContent` route through the same active-menu methods; the only textual difference in `handleContainerSetSlot` is a GUI accessor/screen pattern, with the same menu writes and branches (`26.1.2:1406-1463; 26.2:1404-1459`). Inventory/menu data paths were checked as candidates; direct equipment modifier application remains the entity `setItemSlot` route.

5. **Effects, attributes, abilities and game mode.** Update/remove-effect handlers resolve the packet entity to `LivingEntity` and call `forceAddEffect` / `removeEffectNoUpdate` (`26.1.2:1795-1813, 1982-1985; 26.2:1794-1811, 1980-1983`). `LivingEntity` effect-add/update/removal logic and the `MobEffect` attribute-modifier callbacks match; `MobEffectInstance.onEffectAdded` forwards the same effect/amplifier. `handleUpdateAttributes` resolves entity ID, rejects a non-living entity, then applies base value, clears modifiers, and re-adds transient modifiers in the same per-snapshot order (`26.1.2:2355-2381; 26.2:2357-2381`). `AttributeInstance` mutations and `AttributeMap` copy helpers used on respawn match. The ability packet writes flying/instabuild/invulnerability/mayfly, flying speed, then walking speed directly on the local player in unchanged order (`26.1.2:2087-2098; 26.2:2089-2098`). `handleGameEvent`'s `CHANGE_GAME_MODE` route still calls `MultiPlayerGameMode.setLocalMode`; its `GameType.updatePlayerAbilities` terminal is identical. Its other handler changes are GUI accessor changes only. `handleRespawn` still creates/replaces the local player, conditionally copies delta movement and rotations under `shouldKeep((byte)2)`, copies all or base attributes under `shouldKeep((byte)1)`, then adds and adjusts the new player in the same order (`26.1.2:1253-1343; 26.2:1251-1341`). Its non-movement differences are level renderer/extractor and GUI API names.
