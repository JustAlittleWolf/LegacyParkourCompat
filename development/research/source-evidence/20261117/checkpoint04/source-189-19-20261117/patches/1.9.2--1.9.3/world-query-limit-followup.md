# 1.9.2 → 1.9.3 world-query limit follow-up

## Evidence identity and integrity

Both inputs are `ornithe-feather`, with 1,819 Java source rows each. SHA-256 of the provenance files matches the supplied identities: 1.9.2 `9928b467deb35c7e7f891b4fee1627a68feecdf233c2076909fd4834b0380510`; 1.9.3 `43325cdd53ca34b88ee9af8464782b323a948b98c8a556c4761f1e5737b84c3a`. The compared `World.java`, `ClientWorld.java`, `ClientChunkCache.java`, `EmptyChunk.java`, `WorldChunk.java`, `ChunkPos.java`, `Entity.java`, `LivingEntity.java`, `PlayerEntity.java`, `ClientPlayerEntity.java`, and `LocalClientPlayerEntity.java` hashes match their respective provenance entries.

## Source facts

- **World query gates.** In 1.9.2, `World.contains(BlockPos)` checks `-30,000,000 <= x,z < 30,000,000` and `0 <= y < 256` (`net/minecraft/world/World.java:167-169`). Both `getBlockState` (`:614-620`) and `isChunkLoaded(BlockPos, boolean)` (`:180-182`) reject a position failing that check; the former returns air and the latter false. In 1.9.3, `contains` still has the horizontal limits (`:169-175`), but `getBlockState` now checks only vertical height before fetching its chunk (`:621-627`), and `isChunkLoaded` directly calls `isChunkLoadedAt(x >> 4, z >> 4, allowEmpty)` (`:182-188`).
- **Collision call sequence.** `World.getCollisions` has the same relevant loop and gates in both releases (1.9.2 `World.java:893-927`; 1.9.3 `:899-933`). It tests `isChunkLoaded` at each scanned x/z coordinate (y=64), then, when `worldBorder.contains(pos) || !bl2`, calls `getBlockState(pos)` and `addCollisions`. Here `bl2` is `isWithinBorder(worldBorder, entity)` (`:907-910`); for the assigned out-of-world-border entity case, `!bl2` makes the block-state read occur. The block state can contribute a collision box to the returned list.
- **Local cache result.** `ClientWorld.isChunkLoadedAt` is unchanged in this slice: it returns `allowEmpty || !getChunkSource().getChunk(...).isEmpty()` (both versions, `ClientWorld.java:103-105` in 1.9.2; `:104-106` in 1.9.3). `getCollisions` calls the default `isChunkLoaded(BlockPos)`, which supplies `allowEmpty=true`. Thus in 1.9.3 the client-side loaded-chunk test passes even when the cache has no chunk; that case resolves to the cache's `EmptyChunk` and air. When the cache does have the queried chunk, `ClientChunkCache.getChunk` returns it instead (`ClientChunkCache.java:44-57`), and `World.getBlockState` reads its state. `WorldChunk.getBlockState` selects section data using `x & 15` and `z & 15` (`WorldChunk.java:357-382`). `EmptyChunk.getBlockState` always returns air (`EmptyChunk.java:40-42`).
- **No coordinate clamp in this local cache API.** `ClientChunkCache.loadChunk(chunkX, chunkZ)` constructs and inserts the requested coordinates without a world-limit check (1.9.2 `ClientChunkCache.java:42-47`; 1.9.3 `:48-53`). Its lookup key is `ChunkPos.toLong`, which packs the supplied integer x/z bit patterns (`ChunkPos.java:19-21`); it does not clamp them to the world limit.
- **Player movement caller.** `Entity.move(dx,dy,dz)` invokes `World.getCollisions` for sneaking support, ordinary movement, and step-up resolution (1.9.3 `Entity.java:441-509, 533-542`; corresponding 1.9.2 calls are at `:438-506, 530-539`). `LocalClientPlayerEntity` extends `ClientPlayerEntity`, which extends `PlayerEntity`/`LivingEntity`; inherited `LivingEntity` travel calls `move` (1.9.3 `LivingEntity.java:1341,1391,1420,1448`). After collision resolution, `Entity.move` also reads the foot and below-foot states for fall/landing and step callbacks (`:630-669`), then `checkBlockCollisions` directly reads states across the entity box (`:737-758`). These are additional movement-adjacent direct readers of the changed `getBlockState` gate.

## Verdict and applicability

This is **not source-level neutral** for the stated candidate. In 1.9.2, an out-of-horizontal-range scan coordinate fails `isChunkLoaded`, so `getCollisions` skips it before requesting a block state. In 1.9.3, the same call reaches the client cache; if the matching out-of-range chunk is loaded and contains a collision-bearing state intersecting the query, `getBlockState` can return it and `addCollisions` can add a box. That can change the offsets and collision flags resolved by `Entity.move`. Post-move foot/block-collision readers can likewise observe loaded out-of-range states in 1.9.3 where 1.9.2 supplies air. An absent chunk alone does not establish this effect: the 1.9.3 cache returns `EmptyChunk`/air for it.

The source proves that the local provider API can store and return arbitrary chunk coordinates and that these movement queries consume such a chunk if present. It does **not** prove that an ordinary session populates an out-of-range chunk or that a local player reaches the candidate tick; no packet/loading route or runtime behavior was examined. The concrete movement consequence is conditional on an out-of-range loaded chunk containing a relevant state and the player/query path reaching it.
