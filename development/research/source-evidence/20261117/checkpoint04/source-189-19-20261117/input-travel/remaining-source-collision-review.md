# Remaining collision-provider call order and shape-context checks

## Stairs multipart order through movement clipping

1.8.9 `World.getCollisions` visits block coordinates and invokes `blockState.getBlock().addCollisions(world,pos,state,query,list,entity)` (`world/World.java:905–922`). `StairsBlock.addCollisions` sets the base AABB and emits it first, calls `isInnerStair(world,pos)` (which updates the instance shape), emits that second, and conditionally calls `setStepShapeForCollisions(world,pos)` and emits the final piece third (`block/StairsBlock.java:384–394`; helper methods `:216–294, 297–381`).

1.9 `World.getCollisions` obtains the current `BlockState` from the same `World` receiver and passes that state, world and mutable position to `state.addCollisions` (`world/World.java:922–928`). `StairsBlock.addCollisions` resolves the virtual stair shape from that state/world/position, then iterates `getCollisionShapes(state)` (`block/StairsBlock.java:66–88`): base first, inner piece for straight/inner forms second, outer piece for non-straight forms last. Each piece is passed through the strict shape intersection filter before append. The caller identity is the same current world and block position; the paired shape-selection route remains neighbor-dependent through the adjacent stair states.

The collision list is passed to the same `Entity.move` axis loops as previously traced: Y, then X, then Z, preserving provider append order at each axis (`1.8.9 Entity.java:439–459`; `1.9 Entity.java:506–529`). The step-up path gathers its own list and repeats Y/X/Z before comparing the two alternatives (`1.8.9 :460–540`; `1.9 :530–619`). This closes that the multipart stair boxes are consumed sequentially in an ordered clip operation; it does not predict a concrete player trajectory. The source-owner residual comparison reported no additional stair-provider difference.

## State-dependent shape getter context

Both releases' `World.getCollisions` run on the query's world receiver. At each candidate coordinate the same border predicate selects the current stored state or leaves the stone fallback (World.java:916–922 in 1.8.9; :914–928 in 1.9). The old base provider receives that world, coordinate and the fetched state (`World.java:921–922`, `Block.java:339–350`); the new provider passes the same values to `BlockState.addCollisions` and `Block.addCollisions` (`World.java:922–928`, `Block.java:313–328`). Thus new state-based getters do not receive a neighboring world's state or a stale state object from another block position.

- **Cocoa:** 1.8.9 collision dispatch calls its `getCollisionShape(world,pos,state)`, which calls `updateShape(world,pos)` and reads `world.getBlockState(pos)` for `AGE`/`FACING` before returning the box (`CocoaBlock.java:58–90`). 1.9 `getShape(state,world,pos)` reads those fields from the state passed by the same collision query (`CocoaBlock.java:77–90`). The current-state/world caller identity is closed.
- **Skull:** 1.8.9 collision dispatch likewise calls `getCollisionShape(world,pos,state)`, which updates from `world.getBlockState(pos).FACING` before returning (`SkullBlock.java:70–94`). 1.9 uses the passed state's facing in `getShape(state,world,pos)` (`SkullBlock.java:74–88`). Current-state/world identity is closed.
- **Anvil:** 1.8.9 `updateShape(world,pos)` reads the facing from the queried world and sets mutable instance bounds (`AnvilBlock.java:67–74`); 1.9 `getShape(state,world,pos)` reads `state.FACING` (`AnvilBlock.java:97–100`). The new getter is supplied the current state's exact world/coordinate context. The old collision dispatch does not call `AnvilBlock.updateShape` itself (it reaches base `Block.getCollisionShape` through `Block.addCollisions`); the timing/source of the legacy mutable bounds is therefore still open for a complete getter-equivalence claim.
- **Chest:** old `updateShape(world,pos)` chooses bounds from the four neighboring positions in north/south/west/east order (`ChestBlock.java:56–68`); new `getShape(state,world,pos)` reads those same neighbor positions in that order and returns the corresponding shape (`ChestBlock.java:62–72`). The new world/position context is the current collision query. As with Anvil, the old collision callback does not itself invoke `updateShape`; the legacy mutable-bound timing remains open.
- **Stem:** old `updateShape(world,pos)` reads the state's age at the queried position and mutates the instance height (`StemBlock.java:108–120`); new `getShape(state,world,pos)` chooses a height by the passed state's age (`StemBlock.java:24–44`). The new getter receives the current state's context. The old base collision callback does not call `updateShape`, so legacy mutable-bound timing remains open.

The narrow caller/world-identity path is closed for all five named providers; the old Anvil/Chest/Stem mutable-shape scheduling remains open and is not claimed equivalent here. No new finding is drafted from these checks. Accepted pane and piston-head geometry remained unopened.
