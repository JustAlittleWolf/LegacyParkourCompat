# Moving-block full-cube swept-query witness r2 (1.8.9 → 1.9)

Scope: source-only, bounded witness for one ordinary moved block state (`Blocks.STONE`), piston facing EAST, `extending=true`, moving-block entity at block position `(0,0,0)`. This avoids every pane/piston-head geometry dependency. It establishes a reachable query/clipping difference for the core player move path; it does not assert a broad piston trajectory or downstream response parity.

## Paired progress order

Both client main loops call `world.tickEntities()` (`decompiled_minecraft/1.8.9/ornithe-feather/net/minecraft/client/Minecraft.java:1635`; `decompiled_minecraft/1.9/ornithe-feather/net/minecraft/client/Minecraft.java:1446`). In each version, `World.tickEntities` processes regular entities before entering its `blockEntities` phase and ticking each `Tickable` (`1.8.9 .../world/World.java:1159-1244`, especially `1219` and `1244-1254`; `1.9 .../world/World.java:1216-1302`, especially `1277` and `1302-1314`). Thus a player's entity-phase move on the tick after a moving-block entity advances from `(progress,lastProgress)=(0,0)` to `(0.5,0)` reads exactly those stored values before the next block-entity advance. Each moving-block `tick` assigns `lastProgress=progress`, increments progress by `0.5F`, and clamps at `1.0F` (`1.8.9 .../block/entity/MovingBlockEntity.java:128-147`; `1.9 .../block/entity/MovingBlockEntity.java:163-181`). This witness uses the first advanced state `(0.5F,0.0F)`, encountered in that following entity phase.

## Exact shape pair

Stone is registered in both versions (`1.8.9 .../block/Block.java:827`; `1.9 .../block/Block.java:674`) and is `StoneBlock extends Block` with no collision-shape override (`.../block/StoneBlock.java:16-21`). In 1.8.9, `Block` initializes its default bounds to `(0,0,0)-(1,1,1)` (`.../block/Block.java:201-210`) and returns a world-positioned box from `getCollisionShape` (`.../block/Block.java:346-350`). In 1.9, `Block.getShape` returns `FULL_BLOCK_SHAPE` (`.../block/Block.java:253-255`), and its collision shape delegates to that state shape (`.../block/Block.java:326-328`).

For 1.8.9, `MovingBlock.getCollisionShape` samples `getProgress(0.0F)`, which is `lastProgress` (`.../block/MovingBlock.java:118-130`; `.../block/entity/MovingBlockEntity.java:54-60`). Extending converts that progress to `1-progress`; with `lastProgress=0`, EAST's positive X branch subtracts `1` from the full cube's `maxX` (`.../block/MovingBlock.java:162-197`). Emitted world-space shape at `(0,0,0)` is therefore `[0,0] × [0,1] × [0,1]`.

For 1.9, `MovingBlock.getCollisionShape` delegates to `MovingBlockEntity.getShape` (`.../block/MovingBlock.java:131-134`). That method unions shapes sampled at current and last progress (`.../block/entity/MovingBlockEntity.java:79-88`). For extending, each sample offset is `progress-1` (`.../block/entity/MovingBlockEntity.java:75-77`): current `.5` moves the cube by `-.5`, giving `[-.5,.5]`; last `0` moves it by `-1`, giving `[-1,0]`. Their union is `[-1,.5] × [0,1] × [0,1]`.

The block collision hook tests intersection before appending the emitted box in both versions (`1.8.9 .../block/Block.java:339-344`; `1.9 .../block/Block.java:313-324`). Both `Box.intersects` implementations are strict at touching faces (`1.8.9 .../util/math/Box.java:153-158`; `1.9 .../util/math/Box.java:197-202`).

## Concrete on-foot player move query

Use a regular (not riding), airborne player with current AABB `x=[-1.6,-1.0]`, `y=[0.2,2.0]`, `z=[0.2,0.8]` and request `(dx,dy,dz)=(0.5,0,0)`. These dimensions match the base entity width `0.6F` and height `1.8F` (`1.8.9 .../entity/Entity.java:143-144`; `1.9 .../entity/Entity.java:165-166`); the x center is `-1.3`, z center `.5`, feet y `.2`. This is ordinary player `Entity.move`, reached by `LivingEntity` travel calls (`1.8.9 .../entity/living/LivingEntity.java:1165,1190,1218`; `1.9 .../entity/living/LivingEntity.java:1328,1378,1407,1435`). `Entity.move` expands the current AABB by requested displacement, gathers `World.getCollisions`, clips Y then X then Z (`1.8.9 .../entity/Entity.java:439-459`; `1.9 .../entity/Entity.java:506-529`). With `dy=0` and `onGround=false`, the step-up condition is false (`1.8.9 .../entity/Entity.java:447-468`; `1.9 .../entity/Entity.java:515-538`).

The swept query has x `[-1.6,-0.5]` and overlaps y/z of the moving block. The scan bounds differ observably here: old 1.8.9 sets `i=floor(-1.6)=-2`, `j=floor(-0.5+1)=0` and loops `o < j`, so it visits x=-2,-1 and skips cell x=0; 1.9 sets `i=floor(-1.6)-1=-3`, `j=ceil(-0.5)+1=1` and loops `o < j`, so it visits x=-3,-2,-1,0. These are the exact horizontal bounds in 1.8.9 `World.getCollisions` (`.../world/World.java:891-922`) and 1.9 (`.../world/World.java:893-928`). Assume an otherwise empty local world: no other block or entity collision boxes intersect the swept query, the world border is clear, and cell `(0,0,0)`'s chunk is loaded and contains the moving-block block/entity pair. The displacement difference is jointly due to scan coverage and emitted shape: old 1.8.9 never queries cell `(0,0,0)` for this swept range, while 1.9 does query it and emits its union shape `[-1,0.5]` whose strict overlap with the swept query is `(-1,-0.5)`. Therefore old `dx` stays `0.5`; new appends the moving-block box. On X clipping, `Box.intersectX` sees the player's current maxX `-1` at the emitted box's minX `-1`; its positive-motion branch clips the requested `0.5` to the gap `0` (`1.8.9 .../util/math/Box.java:93-108`; `1.9 .../util/math/Box.java:137-152`). The resulting exact source-level displacement difference is old `dx=0.5`, new `dx=0.0` for this query/state.

## Dependency and acceptance status

Closed for this witness: vanilla full-cube Stone shape; both progress update orders; old sampled-last vs new previous/current union; strict shape-query intersection; the differing old/new scan coverage for cell zero; and the paired `Entity.move` X clipping consequence on the non-riding player path. The observed displacement contrast is the combined scan-bound and union-shape result, not a shape-only result. It is not contingent on custom provider geometry, multipart stairs, anvil/chest/cocoa/skull/stem state or geometry, or piston-head/pane shapes. No trajectory beyond the stated pair state and single move query is inferred.

Source evidence is sufficient for an independent source acceptance of this narrow moving-block sweep candidate. Remaining release acceptance and applicability questions are owned by the pair coordinator; do not generalize this witness to every block, tick phase, or piston response.
