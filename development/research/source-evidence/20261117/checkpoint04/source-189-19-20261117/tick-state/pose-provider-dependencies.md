## Finite pose-query caller and dispatch path

1.9 `PlayerEntity.tick()` calls `updatePlayerPose()` after its superclass movement (`PlayerEntity.java:244–245`). For the accepted ordinary witness, an awake, non-fall-flying, sneaking player proposes `0.6F × 1.65F`. `updatePlayerPose()` keeps the existing box minimum corner, forms a box at the proposed width and height, calls `World.getCollisions(Box)`, and applies `setSize` only when that query returns false (`PlayerEntity.java:284–307`). Width stays `0.6F`, so this operation changes height without directly translating the player. The same method has no `onGround` gate; grounded is the witness condition, not an additional source predicate.

The query's finite block path is:

1. `World.getCollisions(Box)` computes the candidate AABB's integer scan envelope, checks the loaded-chunk column gate, returns collision immediately at the world-border boundary, and reads each admitted `BlockState` (`World.java:1012–1037`).
2. It passes the state, world, position, proposed box, collision list, and `entity = null` to `BlockState.addCollisions`. This overload is a block-only boolean query: unlike `World.getCollisions(Entity, Box)`, it does not append entity collision boxes (`World.java:1012–1044`).
3. `StateDefinition.State.addCollisions` dispatches to its block with the exact state (`StateDefinition.java:353–356`). The base `Block.addCollisions` asks `state.getCollisionShape(world,pos)`, translates a non-empty local box to block coordinates, and adds it only when it intersects the proposed box (`Block.java:313–328`). State-aware shape calls then dispatch through `Block.getCollisionShape` to `state.getShape(world,pos)` and any block override.

Thus the resize gate is a Boolean OR over the intersecting collision outputs of the block states visited by this 1.9 query, plus its loaded-area and world-border gates. A block shape outside the proposed `0.6 × 1.65` volume cannot veto this query. The pose acceptance closes the unobstructed witness only; it does not establish that every state or provider in an obstructed query returns the same result across the pair.

There is no matching 1.8.9 player pose resize query: the accepted source inventory found no `updatePlayerPose` call or sneaking dimension change in `PlayerEntity.tick()`. 1.8.9 movement instead gathers entity-aware collision boxes through `World.getCollisions(Entity, Box)` (`World.java:891–944`); that method has a different scan envelope and appends entity responses after block dispatch. Its movement-query evidence is not a substitute for auditing the new 1.9 pose gate.

1. The accepted pose witness is closed because its proposed box has no colliding block shape. No provider equivalence is needed to establish that particular empty-volume witness.
2. For obstructed proposed boxes, the 1.9 resize gate still depends on a finite but not fully audited matrix of visited block states and their collision providers. Exact queried cells are determined by the candidate box, loaded chunks, border, and 1.9 scan envelope; each admitted block state then contributes zero or more provider boxes. The existing regex inventory is not an independent audit of every 1.9 provider/state/output combination.
3. `StairsBlock` state-to-coordinate evidence is awaiting a bounded correction audit, and multipart provider effects still depend on the complete movement resolver for ordinary `Entity.move` queries. The pose query itself is a Boolean test, so do not transfer a sequential-clip verdict to its early-exit collision result.
4. Moving-block moved-state collision shape/overlap remains a separate source dependency; the accepted piston response procedure does not close it. The frozen pane-connection and piston-head-arm geometry remains excluded.
5. The 1.8.9 Anvil/Chest render/ray-trace cache lifecycle and malformed Door companion state are exclusions or unestablished applicability, not executable player pose-provider findings. Reopen only with new deterministic local-player-reachable source evidence.
6. This bounded dependency map is not the complete tick/provider inventory or a pair-wide independent coverage audit. Product implementation readiness and runtime parity remain separate.
