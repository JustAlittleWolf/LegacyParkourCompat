## Compared producer path

- `net/minecraft/server/network/ServerGamePacketListenerImpl.java:756-892`, `handleMovePlayer(ServerboundMovePlayerPacket)`, is the server's client-movement handler. With `awaitingPositionFromClient != null`, a client that has not acknowledged the pending correction after more than 20 ticks is sent back to that pending position. The sleeping branch corrects when the requested movement squared exceeds 1.0. The movement-speed check is entered only when `!this.player.isChangingDimension()` and `(!this.player.getLevel().getGameRules().getBoolean(GameRules.RULE_DISABLE_ELYTRA_MOVEMENT_CHECK) || !this.player.isFallFlying())` (`:823-826`). The method sets `s = this.player.isFallFlying() ? 300.0F : 100.0F` and corrects to the current position only if `q - p > s * r && !this.isSingleplayerOwner()` (`:828-830`); `r` is the received-minus-known movement-packet count and is reset to 1 when greater than 5 (`:818-820`). Here `p` is the player delta-movement length squared and `q` is the squared displacement from the first good coordinates (`:795-801`). The moved-wrong/collision branch corrects to the last accepted position when the ordinary movement checks reject the proposed position after collision validation. Invalid packet coordinates disconnect instead of invoking a position correction. These are vanilla server validation/correction gates, not historical movement rules.
- `ServerGamePacketListenerImpl.java:903-920`, `teleport(double,double,double,float,float)` and its relative-argument overload, performs the common write. The default overload supplies an empty relative-argument set. The implementation derives coordinate/rotation offsets for relative flags, stores the pending target in `awaitingPositionFromClient`, increments/wraps the teleport ID, records the tick, calls `player.absMoveTo(...)`, then sends `ClientboundPlayerPositionPacket` carrying the adjusted coordinates, relative flags, and ID to the player connection.
- `net/minecraft/server/level/ServerPlayer.java:619-711`, the dimension-change/portal path, invokes `connection.teleport(...)` after the player is placed in the destination level. `ServerPlayer.java:1369-1402`, `teleportTo(ServerLevel, ...)`, distinguishes two routes. When `serverLevel == this.level`, the same-level branch calls `connection.teleport(d,e,f,g,h)` directly (`:1372-1374`). In the cross-level branch, it sends the destination respawn data, removes/transfers the player, calls `moveTo` and `setLevel`, then invokes the same writer (`:1382-1398`). Both branches emit the same position-correction packet. This report does not evaluate upstream command, portal, or dimension behavior.
- `net/minecraft/network/protocol/game/ClientboundPlayerPositionPacket.java` contains the unchanged wire fields and relative-argument encoding for position, rotation, and correction ID. Its client dispatch/receiver and the corresponding `ClientPacketListener.handleMovePlayer` path are already covered by the accepted base inventory above and are not re-reviewed here.
