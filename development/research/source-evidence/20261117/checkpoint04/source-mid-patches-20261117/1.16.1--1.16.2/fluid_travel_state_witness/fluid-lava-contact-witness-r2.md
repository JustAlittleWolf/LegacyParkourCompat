## Static witness

Use a vanilla command-enabled map with a source lava block at `(0, 63, 0)` and air above. Start with an established local player in dry air, already airborne (`onGround=false`), with `firstTick=false` and `isTouchingLava=false`. Issue an absolute `/tp` to `(0.5, 63.5, 0.5)` in the same dimension before the next client tick, then press jump for that tick. Keep flying ability off, so `Player.isAffectedByFluids()` is true. `Blocks.LAVA` constructs a `LiquidBlock` with `Fluids.LAVA`; its default `LEVEL` state is the source fluid. Player standing dimensions are `0.6 × 1.8` (`Player.STANDING_DIMENSIONS`, `Player.java`), and `Entity.setPos()` builds its AABB from `x ± width/2`, `y` through `y + height`, and `z ± width/2` (`Entity.java`, lines 321–325). The AABB spans x `[0.2,0.8]`, y `[63.5,65.3]`, and z `[0.2,0.8]`, so it intersects the source lava and has no solid support. An isolated source lava block with air above has height `8/9` from `FlowingFluid.getHeight`/`LavaFluid.Source.getAmount`, giving fluid top `f = 63 + 8/9 ≈ 63.8888889`. The scanner contracts the AABB: `deflate(0.001)` sets its minimum Y to `63.501`, which is below `f`; the stored lava height is `f - 63.501 ≈ 0.387889`, positive. This is the corrected arithmetic; r1's above-surface position did not pass the scanner gate.

The teleport is a source-supported map setup: `TeleportCommand.performTeleport()` routes a same-dimension `ServerPlayer` through `ServerGamePacketListenerImpl.teleport()`, and `ClientPacketListener.handleMovePlayer()` applies the absolute position with `setPosRaw`/`absMoveTo`; that handler does not call `Entity.move()` or `checkInsideBlocks()`. Choose an already airborne local player in dry air so the old flag is false before the command. The teleport changes position but leaves the client `isTouchingLava` flag false until the next `Entity.move()` callback. This establishes a legal static map state without claiming natural world generation or self-propelled arrival.

In 1.16.1, `Entity.baseTick()` refreshes fluid state before `LivingEntity.aiStep()`. `updateFluidHeightAndDoFluidPushing(LAVA, ...)` stores the same positive fluid height here, but `Entity.isInLava()` reads only the stale `isTouchingLava` flag, which remains false after the teleport. Later in the tick, `Entity.move()` clears that flag and `checkInsideBlocks()` invokes `LiquidBlock.entityInside()`; this is after the jump decision, so the old flag is too late for the current `LivingEntity.aiStep()` branch.

In 1.16.2, the same scan runs after the water update and `Entity.isInLava()` reads `!firstTick && fluidHeight[LAVA] > 0`. Since `firstTick=false` and the scan stores `≈0.387889`, `isInLava()` is true before the jump decision. The 1.16.2 packaged lava tag includes the source fluid, as verified above.

The local player path reaches `LivingEntity.aiStep()` through `LocalPlayer` and `Player`; `LivingEntity.aiStep()` calls virtual `serverAiStep()` before its jump branch, and `LocalPlayer.serverAiStep()` copies the pressed jump input to `jumping`. With `onGround=false` and `isInWater=false`, 1.16.1 sees `isInLava=false`, selects zero water height, and does not execute a liquid jump. 1.16.2 sees `isInLava=true`, selects the positive lava height, and calls `jumpInLiquid(FluidTags.LAVA)`. `LivingEntity.jumpInLiquid()` adds `0.04` to vertical velocity. After the old version's later movement callback, both versions may report lava contact on subsequent ticks; the witnessed difference is the first AI jump decision after teleport. This is a direct source-level movement-state difference.

The old `LiquidBlock.entityInside()` callback, the new accessor, the deflated fluid scan, and the jump branch above are each bound by the exact source hashes in the table. ## Limits

This witness depends on a command-mediated position change between the old contact callback and the next fluid refresh. It establishes a reachable input state and exact tick-order effect for the lava predicate and `LivingEntity` jump response, not a broader trajectory or map-generation outcome. It does not establish full fluid callback/provider coverage, runtime parity, or pair completion.
