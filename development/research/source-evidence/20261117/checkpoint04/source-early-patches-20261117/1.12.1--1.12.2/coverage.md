## Reachable local-player movement inventory

The paired source roots cover the local player tick, inherited player/living/entity travel, position and velocity writes, collision clipping, provider registrations and callbacks, fluids, dimensions/pose, equipment/attributes/effects, world queries, and external player-response handlers. `Entity.java` and the core movement method bodies remain byte-identical. `PlayerEntity.java` changes only its saved DataVersion literal (1241→1343). `LocalClientPlayerEntity.java` adds inventory-screen closure while in a portal; this is a UI/menu transition and has no player position, velocity, size, movement-input or collision write in its changed body.

### Changed behavior and dispositions

- **World block-entity list maintenance — dependency open.** `World.tickEntities()` moves cleanup of `removedBlockEntities` from after the block-entity loop to before it. This method is called on the client by `Minecraft.tick()` (`1.12.1` lines 1462–1469), before `ClientWorld.tick()` later in the same client tick (`Minecraft.java` lines 1479–1485; `ClientWorld.tick()` calls `super.tick()` and then `chunkCache.tick()`, lines 70–92). `WorldChunk.unload()` marks the chunk not loaded and queues its block entities through `World.unloadBlockEntity()` (lines 651–660); unload entries are not marked removed there. The old tick loop checks `!blockEntity.isRemoved()`, `hasWorld()`, `isChunkLoaded(pos)` and world-border containment before calling `Tickable.tick()`; client `ClientWorld.isChunkLoadedAt(..., allowEmpty=true)` returns true (lines 104–107). Thus a queued, still-attached block entity in a removed chunk can pass the old tick gates once before old cleanup, while the new order removes it first. The unchanged `MovingBlockEntity.tick()` calls `moveEntities()` for progress below one, and that method can select and move any intersecting entity with `Entity.move(MoverType.PISTON, ...)`, including the player (1.12.2 `MovingBlockEntity.java` lines 116–156, 273–289). **Not an accepted movement finding yet:** the exact normal client chunk-unload schedule does not establish that such an entity can overlap the local player at this extra tick. Keep this edge partial until that reachability dependency is closed or excluded with exact source evidence.
- **Farmland/grass-path set-dirt response — server-only exclusion.** In `FarmlandBlock.setDirt`, 1.12.1 replaces farmland with dirt, queries entities overlapping the resulting dirt collision box and sets each entity position to that box's `maxY`. In 1.12.2 it queries the static upper slice `[0.9375,1.0]` and calls `entity.teleport(entity.x, entity.y + min(0.0625, 1.0 - entity.getShape().minY) + 0.001, entity.z)`. The new path can alter a player's server-side position, but all sources that reach this method are excluded from the local-client movement loop: `FarmlandBlock.onFallenOn` explicitly starts with `!world.isClient`; `WorldChunk.setBlockState()` invokes `Block.onAdded` only when `!world.isClient`; and `World.setBlockState()` invokes neighbor/observer updates only when `!world.isClient` (lines 255–288), which is the route to `neighborChanged`. `GrassPathBlock` calls the new helper only from its `onAdded`/`neighborChanged` path. Client block packets enter `ClientWorld.setBlockStateFromPacket()` then `World.setBlockState()`, but the shared `WorldChunk` code does not call `onAdded` on a client. Therefore the changed teleport cannot be promoted to local-client movement evidence; server-side movement is out of scope. Source identities: 1.12.1 `FarmlandBlock.java` SHA-256 `B5902F8FAB6BB9388BE5E488021A4977783FEA0CA9404798460F207980374DA2`; 1.12.2 `FarmlandBlock.java` SHA-256 `D84C75DAE139181B5D58CFA34F3CB77C5B2D4BDA63D6AD9C3B52A47350BD0B98`; `GrassPathBlock.java` changes only to call that same server-only helper.
- **End portal callback — equivalent gate.** `EndPortalBlock.onEntityCollision()` moves `!world.isClient` earlier in a short-circuit conjunction; it still requires the same non-client world, non-riding/no-passenger/portal-capable entity, and shape intersection. The moved condition only suppresses earlier pure predicate reads on clients; it does not alter a movement result.
- **Ender pearl / thrower reference — server/projectile exclusion.** `ThrownEntity.thrower` becomes protected and `EnderPearlEntity.changeDimension()` clears it when the pearl changes dimension. The player teleport in `EnderPearlEntity.onCollision()` is inside `if (!world.isClient)` and the changed body is on the non-player projectile. Projectile motion and server-side teleport handling are outside this local-client player movement slice.
- **Client ambient sound RNG — audio exclusion.** `ClientWorld` adds an upper squared-distance bound (`d < 256`) to cave ambience. This changes whether the audio routine consumes its local world random draws; no changed player movement method consumes that value, and the sound selection/output remains an excluded audio operation. No movement delta is asserted from the random-stream change.
- **Other changed paths** are version/DataVersion strings, save migration thresholds, keep-alive protocol representation/timeout handling, recipe/loading-screen changes, server-only sleep iteration, resource-pack/UI/render text, and metadata. They do not write local-player movement state.

The data-fixer delta is likewise only the current-version literal (1241→1343); `DataFixes.java` keeps the same registrations, all registered fix implementations are unchanged, and the maximum registered fix version is 1125. The version bump does not enable a new player-data transform.
