## Tick graph and paired results

The paired call order is: `LocalClientPlayerEntity.tick()` (1.11.2 159–173; 1.12 164–178) → `PlayerEntity.tick()` (174–250 both) → `LivingEntity.tick()` (1.11.2 1581–1643; 1.12 1619–1681) → `Entity.tick()`; within the living tick, `mobTick()` runs after the inherited tick body. In `LivingEntity.mobTick()` (1.11.2 1737–1808; 1.12 1781–1852), the local client invokes `serverTickAi()` after the common cooldown/interpolation and velocity-cutoff work, applies jump selection, damps input axes, runs `flyingTick()`, invokes virtual `moveRelative`, then performs entity pushing. The earlier accepted report paired the wrapper and direct ordering methods and confirms that the jump gates (water, lava, grounded/cooldown), `jump()`'s base impulse/boost/sprint impulse, player override, pose selection and direct packet-response bodies are unchanged. The paired method call order and `PlayerEntity.updatePlayerPose()` (1.11.2 295–319; 1.12 291–315) dimensions/clearance gate also show no new shared player movement change.

### Changed shared movement operation: input-axis API

`LivingEntity.mobTick()` changes its final call from `moveRelative(sidewaysSpeed, forwardSpeed)` (1.11.2 1803) to `moveRelative(sidewaysSpeed, verticalSpeed, forwardSpeed)` (1.12 1844). The `LivingEntity.moveRelative` (1.11.2 1388; 1.12 1425) and `PlayerEntity.moveRelative` (1.11.2 1387; 1.12 1386) overrides change signatures correspondingly and forward those values to the new four-argument `Entity.updateVelocity` form in each travel branch. In the earlier report's complete PlayerEntity-hierarchy write search, `verticalSpeed` has no writer in the player hierarchy; the only write is in sibling `MobEntity`. Thus the added vertical axis is zero on the ordinary local-player path at this call. This is the already-bound axis/API difference, not a newly found independent delta. The unchanged player override still applies the ability-flight `speedInAir`, preserves/restores the pre-call vertical velocity scaled by `0.6`, clears fall distance/flag while flying, and records displacement stats after `super.moveRelative`.

### Other changed bodies reached by the tick

- In `LivingEntity.tick()` (walk animation 1.11.2 1559–1565; 1.12 1591–1598), the walk-animation speed input adds vertical displacement only for `FlyingAnimal`; `PlayerEntity` is not a `FlyingAnimal`. This changes animation state only for the local player path by retaining the old horizontal-distance calculation.
- The body-yaw calculation in `LivingEntity.tick()` (1.11.2 1647–1655; 1.12 1685–1699) adds a wrapped-yaw comparison and may select the opposite body orientation when horizontal movement points sufficiently behind yaw. The writes are body-orientation/animation state after travel; movement calls use entity yaw and this code does not write position, velocity, box or player pose. No local-player movement delta is supported by this changed body.
- `PlayerEntity.tick()` removes the reset of `minecartTravelStartPos` (1.11.2 235–238), whose remaining reader served the minecart-distance statistic and whose field/read are removed in 1.12. No local walking/jumping/travel input or movement state is affected.
- `PlayerEntity.mobTick()` (1.12 413–480) adds shoulder-entity ambient/drop handling. This is a newly introduced companion feature, not a changed historical implementation shared by both versions. On the local client, the `!world.isClient` drop branch is false; only `abilities.flying` can enter the outer condition, where dropping clears shoulder data and entity creation remains client-gated. No player position, velocity, box, pose, jump input or travel input is written by that route. It has no 1.11.2 counterpart and is not evidence of a changed shared movement rule.
- `LocalClientPlayerEntity.mobTick()` (1.11.2 632–790; 1.12 648–807) adds `tutorial.onPlayerInput(input)` (1.12 694) immediately after `input.tick()`. In 1.12, the tutorial forwards the already-produced input to the active tutorial step; the movement tutorial only sets its `moved` flag when a movement/jump key is active. It does not mutate the input or player movement state, so the subsequent same input scaling and superclass tick path are preserved. `LocalClientPlayerEntity.tick()` and `serverTickAi()` have only shifted source lines in the paired tick bodies. `ClientPlayerEntity.java` is byte-identical.
- Other `LivingEntity.java` changes in the file diff concern damage/hurt, dismount, sound, status APIs, and kill/stat/criterion handling; no changed body on the ordinary local-player tick graph was found that writes the movement state listed below. `PlayerEntity.java` changes outside the tick include newly introduced shoulder state, sleep/respawn/death actions, and non-movement API changes; direct response and lifecycle closure remains outside this slice.
