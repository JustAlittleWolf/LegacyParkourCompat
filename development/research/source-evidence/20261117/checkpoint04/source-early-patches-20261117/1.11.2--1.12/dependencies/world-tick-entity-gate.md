## Paired behavior and gates

In 1.11.2, `World.tickEntity(Entity)` delegates to `tickEntity(entity, true)` (World.java:1404–1405). The two-argument body floors `x` and `z`, sets the radius constant to 32, then wraps the entire bookkeeping/tick body in `!requireLoaded || isAreaLoaded(i - 32, 0, j - 32, i + 32, 0, j + 32, true)` (1408–1465). If that condition is false, it returns by falling through without snapshotting previous position/rotation, ticking the entity, or running chunk bookkeeping. If admitted, `entity.tick()` (or `rideTick()`) still requires both `requireLoaded` and `entity.inChunk` (1418–1425); passenger recursion also requires `requireLoaded && entity.inChunk` (1464–1467).

In 1.12, the same overload still delegates with `true` (1408–1409), but the area calculation and early return are guarded by `if (!(entity instanceof PlayerEntity))` (1412–1424). Thus non-player entities retain the old loaded-area rejection; all `PlayerEntity` instances bypass that area test. The shared body then snapshots previous position/rotation. Actual `entity.tick()`/`rideTick()` remains gated by `requireLoaded && entity.inChunk` (1427–1434), and passenger recursion remains gated by `requireLoaded && entity.inChunk` (1473–1476). The change removes only the area-loaded prerequisite for players; it does not force a player tick when `inChunk` is false.

## Callers and local-player reachability

- In both versions, `Minecraft` invokes `this.world.tickEntities()` in its unpaused client tick (`Minecraft.java`: 1.11.2 line 1419; 1.12 line 1468). `ClientWorld` does not override `tickEntities` or `tickPlayers`; the base `World.tickEntities()` iterates `entities` and calls the one-argument `this.tickEntity(entity3)` for nonremoved entities except `ServerPlayerEntity` (1.11.2 World.java:1227–1290; 1.12:1231–1294). That dispatch supplies `requireLoaded=true`.
- `Minecraft` adds its local player to the world on client-world setup and respawn (`Minecraft.java`: 1.11.2 lines 1893, 1925; 1.12 lines 1952, 1989). `ClientWorld.addEntity` delegates to `super.addEntity` (ClientWorld.java:165 onward in both versions), placing accepted entities into the `World.entities` list (World.java:881 onward in 1.11.2; 885 onward in 1.12). In both versions, `LocalClientPlayerEntity` extends `ClientPlayerEntity`, which extends `PlayerEntity` (1.11.2 declarations at LocalClientPlayerEntity.java:77 and ClientPlayerEntity.java:21; 1.12 at LocalClientPlayerEntity.java:80 and ClientPlayerEntity.java:21). The local player is not a `ServerPlayerEntity`, so it is eligible for the regular entity loop and reaches the changed type gate.
- Other direct invocations found in the exact sources are passenger recursion from `World.tickEntity`; `ServerWorld`'s entity loop/override; `Entity` dimension-transfer and `Entity.teleport` calls with `requireLoaded=false`; and `PlayerManager` / `ServerPlayNetworkHandler` calls with `requireLoaded=false`. All these false-argument calls bypass the loaded-area predicate on both versions; the `Entity.teleport` caller is general, not inherently server-only. Server callers are outside historical client movement. The client `World.tickEntities` → local player path above is the relevant scheduled `requireLoaded=true` caller.

## Block-entity distinction and disposition

The adjacent block-entity schedule is a separate loop over `World.tickingBlockEntities` in `World.tickEntities()` (1.11.2 World.java:1315 onward; 1.12:1319 onward). It independently ticks a `Tickable` block entity only when it is not removed, has a world, its own position passes `isChunkLoaded`, and the world border contains that position. It does not call `tickEntity` and does not use the player-type area gate. This candidate is specifically entity scheduling, not block-entity scheduling.

**Disposition: player-eligible movement dependency; closed for this exact gate.** Static source reachability proves the eligible local client player reaches the changed `PlayerEntity` branch with `requireLoaded=true`; when the area predicate would be false, 1.11.2 skips the whole entity body while 1.12 proceeds to the unchanged `inChunk` tick gate. This is movement-relevant because that body controls whether the client player is ticked. No runtime/map frequency or trajectory consequence is asserted. This bounded disposition does not close pair coverage or infer an intermediate introduction boundary.
