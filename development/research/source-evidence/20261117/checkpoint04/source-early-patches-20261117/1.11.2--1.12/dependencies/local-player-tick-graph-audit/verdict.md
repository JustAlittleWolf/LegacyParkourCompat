## Checks

- Recomputed the four paired Java source hashes from the exact `decompiled_minecraft/1.11.2/ornithe-feather/` and `decompiled_minecraft/1.12/ornithe-feather/` trees. All match the report: `LivingEntity.java` (`bb7dc6c9…279f2f` / `190e9ac5…f1ee6`), `PlayerEntity.java` (`87fe94fa…d948b` / `6a9d5f42…ee063`), `LocalClientPlayerEntity.java` (`65c2747b…59ed` / `d7237b8b…d7d1`), and byte-identical `ClientPlayerEntity.java` (`207a0ff4…97809` on both sides).
- The paired tick bodies support the reported order: local-client `tick` delegates through player and living `tick`, which calls `Entity.tick` before living tick work; `LivingEntity.tick` calls virtual `mobTick`, and local/player overrides perform their own work before delegating to the shared living `mobTick`. In that shared path the jump selection precedes travel-axis damping, `flyingTick`, virtual `moveRelative`, then entity pushing. The changed `verticalSpeed` argument is the already-bounded axis/API change.
- I did not find support for an unconditional claim that `verticalSpeed` is always zero. In 1.12, `LivingEntity.verticalSpeed` is public and is passed at the shared call; a whole-source exact-tree search finds its sole vanilla assignment in sibling `MobEntity`. There is no vanilla assignment on the inspected player/local-player tick path, and the field's default value is zero. The supported conclusion is therefore limited to the vanilla local-player path absent external mutation; it does not establish a guarantee against other code writing the public field.
- The 1.12 local-client tick calls `tutorial.onPlayerInput(input)` after `input.tick()`. `Tutorial` forwards the same input; the only concrete `onPlayerInput` override in the 1.12 tutorial package sets `MovementTutorialStep.moved` from key booleans. It does not mutate the input or player movement state. No additional movement delta is supported by this observer.
- `PlayerEntity` has no shoulder-data methods or shoulder references in 1.11.2; the feature appears in the 1.12 player source. In the newly added tick path, ambient playback reads shoulder data, while dropping mutates only shoulder data and entity creation is guarded to the logical server. The client can enter the drop path when `abilities.flying` is true, but the route writes no player position, velocity, box, pose, jump input, or travel input. This is an added companion feature, not a shared historical movement-rule change.
