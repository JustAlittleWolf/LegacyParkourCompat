# MovingBlock extension-head source flag correction: 1.10.2 → 1.11

**Conclusion: distinct conditional player collision-provider candidate.** For the extension-head payload created by `PistonBaseBlock.move`, the constructor flag changes from `(extending=true, source=false)` in 1.10.2 to `(true, true)` in 1.11. In 1.11 that bit selects a synthetic piston-head state whose `SHORT` property changes with progress. Its collision callback emits different arm boxes while short, so an ordinary eligible local-player collision query can receive a different box list. The source flag does not change query eligibility or the callback's no-clip gate. This establishes a conditional collision-provider difference, not a particular map trajectory or net displacement.

## Flag path and collision consequence

`PistonBaseBlock.move` constructs the extension head's moving entity from a normal `PISTON_HEAD` state. In 1.10.2 it passes `true, false` at line 328; in 1.11 it passes `true, true` at line 317. The constructor assigns the two booleans directly to `extending` and `source` (`MovingBlockEntity` 1.10.2 lines 28–33; 1.11 lines 39–44). The client event path is the same as described in the prior report, so this constructor-created payload is reachable on the client.

Neither release serializes `source`: `writeNbt` writes the moved block ID/data, facing, progress and `extending` only (1.10.2 lines 200–208; 1.11 lines 285–293), and `readNbt` restores those fields without assigning `source` (1.10.2 lines 190–197; 1.11 lines 275–282). On a newly constructed entity loaded from NBT, Java's default leaves `source=false`. Thus the `false → true` transition is carried by the in-memory client event payload, not by persisted NBT. This correction concerns that producer path.

The 1.10.2 `MovingBlock` has no entity-aware `addCollisions`; `getCollisionShape` delegates to `MovingBlockEntity.getShape`, which samples the moved state's shape at current and prior progress (lines 132–143; entity lines 80–89). For the extension-head payload, `source` is not read by this collision path (its other occurrences are field declaration, constructor assignment and getter). Both flag values therefore use the captured default-long piston-head state in that flattened shape path.

In 1.11 `MovingBlock.addCollisions` (lines 134–140) forwards the query entity to `MovingBlockEntity.addCollisions`. For an extending entity, the retract-only `!extending && source` base-state branch at entity lines 296–298 does not run. The following branch selects a synthesized piston-head state when `source` is true (lines 300–310); otherwise it selects `movedState`. The synthesized state sets `SHORT` from `extending != (1.0F - progress < 0.25F)` (line 307). With `extending=true`, this is short through progress `0.75F`, then long above that threshold. The selected state's collision boxes are queried and translated back (lines 312–320). `PistonHeadBlock.addCollisions` accepts but does not inspect the entity argument (1.10.2 lines 64–68; 1.11 lines 70–74); in 1.11 its arm-shape selection reads `SHORT` and selects distinct short-arm boxes (lines 76–92). Therefore the flag changes the emitted collision geometry for the extension head during the short interval, even though the main head box is the same.

For the local player's ordinary `Entity.move` query, `World.getCollisions(this, ...)` supplies the player as a non-null entity, and the 1.11 `MovingBlock` dispatch passes it through. `NOCLIP_DIR` is set only around the moving entity's own piston response; `addCollisions` suppresses its shape only when progress is below 1 and that thread-local is true (1.11 `MovingBlockEntity.java`: 158–160, 295–301). The separate ordinary player query is not under that scoped flag, so source does not exclude it. The nested piston-head callback itself has no entity-specific gate. The source delta consequently changes candidate boxes, not which ordinary player queries are eligible. Whether a particular player box intersects the differing arm region is world/pose dependent and is not asserted here.
