## Source trace and audit

- **1.12.2:** `Entity.baseTick` calls `checkWaterCollisions()` at `Entity.java:382`; `checkWaterCollisions` uses `getShape().grown(0.0, -0.4F, 0.0).contract(0.001)` and delegates to `World.applyLiquidDrag` at `Entity.java:948-963`. `World.applyLiquidDrag` scans floor(min) to ceil(max) bounds, considers cells with matching water material, accepts the surface when `ceil(bounds.maxY) >= y + 1 - LiquidBlock.getHeightLoss(LEVEL)` and accumulates each block's `applyMaterialDrag` result (`World.java:1579-1609`). If the sum is nonzero and `entity.hasLiquidCollision()`, it normalizes the combined vector and adds `0.014` times each component to velocity (`World.java:1612-1618`). `LiquidBlock.applyMaterialDrag` adds `getFlow` (`LiquidBlock.java:183-185`); `getFlow` derives horizontal differences from liquid depths, applies the falling/solid-face downward term for LEVEL >= 8, and returns a normalized vector (`LiquidBlock.java:139-180`). `PlayerEntity.hasLiquidCollision()` is false only while flying (`PlayerEntity.java:1732-1735`).
- **1.13.2:** `Entity.tick` calls `baseTick`; `baseTick` calls `m_03231680()` at `Entity.java:332-340,393-395`; that method runs `checkWaterState()` then separate water/submersion and swimming updates (`Entity.java:947-951`). `checkWaterState` reaches `m_69693160(FluidTags.WATER)` (`Entity.java:961-975`). The current scan uses `getShape().contract(0.001)` and a loaded-area guard (`Entity.java:2509-2527`). It considers tagged fluid cells only when `q + fluidState.getHeight() >= box.minY`, updates running maximum depth `d = max(surface - box.minY, d)`, and, when `hasLiquidCollision()` is true, obtains that cell's flow, scales it by the running max depth while `d < 0.4`, and adds it to the vector/count (`Entity.java:2528-2551`). It averages by contributing cell count, normalizes only non-`PlayerEntity` vectors, then adds `0.014` times the components to velocity (`Entity.java:2554-2567`). Player current is therefore not normalized after aggregation; `PlayerEntity.hasLiquidCollision()` is false only while flying (`PlayerEntity.java:1825-1828`).
- `FluidState.getHeight()` delegates to the fluid (`FluidState.java:29-31`); `FlowingFluid.getHeight()` is `state.getLevel() / 9.0F` (`FlowingFluid.java:448-450`). `FlowingFluid.getFlow()` uses neighboring fluid heights to form the horizontal vector and the falling/solid-face downward component; it returns a normalized vector (`FlowingFluid.java:54-99`). This supports the wiki's broad level/area hint, with precision: level is reflected in fluid surface height and flow-vector gradients, while current magnitude additionally depends on the entity's sampled immersion depth and averaging/alignment of contributions.
- The operation occurs during the entity's base tick, directly changes velocity, and is eligible for ordinary non-flying player entities. Swimming state update is adjacent but separate; the current scan does not gate on swimming, sprinting, or the new swimming feature. The verified difference is sampling bounds/surface predicate plus player vector aggregation/magnitude. This is not evidence that the current mechanic itself was newly introduced in 1.13.
