# Independent exact-source audit: Nether vine climbing predicate

## Scope and verdict

Wiki clause audited: “Added Twisting Vines and Weeping Vines - same properties as Vines. (one grows upward, the other downward)”. This report decides only the claim about local-player climb/movement behavior. It does not establish equivalence of growth, placement, shapes, rendering, or all other block properties.

**Verdict:** ACCEPT for the scoped climbability claim. In 1.16, both head and plant block states for twisting and weeping vines enter the vanilla climbable tag. The local player inherits the same predicate and movement treatment ordinary vines had in 1.15.2; the two Nether vine families therefore participate as climbable blocks in the covered 1.16 releases. Twisting grows upward and weeping downward, but that distinction does not alter the climbing predicate. “Same properties” is broader than the predicate evidence and is not accepted as an all-properties statement.

**Movement evolution:** Predicate membership and its normal on-ground/air movement treatment are unchanged across inspected 1.16.0, 1.16.1, 1.16.2 and 1.16.5. In 26.2 the tag still contains both head/body block states, but the predicate has additional flight gates and `Player` overrides it during ability flight. These later gates can change direct local-player movement/response around climbables, including these vines. This is an endpoint finding only: no exact later introduction patch is claimed.

## Evidence and reachable player path

- **Baseline, 1.15.2:** `LivingEntity.onLadder()` first rejects spectators, reads `getFeetBlockState()`, and returns true for exactly `Blocks.LADDER`, `Blocks.VINE`, or `Blocks.SCAFFOLDING`, with the open-trapdoor special case (`LivingEntity.java:1226-1240`). Ordinary vine is therefore directly climbable before Nether vines exist. `LocalPlayer`'s jump-to-elytra-start gate excludes `onLadder()` (`LocalPlayer.java:715-719`). In `LivingEntity` travel, ordinary air movement calls `handleOnClimbable`, moves, then if `(horizontalCollision || jumping) && onLadder()` sets resulting Y to `0.2` (`:1890-1895`); the handler resets fall distance, clamps X/Z to ±0.15 and downward Y to at least -0.15, with the sneaking player/scaffolding exception (`:1989-2001`). The water movement branch also checks horizontal collision and `onLadder()` before setting Y to 0.2 (`:1949-1954`).
- **Feature entry, 1.16.0:** `Blocks.java:2817-2837` registers `WEEPING_VINES`, `WEEPING_VINES_PLANT`, `TWISTING_VINES`, and `TWISTING_VINES_PLANT`; both head registrations use `.noCollission()`. `TwistingVines.java:12-14` passes `Direction.UP`, and `TwistingVinesPlant.java:12-14` does likewise. `WeepingVines.java:13-15` and `WeepingVinesPlant.java:12-14` pass `Direction.DOWN`. `BlockTagsProvider.java:521-530` places `Blocks.VINE` and all four Nether-vine states in `BlockTags.CLIMBABLE`. `LivingEntity.onClimbable()` rejects spectators, reads the state at `blockPosition()` via `getFeetBlockState()`, returns true for `BlockTags.CLIMBABLE`, then retains the trapdoor fallback (`LivingEntity.java:1361-1377`; `getFeetBlockState()` is `:1380-1382`). The `Player`/`LocalPlayer` hierarchy has no `onClimbable()` override in 1.16.0/.1/.2/.5; the local-player jump-to-elytra-start gate calls this inherited predicate (`LocalPlayer.java:750-754` in 1.16.0; same condition at `:725-729` in .2/.5). Thus each listed block state is recognized as climbable without requiring collision with its vine shape.
- **1.16 movement response:** `LivingEntity.handleRelativeFrictionAndCalculateMovement` applies relative input, clamps through `handleOnClimbable`, moves, then on `(horizontalCollision || jumping) && onClimbable()` returns a vector with Y `0.2` (`LivingEntity.java:2062-2071` in 1.16.5). The handler resets fall distance, clamps X/Z to ±0.15 and Y to at least -0.15, with the sneaking-player/scaffolding gate (`:2089-2099`). The same methods and values are present in 1.16.0/.1/.2. This is inherited by `LocalPlayer`; the 1.16 `Player` class contains no predicate override. The fluid branch also uses `horizontalCollision && onClimbable()` before setting Y to `0.2` (`:1944-1953`).
- **26.2 tag and query:** `VanillaBlockTagsProvider.java:252-258` still lists VINE, both Weeping states and both Twisting states in `CLIMBABLE`. `LivingEntity.onClimbable()` still rejects spectators and checks that tag, but first returns false when `isFallFlying()` and the current state is `CAN_GLIDE_THROUGH` (`:1722-1739`). The query state comes from `getInBlockState()`, which resolves `level().getBlockState(blockPosition())` (`Entity.java:3725-3730`); this is the same block-position query used by the older `getFeetBlockState()` for this predicate.
- **26.2 direct movement consequences and gates:** the normal travel handler keeps the ±0.15 clamps and -0.15 downward floor; the climb jump sets Y to `0.2` under collision-or-jump gating, with an additional Powder Snow alternative (`LivingEntity.java:2676-2686,2703-2717`). `VanillaBlockTagsProvider.java:293-299` lists VINE and both head/body states of each Nether vine in `CAN_GLIDE_THROUGH`, so the new fall-flying exclusion makes the predicate false on these vines while gliding. The new `travelFallFlying()` first tests `onClimbable()` and falls back to ordinary air travel/stops gliding only when true (`LivingEntity.java:2581-2595`). For the assigned vines, `CAN_GLIDE_THROUGH` makes that test false, retaining the fall-flying branch; this callsite alone does not show a changed gliding trajectory relative to 1.16.5, whose `LivingEntity.travel()` directly enters its `isFallFlying()` branch (`:1979-1984`).
- **26.2 player override and push path:** `Player.onClimbable()` now returns false during `abilities.flying`, otherwise delegates to `LivingEntity` (`Player.java:2023-2026`); `LocalPlayer` inherits this and invokes it for the jump-to-start-fall-flying gate (`LocalPlayer.java:854-855`). In 1.16, the equivalent `Player` override is absent, so creative/ability flight still queries the climbable vine state. This affects whether local-player travel applies climb clamps/fall-distance reset/jump lift while ability-flying. Additionally, `LivingEntity.isPushable()` depends on `!onClimbable()` in both endpoints (`1.16.5:2648-2651`; `26.2:3375-3378`). Living-entity tick reaches `pushEntities()` (`26.2 LivingEntity.java:3173`), and entity overlap handling gates both participants with `isPushable()` before applying horizontal `push()` impulses (`Entity.java:1895-1900`; see `LivingEntity.pushEntities()` at `:3232+`). Therefore the flight predicate changes can also affect whether nearby entity contact modifies local-player velocity. Exact scenario: while alive/non-spectator and ability-flying, vines are climbable in 1.16.5 (pushability false) but not in 26.2 (pushability true); while fall-flying in the vine blocks, the 26.2 `CAN_GLIDE_THROUGH` gate also flips pushability relative to the 1.16.5 tag-only predicate. This is a caller-supported movement-response difference, though a particular overlapping entity is required to realize the push.

## Boundaries and open dependencies

- The feature exists by the exact 1.16.0 endpoint and does not exist in 1.15.2. This brackets introduction to the 1.15.2→1.16.0 comparison; no narrower patch boundary is inferred.
- The climbable tag and normal movement response match across inspected 1.16.0/.1/.2/.5. Releases 1.16.3 and 1.16.4 were not assigned and no individual claim is made for them.
- 26.2 source confirms the flight gates and direct callers above. Its introduction point after 1.16.5 is unverified because no intervening releases were in this assignment.
- No runtime tick parity was tested or claimed. The pushability result is a reachable caller-based movement response, not a measured tick outcome.
