## Paired movement evidence

- 1.16 and 1.16.1 `Entity.getOnPos()` (`world/entity/Entity.java`, 579–593) floors `position.y - 0.2F`; `getBlockStateOn()` (1032–1034) reads that result. `LivingEntity.onSoulSpeedBlock()` (424–426) uses `getBlockStateOn()` against `SOUL_SPEED_BLOCKS`; `LivingEntity.getBlockSpeedFactor()` (428–431) returns `1.0F` only when that block predicate and a positive Soul Speed level both pass, else delegates to the native block factor. The separate existing `Entity.getBlockPosBelowThatAffectsMyMovement()` uses `boundingBox.minY - 0.5000001` (612–614), so it is not the source query used by the old Soul Speed predicate.
- Exact 1.16.2 `LivingEntity.onSoulSpeedBlock()` (425–427) instead reads `level.getBlockState(getBlockPosBelowThatAffectsMyMovement())`; its return condition, enchantment-level test and fallback ordering in `getBlockSpeedFactor()` (429–432) are unchanged. `Entity.getBlockPosBelowThatAffectsMyMovement()` remains the same helper and math (627–629). Thus the old-to-new change is isolated to which cell the Soul Speed predicate queries, and the adjacent exact stable release comparison establishes 1.16.2 as the first stable release in this interval with the correction.
- On a bottom slab, `getOnPos()` selects the slab cell because feet at the slab top minus `0.2F` still floor to the slab's Y. If the slab is not tagged as a Soul Speed block, the 1.16 / 1.16.1 predicate fails although the movement-support helper reaches the block below it. While jumping from a full Soul Speed block, once feet rise more than about `0.2` the old floor query selects the air cell; the movement-support helper continues to select the support for approximately `0.5` blocks of lift. On failure, the Soul Speed override delegates to Entity's normal speed-factor lookup, which reads the supporting Soul Speed block; the direct Soul Speed bypass is therefore lost in those reachable states. These are source/math consequences, not runtime measurements.
- This changes the local player's movement response, not merely particles: `Entity.move()` calls `getBlockSpeedFactor()` and multiplies horizontal delta movement (1.16: 561–562; 1.16.2: 576–577). The local-player tick reaches `LivingEntity.travel()` through `LocalPlayer.aiStep()` → `Player.aiStep()` → `LivingEntity.aiStep()`; the movement call is at 1.16 `LivingEntity.java` 2457 and `LocalPlayer.aiStep()` calls its superclass at 813. `Player.getBlockSpeedFactor()` skips this path while flying or fall-flying (1967–1970), and `Player.onSoulSpeedBlock()` also rejects flying (917–920); neither gate excludes an ordinary jump or slab traversal. `Enchantments.SOUL_SPEED` is registered in 1.16 (`Enchantments.java`, 29) for `EquipmentSlot.FEET`. The direct predicate has no logical-server-only guard; compatibility implementation applicability remains client-player only under project invariants.
- `LivingEntity.tryAddSoulSpeed()` and its attribute maintenance are a separate path, gated in the base tick by `!level.isClientSide` (1.16 `LivingEntity.java`, 261–264), and use their own `getBlockStateOn()` precheck (446–450). This does not replace the direct `getBlockSpeedFactor()` movement path. The finding concerns the player's direct movement predicate, not server-side attribute production, durability, particles or sounds.

## Boundaries and disposition

The supplied MCPK export itself has no source URL, revision/permalink or retrieval date; it is a hint only. Exact source independently supports MC-174469's 1.16.0 / 1.16.1 behavior and the slab issue, and exact 1.16.1 → 1.16.2 source supports the first fix boundary. 1.16.5 has the fixed predicate, but cannot close the missing exact-source identity gap for 1.16.3 / 1.16.4.

The enchantment is newly registered in 1.16, so no pre-introduction behavior is claimed or backported. At 26.2 the mechanism has evolved: `LivingEntity.getBlockSpeedFactor()` lerps toward 1.0 using `MOVEMENT_EFFICIENCY` (510–512), while Soul Speed supplies location-based movement-speed and movement-efficiency attribute effects (`Enchantments.java`, 448–527) and the location-effect update is routed through `ServerLevel` (`LivingEntity.java`, 546–548). That endpoint does not prove the exact intervening change boundary or justify carrying the 1.16 predicate forward to all later versions.
