# Auto-jump source acceptance audit

Disposition: **ACCEPT**

## Question and scope

Independently audit the supplied auto-jump checklist and `8_push_autojump/source-verification.md` against canonical local decompilations. Scope is the client option, local-player scheduling/consumption path, sneaking and movement gates, obstacle sweep and height bounds, Jump Boost influence, and normal step-up comparison. The source comparison bounds the feature between 1.9 and 1.10.2; it does not identify an exact intervening patch. No implementation, build, test, or game execution was performed.

## Findings

- **Option exists and is user-configurable in 1.10.2, absent in 1.9.** In `GameOptions`, 1.10.2 declares default-on `autoJump` (line 108), toggles it for `AUTO_JUMP` (397–398), returns it through option lookup (470–471), reads and writes the `autoJump` setting (831–832, 949), and defines `AUTO_JUMP` as boolean (1066). `ControlsOptionsScreen` includes that option at 14. Searches for `autoJump`/`AUTO_JUMP` in the 1.9 client source found none. 1.9 `LocalClientPlayerEntity.tick()` lines 641 onward handles physical jump input but has no auto-jump countdown or synthetic jump scheduling.
- **Client-local movement callback is the source of detection.** In 1.10.2 `LocalClientPlayerEntity#move(double dx, double dy, double dz): void` (811–817) stores x/z, calls `super.move`, then calls `autoJump((float)(x - oldX), (float)(z - oldZ))`. Thus the detector sees post-collision actual horizontal displacement, narrowed to floats, after ordinary movement. The option is copied into the local player's `autoJumpEnabled` at 228; the field defaults true at 105.
- **Actual jump is scheduled, then consumed on a later local update.** `autoJump(float dx, float dz): void` (823–923) schedules `ticksToNextAutojump = 1` (914) when an eligible obstacle is found. On the next relevant local-player tick, lines 672–677 decrement the positive countdown and set `input.jumping = true`; `serverTickAi` copies that input into `jumping` at 607. `LivingEntity#mobTick()` then consumes `jumping` for a ground jump only when grounded with zero cooldown (1727–1739). The synthetic flag `bl4` also prevents that input from counting as the player's double-tap flight toggle (719–725). This is automatic input scheduling, not an immediate velocity assignment in the detector.
- **Sneaking and other eligibility gates are explicit.** At 824–827 the routine requires enabled, countdown <= 0, on ground, `!isSneaking()`, `!isRiding()`, and nonzero movement input. It further rejects direction when rotation dot product `m < -0.15F` (845–849). Therefore the checklist's no-auto-jump-while-sneaking gate is exact.
- **Direction and sweep math are order-sensitive.** It builds actual displacement `(dx,0,dz)` and squared magnitude cast to `float`; at `g <= 0.001F` synthesizes direction from input, speed, sine/cosine of yaw and recalculates the float squared magnitude, returning if still <= 0.001F (830–843). It casts `fastInvSqrt(g)` to float, scales direction, then computes float rotation dot product (845–849). It requires null collision shapes at the block containing shape maxY and the block above (850–855). Sweep reach is `max(speed * 7.0F, 1.0F / l)`; the player-width-expanded box and side rays are offset upward by `0.51F`; collision boxes intersecting either side ray are considered (862–884). These checks gate whether an obstacle qualifies.
- **Height lower bound and base upper bound match the checklist.** Candidate top height is measured relative to current shape `minY`; `u = (float)(s - minY)` qualifies only if `u > 0.5F` and `u <= o` (911–915). This means a qualifying obstacle is strictly higher than 0.5 blocks and can be considered although `LivingEntity` initializes `stepHeight = 0.6F` (line 165). At baseline `o = 1.2F`; therefore a 1.25-block height exceeds the base cap and is rejected. The max-height check also appears during the above-center collision-shape scan (888–897), with an additional clearance probe for `t > 1` (899–905).
- **Jump Boost changes detector ceiling independently from jump impulse.** When Jump Boost is active, the detector raises `o` by `(amplifier + 1) * 0.75F` (857–860). Thus the upper bound increases per amplifier level and a 1.25-block obstacle can fall under the raised ceiling when the rest of the gates and clearance checks pass. The actual jump impulse is separate: `LivingEntity#jump()` starts at `0.42F` and adds `(amplifier + 1) * 0.1F` (1301–1309). Do not conflate the detector's `0.75F` ceiling increment with the movement launch's `0.1F` increment.
- **Step behavior is separate.** `Entity#move(double,double,double): void` attempts ordinary step movement when `stepHeight > 0`, the grounded/grounding condition is true, and horizontal movement clipped (`Entity.java:538–547`); it retries with `dy = stepHeight` and later chooses the better horizontal result. Since the detector accepts obstacle tops strictly above `0.5F`, its minimum trigger height can be below the ordinary 0.6F step height.

## Acceptance and limits

The supplied checklist is source-supported: the option automatically injects jump input, auto-jump detection is blocked while sneaking, its minimum candidate obstacle height is strictly over 0.5 blocks, the ordinary step height is 0.6 blocks, and the baseline ceiling is 1.2 blocks so a 1.25-block candidate is rejected unless Jump Boost raises the ceiling. This is a client local-player feature: the callback and input mutation live in `LocalClientPlayerEntity`; riding is excluded. Findings establish absence at 1.9 and presence by 1.10.2 only, not the precise feature-introduction patch. No later endpoint was needed for this question. Out of scope: non-player/vehicle physics, rendering, and any profile-switching behavior.
