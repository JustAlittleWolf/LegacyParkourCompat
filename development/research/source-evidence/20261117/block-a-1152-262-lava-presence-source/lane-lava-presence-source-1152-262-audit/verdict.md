## Source verdict

**Accept the source mechanism and the stated bounded same-block-state witness, conditional on the endpoint's effective vanilla lava-tag membership. Keep runtime tag-resource applicability open.**

The main claim is supported by the exact bodies:

- 1.15.2 `Entity.move` clears `isInLava` and runs `checkInsideBlocks` after positional movement (`Entity.java:450-545`, especially `:533-540`). The scan enumerates block cells intersected by the entity box with the existing 0.001 edge offsets and invokes each state's `entityInside` (`Entity.java:791-823`). `LiquidBlock.entityInside` sets the bit for any lava-tagged liquid block without testing fluid top or stored level (`LiquidBlock.java:170-175`). `Entity.isInLava` returns that retained bit (`Entity.java:1055-1060`). `Entity.baseTick` consumes the retained bit before the later movement callback (`Entity.java:348-384`). So the old movement predicate is callback/cell-overlap based and sampled into later tick consumers.
- 26.2 `Entity.baseTick` rebuilds fluid interaction before `LivingEntity.aiStep` runs (`Entity.java:510-558`; `LivingEntity.tick` calls `super.tick` before `aiStep`, `LivingEntity.java:2764-2806`). `EntityFluidInteraction.update` samples a deflated interaction box, after its expanded X/Z region passes the FULL-chunk/section-fluid gate (`EntityFluidInteraction.java:32-42, 91-119`). Each nonempty fluid contributes only when `fluidTop >= box.minY`; measured height is `max(fluidTop - raw entity minY, prior height)` (`:52-83`). The `isInFluid` predicate is measured height `> 0` (`:139-150`), and `Entity.isInLava` also returns false on `firstTick` (`Entity.java:1742-1744`). This is a current base-tick height sample, before jump/travel, rather than the old post-move callback latch.
- The same raw block state maps in both endpoints: `Blocks.LAVA` with `LiquidBlock.LEVEL=7` resolves through the block's state cache to flowing lava with `FlowingFluid.LEVEL=1`, `FALLING=false` (`LiquidBlock.java:36-69` in 1.15.2; `:66-77` in 26.2). `FlowingFluid.getAmount` for flowing lava is its fluid-state LEVEL (`LavaFluid.java:223-229` / `:247-255`). With no same lava above, both endpoints compute height `amount / 9.0F`, hence `1/9` (`FlowingFluid.java:465-477` in each). The stored block-state level 7 and derived fluid-state level 1 are distinct values; the corrected claim labels them correctly.
- Put an ordinary on-foot player's horizontal box over that cell, raw `box.minY=1/3`, with the box extending upward, no lava above and no other sampled fluids. Require old collision scan loaded and 26.2's entire expanded sample region FULL with its lava section present; require `firstTick=false`, no vehicle, `noPhysics=false`, no support (`onGround=false`), no collision, no flight/gliding, and ordinary gravity. A prior old movement through that same overlapping cell invokes the callback and latches lava true. The new sample rejects the cell because `1/9 < 1/3`, leaving lava height/presence zero. This is a concrete source-level witness for the same stored state and kinematic state, not a claim that `LiquidBlock.LEVEL` is fluid height.
- With held jump and vertical velocity equal to promoted `-0.04F`, old `LivingEntity.aiStep` chooses lava jump and adds `0.04F` even while airborne (`LivingEntity.java:2265-2275, 1823-1825`). Old travel takes the lava path; the resulting zero vertical displacement is moved before lava damping/gravity (`:1913-1925`). New jump sees neither tracked water nor lava and does not ground-jump while airborne (`LivingEntity.java:3098-3123`); new travel takes `travelInAir`, whose movement occurs before gravity/friction updates (`:2430-2497, 2676-2685`). For the stipulated state, the one-tick Y-position divergence follows from operation order. Player travel delegates to the living travel method here because the witness excludes passengers and flight (`Player.java:1402-1423` new; `:1448-1475` old). This is source-derived, not runtime parity evidence.

## Tag/resource gate and applicability

Both exact `FluidTagsProvider` Java sources add the source and flowing lava IDs to `FluidTags.LAVA` (1.15.2 `net/minecraft/data/tags/FluidTagsProvider.java`; 26.2 same path). This is direct evidence of the default data-generator assignment, but it is not itself a raw loaded-resource witness. No `data/minecraft/tags/fluids/lava.json` or `data/minecraft/tags/fluid/lava.json` resource is present in the published source roots inspected here (the 26.2 data tree has no tag files; the 1.15.2 Java tree has no extracted `data/` resources). The supplied source provenance points at a cache directory not present in this checkout, so I could not compare the exact client JAR's packaged tag JSON. Keep applicability conditional on the default vanilla tag containing both lava fluid IDs; do not upgrade the Java data-generator result to proof of packaged/effective runtime tag contents.

This verdict is limited to ordinary on-foot LocalPlayer lava presence timing, its direct jump/travel consumers, and the explicit LEVEL=7 witness for 1.15.2→26.2. It does not establish an intermediate patch boundary, full-pair movement coverage, or runtime parity.
