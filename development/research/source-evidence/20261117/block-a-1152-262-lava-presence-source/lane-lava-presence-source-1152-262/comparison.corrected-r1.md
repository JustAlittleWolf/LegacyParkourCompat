## Producer and operation order

**1.15.2:** `Entity.baseTick` processes the prior `isInLava` bit before setting `firstTick=false` (`Entity.java:348-395`). During `Entity.move`, after movement and before later velocity/post-move work, the code clears `isInLava` then calls `checkInsideBlocks` (`Entity.java:533-544`). That scan uses the entity AABB inset by 0.001 on each side, checks `level.hasChunksAt` over its full integer block range, and calls each overlapped block state's `entityInside` (`Entity.java:791-823`). `LiquidBlock.entityInside` sets the bit whenever its fluid is in `FluidTags.LAVA`, without checking the fluid surface or overlap volume (`LiquidBlock.java:170-175`); `Entity.isInLava()` returns the bit (`Entity.java:1055-1060`). A lava callback observed during movement therefore supplies the stored predicate used by the following base tick and AI step. It is not an input-time fluid sample.

**26.2:** `Entity.baseTick` captures water-eye state, calls `updateFluidInteraction`, updates swimming, applies lava fall-distance behavior, then clears `firstTick` (`Entity.java:510-558`). `updateFluidInteraction` resets trackers and samples the deflated `getFluidInteractionBox` (`EntityFluidInteraction.java:32-42`; `Entity.java:4088-4096`). It scans the box's integer block cells only after `hasFluidAndLoaded` confirms every needed chunk is FULL and returns true only if an examined section contains some fluid (`EntityFluidInteraction.java:91-124`). For each nonempty fluid state it computes `fluidTop = blockY + getHeight(...)`; only a top at or above `box.minY` contributes `max(fluidTop - entityBoundingBox.minY, priorHeight)` (`EntityFluidInteraction.java:52-83`). `isInFluid` means measured height `> 0` (`EntityFluidInteraction.java:139-145`), and `Entity.isInLava` also suppresses the result during `firstTick` (`Entity.java:1742-1744`). Flowing-fluid own height is `amount / 9.0F` when there is no same fluid above in both endpoints (`FlowingFluid.java:470-476` in both versions); flowing lava returns its `LEVEL` as amount (`LavaFluid.java:223-224` in 1.15.2 and `:247-248` in 26.2). Thus current state is recomputed before the living input/jump/travel phase, from positive fluid-surface overlap, with a stricter loaded-region gate.

## Local-player tick path and direct movement consumers

In each version `LocalPlayer.tick` calls `super.tick()` (`1.15.2 client/player/LocalPlayer.java:178-182`; 26.2 `:226-234`), entering `Entity.baseTick` before `LivingEntity.tick` invokes virtual `aiStep` (`1.15.2 LivingEntity.java:2023-2025, 2103`; 26.2 `:2764-2766, 2804-2806`). In 1.15.2, `LocalPlayer.aiStep` ticks its input then calls `super.aiStep` (`LocalPlayer.java:625-636, 778`); the living step calls the player `serverAiStep`, which copies `input.jumping` to `jumping`, before its jump branch (`LivingEntity.java:2253-2268`; `LocalPlayer.java:607-618`). In 26.2, `LocalPlayer.aiStep` reaches `super.aiStep` after its input processing (`LocalPlayer.java:767-793, 914`); `LivingEntity.aiStep` calls `applyInput`, then evaluates jumping before travel (`LivingEntity.java:3084-3100, 3125-3141`), and local `applyInput` copies the current jump key (`LocalPlayer.java:692-704`). Therefore each client jump uses held input from that local AI step; old jump/travel read the lava bit produced during the prior movement, while new jump/travel read the fluid tracker rebuilt in the current base tick.

A concrete same-state witness uses Blocks.LAVA at (0,0,0) with the identical raw block property in both endpoints: LiquidBlock.LEVEL=7 (the block-state property is spelled level in both). The namespaces are separate although their property display spelling overlaps: LiquidBlock.LEVEL aliases BlockStateProperties.LEVEL (range 0..15; 1.15.2 LiquidBlock.java:32, BlockStateProperties.java:82; 26.2 LiquidBlock.java:53, BlockStateProperties.java:116), while FlowingFluid.LEVEL aliases BlockStateProperties.LEVEL_FLOWING (range 1..8; FlowingFluid.java:34, BlockStateProperties.java:80; 26.2 FlowingFluid.java:36, BlockStateProperties.java:113). LiquidBlock index 7 resolves from its state cache to Fluids.FLOWING_LAVA with FlowingFluid.LEVEL=1 and FALLING=false in both versions (1.15.2 LiquidBlock.java:36-47, 66-69; 26.2 LiquidBlock.java:66-77, 123-127). The reverse conversion agrees: each LavaFluid.createLegacyBlock uses getLegacyLevel; the flowing lava amount is its LEVEL, and the non-source/non-falling formula gives 8 - min(1, 8) + 0 = 7 (1.15.2 LavaFluid.java:140-142, 223-229, FlowingFluid.java:461-462; 26.2 LavaFluid.java:155-157, 247-254, FlowingFluid.java:462-463). With no lava directly above, both FlowingFluid.getHeight methods use getOwnHeight, which is amount / 9.0F, so the surface is y=1/9 (FlowingFluid.java:470-476 in each endpoint). The exact witness block state is therefore Blocks.LAVA with LiquidBlock.LEVEL=7 on both sides; FlowingFluid.LEVEL=1 is only the derived fluid-state value, not the stored block-state value.

The local player's deflated bounding box is horizontally within the block cell, has minY=1/3, and extends upward from there; the position is airborne with no supporting block, no vehicle, onGround=false, isFallFlying=false, and abilities.flying=false. Set horizontal velocity and movement input to zero; use ordinary gravity (no slow-falling, levitation or no-gravity) and no movement collision during this step. There is no water or other fluid in the sampled player box, no lava above the stated cell, the old checkInsideBlocks span is loaded, and all chunks in 26.2's expanded hasFluidAndLoaded sample region are FULL with the lava-containing section present. In 26.2 a normal nonflying player is affected by fluids and does not stand on fluid (Player.java:875-876; LivingEntity.java:2415-2417); here isInLava=false because fluidTop=1/9 < box.minY=1/3, and isInWater=false. For a shared pre-jump state with vertical velocity equal to the double obtained by promoting -0.04F and a held jump, the prior old movement callback has latched isInLava=true while the same low lava block cell overlaps the entity AABB. The old jump adds the same 0.04F promoted to double, yielding exactly 0.0 vertical movement; old lava travel therefore moves by zero before applying its lava damping/gravity (LivingEntity.java:2265-2275, 1823-1825, 1913-1925). New jump processing sees neither lava nor water and, while airborne, does not jump from ground or in liquid (LivingEntity.java:3098-3123); its air path applies the shared starting -0.04 movement before air-gravity/friction updates (LivingEntity.java:2430-2446, 2468-2497, 2676-2684). Thus this specified precondition yields a one-tick vertical-position difference: old remains at that y during travel, while 26.2 moves down by 0.04. The post-travel velocities also differ. This is a source-derived reachable witness, not a simulated trajectory.

## Tags and scope notes

Both Java `FluidTagsProvider` sources place source and flowing lava in `FluidTags.LAVA` (1.15.2 `data/tags/FluidTagsProvider.java:17-21`; 26.2 same class `:16-23`). A targeted search found no generated runtime lava-tag JSON resources under either decompiled Java root, so resource files are tracked separately as absent here; tag membership above is verified from the exact Java data-generator code.

This is a bounded endpoint comparison of lava-presence production and its direct held-jump/travel consumers. It does not establish intermediate patch cutovers or full-pair movement coverage. Vanilla block states are unchanged; no product code, Git history, wiki inventory, or implementation was consulted.
