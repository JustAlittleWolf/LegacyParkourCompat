Revision r1 corrects the final destination accessor identified by the independent source audit. It is bound to audit verdict SHA-256 `dd33df95417981163e157a257d972f8218c6ae16106ccbe9abbc609ba8f95c48`; original note remains unchanged.

Difference: The server call sequence in 1.8.9 is optional forced-spawn `PlayerMoveS2CPacket`, `PlayerRespawnS2CPacket`, then final `PlayerMoveS2CPacket`; in 1.9.4 it is `PlayerRespawnS2CPacket`, then final `PlayerMoveS2CPacket`. In both releases, the helper's destination position write selects `toWorld.getForcedSpawnPoint()` because it receives captured old dimension 0 while entity dimension has already become 1. For a live entity the helper next calls `fromWorld.tickEntity(entity, false)`; the final move packet later serializes current player coordinates, and this bounded comparison does not establish the tick's effect on them. The optional 1.8.9 pre-respawn move uses the same forced-spawn accessor via `ServerPlayerEntity.changeDimension`, conditional on a non-null result. Both respawn payloads contain dimension, difficulty, game mode and generator type, with no position or velocity. On a dimension change the client receiver installs a new client world, changes its player dimension, then calls `Minecraft.respawnPlayer`, which replaces the local player and invokes `resetPos`; `Entity.resetPos` zeros all three velocity components and pitch (and may raise Y while checking collisions). Both move packet constructors carry X/Y/Z doubles, yaw/pitch floats and relative-axis flags. The transfer's server calls use the no-flags overload, which passes an empty relative set. The receiver therefore applies absolute X/Y/Z and angles, zeros X/Y/Z velocity, updates position/angles, then sends a client movement response. 1.9.4 additionally includes a teleport ID and sends `AcceptTeleportC2SPacket` after applying the position and before its movement response; 1.8.9 has no teleport-ID acknowledgment. Neither transfer sequence constructs an `EntityVelocityS2CPacket`; position packets do not carry velocity. These are per-packet source effects and source send-call order, not a claim about observed delivery timing.

Movement meaning: If packets are processed in source send order, the 1.8.9 optional correction first applies to the old local player, then respawn replaces/resets that player; the final absolute move applies the server coordinates serialized after the helper; the helper's destination write selected the End world's forced-spawn accessor. In 1.9.4 the respawn/reset precedes the sole final absolute correction, which likewise applies the server coordinates serialized after the helper, whose destination write selected the forced-spawn accessor. In both versions the move packet itself clears local velocity on all three axes because all relative flags are absent; no transfer-path velocity value is sent from the server.
