# Revised independent source verdict: End portal handler and helper tick

Pair: Minecraft 1.8.9 → 1.9 stable; Ornithe Feather. This revision supersedes the earlier verdict only where noted below. It is bound to the unchanged author input SHA-256 `317d5b7ee8bbefdc5ea24decf391af22e2d47b6e5f766b53a2017fb6ca06a435` and the unchanged initial audit SHA-256 `edb947a27d807bbc5006f33404d8dead1c4916b360e70d3d34615f0a5afb1930`.

## Superseding correction

The initial audit incorrectly treated the `dimension` parameter in `PlayerManager.changeDimension(Entity, int, ...)` as the destination dimension. The specialized `ServerPlayerEntity` overload captures the player's old dimension before updating the entity field, then passes that captured value to the generic overload. On ordinary Overworld-to-End transfer, the generic helper therefore receives `dimension == 0` while `entity.dimension == 1`. The initial audit's contrary statements that the destination helper tick and End `PortalForcer` call are skipped are withdrawn. The author's corresponding helper-call and PortalForcer claims are source-supported, subject to the exact gates below.

## Bounded handler and false-helper findings

The author's separate handler-order claims are supported within these source paths. In 1.8.9, `ServerPlayNetworkHandler.tick()` (lines 128–153) does not call `player.tickPlayer()` or snapshot player XYZ. In the ordinary awake, non-riding `handlePlayerMove` path, the handler copies its teleport target and local candidate coordinates before `player.tickPlayer()` (lines 262–293), then writes the current handler teleport-target XYZ with selected angles after that call (lines 290–293). The later movement path calls `player.move(...)` and, after it returns, writes the already-selected inbound coordinates/angles with `updatePositionAndAngles(q,r,s,t,u)` (line 332). The early and final 1.8.9 End-entry teleports are absolute overload calls; the final manager call follows helper work.

In 1.9, `ServerPlayNetworkHandler.tick()` calls `resetPosition()`, then `player.tickPlayer()`, then writes the captured `firstGoodX/Y/Z` to the player with current yaw/pitch (lines 161–164; reset assignments lines 226–233). The final manager teleport send occurs during the nested transfer before that post-tick write. In ordinary `handlePlayerMove`, the handler chooses the no-pending-request branch before `player.move(m,n,o)` (lines 378–389, 439); after move returns it unconditionally writes the already-selected inbound `h/i/j` and angles (line 460). Teleportation-state checks at lines 421–429 and 451–458 gate diagnostics, not that assignment. A later collision-correction teleport is conditional at lines 462–467.

For 1.9 acknowledgment, `handleAcceptTeleport` requires the matching requested ID, writes the stored requested XYZ with current angles, then, when `isInTeleportationState()`, copies the request into `lastGoodX/Y/Z` and calls `onTeleportationDone()`; it clears `requestedTeleportPosition` afterward (`ServerPlayNetworkHandler.java:348–363`). While a request is pending, `handlePlayerMove` does not enter the normal branch; it only resends the stored request after the `> 20` tick condition (`:378–388`). These source statements establish gates and write/send call order only.

For each actual `World.tickEntity(entity, false)` call above, `requireLoaded=false` makes the area-loaded disjunction pass. It copies current XYZ and yaw/pitch to previous snapshots; `if (requireLoaded && entity.inChunk)` is false, so it does not increment entity ticks or call `tick()`/`rideTick()`. Finite checks follow, then chunk bookkeeping. Parent/passenger recursion is also behind `requireLoaded`. In 1.8.9 an unloaded changed chunk leaves `inChunk=false`; in 1.9 the changed-chunk branch calls `resetTeleported()`, allowing the flagged case to proceed to `getChunkAt(...).addEntity(...)`, otherwise an unloaded destination sets `inChunk=false` (`World.java:1330–1396` and `1391–1455`, respectively). The End portal/PlayerManager route above does not itself set Entity's separate `teleported` flag before these helper calls. The previous coordinates are copied before finite checks, so an already non-finite coordinate is restored to that same copied value at this helper boundary.

## Verdict and remaining scope

**Accepted** for the bounded source claims above. The initial audit's two principal rejection reasons—no End destination helper and no End PortalForcer write—were false and are superseded. The unchanged author draft's source-order claims for handler snapshots/writes, matching acknowledgment, alive-gated helper calls, and End PortalForcer positioning are supported as described here. This verdict covers only the 1.8.9→1.9 EndPortalBlock-to-ServerPlayer transfer path, its two PlayerManager overloads, the cited handler writes/ACK, and the two actual false-helper calls. It makes no claim about packet delivery, runtime execution, world/chunk availability, trajectory, other portal paths, or movement parity. No remaining claim within this assigned slice is open; broader source coverage and runtime behavior are outside this verdict.
