# Exact-source verdict: 1.8.9 → 1.9 End portal transfer

This verdict follows the frozen roster in `roster.md` (SHA-256 `7de3ef41e0d40bc94ca3aec4ba65527e874ecb46aa0eba9f630c52f32feeaeb1`). It covers only the successful server-side transfer of an ordinary living player from Overworld to End. Source line references are in the pinned Ornithe Feather files listed in that roster.

## Branch reconstruction

1. **Portal callback and virtual dispatch.** In 1.8.9, `EndPortalBlock.onEntityCollision` calls `entity.changeDimension(1)` when the entity has no vehicle or rider and the world is server-side (`EndPortalBlock.java:61-65`). In 1.9, the successful callback additionally requires not riding, no passengers, `canUsePortals()`, and intersection between entity shape and the translated portal shape (`:62-70`). With a server player argument, the call dispatches to `ServerPlayerEntity.changeDimension`.
2. **Player override.** In 1.8.9 the 0→1 branch increments the End-entry stat, reads target `getForcedSpawnPoint()`, conditionally calls `networkHandler.teleport(blockPos XYZ, 0, 0)` when non-null, then calls the player-manager overload (`ServerPlayerEntity.java:440-459`). That optional teleport call is before the manager's Respawn send. In 1.9 the entry branch increments the stat and delegates without reading the forced point or making that preliminary teleport; the method first sets `inTeleportationState=true` (`:455-479`). After the manager returns, 1.9 calls `sendPacket(WorldEventS2CPacket(1032,...))` (`:479-483`).
3. **First PlayerManager overload: old argument, new field.** Both releases capture `i = player.dimension` while it is 0, capture the source world, assign requested target 1 to `player.dimension`, and obtain the destination world using that updated field. They send Respawn with the now-1 player dimension before invoking the helper with `i`, so the helper's integer `dimension` argument is **old dimension 0** while `entity.dimension` is already **new dimension 1** (1.8.9 `PlayerManager.java:435-458`; 1.9 `:488-513`). In 1.9 `updatePermissions(player)` is called after Respawn and before source-world removal/helper (`:499-502`).
4. **Second PlayerManager overload: both dimension tests matter.** The helper first tests the updated field: `entity.dimension == -1` is false and `entity.dimension == 0` is false because the field is 1. It enters the final `else`. Its spawn accessor test instead uses the passed integer, which is old 0: `dimension == 1` is false, so it calls `toWorld.getForcedSpawnPoint()`, not `toWorld.getSpawnPoint()`. It copies that block position's X/Y/Z into local/player coordinates and sets angles to `90.0F, 0.0F`. Under `if (entity.isAlive())`, it calls `fromWorld.tickEntity(entity, false)`. It then tests `if (dimension != 1)` against the same old argument 0, so that block **does execute**; under its separate alive check it clamps integer-cast X/Z, writes position/angles, calls the destination PortalForcer, adds the entity to `toWorld`, and calls `toWorld.tickEntity(entity, false)`. It finally executes `entity.setWorld(toWorld)` after the placement block (1.8.9 `PlayerManager.java:460-513`; 1.9 `:515-568`). For the ordinary living-player premise, these are the eligible alive-gated call sites; source order alone does not establish runtime delivery or later trajectory.
5. **Destination PortalForcer route.** Because `toWorld` is the End, the destination forcer takes its End branch (`world.dimension.getId() == 1` in 1.8.9, `world.dimension.getType().getId() == 1` in 1.9). That branch lays out the platform, floors entity X/Z and `floor(Y)-1`, calls `entity.setPositionAndAngles(i,j,k,entity.yaw,0.0F)`, and zeros all three velocity components (1.8.9 `PortalForcer.java:29-56`; 1.9 `:30-57`). It is not the Nether portal finder. In 1.9, the `ServerPlayerEntity`-specific `networkHandler.teleport` is only inside the portal-finder success branch (`PortalForcer.java:147-151`); it is not reached by this End destination branch.
6. **Post-helper source-send order.** Both manager overloads call `onChangedDimension` after helper return and then call the final `networkHandler.teleport(player.x, player.y, player.z, player.yaw, player.pitch)` (`PlayerManager.java:448-453` in 1.8.9; `:502-508` in 1.9). Thus the server-side source-call order is: optional 1.8.9 preliminary teleport → Respawn → transfer helper and its writes/ticks → manager final teleport. For 1.9 it is: Respawn → `updatePermissions` → transfer helper and its writes/ticks → manager final teleport → abilities/world/player/status sends → return to the player override and send world event 1032. These are source-call order facts only; they do not establish network arrival or client handling order.

Its additional handler tick/client-handler analysis is outside this narrow branch adjudication; this verdict does not extend or renew acceptance of those claims.
