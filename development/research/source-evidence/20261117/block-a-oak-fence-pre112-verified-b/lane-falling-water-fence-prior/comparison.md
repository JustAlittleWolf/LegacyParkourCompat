# Falling water with dry oak fences above side cells

Exact pair set: 1.8.9 → 1.9.4 → 1.10.2 → 1.11.2, each from the ready canonical `ornithe-feather` source tree. The previously frozen `source-roster.md` records each exact source identity, ready-marker hash and source-manifest hash. This comparison uses those Feather-mapped sources; no other mapping family is substituted.

## Bounded setup

Let `p` be a water block with `LEVEL >= 8` (the falling-water case). For each horizontal direction `dir`, consider the dry default oak fence at `p.offset(dir).up()`. The cell at `p.offset(dir)` is otherwise air; inspect the optional single lower horizontal water neighbor at `p.offset(dir).down()`. The water block and fence remain ordinary vanilla states. Conclusions below concern these exact source versions and the described arrangement; they do not place an introduction boundary in intervening patches or address waterlogging/new blocks.

## Per-version comparison

| Release | Fence/wall adjacency and face abstraction | Lower horizontal neighbor | Local-player reachability and velocity cue |
|---|---|---|---|
| 1.8.9 | Oak fence `shouldConnectTo` consults the adjacent block. In this sparse setup the fence’s horizontal neighbors are air, so its resolved connection bits are false; the predicate is not what produces the flow cue. If evaluated against water as the direct neighbor, its solid-blocking/cube test rejects it. Oak fence itself is non-cube. Base `Block.isFaceSolid` tests only sampled block material solidity; `LiquidBlock.isFaceSolid` returns false for same-liquid, true for UP, false for ICE, otherwise delegates. A dry oak fence has WOOD material, so the LiquidBlock side-face query at the upper side cell is true even though the fence is non-cube. | Air at the same-height side cell passes `!blocksMovement()`, so `getFlow` may inspect exactly one cell below that side cell. A liquid there with computed depth `j >= 0` contributes `(j - (i - 8)) * dir`; falling center depth is 0 because `getLiquidDepth` maps levels >=8 to 0. A fence at the same-height side cell instead blocks movement and suppresses this lower lookup. | `LocalClientPlayerEntity.tick` requires the x/z chunk at player position loaded, then calls `super.tick`; `Entity.tick` calls `checkWaterCollisions`. It passes a player shape grown down by `0.4F` and contracted by `0.001` on each axis to `World.applyLiquidDrag`. World first requires `isAreaLoaded(..., true)`, samples intersecting water cells with the liquid-height gate, then adds the normalized flow scaled by `0.014` if `PlayerEntity.hasLiquidCollision()` (`!abilities.flying`). A fence at any one upper side cell satisfies the falling-level side-face test and adds the downward cue. With one lower level-0 water neighbor and no other flow, the intermediate vector is unit-horizontal plus `(0,-6,0)`, yielding a normalized cue of horizontal `1/sqrt(37)` in that direction and vertical `-6/sqrt(37)`; the player's added velocity is those components times `0.014`. The exact behavioral cue for one fence is independent of which horizontal direction contains it: `getFlow` tests directions in its existing horizontal iteration order, and the first true face check applies `normalize(rawFlow).add(0.0, -6.0, 0.0)` before a final normalization. The fence’s non-cube geometry does not cancel this cue because the tested predicate is material-based, not the collision shape or `isCube()` predicate. The wall/fence adjacency predicate controls their virtual horizontal connection properties; it is not the predicate used by this liquid-flow branch.

## Verdict

Across these four exact ready releases, the defined dry oak-fence arrangement yields the same liquid-flow face result and downward velocity cue. The main source-level abstraction change is the fence/wall adjacency check moving from a block cube predicate to a state cube predicate at 1.9.4; it does not alter this water/fence case. The 1.8.9 to 1.9.4 entity water path changes the generic bound upper-index expression and adds a boat exclusion, but the contracted on-foot LocalClientPlayer path preserves the same geometry and chunk gates and still applies flow when not flying. These conclusions do not establish behavior for any uninspected release or adjacent patch.
