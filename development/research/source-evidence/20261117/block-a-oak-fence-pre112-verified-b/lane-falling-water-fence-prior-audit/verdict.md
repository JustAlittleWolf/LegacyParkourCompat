## Per-claim verdict

| Claim | Verdict | Source finding |
|---|---|---|
| A dry default oak fence directly above the horizontal side cell trips falling-water’s upper face probe even though it is non-cube geometry. | **Accept, bounded to the named states.** | `LiquidBlock.getFlow` checks `p + dir`, then `p + dir.up()` for every horizontal direction when the current `LEVEL >= 8`. The liquid block’s `isFaceSolid` rejects same liquid, treats `UP` specially, rejects ICE, then delegates to `Block.isFaceSolid`; base `Block.isFaceSolid` reads sampled material solidity and ignores fence collision shape and cube state. Registered oak `FENCE` is a `FenceBlock(Material.WOOD, ...)`; default `Material.WOOD` is solid. Thus air at `p + dir` does not match, while dry WOOD at `p + dir.up()` returns true. Sources: each version’s `LiquidBlock.java` (`getFlow` and `isFaceSolid`), `Block.java` (`isFaceSolid` and oak registration), `FenceBlock.java`, `Material.java`. The fence connection bits are irrelevant to this flow test. |
| The optional lower horizontal water cell is probed only after an empty, non-movement-blocking same-height side cell; a same-height fence suppresses that lookup. | **Accept.** | In `getFlow`, if same-height liquid depth `j < 0`, source checks `!sideMaterial.blocksMovement()` and then reads exactly `side.down()`. If that lower cell has depth `j >= 0`, it adds `(j - (i - 8)) * dir`; no second lower cell is read. An oak fence in the same-height side cell blocks movement. For the report’s arrangement, side cell is air, `p` has level at least 8 so `i = 0`, and a level-0 lower water cell has `j = 0`; its raw contribution is `8 * dir`. The upper fence check then normalizes the existing vector, adds `(0,-6,0)`, and the final normalize yields `(dir.x/√37, -6/√37, dir.z/√37)`. With no horizontal contribution, zero normalizes to zero before the downward addition, producing a downward unit cue. |
| The direct local-player path reaches the old water-collision operation behind player and world loaded-area gates. | **Accept for on-foot LocalClientPlayerEntity ticks.** | In all four sources, `LocalClientPlayerEntity.tick` gates `super.tick()` on `world.isChunkLoaded(new BlockPos(x,0,z))`. Its superclass chain is `ClientPlayerEntity` → `PlayerEntity` → `LivingEntity` → `Entity`. The player tick reaches `Entity.tick`/`baseTick`, whose call to `checkWaterCollisions` is unconditional there. On foot, 1.8.9 passes `getShape().grown(0,-0.4F,0).contract(0.001,0.001,0.001)` to `World.applyLiquidDrag`; 1.9.4 onward passes the same shape with `.contract(0.001)`. `applyLiquidDrag` returns false before sampling unless `isAreaLoaded(..., true)` succeeds. The liquid cell is counted only when the loop’s liquid-height test passes. Flow is added only for nonzero vector and `entity.hasLiquidCollision()`; `PlayerEntity.hasLiquidCollision()` is `!abilities.flying`. From 1.9.4 onward, `checkWaterCollisions` also bypasses the water call while mounted on a boat; the report correctly limits its conclusion to the on-foot path. `LivingEntity.checkFallDamage` contains another conditional call when `!isInWater()`; this is a separate entry, not needed to establish the normal tick path. |
| A single lower level-0 water neighbor plus the upper dry fence yields the stated horizontal/downward velocity cue. | **Accept, provided that water cell is in the sampled bounds and the player is not flying.** | `World.applyLiquidDrag` normalizes the accumulated vector, then adds it to each velocity component scaled by `0.014`; the player collision gate is false while flying. For the report’s one-neighbor vector, the added components are `(0.014/√37 * dir.x, -6*0.014/√37, 0.014/√37 * dir.z)`. If flow cue is enabled but there is no horizontal gradient, the face branch still yields straight down. This is source math, not a simulated trajectory. |
| The upper-index formulas are equivalent for these contracted player bounds, so the old and newer on-foot paths sample identical geometry. | **Reject as an unconditional claim; accept only away from integer contracted maxima.** | In 1.8.9 `World.applyLiquidDrag` sets each exclusive upper loop index to `floor(bounds.max + 1.0)`; from 1.9.4 it uses `ceil(bounds.max)`. They agree when the contracted maximum is nonintegral, but differ by one when it is integral: for contracted max `M = 1.0`, old gives `floor(2.0)=2`, newer gives `ceil(1.0)=1`. Since loops use `< upper`, old samples block coordinate 1 and newer does not. Both `Entity.checkWaterCollisions` paths contract the shape by 0.001; contraction does not prove the result cannot be an integer (for example, a pre-contract max of 1.001 produces 1.0 in the exact arithmetic). Therefore a water cell on an exact contracted upper boundary can be sampled only in 1.8.9. The same issue applies independently to X, Y and Z. Whether ordinary gameplay reaches that exact boundary was not runtime-tested; the report’s source-level universal neutralization proof is nevertheless false. This qualifies the “same geometry / same cue” conclusion at the bound edge. |
| The fence/wall join predicate change is unrelated to the liquid cue; 1.8.9 to 1.9.4 changes fence cube checking from `block.isCube()` to `blockState.isCube()`. | **Fence clause accepted; WallBlock clause not audited.** | The frozen source scope includes `FenceBlock`, not `WallBlock`. In the sparse fence setup the fence’s horizontal adjacent blocks are air, so join properties are false. For a hypothetical direct water neighbor, the fence join expression rejects it at its material solid-blocking condition; the cube predicate is not the reason the actual upper liquid face cue fires. The source expression in `FenceBlock.shouldConnectTo` changes from `block.isCube()` to `blockState.isCube()` in 1.9.4. The author’s adjacent claim about `WallBlock.shouldConnectTo` lies outside this audit’s frozen roster and receives no verdict here. |
| The same liquid-side cue holds at all four exact endpoints, with no inferred intermediate boundary. | **Accept only for cells actually sampled and the stated states; qualify by the rejected bound-edge claim.** | `LiquidBlock.getFlow`, its two face probes, `LiquidBlock.isFaceSolid`, and the `0.014` velocity increment have the described behavior in each of the four source trees. This does not establish a patch introduction date or behavior for an uninspected release. The changed loop bound can exclude an exact-edge water cell after 1.8.9. |

## Audit caveats

- The pre-report frozen roster did not list `net/minecraft/util/math/Box.java`. I inspected that exact-version dependency while checking the author’s contraction/equivalence claim. `Box.contract`/`expand` confirms that the max is reduced by the amount, which does not exclude integer results. This late dependency is disclosed rather than silently treated as part of the blind roster.
- `WallBlock.java` and wall connection behavior were not part of the frozen scope and were not independently reviewed.
- This is an exact-source review of 1.8.9, 1.9.4, 1.10.2 and 1.11.2 only. No intermediate versions, game run, TAS/Gym/server launch or runtime trajectory was checked.
- No product source, wiki inventory, product history, or other lane report was consulted. No product source was changed.
