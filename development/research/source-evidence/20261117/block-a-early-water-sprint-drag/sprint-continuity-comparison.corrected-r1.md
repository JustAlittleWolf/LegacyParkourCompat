# Local-player water sprint horizontal drag continuity

## Bounded result

For the assigned exact releases from 1.13 through 1.16.1, ordinary local-player horizontal water drag is continuous: when the player enters the LivingEntity water-movement branch with `isSprinting()` true, the selected factor starts at `0.9F`; the Depth Strider transformation runs next; Dolphin's Grace, if present, then overwrites that factor with `0.96F`; movement is applied; and the resulting X and Z velocity components are multiplied by the selected factor. The selector is the sprinting flag, not the swimming flag. The no-modifier sprint witness therefore has post-move horizontal components `x * 0.9F` and `z * 0.9F` (assuming no horizontal collision/climb adjustment), in each checked release.

There is no source-confirmed horizontal drag change in this assigned interval. Two surrounding changes do not alter the bounded local-player sprint factor: from 1.14.4 the non-sprint base getter is named `getWaterSlowDown()` rather than `getBaseMovementSpeedMultiplier()`, and both getters return `0.8F`; from 1.16 the water branch adds fluid-affect/stand-on-fluid gates and a later falling adjustment that leaves X/Z unchanged. No independent positive finding is warranted for this slice.

## Bounded procedure and preconditions

The LivingEntity water-movement implementation supplies the drag operation used by the player. Feather 1.13–1.14 names the base operation `LivingEntity.moveRelative(...)`; 1.14.1 and later name it `LivingEntity.travel(...)`. The corresponding `PlayerEntity` wrapper is also named `moveRelative(...)` in 1.13 (`PlayerEntity.java:1435–1460`), 1.13.1/.2 (`:1442–1467`), and 1.14 (`:1363–1390`). In each, swimming can first add a look-angle impulse to Y, then the wrapper delegates to `super.moveRelative(...)`; this pre-step does not rewrite X/Z. From 1.14.1, the wrapper is named `PlayerEntity.travel(...)` (1.14.1/.2 `:1362–1390`, 1.14.3 `:1364–1391`, then Mojmap `Player.travel`); it likewise applies only the swimming-related Y impulse before delegating to `super.travel(...)`. The swimming wrapper reads `isSwimming()` while the base water drag selects `f` from `isSprinting()`, so the vertical swim pre-step does not alter the horizontal factor. The LocalPlayer/client-player classes have no separate movement-method override in the checked source set.

Bounded ordinary witness: a locally controlled, non-flying player with no vehicle, already in the water branch, `isSprinting() == true`, Depth Strider level 0, no Dolphin's Grace, and no horizontal collision/climb adjustment. This is a source-path witness conditioned on the sprint state; it is not a runtime test or a claim about every input/state transition that can produce sprinting. No vertical result is asserted.

## Operation and continuity

- **1.13–1.14.3:** the water movement block chooses `0.9F` for `isSprinting()`, otherwise `getBaseMovementSpeedMultiplier()` (`0.8F`). It initializes acceleration `g = 0.02F`; reads Depth Strider; caps it to `3.0F`; halves it when airborne; and, only when positive, applies `f += (0.54600006F - f) * h / 3.0F` and `g += (movementSpeed - g) * h / 3.0F`. The read-only Dolphin's Grace predicate follows and overwrites `f = 0.96F`. It then applies input acceleration, moves, corrects only Y for a climbing collision, and scales velocity by `(f, 0.8F, f)`. Names for the effect constant, movement-speed getter, and movement vector APIs vary across mapping/release; the operation order, sprint selection, float constants, arithmetic order, and X/Z multiplier remain the same.
- **Player wrapper and client reachability:** Feather `PlayerEntity.moveRelative(...)` wrappers were checked at `net/minecraft/entity/living/player/PlayerEntity.java:1435–1460` in 1.13, `:1442–1467` in 1.13.1 and 1.13.2, and `:1363–1390` in 1.14. These wrappers can add the swimming look-angle impulse to Y and then call `super.moveRelative(...)`; they do not replace X/Z. Starting in 1.14.1 the player wrapper is named `travel`: `net/minecraft/entity/player/PlayerEntity.java:1362–1390` in 1.14.1 and 1.14.2, `:1364–1391` in 1.14.3, `net/minecraft/world/entity/player/Player.java:1380–1405` in 1.14.4, `:1456–1481` in 1.15 and 1.15.1, `:1448–1473` in 1.15.2, and `:1380–1405` in 1.16 and 1.16.1. Each applies its swimming-related Y impulse before delegating to the corresponding `super` movement method. Each LocalPlayer/client-player source set has no separate movement-method override. Swimming-state decisions use `isSwimming()` for this vertical pre-step; the base horizontal factor continues to use `isSprinting()`.
- **Water-mode boundary:** the immediately enclosing gate is `!isInWater() || (Player && abilities.flying)` in the 1.13 movement method (local-control gate at `LivingEntity.java:1460`, water-mode gate at `:1467`), `!isInsideWater() || (PlayerEntity && abilities.flying)` in 1.14.1–1.14.3 `LivingEntity.travel` (1.14.1 `:1763–1773`), then `!isInWater() || (Player && abilities.flying)` in 1.14.4–1.15.2 `LivingEntity.travel` (1.14.4 `:1782–1793`). Thus the branch predicate changes at 1.14.4 (`isInsideWater` to `isInWater`); the checked helpers also change from `updateMovementInFluid` in 1.14.3 to `checkAndHandleWater` in 1.14.4. The drag formula is continuous conditional on entering this branch; this report does not assert parity for every shallow-water, unloaded-chunk, or mode-transition edge state at that gate. From 1.16 the gate adds `isAffectedByFluids()` and `!canStandOnFluid(fluidState.getType())` (`LivingEntity.java:1912–1923`); 1.16.1 has the same source hash and gate. These are exact enclosing-state boundaries, not a change to the sprint multiplier.
- **1.14.4 selector refactor:** the base selector changes from `getBaseMovementSpeedMultiplier()` to `getWaterSlowDown()`. Both exact method bodies return `0.8F` (`LivingEntity.java:1778–1780` in 1.14.4 and `:1827–1829` in 1.15.2; the same method/value occurs in 1.16/1.16.1 at `:1904–1906`). This does not affect the sprint branch, whose selected value remains `0.9F`.
- **1.16 gate and post-factor operation:** the shared water branch requires `isInWater() && isAffectedByFluids() && !canStandOnFluid(fluidState.getType())`; `LivingEntity.canStandOnFluid` returns false, and `Player.isAffectedByFluids()` returns `!abilities.flying`, so a non-flying local player satisfies these additional predicates when in water. After the unchanged `multiply(f, 0.8F, f)`, `getFluidFallingAdjustedMovement` can replace Y but returns `new Vec3(vec3.x, e, vec3.z)` (or the original vector when no adjustment applies). Thus it preserves the already-scaled X/Z pair for this witness. These gate and vertical-flow differences bound a source change in the surrounding branch but do not interrupt horizontal-drag continuity.
