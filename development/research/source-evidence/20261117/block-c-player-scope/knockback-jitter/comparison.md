# Knockback near-zero direction jitter comparison

Compared fixed Mojmap sources: 1.20.6, 1.21, and 1.21.1.

## Source difference

- **1.20.6 Mojmap** — `net/minecraft/world/entity/LivingEntity.java`, `hurt(DamageSource,float)`, lines 1118–1220: `hurt` returns false immediately when `level().isClientSide`. After the successful-damage path, if an attacker entity exists and the damage type is not `NO_KNOCKBACK`, it computes attacker-minus-victim X/Z. While the squared magnitude is below the double literal `1.0E-4`, it draws two `Math.random()` values for X and two for Z, each difference multiplied by `0.01`. It then calls `knockback(0.4F, x, z)`. `knockback(double,double,double)`, lines 1475–1482, scales strength by knockback resistance, gates on positive strength, normalizes X/Z, and writes velocity; it has no jitter gate.
- **1.21 and 1.21.1 Mojmap** — `net/minecraft/world/entity/LivingEntity.java`, `knockback(double,double,double)`, lines 1441–1455: the same direction jitter now occurs inside the method, after resistance scaling, the positive-strength gate, `hasImpulse = true`, and reading current velocity. The loop gate is `x*x + z*z < 1.0E-5F`; each iteration draws two `Math.random()` values for X, then two for Z, with each difference multiplied by `0.01`. The subsequent normalization and velocity write keep the 1.20.6 formula and order. The 1.21 and 1.21.1 method bodies are identical.
- **Gate consequence:** directions with squared magnitude from the float-valued `1.0E-5F` threshold up to (but excluding) the double `1.0E-4` threshold are jittered in 1.20.6''s hurt path but are no longer jittered by the 1.21+ knockback method. Smaller directions continue drawing four global `Math.random()` samples per loop iteration in X-pair, Z-pair order. In 1.20.6 the direction came from attacker/victim positions; in 1.21+ any caller of `knockback` passes the direction to this internal gate.

## Player and network reachability

The jitter generation is not a normal logical-client player movement writer in any of these versions. In 1.20.6, the damage method containing the random gate explicitly exits on the logical client. In 1.21+, the gate moved to the public velocity-writing method, but the source call sites are the damage path, player/mob melee knockback, and ram behavior; these are server-side gameplay paths for a remote player target. The local client attack path sends the attack to the server; it does not run the server's victim knockback on the local player. I found no vanilla logical-client call site that invokes this jittering method on the local player. This conclusion is limited to the inspected decompiled source call graph.

Server-side knockback can still affect the local player's later movement through replicated velocity. `ServerEntity.sendChanges()` broadcasts a `ClientboundSetEntityMotionPacket` for `hurtMarked` entities in all three versions (1.20.6 lines 206–213; 1.21/1.21.1 lines 216–220). The client handler applies a decoded velocity with `Entity.lerpMotion` (1.20.6 `ClientPacketListener.handleSetEntityMotion`, lines 515–520; 1.21/1.21.1 lines 517–522). 1.20.6 divides the packet integer components by 8000 in the handler; 1.21+ packet getters divide by 8000 and the handler passes those values through. The decoded scale is equivalent; the packet remains server-authored and contains the server's post-knockback velocity. Thus the source difference can indirectly affect a local player's replicated velocity, but it is not a client-side jitter generator and cannot be reproduced by changing only historical client movement math without modeling server authority/network outcomes.

### Remaining caveats

This is a bounded knockback/network reachability comparison, not a full movement-pair coverage audit. Server-side call-path classification is based on the inspected vanilla callers and client attack flow; mods or custom packets can add client callers. No intermediate release was inspected, so the introduction boundary is only known to lie after 1.20.6 and by 1.21.1. This looks like an excluded server-generated behavior change for a client-only movement hook, while retaining the evidence as a possible indirect-network movement dependency for the master to classify.
