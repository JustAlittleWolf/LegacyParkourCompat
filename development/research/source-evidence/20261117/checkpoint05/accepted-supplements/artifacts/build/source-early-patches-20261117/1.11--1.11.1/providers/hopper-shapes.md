## Comparison

In both releases, `HopperBlock.FACING` allows every direction except `UP`, and `ENABLED` is boolean. Thus the legal provider-state matrix has five facing values (DOWN, NORTH, SOUTH, EAST, WEST) times two enabled values. For all ten combinations, `getShape` returns the full unit box, while `addCollisions` ignores `state` and appends the same five local boxes in the same order: bottom `(0,0,0)-(1,0.625,1)`, west `(0,0,0)-(0.125,1,1)`, east `(0.875,0,0)-(1,1,1)`, north `(0,0,0)-(1,1,0.125)`, and south `(0,0,0.875)-(1,1,1)`. Compare 1.11 lines 32-62 with 1.11.1 lines 32-62. Each call still uses `Block.addCollision`, which translates the box by the block position and appends it only when the query box intersects it; that helper's predicate and ordering are unchanged (Block.java lines 357-363 in both releases).

The method signature gains `boolean forceShape` in 1.11.1 (`HopperBlock.java:56`), but Hopper does not read it. The state-definition forwarder passes it to the block method (`StateDefinition.java:374-375` in both versions, with the extra argument in 1.11.1); the ordinary world query calls the forwarder without the extra argument in 1.11 and with `false` in 1.11.1 (`World.java:994` and `World.java:997`, respectively). Therefore Hopper contributes the same intersecting block boxes to the local-player query for any identical queried box and block position. This is a provider result only; other world-query changes and other providers are outside this slice.

The local-client call path is present on both sides: `LocalClientPlayerEntity.move` delegates to `super.move` (`LocalClientPlayerEntity.java:824-829`), and `Entity.move` gathers `world.getCollisions(this, ...)` during collision-enabled movement (1.11 `Entity.java:455,523`; 1.11.1 `Entity.java:459,564`). This binds the unchanged Hopper provider to an eligible local-player collision query; it does not imply a trajectory difference.

## Disposition and limits

No Hopper collision-shape or provider-output difference was found for the ten legal facing/enabled states. The added `forceShape` parameter causes no Hopper-specific change because it is ignored, and the ordinary world call passes `false`. `ENABLED` may affect hopper redstone/item-transfer behavior elsewhere; item transfer, block-entity ticking, and state-production paths were not examined here and receive no movement disposition from this report. This bounded result does not close the pair's other provider, tick, response, or dependency rows and does not establish pair freeze.
