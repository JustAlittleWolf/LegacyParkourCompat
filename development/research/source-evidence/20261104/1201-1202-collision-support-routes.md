## Shared block-shape provider route

In both releases, `CollisionGetter.getBlockCollisions` creates `BlockCollisions` with the queried entity and box. The iterator creates `CollisionContext.empty()` only for a null entity, otherwise `CollisionContext.of(entity)`; enumerates candidate positions through `Cursor3D`; obtains collision-safe chunk views from `getChunkForCollisions`; and asks each eligible state for `getCollisionShape(collisionGetter, pos, context)` (`CollisionGetter.java:73–85`; `BlockCollisions.java:32–46, 49–62, 64–95`). It translates the returned shape, intersects it with the query shape, and yields the requested result-provider item. `Entity.collideBoundingBox` adds border and block shapes to the list before resolving axes (`Entity.java:896–909` / `898–911`). These method bodies are byte-identical or unchanged in the paired provider files listed below.

State/block provider dispatch is also unchanged in the paired path. `BlockBehaviour.BlockStateBase.getCollisionShape(reader,pos)` uses the cached collision shape when available, otherwise requests the empty-context overload; the context overload dispatches to the registered block (`BlockBehaviour.java:611–617`). The default `BlockBehaviour.getCollisionShape` returns the state's shape only when its `hasCollision` property is true, otherwise `Shapes.empty()` (`BlockBehaviour.java:285–291`). Cache initialization evaluates the same empty-context provider (`BlockBehaviour.java:858–870` in 1.20.1; `862–874` in 1.20.2). The `Blocks.java` static `Block` field inventory has 1003 fields in each version with no added or removed field names. Static block class declarations and the provider dispatch API show no changed collision-provider registration route in the inspected pair.

### Sole changed direct block shape getter found in the provider scan

A static paired scan of direct `getShape` / `getCollisionShape` method declarations in `world/level/block` found 151 declarations on each side, with no added or removed declarations and one changed body: `PinkPetalsBlock.getShape` (`1.20.1:48–50`; `1.20.2:69–71`). The old body returns a fixed state-independent shape; the new body selects a memoized shape from the state's `FACING` and `AMOUNT` properties. The static registry entry remains the same `pink_petals` / `PinkPetalsBlock` registration and calls `.noCollission()` in both (`Blocks.java:7227–7232` / `7235–7240`). `BlockBehaviour.Properties.noCollission()` sets `hasCollision=false` (`BlockBehaviour.java:989–990` / `993–994`), so the shared collision provider returns `Shapes.empty()` for this block in both releases. This changed outline-shape getter is therefore not a changed player collision or support provider in the scoped consumer route.

1.20.2 adds `CollisionGetter.noBlockCollision(entity, box)`, which scans only block collisions (`CollisionGetter.java:65–73`). Its only callsite in the paired source trees is `LivingEntity.wouldNotSuffocateAtTargetPose`, called by `Camel` (`LivingEntity.java:3172–3175`; `Camel.java:382`). Player pose checks continue to call full `noCollision`, so this new block-only consumer is not a player movement route in this pair.

The source route and callback/API inventory alone do not close these dependencies or establish release-wide collision parity.
