# Residual common collision provider review A

Scope: source-only effective collision dispatch for the E1 common providers from `AbstractPressurePlateBlock` through `FenceGateBlock`, inclusive, for the exact 1.12.2→1.13.2 endpoints. This is not a player displacement witness or a full collector closure.

## Source identities

- 1.12.2, Ornithe Feather Gen2 build.2: `decompiled_minecraft/1.12.2/ornithe-feather/`; ready marker source-manifest SHA-256 `b8a37ccfccd2aac5f40f5e34fec85873dbdfa93a266043c103e592e4a8c949da`.
- 1.13.2, Ornithe Feather Gen2 build.2: `decompiled_minecraft/1.13.2/ornithe-feather/`; ready marker source-manifest SHA-256 `2c8cfb646bf622fb26ac0ca0cb5e02a354fb512e29f8b1010f1aaacd509e1211`.
- Each scoped block source and the dispatch/provider support files checked below matches its version's source manifest. The manifests and ready markers identify local exact-version decompilations; this review does not claim runtime verification.

## Effective collision dispatch

- 1.12.2 `World.getCollisions` scans block states and invokes `BlockState.addCollisions` (`World.java:964–1015`, movement wrapper `:1017–1020`; `block/state/StateDefinition.java:374–381`). The base `Block.addCollisions` asks `state.getCollisionShape(world,pos)` then translates and intersects that one `Box` (`Block.java:372–381`). Base `getCollisionShape` delegates to `state.getShape(world,pos)` (`Block.java:385–389`).
- 1.13.2 movement collection obtains each state's collision shape in `WorldView.getBlockCollisions` (`WorldView.java:112–177`). `BlockState` dispatches shape and collision-shape calls to the block (`block/state/BlockState.java:205–210`); base `Block.getCollisionShape` returns `state.getShape` only when `hasCollision`, otherwise empty (`Block.java:388–395`).
- Thus the comparable block-input tuple is not just `getShape`: old inherited/direct collision overrides and new registration `hasCollision` properties participate in the effective result.

## Findings in this slice

1. **Anvil geometry changes.** Old `AnvilBlock.getShape` returns one filled `Box` (`AnvilBlock.java:31–32,92–95`): X-facing is `(0,0,1/8)–(1,1,7/8)` and Z-facing is `(1/8,0,0)–(7/8,1,1)`. New `getShape` returns a union of base, legs and top components (`AnvilBlock.java:29–37,71–74`), leaving portions of the old enclosing prism empty. Direction is still aligned to the same world axis: new `SHAPE_Z` is built from X-extended components and selected for an X-axis facing. Because Anvil uses the default collision-enabled block path, this is a collision-provider delta, not only an outline-shape change. Source establishes the shape difference; displacement consequences were not run.
2. **Chest provider inputs changed.** Old `ChestBlock.getShape` inspects live neighboring block identities in north, south, west, east priority (`ChestBlock.java:68–78`). New code selects a single or directional shape from stored `ChestType` and `getConnectedDirection(state)` (`ChestBlock.java:93–114`). The new `updateShape` maintains pair type for ordinary connected chests (`:72–90`), but the shape getter no longer derives geometry from the current neighboring blocks. Equivalence therefore depends on valid, updated chest-pair state and excludes stale/malformed or multiply-adjacent arrangements until separately closed.
3. **Door virtual-state input changed.** Old `DoorBlock.getShape` first calls `state.resolveVirtualProperties(world,pos)` (`DoorBlock.java:51–66`). The old resolver checks whether the adjacent vertical cell contains the same `DoorBlock` instance; for a lower state it copies hinge/powered from above, and otherwise it copies facing/open from below (`:269–283`). It does not check that the adjacent state has the opposite `HALF`. New `DoorBlock.getShape` consumes only the supplied state (`:51–66`). The slab geometry constants match. The changed input can change output when the same-instance neighbor supplies properties that differ from the current state; an absent neighbor alone does not establish different output because the old resolver then leaves the supplied state unchanged. Close the valid paired-state/property invariant before general admission.
4. **Fence-gate collision path is equivalent at the shape level.** Old `getCollisionShape` ignores `IN_WALL`, returns empty when open, otherwise a facing-axis `Box` rising to 1.5 blocks (`FenceGateBlock.java:22–27,81–87`). New direct collision override makes the same `OPEN`/`FACING` choice with one `VoxelShape` covering the same coordinates (`:22–27,67–73`). The old virtual `IN_WALL` recomputation occurs in `getShape`, not this collision override, so do not transfer that dependency to the fence-gate collision result.

The remaining scoped `getShape` methods and shape constants were compared: pressure plates, rails, buttons, cakes, carpets, crops, cocoa, daylight detector, diode, end rod, farmland, and the other fixed providers preserve their source-defined dimensions/state selectors where they supply a collision shape. For collisionless subclasses, effective empty results are preserved through different dispatch mechanisms:
- Old pressure-plate, rail and button direct collision overrides return `EMPTY_BLOCK_SHAPE` (`AbstractPressurePlateBlock.java:45–47`, `AbstractRailBlock.java:41–43`, `ButtonBlock.java:48–50`). In 1.13.2 their registered `Block.Properties.noCollision()` feeds `hasCollision=false` (registrations in `Block.java:1011–1054`, `:1066`, `:1266–1271`, `:1289–1294`; property setter `:1943–1944`).
- Old crops and dead bush inherit `PlantBlock.getCollisionShape`'s empty result; 1.13.2 registers carrots, beetroots and dead bush with `noCollision()` (`Block.java:923`, `:1264–1265`, `:1598`). This preserves empty movement-collision output despite the nonempty `getShape` used for other shape queries.
- Old/new rail and pressure-plate shape selectors choose corresponding flat/ascending or pressed/unpressed shapes, but those outline shapes do not enter player collision for the collisionless registrations above.

## Boundary

This bounded provider review does not establish the whole collision collector or its admission gates. It excludes other provider lanes, entity-shape composition, query-mode/border behavior, consumer modes such as stepping/sneaking/auto-jump, and 1.13.0/1.13.1. Keep whole-query native fallback for cases whose provider/state inputs are not closed.
