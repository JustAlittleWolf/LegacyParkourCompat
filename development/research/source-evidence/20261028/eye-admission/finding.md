# Eye-submersion admission and point query

1.13.2, Feather: `net/minecraft/entity/living/player/PlayerEntity.java` `tick` (206–208), `updateWaterSubmersion` (257–260); `net/minecraft/client/entity/living/player/LocalClientPlayerEntity.java` `updateWaterSubmersion` (1004–1020); `net/minecraft/entity/Entity.java` `m_03231680` (947–950), `m_61708540` (979–980), `isSubmergedIn` (1042–1051), `m_69693160` (2509–2520); `net/minecraft/world/World.java` `getFluidState` (529–535).

26.2, unobfuscated: `net/minecraft/world/entity/player/Player.java` `tick` (259–260), `updateIsUnderwater` (304–307); `net/minecraft/world/entity/Entity.java` `baseTick` (528–532), `updateFluidInteraction` (1645–1668), `isUnderWater` (1613–1615), `isEyeInFluid` (1738–1739), `getFluidInteractionBox` (4088–4097); `net/minecraft/world/entity/EntityFluidInteraction.java` `update` (32–89), `hasFluidAndLoaded` (91–119), `isEyeInFluid` (148–151).

Difference: In 1.13.2, `PlayerEntity.tick` updates the player’s cached water-submersion flag before `super.tick()`. The client-player override delegates to that same update. It calls `Entity.isSubmergedIn(WATER)`, which returns false for a boat passenger; otherwise it tests only the fluid state at `BlockPos(x, y + getEyeHeight(), z)`, requiring the water tag and `eyeY < blockY + fluidHeight + 0.11111111F`. The entity’s separate body-fluid operation has its own `isAreaLoaded` gate, but that gate is not used by this eye-point query. The ordinary `Entity.tick` water-state routine later runs body contact, refreshes the entity-level `submergedInWater` field from the point query, then updates swimming.

In 26.2, `Player.tick` also updates its player eye cache before `super.tick()`, but `isEyeInFluid` reads the previous `EntityFluidInteraction` tracker at that point. Later in `baseTick`, `wasEyeInWater` captures that same pre-refresh eye state, then `updateFluidInteraction` resets the trackers. It repopulates both body-fluid and eye state only when `hasFluidAndLoaded` succeeds for the body-fluid box expanded by one block on every horizontal side. That helper requires every intersecting chunk to be present as `FULL` without requesting it, and at least one fluid section in that padded region. A failed preflight leaves the just-reset eye tracker false. The subsequent `updateSwimming` call reads the refreshed body and cached eye results. Thus the modern eye result shares a body-scan availability gate that the older point query does not.

Concrete ordinary-player case: place a standing player at `x=15.25, z=8`, with the player’s eye in a water block at `x=15, z=8`, and chunk `(0,0)` loaded while adjacent chunk `(1,0)` is absent. For the usual 0.6-block player width, the deflated fluid box scans x blocks 14–15; its padded preflight spans x blocks 13–16 and reaches chunk `(1,0)`. The 1.13.2 eye query samples the water block in the loaded player chunk and can return true. In 26.2 the missing padded neighbor makes the shared preflight fail, so the eye tracker remains false even though the eye cell itself is in the loaded chunk. This example concerns the eye-query gate only; it does not infer that 1.13.2’s separate body-fluid `isAreaLoaded` check succeeds.

There is also a distinct point-criterion change when the scan runs: 1.13.2’s tagged, boat-vetoed query admits an eye up to (but not including) `1/9` above the fluid height; the 26.2 tracker marks an eye only for a scanned tagged fluid cell whose vertical interval contains the eye, inclusive at both bottom and top. Keep these tests separate from the missing-chunk admission case. Structurally, 26.2 can only set `eyesInside` while iterating cells in the deflated body scan, so an eye cell outside those loop ranges cannot be recognized. The inspected ordinary-player source does not establish a reachable player pose with its eye cell outside that scan; treat that possibility as unconfirmed rather than as an additional player finding. Boat handling also must remain explicit: the 1.13.2 eye query has an early boat veto, while the 26.2 tracker code has no corresponding veto (the passenger fluid box can be modified separately).

Movement meaning: For an ordinary client player near a loaded-chunk edge, the eye-water value sampled by the old per-tick point query can be true while the new per-tick fluid interaction suppresses eye and body tracker updates due to an unloaded neighboring chunk. The player’s cached underwater decision therefore differs; downstream swimming/sprint decisions can observe that cached value in their respective tick order. The old `+1/9` strict upper test versus the new inclusive fluid interval is an additional point-sampling difference under fully loaded conditions.
