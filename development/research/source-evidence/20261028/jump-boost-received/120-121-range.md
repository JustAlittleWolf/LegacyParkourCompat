# Jump boost and ground-jump admission: source report

**Scope:** exact Mojmap client source endpoints 1.20, 1.20.1, 1.20.2, 1.20.5. Read-only canonical tree: `D:\Javastuff\LegacyParkourCompat\decompiled_minecraft`; the read-only cache inspected was `D:\Javastuff\LegacyParkourCompat\.minecraft-decompile-cache`. No wiki or product source was consulted. That cache contains 1.20 but not 1.20.1, 1.20.2, or 1.20.5. I read only the three cache pin files for 1.20 (client jar, client mappings, and version metadata); pins for the other endpoints below were read from their canonical per-version `artifacts.sha256` manifests/provenance. This is a bounded source trace, not full tick or pair coverage.

## Result

- **1.20 and 1.20.1 are byte-identical in all five inspected classes.** 1.20.2 has the same relevant packet, listener, effect storage, jump-power formula, and jump caller behavior. In 1.20–1.20.2 the packet stores the amplifier as `byte`; its write constructor narrows `getAmplifier() & 0xFF`, decode uses `readByte()`, and the getter returns `byte`. `ClientPacketListener.handleUpdateMobEffect` passes that byte to the `MobEffectInstance(..., int amplifier, ...)` constructor, whose storage directly assigns the int. Thus wire byte patterns 128–255 sign-extend to -128…-1 at the getter/listener boundary and are retained by this constructor. This demonstrates the signed-wire representation and client ingestion behavior only; this slice does **not** establish which vanilla effect producers can emit those amplifier values.
- In those three versions `getJumpBoostPower()` is `hasEffect(JUMP) ? 0.1F * (amplifier + 1.0F) : 0.0F`; addition promotes the int amplifier to float, then multiplies in float. `getJumpPower()` is `0.42F * getBlockJumpFactor() + getJumpBoostPower()` (float multiply, then float add). `jumpFromGround()` always writes the computed y velocity, then applies any sprint impulse and sets `hasImpulse`.
- **1.20.5 differs at both boundaries.** The effect packet reads/writes amplifier as VarInt into an `int`; listener construction passes that int to `MobEffectInstance`, which stores `Mth.clamp(amplifier, 0, 255)`. Negative packet values become 0; values above 255 become 255. `getJumpBoostPower()` keeps the same formula. `getJumpPower()` now computes `(float)getAttributeValue(JUMP_STRENGTH) * factor * getBlockJumpFactor() + getJumpBoostPower()` in left-to-right float arithmetic after casting the attribute value to float.
- 1.20.5 `jumpFromGround()` computes power once, then enters its velocity/sprint/`hasImpulse` writes only under `!($$0 <= 1.0E-5F)`. For ordinary ordered float values this admits power greater than the threshold; NaN also passes because `NaN <= threshold` is false. The `LivingEntity.aiStep()` caller still sets `noJumpDelay = 10` immediately after calling `jumpFromGround()`, including when the new method rejects the power. The surrounding input/fluid/ground gates are unchanged at these inspected endpoints: `LocalPlayer.serverAiStep()` transfers controlled local input to `this.jumping`; `LocalPlayer.aiStep()` calls `super.aiStep()`; `LivingEntity.aiStep()` dispatches `serverAiStep()` and handles `this.jumping && this.isAffectedByFluids()`, fluid heights/thresholds, ground/low-water eligibility, and the zero-delay check. It assigns delay 10 after a ground-jump call and clears delay in the non-jump-input branch.
- **Boundary precision:** observed behavior is identical across 1.20/1.20.1 and 1.20.2, and changed by the 1.20.5 endpoint. Versions 1.20.3 and 1.20.4 were not inspected, so the source evidence does not date the change to a specific release within 1.20.2→1.20.5.
