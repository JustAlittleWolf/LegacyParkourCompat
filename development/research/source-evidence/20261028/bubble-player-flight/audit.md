# Independent source audit: Player block responses, flight gates, travel, and climbability

## Scope and verdict

Read-only Mojmap comparison of the exact 1.21.1, 1.21.2, and 1.21.3 snapshots in `D:\Javastuff\LegacyParkourCompat\decompiled_minecraft\<version>\mojmap`. The bounded slices are ordinary Player bubble-column callbacks, the local Player ability-flight path and `Player.travel`, and the climbability/ladder predicates and responses. This is not a complete player-tick or movement-inventory audit; no pair freeze is supported.

One direct Player response changes between 1.21.1 and 1.21.2: Players with `Abilities.flying` stop applying either bubble-column velocity callback. The base callback formulas are unchanged. The callback dispatch also moves from each `Entity.move` in 1.21.1 to post-travel `LivingEntity.applyEffectsFromBlocks` in 1.21.2/1.21.3, with a once-per-traversed-block set and entity-inside-shape gate. The default entity-inside shape remains a full block, so BubbleColumnBlock stays eligible. 1.21.2 and 1.21.3 are byte-identical for all audited Java classes.

`Player.travel`'s swim/passenger and flying/passenger gates are behaviorally equivalent in the ordinary branches checked. Its flight tail no longer clears fall-flying flag 7 or resets fall distance after travel. The fall-distance reset is present earlier in `Player.aiStep`; the flag path is now tied to `canGlide`, with server-side clearing in `LivingEntity.updateFallFlying`. Local-client ordering and state replication for an already-fall-flying Player entering ability flight remain an open timing dependency.

The audited ladder predicate and clamps, local flying suppression gate, water horizontal-collision climb impulse, and LadderBlock directional shape show no source behavior difference across the inspected releases. Full tag-resource membership and the surrounding fluid/travel graph were not closed.

## Source findings

### Bubble-column velocity callback gate

- **1.21.1:** `world/level/block/BubbleColumnBlock.java:49-75` calls `Entity.onAboveBubbleCol` if the block above is air, otherwise `Entity.onInsideBubbleColumn`. There is no Player override of either callback. `world/entity/Entity.java:2357-2380` applies vertical velocity unconditionally: drag-down above uses `max(-0.9, vy - 0.03)`, upward above uses `min(1.8, vy + 0.1)`; drag-down inside uses `max(-0.3, vy - 0.03)`, upward inside uses `min(0.7, vy + 0.06)` and resets fall distance.
- **1.21.2 and 1.21.3:** `world/entity/player/Player.java:354-366` overrides both callbacks and delegates to `super` only if `!getAbilities().flying`. The inherited Entity formulas are otherwise unchanged (`world/entity/Entity.java:2455-2478`). `BubbleColumnBlock.entityInside` keeps the same air-above branch and property forwarding (`world/level/block/BubbleColumnBlock.java:50-77`).
- **Movement meaning / reachability:** A non-flying local Player traversing a bubble column retains the base response. A local Player with `Abilities.flying=true` no longer receives either bubble velocity callback. The inside-column callback also stops clearing fall distance for that Player; the above-column callback never cleared it. Both paths are directly reachable because `LocalPlayer` is a Player, the local ability path toggles `flying` when `mayfly` permits it (`client/player/LocalPlayer.java:648-763` in 1.21.2/3; 1.21.1: `:654-774`), and the block callback is not server-gated.
- The 1.21.2/3 dispatch path only calls block callbacks for a nonremoved, physics-enabled entity (`Entity.isAffectedByBlocks`, `world/entity/Entity.java:769-771`) and, for a client, for the controlled local instance after travel (`world/entity/LivingEntity.java:2771-2776`). `LocalPlayer.isEffectiveAi()` returns true (`client/player/LocalPlayer.java:477-480`), and `Entity.isControlledByLocalInstance()` delegates to that method without a controlling passenger (`world/entity/Entity.java:3149-3150`), so the normal local player reaches this path. `Entity.checkInsideBlocks` traverses movement segments and de-duplicates visited positions (`world/entity/Entity.java:1038-1077`). `BlockBehaviour.getEntityInsideCollisionShape` defaults to `Shapes.block()` (`world/level/block/state/BlockBehaviour.java:353-355`); BubbleColumnBlock does not override it, so the new shape gate does not suppress this callback.
- **Timing dependency:** 1.21.1 invokes `tryCheckInsideBlocks()` at the end of each `Entity.move` (`world/entity/Entity.java:705`, helper `:758-766`; callback loop `:1001-1031`). 1.21.2/3 instead accumulates movement and invokes `applyEffectsFromBlocks()` after `LivingEntity.travel` returns (`world/entity/LivingEntity.java:2771-2776`; implementation `world/entity/Entity.java:736-767`). Thus a callback runs after Player.travel has completed in the newer path and is de-duplicated by visited block position, whereas the old path runs from each move. The full tick's other movement calls and their consequences were not audited here.

### Player.travel flight side effects and ability gates

- **1.21.1:** `world/entity/player/Player.java:1455-1478` first applies swimming uplift only when swimming and not a passenger. For flying and not a passenger it saves old `vy`, calls `super.travel`, writes `oldVy * 0.6`, resets fall distance, and clears shared flag 7. Otherwise it calls `super.travel` directly.
- **1.21.2/3:** `world/entity/player/Player.java:1445-1468` first routes passengers directly to `super.travel`; only the nonpassenger branch applies the same swimming uplift. Its flying branch saves old `vy`, calls `super.travel`, and writes the damped Y with `Vec3.with`; it has no post-travel `resetFallDistance()` or `setSharedFlag(7, false)`.
- **Fall distance ordering:** The new `Player.aiStep` resets fall distance if flying and not a passenger before invoking `super.aiStep()` (`world/entity/player/Player.java:543-555`); 1.21.1 has no such pre-travel reset in `Player.aiStep` (`:513-535`) and instead resets after travel. On the LocalPlayer call path, `LocalPlayer.aiStep` calls `super.aiStep` after its input/ability work (`client/player/LocalPlayer.java:795-799` in 1.21.2/3; 1.21.1 `:804-808`). This moves the reset ahead of the LivingEntity travel/move work for the tick. Whether that impacts gameplay beyond the recorded fall-distance state is not inferred here; damage calculation is out of scope.
- **Fall-flying flag ordering:** `Player.canGlide()` is new in 1.21.2/3 and returns `!abilities.flying && super.canGlide()` (`Player.java:1471-1473`); `tryToStartFallFlying` now calls `canGlide()` (`Player.java:1525-1532`) instead of the older explicit ground/water/levitation/chest-Elytra checks (`Player.java:1529-1539` in 1.21.1). `LivingEntity.updateFallFlying` on the server clears flag 7 when `canGlide()` fails (`LivingEntity.java:2814-2820`); that does not show an equivalent immediate local-client flag write. Check whether a locally controlled Player can retain flag 7 into the same tick's `Player.travel` after ability flight becomes true, and when the server correction arrives, before claiming equivalence.
- **Ordinary gates:** The old `abilities.flying && !isPassenger()` branch and the new passenger-first / then `abilities.flying` structure are mutually equivalent for these conditions. The swim uplift's `!passenger` gate likewise moves to the surrounding `else`. `getBlockSpeedFactor` bypass for flying Players remains in 1.21.1 and 1.21.2/3 (`Player.java:1973-1974`; `:1961-1962`). `getFlyingSpeed`'s flying and passenger predicate is unchanged (`Player.java:2119-2124`; `:2085-2090`).

### Climbability and ladder response

- `LivingEntity.onClimbable()` has the same relevant behavior in 1.21.1 (`world/entity/LivingEntity.java:1517-1532`) and 1.21.2/3 (`:1561-1577`): spectators are false; otherwise the current in-block state is checked for `BlockTags.CLIMBABLE`, recording `lastClimbablePos`, then for a usable TrapDoor ladder, also recording that position. No Player-specific predicate override was found in this slice.
- `handleOnClimbable` is unchanged (`LivingEntity.java:2280-2295` vs `:2379-2394`): reset fall distance; clamp X and Z to +/-0.15 and Y to a minimum of -0.15; if descending, not on scaffolding, ladder-slide suppression is active and the entity is a Player, set Y to 0. The local override `LocalPlayer.isSuppressingSlidingDownLadder()` remains `!abilities.flying && super.isSuppressingSlidingDownLadder()` (`LocalPlayer.java:354-356` vs `:352-354`), and the base implementation remains the shift-key predicate (`LivingEntity.java:3163-3165` vs `:3262-3264`). Thus ability-flight Players do not suppress downward ladder sliding in either audited release.
- In the water travel portion, horizontal collision with a climbable state still replaces Y with `0.2` before water damping (`LivingEntity.java:2121-2129` in 1.21.1; `:2240-2245` in 1.21.2/3). The wider fluid travel routine was refactored and not fully reconciled here.
- `LadderBlock.getShape()` uses the same 3/16-thick direction-facing shape boxes in 1.21.1 (`world/level/block/LadderBlock.java:26-55`) and 1.21.2/3 (`:27-55`). Block-state properties and direct shape are unchanged in this slice. The `BlockTags.CLIMBABLE` resource-tag membership, neighboring-block/trapdoor resource dependencies, and other exact tag data were not checked; they remain dependencies for a full reachability closure.
