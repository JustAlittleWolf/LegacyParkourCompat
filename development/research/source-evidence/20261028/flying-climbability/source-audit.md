## Claim-by-claim verdicts

| Claim | Verdict | Audit finding |
|---|---|---|
| `LocalPlayer.tick` adds a loaded-client gate | **REVISE** | The source fact is correct: 1.21.4 ticks the load timeout, then gates `super.tick()`, packet updates, position reporting, and ambient handlers on `hasClientLoaded()` (`client/player/LocalPlayer.java:191–216`). `Player.CLIENT_LOADED_TIMEOUT_TIME` is 60; the default timer is 60 and `hasClientLoaded()` becomes true at zero, while the client listener also sets it true when the level-load manager reports ready (`world/entity/player/Player.java:159, 167–168, 2096–2110`; `client/multiplayer/ClientPacketListener.java:2458–2463`). This is a reachable connection/level initialization gate, not evidence of an ongoing historical movement mechanic. Keep it out of movement findings unless session initialization is separately brought into scope.
| Local input scaling is a movement difference | **REJECT as a standalone movement finding** | The relocation is real. In 1.21.3 `KeyboardInput.tick` scales the vanilla `-1/0/1` impulses for sneak before `LocalPlayer.aiStep` applies the item-use `0.2F` factor; in 1.21.4 `aiStep` applies item-use then sneak scaling, after the tutorial callback. Both paths multiply the same vanilla keyboard impulses by the same two factors when both gates apply. With vanilla keyboard inputs, the operands commute and preserve the resulting impulse; the changed tutorial-observed impulse is outside movement scope. The report should separate this relocation/UI observation from changed player movement. A third-party replacement of `ClientInput` is not established by these sources and is not a vanilla finding.
| 1.21.4 adds sprint stop/start gates | **ACCEPT** | `shouldStopSprinting()` now stops on fall-flying, blindness, moving slowly, non-camel passenger state, and item use except for passenger/underwater cases (`LocalPlayer.java:816–821`). `canStartSprinting()` adds `!isMovingSlowly() || isUnderWater()` (`1053–1062`). These are local-player tick decisions before travel and alter sprint state/speed under reachable conditions. Preserve the individual gates exactly; the stop-sprint underwater item/passenger conditions differ from the start-sprint slow-movement condition. The report's blindness path is a valid movement predicate, subject to the effect-source qualification below.
| Passenger `Player.tick` clears on-ground | **REVISE** | The diff is exact: 1.21.4 clears on-ground for spectators **or passengers**, versus spectators only in 1.21.3 (`Player.java:256–260`). It is a player-state response reachable for the local player while riding. The method is shared by client and server `Player` instances, so any eventual historical hook must be restricted to the logical client/local player; do not replay it on either integrated or dedicated logical servers. The report notes the state delta but should state this side gate alongside it.
| Flying players report non-climbable | **ACCEPT with side and call-site caveat** | 1.21.4 adds `Player.onClimbable()` returning false for `abilities.flying`, else delegating (`Player.java:2171–2172`). The inherited living movement code consumes this predicate in `handleOnClimbable` and the collision/jump response (`LivingEntity.java:2362–2370, 2390–2404`); local-player AI also checks it before fall-flying initiation (`LocalPlayer.java:749`). This is a direct player movement predicate. The override exists on the shared `Player` type and therefore also runs on server-side players; historical emulation must dispatch only for the local logical-client player. Do not count its attack-critical or other non-movement consumers as in-scope evidence.
| `Entity.move` changes zero-Y vertical/on-ground bookkeeping | **ACCEPT with precise gate** | In 1.21.4 horizontal collision is still recomputed each move, while vertical flags and `setOnGroundWithMovement` are recomputed only if requested Y is nonzero or `isControlledByOrIsLocalPlayer()` is true (`Entity.java:667–671`). The helper resolves `Player.isLocalPlayer()` for players and local-instance control for other entities (`Entity.java:3169–3175`); `Player.isLocalPlayer()` defaults false and `LocalPlayer` supplies the client override. This supports a local-player zero-Y state difference, not a universal “all other entities” statement: controlled non-player entities also pass the gate. Keep all historical behavior client/local-player-only.
| Segment-relative `checkInsideBlocks` traversal | **ACCEPT as a source difference; REVISE applicability/acceptance** | The implementation comparison is accurate. The old method used the current/final bounding box for the movement list and derived a translated-box bottom-center vector; the new method builds a box at each segment destination for block traversal and uses a source-position box plus `to-from` in `collidedWithShapeMovingFrom` (`Entity.java:1038–1084` old; `1050–1095` new). The accumulated path is copied and cleared before callbacks in 1.21.4 (`Entity.java:759–763`). This method is on the local-player path through `LivingEntity.tick` → `applyEffectsFromBlocks`; however, it is a general `Entity` operation run for server entities and non-player entities too. Any candidate implementation must be local-client/player-gated. The report correctly leaves callback behavior, block tags/resources, fluid sampling, `stuckSpeedMultiplier` producers/consumers, and multi-move callers open. Until those are paired, the traversal delta is an accepted source fact only; no particular cobweb, berry-bush, powder-snow, or other trajectory consequence is accepted.
| Existing flower status-duration values affect movement | **REVISE** | The numeric changes are confirmed in `Blocks.java`: azure-bluet blindness 8→11 seconds, cornflower jump 6→5 seconds, plus the listed non-movement status durations. `FlowerBlock.makeEffectList` converts seconds to ticks with `floor(seconds * 20)` and `FlowerBlock` exposes these values as `SuspiciousEffectHolder`; it does not apply them on contact. `SuspiciousStewEffects.onConsume` applies stored effects to the consumer (`world/item/component/SuspiciousStewEffects.java:38–42` in 1.21.4). Therefore blindness/jump duration can reach local sprint/jump behavior through an effect-bearing suspicious stew, but this is an item-consumption/effect path, not a flower `stepOn`/`entityInside` response. Qualify the claim as such and retain recipe/resource, producer, and client/server synchronization checks as open dependencies. Do not report the other changed durations as movement findings absent a movement consumer.
| Multiface waterlogging and existing-block shape summary | **REVISE / NOT INDEPENDENTLY CLOSED** | The report distinguishes new resin content from existing block changes and claims no changed movement override bodies in its sweep. This audit did not repeat the full changed-block/resource/tag sweep. Treat the “no existing shape/callback changes” conclusion as the worker's bounded observation, not an independent accepted negative finding. Existing Glow Lichen/Sculk Vein state/fluid behavior and data-driven tag/resource dependencies still need the source-pair closure the report itself lists.
| Fall-damage gate and exclusions | **ACCEPT as a bounded exclusion** | The call-site gate changes from client-or-locally-controlled to that gate **and** `!isControlledByClient()` (`Entity.java:670–672` old; `681–683` new). `Player.isControlledByClient()` returns true, so this excludes player fall-damage invocation. The report appropriately does not elevate damage calculation to a movement finding. Do not infer that this closes all fall-distance/state consequences or other server-originated player responses.

## Coverage and pair status

It names substantial tick/source slices, but leaves all 865 changed paths without complete movement-inventory classification, resource/tag data, callback block implementations, effect/attribute providers, fluid dependencies, multi-move callers, and server-originated direct player responses incomplete. This independent audit checked the report's identified central claims, not every terminal slice in the pair. The callback traversal's player applicability is credible, but its concrete callback consequences and dependency closure remain unproven. No full-pair freeze is granted; full inventory coverage, closed dependencies, and a complete independent tick-graph audit are still required.
