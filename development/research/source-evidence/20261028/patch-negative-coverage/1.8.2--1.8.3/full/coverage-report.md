## Result and boundary

This is an independently rechecked, source-only endpoint inventory for the ordinary local player. ## Ordered ordinary-player tick and movement inventory

The following call path and terminal movement slices were traced in 1.8.2; matching source identity was checked in both releases for the listed methods unless a changed-file review below is stated. Method names use the same Ornithe Feather mapping family on both sides.

1. **Client tick and world scheduling.** `client/Minecraft.java`, `Minecraft.tick`, calls `world.tickEntities()` before `world.tick()`. `world/World.java`, `tickEntities` / `tickEntity`, schedules loaded entities and calls each entity’s tick; only afterward `client/world/ClientWorld.java`, `tick`, advances client world time and chunks. `Minecraft.java` has only version-title and HTTP-version-string hunks; the tick body is not changed. `ClientWorld.java` and `World.java` are byte-identical.
2. **Local-player entry and packet boundary.** `client/entity/living/player/LocalClientPlayerEntity.java`, `tick`, only runs its inherited tick while its current chunk is loaded, then emits riding-angle/input packets or calls `sendMovementToServer`. The source is byte-identical. `ClientPlayNetworkHandler.java` handles authoritative/corrective player state and external velocity/explosion responses; it is byte-identical. `LocalClientPlayerEntity.sendMovementToServer` sends sprint/sneak transitions and position/rotation/on-ground deltas; network serialization and the relevant packet handlers have no source-hash delta.
3. **Base entity and player tick state.** `PlayerEntity.tick` delegates through `LivingEntity.tick` and `Entity.tick`; their sources are byte-identical. The reachable state work includes prior-position snapshots, effects/status bookkeeping, movement flags, fire/fluid/climbing observations, jump cooldown, movement statistics, and post-movement animation/stat updates. Server-only equipment synchronization and server entity pushing do not run on the ordinary client path. `Entity.tick`, `LivingEntity.tick`, and `PlayerEntity.tick` have no endpoint source delta.
4. **Input acquisition and local pre-travel decisions.** `LocalClientPlayerEntity.mobTick` snapshots prior jump/sneak/forward state, ticks `Input`, applies item-use input scaling, performs the four nearby-entity push-away probes, and evaluates double-tap/manual sprint gates (ground, forward threshold, food-or-flight, item-use and blindness). It also updates flight-toggle/flying vertical input, horse-jump charging, and portal/sprint timers. `KeyboardInput.tick` derives forward/sideways/jump/sneak from `GameOptions`; sneaking scales the two axes. `LocalClientPlayerEntity.serverTickAi` copies the inputs into living-entity movement fields when this player is the camera. These input, options, local-player, and entity-collision sources are unchanged.
5. **Jump selection and application.** `LivingEntity.mobTick` handles jump cooldown, interpolation and near-zero velocity cleanup; clears movement fields for dead entities; calls `serverTickAi` for locally controlled living entities; then selects water jump, lava jump, or grounded jump in that order. Ground jump sets vertical impulse, adds jump-boost amplifier contribution, adds sprint impulse from yaw, and marks velocity dirty. Player jump also updates movement statistics/fatigue. These methods in `LivingEntity`, `PlayerEntity`, and `LocalClientPlayerEntity` are unchanged. Status-effect behavior and effect instance code are unchanged.
6. **Travel dispatch and input normalization.** `LivingEntity.mobTick` scales sideways/forward input by `0.98F`, rotation speed by `0.9F`, then calls `moveRelative`. `PlayerEntity.moveRelative` reads the movement-speed attribute, handles player flight speed and restores the prior vertical velocity; otherwise it delegates. `LivingEntity.moveRelative` is locally controlled only and selects ordinary ground/air, lava, or water movement (unless flying). These methods and movement attribute classes are unchanged.
7. **Ground/air movement branch.** Ground slipperiness is read from the block below the player shape, multiplied by `0.91F`; the `0.16277136F / (i*i*i)` factor scales ground movement speed, while air uses `speedInAir`. `Entity.updateVelocity` normalizes the input vector and rotates it by yaw before adding horizontal velocity. Climbing clamps horizontal speed to ±0.15, clears fall distance, clamps downward velocity to −0.15, and applies player sneaking behavior; movement then calls `Entity.move`. After collision, a horizontal collision while climbing sets vertical velocity to `0.2`. Gravity/drag and client-unloaded-chunk vertical behavior are then applied in the original order. All methods, block/material lookups and math helper sources involved are unchanged.
8. **Water and lava travel.** Water reads depth-strider level from `EnchantmentHelper`, caps it at 3, halves it when airborne, interpolates water drag and acceleration, moves, applies drag, subtracts `0.02` vertical velocity, and can set a `0.3F` step-up impulse when horizontally colliding and `canMove` permits. Lava applies `0.02F` acceleration, moves, halves all velocity components, subtracts `0.02`, and has the corresponding `0.3F` collision step-up gate. `Entity.isSubmergedIn`, `isInWater`, `isInLava`, `World.containsMaterial`/liquid queries, liquid height, `LiquidBlock`, `FlowingLiquidBlock`, and depth-strider lookup were checked. The one changed file, `EnchantmentHelper.java`, was read on both sides: its sole hunk clamps negative protection values in damage-protection calculation; `getDepthStriderLevel` and its equipment/enchantment traversal are identical. No travel delta.
9. **Collision collection and clipping.** `Entity.move` applies cobweb displacement/velocity suppression, player sneaking edge back-off, obtains block/entity collisions, clips Y then X then Z against the same ordered shapes, attempts the two step-height candidates and selects the greater horizontal displacement, writes final position from the box and derives horizontal/vertical collision and on-ground flags. `World.getCollisions`, block collision collection (`Block.addCollisions` / `getCollisionShape`), world-border and loaded-chunk checks, entity collision boxes, and `Box` intersection/expansion math were reviewed by path/hash. `Entity`, `World`, `Box`, `Block`, `ClientWorld`, and the complete block implementation source set have no changed movement code; all block Java paths are in the complete hash inventory.
10. **Post-collision responses and callbacks.** `Entity.move` resets blocked velocity components, updates fall-distance/contact state, calls the supporting block's fall/step behavior, runs `beforeCollision`, `onSteppedOn`, and `onEntityCollision` callbacks, updates fire/water contact and effects, and clears/updates the cobweb/contact flags. `checkBlockCollisions` traverses the occupied block volume and dispatches each block's collision callback. Direct player/entity interaction and push-away paths live in unchanged `PlayerEntity`/`Entity` sources. Piston movement/shape providers and explosion-to-player velocity addition were also checked; relevant block, explosion, network handler and packet sources are unchanged.
11. **Position/velocity/box state sinks.** `Entity.setPosition`, `setPositionFromShape`, `setShape`, `move`, `updateVelocity`, `lerpVelocity`, and packet response methods are state sinks or consumers. `PlayerEntity` collision adjustment, `LivingEntity` movement state, `Box` math and packet classes/handlers are included in the hash/dependency check. No changed source writes ordinary local-player position, velocity, collision flags or dimensions.

## Remaining gaps and limits

No concrete in-scope Java dependency remains open for this two-endpoint comparison: the complete Java source set was hashed on both sides, every differing path was inspected, the changed `EnchantmentHelper` movement consumer was compared directly, and the local tick/travel/collision/response chain and named dependency categories above were checked. This is an endpoint statement only. The interval's intermediate patch versions were not inventoried, so the introduction point of any hypothetical change within 1.8.2→1.8.3 remains unknown. Runtime parity, tests, game/TAS/Gym/server launches, non-player/vehicle simulation, input-device backend internals, and unrelated gameplay are not covered.
