## Scan behavior

### `World.containsMaterial(Box, Material)` — lava-presence predicate

| Release | Source | Bounds, iteration, position, and match |
|---|---|---|
| 1.8.9 | `net/minecraft/world/World.java:1529-1549` | `i=floor(minX)`, `j=floor(maxX+1.0)`, analogously `k/l` for Y and `m/n` for Z. Loops are `i <= o < j`, `k <= p < l`, `m <= q < n`. A reusable `BlockPos.Mutable` is set to `(o,p,q)` for lookup. Presence is `getBlockState(...).getBlock().getMaterial() == material`; first match returns `true`, exhaustion returns `false`. There is no area/chunk-loaded precheck in this method. |
| 1.9 | `net/minecraft/world/World.java:1598-1620` | Lower bounds remain `floor(min*)`; each exclusive upper bound changes to `ceil(max*)`. Same nested half-open loops. A pooled mutable position starts at origin, is set to `(o,p,q)` for lookup, and is released on both early true and final false. Match becomes `getBlockState(...).getMaterial() == material`. There is no area/chunk-loaded precheck here. |
| 1.9.4 | `net/minecraft/world/World.java:1604-1626` | Same bounds, exclusive loops, state-material equality and pooled mutable-position lifecycle as 1.9. |

Thus for any coordinate `x`, `floor(x+1.0)` and `ceil(x)` agree when `x` is nonintegral; at an integral upper edge, the old bound is one larger. Because the loops stop before the upper bound, 1.8.9 visits the voxel at coordinate `x` on an integral max edge, while 1.9/1.9.4 do not. This applies independently to X/Y/Z. For a scan match, material comparison remains equality with the requested `Material`; the source access path changes from block to block-state. At integer upper edges the set of candidate voxels changes; elsewhere these bounds select the same integer range.

### `World.applyLiquidDrag(Box, Material, Entity)` — water-presence and body-effect scan

| Release | Source | Bounds, loaded-area gate, and material/body logic |
|---|---|---|
| 1.8.9 | `net/minecraft/world/World.java:1486-1527` | Uses the same `floor(min*)` / `floor(max*+1.0)` upper bounds and half-open loops as `containsMaterial`. Before scanning, requires `isAreaLoaded(i,k,m,j,l,n,true)`, otherwise returns false. Reuses `BlockPos.Mutable` set to each `(o,p,q)`. Checks `block.getMaterial() == material`; computes `d = p+1-LiquidBlock.getHeightLoss(level)` and only if `l >= d` marks presence and calls `block.applyMaterialDrag(...)`, accumulating a vector. After the scan, if vector length is positive and `entity.hasLiquidCollision()`, normalizes it and adds each component times `0.014` to entity velocity. Returns the presence flag. |
| 1.9 | `net/minecraft/world/World.java:1554-1596` | Bounds change to `floor(min*)` / `ceil(max*)`; loops remain half-open. Same `isAreaLoaded(i,k,m,j,l,n,true)` gate. Uses pooled origin mutable and releases it after scanning. Match is `blockState.getMaterial() == material`; the `l >= d` condition, material-drag accumulation, post-scan normalization, `0.014` velocity addition and presence return are otherwise the same. |
| 1.9.4 | `net/minecraft/world/World.java:1560-1602` | Same as 1.9. |

For `applyLiquidDrag`, the changed `l` is also reused in the surface test `l >= d`; therefore at integral max-Y boundaries its value changes along with the vertical scan endpoint. The unloaded-area gate receives these calculated bounds. In all three releases its helper rejects vertical bounds outside `maxY >= 0 && minY < 256`, shifts X/Z min and max right by four, and checks every chunk coordinate inclusively (`World.java:205-224` in 1.8.9, `210-229` in 1.9, `216-235` in 1.9.4). This chunk gate exists on liquid-drag scan only; it is not present in `containsMaterial`.

## Ordinary player consumption paths

- `PlayerEntity` extends `LivingEntity` in all three sources: `entity/living/player/PlayerEntity.java:79` (1.8.9), `:91` (1.9), `:92` (1.9.4). The common entity routines below therefore apply to an ordinary player.
- `Entity.tick()` calls `baseTick()` at 1.8.9 `entity/Entity.java:245-249` (call at `:246`), 1.9 `:296-304` (call at `:301`), and 1.9.4 `:299-307` (call at `:304`). The cited `checkWaterCollisions()` call is inside `baseTick()` at 1.8.9 `:299-300`, 1.9 `:357-358`, and 1.9.4 `:360-361`. Later in `baseTick()` it checks `isInLava()` and, on true, applies lava damage and halves fall distance (1.8.9 `:318-321`, 1.9 `:376-379`, 1.9.4 `:379-382`). `isInLava()` delegates to `containsMaterial(getShape().grown(-0.1F,-0.4F,-0.1F), Material.LAVA)` (1.8.9 `Entity.java:840-842`, 1.9 `:939-941`, 1.9.4 `:943-945`).
- `checkWaterCollisions()` delegates to `applyLiquidDrag(getShape().grown(0.0,-0.4F,0.0)..., Material.WATER, this)`. On positive result it can play the first-entry splash, resets fall distance, marks `inWater`, and clears fire time; on false it clears `inWater` (1.8.9 `Entity.java:746-759`; 1.9 `:845-863`; 1.9.4 `:849-865`). Its box contraction is written as three explicit `0.001` arguments in 1.8.9 and one uniform `contract(0.001)` argument in 1.9 onward. From 1.9 onward it first clears `inWater` for an entity mounted on a `BoatEntity` (`Entity.java:846-848`, `:850-852`). This is a caller-side gate distinct from the scan upper-bound change.
- In `LivingEntity.moveRelative`, locally/side-updated movement reads `isInWater()` and `isInLava()` to choose the non-water/non-lava acceleration branch; player flight is an explicit exception. The paired water/lava checks remain in order in 1.8.9 `LivingEntity.java:1119-1123`, 1.9 `:1289-1293`, and 1.9.4 `:1302-1306` (with fall-flying handling added in 1.9). In the jump section, `jumping` selects `jumpInWater()`, else `jumpInLava()`, else ground jump when eligible: 1.8.9 `LivingEntity.java:1432-1439`, 1.9 `:1679-1687`, 1.9.4 `:1692-1700`.

## Bounded conclusion and open boundaries

The exact upper-bound change is present between 1.8.9 and 1.9 in both liquid scans; the inspected 1.9 and 1.9.4 scan implementations match in bounds, nested-loop structure, material-presence checks, pooled mutable position use, liquid-height gate, and drag-vector application. The 1.9 caller adds boat suppression to `checkWaterCollisions`; 1.9.4 retains it. The later source also updates player liquid-sensitive movement callers with fall-flying handling while retaining the ordinary water/lava checks.

No claim is made about 1.9.1–1.9.3 or any release outside this assignment, the exact patch introduction point within a release interval, map-specific reachability, or tick-level runtime effect. No trajectory/parity result is inferred from the source diff.
