## Reproduced bytecode checks

On the pinned raw JARs, `javap -p -c -s` confirms the supplement's body-contact claims. `wv.W()Z` and `wx.W()Z` both move the entity box down by `0.4000000059604645`, contract X/Y/Z by `0.001`, then invoke the water overload. The positive path resets fall distance, sets the in-water flag, clears the liquid/fire counter in that order; the negative path clears the in-water flag.

The matched `World.applyLiquidDrag` methods calculate all lower bounds by the mapped floor helper and each exclusive upper bound by applying `+1.0` before floor. They pass `true` to the six-bound area gate and iterate X/Y/Z in half-open loops. Material equality precedes the top-surface calculation; the method marks presence and calls `applyMaterialDrag` only after the exclusive upper-Y bound passes the height comparison. This is the same operation order recorded for 1.8.9. The 1.8 allocation versus 1.8.1 mutable-position reuse is a local allocation difference; it does not alter the inspected bounds, query order, vector accumulation, or effect gates.

The raw `World.isAreaLoaded(IIIIII,boolean)` in each JAR rejects `maxY < 0` or `minY >= 256`, then iterates the inclusive shifted X/Z chunk rectangle and forwards `allowEmpty`. Its `World` per-position containment gate admits only `0 <= y < 256` and the horizontal world border. An inadmissible position returns the default state for `Blocks.AIR` without reading a chunk. The raw `ClientChunkCache` implements `ChunkSource.hasChunk(II)Z` as `true`; its coordinate lookup returns a constructor-created shared `EmptyChunk` when the cache misses. `EmptyChunk`'s block-state lookup returns the `Blocks.AIR` default state. The `ClientWorld` factory bytecode constructs the corresponding cache. Thus the `allowEmpty=true` preflight admits absent client chunks, and an absent chunk contributes air; this is not a requirement that those chunks contain loaded data.

The additional flow gate is also closed against the accepted 1.8.9 source:

- Raw `LiquidBlock.getFlow` is `axl.h(ard,dt):brw` in 1.8 and `axj.h(ara,dt):bru` in 1.8.1. Both use the mapped horizontal direction plane in iteration order, query current and neighboring liquid depths, and accumulate direction-scaled integer depth differences into the vector. For a neighbor with no liquid depth they test material movement blocking, then the lower neighbor and the `neighborDepth - (currentDepth - 8)` term. Both check current level `>= 8` for the downward-flow branch, test the neighbor and block above for the relevant solid face, add `(0,-6,0)` to the normalized vector when that branch qualifies, and normalize again for return. The descriptor-linked `getLiquidDepth` (`f`) body returns the underlying same-material level or `-1` and replaces levels `>= 8` with zero in both releases. Vector `add(DDD)`, `add(Vec3d)`, `normalize()`, and `length()` references are consistently mapped in both Tiny payloads.
- Raw LiquidBlock's `applyMaterialDrag` override adds the returned `getFlow` vector to the accumulated vector. The World scan then performs the same left-to-right accumulator replacement on each accepted cell. After scanning, it requires vector length `> 0` and `Entity.hasLiquidCollision()` before normalizing, then adds `normalizedX * 0.014`, `normalizedY * 0.014`, and `normalizedZ * 0.014` to entity velocity X/Y/Z, respectively. The raw `hasLiquidCollision` methods (`wv.aK()Z`, `wx.aL()Z`) return `true`, matching the 1.8.9 base `Entity` method. The boolean contact result remains separately returned after this effect gate.

The accepted 1.8.9 source has the same relevant source bodies at `LiquidBlock.getLiquidDepth` (lines 53–56), `getFlow` (129–162), `applyMaterialDrag` (164–165), `World.applyLiquidDrag` (1486–1527), and `Entity.hasLiquidCollision` (1753 onward). ## Applicability and limits

For these checked operations, the raw 1.8 and 1.8.1 evidence now supports the same body-contact and current-push behavior as the accepted 1.8.9 source. A body-contact candidate may be source-applicable to 1.8.0/.1 independently of a separate later-version implementation **only if** the implementation preserves the coupled `applyLiquidDrag` flow accumulation and conditional velocity push as well as the contact boolean. A result-only replacement that drops or changes that side effect is not supported by this evidence. This is a source-scope conclusion; it does not inspect the product resolver or establish runtime parity.

No narrow mismatch was found in the requested raw water/flow slice. The 1.8/1.8.1 applicability evidence remains limited to the rebound classes and operations; this audit does not close every water-sensitive movement path, all intermediate patch releases, other fluid behaviors, or any runtime acceptance question.
