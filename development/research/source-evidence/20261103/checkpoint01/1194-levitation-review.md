# 1.19.4 → 1.20–1.20.4 Levitation arrival edge-backoff review

## Immutable verdict

**ACCEPT — bounded source-supported local-player movement witness.** For an airborne, non-flying crouched local player that has accumulated `fallDistance >= maxUpStep` before Levitation arrives, the old path reads that fall distance in the same-tick edge-backoff predicate before resetting it. In 1.20 onward the reset happens before the same movement call. With the same tick-start raw player state, effect, input, and support-edge geometry, this changes the requested horizontal displacement and therefore the tick position. This is specifically an effect-arrival seam; it does not claim a difference for continuously active Levitation across ordinary ticks.

## Ordered source comparison

- **1.19.4:** `LocalPlayer.aiStep` reaches `super.aiStep` (`LocalPlayer.java:795`), and `LivingEntity.aiStep` reaches `travel` (`LivingEntity.java:2540–2551`). Ordinary `LivingEntity.travel` calls `handleRelativeFrictionAndCalculateMovement` (`LivingEntity.java:2092`); that helper calls virtual `move(MoverType.SELF, getDeltaMovement())` before returning (`LivingEntity.java:2152–2162`). Levitation then modifies the returned Y and resets fall distance (`LivingEntity.java:2093–2096`).
- **1.20 / 1.20.1:** `LocalPlayer.aiStep` reaches the superclass at `LocalPlayer.java:801`; `LivingEntity.aiStep` resets for Slow Falling or Levitation at `LivingEntity.java:2565–2567`, then calls ordinary `travel` at `2571–2572`. `travel` invokes the same movement helper at `2112`; the helper moves before returning at `2171–2181`. The 1.20.1 four core file hashes match 1.20 exactly.
- **1.20.2:** `LivingEntity.aiStep` reset at `2594–2596` precedes dispatch to ordinary `travel` at `2602–2603`. `travel` calls the helper at `2146`, which moves before returning at `2205–2213`.
- **1.20.3 / 1.20.4:** `LivingEntity.aiStep` reset at `2596–2598` precedes ordinary `travel` at `2602–2603`; `travel` calls the helper at `2143`, which moves before returning at `2202–2213`. The four relevant source files are byte-identical between these releases.

In each release, `Entity.move` calls virtual `maybeBackOffFromEdge` before collision resolution (1.19.4 `Entity.java:568–570`; 1.20+ `Entity.java:612–616`). `LocalPlayer.move` delegates through `super.move` (1.19.4 `LocalPlayer.java:880–885`; 1.20+ `872–877`). `Player.maybeBackOffFromEdge` has the same relevant gates at 1.19.4 `Player.java:1041–1046`, 1.20/1.20.1 `1043–1048`, 1.20.2 `1047–1052`, 1.20.3/1.20.4 `1048–1053`: not flying, requested Y `<= 0`, mover SELF or PLAYER, shift held, and `isAboveGround()`. That predicate reads `onGround || (fallDistance < maxUpStep && !noCollision(box.move(0, fallDistance - maxUpStep, 0)))` (1.19.4 `1095–1099`; 1.20/1.20.1 `1097–1101`; 1.20.2 `1101–1105`; 1.20.3/1.20.4 `1102–1106`). If true, the horizontal movement is backed off in 0.05 increments while the box shifted down by `maxUpStep` has no collision.

Client effect arrival is a reachable local input: `ClientPacketListener.handleUpdateMobEffect` builds the packet's effect and calls `LivingEntity.forceAddEffect` on the entity (`ClientPacketListener.java:1483–1500` in 1.19.4; `1497–1514` in 1.20/1.20.1; `1452–1469` in 1.20.2; `1501–1518` in 1.20.3/1.20.4). The handler is scheduled onto the client thread. Thus a server-synchronized Levitation arrival before a local tick can occur after a preceding movement tick accumulated fall distance.

## Concrete equal-input witness

1. Before tick N−1, the local player is airborne and descending with no Levitation, with active client movement and `fallDistance` accumulating. At the end of that movement, choose an airborne state with `fallDistance >= maxUpStep`.
2. Before tick N's `LocalPlayer.aiStep` reaches `super.aiStep`, a valid effect update adds Levitation. At tick N start, both compared clients have the same raw player state and same active effect: `onGround=false`, `maxUpStep>0`, `fallDistance >= maxUpStep`, not flying, not passenger, `noPhysics=false`, shift held, `deltaMovement.y <= 0`, and nonzero horizontal movement. Use ordinary non-water/non-lava, non-climbable travel.
3. Place the player just above a support edge, not colliding at its actual box. The box shifted down by `maxUpStep` collides with the support at the current footprint. The requested horizontal displacement carries the shifted box clear of support; at least one 0.05 decrement leaves it supported. Choose downward Y small enough that this move itself does not land the player.

At `maybeBackOffFromEdge`, 1.19.4 still has the accumulated fall distance: with `onGround=false` and `fallDistance >= maxUpStep`, `isAboveGround()` is false and the movement vector is not backed off. The native collision move therefore includes the full horizontal request. In 1.20–1.20.4, `aiStep` first resets fall distance to zero. Since `maxUpStep>0` and the box shifted down by `maxUpStep` intersects support, `isAboveGround()` is true; the backoff loop reduces the horizontal request until that shifted box would collide. The resulting same-tick horizontal position differs.

## Terminal comparisons and limits

The Levitation movement formula is not the asserted difference: in every checked release it adjusts the post-move returned Y by `(0.05 * (amplifier + 1) - returnedY) * 0.2`. The witness comes solely from the time when `fallDistance` is read by player edge-backoff. The 1.19.4 old reset is after that movement; each checked 1.20+ reset is before it. This distinction resolves the earlier limitation that a continuously active Levitation effect already resets on each old-version travel call: the witness uses one transition from absent on tick N−1 to present before tick N.

The older reset statement is only in the ordinary branch shown above. The witness excludes swimming, lava, fall-flying, riding, climbing, grounded states, effect removal, and server-side physics. It requires collision geometry and movement satisfying the stated gates. This is not full-pair coverage, does not establish the exact first patch release after 1.20 where the placement might differ, and does not claim runtime parity. The earlier invalid Slow Falling positive-Y same-tick witness is not used; `handleRelativeFrictionAndCalculateMovement` moves before gravity subtraction, as recorded in `orchestrator-audit/slowfall-order-erratum.md`.
