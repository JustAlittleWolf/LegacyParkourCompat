## Connection predicates and exact boundary

The remaining branch requires both solid-blocking material and `blockState.isCube()`. `CauldronBlock.java:65-68` returns false for `isCube`, so connection is false regardless of cauldron LEVEL or fence material.
- 1.12 and 1.12.2 `FenceBlock.java:124-138`: horizontal cauldron face classification is SOLID (`CauldronBlock.java:253-258`), but the result is `(!shouldConnectTo(block) && faceShape == SOLID) || bl`. Here the misleadingly named static `shouldConnectTo(Block)` is an exclusion predicate. It calls `Block.isExceptionForAttachment` (`Block.java:232-234`), which calls `isExceptionForPlacement` (`219-230`), whose explicit CAULDRON entry is line 224. Thus the SOLID branch is false. `bl` also is false because SOLID is not MIDDLE_POLE. All four horizontal connections remain false.
- This exclusion is already present in exact 1.12, and persists in exact 1.12.2. Complete FenceBlock and CauldronBlock sources are byte-identical between those two publications. The source-level switch to FaceShape at 1.12 does not establish a fence-cauldron movement boundary.
- Registrations use the ordinary CauldronBlock and FenceBlock implementations: 1.11.2 `Block.java:997`, 1.12/1.12.2 `Block.java:1016` register cauldron; `Blocks.CAULDRON` resolves the registered cauldron. No alternative cauldron block variant changes this conclusion.

## Complete shape and collector closure

All versions `FenceBlock.java:45-82`: always add the center box `[.375,0,.375]..[.625,1.5,.625]`; independently append north, east, south, west arm boxes only when that virtual connection is true. The east arm is `[.625,0,.375]..[1,1.5,.625]`; the analogous arms occupy their respective sides. All coordinates, append order and virtual-resolution gate are unchanged. Cauldron adjacency supplies no arm in any version. Other neighbors may still supply their own arms identically for this bounded setup.

All versions `CauldronBlock.java:35-53`: append base `[0,0,0]..[1,.3125,1]`, then west wall `[0,0,0]..[.125,1,1]`, north wall `[0,0,0]..[1,1,.125]`, east wall `[.875,0,0]..[1,1,1]`, south wall `[0,0,.875]..[1,1,1]`. These components are independent of LEVEL. `getShape` returning FULL_BLOCK_SHAPE is not a substitute collision box: the overridden `addCollisions` supplies the five components directly.

1.11.2 `World.java:960-1036`, 1.12/1.12.2 `World.java:964-1040`: the movement collector visits loaded neighboring cells around the swept player box (including the extra lower Y cell needed for 1.5-high fences), reads each world BlockState, then calls `addCollisions(..., entity, false)`. The BlockState wrapper dispatches to the block override (`StateDefinition.java:374-376` old; `375-377` new). FenceBlock consequently recomputes virtual properties from actual neighboring world states, regardless of the stored false default connections. `Block.addCollision` offsets each component to world coordinates and appends it only on strict intersection (old `357-364`, new `376-383`). Entity collisions are appended separately; choose a setup without other entities and inside the world border.

`Entity.move` collects those components, clips Y then X then Z, moves the player box and derives position and horizontal/vertical collision flags. The stepping gate requires prior onGround or a downward Y clip (old `564-601`, new `567-604`). `Box.intersectZ:225-242` uses X/Y overlap and the positive Z face distance. These operations produce the same fence/cauldron outcome for the stated setup. Ordinary client movement reaches this collector through LivingEntity.moveRelative -> `move(MoverType.SELF, velocityX, velocityY, velocityZ)` and LocalClientPlayerEntity.move -> super.move.

## Concrete ordinary moving-player counter-witness

Place an oak fence at `(0,0,0)` and a cauldron at `(1,0,0)`, with other horizontal neighbors air, loaded chunks, no other entities, and ordinary non-flying, non-riding, non-noclip player movement. Consider the airborne portion of a jump above the cauldron: player center X=1, Z=-.1, feet Y=1.1, onGround=false, approaching positive Z. For a specific collision calculation use requested displacement `(0,-.01,.3)`. Normal width `0.6F` yields half-width `0.30000001192092896`, so its X minimum is about .7 and initial Z maximum about .2.

The swept box and resulting feet Y=1.09 remain above every cauldron component (maximum Y=1). Its X minimum exceeds the fence center post's maximum X=.625. The nonexistent east arm is the only proposed component that could clip positive Z at .375. Consequently the setup accepts the requested .3 Z displacement in all three releases. There is no Y clip and onGround=false, so no stepping path obscures the comparison. A hypothetical added east arm would clip Z to `.375 - (-.1 + halfWidth)`, approximately .175, but exact sources never add it. This makes the tempting changed-arm witness invalid. The geometric neighborhood is reachable in ordinary jumping; the numeric displacement is a source-level collision example, not a recorded native tick trace.
