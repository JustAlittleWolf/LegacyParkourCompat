## Bounded source audit

- Route admission: `LocalPlayer.tick` calls `super.tick()` before local input handling (`1.21.2/.3 LocalPlayer.java:189-192`, input's glide-start branch at `735-737`). A jump input only sends `START_FALL_FLYING` after `tryToStartFallFlying()` succeeds. `Player.tryToStartFallFlying` (`Player.java:1525-1532`) requires not already fall-flying, `canGlide()`, and not in water. `Player.canGlide` (`1471-1472`) adds the no-ability-flight gate to `LivingEntity.canGlide` (`LivingEntity.java:2836-2848`), which requires airborne, not passenger, no levitation, and usable glide equipment. Thus the relevant admission is dry start; the water prohibition is a start gate, not a continuation gate.
- Water/swimming state and tick order: `Entity.baseTick` (`Entity.java:430-451`) updates in-water state, eye-fluid state, then swimming. `Entity.updateSwimming` (`1285-1293`) can set swimming while sprinting underwater and not a passenger; `Player.updateSwimming` (`Player.java:1476-1482`) only suppresses this for ability flight. `Player.isSwimming` (`1815-1817`) filters ability flight and spectator, but not fall-flying. `Player.tick` calls `super.tick()` and then `updatePlayerPose()` (`Player.java:253-326`), so the newly updated water/swimming state is visible to the pose selector on the same player tick. In LivingEntity travel, an already set fall-flying flag calls `updateFallFlying` (`LivingEntity.java:2758-2760`); its sole shown clear is server-side (`2814-2819`) on failed `canGlide`, which contains no water test. This admits simultaneous fall-flying and swimming predicates for the scoped non-spectator, non-passenger, non-ability-flight case, assuming sprint/submersion and retained glide eligibility.
- Pose selector and fit/fallback: `Player.updatePlayerPose` (`Player.java:431-459`) has the same body in 1.21.2/.3 and in 1.21.4 at `434-461`: it first requires `Pose.SWIMMING` fit, selects fall-flying before sleeping/swimming, then accepts the desired pose for spectator/passenger or if that desired pose fits; otherwise it tries crouching and finally swimming. Under the assigned exclusions, fall-flying is selected when the shared swimming-fit gate passes; fall-flying and swimming use the same 0.6F × 0.6F dimensions and 0.4F eye height (`Player.java:139-144`). Therefore the bounded pose choice changes the pose value only; there is no direct pose-dimension or eye-height delta for this pair. No broader pose-dependent effects are assessed.
- Flag-writer scope: searching the exact 1.21.2/.3 Mojmap source trees for flag-7 writes/start/stop calls found the normal player start writer (`Player.startFallFlying`, `1534-1536`), the server-side eligibility clear in `LivingEntity.updateFallFlying`, the NBT restoration writer, conversion propagation, and a server packet failure path. No water-entry writer clears the locally started flag. `Player.stopFallFlying` (`1538-1541`) clears flag 7; `ServerGamePacketListenerImpl` calls it when a `START_FALL_FLYING` packet fails `tryToStartFallFlying` (`1445-1448`). Because a duplicate/failed packet can clear the flag, this remains a packet-path caveat; the local route sends the command only after local start succeeds. No network timing or server/client race claim is made.

The above source bodies and digests support direct alias continuity from 1.21.2 through 1.21.3 to the accepted 1.21.4 selector behavior. Fit and ordinary input/equipment gates remain required. This does not establish a specific collision-free trajectory, server-client synchronization, or exact patch-introduction boundary.
