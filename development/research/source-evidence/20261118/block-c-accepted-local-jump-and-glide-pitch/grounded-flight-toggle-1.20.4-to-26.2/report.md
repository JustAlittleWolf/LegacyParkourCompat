# 1.20.4 → 26.2 grounded creative-flight toggle witness

## Scope and disposition

This is a blind, exact-source witness for one local-player operation: double-tap activation of ability flight while a normal player is grounded. Main witness: `mayfly=true`, initially `flying=false`, not spectator, not in always-flying mode, not swimming, not riding, `onGround=true`, and a jump-key rising edge on the second tap (the first tap opened `jumpTriggerTime`; it remains nonzero on this tap). Assume the player is not already fall-flying. No server movement or policy conclusion is made.

**Difference:** In 26.2, the successful non-spectator ability-flight toggle calls `jumpFromGround()` immediately when still on ground, before the existing flight-up input and before `super.aiStep()` performs the ordinary jump phase and travel. 1.20.4 has no call at the toggle site; its regular jump phase follows flight-up input and overwrites vertical velocity with jump power. In 26.2 the immediate jump establishes jump power first; the flight-up input is added to it; and the ordinary jump phase uses `max(jumpPower, currentY)`, preserving that added flight velocity. Both versions can therefore finish the tick with `abilities.flying=true` and airborne, but the new path gives a higher same-tick upward movement/velocity for this witness.

At lines 757–770, newly flying controlled-camera input adds `inputY * getFlyingSpeed() * 3.0F` to Y. There is no `jumpFromGround()` call in this toggle block. The post-super grounded-flight reset is lines 800–804.
- **26.2, unobfuscated:** `decompiled_minecraft/26.2/unobfuscated/net/minecraft/client/player/LocalPlayer.java`, `aiStep`, lines 777–786 and 830–884: capture jump state before `input.tick()`, then require `abilities.mayfly`; the non-spectator branch toggles on a rising jump press when not auto-jumping, using the existing trigger timer, and only toggles when not swimming and either unmounted or on a jumpable vehicle. Lines 871–884 then add `inputYa * abilities.getFlyingSpeed() * 3.0F`; the final reset is lines 914–918.
- **Scheduling and second writer:** 1.20.4 `LocalPlayer.serverAiStep`, lines 610–621, copies the ticked input into `jumping`; in 26.2, `LocalPlayer.applyInput`, lines 692–705, does the same. Their superclass `LivingEntity.aiStep` reaches the jump phase before travel: 1.20.4 `LivingEntity.java` lines 2550–2578; 26.2 `LivingEntity.java` lines 3084–3114. Thus the rising-edge input used to toggle also reaches the ordinary grounded jump phase later in this same `aiStep`. In this witness the direct 26.2 call does not change `onGround` or `noJumpDelay`; the later ordinary jump call can run too. 1.20.4 has only that later ordinary call. This is an additional same-tick writer, not a replacement for vanilla jump processing.
- **Jump math:** 1.20.4 `LivingEntity.jumpFromGround`, lines 2008–2017, assigns Y to `getJumpPower()` (and sets `hasImpulse`). 26.2 `LivingEntity.jumpFromGround`, lines 2389–2400, takes `max(getJumpPower(), movement.y)` (for positive jump power) and marks sync. For a player, 1.20.4 `Player.jumpFromGround`, lines 1440–1448, delegates to that method; 26.2 `Player` has no override, so the inherited 26.2 `LivingEntity` implementation applies.
- **Actual movement and retained velocity:** 1.20.4 `Player.travel`, lines 1463–1473, and 26.2 `Player.travel`, lines 1402–1424, take the non-passenger flight branch, preserve incoming Y, call superclass travel (which consumes current movement in `LivingEntity` travel), then restore Y as incoming Y times `0.6`. For the stated witness, let `J` be `getJumpPower()` and `C = getFlyingSpeed() * 3.0F`, with initial Y zero, positive J, no collision and ordinary dry-air travel. In 1.20.4 flight input first yields `C`, then the ordinary jump assigns `J`; travel moves with that jump velocity and leaves vertical velocity at `0.6J`. In 26.2 the direct jump first yields `J`, flight input produces `J + C`, and the later ordinary jump preserves it via `max(J, J+C)`; travel therefore moves with the larger upward input and leaves vertical velocity at `0.6(J+C)`. With the default flying speed `0.05F`, `C=0.15`; the expressions, rather than these default-only numbers, define the witness. Collisions and environmental movement modifiers can alter realized displacement.
- **Flight remains set after activation:** The direct jump itself does not clear grounded state. Later in the same superclass travel, the upward move leaves the floor in this collision-free witness. Therefore the end-of-`aiStep` check sees `onGround=false`: 1.20.4 does not enter its `onGround && flying && !isAlwaysFlying` reset (lines 800–804), and 26.2 does not enter its `onGround && flying && !isSpectator` reset (lines 914–918). `abilities.flying` remains true.
- **Glide isolation:** Both versions' player `tryToStartFallFlying` require off-ground status: 1.20.4 `Player.java` lines 1506–1516; 26.2 `Player.java` lines 1463–1469 via `canGlide`, whose `LivingEntity` gate requires `!onGround` and `!isPassenger` at lines 3215–3227. Since activation begins grounded and is not yet fall-flying, this witness is inactive-glide ordinary movement. Elytra state is not needed for the witness.

This is a source-level movement consequence, not runtime parity evidence. It is limited to the stated local-player path and its same-tick jump/travel ordering; no server behavior is inferred.
