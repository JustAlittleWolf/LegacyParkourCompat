## Local player as a passenger

This route is reachable for the *player entity itself*. In all three releases, `ClientLevel.tickPassenger` (`ClientLevel.java`: 269-275 / 273-279 / 280-286) accepts a `Player` and invokes its `rideTick()`. `Entity.rideTick()` first sets that entity's delta movement to zero, then calls `tick()`, then positions it from its vehicle if it remains a passenger (`Entity.java`: 1714-1720 / 1817-1823 / 1848-1854). `LocalPlayer.tick()` calls `super.tick()` (`LocalPlayer.java`: 187 / 189 / 190); inherited `LivingEntity.tick()` calls `aiStep()`, and `LocalPlayer.aiStep()` calls `super.aiStep()` (line 795 / 801 / 807). Thus the player's own `LivingEntity.aiStep` route, including the 1.20 reset, does run while riding. `LocalPlayer.isEffectiveAi()` returns true (line 486 / 489 / 489); `Entity.isControlledByLocalInstance()` falls back to `isEffectiveAi()` when that entity has no controlling passenger (1.20.6 `Entity.java:2960-2965`; corresponding method exists in the earlier snapshots). The player's own ordinary `travel` local-control guard is therefore open.

The 1.19.4 local-player route has no shared aiStep effect reset. With Levitation, `LivingEntity.travel` reaches its ordinary branch when the player is not fall-flying and performs the cited reset after the move (`LivingEntity.java:2092-2097`; branch selection begins before line 2048). At 1.20 and 1.20.6, the player's `LivingEntity.aiStep` calls `updateFallFlying()`, then checks Slow Falling or Levitation and calls `resetFallDistance()`, then dispatches travel (`LivingEntity.java:2562-2570` / 2673-2681). The reset is an unguarded write on that `LocalPlayer` object. `Entity.resetFallDistance()` assigns that entity's `fallDistance` field (1.20 `Entity.java:2280-2282`; same operation in 1.20.6). This is a client-side player-state writer, not a server-only write and not the vehicle's fall-distance field.

There is a real ordering difference for the passenger player: reset-before-travel in 1.20/1.20.6 versus ordinary-travel reset after `move` in 1.19.4. However, the passenger `rideTick()` zeroes the player's velocity before `tick()`, and the vehicle positions the rider after its tick. This source slice does not establish a passenger Levitation witness where the old ordinary move itself adds downward fall distance before the old post-move reset; the direct reset timing difference is established, but a distinct final fall-distance or movement-output difference on this passenger route remains unproven here. The vehicle's separate `LivingEntity.aiStep` may also take `travelRidden` because the player controls it; any reset on that vehicle is non-player/vehicle state and excluded.

## Local gliding with Levitation and a tracked flag

Do not infer that `updateFallFlying()` immediately clears the client player's tracked flag. In each inspected release it reads shared flag 7 into a local boolean. A Levitation effect makes its validity predicate false (`LivingEntity.java`: 2590 / 2612 / 2723), so the local boolean becomes false. The only `setSharedFlag(7, value)` in this method is guarded by `!level.isClientSide` (`2610-2612` / `2632-2634` / `2743-2745`). On the local client branch the method does not write the tracked shared flag. `isFallFlying()` continues to read shared flag 7 (`LivingEntity.java`: 2692 / 2714 / 2823-2825). Therefore source permits a local tick in which Levitation is active while the client still reads a previously tracked true gliding flag; it does not prove how long that stale overlap lasts under packet delivery.

For such a local state, the 1.19.4 ordinary Levitation reset is bypassed: `travel` selects its `isFallFlying()` branch (line 2048 onward), whose distinct `checkSlowFallDistance()` is a clamp, not the Levitation reset; the Levitation reset is in the later ordinary branch at 2094-2096. In 1.20/1.20.6, `aiStep` performs the effect reset before `travel` selects that same locally tracked gliding branch. Hence the newly moved direct player reset covers this stale-flag gliding path in source, while the old ordinary reset did not. `Entity.checkSlowFallDistance()` only clamps fall distance to 1 when the current vertical delta is greater than -0.5 and distance exceeds 1 (1.20 `Entity.java:2274-2277`, same operation in 1.20.6); it does not undo the pre-route zero. Subsequent `move` may add fall distance, so this note establishes the reset's route and order, not a complete tick-end value or trajectory.

## 1.20.6 retention and residual disposition

The exact 1.20.6 `LivingEntity.aiStep` retains `updateFallFlying()` → effect predicate/reset → `travelRidden`/`travel` dispatch at lines 2673-2683. `updateFallFlying()` retains the local Levitation gate and server-only shared-flag write at 2721-2745. `Entity` retains the tracked-flag reader and fall-distance clamp/reset methods. The Levitation pre-route operation therefore persists through the cited 1.20.6 endpoint.

Disposition: **gliding-route Levitation reset timing difference confirmed at source level**, conditional on a client-local stale true flight flag while Levitation is active; exact network timing of that overlap remains a witness uncertainty. **Passenger player enters both cited reset routes, but no passenger-specific final-state/trajectory witness is established** because rideTick zeroes its velocity before its tick and positions it from the vehicle afterward. The prior accepted unmounted ordinary and projected reset comparisons remain unchanged. No Slow Falling, vehicle physics, other version, broader gliding/rider behavior, or product implementation was reviewed.
