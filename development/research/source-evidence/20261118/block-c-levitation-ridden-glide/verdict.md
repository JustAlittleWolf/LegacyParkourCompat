## Independent claims and verdicts

| Subclaim | Verdict | Evidence and boundary |
|---|---|---|
| `updateFallFlying`'s shared-flag write authority | **ACCEPT** | In all three `LivingEntity.updateFallFlying` bodies (1.19.4: 2588-2613; 1.20: 2610-2635; 1.20.6: 2721-2746), a local boolean is initialized from tracked flag 7 and is made false if Levitation is active. The call to `setSharedFlag(7, value)` is inside `if (!level.isClientSide)`. Therefore this method computes false locally but does not clear the local client's tracked bit. This describes this method's writer gate, not every possible writer or packet update in the client.
| A conditional local Levitation/stale-flight overlap reaches the gliding route | **ACCEPT, conditional** | `isFallFlying()` reads shared flag 7 (1.19.4: 3010-3012; 1.20: 3032 onward; 1.20.6: 3165-3167). If it is true on entry to `updateFallFlying`, Levitation makes only the local boolean false; on a logical client no tracked write occurs, so the later `travel` can still read true and choose the fall-flying branch. This is a source-permitted same-tick state conditional on a previously true tracked bit. The source does not establish how long a server packet leaves that bit true, or that any particular network schedule produces the overlap.
| Old ordinary Levitation reset versus gliding route | **ACCEPT for ordering** | In 1.19.4, the Levitation reset is in the ordinary gravity branch after `handleRelativeFrictionAndCalculateMovement` (`LivingEntity.java:2092-2096`); the earlier `isFallFlying()` branch (`2048 onward`) calls `checkSlowFallDistance()` instead. Thus the ordinary reset is bypassed when the tracked bit selects gliding. In 1.20 and 1.20.6, `aiStep` calls `updateFallFlying`, then checks Slow Falling or Levitation and resets fall distance before selecting `travelRidden`/`travel` (1.20: 2562-2573; 1.20.6: 2673-2684). The reset precedes the player's gliding route when the conditional stale-bit state is present. `checkSlowFallDistance()` is a separate clamp (`Entity.java:2320-2327` in 1.20.6), not that reset. These are write-order facts; subsequent movement can affect the tick-end field.
| Unqualified Levitation-plus-gliding duration or trajectory/final-value consequence | **REJECT as established** | Source proves the conditional route and operation order only. It does not prove packet duration, a reproduced network overlap, or a full tick-end fall-distance/trajectory result. Do not state the source-order difference as a guaranteed packet-duration or flight-trajectory effect.
| Local player passenger runs its own effect reset/ordinary route | **ACCEPT** | `ClientLevel.tickPassenger` permits `Player` and calls `rideTick` (1.19.4: 269-276; 1.20: 273-280; 1.20.6: 280-287). `Entity.rideTick` zeroes that entity's delta movement, calls `tick`, then positions it from its vehicle if still riding (1.19.4: 1714-1719; 1.20: 1817-1822; 1.20.6: 1848-1853). `LocalPlayer.tick` calls `super.tick`; `LocalPlayer.aiStep` calls `super.aiStep` (1.19.4: 187-190 / 795; 1.20: 189-192 / 801; 1.20.6: 190-193 / 807). In 1.19.4 its own ordinary travel path is likewise eligible.
| Passenger-specific distinct final fall-distance or trajectory witness | **REJECT as established; residual remains open** | The passenger does enter both reset routes, but the inspected route facts do not establish a distinct passenger final fall-distance value or movement output: rideTick zeroes its velocity before the tick and repositions it from the vehicle afterward.
