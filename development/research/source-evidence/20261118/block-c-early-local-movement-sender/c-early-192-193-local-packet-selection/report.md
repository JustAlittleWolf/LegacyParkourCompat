# 1.9.2 → 1.9.3 local-player movement packet selection

## Result

No source difference found in the assigned slice. In both releases, the local player's ordinary, non-riding tick calls `sendMovementToServer()` after `super.tick()`. The compared `sendMovementToServer()` member bodies are byte-for-byte identical (UTF-8 SHA-256 `cc94a93838f95ebe902dafebf47da5e67e40cb420f7ca1fe302fda7a10526944` in each release).

While `isCamera()` is true, sprint and sneak action packets are sent first when their current values differ from the remembered sent values. Position change is measured against `sentX/sentY/sentZ`, with Y taken from the current shape's `minY`; the squared-distance threshold is strictly `> 9.0E-4`, or position is forced when the incremented `ticksSinceSentPosition` reaches 20. Rotation change is exact nonzero yaw or pitch delta. When both position and rotation changed, the chosen form is `PositionAndAngles`; position-only selects `Position`; rotation-only selects `Angles`; otherwise an on-ground change selects the ground-only `PlayerMoveC2SPacket`. Position state is updated and the timer reset only when position is sent; yaw/pitch state is updated only when rotation is sent; `sentOnGround` is updated at the end of the camera-gated block. Gates, packet forms, comparisons, arithmetic, and write order are identical.

The normal tick's riding branch sends angles and input and may send a vehicle packet; it is outside this ordinary-player slice. The `sendMovementToServer()` riding packet branch is textually identical too, but no riding behavior is claimed here.

## Teleport response checked

`ClientPlayNetworkHandler.handlePlayerMove(PlayerMoveS2CPacket)` is identical in the two releases (member-body UTF-8 SHA-256 `0938d46b9efb4eb3eca4ec195b747c09c43156079ddcb926aff87a5ad79a381c`). It resolves the packet against local player state, calls `updatePositionAndAngles`, sends `AcceptTeleportC2SPacket`, and immediately sends a `PlayerMoveC2SPacket.PositionAndAngles` using the resulting player coordinates, shape `minY`, yaw and pitch, with `false` for on-ground. On the first such response (`!started`), it copies player `x/y/z` to `lastX/lastY/lastZ`, sets `started`, and closes the screen. This path does not write the local movement sender's `sentX/Y/Z`, `sentYaw/Pitch`, `sentOnGround`, or `ticksSinceSentPosition` fields in either release; subsequent periodic selection therefore continues from those same remembered sender fields, subject to the player's updated state. No difference found.

This check is limited to local packet-form selection and these directly consumed local sender/interpolation fields. It does not establish parity for teleport coordinate/velocity resolution, server correction behavior, packet crafting or sending internals, riding/vehicle movement, or other movement operations.
