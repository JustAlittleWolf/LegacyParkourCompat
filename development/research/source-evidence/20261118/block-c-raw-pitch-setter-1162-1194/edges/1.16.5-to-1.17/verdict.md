## Frozen technical trace

- **1.16.5**, decompiled_minecraft/1.16.5/mojmap/net/minecraft/world/entity/Entity.java, turn(double d, double e), lines 340–351: double f = e * 0.15; then this.xRot = (float)(this.xRot + f); then this.xRot = Mth.clamp(this.xRot, -90.0F, 90.0F). The multiply and addition are double operations; the one narrowing cast is after adding the old float pitch. It writes the field directly. Current pitch is finally clamped before the method returns.
- **1.17**, decompiled_minecraft/1.17/mojmap/net/minecraft/world/entity/Entity.java, same method, lines 377–388: float f = (float)e * 0.15F;, then this.setXRot(this.getXRot() + f);, then this.setXRot(Mth.clamp(this.getXRot(), -90.0F, 90.0F)). The input is narrowed before multiplication, multiplication and addition use float precision, and each current-pitch write passes through setXRot. Lines 3017–3027 show that getter returns the field and setter stores finite inputs but logs/discards non-finite inputs. The immediately following clamp still limits current pitch to ±90.
- **Normal local call identity:** source search finds the local client MouseHandler call this.minecraft.player.turn(...) in 1.16.5 line 242 and 1.17 line 244. I used only the call-site identity, not its input scheduling/calculation. Entity.turn is public and imposes no input-delta range gate. For example, finite e = 2401.0 produces a finite post-multiply float above 360 in 1.17 (360.1500244F); 1.16.5's double path narrows to 360.1499939F. Both are accepted as finite by 1.17's first setter, then both current-pitch paths clamp to exactly 90.0F. This demonstrates the lawful finite >360 intermediate and its actual setter/clamp sequence, not a >360 pitch surviving turn.
- **Active Elytra path:** in both releases LivingEntity.travel enters its fall-flying branch when isFallFlying() is true (1.16.5 lines 1979–2007; 1.17 lines 2064–2093). The shared flag is maintained for an airborne, non-passenger entity without Levitation while it has an enabled chest Elytra (1.16.5 updateFallFlying, lines 2478–2496; 1.17 lines 2580–2604). In 1.16.5, travel obtains getLookAngle() (which computes the view vector from this.xRot, Entity.java lines 1700–1701) and separately computes float j = this.xRot * (float)(Math.PI / 180.0); Mth.cos(j) affects the vertical velocity term and j < 0.0F gates the lift term. In 1.17, getLookAngle() uses getXRot() (Entity.java lines 1829–1831), and the branch computes j = this.getXRot() * (float)(Math.PI / 180.0) before the same cosine/lift logic. The 1.17 getter returns the same field written by turn and this consumer does no modulo normalization.

## Verdict

There is a source-confirmed current-pitch arithmetic/write-path change: 1.16.5 does double multiply/add followed by float narrowing and direct field write; 1.17 does float narrowing/multiply/add through a finite-checking setter before the clamp. Current pitch is clamped to ±90 in both methods before a later movement consumer. A finite >360 intermediate such as the one above therefore yields pitch 90 in both releases; in active Elytra movement that pitch is actually consumed by the look-vector and angle/cosine path, with no modulo normalization. This scope establishes the exact arithmetic and consumption trace. It does not claim a changed Elytra trajectory from the >360 witness, since its post-turn pitch is identical in both releases, nor claim runtime parity.
