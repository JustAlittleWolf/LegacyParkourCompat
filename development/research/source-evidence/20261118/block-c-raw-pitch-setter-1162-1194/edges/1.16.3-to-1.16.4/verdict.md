## Technical trace

- In each release, `net/minecraft/world/entity/Entity.java:340–352`, public `turn(double d, double e)` first computes `double f = e * 0.15`, then writes pitch with `this.xRot = (float)(this.xRot + f)`. `xRot` is a `float` field (`Entity.java:129`); binary promotion makes the sum `double`, and the explicit cast narrows once to `float` at the assignment. It next updates yaw, then applies `this.xRot = Mth.clamp(this.xRot, -90.0F, 90.0F)` at line 345. The pitch clamp therefore happens immediately after the raw float write and yaw write, before previous-tick rotation (`xRotO`, `yRotO`) updates and their separate pitch clamp. All operands and return in this clamp call use the float overload.
- `net/minecraft/util/Mth.java:94–100` implements that overload with ordered comparisons: if `value < min`, return `min`; else if `value > max`, return `max`; otherwise return `value`. Thus a finite raw value above 360 is clamped to `90.0F` before `turn` returns. `Entity.java:326–329` has another setter, protected `setRot(float,float)`, which uses `% 360.0F`; `turn` does not call it, so modulo is not part of this pitch operation.
- Concrete finite witness: start with `xRot == 0.0F` and call `turn(0.0, 2401.0)`. `f` is the finite `double` result of `2401.0 * 0.15` (approximately `360.15`); the first pitch assignment casts this to finite `float` approximately `360.14999F`, which is strictly greater than 360. The later float clamp stores `90.0F`. The previous pitch can likewise be set to `0.0F` for this witness, so its independent old-pitch write also remains finite. This is an allowed finite argument to the public method: there is no magnitude or finite-value guard in `turn`. In the ordinary control call, `net/minecraft/client/MouseHandler.java:212–243` passes its finite vertical turn delta as `this.minecraft.player.turn(j, k * n)`; the non-smoothing path derives `k` from accumulated vertical mouse movement and the selected sensitivity factor, and `n` is `1` or `-1` for Y inversion. No device callback scheduling or render flow is needed for the source-level call relation.
- The method is inherited by the local player. The source declarations are `LivingEntity extends Entity` (`LivingEntity.java:111`), `Player extends LivingEntity` (`Player.java:111`), `AbstractClientPlayer extends Player` (`AbstractClientPlayer.java:21`), and `LocalPlayer extends AbstractClientPlayer` (`LocalPlayer.java:79`); none of these intervening types declares a `turn` override. Thus the ordinary local player call reaches this `Entity.turn` implementation.
- A reachable active Elytra state exists through `Player.tryToStartFallFlying()` (`Player.java:1520–1529`): while airborne, not already fall-flying, not in water and without levitation, an enabled Elytra in the chest slot triggers `startFallFlying()`, which sets shared flag 7 (`Player.java:1532–1534`). `LivingEntity.isFallFlying()` reads that flag (`LivingEntity.java:2891–2893`). In `LivingEntity.travel(Vec3)`, the active `else if (this.isFallFlying())` branch (`LivingEntity.java:1979–2008`) reads the inherited current pitch twice: `getLookAngle()` uses `Entity.getLookAngle()` (`Entity.java:1700–1702`), which passes `xRot` and `yRot` into `calculateViewVector`; and local `float j = this.xRot * (float)(Math.PI / 180.0)` (`LivingEntity.java:1985–1986`) feeds `Mth.cos(j)` and the negative-pitch condition at line 1998. It then computes and stores gliding velocity and moves the player. This is actual player movement use of the current, clamped pitch; it does not turn the transient >360 intermediate into active state.

## Movement consequence

The direct pitch operation is identical across the compared releases, and its reachable ordinary path ends with the same finite `[-90, 90]` float pitch before active Elytra travel reads it. There is no 1.16.3→1.16.4 behavior finding for this operation. The transient finite >360 value is an intermediate assignment, not persistent pitch or a difference in gliding behavior.
