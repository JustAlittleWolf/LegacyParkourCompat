## Technical trace and verdict

**Verdict: no source difference in the assigned ordinary `Entity.turn` pitch write/clamp operation or its first active Elytra movement pitch read.** This is a bounded operation verdict, not a full-pair movement freeze.

In both exact versions, `Entity.turn(double d, double e)` first computes `float f = (float)e * 0.15F` and `float g = (float)d * 0.15F`. It calls `setXRot(getXRot() + f)` before the yaw write, then separately calls `setXRot(Mth.clamp(getXRot(), -90.0F, 90.0F))`. It subsequently advances `xRotO` by the un-clamped `f` and clamps `xRotO` to the same interval. The call order, float casts, float multiplication, clamp bounds, and old-rotation update are the same in 1.17.0 (`Entity.java`, lines 377–387) and 1.17.1 (lines 377–387).

The ordinary public `setXRot(float f)` is a raw finite-value setter in both versions: if `!Float.isFinite(f)`, it logs/pauses and discards; otherwise it assigns `this.xRot = f`. It does not normalize, modulo, or clamp. This is the first pitch setter invoked by `turn`; the clamp happens only in the later second setter call. Source locations: 1.17.0 `Entity.java`, lines 3021–3028; 1.17.1, lines 3023–3030. The identical finite gate and direct assignment make the intermediate write reachable for finite out-of-range values.

A concrete ordinary client input can make that first write exceed 360 degrees. `MouseHandler` accumulates mouse deltas, computes `f = sensitivity * 0.6F + 0.2F`, `g = f * f * f`, and normally `h = g * 8.0`, then passes `accumulatedDY * h` (with optional sign inversion) to `player.turn` (`MouseHandler.java`, lines 213–244 in both releases). With the sensitivity field set to `1.0`, smooth camera off, not scoping, no Y inversion, zero starting pitch, and a finite accumulated vertical mouse delta of 600, `h` is approximately 4.096; `e` is approximately 2457.6; the required `(float)e * 0.15F` produces approximately `368.64F`, which is finite and greater than 360. The first setter therefore stores that raw intermediate value. The next setter in the same `turn` clamps current pitch to `90.0F` before the method returns. The source imposes no smaller cap on the accumulated mouse delta. This witness demonstrates the intermediate setter/order; it does not claim that `turn` leaves pitch above 360.

For an already active fall-flying entity on the next `LivingEntity.travel` movement, both releases enter `else if (this.isFallFlying())`, get velocity, then obtain `getLookAngle()` and immediately compute `float j = this.getXRot() * (float)(Math.PI / 180.0)`. `Entity.getLookAngle()` itself calls `calculateViewVector(this.getXRot(), this.getYRot())`. Thus the movement reads the post-turn current pitch live, after the final clamp (90 degrees for the witness), not the transient first-setter value. Elytra branch operation order and current-pitch reads are the same: 1.17.0 `LivingEntity.java`, lines 2064–2079; 1.17.1, lines 2068–2083; `Entity.java` `getLookAngle`, lines 1829–1831 in both. No claim is made about other Elytra math changes outside this assigned setter/read boundary.
