## Compared source behavior

- `world/entity/Entity.java`, `turn(double d, double e)`: 1.17 lines 377–389 and 1.17.1 lines 377–389 are identical in relevant operation order. First `float f = (float)e * 0.15F`; then `float g = (float)d * 0.15F`; then `setXRot(getXRot() + f)`; then `setYRot(getYRot() + g)`; only after that, `setXRot(Mth.clamp(getXRot(), -90.0F, 90.0F))`; afterward `xRotO += f`, `yRotO += g`, clamp `xRotO`, and notify the vehicle if present. Both parameters are `double`; the casts occur before `float` multiplication, and pitch addition is `float` plus `float` before the setter.
- `Entity.setXRot(float)`: 1.17 lines 3021–3027 and 1.17.1 lines 3023–3029 have the same finite-only guard: non-finite values go to `Util.logAndPauseIfInIde`; finite values are assigned directly to `xRot`. The setter itself has no angle-range clamp.
- Finite post-cast witness: take finite `e = 3000.0` and initial `getXRot() = 0.0F`. `(float)e` remains finite `3000.0F`; multiplying by `0.15F` yields finite `f = 450.0F`. The first setter therefore receives finite `450.0F` and accepts it. The subsequent yaw setter runs before the direct pitch clamp; the final pitch clamp in `turn` then stores `90.0F`. This is a source arithmetic witness, not a runtime test or claim that the ordinary mouse path produces that input.
- `util/Mth.java`, `clamp(float f, float g, float h)`, lines 120–126 on both sides returns the lower bound for `f < g`, otherwise the upper bound for `f > h`, otherwise `f`. The constants in `turn` are floats, so this overload is selected.
- Caller context only: `client/MouseHandler.java` line 244 calls `this.minecraft.player.turn(k, l * q)` when a player exists; `q` is `1` or `-1` for the invert-Y-mouse option at lines 237–240. Device plumbing and sensitivity calculations are not considered here.

## First active Elytra pitch use

`Player` extends `LivingEntity` on both sides (1.17.1 `player/Player.java` line 113). `Player.travel` delegates to `super.travel(vec3)` on the normal non-swimming/non-creative-flight path (1.17 lines 1418–1444; 1.17.1 lines 1409–1436). In `LivingEntity.travel`, the `else if (this.isFallFlying())` branch is the active flight path (1.17 lines 2064 onward; 1.17.1 lines 2068 onward). Its first pitch-dependent operation is `this.getLookAngle()`; `Entity.getLookAngle()` returns `calculateViewVector(getXRot(), getYRot())` (Entity lines 1831–1833), and `calculateViewVector` converts its pitch argument to radians and uses pitch sine/cosine (Entity lines 1337–1345). The next explicit pitch use is `float j = this.getXRot() * (float)(Math.PI / 180.0)` in the fall-flying branch (1.17 line 2071; 1.17.1 line 2075); `j` feeds `Mth.cos(j)` and, on the negative-pitch branch, `-Mth.sin(j)`, which contribute to the updated movement vector (1.17 lines 2075–2093; 1.17.1 lines 2079–2096). The branch and these pitch operations retain the same order and math in the compared releases.
