# Independent source audit — swim-pitch vertical adjustment, 1.21.7 → 1.21.8

## Frozen independent trace (written before opening the author report)

**Scope:** local, nonpassenger `Player.travel(Vec3)` and its own swim/pitch vertical-velocity adjustment; exact Mojmap decompiled sources. Trace covers the `Player` override, stored pitch input, Mth trig table/index semantics, adjustment gates and sampling order, and the actual inherited movement call.

**1.21.7:** `net/minecraft/world/entity/player/Player.java:1438-1461` overrides `travel`. A passenger immediately calls `super.travel(input)` and skips the player-specific adjustment. For a nonpassenger, the override first checks `isSwimming()`. The player override at `Player.java:1774-1776` defines that predicate as `!abilities.flying && !isSpectator() && super.isSwimming()`; the base `Entity.isSwimming()` reads shared flag 4. When true, `getLookAngle().y` is sampled into a `double`; a `double` coefficient is chosen as `0.085` when look-Y `< -0.2`, otherwise `0.06`. The update gate is `lookY <= 0.0 || jumping || !level.getFluidState(BlockPos.containing(x, y + 1.0 - 0.1, z)).isEmpty()`. Only after that gate passes does it sample current delta movement, then set velocity to the sampled vector plus `(0.0, (lookY - sampledDeltaY) * coefficient, 0.0)`. Thus this is a direct pre-super Y-velocity adjustment; the fluid query uses the pre-super position and exact `y + 1.0 - 0.1` expression. Next, flying players save current Y, call inherited travel, then restore Y scaled by `0.6`; otherwise they call inherited travel directly. The swimming predicate excludes flight, so local swimming and the flying postprocessing branch do not coincide for ordinary `Player` behavior.

`Entity.getLookAngle()` (`Entity.java:2356-2358`) calls `calculateViewVector(getXRot(), getYRot())`. `getXRot()` (`Entity.java:3705-3707`) returns the raw stored `float xRot`; it does not interpolate or clamp at read time. `calculateViewVector` (`Entity.java:1746-1754`) first computes float radians `pitch * (float)(Math.PI / 180.0)` and yaw radians `-yaw * (float)(Math.PI / 180.0)`, then evaluates table cosine(yaw radians), sine(yaw radians), cosine(pitch radians), sine(pitch radians), returning `new Vec3(sinYaw * cosPitch, -sinPitch, cosYaw * cosPitch)`. The Y component is therefore unary-negated float table output, widened to the `Vec3` double coordinate; the subsequent `getLookAngle().y` is double. Pitch is the directly stored current entity pitch, not old/interpolated pitch.

`Mth` initializes private `float[65536] SIN` through `Util.make`; for each integer `i` from 0 inclusive to length exclusive, it stores `(float)Math.sin(i * Math.PI * 2.0 / 65536.0)` (double expression, then float narrowing). `sin(float a)` returns `SIN[(int)(a * 10430.378F) & 65535]`; the multiplication is float, cast to int truncates toward zero, then mask wraps to 16 bits. `cos(float a)` uses `SIN[(int)(a * 10430.378F + 16384.0F) & 65535]`, likewise float operations before cast. This establishes the precise yaw/pitch table path and float-to-double widening in the vertical sample.

For the nonflying nonpassenger path, `Player.travel` calls `LivingEntity.travel` (`LivingEntity.java:2245-2254`). If in water or lava, affected by fluids, and not standing on that fluid, it calls `travelInFluid`; otherwise fall-flying or air travel is selected. Under ordinary swimming-in-water conditions the inherited water branch (`LivingEntity.java:2301-2351`) calculates fluid movement inputs, runs `moveRelative`, then `move(MoverType.SELF, getDeltaMovement())` before applying post-move slowdown/falling adjustment. `Entity.move` (`Entity.java:663+`) is the actual movement/collision/position application, so the direct player Y adjustment is consumed by the real inherited movement path, not merely stored and ignored.

No alternate interpolation or pitch source is used in this override.

Exact source condition in both releases, `Player.java:1445-1446`, is `lookY <= 0.0 || jumping || !level().getFluidState(BlockPos.containing(x, y + 1.0 - 0.1, z)).isEmpty()`. The negation means the fluid state at that position must be nonempty for the third disjunct to pass. The author report instead says the update occurs when that fluid state “is empty.” For a positive look-Y sample with `jumping == false`, an empty sampled fluid state makes the source gate false; a nonempty sampled fluid state makes it true. Thus the reversed clause changes the reachability account and can describe the opposite direct Y-velocity write. Correct that sentence to “the sampled fluid state is nonempty,” while retaining the report's no-difference conclusion.
