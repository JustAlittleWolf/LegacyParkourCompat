## Trace and comparison

Assumptions for the concrete path: a ticking, unmounted local player in a loaded chunk; the player is the camera entity; the player is not immobile, flying, swimming, or sprinting. World, pose, crouch, held-item/use, and logical key states are supplied to their source gates. Keyboard device plumbing and sprint activation/timers are outside this slice.

1. Local login and respawn assign `new KeyboardInput(this.minecraft.options)` to the local player's `input` in both versions (`ClientPacketListener`, 1.16.1 lines 393–400 and 1131–1136; 1.16.2 lines 388–395 and 1102–1107). `LocalPlayer.tick()` calls `super.tick()` inside the `level.hasChunkAt(...)` gate in both versions (1.16.1 lines 182–200; 1.16.2 lines 183–201). `LivingEntity.tick()` dispatches `this.aiStep()` in both (1.16.1 lines 2122–2169; 1.16.2 lines 2124–2171); dynamic dispatch reaches `LocalPlayer.aiStep()`.
2. `KeyboardInput.tick(boolean)` reads up/down/left/right into booleans, then sets float axes in the same order and with the same expressions in both versions (1.16.1 and 1.16.2 `KeyboardInput.java`, lines 12–25). Forward is `0.0F` when up equals down, otherwise `1.0F` for up and `-1.0F` for down. Lateral is `0.0F` when left equals right, otherwise `1.0F` for left and `-1.0F` for right. No diagonal normalization occurs. Jump and shift flags are read after those axes. When `bl` is true, each float is multiplied by the unsuffixed double literal `0.3`, then explicitly narrowed back to float: `(float)(this.leftImpulse * 0.3)` and the corresponding forward expression. `Input` declares both axes as public `float`; its base `tick` is empty and `getMoveVector()` returns `new Vec2(leftImpulse, forwardImpulse)` (both versions `Input.java`, lines 5–24).
3. In both `LocalPlayer.aiStep()` implementations, `crouching` is recomputed before `input.tick`: it is gated by not flying, not swimming, permission to enter `Pose.CROUCHING`, and either `isShiftKeyDown()` or not sleeping and unable to enter `Pose.STANDING` (1.16.1 lines 659–666; 1.16.2 lines 633–641). `isShiftKeyDown()` reads the existing `input.shiftKeyDown` field (1.16.1 lines 619–621; 1.16.2 lines 594–596), so this crouch computation precedes the current tick's keyboard shift read. The subsequent `input.tick(this.isMovingSlowly())` receives `isCrouching() || isVisuallyCrawling()` in both (1.16.1 lines 624–631 and 666; 1.16.2 lines 594–606 and 641). `Entity.isVisuallyCrawling()` is `isVisuallySwimming() && !isInWater()` in both (1.16.1 lines 1852–1858; 1.16.2 lines 1845–1851). This documents the dry visual-crawl slowdown gate; no swimming travel behavior is claimed.
4. Immediately after `input.tick` and tutorial notification, both versions multiply the lateral and forward input floats by `0.2F` if `isUsingItem() && !isPassenger()` (1.16.1 `LocalPlayer.java` lines 666–672; 1.16.2 lines 641–647). With the assigned unmounted assumption, the item-use predicate alone controls this additional slowdown. This is sequential after the optional `0.3` cast path.
5. `LocalPlayer.serverAiStep()` calls its superclass, then copies `input.leftImpulse` to float `xxa` and `input.forwardImpulse` to float `zza` only when `isControlledCamera()` is true (1.16.1 lines 633–645; 1.16.2 lines 608–620). `isControlledCamera()` compares `minecraft.getCameraEntity() == this` in both (1.16.1 lines 647–649; 1.16.2 lines 622–624). The local override of `isEffectiveAi()` returns `true` in both (1.16.1 lines 518–521; 1.16.2 lines 493–496). `LivingEntity.aiStep()` invokes `serverAiStep()` on the non-immobile effective-AI branch (1.16.1 lines 2412–2423; 1.16.2 lines 2414–2425); the immobile branch instead zeros `xxa` and `zza` in both.
6. After the intervening jump section, `LivingEntity.aiStep()` multiplies each float field by `0.98F`, in lateral-then-forward order, and constructs `new Vec3(this.xxa, this.yya, this.zza)` for `this.travel(...)` in both versions (1.16.1 lines 2451–2458; 1.16.2 lines 2453–2460). The floats are widened to the `Vec3` coordinate type by the constructor call; only the horizontal argument dependency is assessed here. LocalPlayer inherits this travel call path. No difference appears in the operations, order, numeric literals, casts, types, or gates in this bounded chain.

## Exclusions and limits

The local `aiStep()` neighborhood has other changes outside this assignment: 1.16.1 calls `checkInBlock(...)` at four offsets (lines 681–685), whereas 1.16.2 calls `moveTowardsClosestSpace(...)` at those offsets (lines 656–660). This is collision/space handling, explicitly outside the owned input-assembly slice; this audit makes no finding about it. Also excluded are travel-body math, movement rotation, collision/support/stepping, swimming, sprint transitions, jump and vertical behavior, flight, riding, input-device plumbing, and the surrounding player tick graph. Other differences or unchanged behavior elsewhere in the pair are not assessed.
