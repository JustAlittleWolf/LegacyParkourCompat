# Horizontal travel coverage: 1.14.3 to 1.14.4

## Bounded result

No independent movement delta was found in the assigned ordinary dry, unmounted, nonsprinting local-player ground/air horizontal-travel slice. This is a coverage report, not a change finding. It does not close the complete 1.14.3--1.14.4 pair inventory or its independent audit.

Inputs treated as supplied for this comparison: movement input vector, yaw, `onGround`, and the slipperiness/friction coefficient from the supporting block. Comparison excludes swimming, lava, fall-flying, abilities flight, sprint behavior, vertical gravity and thresholds, climb handling, collision/support/stepping behavior, block coefficient providers, setters/camera, and jump behavior.

## Compared dispatch and operations

- **Player dispatch and selected speed:** 1.14.3 `PlayerEntity.travel(Vec3d)` (`PlayerEntity.java:1364-1392`) and 1.14.4 `Player.travel(Vec3)` (`Player.java:1380-1408`) both delegate to `LivingEntity.travel` on the ordinary non-swimming, non-ability-flying path when unmounted. Player movement-speed selection is the same float cast of the movement-speed attribute value: `PlayerEntity.getMovementSpeed()` (`PlayerEntity.java:1407-1410`) and `Player.getSpeed()` (`Player.java:1423-1426`). Both player constructors set the base movement-speed attribute to `0.1F` (`PlayerEntity.java:175`; `Player.java:192`).
- **Consumed input scaling and yaw transform:** 1.14.3 `Entity.updateVelocity` / `movementInputToVelocity` (`Entity.java:1055-1070`) maps by body to 1.14.4 `Entity.moveRelative` / `getInputVector` (`Entity.java:1080-1095`). Both compute input length squared in double; return zero below `1.0E-7`; normalize only above length squared `1.0`; scale by the float acceleration; convert the supplied yaw with `g * (float)(Math.PI / 180.0)`; get sine then cosine; and apply the same component expressions. `Vec3d.normalize` (`Vec3d.java:25-27`) and `Vec3.normalize` (`Vec3.java:29-31`) use the same square-root, `1.0E-4` guard and component divisions. The scalar `multiply`/`scale` implementations both delegate to component multiplication. `MathHelper.sin/cos` (`MathHelper.java:24-29`) and `Mth.sin/cos` (`Mth.java:25-30`) use the same table index expressions. No input threshold, normalization, scale type, trig ordering, or yaw rotation difference appears.
- **Ground/air acceleration and horizontal drag:** In the ordinary dry branch, 1.14.3 `LivingEntity.travel` (`LivingEntity.java:1833-1839`, then horizontal post-move writes at `1858-1860`) reads the supplied slipperiness, computes `w = onGround ? v * 0.91F : 0.91F`, applies `updateVelocity(method_18802(v), input)`, then moves. 1.14.4 has the corresponding sequence in `LivingEntity.travel` (`LivingEntity.java:1836-1842`, horizontal post-move write at `1860`): `getFriction()`, the same `w` expression, `moveRelative(getFrictionInfluencedSpeed(v), input)`, then move. The helper bodies are equivalent: 1.14.3 `method_18802` (`LivingEntity.java:1954-1956`) returns `onGround ? getMovementSpeed() * (0.21600002F / (v * v * v)) : field_6281`; 1.14.4 `getFrictionInfluencedSpeed` (`LivingEntity.java:1957-1959`) returns `onGround ? getSpeed() * (0.21600002F / (v * v * v)) : flyingSpeed`. Both air fields are float `0.02F` (`LivingEntity.java:143` in each release, with Yarn name `field_6281` in 1.14.3). After the move and the unchanged vertical-path code, both multiply horizontal velocity components by the same float `w`: 1.14.3 `setVelocity(lv8.x * w, ..., lv8.z * w)` (`LivingEntity.java:1860`); 1.14.4 `setDeltaMovement(vec38.x * w, ..., vec38.z * w)` (`LivingEntity.java:1862`).

The compared methods preserve operation order, float constants and intermediates, double input-vector arithmetic, and horizontal drag. Identifier/mapping and vector API names differ, but no behavior delta is evidenced for this bounded slice. Vertical updates and the post-move collision/climb branches are intentionally not assessed here.
