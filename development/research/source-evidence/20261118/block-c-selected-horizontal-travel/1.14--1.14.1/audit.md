# Independent source audit: 1.14 → 1.14.1 horizontal travel

## Assignment and limits

Compared only stable Java 1.14 to 1.14.1, Yarn-mapped decompiled client sources, for ordinary dry, unmounted, local-player, nonsprinting ground/air horizontal travel. The supplied inputs are block slipperiness, `onGround`, yaw, current velocity, the travel input vector, and the effective movement-speed attribute. Sprint, sneak, item-use input scaling, swimming, lava, Elytra, abilities flight, jump, climb, vertical gravity/threshold behavior, collision/support/step resolution, block/provider behavior, and camera/input-device setters are outside this audit. The comparison does not establish a boundary inside the 1.14.0–1.14.1 interval or tick-level equivalence outside the stated path.

## Traced path and exact findings

1. `LivingEntity.tickMovement` (1.14 and 1.14.1, `net/minecraft/entity/LivingEntity.java:2197–2205`) applies `sidewaysSpeed *= 0.98F` and `forwardSpeed *= 0.98F`, then passes `(sidewaysSpeed, upwardSpeed, forwardSpeed)` in that order to `travel`. `ClientPlayerEntity.tickMovement` calls its superclass movement path (`net/minecraft/client/network/ClientPlayerEntity.java:607–762`); its compared method body is identical between releases. Assumption: ordinary locomotion has already supplied the intended local input values and does not activate excluded input scaling branches.
2. `PlayerEntity.travel` (`net/minecraft/entity/player/PlayerEntity.java:1362–1387`) reaches `super.travel(arg)` in the ordinary nonswimming, nonflight path. In `LivingEntity.travel` (`net/minecraft/entity/LivingEntity.java:1763–1823`), the dry, nonlava, nonfall-flying path selects the block slipperiness `v`, computes `w = this.onGround ? v * 0.91F : 0.91F`, and calls `updateVelocity(this.method_18802(v), arg)` before movement. `method_18801` is a climbing adjustment and is inactive under this assignment's nonclimbing precondition.
3. Acceleration selection is `method_18802(float f)` (`LivingEntity.java:1938–1940`): grounded travel returns `this.getMovementSpeed() * (0.21600002F / (f * f * f))`; airborne travel returns `this.field_6281`. `PlayerEntity.tickMovement` calls `super.tickMovement()` first, then resets `field_6281` to `0.02F` and applies a sprint-only addition (`PlayerEntity.java:492–503`). Therefore, for the nonsprinting path, the current travel uses the default/prior-tick `0.02F` air factor, and the same value is reset for the next tick. The player's override `getMovementSpeed()` (`PlayerEntity.java:1405–1408`) returns `(float)this.getAttributeInstance(EntityAttributes.MOVEMENT_SPEED).getValue()`. Player initialization sets the movement-speed attribute base to `0.1F` (`PlayerEntity.java:170–177`); the effective attribute value, including any applicable modifiers, is what the getter selects. The shared `LivingEntity.getMovementSpeed()` storage getter is overridden for players and is not the player selection path.
4. `Entity.updateVelocity` and `movementInputToVelocity` (`net/minecraft/entity/Entity.java:1009–1024`) add the transformed input to current velocity. The transform returns zero when input length-squared is `< 1.0E-7`; otherwise it normalizes only when length-squared is `> 1.0`, multiplies by the selected float acceleration, computes sine/cosine from yaw times `(float)(Math.PI / 180.0)`, and returns `(x*cos - z*sin, y, z*cos + x*sin)`. This preserves the precise strict comparisons, casts, and operation order in both releases.
5. After the move operation, the dry branch applies the horizontal factor to the resulting x and z velocities as `lv8.x * w` and `lv8.z * w` (`LivingEntity.java:1823–1843`). Thus the supplied grounded block coefficient contributes `v * 0.91F`; in air the horizontal factor is `0.91F`. `Block.getSlipperiness()` (`net/minecraft/block/Block.java:687–689` in 1.14; `:698–700` in 1.14.1) simply returns its stored float; the block coefficient's production is not part of this comparison.

The exact extracted method texts compared equal across releases for `ClientPlayerEntity.tickMovement`, `LivingEntity.tickMovement`, `LivingEntity.travel`, `LivingEntity.method_18802`, `LivingEntity.getMovementSpeed`, `PlayerEntity.tickMovement`, `PlayerEntity.travel`, `PlayerEntity.getMovementSpeed`, `PlayerEntity.initAttributes`, `Entity.updateVelocity`, `Entity.movementInputToVelocity`, and `Block.getSlipperiness`. No scoped source difference was found. The movement-speed path, float constants and arithmetic, input rotation, friction branch, and their order are unchanged for the assigned ordinary ground/air case.

## Exclusions and closure limits

This is a bounded horizontal-travel comparison, not a full player-tick coverage or pair-freeze claim. It does not audit client input generation/setters, attribute modifier producers, block friction producers, movement/collision implementation, post-travel vertical changes, or other movement branches. It makes no claim about runtime parity or other 1.14 patch releases.


## Phase 2 independent review

The assigned provenance identities match, and the paired dry ground/air travel, player travel delegation and movement-speed getter, input acceleration transform, acceleration selection, and horizontal drag/friction operations agree with the frozen independent audit: no source delta is present in those operations.

Qualification: the author report correctly records that `PlayerEntity.tickMovement` writes `field_6281` after the inherited travel call. A preceding sprint tick can therefore leave its sprint-adjusted value for the next travel even if that next travel is nonsprinting. The blind-prefix sentence that current nonsprinting travel uses the default/prior-tick `0.02F` is valid only for steady nonsprinting history; it omits this preceding-sprint edge. Sprint transitions are outside the assigned slice, so this does not change the scoped no-difference verdict, but retain the author report's caveat when reusing the finding. The author report additionally claims exact parity for `Input`, `KeyboardInput`, and `tickNewAi` upstream slices; those were outside the blind audit's stated independent coverage and are not independently accepted by this verdict. No pair-wide coverage or runtime-parity conclusion follows.
