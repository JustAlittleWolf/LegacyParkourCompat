# Player correction gates block rollback snaps by acknowledgment sequence

Difference: Both clients process retained prediction entries with `state.sequence <= acknowledgmentSequence`. 1.21.11 always passes each entry's saved player position to block-state synchronization. 26.1.2 records the current prediction sequence after handling a direct player correction. For each handler call, it passes every processed entry’s saved position when `lastTeleportSequence < acknowledgmentSequence`; otherwise it passes `null` for every processed entry. The comparison is between the correction cutoff and the acknowledgment packet sequence, not between the cutoff and each entry's retained sequence. If a differing block state is restored, `syncBlockState` applies the saved-position `absSnapTo` only when the local player is in the same level, collides with the restored state, and the supplied position is non-null.
Movement meaning: For a block-change acknowledgment whose sequence is at or below the sequence captured by the correction, no retained entry processed by that acknowledgment can snap the player to its saved position. For an acknowledgment above that cutoff, saved positions are supplied for all processed entries, including potentially pre-correction entries; a colliding rollback can still snap the player. The gate therefore prevents only the acknowledgment-bounded stale position response, rather than suppressing every later rollback of pre-correction state.
