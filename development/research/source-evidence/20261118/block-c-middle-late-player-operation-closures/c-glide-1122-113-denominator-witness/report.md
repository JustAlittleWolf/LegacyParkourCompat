## Results

- **A normal vanilla input reaches the changed gate.** In both releases, `updateLocalPlayerCamera` clamps pitch to `[-90.0F, 90.0F]`; therefore `pitch = -90.0F` is an ordinary attainable view angle. With the assigned already-active glide, dry state and local-client control, `LivingEntity.moveRelative` reaches its glide branch. This is source reachability, not a claim about startup or glide activation.
- **The old look vector has a tiny but nonzero horizontal denominator at that angle.** In 1.12.2, `getRotationVector` computes its horizontal multiplier as `-MathHelper.cos(-pitch * (float)(PI / 180.0))`. For `pitch = -90.0F`, the cosine lookup receives positive `1.5707964F`; the source lookup `(int)(x * 10430.378F + 16384.0F)` selects sine-table index `32768`. The table initializes that entry from `(float)Math.sin(PI)`, approximately `1.2246469e-16F`, not zero. For ordinary yaw `0.0F`, the resulting horizontal look magnitude used by the correction is approximately `1.2246468525851679e-16`, hence `j > 0.0` in the old method’s local names. The old pitch correction’s sole gate is `i < 0.0F`, so it enters and divides its look-vector x/z terms by that nonzero magnitude.
- **The 1.13 look vector is exactly horizontal-zero at the same angle.** Its `getRotationVector` instead computes `j = MathHelper.cos(pitch * (float)(PI / 180.0))` and returns horizontal components multiplied by `j`. At `pitch = -90.0F`, the float argument is `-1.5707964F`; the same cosine lookup selects index `0`, whose initialized sine-table value is exactly `0.0F`. Thus both horizontal look components are exactly zero and the 1.13 local horizontal look magnitude `k = sqrt(x*x + z*z)` is `0.0`. Its pitch correction requires `j < 0.0F && k > 0.0`; pitch is negative but the second condition is false, so the correction and divisions are skipped.
- **The gate difference is not dormant for vanilla input.** It is witnessed by the clamped ordinary angle `pitch = -90.0F` (yaw `0.0F` suffices). The old branch enters with a tiny nonzero denominator; the 1.13 branch rejects the exact zero denominator. In each release the correction occurs before that glide path’s immediate `move(MoverType.SELF, velocityX, velocityY, velocityZ)` call (`1.12.2:1464`, `1.13:1504`), which connects the condition to the first active glide movement step. The old correction amount remains proportional to current horizontal speed; if that speed is zero, entering its branch alone does not imply a nonzero velocity change.
