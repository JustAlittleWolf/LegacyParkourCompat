# Mojmap 1.16.1 → 1.16.2: local player input-to-travel handoff

## Result

No residual movement difference was found in the assigned ordinary, no-effect on-foot local-player slice. The compared keyboard input, pose decision, local-player ownership and camera-control gates, pre-travel handoff, no-fluid ground travel path, and direct post-travel movement writes/callback order are identical. The sole direct-write refactor in the examined path (`Entity.setPos`) delegates to an expression with the same operations, types, and AABB argument order.

This is a bounded source result, not full-pair coverage or an independent audit. No implementation, tests, builds, game launch, or source generation were performed.

## Compared call path and gates

1. `LocalPlayer.tick()` is identical (1.16.1 `LocalPlayer.java:183+`; 1.16.2 `:184+`): when the player's chunk is loaded it calls `super.tick()`, then handles the passenger-or-local-position reporting branch. Packet output is outside this assignment.
2. The keyboard layer is byte-identical by source digest. `KeyboardInput.tick(boolean)` reads up/down/left/right, derives `forwardImpulse` and `leftImpulse` as `0`, `+1`, or `-1`, reads jump and shift, then applies `(float)(impulse * 0.3)` to both movement impulses when its slow-movement argument is true (`KeyboardInput.java:13+`). `Input.getMoveVector()` and `hasForwardImpulse()` are identical as well.
3. `LocalPlayer.aiStep()` keeps the same pre-travel order and conditions (1.16.1 `LocalPlayer.java:652+`; 1.16.2 `:627+`): save prior jump/shift and sprint-start state; calculate crouching using flight, swimming, pose eligibility, shift/sleeping; refresh input via `input.tick(isMovingSlowly())`; apply item-use scaling; process auto-jump and sprint/flying/jump state; and, under the identical `isControlledCamera()` gate, copy `input.leftImpulse`, `input.forwardImpulse`, and `input.jumping` into `xxa`, `zza`, and `jumping`. Its controlled-camera check and `LocalPlayer.isLocalPlayer()` are identical. Player pose selection (`Player.updatePlayerPose`, `Player.java:348+`), player pose dimensions, `Entity.canEnterPose`, and dimension refresh are also identical.
4. The handoff is unchanged: `LocalPlayer.aiStep()` calls `Player.aiStep()` (`Player.java:483+`), which calls `LivingEntity.aiStep()` at `Player.java:500`. In `LivingEntity.aiStep()` the jump gate runs first; then `xxa` and `zza` are multiplied by `0.98F`, fall-flying state is updated, the old AABB is saved, and `travel(new Vec3(xxa, yya, zza))` is invoked (1.16.1 `LivingEntity.java:2366+`; 1.16.2 `:2368+`). `isControlledByLocalInstance()` is identical and the `LivingEntity.travel()` entry gate remains `isEffectiveAi() || isControlledByLocalInstance()` (`:1912+` / `:1914+`).
5. For the bounded ordinary path (on foot, no water/lava, no fall flight, no relevant effect), the identical `LivingEntity.travel()` reaches the ground branch: obtain the below-block friction; use `t * 0.91F` on ground, otherwise `0.91F`; compute relative friction movement; subtract gravity only when not levitation-affected, in an unloaded-client-chunk override, or no-gravity; then write `(x*u, y*0.98F, z*u)`. `handleRelativeFrictionAndCalculateMovement()` keeps the same operation order: `moveRelative`, climbable handling, `move(MoverType.SELF, delta)`, then its climb/jump vertical response.
6. `Player.travel()` is identical (1.16.1 `Player.java:1380+`; 1.16.2 `:1387+`). It saves position, conditionally applies the swimming vertical response, delegates flying or normal travel to `super.travel()`, restores flying-speed state on the flying branch, and invokes `checkMovementStatistics()` afterward. In the ordinary path the relevant no-fluid/no-flight gates select the same superclass call. Statistics/food production itself is outside movement scope; its method body is identical.
7. Direct movement writes and callbacks keep their sequence in `Entity.move()` (1.16.1 `Entity.java:469+`; 1.16.2 `:485+`): collision result updates the box and position; collision flags and `onGround` are assigned; fall damage callback runs; blocked horizontal velocity components are zeroed; block `updateEntityAfterFallOn` and `stepOn` run under the same gates; then movement distance, inside-block processing, and block-speed velocity scaling run. `LocalPlayer.move()` is identical. The edge-backoff call is excluded by assignment.
8. `Entity.setPos()` changed shape construction from inline width/height locals to `dimensions.makeBoundingBox(d,e,f)` (1.16.1 `Entity.java:321-325`; 1.16.2 `:331-333`). The new 1.16.2 `EntityDimensions.makeBoundingBox(double,double,double)` (`EntityDimensions.java:21-25`) computes `float g = width / 2.0F`, `float h = height`, and `new AABB(d - g, e, f - g, d + g, e + h, f + g)`, exactly matching the 1.16.1 inline statements, including float types, evaluation order, and constructor argument order. No behavioral delta follows for this write.

## Excluded changes and bounds

- `LocalPlayer.aiStep()` replaces four `checkInBlock(x, y + 0.5, z)` calls in 1.16.1 (`LocalPlayer.java:682-685`) with four `moveTowardsClosestSpace(x,z)` calls in 1.16.2 (`:657-660`). These occur under the same `!noPhysics` gate, before the unchanged subsequent travel handoff. This is suffocation handling and excluded. Replacing only those four call lines with an exclusion marker makes the complete `aiStep()` method bodies equal.
- `Entity.move()` removes the explicit `isTouchingLava = false` assignment before `checkInsideBlocks()` in its exception-guarded section (1.16.1 `Entity.java:552-554`; 1.16.2 `:567-570`). This is fluid-state behavior and excluded. The remaining movement method differs only by that removed reset; edge-backoff mechanics are outside this slice.
- No conclusions are made about fluids, Soul Speed, suffocation, edge-backoff, packet behavior, mounted paths, other effects, other movement branches, or the complete 1.16.1→1.16.2 pair inventory.
