## Compared behavior

- `Entity.turn` (1.15.2 `Entity.java:326–337`; 1.16 `Entity.java:332–343`) is identical. It accepts two `double`s; computes pitch delta `e * 0.15` and yaw delta `d * 0.15` as doubles; adds each to the corresponding float rotation, then casts each result back to float. It independently updates `xRotO` and `yRotO` from their prior values using the same deltas. It clamps current and previous pitch to `[-90.0F, 90.0F]`; yaw is not clamped or wrapped here. There is no explicit finite-value guard. `Mth.clamp(float,...)` is the same comparison-based implementation in both versions: NaN passes through; positive/negative infinite pitch clamps to an endpoint. Yaw infinities/NaN are stored through the float cast. `setRot` separately applies `% 360.0F`, but `turn` does not call it. Both `baseTick` methods copy current rotation to the `O` fields before later tick work (`Entity.java:359–360` and `:365–366`), unchanged for rotation.
- The only direct `.turn(...)` call in either source tree is the local `MouseHandler.turnPlayer` path: when the mouse is grabbed and the window active, it calls `minecraft.player.turn(j, k * n)` if a player exists (1.15.2 `MouseHandler.java:192–223`; 1.16 `:212–243`). Both calls and their caller gate are equivalent. The values remain double through `turn`; `n` is an integer ±1 for inverted Y. Neither caller adds a finite guard.
- The first ordinary dry ground/air yaw acceleration is `Entity.moveRelative` → private `getInputVector` (1.15.2 `Entity.java:1063–1080`; 1.16 `:1073–1090`). Both bodies are identical: movement input is a `Vec3`; its squared length is tested against `1.0E-7`; inputs above unit squared length are normalized; the result is scaled by float acceleration. Yaw is read as float, converted to radians with float arithmetic, fed to identical table-based float `Mth.sin/cos`, and rotated into X/Z as double vector components. The resulting vector is added to double delta movement.
- The ordinary player route reaches that operation through `Player.travel` (`Player.java:1448` / `1380`) into `LivingEntity.travel` only when not swimming/flying through the special player route and not in a vehicle/passenger-driven route; for dry non-fall-flying movement, its ground/air friction-influenced speed becomes the `moveRelative` scale. In 1.15.2 `LivingEntity.travel` calls `moveRelative(getFrictionInfluencedSpeed(v), vec3)` directly (`:1883–1890`). In 1.16 the dry branch calls `handleRelativeFrictionAndCalculateMovement(vec3, t)` (`:2021–2024`), whose first operation is the same `moveRelative(getFrictionInfluencedSpeed(f), vec3)` (`:2060–2063`). The friction-influenced speed formula is identical: ground `getSpeed() * (0.21600002F / (friction * friction * friction))`, air `flyingSpeed` (`LivingEntity.java:2006–2008` / `2104–2106`). Player's attribute API symbol changes from `SharedMonsterAttributes.MOVEMENT_SPEED` to `Attributes.MOVEMENT_SPEED`, but both `getSpeed` methods return the attribute value narrowed to float. The helper extraction/reordering after the yaw-add operation does not alter this first acceleration.
