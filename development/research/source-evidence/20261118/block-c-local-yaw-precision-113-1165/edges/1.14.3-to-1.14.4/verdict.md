## Compared operations and result

1. **Direct entity rotation setter.** Yarn 1.14.3 `Entity.setRotation(float,float)` (lines 300–303) assigns yaw then pitch using `f % 360.0F` and `g % 360.0F`. Feather 1.14.4 `Entity.setRotation(float,float)` (303–306) and Mojmap `Entity.setRot(float,float)` (305–308) use the same float remainder and assignment order. There is no clamp or finite check in this setter; Java float remainder preserves the sign behavior for negative angles and leaves non-finite inputs non-finite.
2. **Direct living-body-yaw setter.** Yarn `LivingEntity.setYaw(float)` (2415–2417) stores the argument directly in `field_6283` (the body-yaw value, established by its body-rotation uses). Feather `LivingEntity.setBodyYaw(float)` (2424–2426) stores it directly in `bodyYaw`; Mojmap `LivingEntity.setYBodyRot(float)` (2419–2421) stores it directly in `yBodyRot`. Each is one float assignment; none wraps, clamps, casts to another width, orders additional writes, or checks finiteness. These names are mapping aliases for the same body-yaw role, not the entity’s ordinary `yaw`/`yRot` field.
3. **Rotation-load validation/order.** Yarn `Entity.readNbt` (1402–1429), Feather `Entity.readNbt` (1409–1436), and Mojmap `Entity.load` (1422–1448) read yaw/pitch into float fields, update previous rotations, set head/body yaw, reject non-finite position with `Double.isFinite` plus an exception, then admit the rotation-dependent setup only when both angles pass `Double.isFinite`. Valid angles reach `setPosition` and then the same modulo setter; invalid angles do not. Since the stored values are floats, widening for `Double.isFinite` does not alter the finite/non-finite result. The order of the head/body setter before the finite-angle gate is the same across the compared mappings.
4. **Position-and-rotation entry paths.** Yarn `Entity.setPositionAnglesAndUpdate` (1091–1114), Feather `Entity.updatePositionAndAngles` (1098–1121), and Mojmap `Entity.absMoveTo` (1116–1139) clamp pitch to `[-90,90]`, assign yaw directly, initialize previous yaw, adjust the previous/current yaw delta using double comparisons against `-180.0`/`180.0` and float `360.0F` corrections, call position setup, then apply the modulo rotation setter. The separate raw `setPositionAndAngles` / `moveTo` overload assigns yaw and pitch without modulo or finite gating in all three. No yaw-order or numeric-width difference was found in these paths.
5. **First ordinary dry ground/air contribution.** In the non-fall-flying dry branch of Yarn `LivingEntity.travel` (1833–1839), the player’s normal non-swimming, non-riding path reaches `updateVelocity(method_18802(slipperiness), input)` before the existing velocity is transformed and movement is applied. The call is Feather `LivingEntity.moveRelative`’s dry branch at 1840–1846 (`updateVelocity(m_70235197(...), input)`) and Mojmap `LivingEntity.travel` at 1836–1842 (`moveRelative(getFrictionInfluencedSpeed(...), input)`). Ground speed remains `getMovementSpeed() * (0.21600002F / (slipperiness * slipperiness * slipperiness))` in 1.14.3 versus the renamed `getSpeed()` equivalent in both 1.14.4 namespaces; air uses the float air-speed field (`field_6281` / `speedInAir` / `flyingSpeed`).

   The actual input rotation/addition is unchanged: Yarn `Entity.updateVelocity`/`movementInputToVelocity` (1055–1069), Feather `Entity.updateVelocity`/`m_51093791` (1062–1076), and Mojmap `Entity.moveRelative`/`getInputVector` (1080–1094) use a float speed and float yaw with a double vector. They compute double squared input length, return zero below `1.0E-7`, normalize only above `1.0`, scale/multiply by float speed, compute float sine then cosine of `yaw * (float)(Math.PI / 180.0)`, rotate horizontal components as `x*cos - z*sin` then `z*cos + x*sin`, preserve the input Y component, and add the resulting vector to existing velocity. The subsequent travel order (climbable transform, move, then friction/gravity updates) is likewise preserved at this point.

**Conclusion:** no independent yaw-setter, finite-check/order, or dry ground/air yaw-relative-acceleration difference is supported for this exact pair and slice. The field/method renames (`field_6283` → `bodyYaw` / `yBodyRot`, `updateVelocity` → Mojmap `moveRelative`) are mapping changes, not behavior changes.
