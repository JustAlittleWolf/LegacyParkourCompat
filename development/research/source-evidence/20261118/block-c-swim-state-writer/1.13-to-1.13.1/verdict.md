# Blind source audit — `PlayerEntity.updateSwimming` (1.13 → 1.13.1)

## Frozen scope and result

Independent blind audit, frozen before opening the author report. Scope is only the player-local `updateSwimming` state-writer gate, its block-position inputs, and a lawful same-tick movement consumer. Environmental block predicates are in scope; fluid mechanics and collision geometry are not reviewed. No wiki, product implementation, product Git history, or author report was used for this trace.

**Verdict:** source confirms a bounded 1.13 → 1.13.1 difference. In 1.13, a non-flying player that is already swimming delegates to `Entity.updateSwimming()` only when the existing suffocation/overhead-block conjunction passes. If it fails, the override does not write the swim flag and leaves the existing state untouched. In 1.13.1 every non-flying player delegates. The flying branch in both versions calls `setSwimming(false)`. The later same-tick `PlayerEntity.moveRelative` swim branch is a real movement consumer of `isSwimming()`, reachable through player → living-entity tick after the base-entity update. This supports the state-writer claim; it does not establish a trajectory outcome independent of the delegated state inputs.

## Paired source trace

Exact files below are from each root’s `net/minecraft/...` relative paths; line numbers are those in the hashed source files.

- **1.13 `PlayerEntity.java:1464–1472`:** constructs `BlockPos blockPos = new BlockPos(this)` and caches `blockPos2 = blockPos.up()` before branching. If `abilities.flying`, it writes `false`. Otherwise it delegates when `!isSwimming() || (doesNotSuffocate(blockPos) && !world.getBlockState(blockPos2).getMaterial().blocksMovement())`; if the condition is false, there is no write and no delegate.
- **1.13 `PlayerEntity.java:1474–1480`:** `doesNotSuffocate(pos)` is `shouldSuffocate(pos) && !world.getBlockState(pos.up()).isSolid()`, and `shouldSuffocate(pos)` is `!world.getBlockState(pos).isSolid()`. Java `&&` short-circuit order means the `pos.up()` solidity sample runs only if the `pos` sample is non-solid. When the outer `isSwimming()` is already true, this pair must pass before the separately evaluated cached `blockPos2` sample asks `getMaterial().blocksMovement()`.
- **1.13.1 `PlayerEntity.java:1471–1477`:** preserves the flying `setSwimming(false)` branch; otherwise it directly calls `super.updateSwimming()` with no existing-swimming or block-state guard. Helper methods remain present but are no longer consulted by this override.
- **Player state predicate:** `PlayerEntity.java:1814–1816` in 1.13 and `1819–1821` in 1.13.1 define `isSwimming()` as `!abilities.flying && !isSpectator() && super.isSwimming()`. Therefore the stated already-swimming case also implies non-spectator; a state bit alone is insufficient.
- **Position conversion:** `BlockPos.java:29–34` defines `BlockPos(Entity)` by forwarding current `entity.x/y/z` doubles to `BlockPos(double,double,double)`. `Vec3i.java:19–21` floors each double with `MathHelper.floor` into integer coordinates; there is no Java narrowing cast. `BlockPos.java:61–66` defines `up()` as `up(1)`, offset one block in `Direction.UP`. Thus the old guard samples the block at the player’s current floored position and the block one integer Y above it. In its already-swimming path, it checks the current-position state’s `isSolid`, then conditionally the upper state’s `isSolid`, then (if those pass) the upper state’s material `blocksMovement`; the upper position is queried twice through two calls.
- **Delegated target:** `Entity.java:952–958` in 1.13 and `953–959` in 1.13.1 contain the inherited `updateSwimming()` implementation. `LivingEntity` does not override this method in either source tree. The body is unchanged across the pair; this audit treats its environmental mechanics as the excluded fluid-mechanics slice.

## Tick-order and movement consumer

The runtime call order is grounded in source, not inferred from method names alone. `PlayerEntity` extends `LivingEntity` in both versions (`PlayerEntity.java:97` / `98`). In the normal local-client path, `LocalClientPlayerEntity` extends `ClientPlayerEntity`, which extends `PlayerEntity`; its `tick()` calls `super.tick()` (`LocalClientPlayerEntity.java:87 and 179–183` (1.13), `:89 and 181–184` (1.13.1)). `PlayerEntity.tick()` calls `super.tick()` at 1.13 `PlayerEntity.java:207` and 1.13.1 `:208`. `LivingEntity.tick()` calls `super.tick()` first (1.13 `LivingEntity.java:1670–1673`; 1.13.1 `:1689–1692`). The chain reaches `Entity.tick()` → `Entity.baseTick()`; `baseTick()` invokes its environmental update helper (1.13 `Entity.java:393–395`; 1.13.1 same lines), whose ordered calls end in virtual `this.updateSwimming()` (1.13 `Entity.java:946–950`; 1.13.1 `:947–951`). After that superclass call returns, the same `LivingEntity.tick()` body reaches its travel section and invokes `this.moveRelative(...)` (1.13 `LivingEntity.java:1901–1908`; 1.13.1 `:1920–1927`). Dynamic dispatch reaches `PlayerEntity.moveRelative()`.

That player override tests `isSwimming() && !isRiding()` (1.13 `PlayerEntity.java:1435–1444`; 1.13.1 `:1442–1451`) and applies its swimming vertical-velocity response before delegating to ordinary relative movement. This is a real same-tick movement consumer under the non-riding precondition. It establishes that the updated/preserved swimming state can affect a movement operation later in the same player tick. Its separate block/fluid query and fluid response are not analyzed here.

## Bounded disposition

The source confirms the change in the `PlayerEntity.updateSwimming` delegate gate and a same-tick consumer. Exact applicability is the 1.13-to-1.13.1 interval; this endpoint audit does not prove the exact patch introduction beyond that interval or claim a complete movement-pair freeze. The author report remained unopened at this freeze.
