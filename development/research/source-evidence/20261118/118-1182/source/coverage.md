## Ordered inventory and dispositions

### Body immersion and fluid pushing

- `Entity.baseTick` calls, in order, `updateInWaterStateAndDoFluidPushing`, `updateFluidOnEyes`, and `updateSwimming` on all three releases (1.18/1.18.1 lines 401-425; 1.18.2 lines 403-426). The fluid map is cleared first; water currents are updated, then lava current/push is accumulated with dimension `ultraWarm()` selecting `0.007`, otherwise `0.0023333333333333335`, then `isInWater() || lavaFound` is returned (Entity 1037-1052 / 1047-1063). No adjacent-edge behavioral change found.
- `Entity.updateFluidHeightAndDoFluidPushing` (1.18/1.18.1 lines 2756-2821; 1.18.2 lines 2769-2834) preflights `touchingUnloadedChunk()` and returns false before writes when any chunk in bounding box inflated by 1 is absent. Otherwise it deflates the box by `0.001`, floors minima/ceils maxima, visits x/y/z in nested ascending loops, sums max surface immersion, and samples flow; scales flow by depth under `0.4`, averages by count, normalizes non-Player flow, applies the small-motion floor (`0.0045000000000000005`) and writes delta movement. The tag-specific height is written after traversal. All these gates, operation order, constants, and writes are textually unchanged; only tag type changes from `Tag<Fluid>` to `TagKey<Fluid>` in 1.18.2. The hash-checked `Level.getFluidState` retains the outside-build-height fallback before chunk lookup; `LevelChunk.getFluidState` delegates section data after height/section lookup. No changed height/chunk boundary found.
- `Entity.updateInWaterStateAndDoWaterCurrentPushing` (1.18/1.18.1 lines 1044-1050; 1.18.2 lines 1054-1060), `isInWater`/`isInLava` (Entity around 1005-1018 and 1144-1148), and their fluid-height map reads retain the same logic and first-tick lava gate. No adjacent-edge behavioral change found for vanilla water/lava tags.

### Eye-fluid state

- `Entity.updateFluidOnEyes` and `isEyeInFluid` are unchanged between 1.18 and 1.18.1 (Entity 1061-1080 and 1140-1142). Current water membership is captured in `wasEyeInWater` before resampling; a not-underwater boat suppresses sampling at its covered eye height; otherwise the eye sample is `getEyeY() - 0.11111111F`, and positive fluid surface height sets the eye tag. No difference found on this edge.
- Between 1.18.1 and 1.18.2, eye state storage/query changes from one selected static `Tag<Fluid>` to a set of every tag on the fluid state: the older method loops `FluidTags.getStaticTags()`, selects first match and returns; the newer clears a `Set<TagKey<Fluid>>`, then adds `FluidState.getTags()` when the surface is above the sample. `isEyeInFluid` changes from identity equality to set membership; `wasEyeInWater` remains the previous sample taken before clear/recompute. This is a conditional difference for custom/dynamic fluid-tag data, especially a state in multiple relevant tags. With vanilla water and lava membership, no changed player movement result was found. Draft at `eye-fluid-tag-membership.md`.

### Ordinary water/lava travel

- `LivingEntity.travel` ordinary water/lava branches (1.18/1.18.1 lines 2005-2080; 1.18.2 lines 2009-2084) retain the local-control/effective-AI gate, water/lava and `isAffectedByFluids` checks, depth-strider and dolphin-grace adjustments, relative acceleration, movement, horizontal climbable adjustment, drag (`water y=0.8`; lava half-speed), falling adjustment, lava quarter-gravity, and collision exit impulse. No numeric/order difference found.
- One signature/input change occurs in 1.18.2: water/lava travel now calls `canStandOnFluid(FluidState)` rather than passing `FluidState.getType()` to `canStandOnFluid(Fluid)`. `LivingEntity`'s implementation returns false in all releases. Search of in-scope entity descendants found only Strider overriding this predicate, an excluded non-player path. Player subclasses do not override it. Thus no player movement effect is established; record as predicate API/boundary change, not a player finding. Dynamic/custom fluid content could matter only with a player-specific override, which the supplied exact source lacks.
