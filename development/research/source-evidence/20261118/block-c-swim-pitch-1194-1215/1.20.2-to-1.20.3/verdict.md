### Trace and comparison

1. `Player.travel` executes the pre-super adjustment only when `isSwimming() && !isPassenger()`. Both releases use the same ordered operations: read `lookY = this.getLookAngle().y`; choose `factor = lookY < -0.2 ? 0.085 : 0.06`; if `lookY <= 0.0 || jumping || above-sample fluid state is nonempty`, read current delta movement and write `old.add(0.0, (lookY - old.y) * factor, 0.0)` via `setDeltaMovement`. References: 1.20.2 `Player.java:1450-1462`; 1.20.3 `Player.java:1451-1461`. The expression, comparisons, constants, state read, vector addition and write are identical. The only line-range difference is the removed leading position snapshot used by movement statistics below.
2. The above-fluid query in both versions samples the current pre-super coordinates at `BlockPos.containing(getX(), getY() + 1.0 - 0.1, getZ())`, i.e. current X/Z and Y+0.9, then calls `getFluidState().isEmpty()`. `BlockPos.containing(double,double,double)` floors each coordinate through `Mth.floor`; its implementation is `(int)value`, then subtract one when `value < castValue` (including negative nonintegral coordinates). References: `BlockPos.java:81-83`; `Mth.java:59-62` in 1.20.2 and `Mth.java:64-67` in 1.20.3. The sample is taken synchronously in `Player.travel`, before `super.travel` performs movement; it is not interpolated and there is no tick-count/time gate.
3. `getLookAngle()` uses `calculateViewVector(getXRot(), getYRot())` in both versions (`Entity.java:2004-2006` / `2005-2007`), not the partial-tick `getViewVector` interpolation. `Entity.xRot` is a private `float`; `getXRot()` returns that raw field (`Entity.java:162, 3299-3301` / `163, 3305-3307`). `calculateViewVector` multiplies raw pitch by `(float)(Math.PI / 180.0)`, forms yaw as its negative degree-to-radian product, then computes `cos(yaw)`, `sin(yaw)`, `cos(pitch)`, `sin(pitch)` and returns `(sinYaw*cosPitch, -sinPitch, cosYaw*cosPitch)` (`Entity.java:1458-1465` / `1459-1466`). Thus the adjustment’s look-Y is negative sine of the current pitch after float conversion and LUT lookup.
4. Both Mth versions initialize `SIN` as a `float[65536]` through `Util.make`, filling indices 0–65535 with `(float)Math.sin(index * Math.PI * 2.0 / 65536.0)` (`Mth.java:25-29` / `27-35`). Both `sin(float)` return `SIN[(int)(radians * 10430.378F) & 65535]` (`Mth.java:42-44` / `47-49`); the cast truncates before the 16-bit mask. Both `cos(float)` use the same LUT with `+16384.0F`. Initialization width, fill expression, LUT index conversion, scale, mask and cosine offset are unchanged.
5. After this adjustment, Player’s flying/nonpassenger branch snapshots the then-current Y velocity, calls `super.travel`, then writes Y as the snapshot times `0.6`; the other branch directly calls `super.travel`. This ordering is identical (`Player.java:1465-1474` / `1463-1472`). For an active locally controlled player in water, inherited `LivingEntity.travel` reaches the same fluid gate (`isInWater() && isAffectedByFluids() && !canStandOnFluid(fluidState)`), calls `moveRelative(0.02F, input)`, and then `move(MoverType.SELF, getDeltaMovement())` before applying the same drag/falling adjustments (`LivingEntity.java:2038-2070` / `2035-2067`). This confirms the adjusted velocity is consumed by the same actual movement operation in both releases.
6. `Player.travel` additionally snapshots X/Y/Z at its beginning and calls `checkMovementStatistics` after inherited travel in 1.20.2 (`Player.java:1451-1453,1476`); 1.20.3 removes those statistics-only reads/call. That is outside the owned vertical movement operation and does not change the adjustment or inherited move.

**Blind source conclusion:** no 1.20.2 → 1.20.3 change is present in the owned Player swim-pitch direct Y-adjustment operation, its raw pitch/look-Y math, its above-fluid predicate/sample/flooring, or the inherited water move that consumes it. This conclusion and the cited byte identities were frozen before candidate-report review.
