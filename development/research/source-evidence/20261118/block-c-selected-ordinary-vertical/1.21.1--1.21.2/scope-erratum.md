# Scope erratum: subthreshold vertical witness is unreachable in ordinary local travel

## Verdict

The prior `dy = 0.0001` witness is valid only as a direct input to `Entity.move`; it is not reachable from ordinary local dry passive travel because the local-player tick calls `LivingEntity.aiStep` first. The assigned slice therefore has **no player Y-position difference** from the new `Entity.move` threshold under the stated assumptions. Keep the source-level `Entity.move` predicate observation, but do not accept its finding as an ordinary-air player movement difference for this slice.

## Exact path and evidence

- In both releases `LocalPlayer.aiStep` calls `super.aiStep()` before returning: 1.21.1 `decompiled_minecraft/1.21.1/mojmap/net/minecraft/client/player/LocalPlayer.java:804`, SHA-256 `c555e68ac3c63ab9b4f9a9e31933e263b96350a2bc599d11a0de5928bc24b583`; 1.21.2 `.../1.21.2/mojmap/net/minecraft/client/player/LocalPlayer.java:795`, SHA-256 `fbd40f1f47adfa66dda9b15188e5dce82af3e8e8d7c3dd0543e602a354ad3fe0`.
- The inherited `LivingEntity.aiStep` snapshots delta movement, replaces its Y component with `0.0` whenever `abs(vY) < 0.003`, writes the resulting vector, and only later reaches travel: 1.21.1 `LivingEntity.java:2608-2624,2665-2679`, SHA-256 `324a3eee8496caab57cfaf5101ef576f1ae3c60c40e3857e96f35f3af9a3a0d8`; 1.21.2 `LivingEntity.java:2697-2713,2755-2772`, SHA-256 `087390495f4fdfd14b9e12230e7aea4fdc50913bb4d1d91119e72892881cfc52`.
- In ordinary air travel the movement helper calls `Entity.move` with the current delta movement before gravity and drag are applied: 1.21.1 `LivingEntity.java:2252-2265,2192-2211`; 1.21.2 `LivingEntity.java:2351-2364,2191-2213`. Jump writes happen later in `aiStep` after the deadzone (`LivingEntity.java:2637-2662` vs `2727-2752`); subsequent travel state again passes through the deadzone on the next local tick.
- Thus, with zero horizontal movement and no collision, at the `Entity.move` call the vertical request is either zero or has `abs(vY) >= 0.003`. A zero request leaves position unchanged in both releases (1.21.2 may call `setPos` with the same coordinates). A nonzero request has squared length at least `0.003^2 = 9.0E-6`, greater than `1.0E-7`, so both releases apply the same Y displacement. The input `0.0001` is zeroed before this call.
- 1.21.1 `Entity.move` applies resolved position only when resolved squared length exceeds `1.0E-7` (`Entity.java:618-630`, SHA-256 `b81905c7879e2cc5c5063a41d865c4164ad919f156306705be791d1017b99850`). 1.21.2 also applies when requested squared length minus resolved squared length is below `1.0E-7` (`Entity.java:640-652`, SHA-256 `a93719c302a0381a972af75ea360465e2e3551708dd07c34d4d40b7e5173c2b9`). This second condition cannot produce a subthreshold vertical resolved displacement from a request of at least `0.003`: if resolved squared length is at most `1.0E-7`, the difference is at least `9.0E-6 - 1.0E-7`, well above `1.0E-7`. If resolved squared length is above `1.0E-7`, the first condition already applies in both releases.

## Boundary disposition

`Entity.move` obtains the resolved displacement from collision processing. Collision/provider changes and externally produced direct movement inputs are outside this assigned ordinary passive-air slice. Even if such a boundary creates a raw subthreshold resolved vector, it cannot satisfy the new near-equal-squared-length condition when the ordinary request had passed the `0.003` deadzone. The original draft and finding are preserved unchanged; this erratum narrows their scope verdict without altering either frozen file.
