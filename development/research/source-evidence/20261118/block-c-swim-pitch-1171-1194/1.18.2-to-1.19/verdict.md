# Independent source audit verdict: 1.18.2 → 1.19 swim-pitch vertical writer

**Verdict:** The assigned direct `Player.travel` swim-pitch Y writer has no source difference between Minecraft 1.18.2 and 1.19. The result applies only to this operation and its pitch calculation/call path; it does not establish full-pair coverage or runtime parity.

## Independent trace

- **Player override and gates:** `Player.travel(Vec3)` (1.18.2 lines 1422–1452; 1.19 lines 1459–1489) has identical extracted method bytes (SHA-256 `8750ff867a76a9577dbbfb38e3f5d8becf9f67285896b6f9ccfad693c89a6833` on both releases). It snapshots position, then gates the pre-super adjustment on `isSwimming() && !isPassenger()`. It reads `getLookAngle().y` once into a `double`, selects double `0.085` only for `< -0.2` and otherwise `0.06`, then short-circuits `lookY <= 0.0 || jumping || !headFluidEmpty` left to right. The head sample is at `new BlockPos(getX(), getY() + 1.0 - 0.1, getZ())`; it is reached only when look-Y is positive and jumping is false. If the OR passes, the Y write is `oldDelta.add(0.0, (lookY - oldDelta.y) * coefficient, 0.0)` followed by `setDeltaMovement`; the arithmetic is double precision after the look vector component is widened into `Vec3`.
- **Authoritative pitch and vector:** `Entity.getLookAngle()` (1.18.2 line 1816; 1.19 line 1841) calls `calculateViewVector(getXRot(), getYRot())`, with no partial-tick interpolation. Neither `Player` nor `LivingEntity` overrides the relevant pitch getter or look-angle method. `Entity.getXRot()` returns `xRot`; `setXRot(float)` rejects non-finite values and otherwise writes that field (1.18.2 lines 3027–3037; 1.19 lines 3055–3065). `calculateViewVector` (1.18.2 lines 1314–1322; 1.19 lines 1339–1347) is byte-identical (method SHA-256 `727b811ceab27ce945bcfac470f79dece2eacb92ff001026f812e551bc11bd1d` both). It first multiplies each float angle by `(float)(Math.PI / 180.0)`, computes float cosine/sine values, then returns `new Vec3(sinYaw * cosPitch, -sinPitch, cosYaw * cosPitch)`. Thus swim look-Y is the float result `-sinPitch`, widened to the vector's double Y component.
- **Mth LUT/math and casts:** Both `Mth` classes have the same table initializer (1.18.2 lines 26–31; 1.19 lines 26–31): 65,536 float slots filled by `(float)Math.sin(index * Math.PI * 2.0 / 65536.0)` using double intermediates. `sin(float)` (lines 43–45 on both) returns `SIN[(int)(angle * 10430.378F) & 65535]`; `cos(float)` (lines 47–49) returns `SIN[(int)(angle * 10430.378F + 16384.0F) & 65535]`. The float multiply/add precedes Java's float-to-int truncation; the integer mask wraps the LUT index. Extracted `sin` and `cos` method hashes are identical across versions (`58ef91a4006204496dfd5fb03bd49afbb1cf7ea24f3f65110720d5fe87191c76` and `371c48a67a6f712d8550fe9242f18451216e84dfc4fe8982e467f90bfdaa8b09`). The table initializer, LUT size, constants, casts, order, and look-vector component are unchanged. 1.19's unrelated replacement of `Random` with `RandomSource` does not alter these paths.
- **Inherited path and the direct writer's consumer:** In the ordinary nonflying player path, `Player.travel` calls `super.travel($$0)`, selecting `LivingEntity.travel` (1.18.2 line 2009 onward; 1.19 line 2042 onward). The extracted full methods are identical (SHA-256 `b357fd9f66141f9e2bf50e30ec9a91f043282d6a31fccc33fcba96730dd4a745` both). Movement first requires `isEffectiveAi() || isControlledByLocalInstance()`; the water path further requires `isInWater() && isAffectedByFluids() && !canStandOnFluid(blockFluidState)`. It calls `moveRelative`, then `move(MoverType.SELF, getDeltaMovement())`, applies water damping, and applies `getFluidFallingAdjustedMovement` before later checks. The swim-pitch velocity is therefore input to this inherited water movement. The separate `abilities.flying && !isPassenger()` branch also calls `super`, then resets Y from the pre-super velocity; it is not the ordinary path. `Entity.move` is reached by the inherited call. Its enclosing body is not byte-identical across endpoints (the 1.19 body uses `getOnPosLegacy()` where 1.18.2 uses `getOnPos()` in the later support-state work); that downstream method is not the direct pitch-Y writer audited here, so this verdict does not assert whole movement parity.

The central comparison for the assigned claim is the same direct writer, same authoritative pitch source, same Mth LUT procedure, same gates and operation order. No independent source delta is present in this operation for 1.18.2 → 1.19.
