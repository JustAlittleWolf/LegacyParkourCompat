## Caller and transition

Across all four exact versions, `LocalClientPlayerEntity.tick()` calls `super.tick()` only while `world.isChunkLoaded(new BlockPos(x, 0.0, z))` is true (`LocalClientPlayerEntity.java`: 1.10.2 lines 152-155; 1.11/1.11.1/1.11.2 lines 159-162). `PlayerEntity.tick()` calls `super.tick()` and then reaches `updatePlayerPose()` at its tail (1.10.2 line 250; newer versions line 249). Consequently the ordinary local player's movement in the inherited tick precedes this pose clearance check.

`LocalClientPlayerEntity.isSneaking()` reads the current `input.sneaking` value and excludes sleeping players (1.10.2 lines 596-599; 1.11+ lines 608-611). In every compared `PlayerEntity.updatePlayerPose()` the active target dimensions are: fall-flying `0.6F × 0.6F`, sleeping `0.2F × 0.2F`, sneaking `0.6F × 1.65F`, otherwise `0.6F × 1.8F`. When either target differs from `width` or `height`, it keeps the current box minimums, constructs a box ending at `minX + targetWidth`, `minY + targetHeight`, `minZ + targetWidth`, and calls `world.getCollisions(box)`. It invokes `setSize(targetWidth, targetHeight)` only when that boolean is false (`PlayerEntity.java`: 1.10.2 lines 296-320; 1.11/1.11.1/1.11.2 lines 295-319). These pose method bodies are identical in the four checked outputs.

The collision predicate is the exact overload used by the accepted finding: `World.getCollisions(Box)` returns `boolean` in all four versions (1.10.2 line 1022, 1.11 line 1044, 1.11.1 and 1.11.2 line 1058). In 1.10.2/1.11 it performs its own list-backed check; in 1.11.1/1.11.2 it dispatches to the shared helper with `entity=null`, the box, `true`, and a new box list. Thus this is a block-clearance check through the accepted boolean path, not the entity-taking list overload. Its world-border setting and dynamic moving-block path are the boolean-path ones already adjudicated by the immutable finding.

`Entity.setSize()` preserves the box bottom for this transition. Player width remains `0.6F`, so the 1.11+ narrower-width branch is not taken and the server-only width-growth move is also not taken. A crouch-to-stand request changes only height `1.65F → 1.8F`; if admitted, the replacement box retains the candidate's `minX/minY/minZ` (`Entity.java`: 1.10.2 lines 264-276; 1.11 lines 267-288; 1.11.1/1.11.2 lines 271-292). On the client, there is no secondary size-change collision correction after the predicate.

## Reachability against the accepted moving-fence snapshot

Use the accepted finding's loaded, non-border witness at moving cell `(x,y,z)`, retaining its oak fence, WEST extension, progress `0.5F`, and the accepted center-post collision shape. Start a local player crouched with width `0.6F`, height `1.65F`, bottom `y+1.3`, center x `x+1.55`, center z `z+0.5`; have the current local input transition to non-sneaking while the ordinary tick moves x by `-0.2`. Before movement, the player box minimum x is `x+1.25`; after the move it is `x+1.05`. The ordinary swept movement query therefore has the accepted witness's lower-x perimeter and lower padded-Y query bounds. In 1.11 the omitted candidate cell permits that movement to finish at the overlapping location. The pose update runs after the inherited movement, builds its standing clearance box from the new minimums, and queries `World.getCollisions(Box)` with `[x+1.05,x+1.65] × [y+1.3,y+3.1] × [z+0.2,z+0.8]`. This unexpanded pose box itself intersects the accepted post; it retains both the query's lower-x perimeter and lower padded-Y location. Because 1.11 omits that cell on the boolean path, the preflight returns false and the client changes height to `1.8F`.

This confirms source-reachable use of the changed boolean predicate: there is no abstract-box-only gap. It is conditional on a crouched player reaching that position through the old scan omission, a non-sneaking input at pose-update time, and the local-player chunk gate being open. Choose the cell away from a chunk edge so the same loaded chunk satisfies the local tick gate and the accepted y=64 block-query loaded check. An ordinary player tick is outside the piston-initiated nested movement call; use the accepted finding's ordinary-query thread-local state (`false` in 1.11 and `null` in 1.11.1/1.11.2).

In 1.11.1/1.11.2 the normal swept movement query appends this same candidate; under the same requested `-0.2` movement it clips before the overlapping endpoint. At the non-overlapping contact endpoint the standing-size preflight can admit growth. If another source path has already placed the player at the overlapping witness, the pose preflight reaches the same boolean query and rejects growth in these versions. Therefore the evidence establishes the ordinary pose caller and an old-version reachable admission decision, while the newer version's ordinary movement collision already removes this exact overlapping pose-query state before the post-movement pose update. No independent posture trajectory or runtime result is claimed.

## Bounded conclusion

The local-player pose transition is a concrete caller of the boolean collision overload whose scan changed in the accepted finding. 1.11's omission makes an overlapping crouch-to-stand preflight return clear after the same tick's omitted moving-fence sweep; 1.11.1/1.11.2 retain the predicate caller but detect the fence on the sweep first, so this specific ordinary-tick overlap is not reached. The 1.10.2/1.11 endpoints also call the boolean overload, but its moving-block provider is separately described in the accepted finding and is not inferred from 1.11's provider. No fresh geometry or scan claim is made.
