# 1.21.1–1.21.2 active-glide fluid fall-distance cap

## Bounded comparison

This comparison covers an ordinary locally controlled client player whose shared fall-flying flag is true at tick entry, whose fluid response is enabled, and who reaches a qualifying water or lava route at `travel`. The glide flag must remain true through pre-travel setup. Entity base ticking runs before LivingEntity travel setup in both releases. Water and lava need separate treatment because their existing fluid-state updater changes `fallDistance` differently.

For an observable lava cap write that survives to fluid movement, the post-base-tick `getDeltaMovement().y()` must be greater than `-0.5`, `fallDistance` must be greater than `1.0F` after lava halves it, and neither Slow Falling nor Levitation may be active (LivingEntity tick resets fall distance for either effect after `updateFallFlying`). This is an explicit state witness, not an inferred trajectory; source alone does not prove a particular incoming trajectory supplies these numeric values or their precise timing relative to fluid entry. The water+climbable sibling witness is structurally compatible, but water resets fall distance before this check and therefore cannot leave the cap residual described below.

## Difference and reachability

- **1.21.1 (Mojmap):** `Entity.baseTick` calls `updateInWaterStateAndDoFluidPushing()` before the living tick reaches travel setup (`Entity.java:420–441`; `LivingEntity.java:2319+`, then `2665–2679`). `LivingEntity.updateFallFlying()` is called unconditionally but does not call `checkSlowFallDistance` (`2716–2740`). `travel(Vec3)` takes the ordinary water branch when `isInWater()`, fluid response is enabled and `!canStandOnFluid(fluidState)` hold (`2099–2100`), or the analogous lava branch (`2131`). Both fluid branches move before fluid adjustment (`2118–2127`, `2133–2145`) and neither calls the cap; the later fall-flying branch that calls it (`2151–2153`) is skipped.
- **1.21.2 (Mojmap):** Entity base ticking also runs first. LivingEntity tick calls `updateFallFlying()` only if `isFallFlying()` is true (`LivingEntity.java:2755–2771`); the call precedes the Slow Falling / Levitation reset (`2764–2766`) and travel. `updateFallFlying()` begins with `checkSlowFallDistance()` (`2814–2816`), then its eligibility check and flag clear are server-only (`2816–2819`), so it does not clear the client’s active flag. `travel(Vec3)` gives qualifying ordinary fluid movement precedence over fall-flying movement (`2178–2187`). `travelInFluid` contains no cap call (`2216–2266`), so the changed pre-travel call is the only cap opportunity before the actual water/lava move.
- **Water residual gate:** In both versions, `Entity.baseTick` recomputes water contact before LivingEntity tick. `updateInWaterStateAndDoWaterCurrentPushing()` calls the fluid-height scan and, on water contact, resets `fallDistance` before setting `wasTouchingWater` (`Entity.java:1242–1263`). The scan examines the entity’s deflated bounding box (`Entity.java:3091–3118`). Thus the ordinary water path can be selected with the client’s active glide flag, but its pre-travel fall distance has already been reset to zero; no >1 water cap residual is supported by this tick order.
- **Lava residual gate:** In both versions, `Entity.baseTick` halves `fallDistance` when `isInLava()` (`Entity.java:465–468`) and does not reset it. On 1.21.2, after that halving, the exact `y > -0.5` and `fallDistance > 1.0F` witnesses can still cause a write to `1.0F` before the lava fluid move. 1.21.1 takes the lava travel branch without invoking the cap. This is a conditional source-level delta; no arbitrary trajectory is asserted.
- **Cap operation (both versions):** `Entity.checkSlowFallDistance()` reads the current vertical delta via `getDeltaMovement().y()` and `fallDistance`; if `y > -0.5` and `fallDistance > 1.0F`, it writes `fallDistance = 1.0F` (`1.21.1 Entity.java:2386–2390`; `1.21.2 Entity.java:2484–2488`). The primitive is the same; only call site, gate and ordering differ.
- **Wet+climbable sibling witness:** `isInWater()` returns the water-contact flag derived by scanning the entity’s deflated bounding box, while `onClimbable()` reads current `blockPosition()` / `getInBlockState()` and tests `BlockTags.CLIMBABLE` (`1.21.1 Entity.java:1200, 1242–1263, 3091–3118`; `LivingEntity.java:1517–1533`). Water overlap beside a foot-cell ladder or vine can therefore satisfy the water route and climbable predicate together. In old water travel, the horizontal-collision climbable response occurs only after the first move (`LivingEntity.java:2118–2122`); it does not alter the cap call ordering above. This is a valid wet sibling witness, not a positive cap-residual witness.
- **Next direct state operations:** In 1.21.2 lava travel’s first `move` reaches `Entity.checkFallDamage`: a grounded move passes positive `fallDistance` to `Block.fallOn` then resets it; a descending non-grounded move increments it by downward displacement (`Entity.java:1216–1231`). A qualifying lava cap write can be the value consumed by a landing during that move; otherwise the move may add downward displacement. No landing or later consequence is predicted. In 1.21.1’s fluid path there was no cap before the same move. Other damage outcomes are out of scope.
