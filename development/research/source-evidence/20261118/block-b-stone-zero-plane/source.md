## Reachable local-player witness

Use a living, awake, non-spectator, non-riding `LocalClientPlayerEntity`, in an otherwise empty dry world, not climbing, sneaking, or in a cobweb. The player is airborne and has `onGround=false`, `noClip=false`; the player and moving-block cells are loaded. Let the local camera face yaw `0` and hold the sideways/right input for the second of two consecutive player ticks. Let the player's feet start at `y=0.2`, with zero X/Z velocity, and have the prior dry travel start with `velocityY=0`; the first tick moves zero and applies gravity after movement, leaving a small negative Y velocity. This setup leaves the player clear of the sheet until the next tick.

The exact size comes from the ordinary awake player's `0.6F × 1.8F` dimensions: `Entity` initializes those fields, `setPosition` uses `float f = width / 2.0F` and `float g = height`, and `PlayerEntity.resetPos` restores the same size. For an exactly touching X face, set player center X to `-(double)(0.6F / 2.0F)`; then the binary32 half-width is `0.30000001192092896`, and the current player box has `maxX == 0.0` exactly. Its X bounds are approximately `[-0.6000000238418579, 0.0]`; with center Z `0.5`, Z bounds are `[0.19999998807907104,0.800000011920929]`; Y bounds begin at `0.2` and have float-height `1.8F`.

The call path is present in source: `LocalClientPlayerEntity.tick` admits a loaded local-player tick and calls `super.tick`; `PlayerEntity.tick` sets `noClip` from spectator state and reaches `LivingEntity.tick`; `LivingEntity.tick` invokes virtual `mobTick`. `LocalClientPlayerEntity.isLocallyControlled()` is true. Its `mobTick` reaches `PlayerEntity.mobTick` and `LivingEntity.mobTick`; the latter runs local `serverTickAi` and then the travel call. For the local camera, `serverTickAi` copies `input.movementSideways` to `sidewaysSpeed`. `LivingEntity.mobTick` scales it by `0.98F`, and `PlayerEntity.mobTick` has established positive airborne `speedInAir` on the prior tick. With sideways input `+1`, yaw `0`, and previous X velocity zero, `Entity.updateVelocity` adds a positive X component and zero Z component. The dry, non-lava, non-water branch in `LivingEntity.moveRelative` calls `Entity.move(velocityX, velocityY, velocityZ)`. The request therefore has `dx > 0`, `dz = 0`, and the previously accumulated small `dy < 0`; this does not depend on guessing a user-authored displacement vector. Keep the prior falling speed small enough that after Y movement the player's bottom remains between 0 and 1 (the ordinary first gravity step is about `-0.0784`, so it does).

On that second tick, `Entity.move` calls `World.getCollisions(this, getShape().expanded(dx,dy,dz))`. Its swept X interval is `[about -0.600000024, positive]`; `World.getCollisions` uses `floor(minX)` and `floor(maxX + 1)` with an exclusive upper loop bound, so it scans X cells `-1` and `0`. The swept Y/Z ranges likewise include cell `(0,0,0)`. Assume cell zero contains the moving-block block/entity pair, its chunk is loaded, the world border is clear, and no other shapes collide.

The existing timing trace closes the moving-block phase: client `world.tickEntities` processes regular entities before ticking block entities. After the first tick, the moved Stone block entity advances from `(progress,lastProgress)=(0,0)` to `(.5,0)`; on the second tick, the player's entity-phase travel runs before the next block-entity tick. `MovingBlock.getCollisionShape` samples `getProgress(0.0F)`, which is `lastProgress=0`; extension changes this to `f=1`. For a full-cube Stone box at `(0,0,0)` facing EAST, the historical helper subtracts `1` from `maxX`, producing `[0,0] × [0,1] × [0,1]`.

`Block.addCollisions` appends this zero-width box when the positive-volume swept query strictly intersects it: the query has `minX < 0 < maxX`, and its Y/Z intervals overlap `[0,1]`. Degenerate width does not appear as an emptiness guard. During `Entity.move`, the Y clip checks the candidate's X overlap first; the player's `maxX == 0 == candidate.minX` makes the strict overlap condition fail, so `dy` remains unchanged. Since the player was airborne and `h == dy`, the step-up condition is false. The following X clip sees Y/Z overlap and positive `dx`; its `player.maxX <= candidate.minX` condition is true at equality, yielding gap `candidate.minX - player.maxX == 0`. The exact source consequence for this ordinary local dry-travel path is therefore clipped `dx=0`.

This gives an end-to-end reachable player-call witness under stated world/input setup, including actual caller admission, velocity-derived request, float-sized box construction, sweep/list path, and Y-then-X clip order. It remains a bounded single-state source witness, not runtime parity evidence.

## Native 26.2 representability

`AABB` stores the zero-width endpoints without expansion, and its strict `intersects` predicate returns true when the degenerate coordinate lies inside a positive-volume query. So AABB can preserve/query the geometry itself. It is not losslessly representable as a collision `VoxelShape`: `Shapes.box` accepts equal endpoints, but delegates to `Shapes.create`, which returns the empty shape when any extent is below `1.0E-7`; `Shapes.create(AABB)` follows that same path. `VoxelShape.collide` returns the requested distance unchanged for an empty shape. Preserving this historical surface's clip requires a separate collision-constraint seam (or a direct AABB-constraint clipping path) alongside native VoxelShape movement collision.
