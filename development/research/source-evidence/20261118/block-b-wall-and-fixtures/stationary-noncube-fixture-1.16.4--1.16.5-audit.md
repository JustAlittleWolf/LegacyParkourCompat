# Independent blind source audit: 1.16.4 → 1.16.5 stationary noncube collision

**Result: COMPLETED.** For the eight assigned block families, I found no 1.16.4→1.16.5 change in registration, inherited collision gates, state selection, returned collision geometry, or the ordinary entity collision provider path. This is a bounded source disposition, not a full-pair coverage freeze.

## Provider and inherited gates

In both releases, `CollisionGetter.getBlockCollisions` constructs a `CollisionSpliterator` (`CollisionGetter.java:58-60`). Its entity constructor chooses `CollisionContext.empty()` only for a null entity; ordinary player collision uses `CollisionContext.of(entity)` (`CollisionSpliterator.java:35-43`). For each selected block, `collisionCheck` applies the state predicate, large-shape/piston checks, then calls `blockState.getCollisionShape(collisionGetter, pos, context)` (`CollisionSpliterator.java:63-75`). Entity movement reaches this provider through `Entity.collideBoundingBoxHeuristically` (`Entity.java:717-725`).

`BlockBehaviour` supplies the default collision method: when `hasCollision` is true it asks the state for its `getShape`; otherwise it returns empty (`BlockBehaviour.java:271-278`). State wrappers dispatch both shape and collision calls to the block (`BlockBehaviour.java:516-530`). The audited ordinary fixed-shape classes do not inspect the collision context. Grindstone and lectern explicitly override collision shape; their provider also ignores context. No target registration has `.noCollission()`; family registrations and all property/default-state definitions are unchanged in `Blocks.java` and class bodies.
