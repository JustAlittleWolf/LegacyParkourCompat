## Compared behavior

**1.17 block and entity state.** `world/level/block/Blocks.java:3496-3498` registers `POWDER_SNOW` as a `PowderSnowBlock`. `PowderSnowBlock.java:32-41` extends `Block` and its constructor only passes properties to `super`; the class declares no block-state properties. The registration supplies powder-snow material, strength, sound, and `dynamicShape`. `entityInside` (`PowderSnowBlock.java:54-84`) calls `makeStuckInBlock` under its entity/feet-state gate, then unconditionally sets `isInPowderSnow`; the local-client particle work is separately gated by `level.isClientSide`. `Entity.java:413-415` saves and clears the powder-snow flag during base ticking. In 1.16.5 there is no `PowderSnowBlock.java` or `POWDER_SNOW` registration, and a case-insensitive search of the entire canonical Mojmap source tree found no `powder_snow`, `PowderSnow`, `isInPowderSnow`, `wasInPowderSnow`, `getTicksFrozen`, or `TicksFrozen` identifiers.

**Post-travel modifier in 1.17.** `LivingEntity.aiStep` performs `travel(...)` at `LivingEntity.java:2537-2543`, then enters its `freezing` section. Frozen-tick progression is guarded by `!level.isClientSide` at lines 2546-2553; it increments by one while `isInPowderSnow && canFreeze()`, otherwise decrements by two. After that server-only update, both sides execute `removeFrost()` and `tryAddFrost()` at lines 2555-2556. `tryAddFrost` (`LivingEntity.java:509-524`) requires a non-air `getBlockStateOn()`, a positive `getTicksFrozen()`, and a non-null movement-speed attribute. It computes `float f = -0.05F * getPercentFrozen()` and adds a transient `AttributeModifier` with `Operation.ADDITION` and the powder-snow UUID. `Entity.java:200, 238-241, 2059-2069` defines the frozen-tick value as synchronized entity data, defaults it to zero, and derives the frozen proportion as `(float)Math.min(ticksFrozen, ticksRequiredToFreeze) / ticksRequiredToFreeze`; the base required duration is 140 ticks (`Entity.java:126, 2076-2078`). The client path therefore applies the modifier from its current frozen-tick value without locally advancing that value in this section.

**Local-player applicability and next travel read.** `LocalPlayer.tick` delegates through `super.tick()` (`client/player/LocalPlayer.java:191-194`); `Player.tick` delegates to `LivingEntity.tick` (`Player.java:219-248`), which calls `aiStep` (`LivingEntity.java:2213-2254`). `Player.aiStep` calls `super.aiStep()` and then updates its cached speed field from the movement-speed attribute (`Player.java:488-512`). More directly, `Player.getSpeed()` returns `(float)getAttributeValue(Attributes.MOVEMENT_SPEED)` (`Player.java:1463-1466`), so the frost modifier is visible to the local player’s next travel even though `setSpeed` is after the current superclass `aiStep`. `Player.travel` delegates to `LivingEntity.travel` (`Player.java:1417-1448`); on the ordinary ground branch, `LivingEntity.handleRelativeFrictionAndCalculateMovement` calls `getFrictionInfluencedSpeed`, whose on-ground formula is `getSpeed() * (0.21600002F / (f * f * f))` (`LivingEntity.java:2107-2112, 2151-2154, 2196-2201`). Thus, with a positive frozen-tick value and a non-air block below, the post-travel additive modifier changes the movement-speed input consumed on the following on-ground travel. Airborne friction uses `flyingSpeed` in that helper, so this evidence does not claim the same direct speed-attribute effect for that branch. The modifier’s source condition is not “currently in powder snow”: it can be re-added while frozen ticks remain positive on any non-air block beneath the entity.

## Boundaries and applicability

This establishes a source difference within the exact endpoint pair: the powder-snow/frozen-tick state and post-travel speed modifier are absent from 1.16.5 and present in 1.17. It supports a bounded local-player movement applicability claim for the on-ground next-travel consumer, conditioned on positive frozen ticks. It does not establish the exact intermediate patch introduction boundary, all travel-branch effects, trajectory magnitude, runtime parity, or broader powder-snow behavior. Damage, rendering, and block-state production are not evaluated.
