## Ordered active-player route

1. **Input-side start is bypassed by the assignment premise.** In both releases `LocalPlayer.aiStep` can request start only when jump is down, no flying/jump-trigger suppression applies, `!onClimbable()`, and `tryToStartFallFlying()` succeeds; it then snapshots `wasFallFlying = isFallFlying()` before `super.aiStep` (1.21.4 `LocalPlayer.java:749–754`; 1.21.5 `LocalPlayer.java:770–775`). `Player.tryToStartFallFlying` is unchanged in the compared ranges and requires `!isFallFlying() && canGlide() && !isInWater()` before setting shared flag 7 (`Player.java:1528–1539` in 1.21.4; `1507–1518` in 1.21.5). Here the player is already actively fall-flying with a default chest Elytra, so startup eligibility/equipment variants are not the question.
2. **Pre-travel velocity cutoff.** In 1.21.4 `LivingEntity.aiStep` independently zeros each of x, y and z when `abs(component) < 0.003`, writes the velocity, then later reaches travel (`LivingEntity.java:2708–2724`, `2766–2783`). In 1.21.5 player entities instead zero both x and z together iff `horizontalDistanceSqr() < 9.0E-6`; non-player entities retain the per-axis x/z checks, and y still independently uses `abs(y) < 0.003` (`LivingEntity.java:2685–2709`). This player-specific radial cutoff occurs before input application and the travel section (`:2710–2718`, `:2751–2767`). Thus it precedes both the first glide calculation and the new ordinary-air route. At the strict radius boundary (`horizontalDistanceSqr() == 9.0E-6`) x/z are retained. This is cutoff, not a speed cap.
3. **Active glide updater remains before travel.** In both versions `updateFallFlying()` is called iff flag 7 is active before `travel`. In 1.21.4 the travel section first multiplies `xxa` and `zza` by `0.98F`, then updates, snapshots the AABB and constructs the travel input (`LivingEntity.java:2766–2783`). In 1.21.5 `aiStep` calls `applyInput()` before jump/travel (`:2710–2718`), whose body multiplies those values by `0.98F` (`:2806–2809`); the travel section then updates, snapshots and constructs input (`:2751–2767`). `updateFallFlying()` calls `checkSlowFallDistance()` on both sides, but its `canGlide()` stop check and periodic equipment wear/event work are inside `!level().isClientSide`; therefore this updater does not clear the local-client glide flag on this route (`1.21.4:2825–2845`; `1.21.5:2815–2835`).
4. **Travel branch order.** 1.21.4 first requires `isControlledByLocalInstance()`, then sends eligible water/lava movement to `travelInFluid`; otherwise it chooses `travelFallFlying` when `isFallFlying`, else `travelInAir` (`LivingEntity.java:2189–2200`). 1.21.5 has no enclosing local-instance condition in this method; its branch order is fluid first, then fall-flying, then air (`:2213–2222`). For the assigned locally controlled, dry player, the reachable route is the fall-flying branch in both releases.
5. **New climbable route is inside fall-flying travel, not an earlier updater.** 1.21.4 `travelFallFlying` immediately computes `updateFallFlyingMovement`, applies it with `move(SELF, ...)`, and has no climbable predicate (`LivingEntity.java:2279–2288`). In 1.21.5 it first calls `onClimbable()`: true calls `travelInAir($$0)` and then `stopFallFlying()`; false performs the existing glide calculation/move/collision sequence (`:2301–2315`). Therefore the contact tick still reaches the pre-travel `updateFallFlying()` while flag 7 is true. On the climbable path it gets one ordinary-air movement for that tick, then clears flag 7; the next dry tick takes ordinary air through the normal travel branch. If the earlier fluid predicate wins, this fall-flying route and its new climbable check are not reached.
6. **Predicate and flag semantics.** Both `onClimbable()` implementations reject spectators, read `blockPosition()` and `getInBlockState()`, accept `BlockTags.CLIMBABLE`, and also accept a usable open trapdoor ladder (`1.21.4 LivingEntity.java:1575–1590`; `1.21.5:1600–1616`). Ladder/vine applicability here is through that state predicate, not a collision-shape/contact test. The stop method sets shared flag 7 true and then false. It exists on `Player` in 1.21.4 (`Player.java:1541–1544`) and moves to `LivingEntity` in 1.21.5 (`LivingEntity.java:2317–2320`); the two writes are the same. The newly added behavior is the climbable-triggered call after air travel, not a new flag bit or a new stop-method body.

## Boundaries

This is a source-only claim for a dry, locally controlled player already fall-flying with the default chest Elytra at a climbable state recognized by `onClimbable()`. It excludes glide startup, other/custom equipment slots or equipment behavior, the exact A/B shape/contact geometry that places the player at the state, fluid cases, spectator behavior beyond the predicate’s explicit gate, remote/server movement, and runtime trajectory outcomes. Exact intermediate patch introduction within 1.21.4–1.21.5 is not established.
