# Independent source audit verdict: 1.20.4 → 1.20.5 Elytra glide cap route

## Verdict

**Accept the frozen bounded no-difference claim, with a sharper applicability limit for gravity.** The active-flag check/update, valid chest Elytra check, dry travel branch order, glide fall-distance cap and first glide move have the same relevant behavior in both releases for the stated ordinary default player. Ladder/vine feet do not reach the climbable fall-distance cleanup on that glide route. The cap itself and its pre-move timing are identical.

The unchanged first-glide gravity value is established only for a default player with the effective gravity attribute at `0.08`, `isNoGravity() == false`, and no Slow Falling or Levitation effect. In 1.20.5, a permission-level-2 `/attribute` command can directly set a player’s `generic.gravity` base value; the attribute is syncable and the client applies attribute update packets. Thus a non-default gravity value is a concrete externally writable player state, not merely a theoretical or mod-only case. `Entity#setNoGravity` also makes `getGravity()` return zero; its generic NBT load path can restore that flag, although this source tree’s direct vanilla setter call sites are for other entity paths, not an ordinary player. Neither case is in the default-player witness.

## Independent trace

- `LocalPlayer.aiStep` reaches `super.aiStep()` in both exact sources (1.20.4 `:800`, 1.20.5 `:807`). The inherited `LivingEntity.aiStep` calls `updateFallFlying()` and then `travel(...)` in that order (1.20.4 `:2593-2604`, 1.20.5 `:2673-2684`).
- `updateFallFlying()` starts from shared flag 7 and requires the flag, airborne state, not being a passenger, and no Levitation before checking the chest slot for Elytra plus `ElytraItem.isFlyEnabled`. The helper is unchanged: `damageValue < maxDamage - 1` (both `ElytraItem.java:18-20` in 1.20.4 and `:19-21` in 1.20.5). When its computed result differs, shared flag 7 is written only off the logical client (`LivingEntity.java:2663-2665` / `:2743-2745`); `isFallFlying()` directly reads flag 7 (`:3086-3088` / `:3165-3167`). This supports the report’s client-side distinction between computed cancellation and the still-read active flag. These exact gates and write conditions match across the pair.
- On the dry controlled-player path, both `travel` methods test water, then lava, then `isFallFlying()`, before the ordinary movement `else` (`1.20.4 LivingEntity.java:2043-2162`; `1.20.5 :2112-2229`). The glide arm calls `checkSlowFallDistance()` first, then reads/updates velocity, sets velocity, and calls `move` (`1.20.4 :2099-2125`; `1.20.5 :2168-2194`). `Entity.checkSlowFallDistance()` is byte-for-byte behaviorally identical at `1.20.4 Entity.java:2313-2318` and `1.20.5 :2320-2324`: if pre-move `deltaMovement.y() > -0.5` and `fallDistance > 1.0F`, it assigns exactly `1.0F`.
- The ordinary branch obtains movement from `handleRelativeFrictionAndCalculateMovement`; that helper invokes `handleOnClimbable` before its own move. The climbable helper resets fall distance when `onClimbable()` is true (`1.20.4 LivingEntity.java:2202-2205, 2230-2232`; 1.20.5 `:2269-2272, 2297-2299`). Since the earlier glide `else if` wins while flag 7 is active in dry conditions, ladder/vine climbable cleanup is bypassed before the glide move. The source is consistent on this routing claim.
- Gravity is the adjacent source difference: 1.20.4 initializes travel gravity to literal `0.08` (`LivingEntity.java:2035-2040`); 1.20.5 initializes it with `getGravity()` (`:2104-2109`). `Attributes.GRAVITY` is registered with base default `0.08` and is syncable (`Attributes.java:42-44`); `LivingEntity.createLivingAttributes()` includes it (`:292-304`), and `Player.createAttributes()` inherits those living attributes (`Player.java:221-229`). `LivingEntity.getDefaultGravity()` reads its effective value (`LivingEntity.java:2099-2102`), while `Entity.getGravity()` returns zero when no-gravity is set (`Entity.java:1093-1107`). For ordinary default gravity and no no-gravity flag, this supplies the same `0.08` to the unchanged glide expression `deltaY + gravity * (-1.0 + lookFactor * 0.75)` (`LivingEntity.java:2109` vs `:2178`).
- Applicability of the attribute exception is concrete: 1.20.5 `AttributeCommand.register` accepts an entity target and requires permission level 2 (`AttributeCommand.java:41-48`); its living-entity path accepts `Player`, and its base setter calls `AttributeInstance.setBaseValue` (`:216-229, 273-276`). Permanent modifiers are another command write (`:279-286`). Gravity syncability, server entity attribute packets and `ClientPacketListener.handleUpdateAttributes` (`Attributes.java:42-44`, `ServerEntity.java:244-249, 297-300`, `ClientPacketListener.java:2059-2079`) establish that such a player value reaches the client movement attribute. With effective `g != 0.08`, the 1.20.5 glide’s first vertical gravity term differs from 1.20.4’s literal. Separately, when Slow Falling is active with non-descending velocity, 1.20.4 replaces gravity with `0.01`, while 1.20.5 applies `Math.min(getGravity(), 0.01)` (`:2038-2041` vs `:2106-2110`); it is not part of the no-effect default witness. In `LivingEntity.aiStep`, Slow Falling or Levitation also resets fall distance before `travel` (`:2596-2598` / `:2676-2678`), which limits a witness asserting a pre-cap distance above one.

## Limits

It does not establish all 1.20.5 gravity-attribute/no-gravity cases, Slow Falling/Levitation witnesses, intermediate patch introduction, later glide ticks, non-dry travel, or full-pair movement coverage. No runtime parity was assessed.
