## Shared route and order

- **Local start guard:** `net/minecraft/client/player/LocalPlayer.java:744-748` gates the jump-triggered start on not being in the excluded jump/ability/passenger states and `!this.onClimbable()`, then requires enabled chest Elytra and `tryToStartFallFlying()`. `Player.java:1534-1543` rechecks airborne, inactive, not in water, no Levitation, and enabled chest Elytra; that predicate itself has no climbable check. A successful start sets shared flag 7 (`Player.java:1546-1548`). Thus ordinary local input does not initiate glide while the player is on a climbable block.
- **Server command guard:** `net/minecraft/server/network/ServerGamePacketListenerImpl.java:1410-1413` re-runs `tryToStartFallFlying()` for `START_FALL_FLYING`; failure calls `stopFallFlying()`. `Player.java:1550-1553` clears flag 7 (with a set-then-clear pair). These checks are unchanged in both releases.
- **Already-active flag and tick entry:** `net/minecraft/world/entity/LivingEntity.java:2671-2684` damps input, calls `updateFallFlying()`, creates the travel input, applies Slow Falling/Levitation fall-distance reset, then enters `travel`. In `updateFallFlying()` (`2721-2745`), an already-set flag remains set when airborne, not passenger, not under Levitation, and the chest Elytra is enabled; climbability is not a cancellation condition. The server writes the resulting flag; the client does not write it here. Therefore an already-active glide can remain active while standing at a climbable state, even though local jump input will not start one there.
- **Glide branch before climb cleanup:** `LivingEntity.java:2168-2207` selects the Elytra branch before the ordinary friction branch. It calls `checkSlowFallDistance()` first, computes glide velocity, applies drag, and calls `move(MoverType.SELF, ...)`; the server-side landing test may then clear flag 7. This branch has no `handleOnClimbable()` call. For an active glide at a ladder/vine, it is glide movement and its collision/ground response, not the ordinary climb velocity cleanup, that runs on that tick.
- **Cap timing and predicate:** `Entity.java:2320-2324` caps `fallDistance` to `1.0F` only when the current vertical delta is `> -0.5` and current fall distance is `> 1.0F`. Because the glide branch invokes it before capturing/computing the movement and before its first `move`, the cap observes pre-move velocity and distance on the first glide-movement tick as well as later glide ticks. A more negative current Y velocity or distance at/below `1.0F` leaves distance unchanged there.
- **Ordinary climb cleanup:** `LivingEntity.java:2269-2279` routes ordinary friction movement through `handleOnClimbable()` before `move`. `2297-2309` shows that helper resets fall distance and clamps X/Z to `[-0.15F, 0.15F]`, clamps Y to at least `-0.15F`, and may suppress negative Y for a sneaking Player on a non-scaffolding climbable. That cleanup is bypassed whenever the earlier glide branch is active. `onClimbable()` (`1541-1556`) reads the in-block state and returns true for `BlockTags.CLIMBABLE` (or a usable trapdoor), not by examining historical block shapes in this slice.

## Bounded tick and interactions

Start boundary: the LocalPlayer jump-input gate and `tryToStartFallFlying()` decide whether ordinary client input sets the active flag. The server command path independently revalidates and cancels failed requests. Final boundary: the next `LivingEntity.aiStep` travel phase reevaluates an active flag before choosing glide vs ordinary movement; invalid ground/passenger/Levitation/Elytra conditions clear it on the server. No climbable check is part of that active-flag reevaluation.

The glide `move` call and its `horizontalCollision`/`onGround` outcomes depend on collision, support, and environmental contacts (the solid-world and environmental movement domains). The climb decision additionally depends on the vanilla in-block state/tag predicate. Those underlying shape/contact implementations and any A/B-owned behavior are not independently audited here; this report only records their call/order interaction with the Elytra route. No difference was found across 1.20.5→1.20.6 in the inspected operation files, including the movement formula, active-flag gates, cap predicate/order, or climb cleanup order.
