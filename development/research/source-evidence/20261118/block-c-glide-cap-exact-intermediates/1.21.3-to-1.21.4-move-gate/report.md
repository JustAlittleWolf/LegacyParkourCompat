# 1.21.3 → 1.21.4 glide cap and route comparison

## Scope and evidence identity

Bound slice: dry, on-foot local player, already fall-flying with the ordinary chest-slot Elytra; compare the active update/cancel order, climbable versus glide travel route, slow-fall-distance cap, and following glide move. A ladder/vine witness is split into **A**, where the feet-position block state makes `onClimbable()` true, and **B**, a nearby geometry control where it is false. Contact alone is not the predicate: `LivingEntity.onClimbable()` reads `getInBlockState()` at `blockPosition()` and checks `BlockTags.CLIMBABLE` (except spectator); `Player.onClimbable()` only suppresses that result for abilities flight. Do not infer a true witness from visual overlap if that state predicate is false.

## Ordered source comparison

1. **Active update and stop flag — no difference found.** In both releases, `LivingEntity.aiStep()` checks `isFallFlying()` and calls `updateFallFlying()` before `travel(...)` (`LivingEntity.java:2758–2782` in 1.21.3; `2769–2793` in 1.21.4). `updateFallFlying()` first calls `checkSlowFallDistance()`. Only after that, on a non-client level, it calls `canGlide()` and clears shared flag 7 then returns when glide is no longer allowed (`2814–2848`; `2825–2859`). A normal dry local-player tick does not execute that server-only cancellation check. If cancellation does clear the flag on a server, the subsequent `travel` dispatch sees the cleared state.

2. **First move route — no difference found in the glide/climbable choice for the stated on-foot, non-abilities-flying player.** Both releases dispatch `travel(...)` for the locally controlled entity to fluid travel first, then `travelFallFlying()` when the active flag remains set, otherwise ordinary air travel (`LivingEntity.java:2178–2187` and `2268–2276`; `2189–2198` and `2279–2287`). For dry A, the active route updates glide velocity and calls `move(MoverType.SELF, deltaMovement)` directly. That route does not call ordinary air travel's `handleRelativeFrictionAndCalculateMovement()` / `handleOnClimbable()`. If the active flag has been cleared before dispatch, ordinary air travel can reach `handleOnClimbable()`, which resets fall distance and clamps horizontal velocity to ±0.15 and downward Y to at least -0.15 (`2379–2398`; `2390–2409`). The climbable cleanup is therefore not applied just because A touches a ladder/vine while the glide route remains active. B confirms the control case where the predicate is false. In 1.21.3 the player inherits `LivingEntity.onClimbable()`; 1.21.4 adds `Player.onClimbable()` (`Player.java:2171–2173`) to return false while abilities flight is enabled, otherwise delegate. That addition has no effect for the assigned on-foot ordinary player; both paths use the inherited climbable predicate.

3. **Fall-distance cap and placement — cap is unchanged; post-move accumulation differs.** `Entity.checkSlowFallDistance()` is identical in both releases: if current vertical delta is greater than `-0.5` and `fallDistance > 1.0F`, it writes exactly `1.0F` (`Entity.java:2484–2492`; `2512–2520`). Because `updateFallFlying()` calls it before the server-only active-flag cancellation check, the cap precedes both that cancellation and the tick's first glide move. It is a cap on the value already present; it does not cap the movement delta.

   The adjacent-pair delta is in `Entity.move()`. In 1.21.3 it always computes vertical collision/on-ground state, then runs `checkFallDamage(...)` whenever `!level().isClientSide() || isControlledByLocalInstance()` (`Entity.java:619–672`). Thus a local client player reaches `checkFallDamage`, whose airborne downward case adds `-(float)dy` to `fallDistance` (`1216–1233`). In 1.21.4 collision/on-ground state is computed only when `abs(requestedDy) > 0.0 || isControlledByOrIsLocalPlayer()`; the local player satisfies the latter. But the later fall-distance call adds `&& !isControlledByClient()` (`Entity.java:627–683`). `Player.isControlledByClient()` returns true (`Player.java:2166–2168`), so this local player's move no longer accumulates client-side `fallDistance`. The cap still runs at the start of each active update. Consequently, for a descending dry A or B witness with pre-move `fallDistance > 1` and vertical delta `>-0.5`, 1.21.3 caps to `1.0F` and then the move may add its downward distance; 1.21.4 caps to `1.0F` and its client move does not add that distance. A landing/contact can still invoke other position/collision behavior; runtime parity is not established by source comparison.

4. **Later glide move — route remains active on the stated client path.** At the end of each LivingEntity tick, `fallFlyTicks` increments while `isFallFlying()` remains true (`2529–2534`; `2540–2545`). On the next tick the same `aiStep()` update/cap runs before `travel(...)` dispatches another glide move. The Elytra wear/event cadence is checked server-side from `fallFlyTicks + 1` every ten ticks; it does not insert a different client movement route.

## Coverage boundary

Compared the ordered `Player.tick` → `LivingEntity.tick`/`aiStep` → `updateFallFlying` → `travel` → `Entity.move` path and its ordinary climbable fallback, including the cap helper and local-player control predicates. `LivingEntity` travel, active update, cap, and climbable cleanup are otherwise source-identical across this pair. `Entity.move` contains the source-confirmed fall-distance gate change above. This report does not cover fluids, mounted players, server simulation, non-default/custom gliders, start-of-glide eligibility, endpoint blocks, or runtime behavior. No wiki, product implementation/history, generated sources, build, test or launch was consulted/performed.
