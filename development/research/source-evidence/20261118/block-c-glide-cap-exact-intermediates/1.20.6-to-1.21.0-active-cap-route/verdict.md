# Independent source audit: Elytra active-update and cap route

## Verdict

**Accepted for the assigned bounded route, with an evidence-coverage correction.** I found no movement-behavior delta between 1.20.6 and 1.21.0 in the local-client, dry, already-active Elytra glide branch, including the climbable A/B and the slow-fall-distance cap before the first glide move. The source report's conclusion is correct for this slice; it is not full-pair acceptance or runtime-parity evidence.

The report does not cite the dynamically dispatched `LivingEntity.checkFallDamage` override, and its first-move summary omits `Entity.move`'s fall-resetting-block clip check. I traced both dependencies below. They do not change the bounded no-difference result: the override's state-relevant path is the same for a local client, and the clip reset predicate and order are unchanged in the compared releases.

## Independent trace

1. **Existing fall-flying flag and client tick order.** `LivingEntity.isFallFlying()` reads shared flag 7 in both releases (1.20.6 `LivingEntity.java:3165–3167`; 1.21 `:3167–3169`). On each `LivingEntity.aiStep`, input is scaled, `updateFallFlying()` is called, and only then `travel` is dispatched (1.20.6 `LivingEntity.java:2671–2684`; 1.21 `:2666–2679`). `LocalPlayer.aiStep` calls `super.aiStep()` at 1.20.6 `LocalPlayer.java:807` / 1.21 `:804`; `Player.aiStep` calls its super at 1.20.6 `Player.java:532` / 1.21 `:534`.

   The ordered `updateFallFlying()` gate and chest-item checks are the same: flag 7, airborne, not a passenger, no levitation, then chest Elytra and `ElytraItem.isFlyEnabled`. With those conditions true it retains the local boolean and calculates `fallFlyTicks + 1`; its flag write is inside `!level().isClientSide` in both versions (1.20.6 `LivingEntity.java:2721–2745`; 1.21 `:2716–2740`). Thus the stated local-client, already-active route keeps using the existing true shared flag. `Player.tryToStartFallFlying`, `startFallFlying`, and the ordered true/false writes in `stopFallFlying` also match (1.20.6 `Player.java:1534–1552`; 1.21 `:1529–1547`).

2. **Climbable A/B and selected travel branch.** The LocalPlayer start-from-rest input condition includes `!onClimbable()` in both releases (1.20.6 `LocalPlayer.java:744–748`; 1.21 `:741–745`). That check prevents this input path from starting a glide from rest; it is not a gate in `updateFallFlying` and does not revoke an already-set flag. `onClimbable()` consults the current in-block state and climbable tag (1.20.6 `LivingEntity.java:1541–1555`; 1.21 `:1517–1533`).

   For dry travel with ordinary player flying ability off, `Player.travel` delegates to `LivingEntity.travel` in both versions (1.20.6 `Player.java:1485–1494`; 1.21 `:1468–1477`). The active `isFallFlying()` branch begins with `checkSlowFallDistance()`, computes glide movement, writes the damped delta, and calls `move(SELF, delta)` (1.20.6 `LivingEntity.java:2168–2194`; 1.21 `:2151–2177`). It does not call `handleOnClimbable`; that reset-and-clamp routine is reached from generic relative-friction movement (1.20.6 `LivingEntity.java:2269–2308`; 1.21 `:2252–2291`). Consequently both feet contexts follow the same active glide branch and neither gets the generic climbable fall-distance reset on this move. A 1.21 water-movement change is not entered under the dry precondition.

3. **Cap and first-move fall-distance effects.** The exact cap is unchanged: `if (getDeltaMovement().y() > -0.5 && fallDistance > 1.0F) fallDistance = 1.0F;` (1.20.6 `Entity.java:2320–2324`; 1.21 `:2386–2390`). Since it precedes glide acceleration and `move`, it tests the pre-glide-move vertical delta. Earlier in `LivingEntity.aiStep`, both releases also reset fall distance if Slow Falling or Levitation is active (1.20.6 `LivingEntity.java:2676–2678`; 1.21 `:2671–2673`); that earlier write is outside the ordinary no-effect route. Both sources then have the same `Entity.move` fall-resetting-block check before position update: only when resolved movement length squared is at least `1.0` and `fallDistance != 0.0F`, clip using `FALLDAMAGE_RESETTING` and reset on a hit (1.20.6 `Entity.java:617–629`; 1.21 `:618–630`).

   After collision resolution, `Entity.move` dispatches `checkFallDamage` with resolved Y movement and current on-ground state (1.20.6 `Entity.java:644–647`; 1.21 `:645–648`). A player reaches the `LivingEntity` override first (1.20.6 `LivingEntity.java:309–342`; 1.21 `:327–359`), which calls the same base method and clears `lastClimbablePos` on ground in both. On a local client, the override's block-effect branch is skipped in both versions (`!isClientSide` in 1.20.6; `level instanceof ServerLevel` in 1.21); therefore it adds no client movement delta here. The base behavior is identical: grounded movement processes and resets positive fall distance; otherwise a negative resolved Y adds `-(float)resolvedY` (1.20.6 `Entity.java:1124–1139`; 1.21 `:1163–1178`).

   The ground-state setter called by `Entity.move` was renamed from `setOnGroundWithKnownMovement` to `setOnGroundWithMovement` (1.20.6 `Entity.java:562–565`; 1.21 `:563–566`); both assign the same `onGround` value and call the same `checkSupportingBlock` procedure. It does not alter the cap or fall-distance branch order in this slice. The tick-tail `fallFlyTicks` increment/reset follows `aiStep` and is unchanged (1.20.6 `LivingEntity.java:2446–2450`; 1.21 `:2429–2433`).

## Boundaries

It does not establish complete 1.20.6↔1.21 movement coverage, water/lava/creative/ridden routes, collision-shape or registry coverage, server synchronization, landing trajectories, patch-boundary introduction, or runtime parity.
