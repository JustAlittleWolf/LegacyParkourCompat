# Elytra active-update and cap route: 1.20.6 → 1.21

## Scope and verdict

Read-only exact-source comparison of the ordinary on-foot, dry, locally controlled player with shared fall-flying flag already true and enabled Elytra in the chest slot. The only contextual A/B is ordinary feet versus a ladder/vine state that satisfies `LivingEntity.onClimbable()`. No release difference was found in the active flag update, glide branch, pre-move fall-distance cap, end-of-tick glide counter, or the first move's fall-distance accumulation/reset. The 1.21 water travel branch differs, but dry input does not enter it. This is bounded evidence for this route, not full-pair coverage or runtime parity.

## Ordered route and evidence

1. **Entry and existing flag.** `LocalPlayer.aiStep` has a start-from-rest input gate requiring jump input and excluding climbing (`!this.onClimbable()`), then checks chest Elytra/enabled before `tryToStartFallFlying`; the shared `Player.tryToStartFallFlying` checks airborne, not already flying, not in water, and not levitating before writing flag 7 true. For this assignment's already-active state, that start gate is not re-entered as a prerequisite. Thus a climbable state can block starting from rest, while it does not itself invalidate an already active glide. `Player.stopFallFlying()` writes flag 7 true and then false in both releases; this ordered pair is unchanged. `LivingEntity.isFallFlying()` reads the shared flag. Evidence: 1.20.6 `LocalPlayer.java:744–748`, `Player.java:1534–1553`, `LivingEntity.java:3165–3167`; 1.21 `LocalPlayer.java:741–745`, `Player.java:1529–1548`, `LivingEntity.java:3167–3169`.

2. **Tick phase and active-update predicates.** `LivingEntity.tick()` calls `aiStep()` before its post-step section. Dynamic dispatch reaches `LocalPlayer.aiStep` (which calls `super.aiStep`) and then `Player.aiStep` (which calls `super.aiStep`); in `LivingEntity.aiStep`, movement inputs are scaled, `updateFallFlying()` runs, then the input vector is built and `travel`/`travelRidden` is dispatched. In `updateFallFlying`, predicate order is: read flag 7; require that flag, `!onGround()`, `!isPassenger()`, and no levitation; fetch chest stack; require `Items.ELYTRA` and `ElytraItem.isFlyEnabled`. Failure assigns the local `$$0=false`; success keeps it true and computes `fallFlyTicks + 1`. Server-only durability/event handling follows. The only flag write in this updater is `setSharedFlag(7, $$0)` under `!level().isClientSide`, so the local client updater itself does not directly rewrite the flag. When the ordered predicates pass (not grounded, not riding, not levitating, enabled chest Elytra), the updater keeps the existing shared flag set. If a predicate fails on the local client, it assigns only the local temporary false; it does not clear the client shared flag here. No `onClimbable()` predicate occurs in this active-update method. Evidence: 1.20.6 `LivingEntity.java:2336–2377, 2591–2599, 2670–2684, 2721–2745`; 1.21 `LivingEntity.java:2319–2360, 2586–2594, 2665–2679, 2716–2740`; the local-player super call is at `LocalPlayer.java:807` (1.20.6) / `:804` (1.21).

3. **Dry glide branch before first movement.** `Player.travel` delegates to `LivingEntity.travel` for the stated non-creative-flying case. With no water/lava branch taken and flag 7 active, `LivingEntity.travel` selects `else if (isFallFlying())` before the generic friction path. Its first operation is `checkSlowFallDistance()`, before reading the look vector and computing glide acceleration. It then sets the computed damped delta movement and calls `move(MoverType.SELF, delta)`. The glide branch has no climbable cleanup call. `handleOnClimbable` is only reached through `handleRelativeFrictionAndCalculateMovement`, called from the non-glide generic branch; it resets fall distance and clamps X/Z and downward Y there. Therefore, on A ordinary feet and B ladder/vine feet that satisfy `onClimbable()`, the same active glide branch and no climb cleanup apply. Evidence: 1.20.6 `Player.java:1473–1494`, `LivingEntity.java:2104–2233, 2168–2208, 2269–2309`; 1.21 `Player.java:1456–1477`, `LivingEntity.java:2091–2216, 2151–2191, 2252–2294`; `onClimbable` reads the current in-block climbable state at 1.20.6 `LivingEntity.java:1541–1551` / 1.21 `:1517–1532`.

4. **Fall-distance cap and first-move interaction.** In both releases, `Entity.checkSlowFallDistance()` is exactly `if (getDeltaMovement().y() > -0.5 && fallDistance > 1.0F) fallDistance = 1.0F;`. The cap is conditional and runs against the pre-glide-move vertical delta because it precedes glide acceleration and the first `move`. The subsequent common `Entity.move` path calls `checkFallDamage` with resolved movement: on a non-ground negative Y move it adds `-(float)resolvedY` to fall distance; on ground it processes/reset the distance. Both methods have the same predicates, casts, writes, and order in this route. Evidence: 1.20.6 `Entity.java:647–648, 1124–1139, 2320–2328`; 1.21 `Entity.java:648, 1163–1178, 2386–2394`.

5. **End-of-tick and termination.** After the `aiStep`/travel movement returns, the later `LivingEntity.tick` section increments `fallFlyTicks` if `isFallFlying()`, otherwise sets it to zero. Thus the active updater reads `fallFlyTicks + 1` before this tick-tail increment, and the first glide move occurs before the tail increment. `LivingEntity.travel` only clears shared flag 7 after the glide move when `onGround() && !isClientSide`; this is server-only. On a local client, that on-ground branch does not directly clear the flag; synchronization is outside this source slice. Evidence: 1.20.6 `LivingEntity.java:2444–2450, 2194–2208`; 1.21 `LivingEntity.java:2427–2433, 2177–2191`.

## Coverage limits

Compared: the active-update predicate/write sequence; local input start guard and `Player` start/stop writers; `Player.travel` dispatch; the dry Elytra branch through first `move`; fall-distance cap, move accumulation/reset, climbable friction cleanup, and tick-tail `fallFlyTicks` update. A/B are block contexts within that same already-active route. Not compared: a full movement tick graph, fresh start from arbitrary states, water/lava, creative flight, passenger/ridden movement, landing trajectories, exact block/tag registries, server packet timing, or runtime parity. The `onClimbable` result depends on the player's current in-block state; a block merely beneath the feet is not assumed to make it true without that predicate.
