## Verdict

**Accepted for the bounded default glide claim.** Given an already-set fall-flying flag, airborne local player, no passenger or Levitation, an enabled chest-slot Elytra, dry state, and no Slow Falling, both versions run `updateFallFlying()` before `travel()`. The updater preserves the active flag candidate under the same gates and only writes shared flag 7 off-client. Water and lava movement branches precede `isFallFlying()` in both versions; the dry active glider therefore reaches the glide branch. The glide equations, operation order, `0.99F/0.98F/0.99F` attenuation, and move call match. No velocity cap occurs before `move`; `$$21 * 3.2` is the negative-pitch vertical-lift term. The only on-ground accessor change is behaviorally equivalent at this call site: 1.20.0 `Entity.onGround()` returns the field.

For climbable feet, both versions take that same glide branch without testing `onClimbable()`. The X/Z clamp, downward Y floor, and ladder player rule reside in `handleOnClimbable()`, called by the ordinary friction route after the glide branch. Thus active glide bypasses that cleanup for ordinary as well as climbable feet in both versions. The post-move grounded flag clear remains guarded to non-client execution. Collision/contact outcomes and glide start eligibility were not audited.

## Separate fall-distance writer and effect boundary

The report’s travel-only Slow Falling comparison needs this additional dependency: `LivingEntity.aiStep()` in 1.20.0 calls `updateFallFlying()`, then unconditionally checks `hasEffect(SLOW_FALLING) || hasEffect(LEVITATION)` and resets fall distance before dispatching to `travel()` (`LivingEntity.java` 2562–2572). `LocalPlayer.aiStep()` reaches that method through `super.aiStep()` (`LocalPlayer.java` 801). The paired 1.19.4 `aiStep()` goes from `updateFallFlying()` to its travel dispatch without this effect-gated reset (`LivingEntity.java` 2543–2550); its reset at line 2694 is in `rideTick()`, outside this non-passenger route. `Entity.resetFallDistance()` assigns `fallDistance = 0.0F` in both versions.

Classify this as a **separate effect-conditioned player-state writer**, introduced on this endpoint pair in `LivingEntity.aiStep`, not as a change to the glide velocity route. It resets fall distance for either effect regardless of starting vertical velocity and runs before travel. In 1.19.4, the in-`travel` Slow Falling reset is conditional on `deltaMovement.y <= 0.0`; consequently the new writer extends Slow Falling reset to positive-Y ticks and adds a Levitation reset on the active local glide route. For Slow Falling at non-positive Y, both paths reset before the glide branch’s unchanged `checkSlowFallDistance()`; the final fall-distance value is zero on that path, so the report’s claimed travel-site deletion alone overstates a value difference there. `checkSlowFallDistance()` is identical: it only caps to `1.0F` when Y velocity is greater than `-0.5` and fall distance exceeds `1.0F`.

**Default no-effect dry behavior is unchanged.** The new `aiStep()` gate does not run without either effect, and the removed 1.19.4 travel reset does not run without Slow Falling. This verdict does not imply that all effect-conditioned fall-distance behavior is unchanged. Keep the aiStep writer as a separate source dependency/finding if the effect boundary is in scope; do not fold its broader gate into the no-effect glide-route claim.
