## Bounded trace and comparison

The reviewed path is an ordinary finite mouse callback delta for the local player while the mouse is grabbed and the window active, with smooth camera off and without first-person scope sensitivity. Screen/device plumbing is outside this trace. In `MouseHandler.onMove` (1.20.2 lines 187–221; 1.20.3 same lines), cursor deltas accumulate only under the grab/active gate, then `turnPlayer()` runs before cursor positions are replaced. `MouseHandler.turnPlayer` (224–264 in both) keeps the same sensitivity order: `s = sensitivity * 0.6F + 0.2F`, `s3 = s * s * s`, ordinary branch deltas `accumulatedD{X,Y} * (s3 * 8.0)`, reset accumulators to zero, apply optional Y inversion, and dispatch `player.turn(yawDelta, pitchDelta)`. The callback and complete `MouseHandler.java` are byte-identical across the pair.

The local player's inherited `Entity.turn` (1.20.2 lines 397–409; 1.20.3 lines 398–410) is text-identical: each double input is cast to float before multiplication by `0.15F`; pitch is written first through virtual `setXRot`, yaw through `setYRot`, pitch is clamped to `[-90.0F, 90.0F]`, old pitch/yaw are incremented by the same float deltas, then old pitch is clamped and a passenger callback may run. `Entity.setXRot` (3303–3309 / 3309–3315) accepts finite values and stores them; the subsequent clamp is the pitch limit. A source-wide signature search found no `turn` or `setXRot` override in these Minecraft source trees, so the `LocalPlayer` dispatch reaches this same implementation on both sides. `Entity.java` differs elsewhere, but these exact bodies do not.

For a reachable active-flight witness, take a locally controlled player in the air with fall-flying active, outside water and lava, and with clear space for the first movement. `LocalPlayer.aiStep` calls `super.aiStep` (1.20.2 line 800; identical file in 1.20.3), which reaches `LivingEntity.aiStep`; the latter calls `updateFallFlying` and then `travel`. The compared methods are text-identical (`aiStep`: 2509–2604 / 2511–2606; `updateFallFlying`: 2639 onward / 2641 onward; `isFallFlying`: 3084–3086 / 3086–3088). The fall-flying flag is retained only while airborne, not riding, not levitating, with an enabled elytra chest item; a reachable active witness satisfies these gates. `LivingEntity.travel` (2038–2175 / 2035–2173) first requires local control, checks water then lava branches, and reaches the `isFallFlying()` branch otherwise. That branch reads `getLookAngle()` and the already-clamped `getXRot()`, forms pitch radians as `float pitch * (float)(Math.PI / 180.0)`, then executes the same ordered double/float operations for gravity, dive lift, upward-pitch lift, horizontal steering and drag before its first `move(MoverType.SELF, delta)` call. `Entity.getLookAngle`, `calculateViewVector`, `move`, `Mth.clamp/sin/cos`, and the used `Vec3.add` / `horizontalDistance` bodies were also text-compared and are identical. A no-collision clear-space witness therefore has the same pitch-derived first flight displacement on both releases.

## Verdict, closure, residuals

No independent finding is warranted.** Mouse accumulation, ordinary sensitivity branch, virtual dispatch, float casts, clamps, look-vector calculation, elytra branch math/order and first move call are equivalent for the stated witness.
