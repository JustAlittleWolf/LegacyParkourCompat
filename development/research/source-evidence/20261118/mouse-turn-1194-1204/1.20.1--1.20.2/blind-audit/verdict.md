## Independent verdicts

| Claim | Verdict | Basis |
| --- | --- | --- |
| Ordinary captured, unscoped, smooth-camera-off callback arithmetic and active gates | **Accepted: bounded equivalence** | `MouseHandler.onMove` (1.20.1 lines 175–210; 1.20.2 lines 187–222) and `turnPlayer` (212–254; 224–266) have the same accumulation order, sensitivity expressions, resets, clears, invert-Y handling, tutorial call and player-turn gate. The ordinary path is active only for the matching window with grabbed mouse and active window; the normal branch assumes smooth camera off, unscoped state, and a player present. The first ignored event only seeds cursor positions. No candidate source delta found. |
| `Entity.turn` virtual pitch setter and clamp | **Accepted: bounded equivalence** | `turn` (1.20.1 lines 395–407; 1.20.2 lines 397–409) has identical float casts and `0.15F` multiplications, pitch-set then yaw-set order, pitch clamp, old-rotation writes/clamp, and vehicle callback. The inherited Entity setter rejects non-finite values and stores finite pitch. A local player has no `setXRot` override in the examined hierarchy, so the virtual call resolves to that setter. No candidate source delta found. |
| Reachability and first active Elytra movement | **Accepted: bounded equivalence** | The cited `LocalPlayer.aiStep` input gate, `Player.tryToStartFallFlying`, `LivingEntity.updateFallFlying`, `LivingEntity.aiStep` travel dispatch, `Player.travel` mode gate, and `LivingEntity.travel` fall-flight branch support the stated witness. For an alive local player in a loaded chunk, not riding, not creative-flying, airborne, not in water/lava, with enabled Elytra and fall-flying active, the selected branch reads pitch and look vector, writes velocity, then calls `move(SELF, ...)`. The relevant gates and flight-move math match across the pair. The writer's `Player.travel`, `LivingEntity.travel`, and Elytra-gate equivalence statement is supported. |
| Scheduler relationship | **Accepted with timing limit** | Both `MouseHandler.setup` callbacks enqueue `onMove` through `Minecraft.execute`; `onMove` itself accumulates and calls `turnPlayer`. In each ordinary active `Minecraft.runTick(true)`, scheduled tasks are drained before the simulation tick loop, and `turnPlayer` is also called after that loop before rendering (`1.20.1` `runTick` lines 1042–1075; `1.20.2` lines 1095–1128). This establishes a reachable local turn before a later movement calculation, and can establish a pre-tick turn for a runnable already queued at the task drain. It does not prove that every OS callback is delivered before a particular logical tick or that a turn affects the tick already in progress. The draft makes no same-tick guarantee. |
| Other flight-mode branch relevant to the trace | **No additional counterexample found** | The separate `Player.travel` `abilities.flying && !isPassenger()` route is unchanged; for this Elytra witness, `abilities.flying` is false. The local creative-flight vertical-input branch in `LocalPlayer.aiStep` is present in both versions and does not supersede the specified Elytra path. This audit does not claim full creative-flight parity. |

`LocalPlayer.aiStep` calls `Player.aiStep`, which calls `LivingEntity.aiStep`; the local branch's enabled-Elytra/jump checks can set the fall-flying shared flag before the inherited `LivingEntity.aiStep` updates that state and dispatches travel. The client local-control gates are reachable: `LocalPlayer.isEffectiveAi()` is true, and Entity's `isControlledByLocalInstance()` uses that result when there is no controlling passenger. The draft appropriately excludes device registration and does not claim runtime parity.

## Scope limits and unresolved gates

No open gate remains for the three claims under this assignment. The timing boundary above is a scope limitation, not a contradiction: OS event delivery and queue arrival relative to a specific tick were excluded as device plumbing. Intermediate patches, broader tick inventory, other movement modes, collision dependencies, and runtime parity remain unreviewed. The 1.20.1-to-1.20.2 endpoint equality does not establish an exact intermediate cutover.
