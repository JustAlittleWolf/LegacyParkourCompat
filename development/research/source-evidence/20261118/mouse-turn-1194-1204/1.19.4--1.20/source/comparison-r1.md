## Ordered mouse path and phase

`MouseHandler.turnPlayer` (`net/minecraft/client/MouseHandler.java:212–254` in both releases) receives already accumulated deltas. With the mouse grabbed, active window, smooth camera off, and not first-person scoping, both versions reset both smoothing accumulators; compute `sensitivity = option * 0.6F + 0.2F`, its cube, and that cube times `8.0`; scale accumulated X/Y by the latter; clear both accumulators; invert only Y when configured; call the tutorial mouse hook; and call `player.turn(x, y * invert)` if a player exists. Operation order, casts, factors, and gates match.

The client scheduler calls `level.tickEntities()` from a client tick (`Minecraft.java:1771` in 1.19.4; `:1759` in 1.20). The outer run loop then calls `mouseHandler.turnPlayer()` after its client-tick loop and before rendering (`Minecraft.java:1085` in 1.19.4; `:1075` in 1.20). Thus this turn update follows the movement ticks already run in that loop; the first subsequent movement tick is the first one that can consume this updated pitch. This establishes scheduler order only. Callback delivery/accumulation phase and how many client ticks the loop runs are outside the claim.

`Entity.turn` is the same ordered operation in both versions (`Entity.java:391–402` in 1.19.4; `:395–406` in 1.20): cast input Y to `float`, multiply by `0.15F`, invoke `setXRot(getXRot() + deltaPitch)`, update yaw by the corresponding cast/multiply, invoke `setXRot(clamp(getXRot(), -90.0F, 90.0F))`, update old rotations, clamp old pitch, then notify a vehicle if present. `Entity.setXRot` rejects a non-finite float before assigning `xRot` (`Entity.java:3155–3161`; `:3273–3279`). `LivingEntity`, `Player`, and `LocalPlayer` provide no override in this pair. With identical pre-turn rotations and the same ordered finite delta, this pitch/yaw and clamp path has the same result. This is same-state operation equivalence; it does not map arbitrary 1.19.4 entity state into 1.20 state.

## First ordinary Elytra move

Under the gates that the local player is locally controlled, airborne, outside the water/lava travel branches, and `isFallFlying()` is true, `Player.travel` delegates to `LivingEntity.travel` rather than taking the abilities-flying branch (`Player.java:1440–1465` in 1.19.4; `:1446–1471` in 1.20; `LivingEntity.java:1983–2048`; `:2004–2068`). The Elytra branch reads current `getLookAngle()` and current pitch, then performs the same glide vector math in the same order in both versions: gravity/lift term; downward-velocity correction; pitch-up correction; horizontal alignment; component damping by `(0.99F, 0.98F, 0.99F)`; and `move(SELF, deltaMovement)` (`LivingEntity.java:2048–2080`; `:2068–2100`). `getLookAngle()` uses current pitch/yaw, without interpolation. Therefore the computed pre-collision move vector is equal for the same starting position/velocity, rotations, gates, and environment.

The narrow position/velocity witness is an ordinary airborne Elytra move with the same collision result and no block/contact response that changes movement: the input vector to `Entity.move` is identical; it adds the same collision-resolved components to position, applies the same horizontal collision velocity clipping, and the same block-speed factor under the same block state (`Entity.java:549–662` in 1.19.4; `:593–706` in 1.20). This bounds equality to that first move's position translation and outgoing velocity under those same-state conditions. Full post-move entity state is not equivalent by this claim: 1.20 has a different on-ground/supporting-block update and movement-emission/contact path in `Entity.move`.

## Separate abilities-flying path

Creative/abilities flight is a distinct route. When `abilities.flying && !isPassenger()`, `Player.travel` saves the prior Y velocity, delegates to `LivingEntity.travel`, restores Y to prior-Y times `0.6`, resets fall distance, and clears the fall-flying flag. `LocalPlayer.aiStep` may add vertical velocity from jump/shift input while flying and controlled-camera (`LocalPlayer.java:752–766` in 1.19.4; `:758–772` in 1.20). For the ordinary airborne, non-fluid, non-swimming abilities-flying case with fall-flying false, `LivingEntity.travel` uses its normal movement branch; `Entity.moveRelative` derives the input vector from yaw (`getYRot()`), not pitch (`Entity.java:1181–1194`; `:1284–1297`). The vertical ability input is not pitch-derived. In this distinct path, pitch does not contribute to the calculated movement vector or first move position/velocity; yaw and movement input still do. The precondition excludes the swimming branch, which reads `getLookAngle().y`, and excludes the active Elytra branch. As above, this is same-state ordinary-path analysis, not a claim about every ability-flight state.

## Changed prelude and limits

The `LivingEntity.travel` prelude differs: 1.19.4 calls `resetFallDistance()` when the controlled entity has non-positive vertical velocity and `SLOW_FALLING`, after setting gravity to `0.01`; 1.20 keeps the gravity assignment but omits that call (`LivingEntity.java:1985–1990` vs. `:2006–2010`). This condition can be reached in the same locally controlled Elytra travel call before the `isFallFlying()` branch. Consequently the whole `travel` call does not have same-state equivalence for `fallDistance`, even though this prelude does not change the first Elytra vector calculation. No wider ramifications of that changed `fallDistance` state are assessed here.

**Bounded verdict:** the ordered mouse path is identical for the same input state, and the first ordinary Elytra move has the same computed vector and, under the stated equal-collision/no-movement-response witness, the same position translation and outgoing velocity. The separate ordinary abilities-flying path is also pitch-insensitive under its stated gates. Whole-call entity-state parity, other flight gates, callback scheduling details, runtime parity, and intermediate patch cutover are not claimed.
