## Bounded trace

The compared path is an ordinary finite cursor callback for the local player while the window is captured and active, with smooth camera off and not scoped. In `MouseHandler.onMove` (1.20 and 1.20.1, lines 175–209), matching-window callbacks accumulate the cursor delta only when `isMouseGrabbed()` and `isWindowActive()`; the callback then calls `turnPlayer()` before updating the stored cursor position. In `turnPlayer` (lines 212–253), the captured/active branch computes sensitivity as `s = sensitivity * 0.6F + 0.2F`, `s3 = s * s * s`, and `s8 = s3 * 8.0`. With smooth camera off and the scoped first-person case false, it resets both smooth-turn accumulators and uses `accumulatedDX * s8` and `accumulatedDY * s8`. It clears the accumulated deltas, applies the invert-Y sign to the vertical value, and calls `player.turn(yawDelta, signedPitchDelta)` if the local player exists. Uncaptured or inactive callbacks clear the accumulated values and do not turn the player.

`Entity.turn` (1.20 and 1.20.1, `Entity.java:395–410`) casts each incoming delta to `float`, multiplies by `0.15F`, then calls virtual `setXRot(getXRot() + pitchDelta)` and `setYRot(getYRot() + yawDelta)`. It next calls virtual `setXRot(Mth.clamp(getXRot(), -90.0F, 90.0F))`, updates the old-rotation fields, clamps old pitch, and proceeds to the vehicle handling. No `LocalPlayer`, `Player`, or `LivingEntity` override of `setXRot` intervenes: the call resolves to `Entity.setXRot` (`Entity.java:3269–3279`), which stores finite values unchanged and discards non-finite values after logging. Thus pitch is first written unbounded, then read back and clamped to `[-90.0F, 90.0F]`; the old-pitch update separately adds the same float delta before its clamp. This order and numeric conversion are identical in both versions.

A reachable next movement uses an airborne, non-passenger local player with an enabled Elytra in the chest slot, no Levitation, no water/lava, and `abilities.flying == false`. A rising jump input can activate glide through `LocalPlayer.aiStep` (`LocalPlayer.java:648–745`): the Elytra and enabled checks precede `tryToStartFallFlying`; `Player.tryToStartFallFlying` (`Player.java:1576–1589`) additionally requires off-ground, not already fall-flying, out of water and no Levitation, and sets shared flag 7. `LocalPlayer.tick` invokes its superclass tick (`LocalPlayer.java:188–207`); `LivingEntity.tick` calls virtual `aiStep` (`LivingEntity.java:2237–2279`). After the local-player input handling calls `super.aiStep` (`LocalPlayer.java:801`), `LivingEntity.aiStep` updates fall-flying state and reaches the travel invocation (`LivingEntity.java:2559–2573`). `updateFallFlying` retains active state only while flag 7 is set, airborne, not a passenger, without Levitation, and still wearing an enabled Elytra (`LivingEntity.java:2610–2635`). With those gates satisfied, `Player.travel` (`Player.java:1445–1473`) takes its ordinary superclass route because abilities flight is false; `LivingEntity.travel` (`LivingEntity.java:2004–2135`) selects its fall-flying branch after the water/lava branches. That branch reads pitch into radians, uses the look vector and pitch in the glide math, sets velocity, and calls `move(MoverType.SELF, ...)` at line 2094. An active elytra tick therefore consumes the mouse-updated pitch on its first subsequent real flight move.
