# Source review: local-player passive vertical air integration, 1.21.5 to 1.21.6

## Bounded verdict

**No movement difference found in this bounded slice; no canonical finding draft.** For an ordinary local player in dry open air, not riding, flying, fall-flying, climbing, jumping, levitating, or slow-falling, the 1.21.5 to 1.21.6 source changes do not alter the post-deadzone Y request, ordinary air gravity/drag, resulting uncollided Y position/velocity, or common fall-distance accumulation/reset. The changed `LivingEntity.aiStep` travel gate is logically redundant for `LocalPlayer`, because both `Player.canSimulateMovement()` and `Player.isEffectiveAi()` have the same local-player predicate in both releases. The reworked `Entity.move` records movement differently, but in the bounded collision-free case it advances the same Y coordinate by the same resolved Y delta. This conclusion does not cover colliding movement, support/collision providers, effects, equipment, fluid movement, jumping, climbing, or gliding.

## Compared slices and trace

- **Local client tick and identity.** `LocalPlayer.tick()` calls `super.tick()` before its position-send path (1.21.5 `LocalPlayer.java:191-216`; 1.21.6 `:197-222`). `LocalPlayer.aiStep()` ends in `super.aiStep()` in both (`:830-834`); `LocalPlayer.isLocalPlayer()` returns true (1.21.5 `:347-350`; 1.21.6 `:341-344`). The outgoing packet threshold at `LocalPlayer.sendPosition()` is network reporting, outside this movement-state comparison.
- **Player simulation gates.** `Player.canSimulateMovement()` and `Player.isEffectiveAi()` both return `!level().isClientSide || isLocalPlayer()` in each release (1.21.5 `Player.java:1320-1328`; 1.21.6 `:1332-1340`). Therefore both predicates are true for this local player. In `LivingEntity.aiStep`, 1.21.5 calls `travel($$10)` when `canSimulateMovement()` (`:2763-2767`); 1.21.6 adds `&& isEffectiveAi()` (`:2815-2819`). `Player.isLocalClientAuthoritative()` delegates to `isLocalPlayer()` (1.21.5 `Player.java:1311-1314`; 1.21.6 `:1323-1326`); through `Entity.isLocalInstanceAuthoritative()` this makes local movement authoritative for the shared vertical-collision and fall-damage gates (1.21.5 `Entity.java:3162-3168`; 1.21.6 `:3335-3341`). Given the identical Player predicates and LocalPlayer identity above, this is behavior-equivalent for the assigned player.
- **Post-deadzone request.** `LivingEntity.aiStep` copies delta movement into `$$1/$$2/$$3`; for players it zeros only X/Z together when horizontal squared speed is `< 9.0E-6`, then independently zeros Y only when `Math.abs($$0.y) < 0.003`, and writes the result with `setDeltaMovement($$1,$$2,$$3)`. Those strict comparisons and ordering are unchanged (1.21.5 `LivingEntity.java:2685-2709`; 1.21.6 `:2737-2761`). With passive input (`yya == 0`) this state reaches the travel vector construction unchanged; LocalPlayer super-dispatch reaches this LivingEntity path.
- **Ordinary air travel.** `LivingEntity.travel()` chooses fluid travel only when in water/lava and affected by fluids and unable to stand on fluid, then fall-flying, else `travelInAir` (1.21.5 `LivingEntity.java:2213-2222`; 1.21.6 `:2245-2254`). For the assigned branch, `travelInAir` calls `handleRelativeFrictionAndCalculateMovement`, takes its `y`, applies levitation or effective gravity subject to the client/chunk gate, then applies either discard-friction or the vertical drag factor. These method bodies match in both versions (1.21.5 `LivingEntity.java:2204-2247`; 1.21.6 `:2236-2299`; exact `travelInAir` range 1.21.5 `:2224-2247`, 1.21.6 `:2276-2299`). With no levitation, a loaded chunk, and ordinary player attributes, gravity is `0.08` (`Attributes.GRAVITY`, 1.21.5 `Attributes.java:41-43`; 1.21.6 `:44-46`; inherited into player attributes by `LivingEntity.createLivingAttributes`, 1.21.5 `LivingEntity.java:305-317`, 1.21.6 `:317-334`). `getEffectiveGravity()` is unchanged; for a dry ordinary player without slow-falling it returns `getGravity()` (1.21.5 `LivingEntity.java:2203-2211`; 1.21.6 `:2235-2243`). With default `discardFriction == false`, ordinary air stores `($$4.y - 0.08) * 0.98`; `handleRelativeFrictionAndCalculateMovement` has no Y change absent a climbable response, and the latter is excluded (1.21.5 `LivingEntity.java:2394-2404`; 1.21.6 `:2446-2456`). These operations/order are identical.
- **Position and velocity.** `handleRelativeFrictionAndCalculateMovement` invokes `move(SELF, current delta movement)` before gravity/drag updates the stored velocity; therefore position advances by the post-deadzone current Y request, while the gravity/drag result is next-tick Y velocity. In no collision, the resolved delta equals the request. `Entity.move` in 1.21.5 builds a movement list by axis and sets its final position (`Entity.java:667-681`); 1.21.6 stores a single start/end movement and sets `start + resolved delta` (`:694-698`). For a collision-free Y-only delta, both write the same Y position, once-added by that delta. Remaining `move` collision, support and block callbacks are not compared.
- **Fall distance and vertical gates.** In both releases `Entity.move` applies the same squared-length acceptance gate (`> 1.0E-7 || requested.lengthSqr() - resolved.lengthSqr() < 1.0E-7`), optional fall-resetting ray check (`fallDistance != 0 && resolved.lengthSqr() >= 1.0`), and local-authority vertical-collision gate; vertical collision compares requested and resolved Y exactly and marks “below” only for requested Y `< 0.0` (1.21.5 `Entity.java:657-665, 685-704`; 1.21.6 `:684-692, 702-720`). `checkFallDamage` in both adds `-(float)resolvedY` to double `fallDistance` only when not in water and resolved Y is `< 0.0`, then on ground handles positive accumulated distance and resets it (1.21.5 `Entity.java:1274-1292`; 1.21.6 `:1336-1354`). `resetFallDistance()` is `fallDistance = 0.0` in both (1.21.5 `Entity.java:2512-2514`; 1.21.6 `:2680-2682`). No open-air landing/reset occurs in this slice. The `> -0.5 && fallDistance > 1.0` fall-distance cap is present in both, but only called from `updateFallFlying()`; 1.21.6 renamed it from `checkSlowFallDistance` to `checkFallDistanceAccumulation` (1.21.5 `Entity.java:2506-2514`, `LivingEntity.java:2815-2817`; 1.21.6 `Entity.java:2674-2682`, `LivingEntity.java:2871-2874`). That call is on the fall-flying branch and outside the assigned non-gliding path.

## Coverage boundary

Checked as paired terminal slices: local-player tick/dispatch and identity; Player simulation predicates; LivingEntity Y deadzone and travel dispatch; dry ordinary `travelInAir`, default gravity, velocity drag and move-before-update ordering; Entity position application, vertical collision threshold, fall-distance accumulation/ground reset, and fall-distance cap call reach. The only notable travel-gate change is redundant for LocalPlayer. No independent source-confirmed movement change in this bounded assignment. Collision resolution, support state and block-provider behavior remain unexamined by design; no pair-wide completeness claim is made.
