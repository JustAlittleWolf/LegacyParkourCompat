## Mirrored ordinary local-player setup (exact 1.8.9 source)

Reuse the accepted dry, airborne, awake ordinary local-player tick and prior-tick setup, with center Z `0.5`, feet Y `0.2`, `onGround=false`, `noClip=false`, and no other colliding shapes. Put the moving Stone block and its entity in loaded cell `(0,0,0)`, extending WEST. Set player center X to `1.0 + (double)(0.6F / 2.0F)`. The source float half-width is `0.30000001192092896`; `Entity.setPosition` subtracts that float half-width, so the player's `minX` is exactly `1.0`. On the first tick use neutral horizontal input; after that tick's local entity travel, its later block-entity tick advances `(progress,lastProgress)` from `(0,0)` to `(.5F,0F)`. On the second local-player tick set camera yaw to `0` and input `movementSideways=-1`, `movementForward=0`.

The exact 1.8.9 direction provider preserves this sign: `LocalClientPlayerEntity.serverTickAi` copies `input.movementSideways` to `sidewaysSpeed` (470–480); `LivingEntity.mobTick` multiplies it by `0.98F` and invokes `moveRelative` (1446–1451); the dry locally controlled branch calls `updateVelocity` then `move` (LivingEntity 1119–1165). `Entity.updateVelocity` (844–859) adds `sideways*cos(yaw)` to X and `sideways*sin(yaw)` to Z. At yaw zero, negative sideways input therefore produces `dx<0`, `dz=0` (positive `speedInAir` and zero prior X/Z velocity as in the accepted witness). This is the same ordinary local-player call path as the accepted EAST witness with only the sideways sign and mirrored contact point changed.

## Intervening push does not move the player

`World.tickEntities` processes regular entities before block entities (1159–1314). During the first tick's extending block-entity tick, `MovingBlockEntity.tick` advances to `progress=.5F,lastProgress=0F` and calls `moveEntities(.5F, .5625F)` (128–147). `moveEntities` converts extending progress to `.5F` and asks the moving-block shape helper for the entity push bounds (80–90). For a full-unit Stone shape and WEST offset `-1`, `MovingBlock.getCollisionShape(..., progress=.5F, facing=WEST)` adds `.5` to `minX`, leaving the push box X interval `[.5,1]` (162–193). The ordinary player's `minX==1` touches its `maxX==1`; `World.getEntities` reaches `WorldChunk.getEntities`, whose `entity.getShape().intersects(bounds)` call is strict (World 2134–2153; WorldChunk 710–721; Box 153–158). The player is consequently not returned or added to `movedEntities`, and the intervening push causes no displacement. This closes the precondition needed to keep exact contact through the next player phase.

## Second-tick zero-width collision and negative-X clip

During the next player move, the moved-block collision provider samples `getProgress(0.0F)` (MovingBlock 118–130; MovingBlockEntity 54–60), which is `lastProgress=0F`; extending maps it to shape-helper progress `1F`. For WEST, `facing.getOffsetX()<0`, so the helper computes `minX = 0 - (-1 * 1) = 1`, while `maxX` remains `1`. The Stone candidate is `[1,1] × [0,1] × [0,1]`.

The negative-X swept player query has `minX<1<maxX`, and its stated Y/Z intervals overlap the block. `World.getCollisions` visits cell `(0,0,0)` (891–922); `Block.addCollisions` appends the candidate when `shape.intersects(candidate)` succeeds, with no nonzero-width guard (339–344). `Box.intersects` accepts the plane strictly inside this positive-volume swept query (153–158).

`Entity.move` clips Y before X (439–453). For the Y test, the candidate box's strict horizontal-overlap guard fails at contact because the player `minX` equals candidate `maxX` (`1==1`), so the small airborne `dy<0` remains unchanged. The step-up condition is false because the player is airborne and the Y request remains unchanged. Then `Box.intersectX` takes its negative branch: `limit<0` and player `minX>=candidate.maxX` (`1>=1`), computes `candidate.maxX-player.minX=0`, and replaces the negative requested limit with zero because `0>limit` (93–108). Thus this reachable mirrored WEST local-player move clips `dx` to zero.
