## Source comparison

- `net/minecraft/world/entity/Entity.java`, 1.21.1 `setXRot` (lines 3363–3368): rejects non-finite input; otherwise stores `$$0` unchanged in `xRot`.
- Same file, 1.21.2 `setXRot` (3489–3494): same finite check; otherwise stores `Math.clamp($$0 % 360.0F, -90.0F, 90.0F)`. Thus finite out-of-range values are source-confirmedly normalized at the setter in 1.21.2; 1.21.1 preserves them at this operation. Example: input `360.0F` stores `360.0F` in 1.21.1 and `0.0F` in 1.21.2; `270.0F` stores 270 versus 90. This describes the setter arithmetic, not by itself an ordinarily reachable player state.
- `Entity.turn` is otherwise identical: 1.21.1 lines 401–413; 1.21.2 lines 412–424. It computes pitch delta as `(float)deltaY * 0.15F`, calls `setXRot(current + delta)`, then calls `setXRot(Mth.clamp(getXRot(), -90.0F, 90.0F))`; it separately adds the pitch delta to `xRotO` and clamps `xRotO` to the same interval. The second setter call does not erase the new modulo effect: for pitch 0 and finite positive pitch delta 360, old code ends with `xRot=90`, new code ends with `xRot=0`; both end with `xRotO=90`.
- Ordinary input reaches `turn`: `MouseHandler.handleAccumulatedMovement` invokes `turnPlayer` when the mouse is grabbed and player exists (1.21.1 lines 239–248; 1.21.2 lines 281–294); `turnPlayer` derives pitch delta from accumulated mouse Y, sensitivity and smooth-camera state, applies invert-Y, then calls `player.turn` (1.21.1 lines 255–286; 1.21.2 lines 297–329). These paths impose no pitch-delta cap before `turn`. Therefore a sufficiently large but finite ordinary accumulated mouse delta can cross the 360-degree modulo boundary during one `turn`; this is a local input reachability fact, not a custom packet or injected flag. For example, from zero pitch, a delta of 360 yields the 90-versus-0 result above. A 1.21.2 next-tick elytra movement read uses `getXRot()` for pitch radians and the look vector in its fall-flying movement calculation (`LivingEntity.updateFallFlyingMovement`, lines 2278–2308); consequently this reachable turn can change the movement input from downward pitch (90 degrees) to level pitch (0 degrees). The trajectory consequence is an inference from those formulas.

## Vanilla map teleport and position/rotation packets

- Both versions’ `server/commands/TeleportCommand.java` normalize requested pitch with `Mth.wrapDegrees` before calling entity teleport: 1.21.1 lines 275–277; 1.21.2 lines 260–267 (which first resolves relative rotation). Both `Entity.teleportTo(ServerLevel, ...)` methods then clamp the pitch argument to `[-90,90]`: 1.21.1 `Entity.java` lines 2693–2712; 1.21.2 lines 2868–2871. This covers the vanilla command-block/map `/tp` route, including finite out-of-range angle arguments; the server-created resulting player pitch is in range before the client receives the teleport.
- The ordinary clientbound player position/rotation packet path calls the setter after resolving relative angles: 1.21.1 `ClientPacketListener.handleMovePlayer` lines 620–680; 1.21.2 `handleMovePlayer` / `setValuesFromPositionPacket` lines 706–735. The 1.21.2 rotation-only handler also calls `setXRot` directly (738–744). These establish where server values enter the local entity; they do not establish a vanilla map path that supplies a finite pitch outside the command/teleport clamps. A command angle such as 360 is wrapped by the command first, and the server teleport method clamps its final pitch. Thus normal vanilla map teleport/position-and-look use does not expose this setter delta as an out-of-range pitch; the confirmed reachable witness here is the uncapped local mouse-turn path.

## Result

Confirmed setter arithmetic change: preserve finite pitch verbatim → modulo 360 then clamp to `[-90,90]`. Ordinary mouse turning can reach the changed result because it has no pre-turn delta bound and its post-turn clamp occurs only after the setter. Vanilla map teleport command arguments are wrapped and server teleport pitch is clamped before the client packet path, so they are not a valid out-of-range witness. No broad server-policy conclusion is made.
