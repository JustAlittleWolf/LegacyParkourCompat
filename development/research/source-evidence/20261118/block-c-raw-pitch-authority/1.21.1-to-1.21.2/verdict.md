## Frozen trace and map

- **Mouse sample accumulation, both:** `MouseHandler.onMove` accumulates `accumulatedDX += newX - xpos` and `accumulatedDY += newY - ypos` while the window is active, with no clamp/cap. `handleAccumulatedMovement` calls `turnPlayer(elapsed)` iff the window is active, mouse is grabbed, and player is non-null, then resets accumulated deltas. 1.21.1 lines 207–222, 225–253; 1.21.2 lines 225–240, 243–295.
- **Sensitivity and branches, both:** `s = options.sensitivity().get() * 0.6F + 0.2F`; `s3 = s * s * s`; `scale = s3 * 8.0`. Smooth-camera branch uses `SmoothDouble.getNewDeltaValue(accumulatedD*scale, elapsed*scale)`. Else first-person while scoping uses `accumulatedD*s3`; otherwise it uses `accumulatedD*scale`. Y inversion is applied to pitch after branch selection; then ordinary code calls `player.turn(yaw, pitch*invert)`. No arithmetic, clamp, or cap difference appears in this input path. 1.21.1 lines 255–286; 1.21.2 lines 297–328.
- **Turn operation, both:** `float pitchDelta = (float)dy * 0.15F; float yawDelta = (float)dx * 0.15F; setXRot(getXRot()+pitchDelta); setYRot(getYRot()+yawDelta); setXRot(Mth.clamp(getXRot(), -90.0F, 90.0F)); xRotO += pitchDelta; yRotO += yawDelta; xRotO = Mth.clamp(xRotO,-90,90);` followed by passenger callback if present. Exact ordering is preserved in 1.21.1 lines 401–413 and 1.21.2 lines 412–424.
- **Setter difference:** 1.21.1 `setXRot` rejects non-finite input via the same `Float.isFinite` gate and otherwise directly assigns `this.xRot = value` (Entity lines 3359–3369). 1.21.2 retains that gate but stores `Math.clamp(value % 360.0F, -90.0F, 90.0F)` (Entity lines 3485–3495). Consequently, the second `setXRot(clamp(...))` in `turn` cannot restore the old outcome: the first setter has already reduced pitch modulo 360 in 1.21.2. Java float remainder is signed; it is not an absolute-angle clamp.
- **Lawful reachability / counterevidence:** No mouse-delta cap exists in the reviewed callback/accumulation/turn path. With smooth camera off, first-person scoping off, sensitivity at 1, invert-Y off, and a lawful 600-pixel downward cursor movement while grabbed, the branch produces `dy = 600 * (0.8^3 * 8) = 2457.6`; `Entity.turn` then computes float `pitchDelta = (float)2457.6 * 0.15F = 368.64F` (subject to normal binary32 rounding). From initial pitch 0, 1.21.1 stores 368.64 then clamps final pitch to +90; 1.21.2's first setter stores `368.64F % 360.0F ≈ 8.64F`, and the second clamp leaves that value. Thus the behavior is reachable via ordinary local input and does not rely on packets, modified servers, or direct setter use.
- **Movement read / consequence:** The pitch result is read by player fall-flying movement. In 1.21.1, `LivingEntity`'s `isFallFlying()` branch obtains `getLookAngle()` and `getXRot()` and uses pitch in cosine/sine velocity updates (`LivingEntity.java` lines 2151–2169). In 1.21.2 the same movement is extracted to `updateFallFlyingMovement`, where `getLookAngle()` and `getXRot()` feed velocity terms (lines 2279–2295). A player already fall-flying when the turn is applied can therefore receive different movement velocity. This does not claim pitch otherwise changes ordinary ground input acceleration; `Entity` ground input in both versions uses `getYRot()`.
- **Other inspected movement-relevant pitch reads:** `Player.getRopeHoldPosition` uses interpolated pitch for fall-flying/autospin and visual swimming offsets, structurally present in both (`Player.java` 1.21.1 lines 2049–2076; 1.21.2 lines 2015–2040). These support pitch observability but are not needed for the primary movement claim.

## Verdict

Source bytes show a real behavioral change at the `Entity.setXRot` authority: 1.21.1 stores finite pitch directly, while 1.21.2 normalizes modulo 360 then clamps. `turn` keeps the same double-to-float cast, `0.15F` multiplication, second clamp call, order, old-angle accumulation, and old-angle clamp; MouseHandler sensitivity/frame accumulation branches retain the same math and have no input cap. Ordinary mouse input can reach a pitch delta over 360 degrees, producing a distinct final pitch and, during fall-flying movement, a distinct velocity result. Difference is source-confirmed for the displayed content; the 1.21.1 tree's absent provenance manifest is the only source-identity gap recorded here.

**Mouse-turn claim: accepted, scoped to the ordinary local input path.** The frozen trace independently confirms active-window cursor differences accumulate without a pitch-delta cap, the normal turn is gated only by active/grabbed mouse and a local player, and the sensitivity/smooth-camera/scoping/invert branches call `Entity.turn` with unchanged cast and operation order in both versions. **Vanilla `/tp` no-witness claim: not accepted as written; a narrow counterexample exists, with an attribution qualifier.** The report follows the base `Entity.teleportTo` pitch clamp but omits dynamic dispatch to `ServerPlayer`:

- In 1.21.1, `TeleportCommand.performTeleport` wraps requested pitch with `Mth.wrapDegrees` (TeleportCommand lines 275–277); `Mth.wrapDegrees(200.0F)` returns `-160.0F` (Mth lines 190–200). `RotationArgument.parse` accepts the pitch as a parsed `WorldCoordinate` without an angle-range clamp (RotationArgument `parse`). The ordinary absolute `/tp ... <yaw> 200` form therefore supplies finite pitch `-160.0F`.
- The command invokes `Entity.teleportTo` virtually. On a same-dimension player, 1.21.1 dispatches to `ServerPlayer.teleportTo` (ServerPlayer lines 1409–1425), which passes that pitch directly to `ServerGamePacketListenerImpl.teleport` (line 1419), bypassing the base `Entity.teleportTo` clamp. The listener calls `player.absMoveTo` and then constructs `ClientboundPlayerPositionPacket` with the unmodified absolute pitch argument when rotation is not relative (lines 993–1006). `absMoveTo` clamps the server's own stored rotation to -90 (Entity lines 1374–1383), but that does not rewrite the packet argument. On the client, `ClientPacketListener.handleMovePlayer` applies the packet pitch directly through `setXRot` (lines 671–679); 1.21.1's setter stores finite `-160.0F` unchanged. This is an exact vanilla command-to-client setter path, not a crafted packet.
- In 1.21.2, `ServerPlayer.teleportTo` calls `super.teleportTo` (ServerPlayer lines 1603–1618). The base `Entity.teleportTo` clamps pitch to `[-90,90]` before building the `TeleportTransition` (Entity lines 2868–2871); the `ServerPlayer.teleport` path and network listener send that transition pitch. For the same 200-degree command argument the client receives -90, not -160. The 1.21.2 client packet handler then sets the already-bounded pitch.

So the author report's sentence that the base teleport methods clamp both player paths is false for 1.21.1 due to the `ServerPlayer` override, and the blanket claim that vanilla map `/tp` cannot expose out-of-range pitch to the client setter is contradicted by this source path. Qualifier: the 1.21.1 versus 1.21.2 end-to-end `/tp` difference also includes the server-side `ServerPlayer`/teleport-path change; do not attribute that counterexample solely to the client `Entity.setXRot` change or treat it as the clean isolated movement witness. The uncapped ordinary mouse path remains the clean client-side setter witness. This source review does not establish how a particular map invokes `/tp`, server configuration/permissions, or runtime parity.
