## Accepted operation and limits

The C adjacent records cover the direct `Entity.turn(double,double)` pitch path from 1.17 through 1.19.4. They repeatedly confirm that the finite first `setXRot` stores the raw float sum, then `turn` writes yaw and clamps current pitch to `[-90.0F, 90.0F]`; the old-pitch accumulator is updated and clamped separately. The 1.17 arithmetic is float cast, float `0.15F` multiplication, and float addition. C's 1.16.5→1.17 record expressly identifies a separate in-range arithmetic change from the older double-width computation. That earlier arithmetic is outside the requested range and is a reason to keep the new profile boundary at 1.17 rather than infer a pre-1.17 claim.

A's five adjacent dispositions accept the bounded `Entity.turn` setter/clamp operation through exact 1.20.4. In particular, the 1.19.4→1.20 audit accepts the setter/clamp slice even though it rejects broad Elytra movement-state equivalence because of a separate Slow Falling fall-distance reset. The 1.20.2→1.20.3 record likewise identifies `checkSlowFallDistance` as a separate operation. Keep that fall-distance behavior in its own hook and resolution; do not merge it into pitch saturation.

The existing exact C 1.20.4→1.20.5 artifact is a **mouse callback batching** difference: .4 turns per callback and .5 applies accumulated input later. Its independent verdict explicitly says `Entity.turn`, the finite raw setter and its clamp order are unchanged. The archive states callback scheduling is excluded input-device plumbing and that direct `Entity.turn` pitch response is independent. Do not implement or gate the batching result as part of this hook. The local standalone C report at `c-raw-pitch-setter-1204-1205-source/report.md` has SHA-256 `45436c6764dc4abcf0ba333d80dc2110de686400944757fb73ca7681605120de`; the signed archive copy confirms its accepted report binding under the mouse-batching verdict, not an independent direct-setter difference.

## Minimal resolver contract

Keep the one existing `EntityTurnPitchHook` operation and mixin call site. The product mixin already modifies only `Entity.turn(DD)V`'s first `setXRot(F)V` argument (ordinal 0), only for `LocalPlayer`, and falls back unchanged if no hook resolves. Keep those gates and the native fallback. The existing clamp implementation is correct for the accepted contract: return non-finite inputs unchanged; return every finite float within inclusive `[-90.0F, 90.0F]` unchanged (preserving exact bits, including signed zero); map only finite values below/above the bounds to the respective bound. Do not alter `Entity.turn` casts, `0.15F` multiplication, addition, yaw order, final clamp, or old-pitch accumulator.

To make resolution include the full requested range without breaking other accepted ranges, add a minimal `V1_17` clamp provider with the existing finite-only transform, retain the existing `V1_21` clamp provider for the later profile groups, and move the no-op native fence from `V1_20_2` to `V1_16_2` (the enum group for 1.16.2–1.16.5). The resolver selects changes annotated at the selected version or later, so a lone `V1_17` provider would not resolve for selected profiles `V1_17_1` through `V1_20_4`; the retained `V1_21` provider covers those profiles. Remove the current `V1_20_2` fence. Then `V1_16_2` keeps earlier profiles native, `V1_17` clamps the exact 1.17 profile, `V1_21` clamps selected profiles 1.17.1 through 1.21.1, and 1.21.2+ uses native fallback. Keep each class in its matching `change/v<version>/` package and update source comments to cite the accepted 1.17-era operation trace, the exact 1.20.4 endpoint records, and the 26.2 setter contrast/cutoff. Do not add exact-profile conditionals or a mouse-handler hook.

The `V1_16_2` no-op fence deliberately limits this task to the requested contract; it makes no parity assertion for older profiles. The lower boundary's in-range arithmetic difference and the direct-field-write structure before 1.17 remain outside the new acceptance. Two clamp providers are needed only because the resolver is forward-looking: the new `V1_17` provider handles that selected profile, while the existing `V1_21` provider remains the nearest eligible entry for later selected profiles through 1.21.1. Both providers keep the identical accepted transform without cross-release inheritance.

## Resolver recheck addendum (supersedes the resolver plan above)

The actual `ChangeResolver` and `ParkourVersion` enum confirm the smaller plan: **do not add a V1_17 clamp provider.** `ChangeResolver.resolve` returns an empty map for `CURRENT`; otherwise it filters to provider versions `>= selected` and chooses the lowest eligible ordinal. The existing `EntityTurnPitchClamp @MovementChange(V1_21)` is therefore already the closest eligible pitch provider for selected 1.17 through 1.20.4 once the intervening `V1_20_2` native fence is moved earlier.

Exact relevant aliases in product commit `9ec57a6256b39ea8a290b298322d827d8b3002de`: `V1_16` = 1.16/.1; `V1_16_2` = 1.16.2/.3/.4/.5; separate `V1_17` and `V1_17_1`; `V1_18` = 1.18/.1; `V1_18_2`; `V1_20` = 1.20/.1; `V1_20_2` = 1.20.2/.3/.4; `V1_20_5` = .5/.6; `V1_21` = 1.21/.1; `V1_21_2` = 1.21.2/.3; then 1.21.4 onward; `V26_1` = 26.1/.1/.2; `CURRENT` is the 26.2 running game.
