# Independent verdict: authoritative X pitch setter, 1.21.1 → 26.2

## Verdict

**Confirmed, with a reachable active-fall-flying movement consequence.** In 1.21.1 Mojmap, `Entity.setXRot(float)` stores every finite argument verbatim. In 26.2 unobfuscated source it first applies Java float remainder by `360.0F`, then clamps to `[-90, 90]`. `Entity.turn` itself is otherwise the same relevant sequence: cast mouse `yo` to float, multiply by `0.15F`, call `setXRot(current + delta)`, update yaw, call `setXRot(clamp(current, -90, 90))`, then update/clamp old pitch. Thus the second call cannot undo 26.2's earlier modulo. Ordinary small inputs and normal pitch values remain equal; sufficiently large lawful accumulated mouse input gives a different authoritative pitch.

The mouse path has no pitch-delta cap: cursor callback deltas are accumulated, `turnPlayer` scales the accumulated Y delta, and calls `player.turn(...)`. At sensitivity slider maximum, `ss = sensitivity * 0.6F + 0.2F`, `sensitivityMod = ss³`, and `sens = sensitivityMod * 8`; unsmoothed, non-scoped input uses `yo = accumulatedDY * sens`. For a reproducible arithmetic witness, start at `xRot = 0`, use maximum sensitivity, no smooth camera, not scoping, non-inverted Y, and one accumulated downward delta of 640 cursor pixels. Then `yo` is about 2621.44, and Entity's float cast and `* 0.15F` produce a value about 393.216 degrees. 1.21.1's two setters leave final `getXRot() == 90.0F`; 26.2's first setter reduces that delta modulo 360 to about 33.216 degrees, and the second clamp leaves `getXRot()` about `33.216F`. Exact decimal low bits follow the source's float operations; the inequality and interval do not depend on them. Cursor deltas are summed without a clamp in both handlers, so this is a lawful input path, not a direct setter injection.

This pitch is consumed by real movement while the player is already fall-flying. 1.21.1 `LivingEntity.travel` enters its `isFallFlying()` branch, obtains `getLookAngle()` and current `getXRot()`, and uses both to derive lift and velocity before `setDeltaMovement` and `move`. 26.2 has the corresponding branch through `updateFallFlyingMovement(movement)`, which reads the same live `getLookAngle()` and `getXRot()` before moving. `getLookAngle()` calls `calculateViewVector(getXRot(), getYRot())`, with pitch directly entering its trigonometric components. Holding yaw at zero, a 90° pitch points approximately `(0, -1, 0)`, while a 33.216° pitch points approximately `(0, -0.548, 0.836)`. The next fall-flying movement therefore receives distinct look and lean values and takes distinct movement math. This does not claim ordinary grounded travel uses pitch: its non-fall-flying branch is not this consumer. Rendering is not used as evidence.

The direct setter also has a difference for externally supplied finite angles outside the conventional pitch range, but the mouse-turn witness above establishes the relevant reachable path without relying on such a setter call. Non-finite setter input is discarded in both versions. In 26.2, `% 360.0F` is Java remainder (sign-preserving), then `Math.clamp`; it is not a wrap-to-[-180,180] operation. `turn`'s post-set clamp is still present in both releases.

**Acceptance with a numerical qualification:** The author report correctly establishes the setter/turn order, default sensitivity value and type, callback accumulation and reset, grabbed-mouse/player caller gate, default non-inverted Y, immediate authoritative `getXRot()` difference, `xRotO` update and later `LivingEntity.tick` synchronization, and the live pitch reads in the two fall-flying movement paths. Its source-level finite mouse-callback witness is admissible as a conditional callback sequence; it does not prove a particular device or OS will emit that coordinate displacement in one handling interval, and it is not runtime evidence.

One exact arithmetic statement in that report needs correction. `Options.sensitivity` is `OptionInstance<Double>` with default `0.5`. Java therefore evaluates `0.5 * 0.6F + 0.2F` in double precision after promoting the binary32 constants, yielding `ss = 0.5000000149011612`, not exactly `0.5`. At default sensitivity this gives `sens ≈ 1.0000000894069698`; `accumulatedDY = 4800` yields `yo ≈ 4800.000429153455`, cast to float `4800.00048828125`, then the float multiplication by `0.15F` yields `xDelta = 720.0001220703125`. The final 1.21.1 pitch is still exactly `90.0F`; the 26.2 setter's remainder is `0.0001220703125F`, so its final pitch is that small positive value, not exactly `0.0F`. The report's stated `yo = 4800`, `xDelta = 720.0F`, and final 26.2 pitch `0.0F` are thus mathematically inexact; correcting them does not change the claimed authoritative pitch divergence or the movement consequence. The recomputation follows the source's declared types and Java float operations; it is arithmetic analysis, not a runtime measurement.
