## Bounded paired findings and dispositions

1. **End Portal contact scan.** In 1.21.1 the post-move entity check enumerates only cells overlapped by the player's final AABB (`world/entity/Entity.java:1001-1025`), then EndPortalBlock itself requires intersection with its half-height portal shape and `canUsePortal(false)` (`world/level/block/EndPortalBlock.java:53-63`). In 1.21.2 player block effects retain and traverse each from/to movement segment, test the candidate block's entity-inside collision shape against that path, then call `entityInside` (`world/entity/LivingEntity.java:2774-2776`; `world/entity/Entity.java:736-751,1038-1083`). EndPortalBlock provides the same half-height shape through `getEntityInsideCollisionShape`; its callback retains `canUsePortal(false)` and sets portal process state without a duplicate overlap check (`EndPortalBlock.java:53-65`). This is a confirmed swept-contact source difference. Client-side End Portal contact can set `portalProcess`, but does not itself write client position/velocity or cause an End portal local effect: the End portal's local transition is `NONE`, LocalPlayer only presents the confusion transition, and `Entity.handlePortal` performs actual transition only on `ServerLevel`. The changed overlap pass can also affect the server-side contact producer. Therefore this is retained as a bounded contact/authority dependency, not a standalone local movement finding.
2. **End Gateway contact scan.** The same Entity contact-pass change can now consider a segment crossing the gateway's full *entity-inside shape* (BlockBehaviour's default is `Shapes.block()` at 1.21.2 `world/level/block/state/BlockBehaviour.java:353-355`). Gateway's own gate sequence remains `canUsePortal(false)`, logical server, matching gateway block entity, not cooling down; it calls `setAsInsidePortal` and starts cooldown (`EndGatewayBlock.java:87-90` in 1.21.1, `:89-93` in 1.21.2). Since the logical-server condition is unchanged, this does not create a client-local Gateway process. Retain only as a server contact/transition dependency. “Full entity-inside shape” is the accurate scope; this does not claim physical collision shape.
3. **Corrected same-portal entry-position behavior.** In 1.21.1 `Entity.setAsInsidePortal` updates the entry position for every callback on a processor with the same Portal object (`world/entity/Entity.java:2121-2131`). In 1.21.2 it creates a new processor when the portal differs; for the same portal it updates only when `insidePortalThisTick` is false (`Entity.java:2214-2224`). EndGatewayBlock passes itself as the portal key (`EndGatewayBlock.java:87-90 / :89-93`), and `PortalProcessor.isSamePortal` compares that key by reference (`PortalProcessor.java:68-69`). Thus, on the server, if one ordinary-player contact pass calls back for two distinct, eligible End Gateway block positions of the same registered EndGatewayBlock instance, the old processor stores the last callback's position and the new processor stores the first. This is a within-one-pass, callback-order-dependent claim, not a claim that arbitrary distant gateways are simultaneous. `PortalProcessor.getPortalDestination` forwards that stored position (`PortalProcessor.java:32-33`); `EndGatewayBlock.getPortalDestination` retrieves the block entity at that position (`EndGatewayBlock.java:96-104 / :98-112`), and `TheEndGatewayBlockEntity.getPortalPosition` resolves that entity's exit (`TheEndGatewayBlockEntity.java:133-148`). The chosen exit can therefore differ. End Portal destination ignores the entry position. This is a server-selected destination dependency, not a client contact-physics hook.
4. **Portal execution authority.** `Entity.handlePortal` processes the transition only while the entity level is `ServerLevel` in both versions (`Entity.java:2134-2153 / :2227-2249`). End Portal's client-local process has no movement write; End Gateway doesn't make a client-local process due its `!level.isClientSide` gate. The block-specific transition plus ServerPlayer/connection packet path is needed to understand where final player movement state comes from, as detailed below.

## Reachable portal packet sequence and equal-input comparison

### End Portal: dimension-changing route

A normal player contacts an End Portal in the Overworld, has an eligible server `portalProcess`, and completes the server portal timer. `EndPortalBlock.getPortalDestination` selects `Level.END` as the new level. This is a dimension change, so both ServerPlayer versions send `ClientboundRespawnPacket(createCommonSpawnInfo(newLevel), (byte)3)` before the clientbound position correction (`ServerPlayer.java:840-888` in 1.21.1; `:1029-1079` in 1.21.2). The `ClientboundRespawnPacket` type and `shouldKeep` implementation are byte-for-byte identical in the two releases; byte 3 contains `KEEP_ENTITY_DATA` (2), so the client takes the keep-data branch under the same raw respawn input.

- 1.21.1 `ClientPacketListener.handleRespawn` creates a replacement LocalPlayer and, under keep-entity-data, copies non-default entity data only; it does not copy the previous LocalPlayer's delta movement (`ClientPacketListener.java:1076-1151`). Then old ServerPlayer's dimension path calls the position-only `connection.teleport(x,y,z,yRot,xRot)` overload. `ServerGamePacketListenerImpl` delegates to an empty relative-argument set and emits an absolute player-position packet (`ServerGamePacketListenerImpl.java:989-1006`). The old client position handler sets a delta component to zero when its corresponding position-relative flag is absent (`ClientPacketListener.java:620-695`). End Portal's 1.21.1 transition carries current entity delta, but this ServerPlayer player-transfer/packet path does not transmit it as a velocity operand.
- 1.21.2 `ClientPacketListener.handleRespawn`, under the same `dataToKeep=3` input, copies the previous LocalPlayer's delta movement to the replacement player (`ClientPacketListener.java:1132-1202`). End Portal's Overworld-to-End transition uses `Vec3.ZERO` with `Relative.DELTA` (`EndPortalBlock.java:69-99`). ServerPlayer forwards the transition relatives to the connection after respawn; the packet contains the zero delta operand and relative-delta flags (`ServerPlayer.java:1029-1079`; `ServerGamePacketListenerImpl.java:1007-1019`). Client `setValuesFromPositionPacket` applies `PositionMoveRotation.calculateAbsolute`; relative delta computes current delta plus packet delta, so zero preserves the copied velocity (`ClientPacketListener.java:706-734`; `PositionMoveRotation.java:37-62`).

The actual sequence therefore preserves nonzero local player velocity in 1.21.2 and clears it in 1.21.1. The result has two sources: (a) a changed client operation under **identical raw respawn packet flags**—the new respawn handler copies velocity when bit 2 is set while the old handler does not—and (b) changed server-carried relative-delta operands/flags on the following position packet. The client position receiver's output is instruction-dependent; given equivalent movement operands and relative-delta instructions, the difference is not located in its generic arithmetic. The client respawn-copy operation is independently describable and is drafted separately below.

The exact server packet sequence is reachable from the End Portal path; the server's newer End Portal transition sets relative delta, while the old player transfer path ignores transition velocity. This finding addresses client movement state writes from those authoritative packets; it does not emulate server portal eligibility or physics.

### End Gateway: same-level route

EndGatewayBlock returns a transition to the same ServerLevel. In 1.21.1 its transition includes current player delta, but ServerPlayer's same-dimension path sends position and rotation through the position-only connection overload, producing no relative args. The client therefore zeroes velocity on the incoming position update. In 1.21.2 the ordinary-player Gateway transition sends zero delta with `Relative.DELTA | Relative.ROTATION`; ServerPlayer uses the same-level teleport overload that forwards those relatives, and the client adds zero to its existing delta. This is a reachable local-player velocity difference, but the protocol-level difference lies in server-produced transition operands/relative flags. The End Gateway client position receiver has no independent operation delta under equivalent operands/flags, and it receives no respawn packet. Accordingly no separate Gateway client receiver finding is drafted here. `ThrownEnderpearl`'s distinct branch is excluded.

## New independent client movement finding

Draft at `development/research/findings/1.21.1--1.21.2/end-portal-respawn-velocity-preservation.md`. It is scoped to the client `handleRespawn` movement-state operation. Under an identical `ClientboundRespawnPacket` with `dataToKeep=3` and a reachable successful Overworld-to-End End Portal transfer, 1.21.2 copies the old LocalPlayer's delta to the replacement; 1.21.1 does not. The incoming position packet later reinforces the distinct end state through different producer relative flags, but those flags are identified as a separate server dependency, not attributed to the client respawn-copy claim.

## Remaining boundaries

- No finding claims End Portal client-local pending state itself moves the player.
- End Gateway swept contact and first-vs-last entry position are server producer dependencies; no server-side historical movement hook is claimed.
- Gateway's final velocity difference is packet-producer-dependent; no distinct Gateway client receiver finding is claimed.
- This bounded portal slice does not establish complete player-tick coverage, full-pair freeze, independent acceptance, implementation, or runtime parity. Intermediate release cutover is unknown within 1.21.1–1.21.2.
