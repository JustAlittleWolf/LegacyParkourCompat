## Independent coverage and traced order

The ordinary local-player path examined was: `LivingEntity.travel` → client-controlled `applyEffectsFromBlocks` → entity block-contact scan → vanilla block-state `entityInside` callback → `Entity.setAsInsidePortal` / `PortalProcessor` state → server-only `Entity.handlePortal` → block-specific transition destination → server teleport and clientbound player-position update. End Gateway block-entity cooldown/exit-position dependencies were read to settle the gateway destination consumer.

Paired slices and results:

1. **Contact scan and End Portal collision gate.** In 1.21.1, `Entity.move` calls `tryCheckInsideBlocks` after resolving the requested move (Entity.java:600–705), and `checkInsideBlocks` enumerates only the current bounding box then calls `BlockState.entityInside` (Entity.java:1001–1025). `EndPortalBlock.entityInside` separately intersects the entity AABB translated to block-local coordinates with the portal block shape and checks `canUsePortal(false)` (EndPortalBlock.java:52–62). In 1.21.2, controlled local players run `applyEffectsFromBlocks` after travel (LivingEntity.java:2774–2776); this records the movement segment and calls `checkInsideBlocks` (Entity.java:736–751). That pass traverses blocks along each movement segment, uses each block's entity-inside collision shape, and tests non-full shapes against the traversed path before calling `entityInside` (Entity.java:1038–1083). `EndPortalBlock` supplies its portal shape through `getEntityInsideCollisionShape` (EndPortalBlock.java:52–65), and its callback now checks `canUsePortal(false)` without a second overlap predicate.
2. **Gateway contact and cooldown gate.** `EndGatewayBlock.entityInside` keeps the same eligibility order in both releases: `canUsePortal(false)`, server-side only, gateway block entity present, not cooling down; it then marks portal contact and triggers cooldown (1.21.1 EndGatewayBlock.java:86–92; 1.21.2:89–94). The changed Entity contact pass is the upstream difference in which block positions can reach this callback.
3. **Portal processor.** Timer increment, per-tick flag clearing, decay by four, expiration, transition-time check, and portal identity test are unchanged (`PortalProcessor.java:9–71` on both sides). The `setAsInsidePortal` update rule is not unchanged: see finding 2 below.
4. **Client pending state and execution authority.** End Portal's callback can create/update `portalProcess` on the client as well as the server, except that an End-dimension ServerPlayer without seen credits is sent to credits instead (1.21.1 EndPortalBlock.java:53–60; 1.21.2:58–65). End Gateway contact intentionally creates state only server-side. `LocalPlayer.aiStep` still runs portal cooldown and local-transition handling in both versions (1.21.1 LocalPlayer.java:643–652; 1.21.2:637–646). `Entity.handlePortal` is gated on `level() instanceof ServerLevel` in both; the local processor is not a client-side teleport writer. For End Portal/Gateway the ordinary local transition is `NONE`; local code does not set player position or velocity from contact.
5. **Transition and inbound movement writes.** The server runs the portal processor and transition (`Entity.handlePortal`, 1.21.1 Entity.java:2134–2153; 1.21.2:2227–2249). For players, the server uses `ServerPlayer.changeDimension` in 1.21.1 (ServerPlayer.java:840–888), which calls `connection.teleport` without relative arguments. That emits an absolute position/rotation packet (ServerGamePacketListenerImpl.java:989–1006); the client handler sets delta components to zero when delta is not relative (ClientPacketListener.java:620–695). In 1.21.2 `ServerPlayer.teleport(TeleportTransition)` passes transition relatives to the connection (ServerPlayer.java:1028–1079); the connection resolves them into player state and includes them in the packet (ServerGamePacketListenerImpl.java:1007–1019); the client resolves the packet against current state, including delta, in `setValuesFromPositionPacket` (ClientPacketListener.java:706–734). These are server-owned portal transitions with client movement-state writes, distinct from historical movement simulation.

## Separate verdicts

### Finding 1 — End Portal contact now uses movement-path shape eligibility

**Verdict: source-confirmed behavior difference, reachable for a controlled local player.** The 1.21.1 callback runs only for a final-box candidate and performs an explicit portal-shape overlap test inside `entityInside`. The 1.21.2 player block pass covers block positions traversed from movement `from` to `to`; the End Portal shape is tested against that movement path before callback. A player whose movement segment intersects the End Portal shape but whose final box no longer overlaps it can therefore seed portal state in 1.21.2 where the old final-box scan would not. Conversely, swept candidates that do not intersect the portal shape are filtered before callback. The callback retains the `canUsePortal(false)` eligibility predicate and the End credits branch. No exact intermediate patch boundary is established by this endpoint pair.

### Finding 2 — repeated same-tick contact preserves the first entry position

**Verdict: source-confirmed state difference; consequential for End Gateway selection when one movement pass contacts multiple gateway blocks.** In 1.21.1, `Entity.setAsInsidePortal` updates `entryPosition` and marks the processor inside on every same-portal callback (Entity.java:2121–2131). In 1.21.2, same-portal updates occur only if `insidePortalThisTick` is false; after the first callback in the tick, later contacts leave the first entry position intact (Entity.java:2214–2224). End Gateway destination resolution looks up the block entity at that stored entry position and asks it for its own portal position (EndGatewayBlock.java:96–104 / 98–112; `TheEndGatewayBlockEntity.getPortalPosition`, 1.21.1 and 1.21.2:133–148). Thus, when the player contacts two End Gateway blocks sharing the same `EndGatewayBlock` instance in one tick, 1.21.1 retains the last callback's position while 1.21.2 retains the first; a different gateway block entity can select a different exit. End Portal destination does not use its entry block position, so this state difference has no corresponding End Portal destination consequence. The processor timer and same-portal identity behavior themselves are unchanged.

### Direct transition movement — player velocity preservation changed

**Verdict: source-confirmed direct movement-state difference for an ordinary local player.** On the 1.21.1 server-player path, `ServerPlayer.changeDimension` calls `connection.teleport` without relative arguments. Its clientbound packet has no relative-delta flags, and `ClientPacketListener.handleMovePlayer` therefore sets the received player delta components to zero. This discards the current client velocity on an End-bound End Portal transition and on an End Gateway transition, even though those block destination methods supply the current velocity in their `DimensionTransition`. In 1.21.2 the End-bound End Portal transition supplies zero delta with `Relative.DELTA`; the non-ender-pearl End Gateway transition supplies zero delta with `Relative.DELTA | Relative.ROTATION`. `PositionMoveRotation.calculateAbsolute` adds each zero delta component to the current delta, and the server connection/client packet listener both preserve that resolved value. Thus player velocity now survives these transitions. The End-bound portal yaw remains west and the current pitch is retained; Gateway rotation remains current. The End-to-Overworld End Portal respawn/spawn-return path is not signed off here. Ender-pearl velocity differs too, but a projectile is outside this ordinary-player assignment. These are server-authored portal responses consumed as local-player movement state; historical physics still does not run on the logical server.
