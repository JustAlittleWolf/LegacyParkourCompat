# Lead C frozen source verdict — `Entity.turn` pitch → active Elytra move request

**Scope.** Exact 1.16.5-to-26.2 source comparison of finite, unsaturated direct `Entity.turn` pitch arithmetic and its first reachable dry, active, nonpassenger local-player Elytra movement request. This is a source/arithmetic audit, not runtime evidence. I read only the permitted source procedures and exact decompiled sources; no product implementation, wiki inventory, research/progress record, network source or Git history was consulted.

## Finding

**Pitch arithmetic changed and can change the actual `move` request, but the effect is downstream-formula dependent and can be erased by the historical trig lookup table.** In 1.16.5, `Entity.turn(double,double)` computes `double f = yo * 0.15`, then assigns `(float)(xRot + f)` and clamps; it independently adds the same double `f` to `xRotO` and clamps. In 26.2 it first computes `float xDelta = (float)yo * 0.15F`, then uses float `getXRot() + xDelta`, clamps through `setXRot`, and adds `xDelta` to `xRotO` before its clamp. Thus rounding occurs at different points. For finite `yo=0.1`, initial `xRot=xRotO=0`, both results are legal interior pitch values but differ by one float ULP: 1.16.5 `0.014999999664723873F` (`0x3c75c28f`), 26.2 `0.015000000596046448F` (`0x3c75c290`). No clamp masks this witness. In 26.2 the called `setXRot` also requires finite input and stores `clamp(xRot % 360.0F, -90.0F, 90.0F)` (`Entity.java:3910-3915`); for the finite, small pitch witness this gate/wrap is inert.

## Reachable state and caller path

`LocalPlayer` inherits `Entity.turn`; there is no LocalPlayer override. Mouse handling reaches it during ordinary captured-camera input: 1.16.5 `MouseHandler.turnPlayer` calls `minecraft.player.turn(j, k * n)` at `client/MouseHandler.java:212-243`; 26.2's mouse callback calls `turnPlayer` when the mouse is grabbed and a player exists, and `turnPlayer` calls `minecraft.player.turn(...)` at `client/MouseHandler.java:325-327,350-376`. The direct finite argument used above is within the method's unsaturated, in-range arithmetic domain; normal pointer input supplies finite deltas.

The next local-player tick reaches travel. In 1.16.5 `LocalPlayer.aiStep` calls `super.aiStep` (`client/player/LocalPlayer.java:788`), `LivingEntity.aiStep` creates the travel input and calls `this.travel(...)` (`world/entity/LivingEntity.java:2454-2460`), and LocalPlayer's `isEffectiveAi()` is true (`client/player/LocalPlayer.java:493-496`). `Player.travel` delegates to `super.travel` for a noncreative-flying player (`world/entity/player/Player.java:1387-1414`). In 26.2 the corresponding local-player `aiStep` calls `super.aiStep` (`client/player/LocalPlayer.java:914`); its `LivingEntity` tick calls `travel(input)` when movement is simulatable/effective (`world/entity/LivingEntity.java:3137-3141`), with `LocalPlayer.isLocalPlayer()==true` (`client/player/LocalPlayer.java:377-380`) satisfying Player's client-side simulation gates (`world/entity/player/Player.java:1289-1297`). Nonpassenger `Player.travel` delegates to `super.travel` when not swimming or creative flying (`world/entity/player/Player.java:1401-1424`).

A reachable dry state is an airborne, non-swimming LocalPlayer, not a passenger, not in water/lava, not on a climbable, not in creative flight, with Elytra active (`shared flag 7`, `isFallFlying()`) and no slow-falling effect. Old `LocalPlayer.aiStep` reaches `tryToStartFallFlying()` on jump when nonpassenger, off-climbable and not flying, after its enabled chest-Elytra check (`client/player/LocalPlayer.java:725-729`); that method requires airborne, dry, not already fall-flying, not levitating, and an enabled chest Elytra before setting flag 7 (`world/entity/player/Player.java:1520-1534`). In 26.2, `LocalPlayer.aiStep` calls `tryToStartFallFlying()` on a new jump press (`client/player/LocalPlayer.java:854-856`); `Player.canGlide()` excludes creative flight (`world/entity/player/Player.java:1427-1430`) and the start method requires glide capability and not in water before setting flag 7 (`:1463-1474`). Both releases define `isFallFlying()` from shared flag 7 (`LivingEntity.java:2891-2893` and `:3663-3665`). In 1.16.5, the water/lava branches precede `isFallFlying()` in `LivingEntity.travel`, whose local-control gate admits the local player (`:1914-1916,1923-1924,1959-1960,1979`). In 26.2, `LivingEntity.travel` selects `travelFallFlying` after the fluid predicate (`:2430-2437,2444-2446`); that function falls back to air travel only on climbable, so the stated state enters Elytra movement (`:2581-2595`).

## Effect isolated at the move request

Both source formulas consume the pitch twice: via `getLookAngle()` and a separately computed pitch-radian lean. In both releases `calculateViewVector` multiplies pitch by the float radians-per-degree value, then forms the view vector from trigonometric outputs (1.16.5 `Entity.java:1243-1250`; 26.2 `Entity.java:1966-1973`, called by `getLookAngle` at `:2579-2581`). The trigonometric quantization is a material dependency: 1.16.5 `Mth.sin/cos(float)` indexes a 65,536-entry table with a float-scaled/truncated angle (`Mth.java:12-16,25-30`); 26.2 builds a table using a double scale and exposes `sin/cos(double)` (`Mth.java:31-55`; float view angles widen to double when passed). Separate from the view-angle LUT, the gliding lift formula itself changes from `Mth.cos(lean)` squared through float intermediates in 1.16.5 to `Math.cos(lean)` squared in 26.2.

For a fixed-formula source-expression witness, use the two pitches above, yaw 0, incoming delta movement `(1.0, -0.1, 0.0)`, default gravity `0.08`, no effects, and no collision. The old formula is held fixed for both pitches: its `getLookAngle` and `Mth.cos(lean)` table indices coincide, so both requested vectors are identical: `(0.8910000085830688, -0.10584000205993653, 0.10969200105667114)`. This is a quantization equality, not evidence that the pitch arithmetic is irrelevant generally.

Holding the 26.2 formula fixed instead, the source-expression calculation gives `(0.8910000085830688, -0.10584000649303339, 0.1096920006902621)` for the 1.16.5 pitch result, and `(0.8910000085830688, -0.10584000649303436, 0.10969200069026203)` for the 26.2 pitch result. The differing requests arise from `Math.cos(leanAngle)` in lift (`LivingEntity.java:2602-2626`), even though the view-angle LUT indices coincide for this witness. The request is the vector read immediately by `move(MoverType.SELF, getDeltaMovement())` (`:2586-2589`). Under 1.16.5 the analogous formula builds a vector from old movement, gravity and lift, applies glide adjustments, then multiplies by `(0.99F,0.98F,0.99F)` and passes that resulting delta to `move` (`LivingEntity.java:1985-2008`). Under either fixed formula the direct pitch result is therefore capable of changing the actual requested vector; this example shows the old table can erase the difference while the 26.2 continuous cosine preserves a tiny one. Formula changes across releases must not be attributed to `turn` itself.

The numerical witness is an arithmetic evaluation of the exact source operations and float/table rounding only; it does not simulate Minecraft, collision, or a runtime tick. Changing pitch may leave the first request equal for other inputs because clamps and LUT indices are discrete. The finding is a behavioral possibility with a concrete reachable witness, not a claim that every finite input changes movement.
