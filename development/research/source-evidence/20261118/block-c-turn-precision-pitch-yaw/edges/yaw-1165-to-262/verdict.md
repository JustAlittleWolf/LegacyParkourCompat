# Independent blind source audit: direct yaw precision, 1.16.5 → 26.2

## Verdict

The inspected source payloads show a concrete finite yaw-update difference in `Entity.turn` that can change the first horizontal velocity increment produced by ordinary ground/air relative movement. The yaw is not wrapped or normalized in either `turn`; the 26.2 setter adds a non-finite-result rejection absent from 1.16.5. The finite witness below avoids that gate.

This verdict is bound to the source-file SHA-256 values listed below, but exact input/mapping provenance is not independently established: the 1.16.5 tree has no `.decompile-provenance.json`, and the 26.2 tree is `unobfuscated`, not `mojmap`, also without a provenance manifest. The documented decompiler policy treats such legacy trees as unverified-provenance inputs. Therefore the operation-level claim is source-payload verified, while an exact Mojmap-to-Mojmap acceptance identity remains open.

## Source comparison

- 1.16.5 Mojmap `Entity.turn(double d, double e)`, `Entity.java:340-352`: yaw delta is computed in double as `g = d * 0.15`; current yaw and `yRotO` are each updated by double addition and cast back to float. Yaw receives no clamp, finite check, or modulo normalization.
- 26.2 `Entity.turn(double xo, double yo)`, `Entity.java:489-501`: `yDelta = (float)xo * 0.15F`; current yaw is updated through `setYRot(getYRot() + yDelta)`, and `yRotO` uses float compound addition. This rounds the argument before multiplying and changes the multiplication/addition precision. `Entity.setYRot`, `Entity.java:3898-3904`, discards non-finite values, otherwise stores the float unchanged; it does not wrap yaw. Thus the setter adds a finite-result gate but no yaw normalization.

A lawful finite witness is a direct yaw call with prior `yRot = 6.9866485595703125F`, `xo = 12.3456789`, `vehicle == null`, and any ordinary finite pitch argument. The prior yaw is a finite float state; both resulting yaw values are finite:

| Path | Resulting `yRot` |
| --- | ---: |
| 1.16.5 double multiply/add, final float cast | `8.838500022888184F` |
| 26.2 float cast/multiply/add | `8.8385009765625F` |

This witness is based on the literal source expressions and Java binary32/binary64 conversions. It uses no NaN, infinity, overflow, pitch behavior, or input-scheduling premise.

## First velocity effect and trig isolation

For ordinary nonzero forward input `(0, 0, 1)` and positive finite relative speed `s`, both `Entity.moveRelative` implementations add the `getInputVector` result to delta movement. The 1.16.5 default non-fluid/non-fall-flying travel path calls `handleRelativeFrictionAndCalculateMovement` (`LivingEntity.java:2022-2026`), which calls `moveRelative` (`2062-2065`). The 26.2 ordinary travel path calls `travelInAir` (`LivingEntity.java:2430-2438, 2468-2475`), then the same-named friction helper (`2676-2680`) and `Entity.moveRelative` (`Entity.java:1746-1749`). Both paths therefore use current yaw at the first relative-acceleration operation.

`Entity.getInputVector` is structurally the same rotation for this input: normalize only when squared input length exceeds 1, scale by speed, then use `x = movement.x*cos - movement.z*sin` and `z = movement.z*cos + movement.x*sin` (1.16.5 `Entity.java:1080-1089`; 26.2 `Entity.java:1751-1760`). For the witness, the resulting float radians are `0.15426091849803925F` and `0.15426094830036163F`. Isolating the yaw state while applying each source's own `Mth` kernel gives sine lookup indices 1608 and 1609 on both sides (1.16.5 `Mth.java:25-30`; 26.2 `Mth.java:50-57`). The corresponding sine values are `0.15355512499809265F` and `0.15364986658096313F`; the cosine lookup is the same for the actual old/new pair, `0.9881253838539124F`. Thus the horizontal velocity increment differs in x by `-0.000094741582870483398 * s` for this forward input, with no pitch or unrelated movement mechanic involved. This establishes that the yaw precision change reaches the first relative-acceleration velocity write; the trig lookup is explicitly accounted for rather than assumed continuous.

## Scope and open boundary

Reviewed only direct finite yaw updating, previous yaw bookkeeping insofar as its arithmetic is shared, yaw storage/normalization behavior, and the first ordinary ground/air relative-acceleration consumer. Pitch, input scheduling, fluid/fall-flying routes, other movement mechanics, implementation, runtime parity, and exact original artifact provenance were not audited here. The version pair supports only an endpoint finding; it does not establish an intermediate introduction boundary.

## Phase-two comparison: caller reachability and fixed-trig isolation

I rehashed the frozen C source report at `C:\Users\Wolfi\.codex\visualizations\2026\11\17\01a1eb7b-b9ff-7a20-8686-0295dde20f26\c-turn-precision-yaw-1165-262-source\report.md`; its SHA-256 is `A510C56EB06F211B44E0FD3F7107FD4FEDEE84C52F9C5A99E6B82FE74304F944`, matching the assigned identity. It independently confirms a live local caller in both versions: `MouseHandler.turnPlayer` calls `player.turn(...)` (1.16.5 line 242; 26.2 line 375), and its default non-fluid/non-fall-flying travel paths feed current yaw into `moveRelative`. That closes the question of whether this direct API operation can affect player motion. It does not prove that the particular decimal arguments in my table are produced by a specific physical mouse event: the report explicitly bypasses sensitivity/delta preprocessing for its API-level witness and leaves that preprocessing unreviewed. Treat the witness as a finite lawful call at the reachable method boundary, not as an exact device-event reconstruction.

The prior velocity paragraph compared each release's own `Mth` implementation, so it showed an end-to-end version difference but did not isolate yaw from the independent trig-index implementation change. For isolation, hold one modern motion trig kernel fixed and feed it both stored yaw values from the finite witness (`yRot` before the call `6.9866485595703125F`; direct yaw argument `12.3456789`; resulting old/new yaw `8.838500022888184F` / `8.8385009765625F`). With the same 26.2 conversion of yaw degrees to float radians and the same 26.2 `Mth.sin(double)` / `Mth.cos(double)` lookup on both values, the sine indices are 1608 and 1609, while cosine indices are 17992 and 17993. For forward input `(0,0,1)` and positive finite speed `s`, the corresponding increments are `(-0.15355512499809265, 0, 0.9881401062011719)*s` and `(-0.15364986658096313, 0, 0.9881253838539124)*s`; changing only the yaw therefore changes this fixed-kernel increment by `(-0.000094741582870483398, 0, -0.000014722347259521484)*s`. This is a controlled dependency witness, not a claim that the legacy client used the modern trig kernel.

The side-by-side release execution still uses different `Mth` kernels, so its exact cross-version velocity delta is jointly dependent on yaw rounding and trig implementation. The fixed-modern-kernel comparison above isolates the yaw contribution without conflating those two source changes. The smaller `turn(0.003, 0.0)` witness in the frozen report is a simpler stored-state difference, but by itself does not cross a trig lookup boundary and should not be cited as a velocity witness.
