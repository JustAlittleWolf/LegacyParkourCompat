# 1.8.9 to 1.9 Feather pitch writer audit

## Verdict

The ordinary live player pitch writer and clamp do not change between 1.8.9 and 1.9. The player-facing mouse path still calls `Entity.updateLocalPlayerCamera`; it subtracts the pitch argument times `0.15`, clamps the result to `[-90.0F, 90.0F]`, then adjusts `lastPitch` by the actual pitch delta. `Entity.setRotation` remains a separate modulo-360 setter with no clamp in either release.

1.9 adds a live pitch **consumer** in the Elytra movement path, not a writer to `Entity.pitch`. When a locally controlled living entity is fall-flying, `LivingEntity.moveRelative` reads both the live look vector and `this.pitch`, computes lift/dive effects, changes velocity, and calls `move`. Elytra model animation writes separate `ClientPlayerEntity.elytraPitch/Yaw/Roll` render fields, not `Entity.pitch`.

The behavioral trace is source-confirmed, but the exact-source publication gate is incomplete for 1.9: the canonical `decompiled_minecraft/1.9/` version root has no ready marker, root provenance record, source manifest, artifact manifest, success log, or verification manifest. Its hidden `.decompile-provenance.json` internally hashes all 1,819 Java source files and names exact Feather 1.9 build.2 inputs, but it cannot substitute for the missing version-root readiness/artifact manifests. Treat this comparison as provisional until that publication gap is resolved.

## Trace

- **Input context and sign:** In both releases, `client/Mouse.java:21-22` reads `Mouse.getDX()` and `Mouse.getDY()` into `x` and `y`. `client/render/GameRenderer.java` scales them at 1.8.9 lines 848-851 / 1.9 lines 833-836, applies `invertMouseY` at 1.8.9 lines 852-855 / 1.9 lines 837-840, and calls `player.updateLocalPlayerCamera(h, i * j)` in both smoothing and direct paths (1.8.9 lines 857-868; 1.9 lines 842-853). Thus a positive pitch argument lowers numeric `pitch` in the player method; the configured invert option reverses the argument before it arrives.
- **Ordinary setter/clamp:** 1.8.9 `entity/Entity.java:221-243`: `setRotation` stores `yaw % 360.0F` and `pitch % 360.0F`; `updateLocalPlayerCamera` adds `yaw * 0.15`, subtracts `pitch * 0.15`, clamps `pitch` to `[-90.0F, 90.0F]`, then adjusts the last-angle fields. 1.9 `entity/Entity.java:269-294` has the same arithmetic and order, followed by `mount.onPassengerLookAround(this)` when mounted. The mount callback is the sole addition in this method; it does not alter the pitch formula or clamp.
- **First movement-specific live-pitch consumer:** In 1.9 `entity/living/LivingEntity.java:1289-1328`, the fall-flying branch of `moveRelative` is reached only under `isFallFlying()` and local/logical movement control. It reads `getLookVector()` and `this.pitch * (float)(Math.PI / 180.0)`, applies pitch-dependent vertical and horizontal velocity changes, then calls `move(...)`. `LivingEntity.getLookVector()` at lines 1803-1812 resolves the live rotation vector with `tickDelta=1.0F`, which reads `this.pitch`. The travel path invokes `moveRelative(this.sidewaysSpeed, this.forwardSpeed)` at lines 1693-1698. The local-player Elytra start request is gated by falling/jumping, equipment and `ElytraItem.canFly` at `LocalClientPlayerEntity.java:703-707`.
- **No Elytra writer to live pitch:** `LivingEntity.moveRelative` reads `this.pitch` but never assigns it. `ElytraModel.java:55-62` interpolates `elytraPitch`, `elytraYaw`, and `elytraRoll` on `ClientPlayerEntity` and assigns them to wing rotations; these are render-model fields. They are distinct from inherited `Entity.pitch`. The audited direct `pitch` assignments in the player/entity movement classes are camera input, position/rotation/NBT synchronization, interpolation, reset, and pig-riding preservation; no Elytra path writes inherited live pitch.
- **Pair contrast:** 1.8.9 has the same mouse-to-camera writer/clamp but no Elytra/fall-flying movement branch. The new 1.9 Elytra path changes which movement code consumes current pitch when fall-flying; it does not introduce a live pitch writer or change ordinary pitch setting/clamping. This is source behavior, not a runtime parity claim.
