## Claim review

In both releases, `Entity.updateLocalPlayerCamera(float yaw, float pitch)` snapshots `f = this.pitch` before updating it (`Entity.java:291–298`). The current pitch assignment is `(float)(this.pitch - pitch * 0.15)`; because `0.15` is a double literal, the multiply/subtract are double operations followed by the explicit float cast. `MathHelper.clamp(this.pitch, -90.0F, 90.0F)` follows that cast, and only then does `lastPitch` receive `lastPitch + (this.pitch - f)`. This exact sequence and expression are the same in both source files.

Finite witness for that order: with old `pitch=89.0F`, old `lastPitch=88.0F`, and camera pitch delta `-1000.0F`, the expression produces `239.0` before its float cast; the current pitch clamps to `90.0F`; then the previous-state adjustment adds `90-89=1`, yielding `lastPitch=89.0F`. No NaN/Infinity behavior is needed for the witness. This demonstrates the shared operation; it is not a cross-version delta.

The local input route is present in both identical `GameRenderer.java` files: ordinary and smooth camera paths call `minecraft.player.updateLocalPlayerCamera(...)` (`GameRenderer.java:843–855`). `LocalClientPlayerEntity.isLocallyControlled()` returns true (`LocalClientPlayerEntity.java:458–460`). In dry Elytra movement, `LivingEntity.moveRelative` reaches the fall-flying branch when local control is active and both `!isInWater()` and `!isInLava()` gates pass (`LivingEntity.java:1332–1346`). At the encompassing travel phase, `flyingTick()` precedes `moveRelative(...)` (`LivingEntity.java:1742–1747`); the first current-pitch read in that full tick path is the pitch/previous-pitch wrap at `LivingEntity.java:1631–1636`. Within the Elytra `moveRelative` calculation itself, the first current-pitch read is earlier than the explicit radians assignment at line 1342: `getLookVector()` at line 1341 calls `getRotationVector(1.0F)`, whose `tickDelta == 1.0F` branch reads `this.pitch` at line 1860, before the angle scalar at line 1342. These routes and gates are also identical across the endpoint files.

**Acceptance boundary:** Accept the source claim that the camera setter uses double arithmetic then float cast, clamps current pitch before previous-pitch adjustment, and that current pitch feeds the described dry local Elytra path. Reject any claim that these operations differ between 1.10.1 and 1.10.2. The first pitch read depends on scope: full travel tick (`flyingTick` wrap), versus the Elytra branch's own calculation (`getLookVector` before `float i`).
