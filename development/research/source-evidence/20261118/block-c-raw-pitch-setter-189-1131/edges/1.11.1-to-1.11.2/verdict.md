## Compared behavior

**Ordinary direct local pitch turn.** In both releases, `GameRenderer` calls `minecraft.player.updateLocalPlayerCamera(h, i * j)` on each of its smooth-camera and ordinary-camera branches when the focused mouse is active (`GameRenderer.java:852–866`). `Entity.updateLocalPlayerCamera(float yaw, float pitch)` (`Entity.java:304–316`) stores old pitch in a `float`; calculates `this.pitch - pitch * 0.15` with the `0.15` double literal (promoting the multiply/subtraction to double); casts the result once back to `float`; clamps that float to `[-90.0F, 90.0F]`; then updates `lastPitch` with `lastPitch + (newPitch - oldPitch)`, all float field/arithmetic operations. It similarly updates yaw, then calls the mount look callback only if mounted. The method bytes and its `GameRenderer` caller are unchanged in the pair.

**First stored pitch consumption while gliding.** The local tick calls through to `LivingEntity.tick`; for locally controlled entities that tick invokes local `serverTickAi`, then reaches `moveRelative(this.sidewaysSpeed, this.forwardSpeed)` after its travel setup (`LivingEntity.java:1581–1804`). `PlayerEntity.moveRelative` delegates to the superclass for the ordinary survival case; only abilities flight while not riding takes its separate branch and clears fall-flying state (`PlayerEntity.java:1387–1402`). In `LivingEntity.moveRelative` (`LivingEntity.java:1388–1442`), execution is gated by local/logical movement authority, dry conditions (`!isInWater`, `!isInLava` unless player abilities flight), and `isFallFlying()` (shared flag 7). The active Elytra state is kept only while airborne, not riding, and wearing a flyable Elytra in `flyingTick` (`LivingEntity.java:1810–1828`; on the client the shared flag is consumed rather than rewritten there).

Inside that dry active branch, the first pitch read is indirect: `this.getLookVector()` (`LivingEntity.java:1397`) calls `LivingEntity.getLookVector()` and `getRotationVector(1.0F)` (`LivingEntity.java:1916–1928`). Dynamic dispatch reaches `LocalClientPlayerEntity.getRotationVector(float)`, which uses the current `this.pitch` and `this.yaw` directly (`LocalClientPlayerEntity.java:153–156`); the shared `Entity.getRotationVector(float pitch, float yaw)` converts them to the look vector (`Entity.java:1229–1235`). It does not use interpolated `lastPitch` on this local-player path. The next pitch read is the explicit `float i = this.pitch * (float) (Math.PI / 180.0)` (`LivingEntity.java:1398`), which drives the glide lift/dive terms immediately following. Thus a camera turn's clamped current float is the value consumed by the actual local glide operation; previous pitch remains relevant to interpolation elsewhere but is not used for this glide look vector.
