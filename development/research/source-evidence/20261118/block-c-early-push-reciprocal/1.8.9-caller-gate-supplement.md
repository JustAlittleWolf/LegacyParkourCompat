## Interpretation of the reciprocal copy

Fact: the ordinary 1.8.9 common client call path performs neither side's write. Fact: the 1.9 common client path can write both the selected local-player receiver and the living caller argument, as detailed in the main report.

Inference under the stated player-movement-only invariant: if a 1.8.9 implementation cancels only the local-player receiver-side response on the modern ordinary collision call while leaving the modern reciprocal write into a mob or remote-player copy intact, that residual write is a non-player/remote-copy state effect outside the target movement output. Preserving it follows native fallback and does not contradict the absence of either write in the historical 1.8.9 execution, provided no in-scope local-player movement later reads that changed copy state; this bounded source comparison does not prove or trace such a dependency. Exact historical reproduction of the *whole* common call would suppress both writes by skipping dispatch at the caller. The project objective only requires local player movement parity, so the source evidence alone does not require cancelling the out-of-scope reciprocal copy.

## Corrected applicability

The earlier statement that whole-call cancellation loses the historical player response applies to 1.9 profiles, where the ordinary client caller reaches `localPlayer.push(caller)`. It does not apply to the 1.8.9 ordinary living-tick path: that profile already skips the call on logical clients. For 1.8.9, a caller-context cancellation/skip of that common operation is compatible with the source. A type-only `Entity.push(Entity)` cancellation remains broader than this finding and cannot be accepted as equivalent without separately evaluating every direct caller and its player response.

This closes only the bounded 1.8.9 common caller gate and direct-callsite distinction. It does not establish full pair coverage, decide historical behavior for vehicle or other direct callers, inspect product code, or claim runtime parity.
