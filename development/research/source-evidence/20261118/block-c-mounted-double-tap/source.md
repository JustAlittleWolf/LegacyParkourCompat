# Mounted forward double-tap sprint survives local dismount into a grounded jump

**Compared source:** exact 1.19.2 and 1.19.3, Mojmap, canonical `decompiled_minecraft/<version>/mojmap/` sources.

## Bounded source comparison

`LocalPlayer.aiStep` snapshots `$$2 = this.hasEnoughImpulseToStartSprinting()` before calling `this.input.tick(...)`. In dry movement, that helper is `forwardImpulse >= 0.8` (1.19.2 `client/player/LocalPlayer.java` 738–746, 1121–1124; 1.19.3 659–667, 1042–1045). Thus `$$2` reflects the previous input impulse, while the later `hasEnoughImpulseToStartSprinting()` call reads the current tick's input.

Start with the player not sprinting, off ground, riding a grounded vehicle, dry, with food above 6, `sprintTriggerTime <= 0`, no item use or blindness, and sprint key up. Tap forward at `forwardImpulse >= 0.8` for one tick, release for one tick, then tap again at that threshold. On the first tap the prior-input snapshot is false; 1.19.3's added `(this.isPassenger() && this.getVehicle().isOnGround())` clause admits the route and arms `sprintTriggerTime = 7`, while 1.19.2's `(this.onGround || this.isUnderWater())` gate does not. On the release tick the counter drops to 6, but the prior-input snapshot is true, so `!$$2` blocks the route. On the second tap the prior-input snapshot is false and the counter drops to 5; 1.19.3 sets sprinting. In 1.19.2 the player remains off ground and dry, so it neither armed nor enters this route. The separate direct route requires the sprint key down and is false on both sides. Keep forward input high after the second tap. References: 1.19.2 `client/player/LocalPlayer.java` 731–795; 1.19.3 `client/player/LocalPlayer.java` 652–716.

Shift input clears `sprintTriggerTime`; it does not clear the already-set sprint flag. With food and forward impulse retained, dry state, and no horizontal collision, 1.19.3's sprint stop gates do not clear sprint. The local dismount write exists in both versions: `ClientPacketListener.handleMovePlayer` calls `removeVehicle()` when the clientbound position packet requests dismount (1.19.2 `client/multiplayer/ClientPacketListener.java` 562–568; 1.19.3 591–597). `Player.removeVehicle` and `Entity.removeVehicle` clear the vehicle relationship without clearing sprint (1.19.2 `world/entity/player/Player.java` 1045–1048 and `world/entity/Entity.java` 1779–1789; 1.19.3 `Player.java` 1034–1037 and `Entity.java` 1784–1798). These are local writes only; this comparison does not model server simulation or packet scheduling.

Keep forward at or above `0.8` through airborne descent and into the first ordinary grounded jump tick. The 1.19.3 sprint remains set: its stop gate tests `input.hasForwardImpulse()`, not the `0.8` sprint-start threshold (1.19.3 `client/player/LocalPlayer.java` 719–728; both `client/player/Input.java` 22–24 define any positive impulse above `1.0E-5F` as forward impulse). In 1.19.2, on the first grounded jump tick the pre-input snapshot `$$2` is still true because the previous tick also had forward impulse at least `0.8`. Therefore `!$$2` fails: the old route neither arms the seven-tick timer nor starts sprint. Continued sufficient forward input keeps that snapshot true on following grounded ticks as well. This corrects the earlier draft's claim that 1.19.2 arms the timer on that first grounded tick.

On that grounded tick, with `input.jumping` true and `noJumpDelay == 0`, `LocalPlayer.aiStep` reaches `super.aiStep()` and the grounded-jump branch in `LivingEntity.aiStep` (1.19.2 `client/player/LocalPlayer.java` 893–894 and `world/entity/LivingEntity.java` 2564–2570; 1.19.3 `LocalPlayer.java` 814–815 and `LivingEntity.java` 2575–2581). The ordinary collision writer sets `onGround = verticalCollision && requestedMovement.y < 0.0` (`world/entity/Entity.java` 585–597 in both versions). Both versions' `LivingEntity.jumpFromGround` write jump Y velocity, then add `(-sin(yRot) * 0.2F, 0, cos(yRot) * 0.2F)` iff sprinting (1.19.2 `world/entity/LivingEntity.java` 2014–2024; 1.19.3 2024–2034). Accordingly, the first grounded jump after the specified continuous-forward dismount has the sprint-only horizontal addition in 1.19.3 and not 1.19.2.

## Timer boundary and scope

For the continuous-sufficient-forward sequence above, no later 1.19.2 timer arming follows merely from becoming grounded: `$$2` is the prior-input snapshot and stays true. A grounded 1.19.2 tick can arm the timer only when that snapshot is false while the current tick's forward input meets the `0.8` threshold and the other route gates pass—for example, after a prior input tick below that threshold. This is a different input sequence. No claim is made that the old timer advances or starts sprinting under the specified continuous-forward sequence.

Vehicle physics, the origin/timing of the client dismount request, server or packet simulation, and resulting trajectory are outside this comparison.
