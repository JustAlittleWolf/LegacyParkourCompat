## Trace and bounded conclusion

- In both versions, `PlayerEntity.mobTick()` calls `super.mobTick()` (1.11.2 `PlayerEntity.java:417–435`; 1.12 `PlayerEntity.java:413–431`). The inherited `LivingEntity.mobTick()` runs `flyingTick()` immediately before `moveRelative()` (1.11.2 `LivingEntity.java:1798–1803`; 1.12 `LivingEntity.java:1842–1847`). Thus, for this ordinary player path, validation/update precedes movement and its climb cleanup.
- Both `flyingTick()` bodies start from tracked flag 7, retain the candidate only if airborne, not riding, and wearing a chest Elytra accepted by `ElytraItem.canFly`, and clear the local candidate otherwise. The `setFlag(7, bl)` write is guarded by `!world.isClient` on both sides (1.11.2 `LivingEntity.java:1810–1828`; 1.12 `LivingEntity.java:1854–1872`). Consequently the local client's already-active flag is not cleared by this updater even if those checks make its local candidate false. `isFallFlying()` directly returns flag 7 in each version (1.11.2 `LivingEntity.java:2145–2146`; 1.12 `LivingEntity.java:2184–2185`).
- `moveRelative()` checks movement authority and water/lava gates, then tests `isFallFlying()` before entering the ordinary branch. In the active glide branch, the strict condition is the **double** comparison `velocityY > -0.5`; if true, it writes `fallDistance = 1.0F` before the glide math and before `move(MoverType.SELF, ...)`. The branch then performs the glide move. The ordinary branch's `isClimbing()` clamps and `fallDistance = 0.0F` are after the `else`, so an already-active glide bypasses them. This order, comparison, literal, timing, move, and bypass agree: 1.11.2 `LivingEntity.java:1388–1427, 1441–1477`; 1.12 `LivingEntity.java:1425–1464, 1478–1514`. In 1.12 the signature and ordinary `updateVelocity` inputs differ, but that code is reached only after the glide branch is rejected.
- Scope check on the player override: in both releases, `PlayerEntity.moveRelative()` calls `super.moveRelative()` and only afterward clears flag 7 and fall distance in its `abilities.flying && !isRiding()` branch (1.11.2 `PlayerEntity.java:1386–1405`; 1.12 `PlayerEntity.java:1385–1403`). That is an ability-flight path, outside the ordinary Elytra/climb case. The server-side on-ground clear inside the glide branch is likewise guarded by `!world.isClient`. NBT read can set flag 7 in both versions (1.11.2 `LivingEntity.java:505–507`; 1.12 `LivingEntity.java:508–510`); launch/start transitions are not audited here. These bounds do not change the active-only conclusion.
