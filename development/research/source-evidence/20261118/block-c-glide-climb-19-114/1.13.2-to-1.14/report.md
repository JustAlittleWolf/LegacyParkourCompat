# 1.13.2 → 1.14 active glide/climb alias gate

## Verdict

No source difference in this bounded active pre-move slice. For a dry, locally controlled player whose fall-flying flag is already active and whose chest slot has an ordinary usable Elytra, the glide branch precedes the ordinary climbing branch in both releases. On a ladder or vine, an active glide therefore does not run the ordinary climb fall-distance reset. The same strict vertical-velocity test and assignment occur before the first glide move in both versions.

This is a bounded no-difference result, not a full-pair coverage freeze. Startup acceptance, post-move/final effects, and A/B profiles were not examined.

## Comparison

- **Active-state validation/cancellation before movement:** 1.13.2 calls `flyingTick()` immediately before `moveRelative()` (`LivingEntity.java:1924-1926`). It reads flag 7, retains it only while airborne, not riding, and equipped with an exact `Items.ELYTRA` item for which `ElytraItem.canFly` is true; otherwise it clears its temporary boolean. It writes the flag only when `!world.isClient` (`1938-1956`). 1.14 calls `initAi()` immediately before `travel()` (`2202-2204`); it applies the corresponding airborne, not-in-vehicle and exact chest Elytra / `ElytraItem.isUsable` checks, then likewise writes flag 7 only when `!world.isClient` (`2216-2234`). Thus an already-active local-client flag is not locally canceled by either validator. Durability handling differs in method names but does not change the client flag gate for this slice.
- **Movement authority and branch order:** 1.13.2 `moveRelative` enters for `isLocallyControlled() || isLogicalSideForUpdatingMovement()` (`1478-1479`). 1.14 `travel` enters for `canMoveVoluntarily() || isLogicalSideForUpdatingMovement()` (`1763-1764`). Under the assigned ordinary local-player case, both enter. In dry conditions, each checks `isFallFlying()` before its ordinary movement `else` (`1.13.2:1486-1489`; `1.14:1772-1775`). The glide branch calls the move (`1.13.2:1523`; `1.14:1802-1803`). The ordinary branch's climb clamp/reset is reached only when the active glide check is false (`1.13.2:1537,1560-1575`; `1.14:1817,1821-1825,1921-1935`). Both `isClimbing()` implementations treat the ladder and vine block as climbing states (`1.13.2 LivingEntity.java:1046-1058`; 1.14 `LivingEntity.java:1216-1229`, with the block identities confirmed in `Blocks.java`).
- **Exact pre-move threshold:** 1.13.2 checks `this.velocityY > -0.5` and assigns `this.fallDistance = 1.0F` (`LivingEntity.java:1488-1491`). 1.14 checks `lv5.y > -0.5` and assigns `this.fallDistance = 1.0F` (`LivingEntity.java:1774-1778`). The velocity component is double in both checks; `-0.5` is a strict double-comparison literal and the assigned fall distance is float `1.0F`. Exactly `-0.5` does **not** assign; any representable value greater than `-0.5` does. This happens before the first glide move in both releases. Because the glide branch bypasses ordinary climbing handling, an active player on ladder/vine preserves the incoming fall distance when vertical velocity is at or below the boundary, and receives `1.0F` above it; climbing does not reset that value in this slice.
