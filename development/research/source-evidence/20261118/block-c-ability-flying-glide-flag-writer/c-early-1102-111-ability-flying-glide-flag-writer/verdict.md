# Independent source audit: ability flight with flag 7 live

## Verdict

**Accepted, bounded claim: no player-movement difference is established for the specified ordinary local-player path.** In both exact Feather source sets, local ability flight with a live fall-flying flag enters the same `PlayerEntity.moveRelative` branch. It calls the superclass first; the superclass executes the glide movement and calls the real `Entity.move` entry point, then its on-ground flag-7 clear is gated by `!world.isClient`. The player override returns from the superclass and unconditionally clears flag 7. This order is the same on the client and logical server; only the superclass's on-ground clear differs by side. The movement entry-point signature changes in 1.11 (`move(MoverType.SELF, ...)`), so this verdict does not claim equivalent `Entity.move` internals or a wider movement parity result.

The local state is ordinarily reachable: `LocalClientPlayerEntity.mobTick` toggles `abilities.flying` on the normal double-jump path for a player with `abilities.canFly`; that toggle has no `!isFallFlying()` guard. The separate glide-start request does require `!isFallFlying()` and `!abilities.flying`, but that gate controls starting a glide, not toggling flight after a glide is already active. This establishes the normal-input coexistence path without relying on crafted state. It does not audit network timing or glide-start authority.

## Independent trace

- **1.10.2:** `LivingEntity.travel` calls `moveRelative` at lines 1742–1747. Its local/control gate in `LivingEntity.moveRelative` passes for the local player; water/lava checks also allow a flying player (1332–1336). With `isFallFlying()` true (flag 7), it applies glide math and calls `this.move(velocityX, velocityY, velocityZ)` at 1371. `Entity.move(double,double,double)` is the actual matching overload (Entity.java:446). The parent clear requires both `onGround` and `!world.isClient` (LivingEntity.java:1382–1383). Back in `PlayerEntity.moveRelative`, `abilities.flying && !isRiding()` selects the branch, calls `super.moveRelative` at 1399, then directly calls `setFlag(7, false)` at 1403 without a logical-side condition (1395–1404).
- **1.11:** `LivingEntity.travel` calls `moveRelative` at lines 1796–1801. The same local/control, flying-in-fluid and active-glide gates appear at 1386–1390. Glide math reaches `this.move(MoverType.SELF, velocityX, velocityY, velocityZ)` at 1425; `Entity.move(MoverType, double,double,double)` is the actual matching overload (Entity.java:455). The parent clear still requires `onGround && !world.isClient` (LivingEntity.java:1436–1437). `PlayerEntity.moveRelative` selects the same ability-flight branch, calls the superclass at 1393, then unconditionally clears flag 7 at 1397 (1389–1398).
- **Ordinary local precondition:** in both LocalClientPlayerEntity versions, `mobTick` toggles `abilities.flying` through its `canFly` double-jump path (1.10.2:713–728; 1.11:725–740). Its glide-start request separately requires `!isFallFlying() && !abilities.flying` (1.10.2:730–734; 1.11:742–747), so that exclusion does not block enabling flight while a previously active glide flag remains live.

The two movement entry points are not treated as semantically identical. Their distinct signatures and arguments are retained above as an open boundary outside this flag-order verdict.
