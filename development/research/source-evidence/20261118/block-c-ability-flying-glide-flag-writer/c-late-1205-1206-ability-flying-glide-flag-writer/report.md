# 1.20.5–1.20.6: creative flight during live Elytra glide

## Result

No source change was found in this bounded behavior from 1.20.5 to 1.20.6. The normal local-player path can overlap authorized creative flight (`Abilities.flying`) with an already-live Elytra shared flag 7 for the travel call in the same tick. On that call, `Player.travel` delegates to `LivingEntity.travel` while flag 7 is still live; the Elytra branch computes and applies that tick's glide displacement before `Player.travel` restores vertical velocity and clears flag 7. The operation and its gates are byte-identical in the two examined source trees.

## Paired source evidence

All references below are in `decompiled_minecraft/<version>/mojmap/` and have identical file bytes in both versions.

- `client/player/LocalPlayer.java:648–751,807–810`: `aiStep` processes normal ability input. The creative-flight toggle is gated by `abilities.mayfly` and the existing jump-toggle conditions (including the swim gate); a successful toggle sets `abilities.flying` and calls `onUpdateAbilities`. The Elytra start-input block at 744–749 separately requires `!abilities.flying`, so normal local input does not request a *new* glide while creative flying. It snapshots `wasFallFlying` at 751, then calls `super.aiStep()` at 807. `onUpdateAbilities` at 343–345 sends the current abilities packet.
- `world/entity/LivingEntity.java:2376,2670–2684,2721–2744`: the living tick calls `aiStep`; its travel phase runs `updateFallFlying()` before `travel(...)`. `updateFallFlying` preserves a live flag 7 when the player is airborne, not riding, not levitating, and wearing an enabled Elytra. It has no `abilities.flying` exclusion. On the client it does not rewrite the shared flag at the end (the setter is inside `if (!level().isClientSide)`); thus a valid prior client flag remains live for `Player.travel` in this tick.
- `world/entity/player/Player.java:1473–1494`: after the swimming preamble, the flying-and-not-passenger branch captures the incoming Y velocity, invokes `super.travel`, then writes `(postTravelX, incomingY * 0.6, postTravelZ)`, resets fall distance, and calls `setSharedFlag(7, false)`. This direct bit-7 clear is after `super.travel` returns.
- `world/entity/LivingEntity.java:2104–2180`: under `isControlledByLocalInstance()`, a live `isFallFlying()` selects the glide math branch. It computes glide velocity, writes it with 0.99F/0.98F/0.99F factors, then calls `move(MoverType.SELF, getDeltaMovement())`. That move is the actual position displacement and occurs before the wrapper's Y-velocity overwrite and flag clear. The glide branch itself also clears flag 7 only on a server-side landing; it does not preempt the flying wrapper's later clear on the local client.
- `world/entity/Entity.java:2236–2247`: `getSharedFlag(7)` tests bit 7; `setSharedFlag(7, false)` masks off only that bit from the shared byte.
- `server/network/ServerGamePacketListenerImpl.java:1410–1413,1689–1693,865–880`: the server handles `START_FALL_FLYING` by calling `tryToStartFallFlying` and stopping glide if the validation fails. Ability updates are marshalled to the server thread and set flying only as `packet.isFlying() && mayfly`. During movement-packet handling, the server snapshots `isFallFlying()` before the Elytra speed-check gate and selects the 300.0F versus 100.0F multiplier from that snapshot. These are vanilla authority/validation timings, not historical server physics.

The normal overlap is reachable without manufacturing flags or packets: a player already in a valid Elytra glide can use the ordinary authorized creative-flight toggle. During the subsequent living tick, the live Elytra state survives `updateFallFlying`; `Player.travel` sees both flags and uses the glide displacement branch once, then clears bit 7. A passenger or an invalid/ended glide does not satisfy this described path.

## Boundary

This is a narrow paired check of the authorized local-player overlap, resulting own displacement, bit-7 clear order, and the adjacent vanilla server guards/timing. No 1.20.5→1.20.6 difference exists in these examined sources. It does not inventory the complete player tick or establish full-pair coverage, intermediate patch introduction, runtime parity, or implementation acceptance. Fall-distance behavior, server movement-check tuning beyond the cited gate, artificial state/packet paths, and network/runtime behavior are not findings in this report.
