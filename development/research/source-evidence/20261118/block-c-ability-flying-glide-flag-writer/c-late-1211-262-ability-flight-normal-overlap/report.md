# 1.21.1 → 26.2: ordinary ability flight during an active glide

## Finding

An airborne local player who already has the live fall-flying shared flag can ordinarily turn on authorized ability flight with the normal jump double-tap while still wearing an enabled Elytra. Both clients can perform the glide branch's local displacement on that same tick despite the new `abilities.flying` value, provided the player is not in the fluid-travel branch or riding. This is a reachable overlap, not an artificial state: the double-tap path does not test or clear the existing glide flag. It does not mean both flight modes are independently selected by `travel`; the fall-flying shared flag selects the glide travel branch, with player flight post-processing afterward.

The important difference is cleanup after that displacement. In 1.21.1 `Player.travel` clears shared flag 7 after `super.travel` returns whenever ability flight is active and the player is not riding. In 26.2, the corresponding player branch adjusts vertical velocity after `super.travel` but does not clear flag 7; local `LivingEntity.updateFallFlying` only clears it under a server-side gate. So the glide flag survives this local displacement in 26.2, while 1.21.1 clears it at the end of the same player-travel call. This is not a claim about how long the 26.2 flag survives: later authoritative synchronization can change it, and no latency/timing guarantee is established here.

## Evidence and paths

**1.21.1, official Mojang mappings (`mojmap`)**

- `net/minecraft/client/player/LocalPlayer.java`, `aiStep`, lines 644–748: with `mayfly`, the ordinary non-spectator jump double-tap toggles `abilities.flying`; the path has no check of `isFallFlying` or shared flag 7. It sets the local toggle marker, calls `onUpdateAbilities`, and the adjacent Elytra-start path is suppressed on this toggle tick. `wasFallFlying` is then sampled at line 748; `super.aiStep()` follows at line 804.
- `net/minecraft/world/entity/LivingEntity.java`, `aiStep`, lines 2668–2670 and `updateFallFlying`, lines 2716–2740: the tick updates glide validity before calling travel. A valid airborne, non-passenger, non-levitating enabled-Elytra flag is retained locally; the method writes the recalculated flag only off the logical client. `travel`, lines 2091–2152, gives fluid handling precedence and otherwise enters its `isFallFlying()` branch before ordinary land travel. The glide branch calls `move` before returning.
- `net/minecraft/world/entity/player/Player.java`, `travel`, lines 1456–1477: when ability flight is enabled and the player is not a passenger, it calls `super.travel` first, then adjusts vertical velocity, resets fall distance and clears shared flag 7. With valid glide conditions and no fluid branch, the `super.travel` call has already completed the glide displacement before that clear.

**26.2, published unobfuscated names (no remapping)**

- `net/minecraft/client/player/LocalPlayer.java`, `aiStep`, lines 830–858: `abilities.mayfly` plus the normal jump double-tap toggles `abilities.flying` without checking the glide flag. The toggle marker suppresses a new glide-start attempt, but does not cancel an already-live flag; the code samples `wasFallFlying` at 858 and calls `super.aiStep()` at 914.
- `net/minecraft/world/entity/LivingEntity.java`, `aiStep`, lines 3127–3140: a live flag invokes `updateFallFlying` before travel. The update's clear path is guarded by `!level().isClientSide()` at lines 3193–3198. `travel`, lines 2430–2435, selects fluid travel first, then `isFallFlying()`/`travelFallFlying`, then air travel. `travelFallFlying`, lines 2581–2592, performs `move` without testing `canGlide`; the latter is an initiation/validity check elsewhere.
- `net/minecraft/world/entity/player/Player.java`, `travel`, lines 1402–1429: the flying, non-passenger branch calls `super.travel`, then scales the resulting Y velocity by the pre-travel Y value. It does not clear shared flag 7. `canGlide` rejects ability flight, but that predicate is not consulted by the client travel branch selected from the already-live flag.

**Ordinary-route conditions used for the finding:** authorized `mayfly` ability; player airborne and not riding; first jump press arms `jumpTriggerTime`, then a normal second jump press toggles ability flight (and the relevant toggle is from false to true); the toggle occurs while not swimming; a valid already-live glide flag with normal enabled Elytra conditions; not climbing, and no fluid-travel precedence. In 26.2 the jump-toggle branch also requires no prior jump on the prior tick, no auto-jump, and either no vehicle or a jumpable vehicle; an actively gliding, non-passenger player satisfies the ordinary no-vehicle case. A grounded toggle can invoke `jumpFromGround`, but that is not needed for this airborne overlap. Only the local player's movement path is assessed.

## Limits

This is a narrow source comparison of ordinary local-player behavior and shared-flag handling through the local displacement. It does not cover server simulation, server-side validation or damage, environment-generated transitions, packets/latency, post-tick reconciliation timing, every fluid type's exact branch behavior, passengers, or other input/vehicle cases. The source establishes that the reachable same-tick overlap exists under the stated non-fluid and non-climbable conditions and where each local implementation clears or leaves the flag; it does not establish a 26.2 flag-duration guarantee.
