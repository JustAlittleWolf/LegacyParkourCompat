# Independent audit: 1.9.4→1.10 creative flight during glide

## Verdict

**ACCEPT the no-difference claim for the bounded player operation.** In both endpoints, a local player with `abilities.flying == true`, not riding, and flag 7 live enters the same outer `PlayerEntity.moveRelative` wrapper. Its `super.moveRelative` call selects `LivingEntity`'s `isFallFlying()` branch and calls `move(...)` while flag 7 is still true. Only after that call returns does the player wrapper clear flag 7. The relevant gates, order, and state writes match in 1.9.4 and 1.10.

The frozen report's 1.10 provenance gap is **not substantiated**: the adjacent `1.10/ornithe-feather.ready.json` and standalone `.sources.sha256` are absent, but the mapping root contains a hidden `.decompile-provenance.json` with pinned exact inputs and a complete per-source hash map. I verified every entry against the local tree. That is sufficient to identify and integrity-check this exact local Feather output. Do not treat the missing ready sidecar or unexamined raw artifact files as missing source pins.

The report's startup caveat can also be narrowed. The local Elytra starter requires both `!isFallFlying()` and `!abilities.flying`, so it cannot initiate a fresh glide while flight is already enabled. But ordinary local creative input can turn flight on **during an already-live glide**: the double-tap flight toggle in `LocalClientPlayerEntity.mobTick()` runs before `super.mobTick()`, which performs the `LivingEntity` movement. With a normal manual second tap (not an auto-jump-generated edge in 1.10), the toggle sets/syncs `abilities.flying`; because `isFallFlying()` is already true, the separate Elytra starter condition is false, then movement runs and the player wrapper clears the flag after movement. `flyingTick()` does not clear a valid airborne Elytra flag on the client. This establishes a source-reachable ordinary local sequence, without relying on latency, a fabricated state, or runtime observation.

## Independent source trace

- **Ordinary input path:** 1.9.4 `LocalClientPlayerEntity.java:690–713`; 1.10 `:713–738`. With `abilities.canFly`, a manual jump rising edge toggles `abilities.flying` after the double-tap timer is primed, then calls `syncAbilities()`. This occurs before `super.mobTick()` (`1.9.4:755`; `1.10:778`). In 1.10 the added `!bl4` rejects an auto-jump-generated edge; a manual second tap with no pending auto-jump timer has `bl4 == false`. The fresh-glide starter later on the same path requires `!isFallFlying()` and `!abilities.flying`, so an already-gliding player does not send another start request.
- **Actual move:** `LivingEntity.java:1706–1711` (1.9.4) and `:1742–1747` (1.10) call `flyingTick()` and then `moveRelative(...)`. In both `LivingEntity.moveRelative` implementations (`1.9.4:1302–1341`; `1.10:1332–1371`), the local-control gate admits the local player, flying ability bypasses the water/lava exclusions, `isFallFlying()` selects the same glide math, and `move(...)` occurs before returning. The glide branch's own flag clear is guarded by `!world.isClient` (`1.9.4:1352–1353`; `1.10:1382–1383`). `flyingTick()` preserves a valid airborne, non-riding Elytra flag on clients because its `setFlag(7, bl)` write is server-only (`1.9.4:1718–1735`; `1.10:1754–1771`).
- **Direct post-move player clear:** `PlayerEntity.moveRelative` at 1.9.4 `:1371–1387` and 1.10 `:1390–1406` has the same `abilities.flying && !isRiding()` gate. It snapshots vertical velocity and `speedInAir`, adjusts air speed, invokes `super.moveRelative`, then applies `velocityY = g * 0.6`, restores `speedInAir`, clears `fallDistance`, and clears flag 7. The clear is unconditional within this wrapper branch and follows the completed glide movement in both versions.
- **Comparison boundary:** 1.10's auto-jump input guard and cached `falling` value do not change the manual-double-tap active-glide sequence or the after-move wrapper. No A/B gameplay, synthetic-state, network/latency, or runtime test was used.
