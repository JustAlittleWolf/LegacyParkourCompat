# Independent source audit: ability-flight fall-flying flag clear

**Verdict: accepted for the bounded claim; no 1.21 → 1.21.1 difference.** The frozen writer report's central claim is correct. In both releases, `Player.travel(Vec3)` takes the `abilities.flying && !isPassenger()` branch, dispatches `super.travel`, restores vertical velocity, resets fall distance, and directly calls `setSharedFlag(7, false)` (Player.java:1456–1477). There is no move-result, collision, ground, or logical-side condition around this final clear. In an initial state with both ability flying and fall-flying set, the superclass `LivingEntity.travel` takes its `isFallFlying()` arm, executes `move(SELF, ...)`, then on the logical client does not clear flag 7 at its own server-gated `onGround() && !isClientSide` check (LivingEntity.java:2151–2190). Control returns to Player.travel and reaches the unconditional clear, even if Entity.move resolves to zero displacement. The source establishes this overlap's behavior when those state preconditions hold; this audit does not claim how that combined state is entered during gameplay.

The real local-player move dispatch is `LocalPlayer.move` → `super.move` → `Entity.move`; the local override only measures X/Z displacement and calls `updateAutoJump` after `super.move` (LocalPlayer.java:881–886). `Entity.move` collision-resolves with `collide` and has no flag-7 write (Entity.java:598–725). Flag 7 is `FLAG_FALL_FLYING` in both Entity.java:209. `setSharedFlag(7, false)` clears only bit 7 of the shared flag byte, preserving other bits (Entity.java:2302–2313). The LocalPlayer synced-data callback's extra Elytra sound is gated on `isFallFlying() && !wasFallFlying`, so it is not a side effect of this false transition (LocalPlayer.java:516–531). Keep the scope precise: Player.travel also separately restores Y velocity and calls `resetFallDistance`; movement itself has its normal collision and entity-state effects. It would be inaccurate to say the entire wrapper or move path has no effects beyond flag 7.

Other relevant flag writers do not change that conclusion: `LivingEntity.travel`'s direct false setter is gated by on-ground and server-side; `LivingEntity.updateFallFlying` writes the computed flag only server-side; `Player.startFallFlying` writes true; `Player.stopFallFlying` writes true then false. NBT restoration writes true only when the saved value is true. These are unchanged across the pair. The distinction from reset-only behavior is concrete: `resetFallDistance()` changes fall distance and does not clear flag 7; the Player.travel wrapper has both a reset and the separate direct false setter.
