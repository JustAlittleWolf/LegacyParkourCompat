# Death direction inputs at status event 3

## Finding

The old client receives the death status event through the entity-event handler, but the event carries no angle. In the ordinary lethal-hit path, the preceding hurt-animation entity event 2 resets old client `damagedSwingDir` to `0.0F`; event 3 then invokes the old player death path using that reset value. The server-side old hit calculation can be nonzero, but that value is not delivered to the old client. Thus matching the event delivery does not imply matching the direction at death.

For an observable stream containing event 2 followed by event 3 for the same victim, with no intervening direction write, the historical input is losslessly recoverable as zero. A concrete nonzero state witness shows why forwarding modern `hurtDir` is not that mapping: victim at `(0,0,0)`, yaw `0`, direct living attacker at `(0,0,1)`, ordinary unblocked lethal melee. Old server formula computes 90 degrees, but received event 2 clears the client field to zero before event 3; modern direct-hit damage animation carries 90 degrees and `hurtDir` remains 90. The values are bit-distinct (`0.0F` versus `90.0F`) at the death response input. This is a client-state witness, not a mismatch in the direct-attacker angle formulas: for this simple input those source formulas yield the same 90-degree float.

The narrow constant-zero remap uses only the observed ordered event stream and current entity yaw; it needs no attacker identity, server authority, or damage simulation. It is not valid for arbitrary event-3 delivery. Sources that bypass event 2, stale or intervening animation state, blocked/NO_KNOCKBACK damage, environmental damage, projectiles, zero/near-zero horizontal offsets, and yaw changes between the relevant packet and death are outside the demonstrated domain. A byte-3 event by itself does not identify which case produced the death.

For a direct living attacker, the old 1.14.4 direction formula and 26.2 direct-source-position formula use corresponding horizontal offsets, `fastAtan2/atan2`, the same `180.0F`, float PI, yaw subtraction and final float cast. The 1.8.9/1.9.0 expression spells `180.0` as a double literal, but 180 is exactly representable as float and is promoted back to double; for identical finite inputs the operation sequence is otherwise equivalent. The source algorithms for `fastAtan2`/`Mth.atan2` retain the same inverse-square-root/table/interpolation structure. No nonzero bit-distinct angle-formula witness was established for identical direct-attacker inputs. That formula-level similarity does not change the packet-level reset: event 2 discards the calculated angle on the old client.
