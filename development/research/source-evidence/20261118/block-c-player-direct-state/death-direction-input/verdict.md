# Independent audit: death direction input

## Verdict

**COMPLETED.** The bound comparison is source-supported for its narrow ordered-event claim. In 1.8.9, 1.9 and 1.14.4, ordinary hurt event 2 clears the client-side `damagedSwingDir` to `0.0F`; server-side hit calculation can subsequently hold another angle, but that angle is not what event 3 makes the client player consume. In 26.2, an unblocked lethal direct-attacker hit sends the hurt animation angle before death event 3 for the bounded ordinary path. The byte-3 event itself does not invoke a player death response on the 26.2 client.

A meaningful nonzero relative witness confirms why modern `hurtDir` cannot simply be forwarded as the old client death input: victim at `(0,0,0)`, yaw 0, and direct living attacker at `(0,0,1)`, with ordinary unblocked lethal melee and no intervening state change. The old server computes 90 degrees, but old event 2 resets the client's field to zero, so old event 3 uses 0 degrees. The corresponding 26.2 direct-source-position angle is 90 degrees, stored by `animateHurt`; adding the unchanged yaw gives 90 degrees. If comparing the old client event-3 response with the modern `Player.die` formula, the horizontal directions differ (old `-X`, modern `-Z`, modulo exact float trig outputs). This is a relative-math witness, not evidence that the 26.2 client executes that modern response: its byte-3 branch explicitly skips `Player.die` for `Player`. This is a client-state / cue-to-response distinction, not a demonstrated difference between the direct-attacker atan formulas.

## Source checks

All three source hashes cited by the bound comparison match canonical files.

- **1.14.4 / Ornithe Feather:** server `takeDamage` computes direction (`LivingEntity.java:917-978`); client `animateDamage` resets it (`LivingEntity.java:1292-1296`), and event 2 also resets it while event 3 calls `die` (`LivingEntity.java:1419-1465`). Player death consumes that field plus yaw (`PlayerEntity.java:581-596`). All four cited source hashes match.
- **26.2 / unobfuscated:** `dealDefaultKnockback` uses the direct source-position delta and calls `indicateDamage` when unblocked (`LivingEntity.java:1290-1305`); `ServerPlayer.indicateDamage` computes and sends `hurtDir` (`ServerPlayer.java:2135-2138`); the client handler applies it through `animateHurt` (`ClientPacketListener.java:1125-1130`) and `Player.animateHurt` stores it (`Player.java:1959-1962`). `Player.die` consumes `hurtDir + YRot` (`Player.java:526-541`), while byte 3's `LivingEntity.handleEntityEvent` explicitly skips setting health and calling `die` for a `Player` (`LivingEntity.java:2067-2082`). Cited 26.2 hashes match.
- **Ordering dependency:** the bound delivery audit has SHA-256 `7e2687b9cc7c28c73d2712d7d363e6c2a8f68dc3a896c0130cad145e6dc6104c`, verified unchanged. It supports the ordinary unblocked lethal direct-attacker sequence only: hurt-animation angle before the controlling client's byte 3. It also explicitly says health and motion synchronization have no universal total order relative to death packets.

## Implementation-ready boundary

A client movement operation may use zero as the historical death-direction input only when it observes the same victim's actual historical hurt cue/event-2 reset followed by byte 3, with no intervening direction write. For the modern ordinary-hit path, the corresponding usable cue is the same-victim hurt-animation packet followed by byte 3; apply the historical player response at byte 3 using the victim's current yaw, because the modern byte-3 handler does not run `Player.die`. Keep the cue/order gate explicit and preserve native fallback when it is absent. The claim does not authorize synthesizing death direction from attacker identity, damage simulation, or `hurtDir`.

The comparison is not accepted for arbitrary byte-3 delivery. Projectiles, environmental or other non-direct damage, blocked/`NO_KNOCKBACK` hits, missing or reordered cues, intervening direction/yaw changes, and other death producers remain outside the witness. In particular, a modern animation angle is only an ordered observable cue for the stated ordinary unblocked hit, and current-vs-hit-time yaw must remain a closed applicability condition for any implementation that uses that angle. No intermediate release boundary or runtime parity is established.
