## Bounded operation 1: ordinary Overworld to End portal transfer

- `EndPortalBlock.onEntityCollision`: 1.9.2 `EndPortalBlock.java:62-70`; 1.9.3 `:63-71`. Same gates and order: not riding, no passengers, can use portals, logical server (`!world.isClient`), player/entity shape intersects the moved portal shape; then `entity.changeDimension(1)`. The 1.9.3 `@Nullable` annotation changes are outside this collision method's behavior.
- `ServerPlayerEntity.changeDimension(int)`: 1.9.2 `ServerPlayerEntity.java:455-484`; 1.9.3 `:458-487`. Same teleportation-state write; same End-entry stat check for current dimension 0 and requested dimension 1; same call into `PlayerManager.changeDimension`; same post-return `WorldEventS2CPacket(1032, BlockPos.ORIGIN, 0, false)` and resets of last-sent XP, health, and hunger trackers.
- `PlayerManager.changeDimension(ServerPlayerEntity,int)`: 1.9.2 `PlayerManager.java:488-513`; 1.9.3 `:489-514`. In both, `int i = player.dimension` captures the old dimension and old source world before `player.dimension = dimension`; target world is then resolved from the updated field. The respawn packet is sent before old-world removal/helper transfer and uses the updated dimension with the player's current world difficulty/generator and game mode. The helper receives captured `i`, not a re-read destination value. After it returns: `onChangedDimension`, absolute `networkHandler.teleport(player.x, player.y, player.z, player.yaw, player.pitch)`, interaction-manager world update, abilities packet, target world info, player info, then status-effect packets. This sequence is identical across the pair.
- `PlayerManager.changeDimension(Entity,int,ServerWorld,ServerWorld)`: 1.9.2 `PlayerManager.java:515-568`; 1.9.3 `:516-569`. With the ordinary 0-to-1 call, `entity.dimension` has already been set to 1 while the helper parameter remains captured old dimension 0. Thus the helper takes its final initial branch (not the -1 or 0 field branches), chooses the target forced spawn point because the helper parameter is not 1, directly assigns the chosen Y, then calls `setPositionAndAngles(..., 90.0F, 0.0F)` and source-world `tickEntity(entity,false)` under an `isAlive()` gate. Since the captured parameter is 0, `dimension != 1` is true for the placing stage: it integer-casts and clamps X/Z, then under a second `isAlive()` gate calls `setPositionAndAngles`, `toWorld.getPortalForcer().onDimensionChanged(entity,g)`, target `addEntity`, and target `tickEntity(entity,false)`. Finally it calls `entity.setWorld(toWorld)` outside that alive gate. The same field/parameter distinction, casts, gates, helper calls, order, and unconditional world write are present in both versions. This records the named source path only; it makes no assertion about spawn geometry or another dimension route.
- `ServerPlayNetworkHandler.teleport` overloads: 1.9.2 and 1.9.3 `ServerPlayNetworkHandler.java:490-516`. The five-argument call delegates with `Collections.emptySet()`. In the six-argument method, empty flags make requested position exactly `(x,y,z)` and rotation exactly `(yaw,pitch)`; it stores the absolute requested position, advances teleport ID (wraps `Integer.MAX_VALUE` to 0), records tick time, directly updates server player position/angles, and sends `PlayerMoveS2CPacket(x,y,z,yaw,pitch,emptySet,id)`. Method content is identical.

## Bounded operation 2: logical-client packet handling and acknowledgment

- `PlayerMoveS2CPacket`: 1.9.2/1.9.3 `PlayerMoveS2CPacket.java:34-52` and `:86-127`. Both read/write three doubles, yaw/pitch floats, relative-argument byte, then teleport ID VarInt. `Argument.getFlags(emptySet)` yields zero; `byFlags` reconstructs the empty set. Packet source and mapping hashes are identical across releases.
- `ClientPlayNetworkHandler.handlePlayerMove`: 1.9.2 `ClientPlayNetworkHandler.java:545-594`; 1.9.3 `:546-595`. Same handler: starts from packet XYZ/yaw/pitch; adds existing player components only for set relative bits, otherwise directly writes each corresponding velocity component to `0.0`; adds current angles only for relative angle bits; calls `updatePositionAndAngles`; sends `AcceptTeleportC2SPacket(packet.getTeleportId())`; then sends `PlayerMoveC2SPacket.PositionAndAngles(player.x, player.getShape().minY, player.z, player.yaw, player.pitch, false)`. First-packet startup bookkeeping follows those sends. With the server's empty relative set, the three direct zero-velocity writes occur and all coordinates/angles are absolute. Identical method behavior across the pair.
- `AcceptTeleportC2SPacket.write`: both releases write the ID as a VarInt; `ServerPlayNetworkHandler.handleAcceptTeleport` accepts only when the ID matches the outstanding requested ID, writes the requested absolute position back through `updatePositionAndAngles`, updates last-good XYZ and clears teleportation state only when applicable, then clears the requested position. The packet and handler are identical for this acknowledgment path.
- The follow-up movement packet is the `PositionAndAngles` subclass: it writes double X, double minY, double Z, float yaw, float pitch, then inherited on-ground byte (`false` here). The same writer is present in both releases. The absolute server teleport handler is the observed transfer path that zeros client XYZ velocity; no claim is made here about unrelated packet arrivals or later trajectory.
