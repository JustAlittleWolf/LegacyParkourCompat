## Per-claim verdict

- **Exact releases, mappings, provenance and no-difference verdict — supported.** The closure names 1.9 and 1.9.1 with Ornithe Feather build 2. Manifest SHA-256 values and pinned client/Feather artifact hashes match the independent audit. Every source file relied on for the bounded transition and packet claims has the same per-file SHA-256 in both source manifests; actual bytes match. The closure's additional `PlayerMoveC2SPacket.java` digest also matches both actual files and manifests.
- **EndPortalBlock to virtual ServerPlayer path — supported.** `EndPortalBlock.onEntityCollision` calls `entity.changeDimension(1)` under the stated logical-server/entity-shape gates. Dispatch for a ServerPlayer reaches `ServerPlayerEntity.changeDimension`, which calls `PlayerManager.changeDimension` for the ordinary dimension 0 -> 1 case.
- **Helper argument and End spawn accessor — supported; corrects the frozen roster's earlier interpretation.** `PlayerManager.changeDimension(ServerPlayerEntity,int)` captures `i = player.dimension` while it is still 0, updates `player.dimension` to 1, then calls the helper with `i`. Thus the helper argument named `dimension` is 0 while `entity.dimension` is 1. The helper's final branch chooses `toWorld.getForcedSpawnPoint()` (the helper argument is not 1), and the subsequent `dimension != 1` condition is true. My frozen roster incorrectly treated the helper argument as destination 1 and incorrectly claimed that this transition uses `getSpawnPoint()` and skips the placing block. The roster remains immutable; this verdict supersedes that incorrect past disposition.
- **Alive gates, placement, PortalForcer and order — supported.** The helper first selects the forced spawn point and sets position/angles `(x,y,z,90F,0F)`; if alive, it ticks the source world with `tickEntity(entity,false)`. After popping the moving profiler, its `dimension != 1` branch clamps `(int)d` and `(int)e`; under a second alive gate it sets position again, calls the destination `PortalForcer.onDimensionChanged(entity,g)`, adds the player to the destination, then calls destination `tickEntity(entity,false)`. Finally `entity.setWorld(toWorld)` runs. Both alive-gated transfer blocks are reachable on ordinary Overworld -> End. The helper has a third alive-gated source-tick site in its `entity.dimension == 0` branch, which is not selected after the player dimension was already changed to 1. `PortalForcer`'s End branch creates the End platform, sets entity position/angles and zeros velocity XYZ; this occurs before the final network correction.
- **Absolute correction and client XYZ/velocity/ACK/PosRot order — supported.** After helper and `onChangedDimension`, PlayerManager calls `networkHandler.teleport(player.x, player.y, player.z, player.yaw, player.pitch)` before abilities/world/player/status packets. The empty relative set produces an absolute player-move correction and pending absolute target. The client handles respawn first; on the correction, absent X/Y/Z relative flags leave packet XYZ absolute and clear velocity X, then Y, then Z; it applies position/angles, sends teleport ACK, then sends `PlayerMoveC2SPacket.PositionAndAngles` with X, shape.minY, Z, yaw, pitch, and onGround false. Reset `started` then causes lastX/Y/Z to be initialized from the corrected position.
- **Accepted-position writes — supported with a scope caveat.** Matching `handleAcceptTeleport` reapplies the pending target. Only while `isInTeleportationState()` it writes `lastGoodX/Y/Z` from the request and calls `onTeleportationDone()`; then it clears the request. It does not write `firstGoodX/Y/Z`. Those fields are initialized together by `resetPosition`; therefore do not describe the ACK handler as updating both firstGood and lastGood.
- **Source difference or runtime claim — none.** No source difference is present in the assigned exact slices. This is source-only bounded closure and does not establish runtime parity or destination geometry.
