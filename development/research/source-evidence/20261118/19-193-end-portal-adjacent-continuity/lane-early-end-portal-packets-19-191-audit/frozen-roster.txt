Call path and ordering

- ServerPlayerEntity.changeDimension (455-483) marks inTeleportationState; for dimension 0 -> 1 records ENTER_THE_END, assigns dimension 1, then calls PlayerManager.changeDimension(player, 1).
- PlayerManager.changeDimension(ServerPlayerEntity,int) (488-513) saves source dimension, obtains source world, assigns the new player.dimension, gets destination world, sends PlayerRespawnS2CPacket, updates permissions, removes the player now, clears removed, calls the helper, updates chunk tracking, sends absolute teleport, updates interaction world, then sends abilities/world/player/status info.
- PlayerManager.changeDimension(Entity,int,ServerWorld,ServerWorld) (515-568) snapshots x,z and yaw, sets f=8.0, opens moving profiler. As caller assigned dimension=1 first, helper sees entity.dimension==1 and reaches the final branch. Since the requested dimension is 1, that branch uses toWorld.getSpawnPoint() (not getForcedSpawnPoint()), sets x/y/z to spawn coordinates and yaw/pitch to 90F/0F, then while alive calls fromWorld.tickEntity(entity,false). It pops moving; dimension != 1 is false, so the placing block does not run (no PortalForcer/addEntity/destination tick); finally entity.setWorld(toWorld).
- Entity.changeDimension base method (approx. 1820-1880) is not the ServerPlayerEntity route. Its generic dimension==1 branch uses getForcedSpawnPoint(); retain this as a distinct non-player implementation and do not substitute it for the virtual ServerPlayer override/helper path.
- The helper contains three isAlive-gated fromWorld.tickEntity(entity,false) call sites in its -1, 0, and final branches. The ordinary Overworld-to-End player call reaches only the final branch (one such call); its dimension==1 guard skips the later placing block and its unguarded toWorld.tickEntity call. The separate spectator transfer handler has two calls under one alive gate (ServerPlayNetworkHandler.handlePlayerSpectate 643-693), outside this ordinary End Portal route.
- PortalForcer.onDimensionChanged is called from PlayerManager only inside the helper placing block (dimension != 1), so ordinary End entry bypasses it. PortalForcer itself distinguishes non-End Nether frame search/generation from End platform generation; neither changes this End-entry call order.

First handled movement after reset seeds lastX/Y/Z, sets started and closes terrain screen.

A mismatched ID does not execute this body or clear the request.
