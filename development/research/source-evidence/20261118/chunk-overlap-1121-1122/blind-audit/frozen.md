# Blind source audit: local player overlapping an unavailable chunk

## Identity and scope

Compared Minecraft 1.12.1 and 1.12.2, both published under Ornithe Feather (`ornithe-feather`). The 1.12.1 mapping-root `.decompile-provenance.json` pins the release metadata and client artifact, Feather metadata and `feather-gen2-1.12.1+build.2-mergedv2.jar`; it records Vineflower 1.12.0, Tiny Remapper 0.14.1, Java 25.0.3+9-LTS on Windows 11. The 1.12.2 version-root `ornithe-feather.provenance.json` identifies version 1.12.2, Feather build.2 mergedv2 plus Tiny inputs, and the same decompiler/tool versions. Its ready marker pins client SHA-256 `8ada07da5ee77dad3527bd7278fbd05ee1fc8a597813b216a871a2d7d64cc64f`, source manifest SHA-256 `b8a37ccfccd2aac5f40f5e34fec85873dbdfa93a266043c103e592e4a8c949da`, and 2050 source files. The verification marker says all 2050 published source files and raw input artifacts matched its independent verification; one regenerated intermediate remap JAR differed, explicitly excluded from the source identity. Relevant sources were read from the canonical `decompiled_minecraft/<version>/ornithe-feather/` trees only.

This audit covers ordinary S2C chunk-forget/cache lifecycle, whether an unavailable chunk can be under the local player's box at a movement query, and that query's cache behavior. Server sources are used only to establish possible schedule inputs. It does not assess collision geometry, full pair coverage, or runtime parity.

## Source trace

- `1.12.1/net/minecraft/server/ChunkMap.java:249-280` (`movePlayer`): after the server player's tracked position differs by squared XZ distance at least 64 and its chunk coordinate changes, it adds newly in-view square positions and removes positions that leave the old view square. This is a square range, not a movement collision rule. `ChunkMap.java:327` clamps server view distance to 3–32 chunks. The method does not itself establish the client's local predicted position at packet application time.
- `1.12.1/net/minecraft/server/ChunkHolder.java:61-76` (`removePlayer`): for a populated chunk, sends `ForgetWorldChunkS2CPacket` to that player before removing the player from the holder. This is the server-side schedule source; the client cache is changed only when that packet is handled.
- `1.12.1/net/minecraft/client/network/handler/ClientPlayNetworkHandler.java:664-668` (`handleForgetWorldChunk`) calls `PacketUtils.ensureOnSameThread`, then `world.updateChunk(x,z,false)`. `ClientWorld.java:155-161` forwards `false` to `ClientChunkCache.unloadChunk` and notifies the changed region. `ClientChunkCache.java:33-40` unloads a nonempty chunk and removes its coordinate key. There is no player-box or player-distance guard.
- `ClientChunkCache.java:23-27, 42-58`: the cache has one `EmptyChunk` fallback; `getChunk(x,z)` returns the mapped chunk or that fallback for any missing coordinate. `ClientWorld.java:105-107` defines `isChunkLoadedAt(x,z,allowEmpty)` as `allowEmpty || !getChunkSource().getChunk(x,z).isEmpty()`. Since `World.isChunkLoaded(pos)` delegates with `allowEmpty=true` (`World.java:186-192`), a missing client chunk reports loaded to callers using that default. `World.java:680-686` then reads the fallback chunk's block state; the empty chunk supplies air.
- The first movement-time contact query is directly reachable from `Entity.move` (`Entity.java:462 onward`): the sneaking edge check, when applicable, and then the swept-box collision query at `Entity.java:525-568` call `World.getCollisions`. That scan (`World.java:964-1019`) checks `isChunkLoaded(pos)` before reading block state. On this client, the default `allowEmpty=true` makes the check pass even when the chunk map has no entry, so `getBlockState` reads the empty fallback and contributes no block collision. Later in the same move, `Entity.java:705-710` samples the block under the feet for fall/step handling. `checkBlockCollisions` (`Entity.java:812-840`) is another direct state read after its default-allow-empty area check. This is the source-level fallback; no historical shape claim is made.
- The client can be placed at a server-provided position without checking chunk presence: `ClientPlayNetworkHandler.java:578-620` (`handlePlayerMove`) resolves relative coordinates, calls `playerEntity.updatePositionAndAngles(...)`, then acknowledges the teleport. The method has no chunk-availability gate. Therefore a position in a previously forgotten chunk is reachable as client state, including a box overlapping that missing coordinate.

## Bounded conclusion and residual

A server view-window departure can make a cache coordinate unavailable, and a later absolute server player-position correction can put the local player at that coordinate. If the local movement tick queries the world before a replacement full-chunk packet is applied, the first swept collision/contact scan treats the missing chunk as the shared empty chunk through the client `allowEmpty=true` path. This establishes a concrete conditional source path to overlap and fallback, beyond mere receipt of a forget packet.

The exact interval between handling that correction and handling the replacement chunk packet is not established by these source excerpts. `ensureOnSameThread` establishes main-thread handling but not which client tick observes the gap; chunk preparation/population and network ordering are outside this bounded trace. Thus this is a reachable condition with a timing gate, not proof that an ordinary continuous walking schedule produces an overlapping movement tick, nor a guarantee that every correction does. For ordinary tracked movement, range departures are behind the server's tracked view center by the configured multi-chunk margin; no source-proven continuous-walk overlap witness was found. Establishing that stronger claim needs bounded packet/tick schedule evidence or runtime observation, both outside this audit.

## 1.12.2 cross-check

The packet handlers retain the same lines and lifecycle (`ClientPlayNetworkHandler.java:639-668`); `ClientWorld.java:105-107,155-161`, `ClientChunkCache.java:33-58`, and the relevant `World.java` and `Entity.java` operations retain the same behavior. `Entity.java` and `ClientChunkCache.java` are byte-identical across the compared source trees. The client handler, client world, and `World.java` files differ elsewhere, but the bounded methods above do not change in the inspected excerpts. This audit identifies no 1.12.1→1.12.2 behavioral delta for this operation; the overlap timing gate remains open on both releases.
