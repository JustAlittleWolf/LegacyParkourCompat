## Trace and comparison

The client handler applies `ForgetWorldChunkS2CPacket` on the client thread and calls `ClientWorld.updateChunk(x, z, false)` (both releases: `net/minecraft/client/network/handler/ClientPlayNetworkHandler.java:664–667`). `ClientWorld` delegates to `ClientChunkCache.unloadChunk`; the cache unloads a nonempty chunk and removes its entry (`ClientWorld.java:155–161`; `net/minecraft/client/world/chunk/ClientChunkCache.java:33–40`). Both releases are identical through this path. An absent cache entry resolves to the shared `EmptyChunk` (`ClientChunkCache.java:44–57`), whose `getBlockState` returns the air state (`net/minecraft/world/chunk/EmptyChunk.java:39–42`).

At a missing chunk, direct state reads therefore return air in both versions: `World.getBlockState` obtains the chunk and reads its state (`net/minecraft/world/World.java:680–687`). The ordinary movement collision query also treats empty chunks as admissible for querying: `World.isChunkLoaded(pos)` passes `allowEmpty=true` (`World.java:186–191`), while `ClientWorld.isChunkLoadedAt` returns true when `allowEmpty` is true (`ClientWorld.java:105–107`). `World.getCollisions` uses that default query before reading each candidate block (`World.java:964–1002`), so a missing chunk contributes its empty-chunk/air state rather than suppressing the query. `Entity.checkBlockCollisions` likewise uses the default `isAreaLoaded` overload and then calls `getBlockState` for blocks in the player's box (`net/minecraft/entity/Entity.java:812–835`). `LocalClientPlayerEntity.tick` also uses the default `isChunkLoaded` at the player's position before ticking (`net/minecraft/client/entity/living/player/LocalClientPlayerEntity.java:164–177`). These exact code paths and results are unchanged in 1.12.2.

The normal server schedule is source-bounded spatially. `ChunkMap.updateViewDistance` clamps the view radius to at least three chunks (`net/minecraft/server/ChunkMap.java:289–291`). `movePlayer` reconciles square chunk windows centered on the server's player chunk (`ChunkMap.java:249–280`); a chunk removed from that window is at least four chunk columns from that center. `ChunkHolder.removePlayer` sends the forget packet for that chunk (`net/minecraft/server/ChunkHolder.java:60–69`). Thus, at the authoritative position used to schedule an ordinary unload, its target is not adjacent to the player box.

A delayed clientbound unload could be received after local prediction has advanced or reversed. The client continues local ticking between movement packets, and the source does not impose a delivery-time bound or establish how a delayed unload interleaves with a later chunk-data packet and client tick. The server schedule alone therefore does not prove an ordinary movement tick with the player box overlapping an unavailable chunk; such a witness would require a transport/tick-order bound or a concrete delayed-packet schedule. Receipt timing is a possible external condition, not a pair-specific source difference.

## Verdict and residuals

No eligible 1.12.1 → 1.12.2 difference was found in client chunk unload handling, empty-chunk fallback, chunk availability gates used by movement collision/block-contact queries, or their cited player callers. The inspected pair-local file changes are elsewhere (the client handler's terrain-screen constructor, client ambient-cave-sound conditions, and inventory-screen handling); they do not alter this bounded operation. No canonical finding is eligible. The report does not establish full-pair movement coverage or runtime parity, and it does not claim a bounded network-delay witness.
