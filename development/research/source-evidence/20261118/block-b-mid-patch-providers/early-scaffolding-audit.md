## Verdict by edge

- **1.18 → 1.18.1: no collision-provider difference.** `ScaffoldingBlock.getCollisionShape` is byte-identical by file hash (lines 117–123 in each); `EntityCollisionContext`, `BlockCollisions`, and `Entity` are also byte-identical. For a fixed state and identical context, the provider shape and collision-consumer/step behavior are equivalent.
- **1.18.1 → 1.18.2: no dry Scaffolding collision-provider difference.** The Scaffolding source file differs, but the collision provider at lines 117–123 and shape constants at lines 157–168 are unchanged. The changed Scaffolding body is the scheduled-tick unsupported-block branch at lines 97–108: `FallingBlockEntity` creation changes to `FallingBlockEntity.fall(...)` at line 102. That is a special block-update/falling-entity path, excluded here. `EntityCollisionContext` changes its fluid-support API from `FlowingFluid` to `FluidState` (1.18.2 `CollisionContext.java` lines 6, 23; `EntityCollisionContext.java` lines 23, 27, 52–54); it does not change constructor capture, `isDescending`, or `isAbove`, and is irrelevant for the specified dry provider. `BlockCollisions` is byte-identical. `Entity` changes elsewhere, but the collision routine and step gates preserve the same expressions/order (1.18 lines 767–790, 793–843; 1.18.2 lines 777–800, 803–854).

## Bounded behavior trace

- **State/geometry:** A legal supported state satisfies `DISTANCE < 7` (`canSurvive`, ScaffoldingBlock lines 111–114); the selected dry fixed state has `WATERLOGGED=false`, which this collision provider never reads. `BOTTOM` is set by `isBottom` when distance is positive and the block below is not scaffolding (lines 130–132). `STABLE_SHAPE` is the top 2/16 plate plus four full-height 2/16 corner posts (lines 157–163); `UNSTABLE_SHAPE_BOTTOM` is a bottom 2/16 plate (line 29, referenced at line 121). These fixed geometries do not vary across the three releases.
- **Context capture and strict threshold:** `BlockCollisions` captures one context when constructed: empty for null entity, otherwise `CollisionContext.of(entity)` (lines 30–36); it passes this context to each candidate state's `getCollisionShape` (lines 65–89). `EntityCollisionContext(Entity)` snapshots `entity.isDescending()`, `entity.getY()`, held main-hand item and fluid predicate (1.18/1.18.1 lines 37–45; 1.18.2 lines 35–43). `Entity.isDescending()` is `isShiftKeyDown()` (1.18/1.18.1 line 1938–1940; 1.18.2 lines 1951–1953), so this gate represents sneaking, not negative vertical velocity. `isAbove` is the strict test `entityBottom > blockY + shape.maxY - 1.0E-5F` (1.18/1.18.1 lines 64–65; 1.18.2 lines 62–63); equality fails. For `Shapes.block()` the top branch threshold is feet above blockY + 1 - epsilon. For `BELOW_BLOCK`, whose max Y is zero after shifting a full block down one, the support test is feet above blockY - epsilon.
- **Top, support, underside and sides:** Scaffolding's first branch returns the stable top-and-post shape exactly when feet pass the full-block strict threshold and the captured context is not descending/sneaking (ScaffoldingBlock lines 117–120). If that branch fails, it returns only the bottom plate when `DISTANCE != 0`, `BOTTOM`, and the strict below-block test all hold; otherwise it returns empty (lines 120–122). Thus distance-zero or non-bottom ordinary states have no fallback collision from below or at sides; a legal bottom state can expose the thin bottom plate when feet are above the block-bottom threshold. A player genuinely underneath the block with feet at or below that threshold gets no fallback plate. At side height below the top threshold, the ordinary state yields no provider shape; at/above the top threshold and not sneaking, side encounters can meet the posts/top plate. These are provider outputs; actual displacement depends on AABB intersection and axis clipping.
- **Consumer and step gates:** `BlockCollisions.computeNext` only queries eligible scanned blocks and returns nonempty shapes that intersect the entity AABB (lines 65–89); `Entity.collide` resolves Y first, then horizontal axes, then optionally compares step alternatives (1.18 lines 767–790, 809–843; 1.18.2 lines 777–800, 819–854). A step attempt requires `maxUpStep > 0`, the entity already on ground or blocked while moving downward, and a blocked horizontal component; it replaces normal movement only when its horizontal distance squared is larger (same line group). The earlier `Entity.move` passes the movement request through `collide`, then derives collision/on-ground state; these gates are unchanged in the reviewed bodies. This matters for whether returned top/post geometry participates in a step, but introduces no provider difference across the edges.

## Exclusions and limits

This verdict covers only dry, stable/legal fixed Scaffolding states, the collision-provider context and its ordinary entity collision/step consumer. It is not a full pair audit. Outline `getShape` and interaction geometry (`ScaffoldingBlock` lines 46–58), climb/contact behavior, waterlogged fluid production (`getFluidState`, lines 125–128) and fluid standing/support API changes are separate/excluded effects. The 1.18.2 scheduled-tick/falling-block update is also excluded. No source edit, build, test, or runtime was performed.
