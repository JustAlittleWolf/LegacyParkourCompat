# Blind source audit: 1.19.4 → 1.20 fluids

Status: frozen independent source roster and verdicts. Scope is normal non-riding local-player water/lava fluid admission and height, flow normalization/push, eye-fluid state writer and order, and first normal water/lava travel drag/gravity gates. The comparison assumes identical effective water/lava tag membership, world fluid states/flows, and other inputs. Elytra and creative movement, vehicle behavior, unrelated callbacks, solid geometry, damage, custom data, whole-pair coverage, product/runtime, and intermediate patch boundaries are excluded.

## Frozen per-operation roster

1. **Water/lava body-fluid admission and sampled height — NO DIFFERENCE.** `Entity.updateInWaterStateAndDoFluidPushing` and `updateInWaterStateAndDoWaterCurrentPushing` clear the fluid-height map, sample water before lava, and set `wasTouchingWater` from the water update. `updateFluidHeightAndDoFluidPushing` rejects touching an unloaded chunk, deflates the entity box by `0.001`, scans floor(min) to ceil(max) on each axis, admits matching fluid cells only when their surface `cellY + getHeight(...)` is at least the deflated box minimum Y, and records the maximum surface overlap. `isInWater` reads `wasTouchingWater`; `isInLava` requires `!firstTick` and positive sampled lava height. These gates, iteration order, bounds, threshold and state writes match under the fixed tag/world inputs. Evidence: 1.19.4 `Entity.java:1033-1035,1072-1094,1177-1179,2887-2965`; 1.20 `Entity.java:1137-1139,1176-1198,1280-1282,3001-3079`.

2. **Fluid-flow averaging, player normalization exception, and velocity push — NO DIFFERENCE.** For each admitted fluid cell the source scales its flow by the current maximum overlap only while that overlap is `< 0.4`, accumulates flow, and increments the contributor count only when `isPushedByFluid()` is true. A nonzero sum is divided by contributor count, normalized only for entities that are not `Player`, scaled by the passed strength, and given the same minimum-push correction when horizontal velocity components are each below `0.003` and push length is below `0.0045000000000000005`; it then adds to delta movement. Thus a normal local player retains the unnormalized averaged direction in both releases. Water uses `0.014`; lava uses `0.007` in ultra-warm dimensions and `0.0023333333333333335` otherwise. No arithmetic, ordering, normalization, gate or write difference found. Evidence: 1.19.4 `Entity.java:1072-1078,1080-1094,2458-2460,2887-2965`; 1.20 `Entity.java:1176-1182,1184-1198,2565-2567,3001-3079`.

3. **Eye-fluid writer and base-tick order — NO DIFFERENCE.** `baseTick` calls body fluid update/push, then `updateFluidOnEyes`, then `updateSwimming` on both releases. The eye writer first assigns `wasEyeInWater = isEyeInFluid(WATER)`, clears `fluidOnEyes`, computes `eyeY - 0.11111111F`, samples the fluid state at the floored eye X/Y/Z, and adds that state’s tags only if its surface is strictly above the sample Y (subject to the same boat exclusion, unreachable for the assigned non-riding case). Writer order and strict comparison match. Evidence: 1.19.4 `Entity.java:430-432,1096-1108,1173-1175`; 1.20 `Entity.java:434-436,1200-1212,1276-1278`.

4. **First normal water/lava travel branch: drag and gravity gates — NO DIFFERENCE in the bounded fluid branch.** With local control, both releases initialize gravity to `0.08`, derive the same nonpositive-vertical-velocity gate, and reduce gravity to `0.01` under Slow Falling. The water branch requires `isInWater && isAffectedByFluids && !canStandOnFluid(current block fluid)`; it retains the same sprint/slowdown drag, Depth Strider cap and airborne factor, Dolphin’s Grace override, movement order, vertical `0.8F` drag, fluid-fall adjustment, and collision step-up probe. The lava branch has the same `isInLava && isAffectedByFluids && !canStandOnFluid(...)` gate, input movement, threshold comparison, shallow/deep drag, fall adjustment and conditional `-gravity / 4.0` application. Elytra fallback is outside scope. Evidence: 1.19.4 `LivingEntity.java:1983-2044`; 1.20 `LivingEntity.java:2004-2064`.

5. **Adjacent Slow Falling side effect in the shared travel preamble — DIFFERENCE; bounded consequence is fall-distance state only.** When local control is active, vertical velocity is nonpositive and Slow Falling is present, 1.19.4 sets gravity to `0.01` and calls `resetFallDistance()`; 1.20 sets gravity to `0.01` but omits that reset. This changes an adjacent movement-state write for an otherwise matching water/lava branch precondition; it does not change the branch’s gravity value, drag, branch gate or velocity arithmetic. Evidence: 1.19.4 `LivingEntity.java:1983-1990`; 1.20 `LivingEntity.java:2004-2011`.
