# Independent verdict: full-stone first-tick piston starting state

## Verdict

**ACCEPT, narrowly and conditionally.** The accepted 1.10.2 full-stone overlap witness is unreachable from an initially non-penetrating local-player box under collision-resolved movement before the first moving-block-entity tick. The destination `MovingBlock` collision shape is already the carried full stone at progress zero; the fact that the old source cell is air does not erase that collision. A reachable east-face contact with player X `[0, 0.6]`, Y/Z positively overlapping the cube, requests `+0.51` in both 1.10.2 and 1.11 on the first extension tick.

This verdict does not revise the already accepted broad-union/raw-overlap arithmetic, and it does not generalize beyond the exact full cube and path conditions below.

## Independent source trace

- The server queues and dispatches an ordinary piston block event (`ServerWorld.java`, both releases, `doBlockEvents` around lines 954–985). The packet dispatches to `ClientPlayNetworkHandler.handleBlockEvent`; that handler calls `PacketUtils.ensureOnSameThread` and `world.addBlockEvent` (1.10.2 lines 1048–1050; 1.11 lines 1065–1067). `World.addBlockEvent` synchronously calls the current block state's `doEvent` (1.10.2 lines 2577–2578; 1.11 lines 2574–2575). For type 0, `PistonBaseBlock.doEvent` runs the extension on the client as well as the server (1.10.2 lines 147 onward; 1.11 lines 151 onward).
- The ordered extension loop clears each carried source cell, writes a `MovingBlock` at the next cell, and then installs its `MovingBlockEntity` there (`PistonBaseBlock.move`, 1.10.2 lines 278–328; 1.11 lines 267–317). The entity constructor leaves `progress` and `lastProgress` at Java's `0.0F` defaults. For an ordinary non-source full-stone extension, its progress-zero shape is the full stone cube shifted one block opposite the facing, at the moving entity's destination position (`MovingBlockEntity.getShape`, 1.10.2 lines 80–89; 1.11 lines 96–105).
- There is a synchronous `setBlockState` then `setBlockEntity` interval at each destination. The packet handler is on the client main thread; the state writes and BE installation run in the same event dispatch, so the normal player tick cannot interleave between them. Ordered multi-block movement also processes the resolver list from its end toward its beginning. No normal source path inspected moves the player or yields between clearing a source cell and installing the moving destination. Once installed, `MovingBlock.getCollisionShape` (1.10.2 lines 134–142; 1.11 lines 129–145) delegates to that moving entity. In 1.11 its explicit `addCollisions` delegation and progress-zero `NOCLIP_DIR` gate preserve the old cube for ordinary collision queries; the suppression applies while the piston itself moves the entity, not during the preceding ordinary player movement.
- On a client tick, `Minecraft` calls `world.tickEntities` (1.10.2 line 1438; 1.11 line 1417). `World.tickEntities` ticks players and regular entities before ticking block entities (1.10.2 around lines 1270–1323; 1.11 around 1292–1345). The first BE tick therefore starts from zero progress after the local player's ordinary collision-resolved movement.
- At zero progress, `MovingBlock.getCollisionShape` returns the old full cube even though the carried block's original source cell is air. `World.getCollisions` scans each horizontal coordinate from `floor(min)-1` through `ceil(max)` (exclusive upper bound `ceil(max)+1`) and checks the chunk before querying its block state (1.10.2 line 903 onward; 1.11 line 960 onward). Any query box that positively intersects the old cube includes the moving destination cell in this over-inclusive scan. A truly intersected X/Z cell cannot be one of the outer scan-edge cells because of the extra cell on each side, so the `q == 2` corner skip does not discard the relevant cube; the Y loop includes intersected rows. `Block.addCollisions` uses strict intersection (1.10.2 around lines 342–352; 1.11 around 353–363). Entity movement therefore clips against the progress-zero moving full stone if its swept player box attempts to enter the cube.
- For reachable boundary geometry, player X `[0, 0.6]` touches the moving full stone's east face at X=0, without interior overlap. With positive Y/Z overlap, the first 1.10.2 BE tick updates to progress 0.5 and evaluates its prior/current union; the eastward amount is `0.5 - 0 + 0.01`. In 1.11 the first BE tick calls `moveEntities(0.5)` while stored progress is zero, evaluates the sweep `[0, 0.5]`, caps the requested amount at the half-step, and adds `0.01`. Both request +0.51 X. The full-stone face contact is reachable while the accepted interior-overlap witness is blocked before that tick.

## Applicability and unresolved gate

Acceptance is limited to an initially non-penetrating local player using ordinary collision-resolved movement; an exact full-stone cube; an eastward extension; correctly synchronized piston/full-stone source state; the moving destination and all queried collision chunks remaining loaded/active; no spawn, teleport, no-clip, or other external position writer; and no external world-state write between the event and first BE tick. The claim does not cover non-full blocks, other facings, later progress ticks, unloaded chunks, or arbitrary injection into a penetrating position. Those cases remain unreviewed rather than inferred from this source trace.

No build, tests, game launch, TAS, or runtime parity check was performed.
