# Independent audit verdict: 1.20.4 to 1.20.5 ability flight / glide clear

## Signed result

**PARTIAL ACCEPTANCE — correction required.** I independently confirm that the direct `Player.travel` ability-flight flag-7 clear remains after `super.travel` and `resetFallDistance()` in both exact releases. For an airborne local player with bit 7 true, an enabled ordinary chest Elytra, no passenger state, and `abilities.flying == true`, the superclass can perform that tick's glide movement before `Player.travel` resets fall distance and clears bit 7. The source report's grounded-client conclusion is not supported: `updateFallFlying()` computes a false local flag when grounded, but only writes it back on the logical server. On the client, `isFallFlying()` still reads shared flag 7, so an already-true bit remains visible to `LivingEntity.travel` until the later `Player.travel` clear. The report must not say that the grounded client state is rejected before travel.

## Findings

1. **Unchanged direct clear and its timing — accepted.** In 1.20.4 `Player.travel` (1451–1472) and 1.20.5 (1473–1494), the `abilities.flying && !isPassenger()` branch saves current Y velocity, calls `super.travel`, restores Y to the saved value times `0.6`, calls `resetFallDistance()`, then calls `setSharedFlag(7, false)`. Thus that direct clear is after the superclass's actual movement and after fall-distance reset in both releases. `LivingEntity.aiStep` calls `updateFallFlying()` before dispatching to `travel` (1.20.4 2591–2604; 1.20.5 2671–2684). With an airborne player and already-true bit 7, enabled Elytra, no passenger, and no levitation, the client-side update retains bit 7; the glide branch in `LivingEntity.travel` runs during `super.travel` before the direct clear. This agrees with the report's airborne ordering conclusion.

2. **Grounded client behavior — report correction required.** `updateFallFlying` sets its local boolean false when `onGround()` is true (1.20.4 2641–2665; 1.20.5 2721–2745), but its final `setSharedFlag(7, $$0)` is guarded by `!level().isClientSide`. `isFallFlying()` simply returns `getSharedFlag(7)` (1.20.4 3086–3088; 1.20.5 3165–3167). Therefore on the local client, the grounded predicate does not clear an already-true bit before movement. Since `LivingEntity.travel` dispatches its glide branch through `isFallFlying()` (1.20.4 2099 onward; 1.20.5 2168 onward), a grounded tick entering with bit 7 true can still glide during the superclass movement; the `Player.travel` ability-flight branch then performs its existing post-movement reset and clear. This effect is conditional on the bit being true at tick entry; it is not an assertion that all normal grounded states are reachable with bit 7 true.

3. **Activation and 1.20.5 grounded toggle — separate from the clear.** The `Player.tryToStartFallFlying` gates match: airborne, not already fall-flying, dry, no levitation, enabled Elytra in chest (1.20.4 1506–1516; 1.20.5 1534–1544). `LocalPlayer.aiStep` excludes ordinary jump-to-start while `abilities.flying` is true in both releases. A separate 1.20.5 delta enables flight on a second jump press and, if still on ground, invokes `jumpFromGround()` before `super.aiStep` (LocalPlayer 720–749 and 807–811); the 1.20.4 toggle does not jump. `jumpFromGround` only replaces velocity/adds impulse and does not clear `onGround`; update-before-travel therefore still sees the grounded predicate. But, because the client does not write that predicate result to shared flag 7, this does not establish a pre-travel glide clear. The new jump is input/velocity behavior, not a changed glide-activation gate or moved flag clear.

4. **Fall distance — distinct.** `resetFallDistance()` is called after `super.travel` and before the direct bit-7 clear in both versions. It is not the `updateFallFlying` predicate and does not suppress the glide branch before movement.
