# 26.2 raw-state representability gate: AutoJump while sleeping

**Corrected bounded verdict: COMPLETED — ordinary vanilla 26.2 cannot present the full local post-move AutoJump consumer domain while in the sleeping pose.** The raw sleeping body is 0.2F and AutoJump has no direct sleeping guard, but the local GUI opens `InBedChatScreen` before the entity tick. Opening any screen releases all `KeyMapping`s and releases the mouse. While a screen is active, keyboard presses do not set gameplay mappings and mouse button events do not set gameplay mappings. `LocalPlayer.input.tick()` then recomputes the raw movement vector from the now-released mappings before movement calls `updateAutoJump`. Thus a vanilla keyboard/mouse producer cannot supply the required nonzero raw vector during sleep. No legitimate clientbound packet interleaving exposes an asleep local player to an entity move before the screen/input gates run: entity-data handling is marshalled to the client thread, packet work is drained before `Minecraft.tick`, GUI routing precedes entity ticking, and the server packs dirty pose/sleep-position values in a single entity-data packet. A preexisting non-bed screen also blocks gameplay mapping input and was opened through `Gui.setScreen`, which released mappings. This corrects the earlier representability verdict.

The precise bounded residual is limited to a non-vanilla writer/injection that changes `ClientInput` or gameplay key mappings while a screen is active, a mixin altering these gates, or an external move piggybacking stale input before the normal local input tick. None is an exact vanilla producer path and these are outside this gate. Vanilla wake-up does not reopen the conjunction: the wake synchronizes pose/sleep state together; if mouse focus restoration or newly accepted input creates a nonzero vector after the screen closes, the player has already left `Pose.SLEEPING` and uses the ordinary pose dimensions. Scale attributes are excluded.
