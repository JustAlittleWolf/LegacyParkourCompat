## Comparison and reachable path

Both LocalClientPlayer classes inherit this operation: `LocalClientPlayerEntity` extends `ClientPlayerEntity`, which extends `PlayerEntity`/`LivingEntity`/`Entity`; neither LocalClientPlayer source declares an override of `updateLocalPlayerCamera`.

In both releases, grabbed fullscreen mouse movement accumulates the raw Y cursor delta as a `double` in `MouseHandler.onMove`; `turnPlayer` scales it in `double`, and for `smoothCamera=false` passes `k = accumulatedDY * g` to `minecraft.player.updateLocalPlayerCamera(j, k * n)`. For an ordinary nonpassenger, `mount == null`, so the camera method's mount callback is skipped. The MouseHandler route and its numeric widths/order are unchanged for this operation.

Both `Entity.updateLocalPlayerCamera(double cursorDeltaX, double cursorDeltaY)` bodies are operation-for-operation identical:

1. `double d = cursorDeltaY * 0.15; double e = cursorDeltaX * 0.15;`
2. First pitch write: `this.pitch = (float)(this.pitch + d);` — double addition followed by an explicit narrowing cast to `float`.
3. Yaw write with the same double-add/float-cast pattern.
4. Clamp the already narrowed pitch to `[-90.0F, 90.0F]`.
5. Add `d` to `lastPitch` as double then narrow to float; update `lastYaw`; clamp `lastPitch` to the same float bounds; invoke passenger callback only when `mount != null`.

The protected `setRotation(float yaw, float pitch)` also has the same `% 360.0F` writes in both versions, but the ordinary direct mouse camera path does not call it. Do not attribute that modulo operation to the mouse pitch path.

A finite witness reaches the first write through the actual path: with sensitivity `1.0`, `smoothCamera=false`, `invertMouseY=false`, `accumulatedDY=600.0`, and initial pitch `0.0F`, `g=((1.0*0.6F)+0.2F)^3*8.0` is approximately `4.0960004`; `k≈2457.6002`; `d=k*0.15≈368.6400`. The first cast/write is therefore finite and greater than 360 degrees, then the immediately following clamp stores `90.0F` before the camera method returns. Both versions produce this same transient and final value. This is not a persistent >360 pitch state.

In the actual local tick path, `LocalClientPlayerEntity.tick()` calls `super.tick()` (1.13.2 lines 181–183; 1.14 lines 178–180), and the LivingEntity travel section calls `moveRelative` (1.13.2 lines 1920–1926; 1.14 lines 2214–2220). In a dry active Elytra movement call, `LivingEntity.moveRelative` reaches the `isFallFlying()` branch only after the no-water and no-lava gates (unless player flight ability bypasses them). Its first pitch-consuming expression is the `getLookVector()` call; `Entity.getLookVector()` directly calls `getRotationVector(this.pitch, this.yaw)`, whose degree-to-radian math uses float pitch. The next explicit pitch read is `float j/l = this.pitch * (float)(Math.PI / 180.0)`, then `MathHelper.cos` feeds the glide velocity update. Thus the consumed field is the post-clamp float, and the first consumption order and cast width are unchanged.

The movement path bounded here is the ordinary local client path: while grabbed in fullscreen, `MouseHandler.onMove` adds raw cursor Y displacement to `accumulatedDY` and calls `turnPlayer`; the unsmoothed branch computes the double `k` and passes it to `minecraft.player.updateLocalPlayerCamera`. `minecraft.player` is the LocalClientPlayer instance, which inherits the method from Entity; `mount == null` skips only the passenger callback.
