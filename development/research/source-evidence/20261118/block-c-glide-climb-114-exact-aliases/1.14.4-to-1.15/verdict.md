## Audited behavior

- **Descent gate — supported.** In 1.14.4, `LocalPlayer.aiStep` requires jump rising edge, airborne, `deltaMovement.y < 0.0`, not already fall-flying, and not ability-flying before it sends `START_FALL_FLYING` (`1.14.4/mojmap/net/minecraft/client/player/LocalPlayer.java:707-712`). The server command branch independently requires `!onGround && deltaMovement.y < 0.0 && !isFallFlying() && !isInWater()` before checking the chest Elytra and starting flight (`.../ServerGamePacketListenerImpl.java:1122-1127`). In 1.15 the local gate has no vertical-speed test; it calls `tryToStartFallFlying()` after the jump/input and chest-item checks (`1.15/mojmap/net/minecraft/client/player/LocalPlayer.java:715-719`). The server command handler calls the same method (`.../ServerGamePacketListenerImpl.java:1137-1140`), whose eligibility requires airborne, not already fall-flying, not in water, and a usable chest Elytra, without a descent test (`.../world/entity/player/Player.java:1586-1595`). Thus the local and server start predicates differ at the strict descent gate as reported for the ordinary dry, non-passenger, non-flying setup.
- **Material correction — same-tick local start.** `Player.tryToStartFallFlying()` calls `startFallFlying()` before returning true; `startFallFlying()` writes shared flag 7 true (`1.15/mojmap/net/minecraft/world/entity/player/Player.java:1586-1600`). `LocalPlayer.aiStep` then calls `super.aiStep()` at line 778. In that same call, `LivingEntity.aiStep` runs `updateFallFlying()` immediately before `travel` (`.../world/entity/LivingEntity.java:2285-2287`); its shared-flag rewrite is server-only (`:2315-2317`), while the local flag set above is already true. `travel` consequently selects the active Elytra branch on this local movement tick. The statement in the input report that this is “not a local client simulation switch” is false for 1.15. The divergence is not merely the command/server acceptance boundary: the 1.15 local path starts its local glide state before travel, while the 1.14.4 local path only sends the command and has no local `startFallFlying()` call in this branch.
- **Climbable write scope and first glide move — supported, with that correction.** `onLadder()` reads the feet block and returns true for ladder/vine (and scaffolding) for a non-spectator in both versions (`1.14.4/.../LivingEntity.java:1228-1238`; `1.15/.../LivingEntity.java:1226-1236`). In ordinary dry travel, `handleOnClimbable` is called before `move`; for ladder/vine it clears `fallDistance`, clamps X/Z to ±0.15 and Y to at least −0.15 (`1.14.4/.../LivingEntity.java:1836-1842,1940-1954`; `1.15/.../LivingEntity.java:1885-1891,1989-2003`). The unsneaking player case has no ladder-downward suppression write. The active Elytra branch does not call `handleOnClimbable`. Its first write is `fallDistance = 1.0F` only when incoming `deltaMovement.y > -0.5`, before the glide vector calculation and `move`; at `y <= -0.5` it leaves the value untouched (`1.14.4/.../LivingEntity.java:1793-1797,1821-1822`; `1.15/.../LivingEntity.java:1842-1846,1870-1871`). In the 1.15 ordinary local startup path, the local flag write means this active branch bypasses climbable cleanup on the same tick. In 1.14.4 the request tick remains ordinary travel; a later locally active glide move applies the same threshold rule. No collision or longer trajectory claim follows from this audit.
- **Friction lookup — source delta supported; geometry/effect bounded.** The ordinary dry branch reads friction from `BlockPos(x, minY - 1.0, z)` in 1.14.4 (`.../LivingEntity.java:1836-1842`) and from `getBlockPosBelowThatAffectsMyMovement()` in 1.15 (`.../LivingEntity.java:1885-1891`), whose Y is `minY - 0.5000001` (`1.15/.../Entity.java:600-602`). These can floor to different block Y values when the fractional part of `minY` reaches that boundary; actual ladder/vine support/contact geometry is not established here. For the audited Elytra-start witness, `!onGround` is required. In this airborne branch, `getFrictionInfluencedSpeed(v)` returns `flyingSpeed` and the damping factor `w` is `0.91F` in both versions (`.../LivingEntity.java:1957-1959` at 1.14.4, `:2006-2008` at 1.15 and the ordinary-branch lines above). So this lookup may select/read a different block state, but it has no direct effect on movement through these friction uses for this airborne setup. Grounded cases, other helper callers and concrete geometry remain outside this bounded verdict.
