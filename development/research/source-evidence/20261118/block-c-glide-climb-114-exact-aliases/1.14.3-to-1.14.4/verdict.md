# Independent source audit: 1.14.3–1.14.4 glide/climb alias gate

## Verdict

**ACCEPTED for the bounded claim:** in exact 1.14.3 Yarn `1.14.3+build.13` and 1.14.4 Mojmap, an already-active, usable-chest-Elytra local player follows the same dry fall-flying route at ladder/vine feet state. The checked code preserves the movement operation order and values under renamed APIs. That branch precedes and bypasses the climb clamp and post-move climb boost. No glide-versus-climb route or movement-math difference was found in this bound.

This verdict covers only the requested already-active dry route, its pre-route state update and velocity snap, the strict vertical threshold, and the climb-route bypass. It does not accept startup, final contact, fluids, shape/geometry, intermediate patch boundaries, full tick-graph coverage, or runtime parity.

## Independent comparison

All paths below are relative to `decompiled_minecraft/`; line numbers are source line numbers.

1. **Local-player call and order.** Yarn `1.14.3/yarn/net/minecraft/client/network/ClientPlayerEntity.java:761` calls `super.tickMovement()`. Mojmap `1.14.4/mojmap/net/minecraft/client/player/LocalPlayer.java:772` calls `super.aiStep()`. In those superclass methods, velocity components with `Math.abs(component) < 0.003` are zeroed at 2171–2183 and 2174–2183 respectively, then stored at 2183/2186. Input damping follows, then `initAi()` / `updateFallFlying()` at 2218/2221, then `travel(...)` at 2220/2223. The threshold is strict and per component; equality at `0.003` is not zeroed. This is independent of the travel branch's `y > -0.5` test.
2. **Active-flight state update.** Yarn `LivingEntity.java:2232–2250` (`initAi`) and Mojmap `LivingEntity.java:2235–2253` (`updateFallFlying`) both start from shared flag 7, retain it only when airborne, not riding (`!hasVehicle()` / `!isPassenger()`), and wearing the Elytra item with the usability predicate true. They write the resulting flag only under `!world.isClient` / `!level.isClientSide`. Thus the local client does not immediately overwrite its tracked flight flag from the updater's local boolean; the already-active valid flag reaches travel. The predicate aliases are source-confirmed at Yarn `item/ElytraItem.java:20–21` and Mojmap `world/item/ElytraItem.java:20–21`, both `damage < maxDamage - 1`.
3. **Strict threshold and movement.** Yarn `LivingEntity.travel(Vec3d)` at 1779–1819 and Mojmap `LivingEntity.travel(Vec3)` at 1782–1822 have matching dry fall-flying control flow and math. Before look-vector math and before `move(SELF, velocity)`, each reads current vertical velocity and assigns `fallDistance = 1.0F` only for strict `y > -0.5` (Yarn 1791–1794; Mojmap 1793–1797). Exactly `-0.5` does not assign. Both then perform the same look/pitch calculations, ordered additions, `0.99F/0.98F/0.99F` multiplication, and move. The prior `< 0.003` component snap is a distinct earlier tick operation.
4. **Ladder/vine route precedence.** The shared travel structure checks the fall-flying flag before its non-fall-flying `else` route. Only that `else` invokes Yarn `method_18801(...)` at 1833–1839 (helper body 1937–1951) / Mojmap `handleOnClimbable(...)` at 1836–1842 (helper body 1940–1954). The `(horizontalCollision || jumping) && isClimbing/onLadder` vertical `0.2` adjustment is likewise only in that ordinary branch (1841–1843 / 1844–1846). Both climbing predicates include ladder/vine based on the feet state (Yarn 1233–1247; Mojmap 1228–1242), but that predicate does not displace the earlier active-flight branch. Consequently, for the stated already-active dry case, ladder/vine feet state does not route the player through climb cleanup or the climb boost.
