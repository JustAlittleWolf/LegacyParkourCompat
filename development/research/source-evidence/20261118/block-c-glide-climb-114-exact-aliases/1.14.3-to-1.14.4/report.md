# 1.14.3 → 1.14.4 glide/climb alias gate

## Scope and result

Bound comparison: exact local 1.14.3 Yarn `1.14.3+build.13` → 1.14.4 Mojmap sources; ordinary dry local player, already fall-flying with a usable chest Elytra, on foot, at a ladder or vine. Startup, final-contact, fluid and block-shape boundaries are reported separately. No product implementation, prior findings, wiki material, or Git history was consulted.

**Result:** no independent glide-versus-climb route or movement-math change was found for that bound. The main movement code is the same operation sequence under renamed APIs. In both releases, the already-active Elytra branch takes precedence over the climb cleanup: `travel` checks water/lava, then `isFallFlying()`, and only its non-fall-flying branch calls the climb velocity clamp and post-move climb boost. A player can therefore be `isClimbing`/`onLadder` at the feet while the active Elytra branch moves them without those climb adjustments.

## Ordered state and movement evidence

- **Tick threshold:** 1.14.3 `LivingEntity.tickMovement()` (2143 ff.) and 1.14.4 `LivingEntity.aiStep()` (2146 ff.) read velocity and zero each component when `Math.abs(component) < 0.003` before AI/jump/travel. The strict comparator and literal match. Client subclasses run their own input/tick path; startup conditions are separate below.
- **Updater authority/order:** 1.14.3 `tickMovement()` calls `initAi()` (2218) after input damping and before `travel`; 1.14.4 `aiStep()` calls `updateFallFlying()` (2221) at the corresponding point. Both validate the shared fall-flying flag, airborne state, non-riding state and usable chest Elytra. Both only rewrite the shared flag on the server (`!world.isClient` / `!level.isClientSide`), preserving server authority. The item predicate aliases `ElytraItem.isUsable` and `ElytraItem.isFlyEnabled` both implement `damage < maxDamage - 1`.
- **Travel precedence:** 1.14.3 `LivingEntity.travel(Vec3d)` 1779–1950; 1.14.4 `LivingEntity.travel(Vec3)` 1782–1953. The dry, non-lava path tests fall-flying before the ordinary movement branch. The Elytra branch keeps the same order: optional `fallDistance = 1.0F` when vertical velocity is above `-0.5`; look/pitch math; vector additions; `multiply(0.99F, 0.98F, 0.99F)`; `move(SELF, velocity)`. The ordinary branch alone calls `method_18801` / `handleOnClimbable`, then after moving applies `(horizontalCollision || jumping) && isClimbing/onLadder` → vertical velocity `0.2`. The water branch has its own post-move horizontal-collision climb boost; it is not part of the ordinary dry bound.
- **Startup:** 1.14.3 `ClientPlayerEntity.tickMovement()` 696–699 and 1.14.4 `LocalPlayer.aiStep()` 707–710 send `START_FALL_FLYING` only when jump is pressed, the player is descending, airborne, not already fall-flying and not ability-flying, and the chest Elytra passes the same durability threshold. The local client does not set the shared flag from this request; it waits for synchronized state. The server packet handlers recheck airborne/descending/not already gliding, water absence, Elytra item and durability before setting the flag: Yarn `ServerPlayNetworkHandler` 1096–1102; Mojmap `ServerGamePacketListenerImpl` 1122–1127. In a normal dry start, entering the special branch is therefore a server-accepted, synchronized state transition, not an immediate consequence of the local input check.
- **Final contact:** `Entity.move` sets `horizontalCollision`, `verticalCollision` and `onGround` from requested versus clipped displacement in both versions (Yarn `Entity` 441–472; Mojmap `Entity` 446–477). The active Elytra travel branch reacts to horizontal contact with server-only Elytra wall-damage calculation (excluded damage behavior) and clears the fall-flying flag only when on-ground, also server-only. Horizontal ladder/vine contact alone does not invoke climb cleanup while the glide branch is active. The local client waits for synchronized flag changes.

## Separate fluid and geometry boundaries

- Both travel methods gate this route on water first and lava second; for the stated dry case both checks admit the fall-flying route. The expressions are aliases with a meaningful boundary to keep separate: Yarn 1.14.3 uses `!isInsideWater()`, while Mojmap 1.14.4 uses `!isInWater()`. Their entity water state is updated in `Entity.checkWaterState` / `Entity.updateInWaterState`; no claim is made here for partially submerged, waterlogged, or other fluid-contact cases. The server startup checks likewise use the respective water predicate.
- Ladder outline/get-shape extents match by coordinates in both mappings: 3/16 thickness on the facing side. Vine shape assembly also selects matching 1/16 side sheets and the same 1/16 top sheet; 1.14.4’s direction-named AABBs are selected with opposite names for the same physical coordinates. No block-state or collision-shape change is indicated by this comparison. State-dependent geometry/contact still feeds the shared `Entity.move` collision flags above.
- `isClimbing()` / `onLadder()` use the feet block and accept ladder/vine states (except spectator), with the same additional scaffolding/trapdoor rules. This only supplies the non-glide route’s climb adjustments; it does not override the earlier Elytra branch.
