The helper math is specifically: `sqrt(float)` calls `Math.sqrt(x)` and casts the returned double to float; `sin` and `cos` index the same 65,536-float table using float multiplication by `10430.378F`, integer truncation, and `& 65535`, with cosine's `+ 16384.0F` offset. The table is populated for `i = 0..65535` by `(float)Math.sin(i * Math.PI * 2.0 / 65536.0)`, so the table expression is double math until the final float cast/store. No alternate overload is reached: each dry helper's squared-input temporary is float and invokes `MathHelper.sqrt(float)`.

## Caller and boundary closure

For each source release from 1.9 through 1.11.2, `Entity.updateVelocity` declares the two-float-input signature `updateVelocity(float sideways, float forwards, float scale)`. The ordinary `LivingEntity` path enters through `moveRelative(float sideways, float forwards)`, gates on local control or logical-side movement update, excludes water and lava except the flying-player exceptions, and routes fall-flying to a separate branch. The remaining on-foot dry branch chooses ground acceleration from `getSpeed() * (0.16277136F / (s * s * s))` or airborne `speedInAir`, then calls `updateVelocity(sideways, forwards, u)`. `LivingEntity.tick` supplies its sideways/forward movement speeds to that helper. Thus the gate under review is specifically ordinary dry local on-foot acceleration, not swimming, lava, elytra, or nonlocal server physics.

In each two-axis helper the source performs float `sideways * sideways + forwards * forwards`; continues unless that value is strictly `< 1.0E-4F`; invokes the float sqrt; clamps the resulting float length to at least `1.0F`; computes `scale / length`; scales both components; computes sine before cosine from `yaw * (float)(Math.PI / 180.0)`; then adds the rotated components to X and Z velocity. These operation gates/order are visible in the canonical `Entity.java` bodies; relevant release source hashes above bind the audited files.

At exact 1.12, `Entity.updateVelocity` adds `upwards * upwards` to the float sum and scales the third coordinate before trig; its corresponding `LivingEntity.moveRelative(float forwards, float sideways, float upwards)` dry caller passes `(forwards, sideways, upwards, u)` to the entity helper. On the ordinary player tick route, `verticalSpeed` occupies the caller's middle/forwards slot and is zero, while the horizontal sideways/forward axes map to helper X/Z. The adjacent accepted audit independently bounds that zero-player-input fact. The 1.12 source helper still uses the identical float sqrt/table trig and yaw expression for horizontal coordinates. This closes the requested boundary witness while leaving nonzero third-coordinate callers out of scope.

One scope qualification retained from the prior audit: 1.8.9's yaw expression is different, but it is outside this review's 1.9–1.11.2 range. Within this bounded range and at 1.12, the shared yaw conversion is `yaw * (float)(Math.PI / 180.0)` with sine evaluated before cosine.
