## Ordered operation coverage and dispositions

Same order, doubles, constants, gates and writes.
2. **Water update caller and `isInWater` height exposure — no difference found.** `Entity.java`, 1.21.10 lines 1483-1504 and 1.21.11 lines 1501-1522, clears fluid heights, then calls water current update with `0.014`; absent boat special case, a positive overlap sets `wasTouchingWater`, resets fall distance, and produces splash only on entry after first tick. `isInWater()` continues to return `wasTouchingWater` (1.21.10 lines 1433-1435; 1.21.11 lines 1452-1454). The preceding base tick invokes fluid update, eye update, then swimming update in both versions (1.21.10 `Entity.java` lines 498-500; 1.21.11 lines 504-506).
3. **Eye-in-water prediction — no difference found.** `Entity.java`, 1.21.10 lines 1506-1518 and 1.21.11 lines 1524-1536, first saves prior eye-water state, clears eye tags, samples `getEyeY()`, skips the same non-submerged boat interval, samples the fluid at `(x, eyeY, z)`, and adds its tags only if `cellY + fluidHeight > eyeY`. `getEyeY()` remains `position.y + eyeHeight` (lines 3663-3665 and 3691-3693). `isEyeInFluid` remains membership in the stored tag set (lines 1582-1584 and 1600-1602).
4. **Swimming state before travel — no difference found in water predicate.** `Entity.updateSwimming()` uses the same sprinting/water/passenger predicates (1.21.10 lines 1473-1481; 1.21.11 lines 1491-1499). `Player.updateSwimming()` continues to suppress swimming while abilities.flying, else delegates (1.21.10 lines 1326-1332; 1.21.11 lines 1391-1397). Other changed `LocalPlayer.aiStep()` conditions are outside this water slice.
5. **Flow sample implementation — no difference found.** `FlowingFluid.java` has identical full-file SHA-256 `905e5a02ab10b23b5f6e64a0f732ee552ae8895801e1944d9850a41cc8bce91a` on both sides. `FluidState.getFlow(BlockGetter, BlockPos)` delegates to the same fluid type operation (1.21.10 lines 95-96; 1.21.11 lines 95-96); its file changes are annotations/nullability only in inspected surrounding declarations. 6. **First water travel move and drag/vertical response — water path equivalent for this player.** `LivingEntity.travel(Vec3)` changes shape: 1.21.10 lines 2275-2284 inlines `(isInWater() || isInLava()) && isAffectedByFluids() && !canStandOnFluid(state)`; 1.21.11 lines 2309-2321 calls `shouldTravelInFluid(state)`, whose body is exactly that predicate. Older combined `travelInFluid` (1.21.10 lines 2331-2381) and extracted `travelInWater` plus `jumpOutOfFluid` (1.21.11 lines 2368-2407, 2427-2432) preserve that water sequence and the same horizontal-collision/free-space vertical `0.3F` response. `getFluidFallingAdjustedMovement` is unchanged (1.21.10 lines 2488-2501; 1.21.11 lines 2546-2559): same `gravity != 0 && !sprinting`, descending/near-terminal tests, `0.003`, `0.005`, `gravity / 16.0`, and returned y adjustment.
