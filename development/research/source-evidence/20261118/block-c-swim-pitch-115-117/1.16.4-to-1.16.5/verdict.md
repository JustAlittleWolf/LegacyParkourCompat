### Frozen technical trace

**Player branch and operation order.** In both `net/minecraft/world/entity/player/Player.java`, `travel(Vec3)` is lines 1387–1417. It first snapshots current X, Y, Z (1388–1390). The local writer is entered only when `this.isSwimming() && !this.isPassenger()` (1391). `Player.isSwimming()` at 1782–1783 additionally requires `!this.abilities.flying`, `!this.isSpectator()`, and `super.isSwimming()`. Thus flying players, spectators, and passengers do not execute this writer.

On entry, it samples `double g = this.getLookAngle().y` (1392), then selects `double h = g < -0.2 ? 0.085 : 0.06` (1393). It adjusts Y only if `g <= 0.0 || this.jumping || !fluidStateAt(new BlockPos(this.getX(), this.getY() + 1.0 - 0.1, this.getZ())).isEmpty()` (1394–1396). Java short-circuit order means the above-head block/fluid lookup is reached only when `g > 0.0` and `jumping` is false. If reached, the lookup uses current X/Z and current Y plus the left-to-right expression `1.0 - 0.1` (equivalent in value to 0.9). When the predicate passes, it then samples `Vec3 vec32 = this.getDeltaMovement()` and writes `vec32.add(0.0, (g - vec32.y) * h, 0.0)` through `setDeltaMovement` (1397–1399). The arithmetic is double-valued after `g` is widened from the view vector’s float Y component; `h` is double, and the existing Y velocity is subtracted before multiplication and addition.

After the local writer, the method tests `abilities.flying && !isPassenger()` (1402). Since the writer’s `isSwimming()` gate excludes flying, its active swim case proceeds through the `else` to `super.travel(vec3)` at 1412–1414. The position delta is measured for movement statistics afterward (1416).

**Pitch to look-vector Y.** `Entity.getLookAngle()` (both `Entity.java:1700–1702`) directly calls `calculateViewVector(this.xRot, this.yRot)`, so this is the current pitch/yaw sample, with no interpolation. In `Entity.calculateViewVector` (1243–1250), pitch conversion is `float h = xRot * (float)(Math.PI / 180.0)`; yaw is independently converted as `float i = -yRot * (float)(Math.PI / 180.0)`. It then samples in this order: `cos(i)`, `sin(i)`, `cos(h)`, `sin(h)`, assigning each to float locals. The returned `Vec3` is `(k * l, -m, j * l)`. Consequently the swim branch’s `g` is the float `-Mth.sin(h)` widened to double; the Y component is not recomputed with `Math.sin` or a double-precision radian conversion.

In both `Mth.java` files, `SIN` is a 65,536-float table built as `(float)Math.sin(ix * Math.PI * 2.0 / 65536.0)` for each integer index. `sin(float f)` returns `SIN[(int)(f * 10430.378F) & 65535]`; `cos(float f)` returns `SIN[(int)(f * 10430.378F + 16384.0F) & 65535]`. The float multiplications, integer truncation cast, and 16-bit mask are part of the traced operation.

**Inherited real water movement.** `Player` extends `LivingEntity`; the `super.travel(vec3)` in the active swim branch dispatches to `LivingEntity.travel(Vec3)` (both releases, `LivingEntity.java:1914+`). Under its effective-AI/local-control gate, its water case requires `isInWater() && isAffectedByFluids() && !canStandOnFluid(fluidState.getType())` (1923–1924). It performs `moveRelative(g, vec3)` and then `move(MoverType.SELF, this.getDeltaMovement())` (1946–1947), so the just-written Y velocity is consumed by the real move. It then applies `vec32.multiply(f, 0.8F, f)` and fluid-falling adjustment before storing the resulting velocity (1953–1955). These inherited lines are byte-identical between the compared sources. The swim-pitch branch is therefore a pre-move velocity writer, not itself the position move.

**Difference disposition:** none for this bounded operation across 1.16.4→1.16.5. Exact `Player`, rotation/look-vector `Entity`, `LivingEntity` water-travel, and `Mth` source bytes match. No claim is made here about uninspected player-movement operations, runtime parity, or an intermediate patch boundary.
