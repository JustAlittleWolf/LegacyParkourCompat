### Player-level operation and call trace

- `Player.travel(Vec3)` is 1.17 `Player.java:1418-1447`, 1.17.1 `Player.java:1409-1438`. The method body is identical. It first snapshots xyz for later statistics. Its player-only correction gate is `isSwimming() && !isPassenger()`. `Player.isSwimming()` excludes flying and spectators (1.17 `Player.java:1811-1813`; 1.17.1 `:1802-1804`); the swimming state itself comes from `super.isSwimming()`.
- Under that gate, `g = getLookAngle().y` (double) and `h = g < -0.2 ? 0.085 : 0.06` (double literals). If `g <= 0.0`, or `jumping`, or the fluid state of the block at `(getX(), getY() + 1.0 - 0.1, getZ())` is nonempty, the writer reads the current delta and sets it to `vec32.add(0.0, (g - vec32.y) * h, 0.0)`. Thus the only changed component is Y, by the double-valued correction `(lookY - currentDeltaY) * h`; there is no explicit cast or clamp here. It converges partway toward look-vector Y, with coefficient 0.085 when lookY is strictly below -0.2 and 0.06 otherwise. Positive lookY with no jump and empty head-space fluid skips the write. The head-space coordinate evaluates as player Y plus 0.9 before `BlockPos` construction.
- `Entity.getLookAngle()` delegates to `calculateViewVector(getXRot(), getYRot())` (1.17 `Entity.java:1829-1831`; 1.17.1 `:1831-1833`). `calculateViewVector` computes float pitch radians `xRot * (float)(PI / 180.0)`, then returns Y as `-Mth.sin(pitchRadians)` (1.17 `Entity.java:1337-1345`; 1.17.1 `:1339-1347`). The helper body is identical between releases.
- `Mth` initializes `float[65536]` with `(float)Math.sin(ix * Math.PI * 2.0 / 65536.0)`; `sin(float)` indexes `SIN[(int)(radians * 10430.378F) & 65535]`; `cos(float)` uses the same table with `+ 16384.0F`. Both versions have byte-identical `Mth.java`. Therefore table width/element type, scale type/value, truncating float-to-int conversion and 16-bit mask did not change in this pair.
- After the correction, ordinary nonflying Player travel calls `super.travel(vec3)` (`Player.java` cited above), resolving to `LivingEntity.travel`. For an active locally controlled player on water, its relevant gate is `(isEffectiveAi() || isControlledByLocalInstance())`, then `isInWater() && isAffectedByFluids() && !canStandOnFluid(fluidState.getType())` (1.17 `LivingEntity.java:1999-2043`; 1.17.1 `:2003-2047`). In that branch it calls `moveRelative(g, vec3)`, then `move(MoverType.SELF, getDeltaMovement())` (1.17 `:2031-2032`; 1.17.1 `:2035-2036`). Only after this actual move does it multiply velocity by `(f, 0.8F, f)`, apply fluid-falling adjustment and possibly a horizontal-collision step-up writer. These later operations can change post-move Y velocity, but the Player correction is present in the delta consumed by the inherited move. The corresponding source statements and ordering are identical in both versions.
- The parent `Entity.move` collision/position path is present at 1.17 and 1.17.1 `Entity.java:534ff`; `Entity.java` differs elsewhere, but the reviewed Player correction calls the same inherited operation with the same pre-move delta. `Vec3.add(double,double,double)` has identical source bytes in the pair.
