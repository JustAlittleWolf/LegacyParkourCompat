# 1.14.4 → 1.15 swim pitch-directed vertical correction

**Pair and scope.** Exact Minecraft 1.14.4 → 1.15.0, Mojmap (`mojmap`) sources. This is a bounded comparison of the voluntary, active, non-passenger player swim correction at the start of `Player.travel`, its look-Y input, gates, and subsequent inherited movement call. It does not claim fluid or collision coverage.

Both Player overrides begin by capturing current position, then guard this correction with `isSwimming() && !isPassenger()`. Both read `double g = this.getLookAngle().y`, select `double h = g < -0.2 ? 0.085 : 0.06`, then test, in short-circuit order: `g <= 0.0 || this.jumping || !aboveBlockFluidIsEmpty`. The last operand samples `new BlockPos(x, y + 1.0 - 0.1, z)` and checks its `FluidState`; in 1.15 the coordinates use `getX()/getY()/getZ()` rather than the 1.14.4 fields. Thus this sample is reached only when `g > 0.0` and jumping is false. If any operand is true, it reads the current velocity and writes `vec32.add(0.0, (g - vec32.y) * h, 0.0)` via `setDeltaMovement`; otherwise it makes no correction write. The coefficient threshold and selection occur before this gate/sample.

For this `getLookAngle` call (not interpolated `getViewVector`), `Entity.getLookAngle()` passes current float `xRot,yRot` to `calculateViewVector`. The vertical component is `-Mth.sin(xRot * (float)(Math.PI / 180.0))`; radians are multiplied/stored as `float` before the trig lookup, and the returned `double` Vec3 Y is the widened float result. `Mth.sin` indexes a `float[65536]` table built by casting `Math.sin(...)` to float; lookup is `SIN[(int)(f * 10430.378F) & 65535]`. The multiply is float arithmetic and the cast to `int` truncates toward zero before the 16-bit mask. This math and operation order match both releases exactly.

After the optional correction, `Player.travel` calls `super.travel(vec3)` for the ordinary non-flying route. Dynamic dispatch reaches `LivingEntity.travel`; the player correction is therefore applied to velocity before that inherited movement consumes it. The corresponding `LivingEntity.aiStep` calls the virtual `travel` (`this.travel(new Vec3(...))`; 1.14.4 line 2223, 1.15 line 2287). The relevant water movement branch in the two inherited methods retains the same movement calls and coefficients; this observation is only to establish the consumer path, not a full fluid audit. The other flying branch is separate and, for a non-flying witness, not taken.

## Reachable local-player witness and result

A legal local-client witness is a non-spectator, non-flying, unmounted player submerged in water and sprinting (sprint input); `Entity.updateWaterState` calls virtual `updateSwimming`. `Player.updateSwimming` clears swimming only when flying and otherwise delegates to `Entity.updateSwimming`, whose underwater branch sets swimming for sprinting and non-passengers. The next normal `LivingEntity.aiStep` dynamically dispatches to `Player.travel`. With upward pitch giving `g < -0.2`, the correction is reached regardless of jump or above-block contents, and uses `0.085`. With horizontal/downward pitch (`g > 0`), no jump, and empty fluid at the sampled block, the short-circuit skips the write. With the same look and nonempty above fluid, the sample is reached and enables the write.

**Finding:** no change in this bounded operation from 1.14.4 to 1.15.0. The swim guard, look-Y generation and numeric width, threshold, coefficient, Boolean gate order, sample coordinates/ordering, vertical write and subsequent inherited movement call are behaviorally the same. 1.15's accessor spelling at the sample and position snapshot is a source/API rewrite, not evidence of a movement delta. No implementation candidate is proposed from this pair for this operation. This is not pair freeze or a statement about unrelated movement.
