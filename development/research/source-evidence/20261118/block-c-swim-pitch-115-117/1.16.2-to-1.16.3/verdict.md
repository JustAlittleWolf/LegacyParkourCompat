## Frozen trace (the cited ranges are identical in both trees)

1. **Reachable own writer and order.** `Player.java:1387–1417`: `travel` snapshots position, then before either super call checks `this.isSwimming() && !this.isPassenger()` (`1391`). `Player.java:1782–1784` further makes `isSwimming()` false for flying or spectator players. The gate has no separate local-water test. It samples `double g = this.getLookAngle().y` (`1392`), chooses `double h = g < -0.2 ? 0.085 : 0.06` (`1393`), and short-circuits the writer unless `g <= 0.0 || jumping || !fluidAt(getX(), getY()+1.0-0.1, getZ()).isEmpty()` (`1394–1396`). On the true path, one current delta vector is read and replaced by `vec32.add(0.0, (g - vec32.y) * h, 0.0)` (`1397–1398`); X/Z are unchanged by this write. This occurs before `super.travel(vec3)` (`1406` or `1413`).
2. **Angle source and math.** `Entity.java:129–131` stores current and old rotations as floats; `getLookAngle()` at `1700–1701` passes current `xRot`/`yRot` directly to `calculateViewVector`, without interpolation through `xRotO`/`yRotO`. The pitch/yaw entry conversion at `Entity.java:340–348` scales mouse deltas in double, adds them to current floats with explicit float narrowing, and clamps current pitch to `[-90,90]`; `setRot` at `326–329` stores supplied rotations modulo `360.0F`. `calculateViewVector` at `1243–1251` converts pitch and yaw using float intermediates: `h = f * (float)(Math.PI / 180.0)` and `i = -g * (float)(Math.PI / 180.0)`, then float `Mth.cos/sin`; returned vector Y is `-m`, where `m = Mth.sin(h)`. The inner `Math.PI / 180.0` division is double before its result narrows to float; multiplication is float. `Vec3` widens that float component to its double Y, so `g` is the exact widened LUT float sample with its sign negated. `Mth.java:12–16` initializes a 65,536-entry float table as `(float)Math.sin(ix * Math.PI * 2.0 / 65536.0)`. `Mth.java:25–27` samples it as `SIN[(int)(f * 10430.378F) & 65535]`: float multiplication, Java truncating float-to-int cast, then 16-bit mask. There is no direct `Math.sin` pitch calculation in this path.
3. **Threshold and write arithmetic.** `g < -0.2` is strict (exactly `-0.2` selects `0.06`); otherwise it selects `0.06`, and values below that threshold select `0.085`. The guard is evaluated left to right: any `g <= 0.0` skips the jumping and above-fluid reads; if that is false, jumping skips the fluid lookup. Thus downward or level look always enters the own Y write; upward look writes only while jumping or when the tested block contains fluid. With the guard true, the exact Y delta added is `(g - currentDeltaY) * h`, evaluated with double arithmetic and then added to the current vector Y by `Vec3.add`. With the guard false, this Player-level writer does not modify velocity.
4. **Separate inherited water branch and actual move.** `LivingEntity.java:1914–1957`: the `super.travel` implementation first gates on effective AI or locally controlled instance (`1915`), then enters water only for `isInWater() && isAffectedByFluids() && !canStandOnFluid(...)` (`1923–1925`). It snapshots Y, computes water slowdown/depth-strider coefficients and calls `moveRelative(g, vec3)` followed by `move(MoverType.SELF, getDeltaMovement())` (`1926–1947`). The branch then may set a climbable Y of `0.2`, multiplies delta by `(f, 0.8F, f)`, applies `getFluidFallingAdjustedMovement`, and may set a climbout Y of `0.3` (`1948–1957`). These are downstream inherited fluid/movement operations, not the Player pitch writer above. `Player` and `LivingEntity` declare no `move` override; `Entity.java:485–530` is the inherited implementation: absent `noPhysics`, it applies edge backoff and `collide`, moves the bounding box/location for a nontrivial resolved vector, then updates collision/on-ground/fall state and zeros blocked horizontal velocity components. This completes the requested call path through the actual inherited move.
