# 1.16.5→1.17 Mojmap: player swim pitch-to-Y correction

## Scope and result

Bounded comparison: the ordinary player swimming correction in `Player.travel(Vec3)`, its pitch-derived `getLookAngle().y` input, the sine lookup math, and its inherited water-travel movement call. Result: no behavioral source delta was found in this Y correction. The pitch access was rewritten through getters in 1.17, but the getters return the same stored `xRot` and `yRot` fields.

This result does not establish full movement-pair coverage. `Entity.move` is the downstream movement boundary and its implementation was reorganized in 1.17; it is recorded below as a dependency requiring its own comparison if exact positional/collision parity is being closed.

## Compared source path

- 1.16.5 Mojmap, `net/minecraft/world/entity/player/Player.java`, `Player.travel(Vec3)`, lines 1387–1400: only when `isSwimming() && !isPassenger()`, assign `g = getLookAngle().y`; choose `h = 0.085` when `g < -0.2`, otherwise `0.06`; if `g <= 0.0 || jumping ||` the fluid at `BlockPos(getX(), getY() + 1.0 - 0.1, getZ())` is nonempty, add `(g - currentVelocityY) * h` to velocity Y. Then call `super.travel(vec3)` (except the separate nonpassenger flight branch, which also delegates), and later update movement statistics.
- 1.17 Mojmap, same file/member, lines 1418–1431: same swim/nonpassenger gate, pitch-derived value, strict `g < -0.2` coefficient split, coefficient values, above-fluid lookup and `g <= 0.0 || jumping || above-fluid` gate, and delta-Y expression/order. No extra clamp, cast, or alternate state write was introduced in this player correction.
- `net/minecraft/world/entity/Entity.java`, `getLookAngle()`: 1.16.5 lines 1700–1702 computes `calculateViewVector(this.xRot, this.yRot)`; 1.17 lines 1829–1831 computes `calculateViewVector(this.getXRot(), this.getYRot())`. 1.17 getters at lines 3005–3022 return the stored `yRot` and `xRot` fields directly. The 1.17 access change therefore has no value difference for this inherited ordinary-player path.
- In both releases, `Entity.calculateViewVector(float pitch, float yaw)` computes pitch radians as `pitch * (float)(Math.PI / 180.0)`, yaw radians as `-yaw * (float)(Math.PI / 180.0)`, and returns `(sin(yawRadians) * cos(pitchRadians), -sin(pitchRadians), cos(yawRadians) * cos(pitchRadians))`. Thus the correction's `g` is the lookup-table-derived negative sine of pitch, without a normalization or extra Y cast.
- `net/minecraft/util/Mth.java`: both versions build a 65,536-entry float `SIN` table with `(float)Math.sin(ix * Math.PI * 2.0 / 65536.0)`. In 1.16.5 `sin` indexes `SIN[(int)(f * 10430.378F) & 65535]`; `cos` adds `16384.0F` before the same truncating float-to-int cast and mask. 1.17 introduces `SIN_SCALE = 10430.378F` and uses the same expressions with that constant. Table generation, float operand, cast/truncation, 16-bit mask, and cosine quarter-table offset are otherwise identical.
- In both `LivingEntity.travel(Vec3)` methods, the water branch is gated by `isInWater() && isAffectedByFluids() && !canStandOnFluid(fluidState.getType())`; after `moveRelative(g, vec3)`, it invokes `move(MoverType.SELF, getDeltaMovement())`, then applies horizontal-collision adjustment, water drag (`f, 0.8F, f`), falling adjustment, and the possible `0.3F` vertical collision response. The corresponding code/order is unchanged (1.16.5 around lines 1914–1957; 1.17 around lines 1999–2042). This is the inherited path reached by `Player.travel` for the ordinary swimming-in-water case.

## Downstream move boundary

The `Entity.move(MoverType, Vec3)` implementation changed between the releases. In the normal physics branch, 1.16.5 translates the bounding box by the resolved collision vector then derives entity position from the box; 1.17 writes the resolved vector through `setPos`. 1.17 also adds a removed-entity guard after fall-damage handling and uses the newer movement-emission bookkeeping. Those changes are beyond the pitch-to-Y correction itself, so no positional-equivalence claim is made here. Compare the corresponding `Entity.move` and position/box accessors as a separate operation before declaring the downstream movement dependency closed.
