# 1.9 → 1.9.1: sprint timers, ability-flight fall reset, sneak-flight input

## Result and boundary

Scoped source comparison found **no movement-behavior difference** in these three operations between Minecraft 1.9 and 1.9.1:

1. Local-player sprint timeout/timer handling, sprint-state initialization, and transition packet dispatch.
2. The player `moveRelative` ability-flight gate and `fallDistance` reset order.
3. The local camera player's sneaking-flight input rescale, including the preceding sneaking and item-use input multipliers.

This is a bounded result for the named operations, not full 1.9--1.9.1 tick/inventory coverage or a complete-pair audit. Sprint food/ability eligibility and server-side packet simulation were not assessed. No product code, tests, builds, game launches, wiki inventories, prior findings, or Git history were consulted.

## Scoped claims and exact source references

### 1. Local-player sprint timer and stop dispatch — no difference found

- 1.9: `LocalClientPlayerEntity.java:84-85, 141-167, 401-405, 599-605, 641-684`.
- 1.9.1: `LocalClientPlayerEntity.java:85-86, 142-168, 402-406, 600-605, 642-685`.
- In both versions, `doubleTapSprintTime` and `sprintTimer` have no field initializer. Java's default integer initialization therefore starts them at zero. Local `setSprinting` first delegates to `super.setSprinting(sprinting)`, then resets `sprintTimer` to zero. Each `mobTick` increments `sprintTimer`, then decrements `doubleTapSprintTime` only when it is positive. The item-use/non-riding branch scales both inputs by `0.2F` and clears `doubleTapSprintTime`. A qualifying ground-forward transition sets the debounce to `7` or starts sprinting; the key-held path can start sprinting directly. Existing sprint is stopped when forward input falls below `0.8F`, horizontal collision is present, or the shared eligibility boolean is false. Eligibility itself is outside this claim.
- In both versions, `LocalClientPlayerEntity.tick` runs `super.tick()` only while the player's chunk is loaded, then calls `sendMovementToServer()` on the non-riding path. That method compares `isSprinting()` with cached `sentSprinting`; only a difference sends START/STOP, and the cached value is assigned after the packet send. The sprint action packet is dispatched before sneak and position/angle dispatch.
- The underlying `Entity.isSprinting`/`setSprinting` pair reads/writes flag 3 in both versions (`Entity.java:1604-1610`). The inherited `LivingEntity.setSprinting` delegates to that flag update, removes an existing sprint-speed modifier, then adds it only when the requested state is true (`LivingEntity.java:1167-1176` in 1.9; `1171-1180` in 1.9.1). Its method text is identical.

### 2. Ability-flight fall-distance reset — no difference found

- 1.9: `PlayerEntity.java:1365-1381`.
- 1.9.1: `PlayerEntity.java:1365-1381`.
- Both gate the special branch on `abilities.flying && !isRiding()`. Inside it, they snapshot `velocityY` as `double` and `speedInAir` as `float`; replace `speedInAir` with `getFlySpeed() * (isSprinting() ? 2 : 1)`; call `super.moveRelative(sideways, forwards)`; set `velocityY` to the saved double multiplied by `0.6`; restore the saved float speed; set `fallDistance = 0.0F`; then clear flag 7. The reset follows the superclass input-relative operation and is absent from the ordinary/vehicle `else` branch. The caller's living movement travel invokes this override after input speed decay and `flyingTick` (`LivingEntity.java:1693-1699` in 1.9; `1697-1703` in 1.9.1).

### 3. Sneaking flight input rescale — no difference found

- 1.9: `KeyboardInput.java:13-50`; `LocalClientPlayerEntity.java:641-650, 710-720`.
- 1.9.1: `KeyboardInput.java:13-50`; `LocalClientPlayerEntity.java:642-651, 712-722`.
- `KeyboardInput.tick` starts each axis at `0.0F`, adds/subtracts key presses, sets the jumping/sneaking booleans, then, if sneaking, assigns each axis `(float)(axis * 0.3)`. The unsuffixed `0.3` makes the multiplication double before the cast back to float. In local-player `mobTick`, prior jump/sneak/forward values are sampled before `input.tick()`. Item use, when not riding, then multiplies the refreshed axes by `0.2F` and clears the double-tap timer. After sprint and flight-toggle handling, the vertical-flight block is gated by `abilities.flying && isCamera()`. Within its sneaking branch, sideways and forward are independently assigned `(float)(axis / 0.3)`—again double division then float cast—before subtracting `getFlySpeed() * 3.0F` from double `velocityY`. Jumping is processed afterward and adds the same float product to `velocityY`. The axes then flow into `LivingEntity` travel (`sidewaysSpeed`/`forwardSpeed` decay by `0.98F` before `moveRelative`).
- Thus ordinary keyboard sneaking applies the `0.3` multiplier; the local camera player attempts to reverse that multiplier only while ability-flying and still sneaking. When item use is active, the additional `0.2F` scaling occurs between those operations. I make no bitwise cancellation claim beyond the source's explicit casts/order.

## Pair-local caveat

`LocalClientPlayerEntity.mobTick` is not wholly identical: 1.9.1 adds an `ElytraOnPlayerSoundInstance` play at `LocalClientPlayerEntity.java:708`, after the START_FALL_FLYING packet; 1.9 has no corresponding sound call (`1.9.1` also has the added import). That audio change is outside the three claims above. It does not change their cited timer, sprint-packet, ability-flight reset, or sneak-rescale statements. This report does not freeze the whole pair.
