# Entity-motion packet vector quantization
1.21.8, Mojmap: `net/minecraft/network/protocol/game/ClientboundSetEntityMotionPacket.java`, constructor, stream read/write and getters (lines 24–73); `net/minecraft/client/multiplayer/ClientPacketListener.java`, `handleSetEntityMotion` (598–603); `net/minecraft/world/entity/Entity.java`, `lerpMotion(double, double, double)` (2420–2422).
1.21.10, Mojmap: `net/minecraft/network/protocol/game/ClientboundSetEntityMotionPacket.java`, constructor and stream read/write (21–33); `net/minecraft/network/LpVec3.java`, `read`, `write`, `sanitize`, `pack`, `unpack` (24–70); `net/minecraft/client/multiplayer/ClientPacketListener.java`, `handleSetEntityMotion` (592–597); `net/minecraft/world/entity/Entity.java`, `lerpMotion(Vec3)` (2493–2495).
Difference: 1.21.8 clamps each packet component to ±3.9, truncates `component * 8000` to an integer, transmits a short, and reconstructs `short / 8000.0`. 1.21.10 transmits a common-scale, normalized 15-bit-per-component `LpVec3`; it maps NaN to zero and clamps input components at ±1.7179869183E10, with a zero-vector threshold of 3.051944088384301E-5. The client handler writes the decoded vector directly to the target entity's delta movement in both versions.
Movement meaning: When the server sends this state update for the local player, the accepted velocity, component limit, zeroing threshold, and quantization precision differ before the next player movement tick. This is an inbound player-state response; the finding concerns its client-side state decoding/application, not damage or knockback generation.
