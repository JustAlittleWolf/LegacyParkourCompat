# Block prediction rollback after position correction
1.21.11, Mojmap: `net/minecraft/client/multiplayer/ClientPacketListener.java`, `handleMovePlayer`, lines 776–784; `net/minecraft/client/multiplayer/prediction/BlockStatePredictionHandler.java`, `endPredictionsUpTo`, lines 37–46; `net/minecraft/client/multiplayer/ClientLevel.java`, `syncBlockState`, lines 182–190.
26.1.2, published unobfuscated: `net/minecraft/client/multiplayer/ClientPacketListener.java`, `handleMovePlayer`, lines 796–806; `net/minecraft/client/multiplayer/prediction/BlockStatePredictionHandler.java`, `onTeleport` and `endPredictionsUpTo`, lines 38–68; `net/minecraft/client/multiplayer/ClientLevel.java`, `syncBlockState`, lines 187–193.
The same correction and acknowledgement methods are present in 26.1, and the six exact caller/state files are byte-identical across 26.1, 26.1.1, and 26.1.2, so the newer behavior is present by the first stable 26.1 release.
Difference: After applying a server position correction, 26.1.2 records the current block-prediction sequence. When a later block-change acknowledgement restores a predicted block, it supplies the saved pre-prediction player position to `syncBlockState` only if the acknowledged sequence is newer than the recorded teleport sequence. The 1.21.11 path always supplies that saved position. Both versions restore the authoritative block state, but `syncBlockState` snaps the player to the saved position when the restored state collides with them; the 26.1.2 sequence gate suppresses this snap for acknowledgements at or before the correction.
Movement meaning: If a pending local block prediction is acknowledged after a server correction and the restored block collision shape intersects the corrected player, 1.21.11 can move the player back to the position captured before the prediction, while 26.1.2 keeps the corrected position. This changes a direct client player position response and can alter the next tick's pose-fit and collision movement.
