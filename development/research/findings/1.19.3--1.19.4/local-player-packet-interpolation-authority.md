# LocalPlayer network movement control gate
1.19.3, Mojmap: `net/minecraft/world/entity/Entity.java`, `getControllingPassenger`/`isControlledByLocalInstance` lines 2671–2673 and 2742–2745; `net/minecraft/client/player/LocalPlayer.java`, `isEffectiveAi` lines 493–495; `net/minecraft/client/multiplayer/ClientPacketListener.java`, `handleMoveEntity` lines 552–573 and `handleTeleportEntity` lines 526–541.
1.19.4, Mojmap: `net/minecraft/world/entity/Entity.java`, `getControllingPassenger`/`isControlledByLocalInstance`/`isEffectiveAi` lines 2719–2721 and 2795–2801; `net/minecraft/client/player/LocalPlayer.java`, `isEffectiveAi` lines 486–488; `net/minecraft/client/multiplayer/ClientPacketListener.java`, `handleMoveEntity` lines 565–586 and `handleTeleportEntity` lines 539–554.
Difference: `Entity.getControllingPassenger()` returns null for LocalPlayer in both releases. In 1.19.3 the no-passenger branch of `isControlledByLocalInstance()` returns `!level.isClientSide`, so LocalPlayer is not controlled on the client and passes the packet handlers' negated guard. In 1.19.4 that branch calls `this.isEffectiveAi()`; LocalPlayer overrides it to return true, so the same negated guards filter LocalPlayer. The 1.19.4 teleport handler still synchronizes the packet codec base before the guard, but no longer lerps LocalPlayer or writes its on-ground state through that branch. `LivingEntity.aiStep` also changes from skipping the controlled-instance lerp reset/base sync to taking it for LocalPlayer (1.19.3 `LivingEntity.java:2515–2521`; 1.19.4 `:2459–2467`).
Movement meaning: When an incoming move or teleport packet resolves to the LocalPlayer, 1.19.3 applies the packet movement response; 1.19.4 filters its position/rotation/on-ground application and treats LocalPlayer as controlled for the tick-side lerp/base path. This finding makes no claim that vanilla server code normally emits self packets, and makes no producer or runtime claim.
