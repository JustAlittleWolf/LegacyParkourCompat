# Block acknowledgement position restoration

1.18.2, Mojmap: `net/minecraft/client/multiplayer/MultiPlayerGameMode.java`, `continueDestroyBlock` lines 219–226 sends `STOP_DESTROY_BLOCK` before `destroyBlock`; `sendBlockAction` lines 452–456 saves the local player's position under the block position and action; `handleBlockBreakAck` lines 458–467 removes that entry and applies the acknowledged state when the current state differs and the action/result gate passes. With a saved position, it restores `Player` position only when the acknowledged level is the player's level and the acknowledged state collides with the player. `net/minecraft/client/multiplayer/ClientPacketListener.java`, `handleBlockBreakAck` lines 2203–2205 forwards the packet fields, including action and `allGood`.

1.19, Mojmap: `net/minecraft/client/multiplayer/MultiPlayerGameMode.java`, `continueDestroyBlock` lines 238–244 runs completed destruction inside `startPrediction`, which sequences the action and closes the prediction scope at lines 256–261; `destroyBlock` lines 103–125 reaches `ClientLevel.setBlock`. `net/minecraft/client/multiplayer/ClientLevel.java`, `setBlock` lines 141–153 retains the prior block state and local-player position when a predicted write succeeds; `syncBlockState` lines 125–134 restores that state and calls `Player.absMoveTo` when the current state differs, this is the player's level, and the restored state collides with the player. `net/minecraft/client/multiplayer/prediction/BlockStatePredictionHandler.java`, `retainKnownServerState` lines 17–25 keeps the first saved position for a block while later predictions update its sequence, and `endPredictionsUpTo` lines 37–48 syncs entries whose sequence is acknowledged. `net/minecraft/client/multiplayer/ClientPacketListener.java`, `handleBlockChangedAck` lines 2237–2240 forwards the acknowledged sequence.

Difference: with a pending saved action, the 1.18.2 correction requires a differing block state and is additionally gated by `allGood` and action kind: a successful `START_DESTROY_BLOCK` acknowledgment skips correction, while a failed action or another action kind can enter it. Its position target is captured when that action is sent. In 1.19, an acknowledged pending prediction with a differing verified state can reach the position correction without an action-kind or `allGood` gate; the target is the player's position when the block was first predicted. In both paths, state equality suppresses correction, and a position write additionally requires the relevant level to be the player's level and the acknowledged/restored block state to collide with the player. The prediction response is sequence-gated. This finding concerns the client player's response to verified block state and makes no claim about server-side production or protocol parity.

Movement meaning: for a locally predicted block change whose verified state differs and collides with the player, the client can restore the player's position. The old action/result gate and action-time capture can produce a different correction from the newer sequence-closed prediction and first-prediction capture. The exact introduction boundary within 1.18.2–1.19 is unknown.
