# Legacy item movement-speed modifier order

1.20.4, Mojmap: `net/minecraft/world/entity/ai/attributes/AttributeInstance.java`, operation buckets and `calculateValue` (lines 21, 50–52, 130–152); `AttributeModifier.java`, UUID equality/hash (57–69); `world/item/ItemStack.java#getAttributeModifiers` (888–911); `world/entity/player/Player.java`, movement-speed initialization and `getSpeed` (204–210, 1489–1491).

1.20.5, Mojmap: `net/minecraft/world/entity/ai/attributes/AttributeInstance.java`, operation buckets and `calculateValue` (21, 50–53, 140–161); `world/item/ItemStack.java#forEachModifier` (883–890); `world/item/component/ItemAttributeModifiers.java#forEach` (63–68); `util/datafix/fixes/ItemStackComponentizationFix.java#fixAttributeModifiers` (411–435); `world/entity/player/Player.java`, movement-speed initialization and `getSpeed` (221–230, 1511–1513).

Difference: Per-operation modifier storage changes from a Java `HashSet` of UUID-equal modifiers to a fastutil 8.5.12 `Object2ObjectOpenHashMap<UUID, AttributeModifier>`. `MULTIPLY_TOTAL` still multiplies the running double sequentially, so its iteration order affects rounding. The old item-data feature accepts feet-slot movement-speed modifiers with UUIDs `00000000-0000-0003-0000-000000000002` and `00000000-0000-0003-0000-000000000001`, amounts `0.01` and `0.23456786252907091`, and operation 2. Componentization preserves both. For this two-entry set, the old bucket visits the first UUID then the second; the new map visits them in reverse order.

Movement meaning: Starting from the player's widened `0.1F` base, the old running double is `0.12469135597348215`, versus `0.12469135597348213` in the newer order. `Player.getSpeed()` therefore returns float bits `0x3dff5e2f` versus `0x3dff5e2e`, supplying a different ordinary movement-speed input. Both modifiers use an existing vanilla attribute and valid legacy item data; no new attribute, modded item or damage result is required. This is a source-backed speed-value difference, not a measured displacement.
