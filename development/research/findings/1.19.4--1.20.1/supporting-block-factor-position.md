# Supporting-block position used for movement factors

1.19.4, Mojmap: `decompiled_minecraft/1.19.4/mojmap/net/minecraft/world/entity/Entity.java`, `getBlockPosBelowThatAffectsMyMovement()` (758–760) constructs the position from entity X/Z and `boundingBox.minY - 0.5000001`. `getBlockSpeedFactor()` (748–756) and `getBlockJumpFactor()` (742–746) query it. `LivingEntity.java` reads it for Soul Speed (456–462) and jump power (1948); `Player.java` bypasses speed factors while flying or fall-flying (1973–1974). The water and bubble-column speed-factor bypass is in `Entity.java` (751–755).

1.20 (Mojang release ID `1.20`) and 1.20.1, Mojmap: `decompiled_minecraft/<version>/mojmap/net/minecraft/world/entity/Entity.java`, `checkSupportingBlock()` (567–587) records a colliding support from a thin AABB extending `1.0E-6` below the feet; a false grounded state clears it. `getBlockPosBelowThatAffectsMyMovement()` (790–792) delegates to `getOnPos(0.500001F)` (798–814). When a tracked support exists, the result keeps its X/Z. For this offset, `position.y - offset` is floored for ordinary supports and fences, while walls and fence gates return the tracked position unchanged, including Y. Without a tracked support, X/Y/Z are floored from entity position. `CollisionGetter.findSupportingBlock()` (95–109) chooses the nearest colliding block position, with `compareTo` as the tie-breaker; `BlockCollisions` (constructor 32–46, `computeNext()` 64–95) supplies candidates using entity collision context and block collision shapes. The water/bubble bypass remains in `Entity.java` (826–829), Soul Speed remains in `LivingEntity.java` (471–477), and player flying/fall-flying bypass remains in `Player.java` (1999–2000).

Difference: the factor query changes from the entity's X/Z column and bounding-box minimum Y to a tracked support position. With tracked support, the support X/Z are retained; the query Y is floored from `position.y - 0.500001F` for ordinary supports and fences, but stays at the tracked Y for walls and fence gates. If grounded support tracking has no position, the fallback floors all three entity-position coordinates. The existing fluid and player-state gates still determine whether the selected block factor is used. `LivingEntity` consumers of the same support position include Soul Speed and block jump factor.

Movement meaning: place a player at x=0.9, z=0.5, feet y=0.875, with width 0.6. Put a bottom stone slab at (0,0,0) beside soul sand at (1,0,0). The player's box spans x=0.6–1.2. The soul-sand collision shape reaches y=0.875 and intersects the support slice; the slab reaches only y=0.5 and does not. In 1.19.4, the query is (0,0,0), selecting the slab's default factor 1.0. In 1.20, the tracked support is (1,0,0); the factor query retains X/Z and floors Y to 0, selecting soul sand's 0.4 factor. `Entity.move()` multiplies horizontal delta movement by that factor after collision (1.19.4 lines 659–661; 1.20/1.20.1 lines 701–702), changing the velocity carried into following player movement.

Boundary evidence: 1.19.3 `Entity.java` (758–760) has the same position-column calculation and water/bubble gate, with no `checkSupportingBlock`; its `CollisionGetter.java` and `BlockCollisions.java` match 1.19.4 byte-for-byte. The support-tracked change is absent in 1.19.4 and present by 1.20; the patch-introduction boundary within that interval remains uninspected.
