# Swimming-pose gate for sneak input slowdown

1.14, Ornithe Feather: `net/minecraft/client/entity/living/player/LocalClientPlayerEntity.java`, `m_63723874` (596–598) and `mobTick` (625–632); `net/minecraft/client/entity/living/player/KeyboardInput.java`, `tick` (13–26). The pose predicate requires non-flight and a fitting sneaking pose, then accepts held sneak or a non-fitting standing pose; `mobTick` passes it OR `m_99544176()` to input before polling and scaling the keys.

1.14.1, Yarn: `net/minecraft/client/network/ClientPlayerEntity.java`, `isInSneakingPose` (582–586) and `tickMovement` (613–620); `net/minecraft/client/input/KeyboardInput.java`, `tick` (13–26); `net/minecraft/entity/Entity.java`, `shouldLeaveSwimmingPose` (1773–1775), `wouldPoseNotCollide` (1579–1580), and `method_20343` (2239–2244); `net/minecraft/entity/player/PlayerEntity.java`, pose sizes (108–116) and `getSize` (1941–1942); `net/minecraft/world/ViewableWorld.java`, `doesNotCollide` (117–123). The predicate has no swimming guard.

1.14.2, Yarn: same client members; `isInSneakingPose` (582–586) adds `!this.isSwimming()` to the outer predicate, and `tickMovement` still passes it OR `shouldLeaveSwimmingPose()` to input (613–619). `Entity.shouldLeaveSwimmingPose` remains `isInSwimmingPose() && !isInsideWater()` (1775–1777); `wouldPoseNotCollide` (1581–1582) and `method_20343` (2250–2255) retain the same bounding-box fit path. `PlayerEntity` retains the same pose sizes and size lookup. The same swimming guard and input call remain in 1.14.3 Yarn and 1.14.4 Ornithe Feather.

Difference: The exact stable patch boundary is 1.14.1 to 1.14.2: 1.14.0 and 1.14.1 permit the pose-derived slowdown while swimming; 1.14.2, 1.14.3 and 1.14.4 exclude it. The pose-fit helper builds a box for the requested pose dimensions and asks the world whether it collides. Player pose heights are 1.8 blocks standing, 1.5 sneaking and 0.6 swimming. Across 1.14.0–1.14.4, `KeyboardInput.tick` otherwise polls directional keys, then when not spectator and either sneak is held or the pose predicate is true, multiplies both movement inputs by the unsuffixed double literal `0.3` and casts each result to `float`. For forward `1.0F`, this is a binary64 multiplication followed by binary32 narrowing, yielding `0x3e99999a` (`0.30000001192092896`). Every earlier resolver representative—1.8.9, 1.9.4, 1.10, 1.10.2, 1.11, 1.11.1, 1.11.2, 1.12.2 and 1.13.2 (Ornithe Feather)—calls parameterless `input.tick()` from local-player `mobTick` and has key-only slowdown in `KeyboardInput.tick`; for example, the caller is at 1.8.9:539, 1.10:665, 1.10.2:665, 1.11/.1/.2:677, 1.12.2:698 and 1.13.2:702, while the keyboard scaling is at 1.8.9:35–36 and 1.9.4–1.13.2:47–48. Those profiles have no pose-derived gate to modify and retain native sneak-key scaling.

Movement meaning: A non-spectator swimming in water in a 1.6-block-high passage, with a solid floor and ceiling, fits the 1.5-block sneaking box but not the 1.8-block standing box. With sneak released and forward held, this player receives the 0.3-scaled horizontal input in 1.14.0–1.14.1 and full forward input from 1.14.2 onward. `shouldLeaveSwimmingPose()` is false while the player remains in water, so that alternative does not restore the old slowdown. This changes the input sent into travel for the tick; it does not establish a full trajectory delta.
