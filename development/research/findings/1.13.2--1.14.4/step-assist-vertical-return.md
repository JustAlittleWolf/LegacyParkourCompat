# Step-assist vertical return incorporates requested movement
1.13.2, Ornithe Feather build 2: `net/minecraft/entity/Entity.java`, `move`, lines 601–672; `net/minecraft/entity/living/LivingEntity.java`, constructor, line 185.
1.14.4, Ornithe Feather build 2: `net/minecraft/entity/Entity.java`, `m_72373519`, lines 656–686; `net/minecraft/entity/living/LivingEntity.java`, constructor, line 206.
Difference: In both versions, step assistance requires positive `stepHeight`, a grounded state or downward collision, and horizontal clipping; a step candidate is kept only when it improves horizontal travel over the ordinary collision result. In 1.13.2, candidate vertical return is set to the negative actual rise (`-u` or `-aa`) and then collision-clipped; this offsets the rise but omits the original requested vertical component. In 1.14.4, the selected step candidate receives the clipped correction `-vec3d3.y + vec3d.y`, offsetting its rise while including the requested vertical component. The correction is itself collision-clipped, so it yields the requested vertical component only when collision geometry does not clip it. Living entities initialize `stepHeight` to `0.6F` in both versions; this is the upward step limit, not the old candidate's downward displacement.
Movement meaning: When a player meets the step gate and the step route wins the horizontal comparison, 1.14.4 uses an input-Y-aware vertical correction. The resulting vertical movement depends on collision geometry because that correction can be clipped. The 1.13.2 route offsets the achieved rise before its own collision clipping and has no input-Y term. This comparison establishes only the 1.13.2→1.14.4 endpoint difference, not an exact patch cutoff.
