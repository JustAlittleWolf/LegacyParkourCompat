# Eye submersion reads contextual fluid height

1.13.2, Ornithe Feather Gen2 build 2: `net/minecraft/entity/Entity.java`, `isSubmergedIn`, lines 1042–1051, and water-state refresh, lines 947–980; `net/minecraft/fluid/FlowingFluid.java`, `getHeight`, lines 447–450.
1.14.4, Ornithe Feather Gen2 build 2: `net/minecraft/entity/Entity.java`, `m_69330161`, lines 1035–1052, and water-state refresh, lines 942–975; `net/minecraft/fluid/FlowingFluid.java`, `getHeight`, lines 442–454.
1.14, Yarn: `net/minecraft/entity/Entity.java`, `isInFluid`, lines 986–998; `net/minecraft/fluid/BaseFluid.java`, `getHeight`, lines 430–436. The contextual rule is present in this first stable 1.14 release and persists through 1.14.4. Yarn 1.14.1–1.14.2 use `isInFluid`; 1.14.3 uses `isSubmergedIn` for the helper.

Difference: Both sides reject boat passengers and sample fluid at `y + getEyeHeight()`, then compare that double eye height against the sampled block's fluid height plus `0.11111111F`, with the addition performed in float. In 1.13.2, flowing-fluid height is `state.getLevel() / 9.0F`. In 1.14–1.14.4, the world-aware height is `1.0F` when the block above contains the same fluid, otherwise it uses the same level-derived value. The helper also has a `checkLoaded` branch and the tick refreshes pass `true`, but the client world's virtual `isChunkLoaded(int,int)` override always returns true (1.14 Yarn `ClientWorld.java:212–214`; 1.14.4 Feather `ClientWorld.java:222–224`). Thus this branch does not establish a client chunk-residency difference.

Movement meaning: With the eye near the top of a non-source flowing-fluid block that has the same fluid above, contextual height can make the player submerged where the old state-only height does not. The tick feeds the eye-fluid state into `updateSwimming`, so sprinting can enter swimming under the changed condition. An absent adjacent chunk does not reject the point query through this inherited client-world check.

Native 26.2 eye-state gate and phase comparison: `decompiled_minecraft/26.2/unobfuscated/net/minecraft/world/entity/Entity.java`, `baseTick`, 528–532, reads `wasEyeInWater` from `isEyeInFluid(WATER)` before refreshing `EntityFluidInteraction` and then updating swimming. The generic `Entity.isUnderWater` is a separate derived value (`Entity.java:1613–1615`): prior `wasEyeInWater` AND current body-water state. `Player.updateIsUnderwater` instead writes Player's distinct `wasUnderwater` field from `isEyeInFluid(WATER)` (`Player.java:304–306`); `Player.tick` invokes it before `super.tick` (`Player.java:259–260`). `LocalPlayer.isUnderWater` overrides the generic method to return that player cache (`LocalPlayer.java:1176–1179`).

`EntityFluidInteraction.update`, 32–89, resets trackers before admission. It scans only if `hasFluidAndLoaded` (91–119) finds every chunk touched by the deflated fluid-interaction box padded one block in X/Z at FULL status and finds any fluid in covered vertical sections. During scanning it marks `eyesInside` only for a matching fluid cell at the entity's X/Z whose vertical interval contains eye Y (52–70). A missing padded adjacent chunk returns before scanning; eye state therefore remains false even when the eye cell and entity box are otherwise loaded and wet. Because both player and generic entity latches read the prior tracker before the refresh, a denied refresh is observed on the following tick through those prior-state reads.

Keep the consumers separate. Native `Entity.updateSwimming` (1635–1642) dynamically enters swimming only when sprinting, `isUnderWater()` is true, the entity is not a passenger, and the current block position is water. If already swimming, the branch ignores eye state and requires sprinting, body-water and not being a passenger. `LocalPlayer.canStartSprinting` (1141–1148) separately uses the Player cache via its override: the underwater condition permits starting sprint while fall-flying or moving slowly. That is a 26.2 target contrast, not the historical consumer contract. Historical 1.13.2, 1.14 Yarn and 1.14.4 swimming updates are respectively `Entity.updateSwimming` at 953–958, 895–900, and 948–953; their non-swimming branches call `isSubmergedInWater()` (1.13.2/1.14.4) or `isInWater()` (1.14 Yarn), while already-swimming branches use body-water. They do not use the modern `LocalPlayer.canStartSprinting` cached API route. The padded admission finding remains limited to this source-level gate and its potential interaction with these distinct readers; it does not establish a product defect or require a broad eye-tracker implementation. `LivingEntity.isEyeInFluid` reads used for drowning/air supply (26.2 `LivingEntity.java:436–445`) remain outside movement scope.
