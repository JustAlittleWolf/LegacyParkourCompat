# flight cancels crawl slowdown only in 1.14.4

1.14.4, Mojmap: `LocalPlayer.java`, `aiStep`, lines 628–634 and 727–732; `KeyboardInput.java`, `tick`, lines 13–25; `Entity.java`, `isVisuallySwimming` and `isVisuallyCrawling`, lines 1836–1842.
1.15, 1.15.1 and 1.15.2, Mojmap: `LocalPlayer.java`, `isMovingSlowly` and `aiStep`, lines 602–604, 633–640 and 735–746; `KeyboardInput.java`, `tick`, lines 13–25; `Entity.java`, `isVisuallySwimming` and `isVisuallyCrawling`, lines 1815–1825. The 1.15 and 1.15.1 `LocalPlayer.java`, `KeyboardInput.java` and `Entity.java` bytes are identical and match each ready source manifest.

Difference: Conditional input witness, not a pose-reachability claim: assume the local player is already in dry `Pose.SWIMMING`, is ability-flying and the controlled camera, has current sneak/shift input down, holds one cardinal horizontal direction, is not a spectator, and is not using an item. In both versions the assumed pose makes `isVisuallyCrawling()` true (`getPose() == Pose.SWIMMING && !isInWater()`), which supplies the slow-movement gate before keyboard polling. In 1.14.4 `LocalPlayer.aiStep` passes `isVisuallySneaking() || isVisuallyCrawling()` and spectator state to `KeyboardInput.tick`; the keyboard polls current sneak input and applies `(float)(axis * 0.3)` to each axis when non-spectator and current sneak or the supplied prior-pose predicate is true. In 1.15.2, `isMovingSlowly()` is crouching or visually crawling; `aiStep` supplies that value to `KeyboardInput.tick`, which applies the same double-literal multiplication and float narrowing after polling keys. For the assumed cardinal axis `±1.0F`, each keyboard result is `(float)(±1.0F * 0.3)`.

The subsequent horizontal operation differs. In 1.14.4 `LocalPlayer.aiStep` applies item-use scaling first, then its `abilities.flying && isControlledCamera()` block divides both stored impulses by the double literal `0.3` when current sneak input is down, narrowing each result to float. With the witness's no-item-use condition, this yields full-scale cardinal input after the division. In 1.15, 1.15.1 and 1.15.2, the controlled-flight block only changes vertical `j` from jump/shift state and does not divide horizontal input; with no item use, the cardinal input therefore remains the float-narrowed `0.3` result. Item use is deliberately excluded from this witness: the source applies its `0.2F` multiplier after keyboard polling and before 1.14.4's horizontal division, so that combined operation has a different result and is not claimed here.

The dry swimming-pose state is an explicit precondition only. This finding does not establish how that pose is reached, its pose-selection gates, or collision/dimension-provider reachability.

Movement meaning: For this conditional state witness and without item use, the stored cardinal horizontal input is restored to full scale by controlled flight in 1.14.4, while it remains at the 0.3-scaled value in 1.15, 1.15.1 and 1.15.2. This is an input-operation difference; it makes no broader trajectory or pose-reachability claim.
