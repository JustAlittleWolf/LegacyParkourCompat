1.15, Mojmap: `1.15/mojmap/net/minecraft/client/player/LocalPlayer.java`, `isShiftKeyDown`, lines 591–593, `isCrouching`, lines 596–600, `isMovingSlowly`, lines 602–604, and `aiStep`, lines 632–640; `1.15/mojmap/net/minecraft/client/player/KeyboardInput.java`, `tick`, lines 13–26; `1.15/mojmap/net/minecraft/world/entity/Entity.java`, `canEnterPose`, lines 1605–1607, and `isVisuallyCrawling`, lines 1819–1825. Exact 1.15.1 and 1.15.2 retain these members and the same input sampling operation.

Difference: In 1.14.4 the local player evaluates its crouch-or-crawl predicate before polling input and passes that value plus spectator state to the keyboard. After polling current sneak input, keyboard slowdown requires no spectator and either current sneak input or the supplied pre-poll predicate. In 1.15 the keyboard instead slows only for the supplied pre-poll `isMovingSlowly` value: it neither combines the newly sampled shift input nor applies a separate spectator gate. `isMovingSlowly` is crouching or the unchanged crawl predicate, which requires swimming pose and no body water. The crouching branch requires no ability flight, no swimming state and collision-free crouch fit, followed by previous input shift intent or standing-fit failure. 1.15 additionally excludes sleeping from that standing-fit-failure branch, while previous shift intent remains an alternative. Neither crouching branch has a passenger guard. The keyboard scalar remains `(float)(axis * 0.3)` on both axes; item slowdown follows input polling.

Movement meaning: With an ordinary non-flying, non-swimming player in open space, forward held, no item use and previous sneak input false, pressing sneak during this tick produces `0.3F` forward input in 1.14.4 but `1.0F` in 1.15. With sneak still held, the next tick's previous input makes the newer predicate true and produces `0.3F`. On releasing sneak after it was held, the pre-poll predicate can keep input slowed for that release tick in both versions. Crouch-fit failure, forced crouching and dry swimming-pose crawling can independently determine the supplied predicate; actual pose production and collision shapes remain separate inputs. This changes an existing player input response, rather than introducing a new movement feature.

## Stored keyboard-input continuation through 1.21.4

This continuation was checked against exact Mojmap source publications in the canonical decompiled tree for 1.15.2; 1.16, 1.16.1, 1.16.2, 1.16.3, 1.16.4 and 1.16.5; 1.17 and 1.17.1; 1.18, 1.18.1 and 1.18.2; 1.19, 1.19.1, 1.19.2, 1.19.3 and 1.19.4; 1.20.1, 1.20.2, 1.20.3, 1.20.4, 1.20.5 and 1.20.6; and 1.21, 1.21.1, 1.21.2, 1.21.3 and 1.21.4. For legacy ready publications, relevant source files matched the sibling source manifest. For 1.16.3, 1.16.4, 1.17, 1.20.3, 1.21 and 1.21.2, the exact release identity and source hashes were taken from `mojmap/.decompile-provenance.json`, and the relevant source files matched those provenance entries. The 1.20.3 provenance input is `https://piston-meta.mojang.com/v1/packages/86c3a686b59ee1bcd70febee4de962ec3e1a5d87/1.20.3.json` (SHA-256 `05e727aac55594b6014e9714ad38fa16af09f075daf5efa0f5743f2453fa8fc2`); its `KeyboardInput.java`, `LocalPlayer.java`, `Entity.java` and `Player.java` hashes match the source entries in that marker. The next checked release, 1.21.5, is a separate derived-input boundary and is not included in this stored-axis operation.

From 1.15.2 through 1.18.2, `LocalPlayer.isMovingSlowly()` remains `isCrouching() || isVisuallyCrawling()`. `aiStep` computes the `crouching` field before calling `input.tick(this.isMovingSlowly())`; the keyboard polls directional keys into independent `0.0F`/`1.0F`/`-1.0F` axes. For a true supplied pre-poll boolean, 1.15.2 through 1.18.1 multiply each axis by the double literal `0.3` and narrow the result to float: `axis = (float)(axis * 0.3)`. Starting in 1.18.2, the operation is float multiplication by `0.3F`: `axis *= 0.3F`. These expressions are retained as distinct source math, not normalized to one operation. The current shift key is polled into `shiftKeyDown` by that same keyboard call after the crouching predicate was computed. The optional item-use multiplier (`0.2F`) is applied by `LocalPlayer.aiStep` after the keyboard call, guarded by `isUsingItem() && !isPassenger()`.

Two ordinary crouch-predicate cutovers are present. In 1.16, `Entity.canEnterPose(Pose)` first changes from testing the unmodified pose box to testing `getBoundingBoxForPose(pose).deflate(1.0E-7)` with `level.noCollision`; 1.16, 1.16.1, 1.16.2, 1.16.5, 1.17.1, 1.18, 1.18.1, 1.18.2, 1.19, 1.19.1, 1.19.2, 1.19.3, 1.19.4 and 1.20.1 retain that inset provider. In 1.20.2, `LocalPlayer.aiStep` adds `!this.isPassenger()` to the ordinary crouching field predicate after the flight and swimming gates and before the crouch-fit query; this guard remains in the checked 1.20.4, 1.20.5, 1.20.6, 1.21.1, 1.21.3 and 1.21.4 sources. The pose-fit provider moves to `Player.canPlayerFitWithinBlocksAndEntitiesWhen(Pose)` by 1.20.2 and constructs the box from `getDimensions(pose).makeBoundingBox(position()).deflate(1.0E-7)` before `level().noCollision`; the same inset and provider operation are present in 1.21.4. Thus the `1.0E-7` fit-box inset is continuous across the provider rename.

The player-local tick tail keeps item-use slowdown after keyboard polling through 1.21.3. In 1.21.4, `KeyboardInput.tick()` first polls keys and reconstructs the independent axes; `LocalPlayer.aiStep` then applies item-use scaling (`0.2F`) before testing `isMovingSlowly()` and multiplying both axes by the sneaking-speed attribute. This is an operation-order change from 1.21.3, where the slow scalar is passed into `input.tick(isMovingSlowly, scalar)` and item-use scaling follows that call. 1.21.4's separate post-poll multiplication preserves the stored-axis response but makes combined item-use-and-sneak rounding/order distinct.

For the ordinary default keyboard case, each axis is -1.0F, 0.0F or 1.0F before scaling, and the source gate/order above determines when the default sneak scalar applies. The scalar's production is a separate dependency: 1.15.2–1.18.1 uses the double `0.3` literal before float narrowing; 1.18.2 uses float `0.3F`; 1.19–1.20.6 computes a clamped `0.3F + EnchantmentHelper.getSneakingSpeedBonus(this)`; 1.21 onward reads `Attributes.SNEAKING_SPEED`. Custom attribute modifiers and Swift Sneak therefore are not established by the ordinary default-input claim and require their own source closure. This finding also does not establish movement inputs from non-keyboard `ClientInput` implementations.

The newly published 1.20.3 source closes the previously absent middle point between 1.20.2 and 1.20.4.
