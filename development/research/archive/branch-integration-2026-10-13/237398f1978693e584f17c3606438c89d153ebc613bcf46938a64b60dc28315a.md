## Guards, progress, and player-query reachability

Both endpoint methods construct the extended base shape only when `!extending && isSourcePiston`. Both return that base shape early when `progress < 1.0F` and the thread-local `NOCLIP` direction equals the piston movement direction. The head-threshold branch is reached when that matching guard is false. Thus the finding's exclusion for the matching piston-push query is correct; it does not conflate that direct push path with ordinary block collision.

In 1.16, `tick()` advances a value below `1.0F` by `0.5F` and stores it, making `progress == 0.5F` reachable. `MovingPistonBlock#getCollisionShape` dispatches the moving block query to `PistonMovingBlockEntity#getCollisionShape`. A concrete client-player route is `LocalPlayer#move` → `Entity#move` → `Entity#collide` → `collideBoundingBoxHeuristically`: for a normal player with `noPhysics == false` and a requested move with at least two nonzero components (such as diagonal ground movement), the heuristic combines `level.getBlockCollisions(...)`. `CollisionGetter#getBlockCollisions` constructs `CollisionSpliterator`; its moving-piston candidate reads the block state's collision shape, offsets it, and emits it when it intersects the queried entity box. The block-state shape call reaches `MovingPistonBlock#getCollisionShape`, closing the concrete player query path to the changed selector. This establishes reachability only; it does not claim a specific displacement.
