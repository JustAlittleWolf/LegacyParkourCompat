## Evidence and conclusions

- **Eligibility math matches 1.14.4.** Feather `LocalClientPlayerEntity#aiStep`, line 708, requires a fresh jump edge, airborne state, `y < 0.0`, not already fall-flying, and no ability flight. `ElytraJumpStart.shouldStartFallFlying` preserves those predicates and uses `!(y < 0.0)`, so NaN is rejected just as the source comparison rejects it. `ElytraItem.canFly` at line 20 uses `damage < maxDamage - 1`; the implementation uses the same strict comparison. No casts or arithmetic were rearranged.
- **Passenger, ladder, and water behavior is retained for the 1.14 delta.** The old call site contains no passenger or ladder check, and it does not reject water before sending `START_FALL_FLYING`. The current 26.2 call site has a climbable gate, which `isOnClimbableForFallFlyingStart` disables for this behavior. Its outer gate has no passenger check. The wrapped `Player.tryToStartFallFlying()` is not invoked when this historical behavior is present, so its newer water and other helper checks do not suppress the old request.
- **Request timing and local state match the old path.** The current call site invokes the wrapped helper once and sends one command packet only when it returns true. The historical hook returns the eligibility result without calling vanilla or `startFallFlying()`, so it does not set the local shared fall-flying flag before the request; this matches the 1.14.4 source. The adjacent 1.15.2 source calls `tryToStartFallFlying()` before sending, and that helper sets the shared flag, confirming the reviewed distinction.
- **The independent creative-flight ordering gate is covered.** For the 1.14 change, `justToggledCreativeFlightForStart` returns false, allowing the later Elytra gate in the same `aiStep` after flight toggles off; `shouldStartFallFlying` still rejects when the toggle turns flight on. Those are the two sides of the 1.14 ordering. This hook is registered once under `player.elytra.jumpStart`; a separate mechanic registration is unnecessary for the same start-request gate. For later selections the V1_14 change is not chosen: `ChangeResolver` filters to `emulates >= selected`, and the untouched 26.2 `LocalPlayer#aiStep` still gates on `!justToggledCreativeFlight`. Thus the independent 1.15.2 ordering finding is preserved by the native fallback. This does not claim a first changed release or add a V1_15_2 cutover.
- **Mixin bindings match current 26.2 source.** `LocalPlayer#aiStep` calls `Player#tryToStartFallFlying()Z`, `Entity#onClimbable()Z`, and stores `justToggledCreativeFlight`; the three mixin injections target those operations/local by method and descriptor/name. The 26.2 `Player#tryToStartFallFlying` writes the shared flag, which the historical wrapper deliberately skips. Disabled/native lookup falls through to the original invocation/value in all three injections.
- **Resolution and scope are appropriate.** `ElytraJumpStart` is annotated `@MovementChange(emulates = V1_14)` and registered in the 1.14 provider. Resolver direction means it supplies the older behavior for selections through that bucket, while later selections without an applicable start hook retain vanilla. The change is in a shared `LocalPlayer` path but only affects player state; it does not alter blocks, rendering, other entities, vehicles, or combat/health behavior.
