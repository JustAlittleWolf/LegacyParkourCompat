# Integrated movement implementation static decision

Reviewed integrated implementation commit `d7b56bf8ce468f756044c6087e12466a2c176cb2` on `feat/movement-completeness-integration`. This report covers the integrated 1.8 implementation delta and its lookup, selection, and native fallbacks. Exact decompiled source and remapped bytecode are the reference. No wiki-audit files were read.

## Decision

**No static blocker remains in the reviewed 1.8 deltas at `d7b56bf`.** The pane mask defect found in the first implementation was corrected by `8b71cda`; the direct velocity cutoff matches the accepted source delta; the dimension refresh runs through the common player tick path and selects the correct entity profile; and all reviewed hooks retain native behavior when no historical player hook resolves. This decision does not establish runtime Mixin application or tick-by-tick movement parity.

## Delta review

- **Velocity cutoff (`6414203`).** Exact 26.2 `LivingEntity.aiStep` source and remapped bytecode identify the direct `setDeltaMovement(DDD)V` call at ordinal 0 before input/jump processing. The three argument modifiers filter independently with `abs(component) < 0.005`, retaining equality. The `V1_8` registration and `MovementRuntime.find` restrict the behavior to applicable players/profiles. Empty lookup returns each original component, preserving native behavior for CURRENT, later profiles, disabled emulation, and non-player entities. The source and bytecode phase/descriptor/ordinal check was completed in the earlier static checkpoint; no issue found.
- **Dimension refresh (`52a1620`).** The shared `LivingEntity.tick()` head injection checks the movement epoch for players, resolves dimensions for the current pose/profile, and refreshes only when width, height, or eye height differs. Global selection, per-player selection/clear, and registry rebuilds advance the epoch. Exact 26.2 source places `Player.updatePlayerPose()` after `super.tick()`; client `LocalPlayer.tick()` and server `ServerPlayer.doTick()` reach that path. This addresses the prior cached-dimensions-on-profile-switch gap structurally. It does not change non-player dimensions. Live refresh behavior remains a runtime witness item.
- **Pane collision shapes (`cea48d0`, corrected by `8b71cda`).** Registration is limited to the 18 existing pane/bar block IDs. The corrected branch assembly explicitly returns the full cross only when no neighbors connect; otherwise it adds each axis only when that axis has one or two connections. Compared with exact 1.8.9 `PaneBlock.addCollisions` branches, all 16 masks now match: one arm yields its half bar, an opposing pair yields its full bar, perpendicular connections union their arms, and the zero-neighbor case yields `X ∪ Z`. The old six-mask over-collision is resolved. The current predicate includes a solid-render criterion and the explicit pane/glass categories from the legacy connection test. The old code queried block-global `isOpaque()` while the new code queries state-level `isSolidRender()`; this review did not exhaustively prove state-by-state equivalence, and found no concrete vanilla mismatch.
- **1.8 pose dimensions (`cd42884`).** The V1_8-only `SneakingDimensions` restores standing width and height for `Pose.CROUCHING` while retaining the current vanilla eye height. The exact 1.8.9 player source sets the ordinary player size and has no sneak pose resize. Because the resolver chooses the closest applicable change for this mechanic, V1_8 receives this delta; CURRENT has no historical hook, and the existing V1_12 swimming behavior remains the closest dimension implementation only for profiles to which it applies. No regression found in the added 1.8 behavior.
- **Collision dispatch and fallback.** `BlockStateCollisionShapeMixin` is registered in the required common mixin configuration and injects at the return of the context-bearing block collision-shape method. It asks `MovementRuntime.playerFrom(context)` and does nothing for non-player or absent contexts. For player contexts it resolves a shape by the vanilla block identifier and replaces the vanilla result only when a shape is registered and returns a value. `MovementRuntime.find` returns empty when the entity is not a player, movement emulation is disabled, or the selected profile has no applicable registration. The velocity and dimension call sites likewise retain their original/native values on empty lookup. `ChangeResolver` returns no changes for CURRENT and chooses only the nearest applicable registration per mechanic. Per-player selection uses `profileFor(entity)`.

## Separate remaining coverage gap

The exact accepted 1.9.4 source evidence still shows a crouching height of 1.65 only when the resize box is collision-free, while the current V1_9.4 emulation leaves `Pose.CROUCHING` at the native 1.5 height. That gap predates the reviewed 1.8 implementation commits (base `c1c5ea3` had no crouch-dimensions change), so it is not a regression from these deltas and is tracked separately. This review does not extend it through V1_13 without an independently accepted boundary. The integrator indicated it is not a blocker for the 1.8 fixes.
