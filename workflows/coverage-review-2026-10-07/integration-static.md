# Independent movement-completeness static review

Checkpoint: integration commit `41c81efac78291c345ac7d16cdf8aa6a6c2f9183` on `feat/movement-completeness-static-review`, based on the committed movement-completeness integration branch. This is a static source review, not a runtime movement-parity claim. The wiki-audit reports were not read.

## Critical bugs

- **Live profile changes do not refresh a player's pose dimensions/AABB.** `MovementControllerImpl.select` replaces the profile and increments `epoch`, but nothing in `src/` consumes `MovementRuntime.epoch()` or listens to version changes to call `refreshDimensions`. `PlayerDimensionsBehavior` only changes a value when `LivingEntity.getDimensions(Pose)` is next called; changing profile while already crouched does not itself recalculate the current bounding box. This contradicts the API promise that switching takes effect on the next player tick, including pose and dimensions. Relevant files: `src/main/java/me/wolfii/legacyparkourcompat/impl/MovementControllerImpl.java:74-97,163-176`, `src/main/java/me/wolfii/legacyparkourcompat/api/MovementController.java:80-87`, `src/main/java/me/wolfii/legacyparkourcompat/mixin/LivingEntityMixin.java:193-201`. The parent assigned this fix to another implementation owner; this review did not modify it.

## Other actionable findings

- **Server per-player selection is not part of the join handshake.** `MovementController.selectFor` changes the server's player-specific profile, and `MovementRuntime` uses that override for server-side player hooks. `ParkourHandshake.configure` always sends `selectedVersion()` (global profile), never the connecting player's `versionFor(player)`. If another server mod uses the public per-player API, client prediction and server movement can run different profiles. There are no in-repository `selectFor` callers, so this is a conditional public-API integration issue, not a current built-in path. Relevant files: `src/main/java/me/wolfii/legacyparkourcompat/impl/MovementControllerImpl.java:63-79,99-111`, `src/main/java/me/wolfii/legacyparkourcompat/network/ParkourHandshake.java:24-35`.
- **Unknown required profile can be acknowledged as if applied.** A client that does not know the server's profile maps it to `CURRENT` in `ParkourVersion.of`. The receiver then echoes the raw server ID in the acknowledgement; the server compares the echoed string to its configured ID and reports success. The client can therefore run vanilla while the server runs historical movement. This requires mod-version/profile skew, but the handshake currently accepts all modded clients. Relevant files: `src/main/java/me/wolfii/legacyparkourcompat/api/ParkourVersion.java:185-198`, `src/client/java/me/wolfii/legacyparkourcompat/LegacyParkourCompatClient.java:20-36,67-70`, `src/main/java/me/wolfii/legacyparkourcompat/network/ParkourNetworking.java:17-35`.
- **Via-inferred profile is absent from the selection screen's model.** The Via path calls `MovementController.select` directly but does not update `MovementVersions`' `wanted`/`input`; the screen reads those fields and commits its draft on close. Opening and closing the screen can overwrite the active Via selection with stale UI state. This does not affect movement until the screen is closed. Relevant files: `src/client/java/me/wolfii/legacyparkourcompat/LegacyParkourCompatClient.java:49-56`, `src/client/java/me/wolfii/legacyparkourcompat/config/version/MovementVersions.java:130-139,187-202`, `src/client/java/me/wolfii/legacyparkourcompat/config/MovementVersionScreen.java:140-155`.

## Accepted static evidence

- Profile selection is session-only and the version screen commits its draft when closed. `CURRENT` resolves to an empty profile. Historical versions are all marked partial, so the UI does not claim completeness.
- `ChangeResolver` independently chooses the nearest applicable registration per `MechanicKey`; a `CURRENT` selection resolves no historical changes. Registry application is independent per interface/key and the controller canonicalizes non-older profiles to `CURRENT`.
- Collision-shape dispatch is on the shared `BlockBehaviour.BlockStateBase.getCollisionShape(BlockGetter, BlockPos, CollisionContext)` return path. It only dispatches for player entity contexts and therefore bypasses the two-argument cached shape for player collision while retaining the vanilla virtual shape result as the default. Empty contexts and non-player entity contexts stay native. Global selection rebuilds empty-context state caches. Exact runtime Mixin application and subclass/bytecode coverage were not independently exercised here.
- The source contains a `PlayerDimensionsBehavior` dispatch from `LivingEntity.getDimensions`, but the only retained implementation at the integration checkpoint is `SwimmingDimensions` and it handles `Pose.SWIMMING`; exact historical crouch-pose heights remain source-evidence-pending.
- `CURRENT` and non-player hook paths are guarded by `MovementRuntime.appliesTo`; block-specific deltas are registered by vanilla block identifier. No modern-only block behavior was identified in the collision-shape registration inspected at this checkpoint.
- The retained integration record reports exact 26.2 selector/descriptor/ordinal checks against published bytecode, registration inventory counts, and a successful no-tests build. These are accepted as prior integration evidence, not repeated for the full foundation.
- **Critical implementation commit `641420367f4efa62127d630ae480c3cc205d924a` — accepted static delta.** The admitted 1.8.9 → 1.9.4 STATE-01 report names a strict per-component cutoff and threshold interval; its supplied SHA-256 is recorded in the handoff. In 26.2 source, `LivingEntity.aiStep` prepares velocity, then calls `setDeltaMovement(dx, dy, dz)` at the only direct `(DDD)V` call before `applyInput` and jump handling. Exact remapped 26.2 bytecode in `C:/Users/Wolfi/.gradle/caches/fabric-loom/26.2/minecraft-merged.jar` confirms the call is on `LivingEntity`, descriptor `(DDD)V`, and ordinal 0; earlier `setDeltaMovement` in `aiStep` is the Vec3 overload. The three `@ModifyArg` injections filter the respective components through `Math.abs(component) < 0.005`, with equality retained. `MovementRuntime.find` makes it player-only and returns empty when disabled or when the selected profile has no such hook; all three methods then preserve their original argument. The change is registered once at `V1_8`, so CURRENT and profiles from V1_9 onward use the native threshold. Source phase, owner/descriptor, ordinal, player/profile fallback, toggle behavior, and arithmetic match the accepted delta. No issue found in this commit. This is source/bytecode static verification only, not runtime Mixin application or trajectory proof.
