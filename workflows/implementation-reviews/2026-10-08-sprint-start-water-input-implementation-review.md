## Confirmed finding in the submitted commit

**Important — grounded double-tap restriction was narrowed to two selected profiles.** In the submitted `change/v1_12/SprintInputStart.java`, `allowDoubleTapStart` returned `vanilla` unless the selected profile was exactly `V1_11_2` or `V1_12`. `ChangeResolver` chooses the closest registered change with `emulates >= selected` separately for this hook key. Therefore V1_8, V1_9, V1_10, V1_10_1, V1_11 and V1_11_1 also resolve the V1_12 change; the exact-profile guard made those older profiles fall through to the modern airborne decision.

That fallthrough is observably wrong for source-covered older profiles. In current 26.2 `LocalPlayer.aiStep()`, after `canStartSprinting()`, the double-tap path calls `setSprinting(true)` when `sprintTriggerTime > 0` (first call at the inspected source lines 806–812). A player who is airborne but otherwise eligible can therefore enter sprint through the wrapper. The exact 1.8.9, 1.9.4, 1.10.2, 1.11.2 and 1.12.2 sources put the double-tap decision under `onGround`; for example, 1.12.2 `LocalClientPlayerEntity.mobTick()` lines 719–731 checks `onGround` before setting the timer or starting sprint. Thus the submitted guard suppresses the V1_12 delta precisely for earlier selected profiles whose ready endpoint has the same grounded rule.

**Proposed correction (not independently accepted):** `allowDoubleTapStart` in the separate review-branch commit returns `vanilla && player.onGround()` without a profile guard. The resolver's closest-change rule makes that V1_12 behavior apply to older selections only while it is the closest registered change. V1_13 selects its own change, retaining the underwater exception; V1_14 and newer do not select either of these V1_13/V1_12 deltas, and `CURRENT` resolves no changes. The diff is preserved for separate independent review; this report does not accept it or recommend integration before that review.

## Bounded source correspondence and interaction checks

- **V1_12.2:** the exact local source gates double-tap on ground, prior forward-input state, forward threshold, not already sprinting, food/flight, not using an item, and no Blindness; the separate held-key path has no ground check but retains forward, food/flight, item-use, Blindness and key-pressed gates. The V1_12 class leaves the held-key result unchanged and only tightens the double-tap setter path. Current `Player.isMobilityRestricted()` is exactly the Blindness predicate, `hasEnoughFoodToDoExhaustiveManoeuvres()` delegates to food availability or may-fly, and `canStartSprinting()` retains forward impulse and its `isSlowDueToUsingItem()` restriction before either setter wrapper. The patch does not broaden the held-key route. The current item-use predicate is component-aware, unlike 1.12's unconditional `isUsingItem()` gate; behavior with modern sprintable-use item components is outside the historical source claim.
- **V1_13.2:** the local source allows double-tap when grounded **or** submerged, but held-key start only when dry or submerged. The V1_13 implementation keeps those as separate methods and requires the incoming setter value to remain true. The shared shallow-water start allowance is adjusted through `canStartSprinting`'s `isSprintingPossible` argument; the branch-specific held-key predicate still rejects partial-water starts. The submerged predicate uses the current local player's water-state method at the setter call.
- **Timer and call order:** current `aiStep()` decrements the sprint trigger timer, checks eligibility, processes the double-tap call, then processes the sprint-key call. The two `@WrapOperation` selectors target ordinals 0 and 1 of `setSprinting(Z)V`, matching those two `true` calls in the exact 26.2 source. Later false calls are not intercepted. The existing sprint-window hook remains responsible for the timer duration.
- **Water and continuation:** V1_12's existing `WaterSprintGate` is registered in its provider and resolves independently under its own mechanic key. The new hook only adjusts the start allowance; existing `shouldStopRunSprinting` dispatch and `SwimmingUpdate` code are unchanged. The patch does not alter food, effect, item-use, or vehicle state producers.
- **Riding:** current `isSprintingPossible` uses the vehicle's `canSprint` capability for passengers, while the inspected 1.12/1.13 local start predicates use the normal hunger/flight gate. This is pre-existing shared eligibility behavior and is outside the accepted finding's branch-specific water/double-tap delta; this review does not claim historical mounted sprint-start parity.
