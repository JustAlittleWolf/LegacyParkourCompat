## Verified behavior and activation path

The accepted source delta is implemented at the saved-player-state boundary. 1.10.2 writes `FallFlying` and restores shared flag 7 from that key; the 1.9.4 methods do neither. The V1_9 change omits that key and clears flag 7 after the server player's saved data has been read. `ServerLivingEntityMixin` applies the save rule only when the entity is a `ServerPlayer`; `ServerPlayerMixin` limits the load rule to player records. Other living entities are not altered.

The in-repository dedicated-server path activates the profile before player data load: common `LegacyParkourCompat.onInitialize()` registers changes and initializes the controller; `LegacyParkourCompatServer.onInitializeServer()` calls `ServerMovementConfig.load()`; a configured `movementVersion=1.9` reaches `MovementController.select(V1_9)`. The mod's configuration handshake reads the already-selected global version and forces that version on a modded client. In current 26.2, `PrepareSpawnTask.Ready.spawn()` constructs the `ServerPlayer`, loads stored input through `player.load(input)`, and only then calls `PlayerList.placeNewPlayer()`. `Entity.load()` dispatches to `ServerPlayer.readAdditionalSaveData()`, which calls `LivingEntity.readAdditionalSaveData()` before the mixin TAIL hook. ## Profile timing limit

The implemented hook is load/save scoped. The supported in-repository dedicated-server path selects the global profile in `LegacyParkourCompatServer.onInitializeServer()` from `ServerMovementConfig.load()` before any player can complete configuration and enter `PrepareSpawnTask.Ready.spawn()`. The handshake reads this already-selected server version and forces it on the client; it does not select or change the server profile. Therefore a configured V1_9 profile is active when the player's saved data is read. If an integrator uses the public `selectFor(UUID, ...)` API for an initial per-player profile, it must set that override before this player's data is read; the repository has no internal late per-player assignment path.

Changing a profile after player data has loaded is live version switching. That behavior is explicitly undefined/out of scope for this review, so the fact that the load hook does not retroactively clear flag 7 after a later profile change is not a blocker here. The per-player pre-load limitation is recorded rather than treated as a promised late-switch behavior. The API's general next-tick switching documentation does not change this persistence hook's load-time boundary.
