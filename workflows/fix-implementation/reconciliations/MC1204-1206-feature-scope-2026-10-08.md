## Per-finding scope disposition

### MC02 — split the cutoff from sprint precision

**Low-power cutoff: no eligible 1.20.4 vanilla player input established.** A's player jump power is `0.42F * getBlockJumpFactor() + getJumpBoostPower()`. In the exact A source, block properties default to jump factor `1.0F`; the only vanilla override in the block registry is Honey Block at `0.5F`. Thus the lowest vanilla block term is `0.21F`, and jump boost adds a nonnegative term. A vanilla 1.20.4 ground jump therefore cannot reach B's `power <= 1.0E-5F` gate. That gate is a real source-level response difference for supplied values, but the values that make it observable require a non-vanilla block/effect input or the new generic jump-strength attribute set to a non-default value (the latter is MC03). Do not add a historical cutoff rule for an unreachable old-era player input.

**Sprint arithmetic: genuine old-input delta, not covered for the 1.20.4 profile.** For an ordinary sprint jump, A evaluates `Mth.sin(floatAngle) * 0.2F` and `Mth.cos(floatAngle) * 0.2F` in float arithmetic before widening the components into `Vec3`. B multiplies the float trig results by double literal `0.2`, so the products are double precision. This branch is reachable with ordinary positive jump power and sprinting; the cutoff is irrelevant to it. Existing `change/v1_19_4/SprintJumpImpulse` reconstructs the older float impulse, but it is registered at `V1_19_4`. `ChangeResolver` only selects changes whose `emulates()` is not older than the selected profile, so that registration does not cover a `V1_20_4` profile; no later sprint-impulse registration exists in the current code. Recommendation: keep this as the implementation-eligible subdelta if the root review approves it; a narrowly versioned correction at the verified transition is needed. Do not bundle the unreachable cutoff into that change.

The boundary memo `e277edd19eb8f8ce63681ab7985a5d92df8a259f` is bound to blob `cda4a40cadde768c36b5523cc5c11a3a56adc78f`, raw SHA-256 `a97e20b5abaa131f9ec090d1d186eae63592d839e8cd9c3c254b80acdea8de82`. The `0.2F` versus `0.2` arithmetic is separate from cutoff reachability and retains the same boundary uncertainty.

### MC03 — generic jump strength: no eligible old-era delta

A computes `0.42F * blockJumpFactor + jumpBoostPower`. B computes `(float) JUMP_STRENGTH * factor * blockJumpFactor + jumpBoostPower`; B's syncable `generic.jump_strength` default is `0.42F`, and Player inherits the attribute from `LivingEntity.createLivingAttributes()`. The default therefore preserves A's base term. Only a non-default synchronized generic attribute changes the response. A has no generic player jump-strength attribute or vanilla player producer for such a value; its `horse.jump_strength` is not a player input. This is a source-accepted conditional consumer, but it establishes no eligible historical player delta. Recommendation: no code for MC03; do not invent or reset a historic value in response to a modern-only attribute producer.

### MC04 — generic gravity, old Slow Falling, and `noGravity` are separate

For an ordinary player with default gravity, A starts travel with `0.08`; B's `getGravity()` is also `0.08`. When descending with Slow Falling, A substitutes `0.01`, while B takes `Math.min(0.08, 0.01)`, also `0.01`. For ordinary land, water and lava movement, the old `!isNoGravity()` gates and B's effective-gravity-zero checks agree for the old `noGravity` state. A non-default generic gravity value, including a value below `0.01` in the Slow Falling branch or zero with `noGravity` false, is supplied by B's newly syncable `generic.gravity` attribute and has no equivalent 1.20.4 player attribute input. These generic-attribute cases are not eligible historical deltas.

The corrected finding and its blind acceptance expose a separate old-state interaction: in fall-flying travel, A's local gravity remains the literal `0.08` even when `noGravity` is true, and that local feeds the glide's vertical acceleration; B obtains zero from `getGravity()` when `noGravity` is true and uses zero in the same expression. This is not caused by the new gravity attribute. The exact-source search finds no 1.20.4 or 1.20.6 vanilla player writer for `setNoGravity`; the observed writers are mob/entity paths (including Vex/flying-mob behavior and entity NBT loading), not a player gameplay path. Thus a differing response is source-proven if a player arrives in fall flight with this existing flag set, but a vanilla player producer/reachability witness is not established. Recommendation: do not implement this under MC04's generic-attribute finding. Keep the `noGravity` fall-flight case as a separately scoped reachability question for root review; if a supported player producer is established, model that old branch specifically and preserve the old `.08` fall-flying input. Do not conflate it with ordinary no-gravity travel, Slow Falling, or modern attribute input.

### MC05 — generic step height: no eligible old-era delta

A's inherited player step height defaults to `0.6F`; the controlling-player passenger override raises it to at least `1.0F`. B reads syncable `generic.step_height`, default `0.6`, and keeps the same passenger minimum. Player construction inherits the attribute through the living-attribute builder. A non-default value changes the input to the step-candidate path, but only through B's newly introduced attribute; the old-era default and passenger case match. The accepted finding also leaves full step-candidate collision coverage open, so it does not prove a particular collision outcome. Recommendation: no code from MC05; do not add support for a modern-only non-default value or infer broader collision behavior.

### MC06 — generic scale: no eligible old-era player delta

A's `LivingEntity.getScale()` returns `1.0F` for a player (the baby branch does not apply to Player), and the player's pose dimensions use that scale. B reads syncable `generic.scale`, default `1.0`, and applies it to player pose dimensions; changed attributes refresh dimensions, eye height and bounding box. The default player inputs preserve dimensions. Only B's external non-default scale value changes the player dimension response; no corresponding old player input or producer exists. Recommendation: no code from MC06, and no added scale or block-state behavior.
