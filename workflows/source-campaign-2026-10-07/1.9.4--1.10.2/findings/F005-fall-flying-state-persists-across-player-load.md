## Source-level difference

B writes the current fall-flying flag as a `FallFlying` player/entity NBT boolean and restores flag 7 when that boolean is true. A's corresponding `LivingEntity` save/load methods do not write or read that key, and its default shared flag byte is zero. The normal player persistence path invokes these virtual living-entity methods in both releases.

## Reachability and dependencies

For a B-saved player record containing `FallFlying=true`, player loading restores the shared flag before the next movement tick. If the player remains off-ground and not riding with a fly-capable chest-slot Elytra, B's `flyingTick()` retains flag 7 and the following `moveRelative()` call selects its fall-flying movement branch. Loading the same tag through A's source path leaves its initialized flag clear, so the ordinary movement branch is selected. This route uses NBT-backed player state, server player persistence, synchronized flag state and vanilla Elytra equipment/durability checks; no data resource supplies the flag or a glide coefficient.

## Consequence and uncertainty

The source proves that 1.10.2 preserves this movement mode across player-data save/load and 1.9.4 does not. Under the stated preconditions, the later movement branch differs. No exact position or velocity trajectory, runtime reproduction, or behavior outside this endpoint pair is claimed. An invalid or missing Elytra, grounded state, or riding state causes B's existing `flyingTick()` guard to clear the flag before the glide branch.
