- Provider inventory: all 23 `getCollisionShape(..., CollisionContext)` implementations in each exact block source tree have identical A/B method bodies. Of these, only `ScaffoldingBlock`, `PowderSnowBlock` and `LiquidBlock` read context values. Scaffolding and Powder Snow inspect placement; LiquidBlock inspects `isAbove` and `canStandOnFluid` (A/B source SHA-256 `fde1e2837b405158c6bf9614eb36fff668d00bd1a46e600d54381d97438b553e`). For direct Player validation, the two placement-sensitive providers are Scaffolding and Powder Snow; B's placement context returns empty before their `isAbove` branches.
- Bounded concrete path and guards: a non-passenger Player movement packet reaches `ServerGamePacketListenerImpl#handleMovePlayer`'s new-collision validation branch, and its candidate target AABB includes a Scaffolding block whose stable top shape intersects the pre-move AABB. The server query runs after `player.move`; A evaluates `ScaffoldingBlock#getCollisionShape` with the ordinary entity context, and the stable-shape branch requires `isAbove(Shapes.block(), pos, true)` and `!isDescending()`. For a Player standing above the block and not descending, that branch returns `SHAPE_STABLE`. B constructs its context with `placement=true`, so the same provider returns `Shapes.empty()` before inspecting the other conditions. The context-dependent block shape therefore changes the validator's overlap result for this bounded geometry. Scaffolding's stable branch has no tag, equipment or resource input; the block is registered in each endpoint's `Blocks` source (A SHA-256 `026290c103c399d94ba4218317e3e627e7275836c5abe91fc4711443b7d2bec0`; B SHA-256 `5f929198d7e975bdf82582e7448be45601b9a0e140d435a1a6013e1b6d10ca9f`). Powder Snow is a second context-sensitive provider, but is not needed for this bounded claim. Other context-reading block providers were checked and do not change shape for Player under this context substitution.
- Correction response: the paired `handleMovePlayer()` branches keep the same accept/reject structure: when the new-collision query passes, both snap to the requested coordinates, update last-good movement, and continue normal movement bookkeeping (A lines 1048-1083; B lines 1067-1103); when it fails, both teleport to the pre-move coordinates, run fall-damage bookkeeping and remove the latest movement recording (A lines 1084-1089; B lines 1104-1109). A calls `removeLatestMovementRecordingBatch()` and B calls `removeLatestMovementRecording()`, but both corresponding `Entity` methods remove the last deque entry (A `Entity.java` lines 781-785; B lines 809-813). Thus the observed context-dependent shape result feeds an established server accept/correct decision; no separate correction-policy delta was found. This is a server-authoritative player movement/query change and does not claim the client `Entity.move` resolution changed. Independent review and pair-wide inventory closure remain open.
