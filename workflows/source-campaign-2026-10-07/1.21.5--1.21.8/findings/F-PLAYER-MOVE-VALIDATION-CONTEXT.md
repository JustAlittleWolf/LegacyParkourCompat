# Candidate: server player movement validation uses a placement collision context

- Finding ID: `F-PLAYER-MOVE-VALIDATION-CONTEXT-1.21.5-1.21.8`
- Status: candidate; the exact A/B query, Player-relevant shape providers and accept/correct response are source-verified; independent review and broader provider/resource closure remain pending.
- Slice routes: S4.3, S5.2, S7.1; inventories INV-COLLISION, INV-WORLD-MOVEMENT, INV-EXTERNAL.
- A evidence: after the server applies `player.move`, `ServerGamePacketListenerImpl#isPlayerCollidingWithAnythingNew` translates the target AABB, then calls `LevelReader#getCollisions(player, targetBox.deflate(1.0E-5F))` and tests returned shapes against the pre-move box (`ServerGamePacketListenerImpl.java:1131-1143`; file SHA-256 `fdb8726f77618ebcfd4fe3973e1740d999c2fd3d220ca4a3ddba837f160e6d69`). `CollisionGetter#getCollisions` gets entity collisions and ordinary block collisions using `CollisionContext.of(entity)` (`CollisionGetter.java:83-86`; SHA-256 `de8b38cdc04db6f981ab5d3c21cbd965f9abbd17fdcb393d706749f0f65ad920`). `CollisionContext.of` uses the ordinary non-placement entity context, whose bottom is `entity.getY()` (`CollisionContext.java:17-27`; SHA-256 `17a6ec5e1001522282203181b3b9734d5b2dd48b75b4a73ee7b5c42e2dbf2960`; `EntityCollisionContext(Entity, boolean, boolean)` lines 40-48 sets `entityBottom` from `entity.getY()` and `placement` from the third argument; `isAbove` lines 72-74 consumes that bottom value. - B evidence: the validator calls `LevelReader#getPreMoveCollisions(entity, targetBox.deflate(1.0E-5F), oldBox.getBottomCenter())` (`ServerGamePacketListenerImpl.java:1151-1163`; file SHA-256 `100f83ae1f264dd26170147cf1319f78b7bf837d5b1b5603934b414cde63a16d`). `CollisionGetter#getPreMoveCollisions` retains entity collision shapes but evaluates block shapes with `CollisionContext.withPosition(entity, oldBottomY)` (`CollisionGetter.java:89-105`; SHA-256 `03752693709491670a3c6b1d91114d46d92d6dfb1f48d3ecea3725c08b22ac8c`). - Concrete provider evidence: the unchanged `ScaffoldingBlock#getCollisionShape` returns an empty shape for placement contexts, otherwise selects shapes using `isAbove` and descending state (A/B lines 133-140; SHA-256 `98e41af291de4c5ed47f3d5aed06c947e8e31e368fed2242439e18362943a35a`). `PowderSnowBlock#getCollisionShape` also gates its player collision shape on `!context.isPlacement()`, `isAbove`, descending state, equipment walkability or fall distance (A/B lines 114-130; SHA-256 `de72fb6e70616d7727bf324b0da4a98250cabd97ad39ecbe1062732d47f39770`). These blocks predate the compared releases and are not modern-only features.
- Provider inventory: all 23 `getCollisionShape(..., CollisionContext)` implementations in each exact block source tree have identical A/B method bodies. Of these, only `ScaffoldingBlock`, `PowderSnowBlock` and `LiquidBlock` read context values. Scaffolding and Powder Snow inspect placement; LiquidBlock inspects `isAbove` and `canStandOnFluid` (A/B source SHA-256 `fde1e2837b405158c6bf9614eb36fff668d00bd1a46e600d54381d97438b553e`). Player inherits `LivingEntity#canStandOnFluid`, which returns false in both releases; it therefore gets no LiquidBlock collision shape. `LightBlock`'s `isHoldingItem` check is in `getShape()`, an outline-shape method, so it is not a collision provider. For direct Player validation, the two placement-sensitive providers are Scaffolding and Powder Snow; B's placement context returns empty before their `isAbove` branches.
- Exact precondition: a non-passenger player movement packet reaches the validator's new-collision branch with a target candidate box overlapping Scaffolding or Powder Snow, while the ordinary A query selects a non-empty shape and B's placement context returns empty; the resulting shape intersection with the pre-move AABB differs. Other vanilla block providers that inspect collision context were checked and do not change shape for Player under this context substitution.
- Correction response: the paired `handleMovePlayer()` branches keep the same accept/reject structure: when the new-collision query passes, both snap to the requested coordinates, update last-good movement, and continue normal movement bookkeeping (A lines 1048-1083; B lines 1067-1103); when it fails, both teleport to the pre-move coordinates, run fall-damage bookkeeping and remove the latest movement recording (A lines 1084-1089; B lines 1104-1109). A calls `removeLatestMovementRecordingBatch()` and B calls `removeLatestMovementRecording()`, but both corresponding `Entity` methods remove the last deque entry (A `Entity.java` lines 781-785; B lines 809-813). Thus the observed context-dependent shape result feeds an established server accept/correct decision; no separate correction-policy delta was found. This is a server-authoritative player movement/query change and does not claim the client `Entity.move` resolution changed. Independent review and broader provider/resource closure remain open.
