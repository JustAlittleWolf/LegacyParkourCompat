# Candidate: fresh-login spawn angle changes the initial player movement heading

- Finding ID: `F-PLAYER-FRESH-LOGIN-SPAWN-ANGLE-1.21.5-1.21.8`
- Status: candidate; source path and yaw-dependent movement consumer are verified, while client/server first-input timing, materiality and independent review remain pending.
- Slice routes: S1.1, S2.2, S7.3; inventories INV-TICK, INV-STATE, INV-EXTERNAL.
- A evidence: A `ServerPlayer` constructor calls `super(level, sharedSpawnPos, sharedSpawnAngle, profile)`, then snaps to `adjustSpawnLocation(...).getBottomCenter()` with yaw `0.0F` and pitch `0.0F` (A `ServerPlayer.java` SHA-256 `81ec90de6bf1521f45f1552c60af1ebb1a83fbcfa2eebf41b99e25b99d2f0d1b`; constructor lines 344-363). `PlayerList#placeNewPlayer()` does not apply another yaw for a player with no saved data before its connection teleport (A `PlayerList.java` SHA-256 `9d92d51c73c79ddaf6997e05d51eb21433cdf3e107a5f51f4b5248f5ef4471c9`).
- B evidence: `Player` and `ServerPlayer` constructors no longer set the initial spawn pose. In `PlayerList#placeNewPlayer()`, when player data is absent, B snaps the new player to `adjustSpawnLocation(...).getBottomCenter()` using `getSharedSpawnAngle()` and pitch `0.0F` before sending the connection teleport (B `PlayerList.java` SHA-256 `3ede172d032d66d3b0426b4299fe09b023d5b8628dc5dc19d1664395732ef4eb`; branch at lines 161-166). B `ServerPlayer.java` SHA-256 is `1933118f0445fcb08dcdd0a5abd9e658d8669c210ea8ce9dfbf206d6b7193612`. `Level#getSharedSpawnAngle()` returns `levelData.getSpawnAngle()` in both versions (A/B `Level.java` hashes `8f9d6135266b9d8e1cee0cd56bb1c2c1afaf5c6c311f93facb527077e54a38ef` / `47e9510cc54f8463faa0c63f389e9222cecf75372fc4ca059724d350bdb6be19`, lines 634-636).
- Direct Player movement consumer: paired `Entity#moveRelative()` calls `getInputVector(input, scale, this.getYRot())`, then adds that rotated vector to delta movement. The body is unchanged (A/B ranges and file hashes recorded in S3.4).
- Client handoff: A/B `ClientPacketListener#handleLogin()` creates or resets the local player, and the subsequent server connection teleport is consumed by the paired `handleMovePlayer()` / `setValuesFromPositionPacket()` correction methods in S7.1. Those consumers match across the versions; the candidate is the different yaw value supplied by the server before the local input vector uses `getYRot()`. Packet-versus-first-input ordering remains unverified.
- Exact candidate precondition: first login of a profile with no saved player data into a level whose shared spawn angle is nonzero; then the player provides directional input before another action changes yaw. A starts at yaw 0; B starts at the configured shared spawn angle. That heading can rotate the resulting direct Player movement vector. Returning players with saved pose and fresh logins into a zero-angle level do not follow this difference. `SetWorldSpawnCommand` accepts an `angle` argument and passes it to `ServerLevel#setDefaultSpawnPos()` (A/B `SetWorldSpawnCommand.java` SHA-256 `08bafad485c20cfee541657d75ab39139a40341c84c270fa3c8c325481fe788f` / `8f3f03cbddfd33a656bed7da33aa71ebe83e76514195d445691258e190e62157`). The shared-angle getter reads this stored value in both versions.
- Analysis: this is an initial player-yaw difference feeding the unchanged movement input rotation, not a changed travel formula. The route is direct movement-relevant; exact first-input/client synchronization timing and whether a typical configuration makes it material still need closure.
