# Candidate: client owner reacquisition can change a fishing-hook player pull

- Finding ID: `F-FISHING-HOOK-CLIENT-OWNER-REACQUIRE-1.21.5-1.21.8`
- Status: candidate; UUID owner-resolution and direct client Player pull path are source-verified, while owner-respawn lifecycle, event timing and materiality remain pending.
- Slice routes: S7.2, S7.1; inventories INV-EXTERNAL, INV-STATE.
- A evidence: `Projectile#getOwner()` first uses a non-removed cached owner, then calls `findOwner(ownerUUID)`; `findOwner()` only queries a `ServerLevel` and returns null on a client level (A lines 64-78; `Projectile.java` SHA-256 `d8948903dc73e94ae8e0364eb5775e944b6edcb3de6662a7238b04399cfb6269`).
- B evidence: `Projectile#getOwner()` resolves its `EntityReference` against `this.level()` (B lines 62-68; `Projectile.java` SHA-256 `b13b4289ed88c68da9cf33a4c625e46a339d3bebf10e6ea7cfae5e28b6fd4d71`). If the referenced owner is removed, `EntityReference#getEntity()` replaces it with its UUID and calls `UUIDLookup#getEntity(UUID)` (B lines 45-64; `EntityReference.java` SHA-256 `e2b98f5488ac5e8b984b8da4044675a08c622989eff7090c3811126ca20b546d`). A/B `Level#getEntity(UUID)` uses the same lookup body at lines 721-723; source hashes are recorded in the owner-resolution route in `run.md`.
- Same-UUID replacement reachability: vanilla `PlayerList#respawn()` creates a new `ServerPlayer` in the respawn transition's target level from the old player's `GameProfile`, then restores player state and reuses its entity ID (A/B lines 405-411; `PlayerList.java` SHA-256 `9d92d51c73c79ddaf6997e05d51eb21433cdf3e107a5f51f4b5248f5ef4471c9` / `3ede172d032d66d3b0426b4299fe09b023d5b8628dc5dc19d1664395732ef4eb`). When the respawn target is the same dimension, this replaces the owner object in the same server level under the same profile UUID.
- Player reachability: the caught entity is synced to clients through `FishingHook#DATA_HOOKED_ENTITY`; `onSyncedDataUpdated()` resolves its entity ID in both versions (A lines 118-122; B lines 128-132). Server `FishingHook#retrieve()` applies its pull and broadcasts event 31 when `hookedIn` is present (A lines 442-450; B lines 453-461). The client handler responds to event 31 only when `hookedIn` is the local Player and calls `pullEntity()` (A lines 491-497; B lines 502-508). That unchanged method obtains the fishing-hook owner and, if non-null, adds `0.1 * (owner position - hook position)` to the target Player's delta movement (A lines 499-505; B lines 510-516; method-body SHA-256 `55cc5f961d8b18d603fb6ad74cb0888e6d0d08ee617d7f3858390a22c50f3f06`). The A/B `FishingHook.java` source SHA-256 values are `861776ebb8c85c0ae91fd83b4d1b74028a41289d908959c1bd3639651d1a4ca3` / `42eed1d0d62fb1aebf4283b591dcdbf5b766e2dba84d7ff853e2eee53f6bf105`.
- Exact candidate precondition: the FishingHook was spawned while its owner was client-visible; afterward, a remote hook owner is removed and re-created with the same UUID in the same dimension before the server discards the existing hook. The replacement is alive, holds a fishing rod and is within the 32-block squared-distance limit used by `shouldStopFishing()` (A lines 242-251; B lines 253-262). The client still has that hook with the local Player as `hookedIn`, receives the replacement owner, then processes event 31 before A's unresolved client hook is discarded. On that path A's client `getOwner()` returns null and does not add the pull vector; B can reacquire the owner by UUID and adds it. If the server discards the hook before replacement/reel, or if the client hook is discarded before event 31, this candidate path does not occur.
- Analysis: the authoritative server owner lookup reaches the same `Level#getEntity(UUID)` implementation in A and B, so the server-side pull is not claimed to differ. The candidate is limited to the client event's direct velocity prediction for the local hooked Player, with respawn ordering and later server correction still open.
