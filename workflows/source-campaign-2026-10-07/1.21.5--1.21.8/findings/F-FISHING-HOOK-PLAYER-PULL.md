- Player reachability: `FishingHook#canHitEntity()` delegates to `Projectile#canHitEntity()` for non-item entities; an eligible non-owner Player can be hooked. Server `onHitEntity()` stores that entity in `hookedIn` (A lines 266-270; B lines 277-281). On rod retrieval, `retrieve()` calls `pullEntity(hookedIn)` (A lines 442-448; B lines 453-459), and the unchanged `pullEntity()` adds `0.1 * (owner position - hook position)` to the target's delta movement (A lines 499-505; B lines 510-516; body SHA-256 `55cc5f961d8b18d603fb6ad74cb0888e6d0d08ee617d7f3858390a22c50f3f06`). While hooked, the hook is repositioned to the hooked entity and the tick returns before the changed gravity branch in both versions.
- Exact candidate precondition: a non-water fishing hook is on ground while it still has relevant movement or enters a grounded/bobbing trajectory where its subsequent vertical path affects an entity-hit sweep; that sweep differs between A and B and hooks an eligible Player. The player owner then reels the hook before it detaches, invoking the unchanged player delta-movement writer with the resulting hook position. This candidate is limited to the indirect changed trajectory-to-player-hit path; it does not claim `pullEntity()` or player travel math changed.
- Analysis: the guard removes a gravity write only in B for grounded or already-hooked states. The already-hooked state returns before this branch, so it does not directly alter the settled hook position or pull formula. The remaining grounded path can alter the next swept collision and thereby whether/when a Player is hooked; if so, the subsequent native pull changes that player's velocity. Exact reachable geometry and materiality remain to be established, so this stays a candidate.
