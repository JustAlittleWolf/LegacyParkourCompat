- Finding ID: `F-FISHING-HOOK-PLAYER-PULL-1.21.5-1.21.8`

- Player reachability: `FishingHook#canHitEntity()` delegates to `Projectile#canHitEntity()` for non-item entities; an eligible non-owner Player can be hooked. Server `onHitEntity()` stores that entity in `hookedIn` (A lines 266-270; B lines 277-281) while the current state remains `FLYING`. This callback runs from `checkCollision()` before the non-water gravity branch in the same `tick()`. A therefore subtracts gravity and moves the hook after capture; B sees `hookedIn != null`, skips gravity, and moves it with its prior velocity. On a later tick the hook first changes to `HOOKED_IN_ENTITY` and returns; a subsequent tick places it on the hooked entity. Rod use invokes `retrieve()` (A lines 442-448; B lines 453-459), which calls `pullEntity(hookedIn)`; the unchanged `pullEntity()` adds `0.1 * (owner position - hook position)` to the target's delta movement (A lines 499-505; B lines 510-516; body SHA-256 `55cc5f961d8b18d603fb6ad74cb0888e6d0d08ee617d7f3858390a22c50f3f06`).
- Server tick ordering: A/B `ServerLevel` ticks its entities inside `MinecraftServer#tickChildren()` (A lines 1019-1049; B lines 1020-1050); after the tick, the server loop calls `waitUntilNextTick()`, which drains `runAllTasks()` and continues processing queued tasks while waiting (A lines 696, 807-813; B lines 697, 808-814; `BlockableEventLoop#runAllTasks()` at line 108). Network packet handling uses `PacketUtils#ensureRunningOnSameThread()` to enqueue packet work on that server event loop (A/B `PacketUtils.java` line 21; identical SHA-256 `53f287b51315bff0be19f4a0de817c98610bb4c4b12c55f1b4f460adedae3f74`). `ServerGamePacketListenerImpl#handleUseItem()` (A line 1264; B line 1284) passes the held rod to item use, and unchanged `FishingRodItem#use()` (line 23 onward; identical SHA-256 `85c27f483d983034c39752dacfd9a76cea2f6e63d183268d412fe88140737666`) invokes server `FishingHook#retrieve()` when `Player.fishing` is present. So a reel packet handled in the post-hit wait interval can run after the hit tick and before the next world tick updates the hook attachment. The scheduler establishes a possible one-tick window; it does not establish typical network timing or impact magnitude. A/B `MinecraftServer.java` hashes are `d30b7d1b9a9b23a6ab1dc4b398faade368c3b3bfb8e67b66390c7075accab895` / `ab086f76da3a37c97a48335cf80cc545889269ad45e6d429bbd967a2f42186e0`; `BlockableEventLoop.java` is identical with SHA-256 `f4965b0b3c99fb3b6e3be71ca9e0191fc34435bf5535b0b660e8b6ab300fec77`.
- Analysis: this is a post-hit position delta from the same changed gravity guard, not a changed hit-registration rule. The direct authoritative Player pull formula is unchanged, but its hook-position input can differ if a reel packet is handled in the source-confirmed post-hit, pre-next-hook-tick interval. That ordering is reachable in the server task schedule; frequency and resulting movement magnitude remain unmeasured, and blind review remains open, so this stays a candidate.
