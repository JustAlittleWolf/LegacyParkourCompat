- Registration and reachability: both `Blocks` registries expose HopperBlock as `HOPPER`; the paired generic `Block.addCollision(s)` appends each intersecting box to the supplied list (A `Block.java` SHA-256 `ea10f05106a3cf7189aec85236a7ecf9c7106a717f37bed583b5ea4adeffa528`; B SHA-256 `e62ece80c6a7e7121346f65f8fdfd9b148c29441a27de9f568bba9afe1d84fe6`). `World.getCollisions` feeds entity movement collision resolution; axis-clipping consequences remain in COLL-01.
- Consumer closure: `Entity.move()` consumes this list in ordered Y/X/Z clipping loops, with each axis comparing every collision box against the same pre-axis shape and retaining the nearest permitted signed displacement; those min/max clamps are order-independent for the same box set. The same loops feed both step candidates. The other player-reachable `getCollisions` uses inspected for movement gating (`canMove` and B's pose-fit query) test only whether the list is empty, so append order is not observed there.
- Disposition: the source list order differs but the five-box candidate set is identical. Given the same other collision candidates, the changed north/east append order cannot change player clipping or step selection because the axis clamps are order-independent; emptiness predicates are also order-independent. This is a no-movement-difference disposition for this provider-order delta, not a claim that the full collision candidate list is equivalent.
