## Source-level difference

A computes each interpolated position component as `current + (target - current) / steps`. It computes yaw as `currentYaw + (float)wrapDegrees(targetYaw-currentYaw) / steps`, and pitch as `currentPitch + (float)(targetPitch-currentPitch) / steps`; the angle difference is converted to float before division. The decrement occurs before the position/rotation setters.

B computes `inverseSteps = 1.0 / steps` once, then calls `Mth.lerp(inverseSteps,current,target)` for XYZ and `Mth.rotLerp` / `Mth.lerp` for yaw/pitch, casting the resulting angle after interpolation. The helper sets position and rotation; `RemotePlayer.aiStep` decrements the counter immediately after the helper returns.

These formulas are mathematically equivalent over real numbers, but use different IEEE-754 operation order and angle precision. For example, for `currentX = Math.PI`, `targetX = 123456.789`, `steps = 3`, A's expression gives `41154.3573951024`, while the B `Mth.lerp` expression gives `41154.357395102394` in double precision.

## Reachability and consequence

Server position/rotation snapshots pass through client packet handlers to `LivingEntity.lerpTo`, then `RemotePlayer.aiStep` consumes the queued interpolation state over subsequent client ticks. This source difference can alter the rounded position/angle written during remote-player interpolation. It does not run for the local controlled player: `LivingEntity.aiStep` clears that player's `lerpSteps` before its ordinary interpolation branch, and LocalPlayer's own path is separately covered by S1.

Source-proven: the per-tick position/rotation calculation and setter/decrement order changed for remote players with pending interpolation. Predicted: intermediate client-side remote-player positions/rotations can differ at floating-point precision. No gameplay trajectory or server-authoritative position difference is claimed.
