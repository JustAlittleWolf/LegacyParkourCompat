## Source-level difference

Both versions enter this branch after movement distance passes `nextStep`, when the moved-over state is non-air and the entity is not in water. A requires an event-emitting support state and rejects a support state tagged `OCCLUDES_VIBRATION_SIGNALS`. B replaces that second condition with movement/support predicates: the entity is grounded, the requested vertical delta is exactly zero, it is in powder snow, or the support state is climbable or powder snow. B also supplies the current entity and `getBlockStateOn()` in the event context. The `GameEvent.STEP` dispatch condition and source context therefore differ within the core movement path.

## Consequence and uncertainty

Source-proven: under the respective guards, B can dispatch a step event in cases where A's support-block occlusion gate rejects it, and the event context can include an explicit affected block state. The changed branch contains no direct player position or velocity write. Predicted consequence: a reachable event listener may respond differently and change surrounding world state. No listener trajectory or resulting movement was simulated; resource and listener applicability remain unverified.
