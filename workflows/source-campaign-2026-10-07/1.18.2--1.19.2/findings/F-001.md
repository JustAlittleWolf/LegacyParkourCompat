## Source-level difference

A has no Swift Sneak registry entry, and `KeyboardInput.tick(boolean)` always uses the fixed `0.3F` for its slow-input branch. B adds a legs-slot Swift Sneak enchantment and computes a clamped factor from its level before the same input branch. Levels 1, 2 and 3 yield `0.45F`, `0.60F` and `0.75F`. At level zero, B remains `0.3F`. The slow-input predicate is `isCrouching() || isVisuallyCrawling()` in both releases. The changed expression runs before local movement consumes the sampled impulses.

## Reachability and dependencies

Local client tick -> `LocalPlayer.aiStep()` updates crouching state -> `isMovingSlowly()` -> `EnchantmentHelper.getSneakingSpeedBonus(this)` -> `KeyboardInput.tick()` writes `leftImpulse` and `forwardImpulse` -> the existing local movement consumers. Swift Sneak's level is read from the equipped legs slot. The vanilla `Entity.moveRelative()` / `getInputVector()` conversion has the same threshold, normalization and yaw operation order on both sides (A `Entity.java` lines 1151-1166; B lines 1170-1185; source hashes in the run ledger). This pair comparison does not establish that the mechanic first appeared in release 1.19.2.

## Consequence and uncertainty

Source-proven: while slow keyboard input is sampled and Swift Sneak is equipped, B writes larger lateral and forward input impulses than A. B's bundled ancient-city loot table contains a Swift Sneak enchanted-book entry; the A client jar has no matching table entry. Predicted consequence: subsequent player movement can receive stronger horizontal input in those conditions. No trajectory was simulated.
