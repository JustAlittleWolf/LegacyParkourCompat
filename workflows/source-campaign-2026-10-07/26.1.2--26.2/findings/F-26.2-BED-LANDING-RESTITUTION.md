## Source-level difference

This finding binds an exact, reachable local-player contact witness rather than treating every clipped landing as zero displacement:

1. At exact contact with an ordinary bed's collision top (`bed Y + 9/16`), a `ClientboundSetEntityMotionPacket` supplies the local player a Y velocity of `-1.0`. The paired packet codec preserves this value exactly; the client handler looks up the entity and assigns the decoded vector through `Entity.lerpMotion`. The local player inherits that `Entity` path. No gravity modifier or movement effect is active. The paired pre-input vertical dead-zone preserves `-1.0` because `abs(-1.0)` is not less than `0.003`.
2. `Player.travel` selects ordinary `LivingEntity.travel`; the player is not a passenger, swimming, or ability-flying, so it calls superclass travel. `travelInAir` computes horizontal friction, then `handleRelativeFrictionAndCalculateMovement` applies input and calls `Entity.move` before `travelInAir` subtracts gravity or applies vertical drag. With no horizontal input and exact bed-surface contact, collision resolves `movement.y = 0.0`; the packet delta remains `currentMovement.y = -1.0` until restitution. The B guard passes because `-currentMovement.y == 1.0 >= getEffectiveGravity() == 0.08`; the bed is not suppressed or bounce-tagged.

For B, `portionWithMovement = 0.0 / -1.0 = -0.0`; gravity compensation is `-0.0 * 0.08 = -0.0`. The player is not an omnidirectional air mover. B casts the default `AIR_DRAG_MODIFIER` value `1.0` to `float`, computes `computeModifiedFriction(0.98F, 1.0F) = 0.98F`, and evaluates `Mth.lerp(-0.0, 1.0, 0.98F) = 1.0`. B writes `(-0.0 - (-1.0)) * 1.0 * 0.75F = 0.75`. A writes `-(-1.0) * 0.66F * 1.0 = 0.6600000262260437` (`0.66F` widened to double); these response values differ by `0.0899999737739563`.

The same `travelInAir` call then subtracts gravity and applies vertical drag after the collision response. For a player with `shouldDiscardFriction() == false`, A uses `verticalFriction = 0.98F`; B casts the default `AIR_DRAG_MODIFIER` attribute `1.0` to float and computes `verticalFriction = computeModifiedFriction(0.98F, 1.0F) = 0.98F`. With Java double subtraction followed by multiplication by the widened float, A writes `(0.6600000262260437 - 0.08) * 0.98F = 0.56840003676414541`; B writes `(0.75 - 0.08) * 0.98F = 0.65660001277923585`. Starting instead from zero Y movement, both endpoints first move with zero, then subtract `0.08`, then apply `0.98F`, storing `-0.07840000152587891`; this is why `-0.08` is not used as the next movement request, and that value is below B's `0.08` restitution threshold. This traces the exact tick order and casts; no runtime trajectory is claimed. Positive-gap landings generally have nonzero resolved movement and are outside this exact-contact calculation.

This finding assumes the ordinary local-player BOUNCINESS default (`0.0`) or a value no greater than the bed restitution; the synced attribute, if externally modified above `0.75`, raises B's restitution through the stated `max` formula. The later same-tick output assumes default `AIR_DRAG_MODIFIER` (`1.0`), default gravity (`0.08`), no Slow Falling effect, and friction is not discarded. Crouch/shift suppression and B's explicit suppression tag bypass the bed bounce condition.

## Reachability and dependencies

The client `LocalPlayer` reaches `Player`/`Avatar`/`LivingEntity` movement and its `Entity.move` collision handling. `Player.canSimulateMovement()` returns true for the local client player. A bed support is selected as the effect block for the clipped landing. The rewritten state is player Y velocity, consumed by subsequent local travel/ticks. B's new BOUNCINESS attribute is part of living attributes and syncable; its base default is zero. The paired bed registration is source evidence for the `0.75F` block value. No damage calculation is emulated or compared; A's bed `fallOn` damage multiplier is outside this finding.
