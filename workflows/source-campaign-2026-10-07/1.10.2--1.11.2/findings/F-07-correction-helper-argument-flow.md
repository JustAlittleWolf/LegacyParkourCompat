# Correction: F-07 is withdrawn after rechecking the boolean query argument flow

- Supersedes the conclusion in `F-07-player-pose-fit-stale-outer-stair-shape.md` (immutable snapshot, commit `bd95d35bd9a9a0ae468b9cf035f99f08639e91c0`). Keep that file unchanged as an audit record; it is no longer an accepted finding.
- Evidence: exact B source `World.java::getCollisions(Entity,Box,boolean,List)` declares the parameter `enforceWorldBorder`. `World.getCollisions(Box)` passes `true` to it. Within the helper, block dispatch is `blockState3.addCollisions(this, pooledMutable, shape, collisions, entity, false)`, so `false` is the `forceShape` argument for every block provider.
- In B, `StairsBlock.addCollisions`, `PaneBlock.addCollisions`, and `ChorusPlantBlock.addCollisions` resolve virtual neighbor-derived properties when `!forceShape`; the helper passes `false`. Their boolean-query path therefore resolves those properties, as does A's `World.getCollisions(Box)` path. The prior report misread the wrapper's `true` as the provider flag.
- The F-07 outer-stair example does not produce different collision results: B resolves `OUTER_LEFT` before selecting collision boxes, matching A for the same block and neighbors. Withdraw the stale-straight-shape claim and all player-size consequences derived from it.
- This correction does not close the separate World scan-boundary difference. A excludes both padded y end rows on x/z perimeter cells; B excludes only the upper row. F-06 proves one reachable moved-fence collision candidate. Whether that query difference affects pose-fit or dismount cases remains open under `D-COLLISION`.
