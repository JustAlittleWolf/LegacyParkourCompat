## Source-level difference

After `Entity.move` resolves movement, it calls `tryCheckInsideBlocks`, whose wrapper calls `checkInsideBlocks`. Both versions use the resulting entity AABB to construct min/max block positions and iterate the covered cells inclusively before invoking each block state's `entityInside` callback. A insets all six bounds by `0.001`; B insets them by `1.0E-7`. Therefore a cell just across a horizontal AABB edge can be visited in B but omitted in A when the overlap is greater than `1.0E-7` and less than `0.001`.

Both versions register the same Honey Block and have byte-identical Honey Block callback code. Its collision shape is `Block.box(1.0, 0.0, 1.0, 15.0, 15.0, 15.0)`, so the solid X/Z bounds begin `1/16` inside the cell. `Block.box` divides each coordinate by `16.0`; the shape is not solid in the first `1/16` of the cell next to each horizontal face. The normal collision path gathers the Honey shape and resolves movement against its voxel cells; the box in the witness below remains entirely in this side gap, so downward movement is not clipped by Honey.

When the additional B cell is Honey, `entityInside` calls `isSlidingDown`. That method returns false for a grounded entity, an entity above block Y + `0.9375 - 1.0E-7`, or vertical velocity at least `-0.08`. It then requires either horizontal center separation plus `1.0E-7` to exceed `0.4375 + entity width/2.0F`. For the default player width `0.6F`, the side-overlap witness below satisfies that center-distance test. The callback calls `doSlideMovement`, which immediately sets Y velocity to `-0.05`; when prior Y is below `-0.13`, it scales X/Z by `-0.05 / y`, otherwise preserves X/Z. It then resets fall distance. These callback predicates and writes are identical; the difference is whether the Honey cell is visited.

## Reachability and dependencies

The paired sources provide a vanilla command-to-client-motion witness for the overlap, rather than assuming the narrow box state. In a loaded interior chunk containing Honey at block `(1,64,1)` and air in the other cells traversed by the player box, an authorized same-world `/tp @s 0.7005 64.9 1.5` supplies absolute in-bounds coordinates. `TeleportCommand.teleportToPos` leaves the position-relative flags empty for absolute coordinates, then `performTeleport` passes those values to the same-level player's connection. The command's spawnable-bounds guard accepts block position `(0,64,1)`. `ServerGamePacketListenerImpl.teleport` sends the absolute coordinates; `ClientPacketListener.handleMovePlayer` sets the client player's coordinates, clears velocity on absolute axes and rebuilds the box (`absMoveTo` in A, `setPos` in B). The x coordinate is far inside both entity coordinate clamps. The client handler does not write the local `onGround` flag; take the client player airborne before this correction.

`EntityType.PLAYER` registers width `0.6F` and height `1.8F`. `EntityDimensions.makeBoundingBox` uses the float expression `width / 2.0F` and places the bottom at the entity Y. At the stated target, the resulting box is approximately X `[0.4005,1.0005]`, Y `[64.9,66.7]`, Z `[1.2,1.8]`; retain the source float half-width and coordinate arithmetic rather than replacing `0.6F` with a double literal. The Honey collision shape begins at X `1 + 1/16 = 1.0625`; the box's maxX `1.0005` is before that solid interval. With zero horizontal input, there is no Honey X/Z collision, and no other solid shapes in the witness arrangement. `Entity.collide` therefore leaves the requested downward displacement uncut; `Entity.move` updates position/box and, after ground/fall/step callbacks, calls `tryCheckInsideBlocks`.

After the correction, client X/Z velocity is zero. `LocalPlayer.serverAiStep` copies zero input impulses to `xxa`/`zza`; `LivingEntity.aiStep` passes those fields to `travel`. With no fluid, flight, Slow Falling, Levitation or no-gravity state, the ordinary air branch moves with the prior velocity and then applies `v := (v - 0.08) * 0.98F`. On the first pass from zero, `v1 = (0.0 - 0.08) * 0.98F` (about `-0.0784`); on the second, `v2 = (v1 - 0.08) * 0.98F` (about `-0.1552`). The second pass's Honey gate still rejects `v1 >= -0.08`; the third movement consumes `v2` and reaches approximately Y `64.6664`, so the post-move player is still below Honey's `64.9375 - 1.0E-7` Y limit and is not on ground. This is an airborne downward player motion produced by the paired vanilla gravity path.

For the third movement, source AABB maxX is approximately `1.0005`. A scans `floor(maxX - 0.001) = floor(0.9995) = 0`; B scans `floor(maxX - 1.0E-7) = floor(1.0004999) = 1`. `BlockPos(double,double,double)` delegates to the paired floor conversion, and the inclusive X/Y/Z loops therefore visit cell `(1,64,1)` only in B. The min/max Y range is interior and both versions' `LevelReader.hasChunksAt` height and loaded-chunk checks pass for the already loaded same chunk. The Honey callback sees `abs(1.5 - playerX) ≈ 0.7995`, greater than `0.4375 + 0.6F/2.0F ≈ 0.7375`, and downward velocity `v2 < -0.08`; B writes the Honey response while A never calls it. The following base `Entity.onInsideBlock` method is empty in both versions.

This closes a source-reachable entry-state producer for a vanilla command witness and the callback caller into the final box. It does not claim that an ordinary walk from outside Honey's collision shape ends in this narrow band; that broader entry path remains unestablished. The movement response itself is conditional on the stated world/command/player preconditions.
## Consequence and uncertainty

Source-proven: the in-bounds vanilla command and subsequent ordinary air-movement source can produce the stated post-move box and velocity in a loaded Honey/air arrangement. On the third movement callback B writes the immediate Honey response (`Y = -0.05` here because `v2` is below `-0.13` and X/Z are zero) and resets fall distance; A omits that callback. `LivingEntity.travel` reads the post-move velocity and later applies gravity and `0.98F` drag in the same call, so `-0.05` is not the end-of-tick Y velocity. No runtime trajectory or measured state was observed.
