## Source-level difference

At B's default `STEP_HEIGHT` value `0.6`, the ordinary player step limit matches the A base limit. A nondefault B attribute value changes `LivingEntity.maxUpStep()` and therefore the vertical candidate in `Entity.collide`; the same ordered candidate and tie-break algorithm then operates over a different height. A's player does not read an equivalent attribute.

## Reachability and dependencies

The client player inherits `LivingEntity.maxUpStep()` and `Entity.move()` calls `Entity.collide()` on its movement path. The B attribute is synchronized state; this finding does not claim vanilla map data or the client alone sets a nondefault value. The passenger-control minimum of `1.0F` can mask lower attribute values for a ridden entity and is retained in both versions.

## Consequence and uncertainty

Source-proven: B can use a step-up limit other than A's base player limit when the synchronized attribute differs from `0.6`. Which obstacles can be cleared and the resulting trajectory have not been runtime-tested. This attribute is modern-only; do not project it into A-era behavior.

## Handoff

Independent delta: B's synced `STEP_HEIGHT` value is consumed directly by the shared step-up collision solver. Default `0.6` preserves the A limit; nondefault values do not.
