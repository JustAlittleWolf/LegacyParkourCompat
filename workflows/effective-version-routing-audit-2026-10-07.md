# Effective movement-version routing audit

Date: 2026-10-07

This is an implementation-side static trace for integration. Keep it separate from blind source-discovery reports and do not send implementation-derived observations to source owners before full-pair freeze. No game, server, test, TAS, or runtime check was performed.

## Static route

1. **Client selection.** Mod Menu opens `MovementVersionScreen` (`src/client/java/me/wolfii/legacyparkourcompat/config/ModMenuIntegration.java:6-10`). The screen lists `CURRENT` plus historical profiles (`MovementVersionScreen.java:76-89`). Selecting a row only changes the screen's draft; `onClose`/`removed` commit it through `MovementVersions.select` (`MovementVersionScreen.java:128-155`). Thus the screen must be closed before the controller selection changes. Client selection is session-memory only (`config/version/MovementVersions.java:10-18`); it is not restored after a game restart.
2. **Version mapping and enablement.** `ParkourVersion.of("1.8.9")` maps the patch to the `V1_8` profile; that group's canonical ID is `1.8` and its display label spans `1.8-1.8.9` (`api/ParkourVersion.java:50-80, 141-154, 194-222`). `CURRENT` resolves to native vanilla and an empty profile. Historical profiles are currently partial: the enum constants use the default `fullyImplemented=false` constructor and the screen shows a partial warning (`ParkourVersion.java:87-101, 233-244`; `MovementVersionScreen.java:157-180`). The screen has no per-mechanic toggles; selecting `CURRENT` disables all historical changes. The static `MovementVersions.setWanted` API has no call site in `src/`.
3. **Controller and per-player route.** `MovementVersions.apply` calls `MovementController.select` unless a remote modded server has forced its choice (`config/version/MovementVersions.java:187-202`). The controller canonicalizes a profile that is not older than this running game to `CURRENT`, rebuilds the global profile, invalidates the collision cache, increments the epoch, and notifies listeners (`impl/MovementControllerImpl.java:82-97, 152-194`). `versionFor(entity)` uses a UUID override for `Player` entities when present, otherwise the global selection (`MovementControllerImpl.java:71-79`). Non-player entities stay vanilla (`mechanic/MovementRuntime.java:26-39`). `profileFor` uses the cached global profile or resolves the per-player version (`MovementControllerImpl.java:119-130`).
4. **Resolved mechanics and hooks.** Providers are registered from the `legacyparkourcompat:movement-change` entrypoint during common initialization (`LegacyParkourCompat.java:17-29`; `fabric.mod.json:20-57`). `ChangeResolver` selects the closest applicable registration independently per `MechanicKey` (`impl/ChangeResolver.java:21-34`). Mixin hooks call `MovementRuntime.find`, which checks player/enabled state and resolves the profile on each hook lookup (`mechanic/MovementRuntime.java:30-35, 59-75`). The mixin config lists common and client hooks and uses `defaultRequire: 1` (`legacyparkourcompat.mixins.json:1-27`). This establishes the static local route from a selected version to hook lookup; actual runtime mixin application remains unverified.
5. **Dedicated-server configuration and authority.** The dedicated server reads `config/legacyparkourcompat.properties` key `movementVersion`; a missing file is created with an empty value, which means vanilla, and invalid IDs also disable historical changes (`config/ServerMovementConfig.java:15-29, 38-80`). During configuration, a server with the mod sends its global selected profile to the client (`network/ParkourHandshake.java:24-37`). The client selects that profile, locks the remote UI, queues a visible forced-version chat notice, and sends an acknowledgement (`LegacyParkourCompatClient.java:20-42, 65-84`; `network/ForcedVersionNotifier.java:16-31`). The forced profile is therefore authoritative over the client's previous local selection. The version screen shows a forced label and cannot change a remote server's choice (`MovementVersionScreen.java:140-155, 164-180`).
6. **Via-translated server without this mod.** When the server has no force-packet receiver, the client may infer the remote server's translated version and call the controller directly (`LegacyParkourCompatClient.java:44-56, 72-81`; `network/ViaVersionAccess.java:39-48`). This route is not a server force and does not update the `MovementVersions` UI model.

## Separate routing/configuration findings

- **A modded server can explain “I selected 1.8.9 but saw no change.”** The dedicated server's default config is vanilla. On a server with the mod, its configured global profile replaces the client's local selection; check the server config and the server/client forced-version logs/chat before attributing the result to missing movement code. A local profile shown before joining is not evidence of the profile after the server handshake.
- **Via selection can be misrepresented by the UI.** The Via path calls `MovementController.select` directly but leaves `MovementVersions.wanted/input` unchanged. The screen derives its selected row from those fields (`MovementVersions.java:130-139`), then commits that row when closed (`MovementVersionScreen.java:140-145`). It can therefore display a stale local choice (or `CURRENT`) while Via has selected another profile; opening and closing it can overwrite Via's inferred profile. This does not affect ordinary hooks until the user opens/closes that screen.
- **The handshake acknowledgement does not prove the client applied the requested profile.** The client acknowledges the raw payload ID immediately after `select(required)` (`LegacyParkourCompatClient.java:67-70`), while `select` may canonicalize an unsupported/non-older profile to `CURRENT` (`MovementControllerImpl.java:82-90, 152-160`). The server compares the echoed string to its own global ID and logs success on equality (`ParkourNetworking.java:17-35`), so it can miss that fallback. This matters across clients whose supported profile range differs.
- **The public per-player server override is not sent in the handshake.** `MovementController.selectFor` and `versionFor` support UUID overrides (`api/MovementController.java:65-73`; `MovementControllerImpl.java:71-79, 99-111`), but no in-repository caller of `selectFor` exists. `ParkourHandshake` always sends `selectedVersion()`, not `versionFor(the connecting player)` (`network/ParkourHandshake.java:24-35`). If an external server mod uses `selectFor`, client and server profiles can diverge.
- **A row selection is a draft until the settings screen closes, and the client choice does not persist across restarts.** These are expected lifecycle rules, but can look like a selection failed if the user reads the row before closing or expects it to survive a relaunch.

## Live switching and already-sneaking/moving state

The controller selection is volatile and `select` replaces the cached global profile immediately. Hooks that call `MovementRuntime.find` use the new profile on their next invocation, including player-context collision shape lookups. There is no need to restart the world for those dynamically looked-up hooks. A hook that has already copied profile-dependent state into a player field can retain that value until its next update.

The controller increments `epoch`, and the public API comment says in-world players can refresh pose/dimensions on the next tick (`api/MovementController.java:83-87`). However, repository search finds no consumer of `MovementRuntime.epoch()` outside its definition, and no mixin calls `refreshDimensions` or dispatches `PlayerDimensionsBehavior`. The behavior exists in the hook interface and a `SwimmingDimensions` implementation only. Therefore the static code does not establish a live pose/AABB resize when switching while already sneaking. Verify such a state after a fresh pose transition or add a narrowly scoped diagnostic; do not infer it from the selected-profile log.

## Observable manual routing witness

No witness was executed. When a later manual pass is authorized:

1. For a local-world check, select a historical profile in Mod Menu and close the screen. Confirm the `legacyparkourcompat` INFO log `Selected movement version ...` names the canonical target and its resolved mechanic keys; `ActiveMovementProfile.describe()` is the format for that log (`api/ActiveMovementProfile.java:56-73`). The screen's `CURRENT` row means native movement; historical rows should carry the partial warning. This confirms controller/profile resolution, not that a particular Mixin callback ran.
2. For a multiplayer check, inspect the dedicated server's `movementVersion` property and `Accepting ... forcing parkour version ...` log, then the client's `Server forced parkour version ...` log, forced-version chat notice, and gold forced label in the screen. Do not use the pre-join local row as the effective server profile. For Via without the mod, the client log `ViaFabric is translating this connection; selecting parkour version ...` identifies the inference path, but the current screen can be stale.
3. To prove an individual hook invocation, the current logs/profile summary are not enough. The minimal diagnostic is a one-shot, opt-in DEBUG entry at the selected hook after `MovementRuntime.find` resolves it, recording the player UUID, mechanic key, effective profile ID, and returned behavior class. Keep it limited to one controlled invocation to avoid per-tick log spam. Pair it with a source-confirmed movement witness only after its finding snapshot is independently accepted.
4. For a live switch while already moving, close the selection screen, then confirm the next controlled hook log uses the new profile. For crouch dimensions, first verify the refresh-path gap above; the selected profile alone does not prove that the existing bounding box changed.
