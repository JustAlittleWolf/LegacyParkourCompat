# Historical Minecraft source decompilation

`buildSrc` implements the root `decompileMinecraft` Gradle task. It downloads the requested Minecraft client, applies an available mapping set, and runs Vineflower in a forked Java 25 process. Its output is reference source for matching historical movement math; it is not part of the mod at runtime.

Run the task from the repository root:

```powershell
.\gradlew.bat decompileMinecraft
.\gradlew.bat decompileMinecraft --versions=1.16.5
.\gradlew.bat decompileMinecraft --versions=1.13.2 --mappings=feather,legacy-yarn
.\gradlew.bat decompileMinecraft --versions=1.16.5 --decompiler-heap=2G
.\gradlew.bat decompileMinecraft --versions=1.16.5 --force
```

The default set is `latest,1.8.9,1.12.2,1.13.2,1.14.4`. `--versions` takes comma-separated exact release IDs or `latest`; it does not remap a requested patch version. `-Pversions=` and `-PminecraftVersions=` are alternatives. Every worktree defaults to the primary checkout's ignored `decompiled_minecraft/<version>/<mapping>/` directory. Downloads and intermediates live in that checkout's persistent `.minecraft-decompile-cache/`, outside `build/`.

`--mappings=auto` is the default. It uses official Mojang mappings when published, prefers Ornithe Feather through 1.12, and falls back to Yarn for later releases without official mappings. The 1.13.2 auto profile produces both `ornithe-feather` and `legacy-yarn`; 1.14.4 produces both `mojmap` and `yarn`. Unobfuscated releases are decompiled as published. For a specific comparison, pass a comma-separated set from `mojmap`, `legacy-yarn`, `yarn`, `feather`, and `unobfuscated`. The default decompiler heap is `4G`; `--decompiler-heap` accepts values such as `2G` or `2048M`.

`DecompileMinecraftTask` owns the Gradle options and fork. `MinecraftDecompileMain`, `MinecraftDecompileEngine`, and `MojangMeta` resolve releases, mappings, and decompilation; the remaining classes handle output and logs. Keep version and mapping resolution here rather than in the movement runtime. Use the generated source as the primary reference for exact casts, operation order, and floating-point expressions. Do not use online mapping lookups.

## Sharing sources between worktrees

The default root is derived from `.git` and Git's `commondir` pointer, so it does not depend on a user's directory name or the worktree location. A normal checkout uses its own root. Unusual bare/separate Git directory layouts cannot infer the primary checkout and require explicit overrides. Pass `--output-root=<absolute-directory>` and `--cache-directory=<absolute-directory>` for a separate pair; relative overrides resolve against the invoking project. Output and cache directories must be distinct. No task copies or migrates existing worktree sources.

Assign one preparation owner. The engine holds OS file locks in both roots for the entire invocation and fails immediately if another writer holds either lock. Researchers only read published sources. Changing the source tree while researchers use it still requires coordination: directory replacement has a short publication gap, and locks protect writers rather than readers.

Completed sources are reused by default without remapping or decompilation. Trees with `.decompile-provenance.json` are checked against the current input, tool, runtime and source hashes. A mismatch fails and requires inspection followed by deliberate `--force` regeneration. Legacy trees without a manifest are checked for required movement files, retained and reused with an explicit unverified-provenance warning. Reuse never manufactures a provenance claim for legacy output.

`--force` regenerates an exact version with the same pinned inputs; it does not refresh mapping metadata or artifacts. It writes into a sibling staging directory, requires zero Vineflower ERROR reports, checks required movement classes and creates a provenance manifest before publishing. Failed classes or methods abort publication even when the required movement filenames exist. The old tree is retained in a sibling `.<mapping>.previous-<id>` directory, including legacy trees. Generation failures remove only staging. Publication uses atomic directory moves and rolls back the previous tree on ordinary failure. An abrupt process/host failure between moves may leave the previous tree in its retained directory; the preparation owner must restore it before resuming readers. There is no automatic migration or backup deletion.

Exact version metadata and downloaded artifacts are pinned on first successful use with URL and SHA-256 sidecars; Mojang-provided SHA-1 values are additionally verified. Community metadata is cached before selecting a stable/highest build, fixing the mapping artifact for later runs. Existing cache artifacts get a local content pin on first use, which establishes a baseline rather than proving their historical origin. Missing or modified pinned artifacts fail rather than silently changing the input. Libraries cannot be silently omitted after a download failure.

The audited 1.8.1 Feather enum-helper ordering pins the ordinary mapped archive by a canonical content digest rather than its ZIP-file hash. ZIP timestamps and other container metadata can vary between identical remaps; the digest sorts entry paths and hashes each UTF-8 path and uncompressed content with explicit length framing, rejecting duplicate paths. Raw client, Tiny mapping and Feather artifact inputs retain their exact SHA-256 gates. The order stage recognizes flat synthetic enum helpers from their class shape, adds dependencies for every direct `GETSTATIC [I` consumer, and stably topologically reorders class-entry slots. It rejects nested-class metadata and cyclic or incomplete dependency graphs. A path-and-uncompressed-byte comparison plus the same canonical digest verifies that the ordinary mapped archive's contents are unchanged by ordering. The original 59 Vineflower diagnostic bindings remain an independent input gate.

The exact 1.8 Feather build.2 archive uses the same byte-preserving helper-order operation under separate raw-client, mapping-artifact, Tiny and canonical mapped-content pins. Its 2,497 classes are also flat, with no nesting metadata. The 1.8 and 1.8.1 cache outputs and pipeline identities remain separate. Strict decompiler error, failed-method, required-source and provenance checks apply after ordering.

The Mojang release catalog is a separate mutable discovery index with no permanent content pin. It downloads when absent, refreshes once if a requested exact ID is missing, and refreshes on every `latest`/`latest-snapshot` invocation. Existing exact-version metadata, artifacts and community-mapping pins remain fixed when the catalog changes. Use exact version IDs for reproducible research and forced regeneration: a moving alias deliberately resolves again before selecting the exact version. To adopt newer pinned version metadata or community mapping builds, prepare a deliberate new cache/output pair with the overrides and compare evidence before choosing it as the shared root. `--force` alone does not change those pins.

The manifest records the complete input URLs/hashes, decompiler/remapper classpath content hashes, pipeline options, JVM/vendor/OS identity and relative source hashes. Single-thread remapping/decompilation, fixed JVM locale/timezone/encoding and UTF-8 LF output reduce environment-dependent variation. A forced run with identical recorded provenance must reproduce the same source hashes or publication fails. This check detects divergence; it does not establish reproducibility across different toolchains or environments, nor does source completion prove movement parity. Campaign preparation markers remain a separate evidence/coverage decision and are not written by this task.
